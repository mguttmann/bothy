### Added

- Computer sessions (CU-03, docs/spec/27-computer-use.md): with `host_service.computer_use` the host
  service opens the local channel to the computer helper (peer rule of 27 9.4, refused peers logged
  with `computer_peer_refused`), mirrors its enablement into the `report` object `computer`,
  handles `computer.open`, `computer.close` and `computer.disable`, checks message 1 of the data
  connection `/api/v1/hosts/computer-sessions/{session_id}/stream` with the prologue
  `bothy-computer/1` and the attach token (`computer-session+jwt`), holds one controller per host,
  pauses while the screen is locked, maps coordinates with scale IDs, sends images in chunks at
  the Noise limit (only in memory), and reports `computer.started`, `computer.state` and
  `computer.ended`.
- The frame types `0x20` to `0x25`; `frame.Decode` takes the session kind, so computer frames are
  refused on a terminal session and the reverse.
- Configuration keys `host_service.computer_use`, `host_service.computer_frame_max_bytes` and
  `host_service.computer_test_peer` (Linux, tests only); `computer_use` is refused together with
  `host_service.owner_account`.
- `bothy-host doctor` prints a section `computer` after the checks (no HD check).
- `bothy-host install` creates the folder of the helper endpoint when `host_service.computer_use`
  is set.
- A Linux test backend of the helper (`test/computer_backend/`, Python with python-xlib and XTEST)
  and a fixture app for the end-to-end test of computer use.

- With `host_service.computer_use` the `report` carries the object `computer`; without the key
  the report is unchanged.

- A computer-use-only host (`host_service.computer_use` without session users) starts: the
  doctor reports `session_users_empty` and `peer_check_unavailable` as warnings there, and the
  host gives no terminal session (D-CU-03-13).

### Fixed

- The Windows computer helper opens the host service's pipe with only the rights its DACL grants
  interactive users; it asked for `GENERIC_WRITE`, was refused with error 5 and never connected.
  It grants the service account query access to its own process, which the host service needs to
  bind the connection to the helper process (before, the refusal `no_binding`).
- On macOS the host service reads the helper's executable with `proc_pidpath`; `kern.procargs2`
  is closed to other users, so every helper was refused.
- `computer_peer_refused` carries the refusing step under `reason`; `computer_helper_connected`
  and `computer_helper_gone` log the helper's connection, and the Windows helper writes its
  channel changes to `%LOCALAPPDATA%\bothy-computer-helper\channel.log`.
- The Windows MSI starts the helper in the console session right after the install
  (`start-computer-helper.ps1`), as the macOS postinstall already did.
