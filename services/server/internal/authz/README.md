## Storage (M1-27)

Migration `migrations/00005_authz_groups_grants.sql` (M1-27) creates the three tables exactly as 03 section 4.3
states, with named constraints (`grants_subject_shape_check`, `grants_bot_limits_check`,
`grants_host_shape_check` and the others) that the adapter maps to fields.

- **Deferred foreign keys.** The target tables do not exist yet, so these columns are plain `uuid`
  until the migration that creates each table adds the key: `groups.provider_id ->
  identity_providers(id)` (M1-36), `grants.target_space_id -> spaces(id)` (M1-52),
  `grants.target_channel_id -> channels(id)` (M1-53), all `ON DELETE RESTRICT`; `grants.target_host_id
  -> hosts(id)` exists since M2-39 (migration `00028_terminal_hosts.sql`). Until then no code path
  creates space or channel grants.
- **Immutability trigger** `authz_grants_immutable` (BEFORE UPDATE ON `grants`, SQLSTATE `23514`):
  allowed are only the revocation (`revoked_at`, `revoked_by`, `revoke_reason`, once, with
  `revoked_at` set) and setting `expiry_reminded_at` or `expiry_reported_at` from NULL. Every
  other change raises, including a second revocation; the comparison covers the whole row, so a
  column a later migration adds is immutable by default (R-DM-09).
- **People only.** `group_memberships.user_id` references `users(principal_id)`, so agents and apps
  cannot be members (R-DM-07).
- **Bots.** `grants_bot_limits_check` refuses `trigger` and any capability beyond `upload` for agent
  and app subjects (R-DM-08, R-DM-20); `CheckCreate` refuses them first with
  `subject_kind_not_allowed`.
- **Subject kind.** The database does not check that `subject_principal_id` has the kind of
  `subject_kind`; the use case checks it through `PrincipalSource` (M1-48) and the snapshot caps
  rights by the real kind (M1-28).
- **Privileges.** `bothy_app` has `SELECT, INSERT, UPDATE` on the three tables, no `DELETE`: the
  rows are history. A retention job that must delete (M7) grants it in its own migration.

## Delivery mode and Observe (M1-65)

`Observe(ctx, LogEvent)` is called by the log tail of every api process for each durable event in
`seq` order, before the gateway hub sees it (`app/observe.go`):

- Every event raises the highest permission version seen in the log. A delivery snapshot built at an
  older version is rebuilt at its next delivery check. The key is this process-wide version, not a
  floor per principal, because a permission change without a difference of visible targets writes no
  `access.changed` (04 8.2), for example `token.revoke`; the next event of the log carries the new
  version (DECISIONS M1-65).
- `access.changed` also forgets the delivery snapshots of its audience.
- `channel.created`, `channel.updated`, `channel.archived`, `space.archived` and `thread.moved`
  advance a process-wide structure generation; snapshots of an older generation are rebuilt
  (DECISIONS M1-65). `channel.settings_changed` does the same, because the channel facts carry
  the mention switches `agent.invoke` evaluates at delivery time (DECISIONS D-M2-02-8).
- The project facts of `agent.invoke` (`ChannelFacts.ProjectBound`, `ProjectReady`, M2-03) are
  read fresh even inside a structure scope, because a readiness change writes no event
  (DECISIONS D-M2-03-11).

`authorize.Delivery(ctx)` marks the checks of the hub and the gateway catch-up: the snapshot is
validated against that state instead of reading `permission_version` per check; a rebuilt snapshot
reads the current database state. Delivery implies `Filter(ctx)`, so a denial writes no audit entry
(07 4.2, R-AZ-04); requests and ops keep auditing denials. A revoked credential answers
`unauthenticated`, which the hub turns into `4012`.

Tests: `TestAuthzObserve_AccessChangedRaisesFloor`,
`TestAuthzObserve_NewRightsVersionInvalidatesWithoutAccessChanged`,
`TestAuthzObserve_StructureEventInvalidates`, `TestAuthzObserve_SettingsChangedAdvancesGeneration`,
`TestAuthzDelivery_DenialWritesNoAudit`.

## Check without a request (M2-08, R-AZ-29)

`actor.Recheck(person)` builds the principal of a check the server runs for a person without the
person's request: kind `user`, the marker `RecheckPrincipal` and nothing else. `Authorize` refuses
the marker with an internal error for any action other than `agent.invoke`, `push.deliver`
(M3-19: the hint check of the worker consumer `push` and of the job `notify.push_send` is a check
without a request, R-AZ-31), `command.invoke` and `interaction.create` (M2-25: the re-check of the
job `runs.app_dispatch` before a request to an app) and when the principal carries a session,
device, token, installation, "view as" or acting-for binding. Liveness comes only from the principal status
(`principal_inactive`, `principal_pending`); the owner status comes from the current owner list
without a session (the exception to R-AZ-14 and 05 2.3 point 1). The snapshot has its own cache key
(`cacheKey.recheck`), so no request principal of the same person, a personal token included, ever
gets the owner snapshot; the version is the one the caller pins, also in delivery mode. The
caller is `runs.Delivery` before every invocation-bearing delivery to an agent (D-M2-08-1) and,
since M2-25, the job `runs.app_dispatch` in filter mode without audit, for a person who ran an app
command or operated an app component; an agent or app that did so is re-checked as itself, with
its kind from the directory and, for an app, the job argument `person_installation_id`.

`InvokeFacts.NewThread` (M2-08): the auto thread of the trigger is decided with the channel's
main-thread mention rule ("in the main thread and for new threads", 05 section 5 point 3), not
with `thread_require_mention`.

A personal event whose receive action takes the principal kind `agent` (`agent.events.consume` of
`agent.invocation`, 05 section 6) is decided on its audience only for the page reads of the agent
consumer engine (`sync.PageInput.AgentConsumer`), which pass every such event through
`runs.Delivery`: sync then sets `EventScope.AudienceID` after it matched the audience with the
receiver, and `eventTarget` adds the agent of the audience as the last candidate. The generic
catch-up `listEvents` never sets it, so an agent never gets an invocation there (D-M2-08-14).

`Scope(actor.Recheck(person), push.deliver)` lists the channels the person reads, with the owner
status from the current owner list (the badge of M3-19 design note 16); a disabled or pending
person gets the error of its liveness decision.

## Recipients of hints (M3-19)

`authz.Recipients.Readers(ctx, channelID)` (`recipients.go`) is implemented on the `Authorizer`
that `internal/wire` builds (`app/recipients.go`), because it reuses the candidate reads of "who

## Action catalogue (M1-25)

The closed catalogue of [docs/spec/actions.yaml](../../../../docs/spec/actions.yaml) (ADR 0049) exists twice in generated Go code, both written by `tools/catalogen` through the `go:generate` line in `internal/kernel/authorize/doc.go` and held by `make codegen-check`:

- `internal/kernel/authorize/catalog_ids_gen.go`: the types `Action`, `EventType`, `Op`, `ResourceKind` and `ChannelOp` with one constant per entry (for example `ActionMessageRead`, `EventAccessChanged`, `OpCommandAutocompleteResult`, `ResourceAuthSession`, `ChannelOpHostControlSessionOpen`), `Parse*` and `All*`. They are the only constants of these types. The Semgrep rule `bothy-go-catalog-id-conversion` forbids, outside generated and test files, an explicit conversion (`authorize.Action(s)`), a typed declaration from a string literal, a string literal passed to `Spec`, `Registry.Event`, `Registry.Op` or `Registry.ChannelOp`, and a dot import of `kernel/authorize`; `TestNoConversionInsideThePackage` holds the hand-written files of `kernel/authorize` to the same rule. Not covered, because Semgrep has no type information: an untyped string constant or literal passed to any other function, field, return value or composite literal of these types; a conversion through a type alias or a generic function; an assignment of a literal to a variable of these types; and decoding (for example JSON) into a field of these types. Such a value still fails closed at run time (`Catalog.Spec`) or at start (`VerifyRegistrations`).
- `domain/catalog_gen.go`: the metadata keyed by plain strings, read through `LookupAction`, `LookupEvent`, `LookupOp`, `LookupChannelOp` and the list functions. Fields that 05 writes as text stay raw (`Right`, `Audit`, `ReceiveAction`, `ActionsText`); flags, classes and resource kinds are normalized as the brief of M1-25 lists them.

To change the catalogue, edit `actions.yaml`, run `make catalog` and `cd services/server && go generate ./...`, and commit all diffs.

### Unknown action

`Catalog.Spec` is the first step of every `Authorizer` (M1-28). For an action outside the catalogue it returns a `kernel/errs` error of kind internal with code `internal_error` and cause `unknown_action`, writes one ERROR record `unknown action` with `bothy.action` and `error.type=unknown_action`, and counts `bothy.authz.errors{bothy.reason=unknown_action}` (alarm `BothyAuthzError`). The HTTP chain answers `500 internal_error` without the action (07 AZ-P3).

### Start check

Start step 7 (`internal/wire`, 02 section 15.1) calls `Catalog.VerifyRegistrations` for every role, before any route is mounted, with the route bindings of the generated route table and the registry of all modules. It collects every violation: a route whose action is unknown, a system action, without a rate-limit class or with another class than the catalogue (AZ-P1); a gateway op that is unknown or goes from the server to the client; an event type that is unknown or registered by two modules; a terminal channel op that is unknown; a mentioned action that is unknown or a system action; a registration without a module name (AZ-P2); a route binding without operation id, method or pattern. A gateway op or channel op registered by two modules is accepted (the brief asks the two-module rule only for event types). Each violation is one ERROR line `registration check failed` (with `error.type` as the violation kind and, where known, `bothy.action`, `bothy.ratelimit.class`, `bothy.event.type`); the full text with operation id, op and module goes to stderr, and `bothy serve` exits with code 1. The routes are then mounted through the same catalogue (`Catalog.Class`), so there is one definition of a known action.

### How a module registers

A module that emits event types or accepts gateway or terminal channel ops declares in its port package:

```go
// Register declares what this module emits and accepts (M1-25).
func Register(r *authorize.Registry) {
	r.Event("<module>", authorize.EventAccessChanged)
	r.Op("<module>", authorize.OpTypingStart)
}
```

and its ticket appends the function to `moduleRegistrations` in `internal/wire/authz.go`. No module registers anything in M1-25.

## Authorize (M1-28)

`app.Authorizer` implements `kernel/authorize.Authorizer`; `internal/wire` builds it (`NewAuthorizer`) in start step 6b with the recorder of audit.

### Algorithm

`Authorize(ctx, p, a, r)` (07 section 4.2, brief M1-28 "Algorithm"):

1. `Catalog.Spec(a)` and the requirement entry of `domain/requirements_table.go`; an unknown or deferred action is an internal error with cause `unknown_action` (one ERROR record, `bothy.authz.errors`), a system action an internal error. The resource kind must be one of the action's kinds.
2. The clock is read once. Anonymous principals pass only `Public` requirements.
3. The permission version (pinned, request memo, or `instance.Versions`), the snapshot entry from the cache, the liveness checks (status, session, device, token, installation) and the pending rule (`principal_pending`, `device_pending`; `device.list` only for the own device).
4. The path is resolved fresh from `StructureSource` (thread, channel, space; a grant's target; a host has no path). A missing object is `not_found no_grant`; a hint that contradicts the structure is an internal error.
5. The effective rights on the path (`domain.Effective`): dm participation, owner, the highest level and union of capabilities of instance, space and channel grants, the operator rule, the limits of agents and apps; then the intersections with "view as" and acting for.
6. `domain.Decide`: visibility per resource kind (D4), the requirement with the reason of the deciding atom, the app scope (`domain/scopes.go`), the read-only channel, "view as" is read-only, step-up (`auth.step_up_max_age`), the guards of `agent.invoke` (also on `interaction.create` of an agent's card, M2-15; never for an app owner, M2-25), the app-owner guard `AppOwnerReachable` (M2-25), `grant.create`, `grant.revoke` and `token.create` (M1-44: a personal token only for the person itself, else `forbidden not_self`; the application layer reads the holder's kind from the principal source into `domain.TokenFacts`). The requirement of `token.create` names `owner` before `self`, so a caller with neither right is refused with `owner_only` for an agent or app holder (SR5: the owner's personal token has no owner role) and with `not_self` for another person.
7. The check is recorded in the request check log; outside filter mode every denial goes to `auditing.Recorder.RecordDenial` (aggregated) and every error to `RecordDetached` with decision `error`. A recorder failure is logged and never changes the decision.

`Scope(ctx, p, a)` serves list actions whose requirement is read on a channel path or a space: it builds the visible channels, spaces, fully visible spaces and the instance-wide flag per request from the snapshot and the current structure (07 sections 7.2 and 7.4) and memoises them in the request memo only.

### Cache

The snapshot (`domain.Snapshot`) holds the direct grant maxima per target, the owner role and the groups (D5). It is cached per `(principal, session, device, token, permission_version)` in an LRU bounded by `authz.snapshot_cache_max_entries`; a hit needs `t < ValidUntil`, the earliest expiry of a grant, membership, session or token read, so an expiry takes effect without a job (AZ-P10). Structure is never cached: a channel or space created without a new permission version is judged and listed at once. Nor is the place of a thread: REST decisions resolve the channel of a thread from the structure source at decision time and cache no thread-to-channel resolution across requests, so after a `thread.move` (M1-62) no `authorize` call in any process instance evaluates the thread at its old channel (07 4.2). `thread.move` itself requires `All(Cap(manage), TargetCap(manage))` with the destination in `Resource.TargetChannelID`; an invisible or unknown destination, the nil UUID included, is `not_found` like an invisible thread (`TestThreadMoveRequirement`). The gateway's permission cache applies `thread.moved` in log order (M1-65). `platform/httpserver` installs one request memo per request (`authorize.WithRequestScope`), so the permission version is read once per request.

### Deferred actions

The requirement entries of `domain.DeferredActions()` (held by `domain/testdata/deferred_actions.golden`) need facts of a later milestone. `Authorize` and `Scope` answer them like an unknown action, and `VerifyRegistrations` rejects a route, op, channel op or event type that names one (D3). The ticket that builds one replaces its row in the table and removes it from the golden file.

### Delivery check `webhook_out.deliver` (M2-26)

`webhook_out.deliver` is no longer deferred: its requirement is `Delivery`, decided by
`Authorizer.authorizeDelivery` with `domain.DeliveryGate` before the receive action. In this order:
the liveness check of the receiving principal; a principal that is not an app is `forbidden
subject_kind_not_allowed` (agents until the agent transport); an app without `events:subscribe`
in its granted scopes is `forbidden scope_missing`; a personal event (`Resource.Audience` set) is
allowed for its audience and `not_found not_self` for anyone else; otherwise the full decision of
the receive action `Resource.DeliveryOf` on the same resource (visibility, requirement and the app
scope of the action, for example `messages:read` for `message.read`) is the result. A personal
event carries no `DeliveryOf` (its receive action is `self`); without an audience an empty
`DeliveryOf` or `webhook_out.deliver` itself is an internal error.
The delivery job calls it in filter mode, so no denial is written (AZ-P13).
### Stored events (M1-63)

`authorize.ResourceFromEvent` describes a stored event for the check of its receive action at
delivery (REST catch-up, gateway, webhooks): a thread, channel or space by its id, any other kind
with its most specific scope, and `Resource.Event` with the full scope. Its last parameter is

(`TestResourceFromEventCatalogue` decides every durable event type; docs/DECISIONS.md M1-63/9,
M1-63/12).

### Invocation token of `run.start` and `run.token.renew` (M2-09)

Both are no longer deferred. `runs` verifies the invocation token and passes its verdict in
`Resource.Token` (`authorize.TokenFacts`); authz decides on it (05 rule 1.1). The requirements are
`run.start`: `All(AgentSelf, Token(valid))` ("agent-self and token valid") and `run.token.renew`:
`All(AgentSelf, Token(valid, expired))` ("agent-self and token current"). The resource is the run
(`Kind` run, `ThreadID` of the run, `OwnerID` the run's agent), so visibility (`not_found`) and
`AgentSelf` (`not_self`, `subject_kind_not_allowed`) decide first. A verdict outside the allowed
set is `forbidden invocation_token_invalid` with `Decision.Detail` the verdict (`expired`,
`superseded`, `invalid`); `Decision.Err()` answers `403 invocation_token_invalid` with that verdict
as `reason`, while the audit reason stays `invocation_token_invalid`. A missing `Resource.Token`
or the zero verdict is an internal error on every path.

The guard of `run.start` (07 section 4.2 step 9) runs only when `BillingModeUsed` is set:
`BillingKeyType = unknown` or a reported mode other than `BillingModeExpected` is
`invariant_violation billing_mode_mismatch`; then a `ToolClassUsed` above `ToolClassClaim`
(`chat` < `scoped` < `host`, an unknown class counts as `host`) is `invariant_violation
tool_class_mismatch`. A token that is not valid never reaches the guard.

The deny entry carries codes as details, never a token or `jti`: `token_verdict` for
`invocation_token_invalid`; `billing_mode_expected`, `billing_mode_used` and, when present,
`billing_evidence_provider`, `billing_evidence_key_type`, `billing_evidence_method` for
`billing_mode_mismatch`; `tool_class` (the claim) and `tool_class_used` for `tool_class_mismatch`.
A value that is not a code is left out, so the denial is still written.

### Interactions (M2-15)

`interaction.create` is no longer deferred (removed from `domain/testdata/deferred_actions.golden`):
its row in `domain/requirements_table.go` is `AtLeast(LevelTrigger)` ("trigger") on the resource
`component`, a channel path kind, so a component resolves through its `ThreadID` and a person
without read on the channel gets `not_found`. The descriptor of an agent's card carries `Invoke`
(the card's author as `AgentID`, which must equal `OwnerID`, origin `human`, the agent of the
thread's active run) and `Interaction` (`authorize.InteractionFacts`, stage `accept`, read from the
locked rows); missing facts, another stage and an `AgentID` other than the author are internal
errors, and so is a state, `restricted_to` or capability outside its list. A card of an app
(`OwnerKind = app`) carries no `Invoke` and is decided by the app branch (section "Apps as owners
of commands and components (M2-25)" below).

For an agent's card the guard (`domain/guards.go` `invokeGuard`, `domain/interaction.go`) is the
guard of `agent.invoke` with these additions, in this order (brief M2-15 design note 8 b):

1. `origin_not_human`; 2. and 3. `agent_not_reachable`, where the mention rule counts as met for
   the operator of the thread whatever the mention switches say (the card is the agent's own
   address to the person); a guest agent still needs `allow_mentioned_agents`, its own `write` and
   billing mode `organization`; 4. `billing_mode_personal_not_holder` (I2); 5.
   `tool_class_owner_only` (SR2);
6. at stage `accept`: `component_inactive` for a state other than `active`, an expiry at or before
   the request time, or a run that is no longer active; at both stages: `capability_missing` when
   `required_capability` is not among the effective capabilities on the path,
   `component_restricted` for `restricted_to = run_starter` when the principal is neither the run's
   starter nor an effective owner, and for `restricted_to = owner` when it is not an effective owner
   (owners hold every capability and pass every restriction);
7. `project_not_ready`, `dev_environment_not_ready`;
8. `run_active_other_agent` when the thread's active run belongs to another agent; at stage
   `accept` `run_active` for a component without a run while the card's agent has an active run.

Stage `deliver` is `agent.invoke` with `Interaction` set (the re-check before the delivery an
interaction caused, design note 8 c): it skips the state check and `run_active` and evaluates the
capability and the restriction with the rights of that moment. `agent.invoke` with interaction
facts of another stage is an internal error; without them it behaves as before (SR2, then the
project rules, then `run_active_other_agent`). Denials are audited by the normal flow (07 4.2).

`component.update` and `interaction.respond` keep `Any(AgentSelf, AppSelf)` with `OwnerID` the
card's author: the author is allowed, a person gets `forbidden subject_kind_not_allowed`, another
agent `not_found no_grant` without read on the channel and `forbidden not_self` with read.

`Decision.Err()` (design note 8 d): `forbidden component_inactive` answers `409 component_used`
without a reason (the reason stays in the audit, so a lost race answers the same whether
`authorize` or the single-use lock decided); `origin_not_human`, `agent_not_reachable`,
`billing_mode_personal_not_holder`, `tool_class_owner_only`, `project_not_ready`, `run_active` and
`run_active_other_agent` answer `403 agent_invocation_denied` with the reason, for `agent.invoke`
as well; `level_insufficient`, `capability_missing`, `component_restricted`,
`subject_kind_not_allowed`, `not_self` and `view_as_read_only` stay `403 forbidden` with the reason,
`channel_read_only` and `channel_archived` `403 channel_read_only`, `not_found` `404`.

### Acting-for binding (SR9, M2-14)

An agent that works inside a run sends the run's invocation token in the request header
`Invocation-Token`; identity checks it on every request through `identity.ActingForSource` (runs)
and puts the result into `actor.ActingFor` (status `bound`, `run_inactive` or `invalid`, the
triggering person, the run and its thread). authz reads it through `authorize.ActingForBinder`
(`authorize.ActingForOf`) in `bindActingFor`, right after the liveness and pending checks:

- Delivery mode (`authorize.Delivery`) ignores the binding completely: an agent consumer is judged
  by its own grants (07 section 8.1). `Filter(ctx)` stays bound.
- `domain.CheckActingFor`: `invalid` (and any unknown status) ends every action and `Scope` with
  `forbidden invocation_token_invalid`, `Decision.Detail` `invalid`, before the path is resolved;
  `run_inactive` does the same with `Detail` `run_inactive`, except for the unbound actions.
- The mode table `domain.ActingForModeOf` (golden `domain/testdata/actingfor_modes.golden`):
  own exceptions `message.create`, `run.update`, `run.finish`, `interaction.respond`,
  `agent_session.report`; unbound `run.start` and `run.token.renew`; every other action is bound
  (fail closed for new actions). `domain.ActingForApplies` decides after the path is resolved: an
  own exception uses only the agent's rights when the resolved thread equals the run's thread and,
  for a resource of kind `run`, the run is the own run; elsewhere it is bound.
- Bound: the rights are `eff(agent) ∩ eff(person)` on the path; a target visible only with the
  agent's own rights is `not_found acting_for_insufficient`, a requirement that holds only with
  them is `forbidden acting_for_insufficient`; when the agent alone fails, its own reason stays.
  `Scope` intersects every list the same way.
- The person's rights: the snapshot of the check without a request (R-AZ-29, `loadRecheck`, cache
  key `recheck`), so an owner keeps the owner rights without a session and no token principal of
  the same person shares the entry; a person who is not active has no rights (SR7).
- Denials of a principal with a binding name `acting_for_user_id` and `run_id` (IDs, absent for
  `invalid`) and, for `invocation_token_invalid`, `token_verdict`; never the token or its `jti`.

What SR9 does not cover: the server cannot tell a request inside a run that omits the header from
one outside a run (AZ-M45, hint H1); the SDKs and reference adapters always send it (M2-29, M2-30,
M2-33, M2-34). Knowledge a runtime keeps across runs is outside the API (H1, T-AI-01). An owner who
triggered with a personal API token is intersected as owner (the residual of R-AZ-29). Gateway
connections carry no binding (D-M2-14). Tests: `app/actingfor_test.go`,
`app/reference_sr9_test.go` (AZ-P8 dimension, `TestAZP11_ActingForProperty`),
`domain/actingfor_test.go`, `BenchmarkAuthorizeCachedActingFor`.

### Agent sessions (M2-12)

`agent_session.reset` and `agent_session.bind` are no longer deferred. Their row in
`domain/requirements_table.go` keeps the 05 text "trigger and `agent.invoke`" and is
`Level(trigger)`; `guards` applies the `agent.invoke` guard to both with the invoke facts of the
descriptor, and a missing `Resource.Invoke` is an internal error, as for `agent.invoke`. The
descriptor is the thread with `Invoke: &authorize.InvokeFacts{AgentID: <operator of the thread>,
TriggerOrigin: "human", MentionsAgent: true}` and `ActiveRunAgentID` zero: a session switch names
the operator explicitly and starts no run (brief M2-12 design note 5). A thread without operator
has `AgentID` zero, which the guard refuses with `agent_not_reachable`. A read-only channel is
`forbidden channel_read_only`; the agents use case maps a guard reason to `403
agent_invocation_denied`.

`agent_session.bind` has a second target (07 4.2 "Actions with two targets", 09 9.4 point 1):
`Resource.TargetThreadID`, the thread in which the reference is current, zero when it is current
nowhere. With a non-zero target, `decideFor` decides the same action again on that thread with the
same invoke facts, after the first path allowed: an invisible or unknown target is `not_found
no_grant` like an unknown thread, and level, read-only rule and guard hold on the target's path,
its operator and its channel settings. Both paths must allow; `Authorize` audits the one final
denial (R-AZ-04). `agent_session.report` stays `AgentSelf` on the descriptor `{Kind:
agent_session, ID: <session of the run or zero>, ThreadID: <thread>, OwnerID: <the run's agent>}`;
the zero ID resolves through `ThreadID`. Tests: `app/session_test.go`.

### How a module builds a `Resource`

Load the resource first (02 section 9.2), then describe it: `Kind`, `ID`, the path hint (`ThreadID` for things in a thread, `ChannelID` for a channel or an unattached file, `SpaceID` for a space), `OwnerID` (author, creator, holder or the principal itself) and the facts of the action (`File` for a file, `HasAttachments` for `message.create`, `RestrictedTags`, `TargetChannelID` for `thread.move`, `Grant` for `grant.create`, `Invoke` for `agent.invoke`, `run.followup.create`, `interaction.create`, `agent_session.reset` and `agent_session.bind`, `TargetThreadID` for `agent_session.bind`, `Interaction` for `interaction.create` and for `agent.invoke` at stage `deliver`, `Token` for `run.start` and `run.token.renew`, `PreviewOf` for `access.preview`, `DeliveryOf` and `Audience` for `webhook_out.deliver`). Pass the `actor.Actor` of the request as the principal; it implements `authorize.Principal`. Treat an error like a denial and return it. Per-element checks of lists, searches and deliveries run with `authorize.Filter(ctx)`.

### Slash commands (M2-16)

`kernel/authorize.CommandFacts` on `Resource.Command` describes a command (owner kind, scope,
`OfferedInChannelID` of a list item) and the invocation facts of `command.invoke`
(`RequiredLevel`, `Control`, `ActiveRun`); the owner is `Resource.OwnerID`, for `command.invoke`
and `command.autocomplete` `CommandFacts.OwnerID` (M2-25: there `Resource.OwnerID` names the
creator of the target thread). In request mode a
resource of kind `command`, and `command.invoke`, without the facts is an internal error; only the
filter-mode receive check of `command.changed` takes the path from the event scope.

- `command.read` takes the kinds `channel` (`Level(read)`, the list of `listChannelCommands`) and
  `command` (`Auth`; the visibility decides). The catalogue names only `channel`, so
  `domain.ActionResourceKinds` adds `command` for this action.
- Visibility of kind `command` (`domain/commands.go`, `commandVisible`): without an offered channel
  the owner, an effective owner, or a principal that sees the scope target (`read` on the channel,

### Apps as owners of commands and components (M2-25)

An app owns commands and components like an agent, and none of them triggers an agent: app
commands and app components never check the guard of `agent.invoke` or I2 (05 section 5, last
paragraph; R-AZ-18). The rights logic of the app side lives here like every other (07 4.2).
Rulings: docs/decisions.d/M2-25.md.

- **Facts.** `PrincipalFacts.AppGrantedScopes` holds the granted scopes of the app's active
  installation; the identity principal source fills it from the active installation, next to
  `AppInstallationActive`. `kernel/authorize.CommandFacts.OwnerID` names the owner of the command
  for `command.invoke` and `command.autocomplete`, whose `Resource.OwnerID` names the creator of
  the target thread. An app card names its author in `Resource.OwnerID`, with
  `InteractionFacts.OwnerKind = app`. The guard reads the facts and the snapshot of the owner (its
  effective level on the resolved path), never those of the principal of the request.
- **Guard `AppOwnerReachable(scope)`.** True when the owner's installation is `active`, `scope` is
  among its granted scopes and the owner's effective level on the resolved path is at least
  `write` (apps hold at most `write`, 07 2.1 and 2.10; a dm channel is never reached, 05 2.2).
  Where no channel is resolved (`getCommand` of an instance-wide command, without
  `OfferedInChannelID`) it checks only the active installation and `commands:write`, so
  `getCommand` answers whatever the app's grants are. The guard is skipped when the principal is
  the owning app itself.

| Action | Scope of the guard | Mode | False guard |
|---|---|---|---|
| `command.read` of an app-owned command (list item with `OfferedInChannelID`, `getCommand`) | `commands:write` | filter for list items, request for `getCommand` | `not_found` `no_grant` |
| `command.invoke` | `commands:write` | request; filter in the re-check of `runs.app_dispatch` | `not_found` `no_grant` |
| `command.autocomplete` | `commands:write` | request | `not_found` `no_grant` |
| `interaction.create` on a card whose author is an app | `components:write` | request at stage `accept`; filter at stage `deliver` in the re-check of `runs.app_dispatch` | `forbidden` `component_inactive`, answered `409 component_used` |

An unusable app command is hidden (11 4.2 "inactive", 4.3 "hidden"), so it answers exactly like an
unknown command (R-AZ-01, AZ-P4); an unusable app component cannot be used from the person's view
(11 4.2).

- **Order for app owners** (07 4.2): the visibility of the place for the person; for commands
  then the guard (part of the visibility); then `Level(required_level)` for commands or
  `Level(trigger)` for components; then the read-only and archive rules (`channel_read_only`,
  `channel_archived`); for components then point 6 of 05 section 5 with the guard first: a state
  other than `active`, an expiry at or before the request time or a false guard give
  `component_inactive` (stage `deliver` skips the state and expiry check as for an agent's card),
  a missing `required_capability` gives `capability_missing`, and `restricted_to = owner` without
  an effective owner and `restricted_to = run_starter` give `component_restricted` (an app card
  has no run, so only effective owners pass).
- **Never for app owners:** the guard of `agent.invoke` (SR4 origin, operator or mention
  reachability, I2 `billing_mode_personal_not_holder`, SR2, SR3, project readiness, the active-run
  rules), so no reason of that guard ever appears for an app command or an app component.
- **Mapping.** `Decision.Err()` is unchanged: `command.invoke` and `command.autocomplete` answer
  through the mapping of `invokeCommand` (M2-16), `interaction.create` through the mapping of
  M2-15 above.
- **Re-check.** The job `runs.app_dispatch` checks `command.invoke` or `interaction.create` at
  stage `deliver` again with the rights of that moment, in filter mode, before it sends a request to
  the app; a person is the principal of the check without a request (section "Check without a
  request (M2-08, R-AZ-29)" above).

**Receive rule for apps** (05 section 6 rows `command.invoked` and `interaction.created`; 03
`event_log.receive_action`; 07 8.1). When the action is `agent.events.consume`, the principal is
an app and the mode is filter (`authorize.Filter(ctx)`, implied by `Delivery(ctx)`), the domain
rule `AppReceive` decides instead of `AgentSelf`: `not_self` (`not_found`) for an event whose
audience is another principal, `app_not_installed` without an active installation,
`scope_missing` (`forbidden`) without `events:subscribe`, otherwise `allow`. sync passes the
audience in the descriptor of a personal event for an app receiver as it does for the agent
consumer. So the hub delivers `command.invoked`, `interaction.created` and the ephemeral
`command.autocomplete_requested` to the connections of the audience app, `listEvents` returns them
to it, and a webhook subscription of the app passes `webhook_out.deliver` (above). Filter-mode
checks write no denial (AZ-P13). In request mode the requirement stays `AgentSelf`, so an app on
the consumer operations of M2-07 (poll, ack and the consumer take) keeps `403 forbidden` with
`subject_kind_not_allowed`. Agents are unchanged: the catalogue has one receive action per type,
and the mode separates the receive check from the agent operations.

## Rights changes (M1-29)

Every rights change runs through one transactional path (02 section 8.1). A use case declares it
with `txn.DeclareRightsChange` (action of the catalogue with column "Permissions" = yes, the resource of
the deny entry, the affected principals, or targets); `platform/pg` then runs the hooks of
`app.RightsHook` that `internal/wire` registers:

1. **Phase 1, `Begin`.** First statement of the transaction: `permission_version` is locked and
   raised through `instance.Counters` (03 section 6.3), then the views (visible spaces, visible
   channels with level and capabilities) of the declared principals are recorded. For declared
   targets authz derives the affected itself: subjects of grants in effect on the target, its
   ancestors and, for a space, its channels (group members expanded), the active owners and the
   effective operators. Views use the snapshot and `Effective` of `Authorize`, never the cache.
   Before that, the due expiries are folded in (M1-30, section "Sweep and the fold of due
   expiries").
2. **Phase 2, the use case.** It writes; a principal it learns about only now (a new operator)
   it names with `RightsChanges.AddAffected` before writing rows that concern it.
3. **Phase 3.1, `BeforeCommit`.** `VerifyInvariants` (SR8: at least one active owner; I1: for
   every active personal agent the trigger set over its served targets is exactly its credential
   holder). A violation rolls the unit back with `InvariantError` (`409 last_owner` before
   `409 i1_violation`, the problem body carries `conflicts`), and the deny entry goes to
   `auditing.Recorder.RecordDenial`, which writes it in its own transaction. Otherwise one
   `access.changed` per principal with a non-empty difference is appended and
   `authorize.AccessChanged` is published once; a subscriber veto rolls everything back.

The store refuses writes of memberships and grants and the deletion of a group outside a unit
declared as a rights change, and the Authorizer neither reads nor fills its cache or version memo
inside one (the unit sees an uncommitted version). A hook that is not bound (`Bind` with the
appender and the recorder, start step `authz`) fails every rights change.

### How another module declares a rights change

```go
err := uow.Do(ctx, func(ctx context.Context) error {
	if err := rights.AddAffected(ctx, newOperator); err != nil { // authz.RightsChanges
		return err
	}
	return repo.SetOperator(ctx, channelID, newOperator)
}, txn.DeclareRightsChange(txn.RightsChangeSpec{
	Action:     string(authorize.ActionChannelOperatorSet),
	Resource:   txn.Ref{Kind: string(authorize.ResourceChannel), ID: channelID},
	Principals: []ids.ID{oldOperator},
}))
// err is an *authz.InvariantError for i1_violation or last_owner; nothing was written.
```

### `access.changed`

Personal event (04 section 2.2): `audience = self`, resource `principal`, no scope, the actor of
the request (`system` for a system action without one), payload `AccessChangedPayload` with the
version of phase 1 and the lists `added`, `removed`, `changed` (always present, sorted by kind and
id; spaces only appear or disappear; channels carry level and capabilities, changed ones also
`previous_level`). A change without visible effect raises the version and writes no event.

### Admin

Each method loads the resource, authorizes it (step-up for all, the delegation limits of
`grant.create` and `grant.revoke`, 07 section 2.6, which belong to the requirement since M1-48),
runs in one unit of work and records the allow
entry in it (ids and codes only, the reason as `ReasonText`). Calls without effect (deleting a
deleted group, removing a removed or expired membership, revoking a revoked grant, an update
without change) succeed without rights version and audit `no_change: true`; they decide that in
a first unit without rights change. Missing and invisible resources give the same `404`.
Grants on hosts give `404` until M2-39 adds hosts. `group.name_max_chars` and
`group.description_max_chars` reach `AdminConfig` through `wire.NewAuthzAdmin` (M1-48).

### Use cases

- Reads (`app/adminread.go`): `ListGroups`, `GetGroup`, `ListGroupMembers`, `ListGrants`,
  `GetGrant`. The query and the counts of a request use one clock read; lists are keyset pages by `id` with cursors bound to the
  caller and the filters (`400 cursor_invalid` otherwise), `limit` capped at `api.page_size_max`,

- Writes (`app/admin.go`): the M1-29 methods, with `CreateGroup` for local and claim groups

### Visibility

| Operation | Not visible (`404`, like a random id) | Visible, not allowed (`403`) |
|---|---|---|
| `listGroups` | | owners list every live group; anyone else the groups with a membership in effect; a `member_id` filter for another person gives an empty page |
| `getGroup`, `listGroupMembers` | deleted, unknown, or caller neither owner nor member in effect | |
| `createGroup` | | `owner_only` |
| `updateGroup`, `deleteGroup`, `addGroupMember`, `removeGroupMember` | as `getGroup` | `owner_only` |
| `listGrants` | a target filter the caller cannot read | a readable target without `manage`; the instance for everyone but owners |
| `getGrant`, `revokeGrant` | unless owner or `manage` on the grant's target (a channel inherits it from its space); instance grants owner only | `revokeGrant`: the delegation reasons |
| `createGrant` | a target the caller cannot read | `owner_only`, the delegation reasons |

Every operation with an id authorizes before it answers a missing resource, so a caller that
`authorize` refuses before visibility (anonymous, a pending device) gets the same answer for an
existing and an unknown id; the shape of a write is checked before `authorize` without the
caller's id. Non-owners see grants only inside their `manage` scope; the query applies the scope, so filters
narrow it and never widen it (07 section 2.6 item 6). `grant.read` on an instance grant is
checked as `grant.read` on the caller as `principal`, whose requirement is `owner`. Step-up comes
after the requirement and the delegation limits: without a fresh step-up `401
step_up_required`, with a token without a session `403 forbidden`
(reason `step_up_not_possible`).

### Events

Every write appends, in its unit of work, `grant.changed` (`created` or `revoked`; resource the
grant, scope the target's space and channel, receive action `grant.read`) or `group.changed`
(`created`, `updated`, `deleted`, `member_added`, `member_removed` with `user_id`; empty scope,
receive action `group.read`, `member_count` counted after the change). Deleting a group appends
one `grant.changed` per revoked grant and one `group.changed`. `access.changed` comes only from
the rights hook (M1-29). Calls without effect append nothing.

## Expiry (M1-30)

Expiry is decided at every `authorize` call: a grant or membership is invalid from the second of
its `expires_at` (07 section 2.5), and a cached snapshot ends at `valid_until` (AZ-P10, proven
again by `TestAZ_P10_ExpiryWithoutJob` with no job running). The two jobs only report.

| Job | Registered by | Queue | Period | Arguments |
|---|---|---|---|---|
| `authz.expiry_sweep` | `adapters/jobs.Register` from `internal/wire` (every role builds the registry; `worker` and `all` run it) | `maintenance` | `authz.expiry_sweep_interval` | none |
| `authz.expiry_reminder` | the same | `maintenance` | `authz.expiry_sweep_interval` | none |

### Sweep and the fold of due expiries

Every rights change folds in the expiries that are due and not reported yet, as the first step
after phase 1 has locked and raised `permission_version` (`expiryfold.go`):

1. `ExpiryStore.DueExpiredGrants` and `DueExpiredMemberships` select the rows that are not revoked
   or removed, with `expires_at <= t` and `expiry_reported_at IS NULL`, in ascending id, `FOR
   UPDATE` (03 section 6.3).
2. The principals they affect (the subject of a grant to a user, agent or app; every member that
   is not removed of a group that is not deleted for a group grant; the member of a membership)
   get their view before with these rows treated as not expired (`domain.AssumeValid`).
3. `expiry_reported_at = t` is set, `grant.changed` (`change = expired`, scope space and channel)
   or `group.changed` (`change = member_expired`, `user_id`, empty scope) waits for phase 3.1
   with `actor = system`, and one allow audit entry per row is recorded without actor and without
   IP pseudonym, also inside a person's change (`grant.expire`: `subject_kind`, `subject_id`,
   `target_kind`, `target_id`, `expires_at`; `group.member.expire` on the group:
   `membership_id`, `user_id`, `expires_at`). `group.changed` is built in phase 3.1, so its
   `member_count` includes the memberships the change itself wrote.
4. Phase 3.1 appends these events, verifies I1 and SR8 and writes `access.changed` for every
   principal whose visible targets changed, with the action of the unit.

`ExpiryService.Sweep` is a rights change that only folds: units declared as `grant.expire`, then
`group.member.expire`, each folding at most `authz.expiry_sweep_batch_max` rows of its kind,
repeated while a batch was full. A batch without rows rolls back, so `permission_version` only
moves when something expired. An invariant violation (only possible in a world that was already
invalid) rolls the batch back, leaves the deny entry with the agent ids in the audit log, is
logged with the action, and the job returns the error so River retries.

**Exactly once.** The marker, the events and the audit entries commit in one transaction with
the change; an error rolls everything back and the next unit selects the same rows again. The
selection hangs on the stored marker, not on the time of the last run, so rows that expired while
the worker was down are found on the next run, and the lock of `permission_version` before the
row locks keeps two units from reporting a row twice. The trigger `authz_grants_immutable` allows
`expiry_reported_at` on grants to be set only once.

**Why every change folds.** A view is what the client was told, and an expiry reaches the client
only once it is reported. After the fold no due row of the change is unreported, so its view
before is what the client was told and its view after is what `authorize` decides: a loss through
an expiry is reported once (by the sweep or by the first rights change after the expiry, which
then also writes the event and the audit entry of the expiry), and no change reports a gain that
`authorize` denies. Rows not due yet, and in a sweep batch the rows of a later batch, count as
valid in both views (`domain.AssumeValid.Unreported`).

A grant revoked or a membership removed before its expiry is never reported as expired: the
revocation wrote its own `access.changed`. Memberships of deleted groups are folded too; their
difference is empty, so no `access.changed` follows. The cancellation of runs of people who lost
`trigger` subscribes to `authorize.AccessChanged` in M2.

### Reminder

`ExpiryService.Remind` runs batches in units of work without rights change: grants, then
memberships, with `t < expires_at <= t + authz.expiry_reminder_lead` and `expiry_reminded_at IS
NULL` (grants of deleted groups and memberships of deleted groups are not selected). Per row one
`access.expiring` per active recipient, without duplicates: subject and `granted_by` for a grant
to a user, agent or app; all active owners and `granted_by` for a grant to a group; member and
`added_by` for a membership. The payload `AccessExpiringPayload` carries `target` only for space and
channel grants. `expiry_reminded_at = t` is set in the same transaction, so each row is
reminded once; a grant created with less than the lead left is reminded on the next run.
Reminders write no audit entry and send no e-mail.

## Target host (M2-39)

A host is a target outside the tree instance, space, channel (07 section 2.12):

- **Source.** `HostSource` (`Host`, `HostIDs`, `AssignedTo`) with `HostFacts` (state, holder, LLM
  declaration, server host); terminal implements it (`terminal/app.HostSource`), `internal/wire`
  binds it for the Authorizer, the rights hook and the Admin use cases. A nil source means a world
  without hosts: every host is not found.
- **Snapshot.** `Snapshot.Hosts` holds the capabilities of the host grants in effect (own and of
  the groups in effect); their expiries enter `ValidUntil`. `TerminalOn(s, h)` is an effective owner
  or a grant `terminal` on `h`; the I6 exception for owners belongs to SR11 (M2-40).
- **Requirements.** `host.read` is `All(HumanSession, Any(Owner, Assignee, Terminal))`,
  `host.manage` `All(HumanSession, Owner)`. A requirement whose first part is `HumanSession` is a
  gate: `authorize` and `Scope` refuse agents, apps and personal tokens with
  `subject_kind_not_allowed` right after the liveness checks, before any resource is resolved.
  `host.pair` is `Public` since M2-41 (the use case proves the pairing code before `authorize`, as
  for the refresh token); `host.connect` is `HostSelf` since M2-43 (below); the terminal actions
  are real since M2-40 (section below).
- **Host principal (M2-43).** `host.connect` passes only for the principal of kind `host` on its
  own host row (`HostSelf`). `authorize` decides it on its own path (`authorizeHost`): a host
  principal is never looked up in `principals` and has an empty snapshot; `Resource.HostAuth`
  carries the verdict of the proof (missing: internal error); an unknown key or an invalid proof is
  `unauthenticated` with `host_auth_failed`, a host outside `confirming` and `active` is
  `unauthenticated` with `principal_inactive`, another host is `not_found`; people, agents and apps
  get `forbidden` with `subject_kind_not_allowed`; a host principal is not authenticated for any
  other action. Tests: `TestHostConnectRequirement`, `TestHostPrincipalSkipsPrincipalSource`.
- **Visibility.** A host resource resolves through the source; it is visible to an effective
  owner, its holder and a person with `TerminalOn`, with "view as" to both views, and to any
  principal for an action whose requirement is exactly `Public` (only `host.pair`, M2-41).
- **Scope.** `Scope(host.read)` gives `AllHosts` to an effective owner, otherwise the ascending
  `HostIDs` of the terminal grants and the own hosts, intersected with "view as".
- **access.changed.** `AccessView.Hosts` holds the hosts with `TerminalOn` (every host for an
  owner); a host is `added` with `capabilities: ["terminal"]` and no level or `removed`. The rights
  hook derives the affected principals of a `host` target: every active owner, the holder and the
  subjects of the grants on the host (`Store.ActiveGrantsOnHosts`, groups expanded).
- **Grants.** `CreateGrant` on a host needs an existing host and refuses a retired one with `409
  conflict`; subject and capability rules stay with `CheckGrantShape`.
- **Tests.** `TestHostRequirement`, `TestAZM60_InstanceGrantGivesNoHost`, `TestScope_Hosts`,
  `TestSnapshot_HostGrants`, `TestDiffVisible_Hosts` and the hosts of the AZ-P8 differential test.

## Terminal rights (M2-40)

- **Entries.** `terminal.open` `All(HumanSession, Terminal)` on `host`, `terminal.attach`
  `All(HumanSession, Self, Terminal)` on `terminal_session` (Terminal on the session's host),
  `terminal.stream` `All(HumanSession, Self)`, `terminal.close` `All(HumanSession, Any(Self,
  Owner))`, `terminal.read_own` `All(HumanSession, ByKind{terminal_session: Any(Self, Owner), host:
  Auth})`. A `terminal_session` resource names its host in `Resource.HostID` and its person in
  `OwnerID`; it is visible to that person and to effective owners (else `not_found` `not_self`).
- **Step-up `fresh`.** `domain/terminal.go`: `FreshStepUp` (`terminal.step_up_max_age`, passkey or
  device key, unconsumed, never the console) and `QuickReattach` (`terminal.quick_reattach_window`,
  same device and login session, `detached` only; `Decision.QuickReattach`). Step 8 of a `fresh`
  action evaluates only this branch. `app.FreshCheck` implements `authz.FreshStepUpCheck` for
  `identity.StepUp.ConsumeFresh`, so the consumption judges with the same rule.
- **Guards.** `TerminalGuard` after step 8: SR10 server host, SR10 assignee, SR11 (I6, also other
  owners), SR12 (an own reported session user, also owners). After SR12 `TerminalLiveGuard`:
  `terminal_session_limit` (M2-46), then `host_not_active` and `terminal_profile_unknown` (M2-44).
  The reasons map to `403 terminal_denied` with the `reason` of 24 13
  (`kernel/authorize.Decision.Err`).
- **Session limits (M2-46).** The terminal module counts the sessions of the person and of the host
  that are not `closed` under its person lock and host row lock and passes them in
  `TerminalFacts.OpenSessionsOfPerson` and `OpenSessionsOfHost`; `domain.TerminalSessionLimit`
  denies `terminal.open` with `terminal_session_limit` (`403 terminal_denied`, `reason`
  `session_limit`, audited like every denial) when a count is at least
  `terminal.max_sessions_per_person` or `terminal.max_sessions_per_host`
  (`AuthorizerConfig.MaxSessionsPerPerson`, `MaxSessionsPerHost`). Attaching is never counted. A
  zero limit in a hand-built configuration is not configured (the binding through `internal/wire`
  requires at least 1), a negative one is refused by `NewAuthorizer`. `terminal.open` without
  `Resource.Terminal` is an internal error, so a caller cannot pass the limit by leaving the counts
  out. Tests: `TestTerminalSessionLimit`, `TestTerminalLiveGuard_SessionLimit`,
  `TestTerminalOpenLimitGuard`, `TestTerminalOpenLimitGuard_NotConfigured`,
  `TestNewAuthorizer_NegativeSessionLimit`, `TestDecisionErr_TerminalSessionLimit`.
- **Rights state.** `HostSource.SessionUsersOf` fills `Snapshot.SessionUsers` for people and
  `HostSource.PersonalHosts` fills `Snapshot.PersonalHosts` for effective owners; both are cached
  per rights version (a change of an assignment, a report or a declaration raises it).
- **Difference.** `TerminalEffective` (07 2.12 point 3 with the I6 clause) decides
  `AccessView.Hosts`, so a switch to `personal` removes the host from every other owner's view.
- **I6.** `VerifyInvariants` checks every personal host on every rights change (`domain.CheckI6`
  over the valid grants and the members in effect of group grants); `InvariantError` with code
  `i6_violation`, `HintI6` and one conflict per host; the deny entry carries `violations` with
  `host_id`. `host.pair` and `host.connect` may declare a rights change (their reports are rights
  state, D-M2-40-9).
- **Preview.** A grant on a host gets host effects (`capabilities_added: [terminal]`), I6 in
  `invariant_violations` and the hint `terminal_not_effective` (SR10 or SR12 would deny), with the
  templates `summary.host`, `hint.i6` and `hint.terminal_not_effective.*` (golden files
  `example_host_de.golden` and `example_host_en.golden`).
- **Tests.** `TestFreshStepUp`, `TestQuickReattach`, `TestTerminalGuard`, `TestTerminalEffective`,
  `TestCheckI6`, `TestRequirementSources_Terminal`, `TestAZ_M54_*` to `TestAZ_M61_*`,
  `TestTMT08_SR10`, `TestTMT28a_NoSessionUser`, `TestTerminalDecisionOrder`,
  `TestTerminalAttachStreamReadClose`, `TestSubjectGate_TerminalActions`,
  `TestTerminalSnapshotVersion`, the terminal decisions of `TestAZP8_CacheMatchesReference` and the
  preview text tests.

## Apps (M2-24)

- **Scope check.** An app needs the scope of each action in `GrantedScopes` of its installation
  and, when the request carries an API token, in the token scopes (`kernel/authorize.Principal`
  gained `AppTokenScopes`, which `actor.Actor` answers with `Scopes`); missing in either is
  `forbidden` `scope_missing`. A check without a token (a webhook delivery of M2-26) uses the
  installation alone. `Scope` filters the lists of an app with the same rule. Agents are unchanged.
  This replaces ruling M1-28 D6 (token scopes not evaluated); docs/DECISIONS.md D-M2-24-10.
- **Snapshot.** `PrincipalFacts.AppInstallationActive` (set by identity from
  `identity.AppInstallations`): an app without an active installation has an empty snapshot and an
  empty access view, like a principal that is not active (`PrincipalFacts.GrantsInEffect`). So
  `app.suspend` and `app.uninstall` remove every visible target of the app and `app.resume` adds
  them again; the rights hook writes `access.changed` for them. A change of the granted scopes alone
  changes no visible target and writes none (the gap of docs/DECISIONS.md D-M2-24-11).
- **`AppScopes`** (`appscopes.go`, implemented by `app.ScopeTable`): `EventScope` decides which
  durable event types an app may subscribe to (`domain.AppEventScope`: a receive action of the
  scope table, or `interaction.created` and `command.invoked` with `events:subscribe`) and
  `Scopes` lists the scopes of the catalogue.
- **`Admin.RevokeSubjectGrants`**: revokes every active grant of a principal in ascending id inside
  the caller's rights change, without `authorize` per grant (a consequence of the authorized
  `app.uninstall`).
- **The collection of apps.** `app.read` on a resource of kind `app` without an id is the
  collection (`listApps`, `validateManifest`): visible like the instance, so the requirement owner
  answers a non-owner `owner_only`; one app stays invisible to non-owners (`not_found`).
- Tests: `domain/appscope_test.go` (`TestAppEventScope_AllCatalogueEvents`,
  `TestAppScope_TokenAndInstallation`), `app/appscope_test.go`
  (`TestSnapshot_AppWithoutActiveInstallationIsEmpty`, `TestAZM32_TokenScopes`,
  `TestAppCollection_OwnerOnly`, `TestScopeTable`, `TestRevokeSubjectGrants`).

## Trigger holders (M2-13)

`app/triggerholders.go`: the `Authorizer` implements `authorize.TriggerHolders`. `WithTrigger(ctx,
Resource{Kind: channel}, people)` returns, ascending and without duplicates, the people with
effective `trigger` on the channel path at the rights version of the request: each person's
snapshot is loaded without credentials (cached like "view as"), only active humans count, the
DM rule and the archive cap apply, and an active owner counts on every channel that is not a DM
(the owner role of `Authorize` needs a session, R-AZ-14). No audit entry, no check-log entry; a
source error is returned and never means "has trigger". `adapters/fake.TriggerHolders` is the fake
for the tests of other modules. Tests: `app/triggerholders_test.go`. Rulings:
docs/decisions.d/M2-13.md (D-M2-13-1 and D-M2-13-2).

## Personal data (M7-06)

`app/personaldata.go`: `PersonalData` is the participant of authz in the privacy requests
(`kernel/personaldata.Participant`, docs/spec/20-privacy.md sections 4.4 and 5.2). It lives in
`app` because the erasure reuses the rights path of the use cases.

- **Tables:** `groups`, `group_memberships`, `grants`. `groups` has no export or erasure of its
  own: its personal column `created_by` stays, because the group belongs to the organization; the
  group name reaches the person through the memberships. The owner status (`owners`) belongs to
  `identity` (architecture/modules.yaml) and is exported there.
- **Export:** `access.json` sections `grants` (every grant whose subject is the person, revoked ones
  included: target by ID, level, capabilities, reason, `granted_by`, times, expiry, revocation) and
  `group_memberships` (every membership of the person, removed ones included: group ID and name,
  `added_by`, times, expiry, removal). Grants to a group of the person belong to the group and are
  not listed. Both lists come from one read-only snapshot (`Repository.PersonalAccess`, queries in
  `adapters/postgres/queries/personaldata.sql`). Schemas:
  `docs/api/gdpr-export/v1/sections/access.grants.schema.json` and
  `access.group_memberships.schema.json`.
- **Erasure:** only the step `access` (20 section 4.4 item 4). Two units, each declared as a rights
  change and acting as the system: `group.member.remove` sets `removed_at` on every open
  membership of the person and appends `group.changed` (`member_removed`) for those of a live
  group whose expiry was not reported; `grant.revoke` sets `revoked_at` with the reason
  `account_deleted` on every open grant of the person and appends `grant.changed` (`revoked`). The
  rights hooks raise `permission_version`, fold due expiries in, verify the invariants and append
  `access.changed`, all with actor `system` (`asSystemChange`, read by `eventActor`). `removed_by`
  and `revoked_by` stay NULL, the rows stay with the ID as evidence, and no audit entry is written
  per row (privacy writes the entry of the deletion). A unit that finds nothing open rolls back, so
  a resumed step repeats nothing.
- Tests: `app/personaldata_test.go` (`TestPersonalDataExport`, `TestPersonalDataErase`).
