## Storage (M1-27)

Migration `migrations/00005_authz_groups_grants.sql` (M1-27) creates the three tables exactly as 03 section 4.3
states, with named constraints (`grants_subject_shape_check`, `grants_bot_limits_check`,
`grants_host_shape_check` and the others) that the adapter maps to fields.

- **Deferred foreign keys.** The target tables do not exist yet, so these columns are plain `uuid`
  until the migration that creates each table adds the key: `groups.provider_id ->
  identity_providers(id)` (M1-36), `grants.target_space_id -> spaces(id)` (M1-52),
  `grants.target_channel_id -> channels(id)` (M1-53), all `ON DELETE RESTRICT`; `grants.target_host_id
  -> hosts(id)` exists since M2-39 (migration `00028_terminal_hosts.sql`). Until then no code path
  creates space or channel grants.
- **Immutability trigger** `authz_grants_immutable` (BEFORE UPDATE ON `grants`, SQLSTATE `23514`):
  allowed are only the revocation (`revoked_at`, `revoked_by`, `revoke_reason`, once, with
  `revoked_at` set) and setting `expiry_reminded_at` or `expiry_reported_at` from NULL. Every
  other change raises, including a second revocation; the comparison covers the whole row, so a
  column a later migration adds is immutable by default (R-DM-09).
- **People only.** `group_memberships.user_id` references `users(principal_id)`, so agents and apps
  cannot be members (R-DM-07).
- **Bots.** `grants_bot_limits_check` refuses `trigger` and any capability beyond `upload` for agent
  and app subjects (R-DM-08, R-DM-20); `CheckCreate` refuses them first with
  `subject_kind_not_allowed`.
- **Subject kind.** The database does not check that `subject_principal_id` has the kind of
  `subject_kind`; the use case checks it through `PrincipalSource` (M1-48) and the snapshot caps
  rights by the real kind (M1-28).
- **Privileges.** `bothy_app` has `SELECT, INSERT, UPDATE` on the three tables, no `DELETE`: the
  rows are history. A retention job that must delete (M7) grants it in its own migration.

## Delivery mode and Observe (M1-65)

`Observe(ctx, LogEvent)` is called by the log tail of every api process for each durable event in
`seq` order, before the gateway hub sees it (`app/observe.go`):

- Every event raises the highest permission version seen in the log. A delivery snapshot built at an
  older version is rebuilt at its next delivery check. The key is this process-wide version, not a
  floor per principal, because a permission change without a difference of visible targets writes no
  `access.changed` (04 8.2), for example `token.revoke`; the next event of the log carries the new
  version (DECISIONS M1-65).
- `access.changed` also forgets the delivery snapshots of its audience.
- `channel.created`, `channel.updated`, `channel.archived`, `space.archived` and `thread.moved`
  advance a process-wide structure generation; snapshots of an older generation are rebuilt
  (DECISIONS M1-65).

`authorize.Delivery(ctx)` marks the checks of the hub and the gateway catch-up: the snapshot is
validated against that state instead of reading `permission_version` per check; a rebuilt snapshot
reads the current database state. Delivery implies `Filter(ctx)`, so a denial writes no audit entry
(07 4.2, R-AZ-04); requests and ops keep auditing denials. A revoked credential answers
`unauthenticated`, which the hub turns into `4012`.

Tests: `TestAuthzObserve_AccessChangedRaisesFloor`,
`TestAuthzObserve_NewRightsVersionInvalidatesWithoutAccessChanged`,
`TestAuthzObserve_StructureEventInvalidates`, `TestAuthzDelivery_DenialWritesNoAudit`.

## Action catalogue (M1-25)

The closed catalogue of [docs/spec/actions.yaml](../../../../docs/spec/actions.yaml) (ADR 0049) exists twice in generated Go code, both written by `tools/catalogen` through the `go:generate` line in `internal/kernel/authorize/doc.go` and held by `make codegen-check`:

- `internal/kernel/authorize/catalog_ids_gen.go`: the types `Action`, `EventType`, `Op`, `ResourceKind` and `ChannelOp` with one constant per entry (for example `ActionMessageRead`, `EventAccessChanged`, `OpCommandAutocompleteResult`, `ResourceAuthSession`, `ChannelOpHostControlSessionOpen`), `Parse*` and `All*`. They are the only constants of these types. The Semgrep rule `bothy-go-catalog-id-conversion` forbids, outside generated and test files, an explicit conversion (`authorize.Action(s)`), a typed declaration from a string literal, a string literal passed to `Spec`, `Registry.Event`, `Registry.Op` or `Registry.ChannelOp`, and a dot import of `kernel/authorize`; `TestNoConversionInsideThePackage` holds the hand-written files of `kernel/authorize` to the same rule. Not covered, because Semgrep has no type information: an untyped string constant or literal passed to any other function, field, return value or composite literal of these types; a conversion through a type alias or a generic function; an assignment of a literal to a variable of these types; and decoding (for example JSON) into a field of these types. Such a value still fails closed at run time (`Catalog.Spec`) or at start (`VerifyRegistrations`).
- `domain/catalog_gen.go`: the metadata keyed by plain strings, read through `LookupAction`, `LookupEvent`, `LookupOp`, `LookupChannelOp` and the list functions. Fields that 05 writes as text stay raw (`Right`, `Audit`, `ReceiveAction`, `ActionsText`); flags, classes and resource kinds are normalized as the brief of M1-25 lists them.

To change the catalogue, edit `actions.yaml`, run `make catalog` and `cd services/server && go generate ./...`, and commit all diffs.

### Unknown action

`Catalog.Spec` is the first step of every `Authorizer` (M1-28). For an action outside the catalogue it returns a `kernel/errs` error of kind internal with code `internal_error` and cause `unknown_action`, writes one ERROR record `unknown action` with `bothy.action` and `error.type=unknown_action`, and counts `bothy.authz.errors{bothy.reason=unknown_action}` (alarm `BothyAuthzError`). The HTTP chain answers `500 internal_error` without the action (07 AZ-P3).

### Start check

Start step 7 (`internal/wire`, 02 section 15.1) calls `Catalog.VerifyRegistrations` for every role, before any route is mounted, with the route bindings of the generated route table and the registry of all modules. It collects every violation: a route whose action is unknown, a system action, without a rate-limit class or with another class than the catalogue (AZ-P1); a gateway op that is unknown or goes from the server to the client; an event type that is unknown or registered by two modules; a terminal channel op that is unknown; a mentioned action that is unknown or a system action; a registration without a module name (AZ-P2); a route binding without operation id, method or pattern. A gateway op or channel op registered by two modules is accepted (the brief asks the two-module rule only for event types). Each violation is one ERROR line `registration check failed` (with `error.type` as the violation kind and, where known, `bothy.action`, `bothy.ratelimit.class`, `bothy.event.type`); the full text with operation id, op and module goes to stderr, and `bothy serve` exits with code 1. The routes are then mounted through the same catalogue (`Catalog.Class`), so there is one definition of a known action.

### How a module registers

A module that emits event types or accepts gateway or terminal channel ops declares in its port package:

```go
// Register declares what this module emits and accepts (M1-25).
func Register(r *authorize.Registry) {
	r.Event("<module>", authorize.EventAccessChanged)
	r.Op("<module>", authorize.OpTypingStart)

```

and its ticket appends the function to `moduleRegistrations` in `internal/wire/authz.go`. No module registers anything in M1-25.

## Authorize (M1-28)

`app.Authorizer` implements `kernel/authorize.Authorizer`; `internal/wire` builds it (`NewAuthorizer`) in start step 6b with the recorder of audit.

### Algorithm

`Authorize(ctx, p, a, r)` (07 section 4.2, brief M1-28 "Algorithm"):

1. `Catalog.Spec(a)` and the requirement entry of `domain/requirements_table.go`; an unknown or deferred action is an internal error with cause `unknown_action` (one ERROR record, `bothy.authz.errors`), a system action an internal error. The resource kind must be one of the action's kinds.
2. The clock is read once. Anonymous principals pass only `Public` requirements.
3. The permission version (pinned, request memo, or `instance.Versions`), the snapshot entry from the cache, the liveness checks (status, session, device, token, installation) and the pending rule (`principal_pending`, `device_pending`; `device.list` only for the own device).
4. The path is resolved fresh from `StructureSource` (thread, channel, space; a grant's target; a host has no path). A missing object is `not_found no_grant`; a hint that contradicts the structure is an internal error.
5. The effective rights on the path (`domain.Effective`): dm participation, owner, the highest level and union of capabilities of instance, space and channel grants, the operator rule, the limits of agents and apps; then the intersections with "view as" and acting for.
6. `domain.Decide`: visibility per resource kind (D4), the requirement with the reason of the deciding atom, the app scope (`domain/scopes.go`), the read-only channel, "view as" is read-only, step-up (`auth.step_up_max_age`), the guards of `agent.invoke`, `grant.create`, `grant.revoke` and `token.create` (M1-44: a personal token only for the person itself, else `forbidden not_self`; the application layer reads the holder's kind from the principal source into `domain.TokenFacts`). The requirement of `token.create` names `owner` before `self`, so a caller with neither right is refused with `owner_only` for an agent or app holder (SR5: the owner's personal token has no owner role) and with `not_self` for another person.
7. The check is recorded in the request check log; outside filter mode every denial goes to `auditing.Recorder.RecordDenial` (aggregated) and every error to `RecordDetached` with decision `error`. A recorder failure is logged and never changes the decision.

`Scope(ctx, p, a)` serves list actions whose requirement is read on a channel path or a space: it builds the visible channels, spaces, fully visible spaces and the instance-wide flag per request from the snapshot and the current structure (07 sections 7.2 and 7.4) and memoises them in the request memo only.

### Cache

The snapshot (`domain.Snapshot`) holds the direct grant maxima per target, the owner role and the groups (D5). It is cached per `(principal, session, device, token, permission_version)` in an LRU bounded by `authz.snapshot_cache_max_entries`; a hit needs `t < ValidUntil`, the earliest expiry of a grant, membership, session or token read, so an expiry takes effect without a job (AZ-P10). Structure is never cached: a channel or space created without a new permission version is judged and listed at once. Nor is the place of a thread: REST decisions resolve the channel of a thread from the structure source at decision time and cache no thread-to-channel resolution across requests, so after a `thread.move` (M1-62) no `authorize` call in any process instance evaluates the thread at its old channel (07 4.2). `thread.move` itself requires `All(Cap(manage), TargetCap(manage))` with the destination in `Resource.TargetChannelID`; an invisible or unknown destination, the nil UUID included, is `not_found` like an invisible thread (`TestThreadMoveRequirement`). The gateway's permission cache applies `thread.moved` in log order (M1-65). `platform/httpserver` installs one request memo per request (`authorize.WithRequestScope`), so the permission version is read once per request.

### Deferred actions

The requirement entries of `domain.DeferredActions()` (held by `domain/testdata/deferred_actions.golden`) need facts of a later milestone. `Authorize` and `Scope` answer them like an unknown action, and `VerifyRegistrations` rejects a route, op, channel op or event type that names one (D3). The ticket that builds one replaces its row in the table and removes it from the golden file.

### Delivery check `webhook_out.deliver` (M2-26)

`webhook_out.deliver` is no longer deferred: its requirement is `Delivery`, decided by
`Authorizer.authorizeDelivery` with `domain.DeliveryGate` before the receive action. In this order:
the liveness check of the receiving principal; a principal that is not an app is `forbidden
subject_kind_not_allowed` (agents until the agent transport); an app without `events:subscribe`
in its granted scopes is `forbidden scope_missing`; a personal event (`Resource.Audience` set) is
allowed for its audience and `not_found not_self` for anyone else; otherwise the full decision of
the receive action `Resource.DeliveryOf` on the same resource (visibility, requirement and the app
scope of the action, for example `messages:read` for `message.read`) is the result. A personal
event carries no `DeliveryOf` (its receive action is `self`); without an audience an empty
`DeliveryOf` or `webhook_out.deliver` itself is an internal error.
The delivery job calls it in filter mode, so no denial is written (AZ-P13).
### Stored events (M1-63)

`authorize.ResourceFromEvent` describes a stored event for the check of its receive action at
delivery (REST catch-up, gateway, webhooks): a thread, channel or space by its id, any other kind
with its most specific scope, and `Resource.Event` with the full scope. When the receive action
does not take the stored kind, `eventTarget` (`app/eventtarget.go`) decides on the first object
it does take: the target of a grant (for an instance grant its subject principal), then the
thread, channel and space of the scope. No fitting object, or a receive action whose requirement
is still deferred, is `not_found` without an error line, so one event never stops a reader
(`TestResourceFromEventCatalogue` decides every durable event type; docs/DECISIONS.md M1-63/9,
M1-63/12).

### How a module builds a `Resource`

Load the resource first (02 section 9.2), then describe it: `Kind`, `ID`, the path hint (`ThreadID` for things in a thread, `ChannelID` for a channel or an unattached file, `SpaceID` for a space), `OwnerID` (author, creator, holder or the principal itself) and the facts of the action (`HasAttachments` for `message.create`, `RestrictedTags`, `TargetChannelID` for `thread.move`, `Grant` for `grant.create`, `Invoke` for `agent.invoke`, `PreviewOf` for `access.preview`, `DeliveryOf` and `Audience` for `webhook_out.deliver`). Pass the `actor.Actor` of the request as the principal; it implements `authorize.Principal`. Treat an error like a denial and return it. Per-element checks of lists, searches and deliveries run with `authorize.Filter(ctx)`.

## Rights changes (M1-29)

Every rights change runs through one transactional path (02 section 8.1). A use case declares it
with `txn.DeclareRightsChange` (action of the catalogue with column "Permissions" = yes, the resource of
the deny entry, the affected principals, or targets); `platform/pg` then runs the hooks of
`app.RightsHook` that `internal/wire` registers:

1. **Phase 1, `Begin`.** First statement of the transaction: `permission_version` is locked and
   raised through `instance.Counters` (03 section 6.3), then the views (visible spaces, visible
   channels with level and capabilities) of the declared principals are recorded. For declared
   targets authz derives the affected itself: subjects of grants in effect on the target, its
   ancestors and, for a space, its channels (group members expanded), the active owners and the
   effective operators. Views use the snapshot and `Effective` of `Authorize`, never the cache.
   Before that, the due expiries are folded in (M1-30, section "Sweep and the fold of due
   expiries").
2. **Phase 2, the use case.** It writes; a principal it learns about only now (a new operator)
   it names with `RightsChanges.AddAffected` before writing rows that concern it.
3. **Phase 3.1, `BeforeCommit`.** `VerifyInvariants` (SR8: at least one active owner; I1: for
   every active personal agent the trigger set over its served targets is exactly its credential
   holder). A violation rolls the unit back with `InvariantError` (`409 last_owner` before
   `409 i1_violation`, the problem body carries `conflicts`), and the deny entry goes to
   `auditing.Recorder.RecordDenial`, which writes it in its own transaction. Otherwise one
   `access.changed` per principal with a non-empty difference is appended and
   `authorize.AccessChanged` is published once; a subscriber veto rolls everything back.

The store refuses writes of memberships and grants and the deletion of a group outside a unit
declared as a rights change, and the Authorizer neither reads nor fills its cache or version memo
inside one (the unit sees an uncommitted version). A hook that is not bound (`Bind` with the
appender and the recorder, start step `authz`) fails every rights change.

### How another module declares a rights change

```go
err := uow.Do(ctx, func(ctx context.Context) error {
	if err := rights.AddAffected(ctx, newOperator); err != nil { // authz.RightsChanges
		return err
	}
	return repo.SetOperator(ctx, channelID, newOperator)
}, txn.DeclareRightsChange(txn.RightsChangeSpec{
	Action:     string(authorize.ActionChannelOperatorSet),
	Resource:   txn.Ref{Kind: string(authorize.ResourceChannel), ID: channelID},
	Principals: []ids.ID{oldOperator},

```

### `access.changed`

Personal event (04 section 2.2): `audience = self`, resource `principal`, no scope, the actor of
the request (`system` for a system action without one), payload `AccessChangedPayload` with the
version of phase 1 and the lists `added`, `removed`, `changed` (always present, sorted by kind and
id; spaces only appear or disappear; channels carry level and capabilities, changed ones also
`previous_level`). A change without visible effect raises the version and writes no event.

### Admin

Each method loads the resource, authorizes it (step-up for all, the delegation limits of
`grant.create` and `grant.revoke`, 07 section 2.6, which belong to the requirement since M1-48),
runs in one unit of work and records the allow
entry in it (ids and codes only, the reason as `ReasonText`). Calls without effect (deleting a
deleted group, removing a removed or expired membership, revoking a revoked grant, an update
without change) succeed without rights version and audit `no_change: true`; they decide that in
a first unit without rights change. Missing and invisible resources give the same `404`.
Grants on hosts give `404` until M2-39 adds hosts. `group.name_max_chars` and
`group.description_max_chars` reach `AdminConfig` through `wire.NewAuthzAdmin` (M1-48).

## Groups and grants over the API (M1-48)

`adapters/httpapi` implements `listGroups`, `createGroup`, `getGroup`, `updateGroup`,
`deleteGroup`, `listGroupMembers`, `addGroupMember`, `removeGroupMember`, `listGrants`,
`createGrant`, `getGrant` and `revokeGrant` over the port `authz.Admin`, and `Cursors`, the
cursor codec of `platform/httpserver` behind `app.Cursors`. `internal/wire` builds the use cases
in start step 6c (`NewAuthzAdmin`, configuration `AdminConfig`: `group.name_max_chars`,
`group.description_max_chars`, `api.page_size_default`, `api.page_size_max`) and embeds the
handlers as `Handlers.Access`.

### Use cases

- Reads (`app/adminread.go`): `ListGroups`, `GetGroup`, `ListGroupMembers`, `ListGrants`,
  `GetGrant`. The query and the counts of a request use one clock read; lists are keyset pages by `id` with cursors bound to the
  caller and the filters (`400 cursor_invalid` otherwise), `limit` capped at `api.page_size_max`,
  no totals. The list scope comes from `Authorizer.AdminScope` (owner role and the spaces and
  channels with effective `manage`, from the rights snapshot and the current structure).
- Writes (`app/admin.go`): the M1-29 methods, with `CreateGroup` for local and claim groups
  (`provider_id` and `external_ref` only for `oidc_claim`), the subject check of `CreateGrant`
  after `authorize` (`400 validation_failed`, `/subject_id`, `unknown_subject`), the member check
  of `AddGroupMember` (`/user_id`, `unknown_user`), a reason that is not blank for every
  revocation and `group_deleted` as the revocation reason of a deleted group's grants.

### Visibility

| Operation | Not visible (`404`, like a random id) | Visible, not allowed (`403`) |
|---|---|---|
| `listGroups` | | owners list every live group; anyone else the groups with a membership in effect; a `member_id` filter for another person gives an empty page |
| `getGroup`, `listGroupMembers` | deleted, unknown, or caller neither owner nor member in effect | |
| `createGroup` | | `owner_only` |
| `updateGroup`, `deleteGroup`, `addGroupMember`, `removeGroupMember` | as `getGroup` | `owner_only` |
| `listGrants` | a target filter the caller cannot read | a readable target without `manage`; the instance for everyone but owners |
| `getGrant`, `revokeGrant` | unless owner or `manage` on the grant's target (a channel inherits it from its space); instance grants owner only | `revokeGrant`: the delegation reasons |
| `createGrant` | a target the caller cannot read | `owner_only`, the delegation reasons |

Every operation with an id authorizes before it answers a missing resource, so a caller that
`authorize` refuses before visibility (anonymous, a pending device) gets the same answer for an
existing and an unknown id; the shape of a write is checked before `authorize` without the
caller's id. Non-owners see grants only inside their `manage` scope; the query applies the scope, so filters
narrow it and never widen it (07 section 2.6 item 6). `grant.read` on an instance grant is
checked as `grant.read` on the caller as `principal`, whose requirement is `owner`. Step-up comes
after the requirement and the delegation limits: without a fresh step-up `401
step_up_required`, with a token without a session `403 forbidden`
(reason `step_up_not_possible`).

### Events

Every write appends, in its unit of work, `grant.changed` (`created` or `revoked`; resource the
grant, scope the target's space and channel, receive action `grant.read`) or `group.changed`
(`created`, `updated`, `deleted`, `member_added`, `member_removed` with `user_id`; empty scope,
receive action `group.read`, `member_count` counted after the change). Deleting a group appends
one `grant.changed` per revoked grant and one `group.changed`. `access.changed` comes only from
the rights hook (M1-29). Calls without effect append nothing.

## Who has access, preview and view as (M1-49)

`adapters/httpapi` implements `explainSpaceAccess`, `explainChannelAccess` (`access.explain`),
`previewGrant` (`access.preview`) and `viewAsUser` (`access.view_as`) over `authz.Admin`. The use
cases compute with the Authorizer and the rights hook of authz (`AdminDeps.Engine` and `Hook`),
so an explanation, a preview and a view cannot disagree with a real decision. Rulings:
docs/DECISIONS.md M1-49.

- `ExplainAccess` (07 section 9.1): `authorize(access.explain)` first (no read `404`, read
  without `owner` or `manage` `403`); then the owners (active or not), the subjects of grants not
  revoked on the target's path with the members of such groups, the operator of a channel or the
  default operator of a space and the participants of a dm channel. Each gets its effective rights
  from `readGrants`, `BuildSnapshot` and `Effective` (built as active, so an inactive principal
  shows what its grants would give, with `inactive`) and its sources from `domain.Provenance`.
  `via_agent` (H1): a person in T(A) of an active agent A whose H(A) holds the channel (or, for
  a space, one of its channels) the person cannot read; `guard_blocked`: `trigger` on a target
  whose operator has the effective tool class `host` (SR2). Entries with level `none` stay only
  with `via_agent`; owners first, then by display name, then by id.
- `PreviewGrant` (07 section 9.3): the shape like `createGrant`, `authorize(access.preview)` with
  the requirement of `grant.create` (no step-up, no audit), then the delegation limits
  (`CheckCreate`; a limit is `allowed = false` with `denial_reason`). The dry run runs the apply
  step of `createGrant` in a unit of work with the same rights change, reads
  `RightsHook.Evaluate` (I1, SR8, the views before and after) and the hints inside it and ends with
  the sentinel `errPreviewRollback`, so the sync and audit hooks never run: no row, counter or
  notification survives. The text comes from `domain/previewtext` in the caller's language and
  time zone.
- `ViewAs` (07 section 9.2): `authorize(access.view_as)` (owner in a session, step-up; denials
  audited by `authorize`), `404` for an id that is not a person, then `Scope` for `message.read`
  and `space.read` with `actor.ViewAs{UserID, StartedAt}` and the rights of `authorize` per item:
  the intersection of owner and person, without dm channels and archived structure. The allow
  entry carries `target_user_id` and `expires_at`. `authorize` refuses every write under "view
  as" with `view_as_read_only` and answers `step_up_required` from `StartedAt +
  authz.view_as_max_duration` on.

## Expiry (M1-30)

Expiry is decided at every `authorize` call: a grant or membership is invalid from the second of
its `expires_at` (07 section 2.5), and a cached snapshot ends at `valid_until` (AZ-P10, proven
again by `TestAZ_P10_ExpiryWithoutJob` with no job running). The two jobs only report.

| Job | Registered by | Queue | Period | Arguments |
|---|---|---|---|---|
| `authz.expiry_sweep` | `adapters/jobs.Register` from `internal/wire` (every role builds the registry; `worker` and `all` run it) | `maintenance` | `authz.expiry_sweep_interval` | none |
| `authz.expiry_reminder` | the same | `maintenance` | `authz.expiry_sweep_interval` | none |

### Sweep and the fold of due expiries

Every rights change folds in the expiries that are due and not reported yet, as the first step
after phase 1 has locked and raised `permission_version` (`expiryfold.go`):

1. `ExpiryStore.DueExpiredGrants` and `DueExpiredMemberships` select the rows that are not revoked
   or removed, with `expires_at <= t` and `expiry_reported_at IS NULL`, in ascending id, `FOR
   UPDATE` (03 section 6.3).
2. The principals they affect (the subject of a grant to a user, agent or app; every member that
   is not removed of a group that is not deleted for a group grant; the member of a membership)
   get their view before with these rows treated as not expired (`domain.AssumeValid`).
3. `expiry_reported_at = t` is set, `grant.changed` (`change = expired`, scope space and channel)
   or `group.changed` (`change = member_expired`, `user_id`, empty scope) waits for phase 3.1
   with `actor = system`, and one allow audit entry per row is recorded without actor and without
   IP pseudonym, also inside a person's change (`grant.expire`: `subject_kind`, `subject_id`,
   `target_kind`, `target_id`, `expires_at`; `group.member.expire` on the group:
   `membership_id`, `user_id`, `expires_at`). `group.changed` is built in phase 3.1, so its
   `member_count` includes the memberships the change itself wrote.
4. Phase 3.1 appends these events, verifies I1 and SR8 and writes `access.changed` for every
   principal whose visible targets changed, with the action of the unit.

`ExpiryService.Sweep` is a rights change that only folds: units declared as `grant.expire`, then
`group.member.expire`, each folding at most `authz.expiry_sweep_batch_max` rows of its kind,
repeated while a batch was full. A batch without rows rolls back, so `permission_version` only
moves when something expired. An invariant violation (only possible in a world that was already
invalid) rolls the batch back, leaves the deny entry with the agent ids in the audit log, is
logged with the action, and the job returns the error so River retries.

**Exactly once.** The marker, the events and the audit entries commit in one transaction with
the change; an error rolls everything back and the next unit selects the same rows again. The
selection hangs on the stored marker, not on the time of the last run, so rows that expired while
the worker was down are found on the next run, and the lock of `permission_version` before the
row locks keeps two units from reporting a row twice. The trigger `authz_grants_immutable` allows
`expiry_reported_at` on grants to be set only once.

**Why every change folds.** A view is what the client was told, and an expiry reaches the client
only once it is reported. After the fold no due row of the change is unreported, so its view
before is what the client was told and its view after is what `authorize` decides: a loss through
an expiry is reported once (by the sweep or by the first rights change after the expiry, which
then also writes the event and the audit entry of the expiry), and no change reports a gain that
`authorize` denies. Rows not due yet, and in a sweep batch the rows of a later batch, count as
valid in both views (`domain.AssumeValid.Unreported`).

A grant revoked or a membership removed before its expiry is never reported as expired: the
revocation wrote its own `access.changed`. Memberships of deleted groups are folded too; their
difference is empty, so no `access.changed` follows. The cancellation of runs of people who lost
`trigger` subscribes to `authorize.AccessChanged` in M2.

### Reminder

`ExpiryService.Remind` runs batches in units of work without rights change: grants, then
memberships, with `t < expires_at <= t + authz.expiry_reminder_lead` and `expiry_reminded_at IS
NULL` (grants of deleted groups and memberships of deleted groups are not selected). Per row one
`access.expiring` per active recipient, without duplicates: subject and `granted_by` for a grant
to a user, agent or app; all active owners and `granted_by` for a grant to a group; member and
`added_by` for a membership. The payload `AccessExpiringPayload` carries `target` only for space and
channel grants. `expiry_reminded_at = t` is set in the same transaction, so each row is
reminded once; a grant created with less than the lead left is reminded on the next run.
Reminders write no audit entry and send no e-mail.

## Claim groups (M1-42)

Groups with `source = oidc_claim` follow the group claim of their provider at every OIDC login
(08 section 3.4, system action `group.member.sync`).

- Port: `ClaimSync` with `SyncClaimGroups(ctx, SyncClaimGroupsCmd) (SyncClaimGroupsResult, error)`,
  part of `Admin`; `ErrClaimSyncNeedsRightsChange`; `HintI1ClaimSync`; `InvariantError.WithHint`.
  identity calls it inside the unit of work of `completeOidcLogin`.
- Domain (`domain/claimsync.go`): `ReconcileClaimMemberships(provider, current, matched, claim, now,
  maxAge)` returns `ClaimDiff{Add, Extend, Remove, ExpiresAt}` (group ids sorted). Only live claim
  groups of the login's provider take part; local groups, deleted groups and claim groups of other
  providers are never touched; unknown values are ignored; an expired membership is extended,
  never duplicated.
- Use case (`app/claimsync.go`): locks the person's claim memberships of the provider
  (`Store.LockClaimMembershipsOfUser`, `FOR UPDATE` in ascending id), reads the matched groups
  (`ClaimGroupsByRefs`) and computes the diff. An empty diff writes nothing. In a unit without a
  rights change a non-empty diff returns `ErrClaimSyncNeedsRightsChange` and writes nothing; in a
  unit declared for `group.member.sync` it names the person as affected, removes (`removed_by` the
  person), extends (`Store.ExtendMembership`: new `expires_at`, `expiry_reminded_at` and
  `expiry_reported_at` cleared, so the new expiry is reminded and reported once) and adds
  (`added_by` the person, `expires_at = now + auth.group_claim_max_age`), appends `group.changed`
  (`member_added`, `member_removed`) per addition and removal and records one allow entry
  (resource the person, actor the person, details `provider_id`, `added`, `removed`, `extended`:
  group ids only, never a claim value).
- Rights hook: the use case leaves a per-unit state, so the rights check of the unit names the
  person as actor of `access.changed`, and on an I1 violation writes the deny entry with the
  person as actor and resource and the details `provider_id`, `group_ids`, `agent_ids` beside the
  violations, and answers with `HintI1ClaimSync`.
- Tests: `domain` (`TestReconcileClaimMemberships`), `app` (`TestSyncClaimGroups_AddExtendRemove`,

## Target host (M2-39)

A host is a target outside the tree instance, space, channel (07 section 2.12):

- **Source.** `HostSource` (`Host`, `HostIDs`, `AssignedTo`) with `HostFacts` (state, holder, LLM
  declaration, server host); terminal implements it (`terminal/app.HostSource`), `internal/wire`
  binds it for the Authorizer, the rights hook and the Admin use cases. A nil source means a world
  without hosts: every host is not found.
- **Snapshot.** `Snapshot.Hosts` holds the capabilities of the host grants in effect (own and of
  the groups in effect); their expiries enter `ValidUntil`. `TerminalOn(s, h)` is an effective owner
  or a grant `terminal` on `h`; the I6 exception for owners belongs to SR11 (M2-40).
- **Requirements.** `host.read` is `All(HumanSession, Any(Owner, Assignee, Terminal))`,
  `host.manage` `All(HumanSession, Owner)`. A requirement whose first part is `HumanSession` is a
  gate: `authorize` and `Scope` refuse agents, apps and personal tokens with
  `subject_kind_not_allowed` right after the liveness checks, before any resource is resolved.
  `host.pair` is `Public` since M2-41 (the use case proves the pairing code before `authorize`, as
  for the refresh token); `host.connect` stays deferred for M2-43; the terminal actions are real
  since M2-40 (section below).
- **Visibility.** A host resource resolves through the source; it is visible to an effective
  owner, its holder and a person with `TerminalOn`, with "view as" to both views, and to any
  principal for an action whose requirement is exactly `Public` (only `host.pair`, M2-41).
- **Scope.** `Scope(host.read)` gives `AllHosts` to an effective owner, otherwise the ascending
  `HostIDs` of the terminal grants and the own hosts, intersected with "view as".
- **access.changed.** `AccessView.Hosts` holds the hosts with `TerminalOn` (every host for an
  owner); a host is `added` with `capabilities: ["terminal"]` and no level or `removed`. The rights
  hook derives the affected principals of a `host` target: every active owner, the holder and the
  subjects of the grants on the host (`Store.ActiveGrantsOnHosts`, groups expanded).
- **Grants.** `CreateGrant` on a host needs an existing host and refuses a retired one with `409
  conflict`; subject and capability rules stay with `CheckGrantShape`.
- **Tests.** `TestHostRequirement`, `TestAZM60_InstanceGrantGivesNoHost`, `TestScope_Hosts`,
  `TestSnapshot_HostGrants`, `TestDiffVisible_Hosts` and the hosts of the AZ-P8 differential test.

## Apps (M2-24)

- **Scope check.** An app needs the scope of each action in `GrantedScopes` of its installation
  and, when the request carries an API token, in the token scopes (`kernel/authorize.Principal`
  gained `AppTokenScopes`, which `actor.Actor` answers with `Scopes`); missing in either is
  `forbidden` `scope_missing`. A check without a token (a webhook delivery of M2-26) uses the
  installation alone. `Scope` filters the lists of an app with the same rule. Agents are unchanged.
  This replaces ruling M1-28 D6 (token scopes not evaluated); docs/DECISIONS.md D-M2-24-10.
- **Snapshot.** `PrincipalFacts.AppInstallationActive` (set by identity from
  `identity.AppInstallations`): an app without an active installation has an empty snapshot and an
  empty access view, like a principal that is not active (`PrincipalFacts.GrantsInEffect`). So
  `app.suspend` and `app.uninstall` remove every visible target of the app and `app.resume` adds
  them again; the rights hook writes `access.changed` for them. A change of the granted scopes alone
  changes no visible target and writes none (the gap of docs/DECISIONS.md D-M2-24-11).
- **`AppScopes`** (`appscopes.go`, implemented by `app.ScopeTable`): `EventScope` decides which
  durable event types an app may subscribe to (`domain.AppEventScope`: a receive action of the
  scope table, or `interaction.created` and `command.invoked` with `events:subscribe`) and
  `Scopes` lists the scopes of the catalogue.
- **`Admin.RevokeSubjectGrants`**: revokes every active grant of a principal in ascending id inside
  the caller's rights change, without `authorize` per grant (a consequence of the authorized
  `app.uninstall`).
- **The collection of apps.** `app.read` on a resource of kind `app` without an id is the
  collection (`listApps`, `validateManifest`): visible like the instance, so the requirement owner
  answers a non-owner `owner_only`; one app stays invisible to non-owners (`not_found`).
- Tests: `domain/appscope_test.go` (`TestAppEventScope_AllCatalogueEvents`,
  `TestAppScope_TokenAndInstallation`), `app/appscope_test.go`
  (`TestSnapshot_AppWithoutActiveInstallationIsEmpty`, `TestAZM32_TokenScopes`,
  `TestAppCollection_OwnerOnly`, `TestScopeTable`, `TestRevokeSubjectGrants`).
