# Module `files`

Status: skeleton (M1-05) plus object storage port and file system driver (M3-01), the S3 driver (M3-02), the upload sessions in mode `direct` with `getFile` (M3-03), the scan pass with clamd (M3-04), the downloads with download tickets and transcripts (M3-05) the removal of image metadata with thumbnails (M3-06), avatar and logo files (M3-10), the attachments of messages (M3-07), the read operations for the search coordinator (M3-14) and the text extraction of attachments (M3-15). The other use cases follow with the tickets of milestone M3.
The normative source is [docs/spec/02-architecture.md](../../../../docs/spec/02-architecture.md); if this file differs, the chapter applies.

Upload sessions in parts, object storage drivers, scan, metadata removal, thumbnails, attachments, transcripts, file text extracts.

## Upload sessions (M3-03)

Normative: [12-files.md](../../../../docs/spec/12-files.md) sections 2, 3 and 6, the rulings D-M3-03-1 to D-M3-03-27 in [docs/DECISIONS.md](../../../../docs/DECISIONS.md).

- **Port.** `Uploads` (`Create`, `PutPart`, `State`, `Complete`, `Abort`) and `Files` (`Get`); the actor comes from `kernel/actor`. An unknown and a foreign file answer the same `404`. `Register` declares `file.updated`.
- **Tables.** `files` (retention class `content`), `file_upload_sessions` and `file_upload_parts` (retention class `transient`), exactly as 03 4.7; `files.search_vector` of 03 5; the foreign key `principals.avatar_file_id -> files(id) ON DELETE SET NULL`, added `NOT VALID` and validated by the next migration. The retention jobs are M7-05.
- **Actions.** `createUpload`, `uploadPart`, `getUpload` and `completeUpload` authorize `file.upload` on the scope channel; `abortUpload` authorizes `file.delete`, `getFile` `file.read`, both on the file with `authorize.FileFacts` (before attachment only the uploader sees the file).
- **Event.** Only `abortUpload` and the abort after a lost read right write `file.updated` (receive action `file.read`, payload `FilePayload`), with `audience_principal_id` = uploader; create and completion write none. `app.FileUpdated` is the one builder; since M3-07 only `recordFileChange` calls it (see Attachments).
- **Part strategies.** `app.PartStore`, chosen in `internal/wire` from `file.storage.driver`: `fs` keeps part `n` as `uploads/<file_id>/<n>` (ETag derived from its SHA-256), `s3` as part `n` of a multipart upload of the final key, created at the first part with its id in `storage_upload_id`. Completion calls no object store; the verify pass of M3-04 joins the parts or runs `CompleteMultipart`. No object store call runs inside a unit of work (02 8.5).
- **Outgoing ports.** `Repository` (adapters/postgres), `PartStore`, `FreeSpace` (the file system driver), `NameNormalizer` (adapters/unicode), `TypeExtensions` (adapters/mimetype), `ChannelLocator` (adapters/channels over `chat.Structure.NotificationPath`), `Metrics` (adapters/otelmetrics).
- **Query exceptions (AZ-P12).** Every read is keyed by the file id or the uploader and stands with this reason in `tools/lint/sql_visibility.yaml`: `files.GetFile` and `files.GetSession` resolve one file for authorize, `files.QuotaUsedBytes` and `files.CountOpenSessions` count the caller's own files and sessions, `files.LockSessionForUpdate` and `files.LockSessionForShare` lock the caller's own session. The writes touch only rows of a session the use case authorized.
- **Logs and metrics.** Lines carry at most `bothy.file.id`, never a name, digest, declared type or channel name (the file name is a canary value, SEC-T10). `bothy.file.upload.size` has no attributes.
- **Tests.** Unit tests in `domain` and `app` (fakes; the fake object store fails any call inside a unit of work); integration tests in `test/uploads` through the real server (`go test -tags contract_validate ./test/uploads/`); the paths of `test/canary`, `test/leak` and the G7 hook of `tools/contract`.

## Scan pass (M3-04)

Normative: [12-files.md](../../../../docs/spec/12-files.md) sections 2, 3.4, 5 and 6.1, [ADR 0033](../../../../docs/adr/0033-malware-scan-of-uploads-as-a-separate-service.md), the rulings D-M3-04-1 to D-M3-04-16 in [docs/DECISIONS.md](../../../../docs/DECISIONS.md).

- **Job.** `files.scan` (args `FileID`, `Round`; queue `files`; no River job timeout) is inserted by `completeUpload` in its unit of work through `app.ScanQueue` (`adapters/jobs.Queue` over `jobs.Inserter`). The handler runs `app.ScanPass.Run` inside the CLIENT span `file.scan` with `bothy.file.id` and `bothy.outcome`.
- **Pass.** A file awaits the pass when its session is `completed`, it is not deleted and both states are `pending`. In mode `required` the pass pings clamd first; then it reads the bytes once (the object when it exists; on S3 after `CompleteMultipart`; otherwise the parts in order, joined into the object through a pipe), limited to the declared size plus one byte, and tees them to SHA-256 and the counter, the head of `file.sniff_bytes` for the type, the assembly and clamd. The outcome table is `domain.DecidePass`; `domain.IsDeliverable` and `domain.Final` are the only definitions of 12 2 (`domain.ReadinessOf` sorts the states for the downloads of M3-05). No scanner or object store call runs inside a unit of work.
- **Result.** One unit of work locks the session and then the file (the order of M3-03), checks again, writes the states, `mime_type`, `scanned_at` and `scan_engine` and the session's `failure_reason`, records the malware entry (`file.upload`, deny, `malware_detected`, details `signature`, `sha256`, `size_bytes`) and calls `recordFileChange` without actor, which appends `file.updated`, publishes `files.FileFinalized` for a file that became final (M3-07) and runs the trigger of the text extraction for a file that became deliverable (M3-15); M3-06 inserts `files.thumbnail` after it. After the commit the objects of failed and blocked files and the parts go.
- **Retry rule.** A transient failure inserts the next round with a delay doubling from `file.scan.health_interval` up to `file.scan.retry_backoff_cap`, without an attempt limit, and changes nothing else (Warn log with `bothy.file.id` and the reason class `unreachable`, `timeout`, `protocol` or `storage`).
- **Residual crash window.** A process that dies between the commit of the result and the deletions leaves the objects of a failed or blocked file, or the parts of a clean one, in storage; the sweep of M3-08 removes them. Such objects are never served, because delivery reads the states.
- **Ports.** `Scanner` (`adapters/clamd`, standard library only, Unix socket only, at most `file.scan.max_concurrent` scans per process), `TypeDetector` (`adapters/mimetype.Detector`), `ScanQueue` (`adapters/jobs`), `ScanRepository` (`adapters/postgres`), `ScanMetrics` (`adapters/otelmetrics`: `bothy.file.scan`, `bothy.file.scan.duration`, `bothy.file.scan.queue`). The port package declares `FileFinalized` and `ScannerHealth`; `app.ScanHealth` implements it per worker process and never changes readiness.
- **Logs.** Constant messages with `bothy.file.id`, `bothy.outcome` or `bothy.reason` only; no file name, signature or clamd reply text outside the audit log.
- **Tests.** Unit tests in `domain` (with `FuzzParseClamdReply`) and `app` (fakes); the client against the fake clamd of `adapters/clamd/clamdtest` and against a real clamd container of the pinned image (`clamdtest.Image`, equal to `BOTHY_CLAMAV_VERSION`; one test signature for EICAR built at run time, no signature download, label `org.bothy.test=clamdtest`); integration tests in `test/scan` through the harness. They need a Docker-compatible runtime and fail without one: `cd services/server && go test ./internal/files/adapters/clamd/ ./test/scan/`.

## Downloads, tickets and transcripts (M3-05)

Normative: [12-files.md](../../../../docs/spec/12-files.md) sections 2, 7.3, 8.2 and 9, [ADR 0048](../../../../docs/adr/0048-file-download-only-through-the-server-with-short-lived-tickets.md), the rulings D-M3-05-1 to D-M3-05-20 in [docs/decisions.d/M3-05.md](../../../../docs/decisions.d/M3-05.md).

- **Port.** `Files` gains `Open(ctx, OpenRequest)` (`downloadFile` with variant `original`, `downloadThumbnail` with its variant; returns a `Delivery` with status `200` or `206`, size, served range, the header values and the body the caller closes), `IssueTicket(ctx, fileID, variant)` (`createFileTicket`; returns `IssuedTicket{URL, ExpiresAt}`; M3-22 builds the push preview on it) and `Transcript(ctx, fileID)` (`getTranscript`; returns `TranscriptView`). The actor comes from `kernel/actor` in the context. `app.Service.EnableDownloads(DownloadConfig, DownloadDeps)` adds them in the roles `api` and `all`.
- **Read path of `Open`.** (1) Who asks: the actor of the chain when it is not anonymous (the `Authorization` header wins over a ticket, D-M3-05-3); for an anonymous request with `ticket` the verified ticket and `identity.Auth.SessionActor(principal, session)`; an anonymous request without a ticket gets `401` before the file is read. (2) `FileForDelivery`: unknown or deleted is `404`. (3) `authorize(file.read)`; on the ticket path every refusal is the unknown-id `404` (D-M3-05-4). (4) Readiness: `409 file_blocked`, or `409 file_not_ready` with `Retry-After` from `file.not_ready_retry_after`; only a reader learns the state. (5) Variant: the file itself, or its row of `file_thumbnails` (`404` when missing). (6) Range (`domain.ParseRange`): `416` with `Content-Range: bytes */<size>` when unsatisfiable. (7) `ObjectStore.Get` with the range; a missing object of a deliverable file is `500` with the file id in the error log, any other storage failure `503` (D-M3-05-6). The adapter writes the headers before the first byte and aborts the connection on an error after it. Downloads, tickets and transcripts write no state of their own: no unit of work, lock, event or job; only `authz` audits a denial.
- **Delivery headers.** `Content-Type` and `inline` only for the inline list of 12 9.3 (`domain.Presentation`), everything else `application/octet-stream` and `attachment`; `Content-Disposition` with the ASCII fallback before `filename*` (`domain.ContentDisposition`, an empty name becomes `file`); a thumbnail is named by `domain.ThumbnailName`. Always `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin`, `ETag: "<sha256 hex>"` and `Repr-Digest: sha-256=:<base64>:` of the whole variant (for a thumbnail computed by one extra full read, D-M3-05-10), `Accept-Ranges: bytes` and `Content-Length`; `206` adds `Content-Range`. `Cache-Control` is `private, max-age=<client.cache_max_age>, immutable` with normal authentication and `private, no-store` with a ticket; it overrides the `no-store` of the chain on `200` and `206`, while problem responses keep the API headers.
- **Ticket layout** (`domain.EncodeTicket`, `domain.DecodeTicket`, D-M3-05-1). Payload: version byte `1`, file id (16 raw UUID bytes), variant code byte (`original` 0, `small` 1, `medium` 2, `large` 3, `poster` 4), principal id and auth session id (16 bytes each), expiry as `uint64` big-endian Unix seconds. Ticket: base64url without padding of the payload followed by the full HMAC-SHA-256 tag over it; any other length, alphabet, version or variant code is invalid, and tags are compared with `hmac.Equal`. The ticket URL is the relative reference `/api/v1/files/{file_id}/content?ticket=<t>` or `/api/v1/files/{file_id}/thumbnails/{variant}?ticket=<t>`. The ticket and its URL are bearer secrets: no log line, span attribute, problem body or audit row carries them.
- **Key ring.** `app.TicketKeySource` (implemented by `wire.TicketKeys` over the secret provider and `file.ticket_key_ref`) returns the current key and its version. The service keeps the key it saw before the last version change as the previous key, verifies against current and previous and mints with current. The roles `api` and `all` do not start when the key is missing, unreadable or shorter than 32 bytes as hex (D-M3-05-15).
- **Rotating the ticket key.** (1) Replace the file that `file.ticket_key_ref` points to (by default `file_ticket_key` in `secrets.dir`) with a new key of at least 32 random bytes as hex. (2) Wait `secrets.cache_ttl`: each process picks up the new key when its provider cache expires, mints new tickets with it and keeps the old key as the previous one. (3) Tickets minted with the old key keep working until they expire (`file.ticket_ttl`) in every process that saw the old key. The previous key lives only in process memory: a process that starts or restarts after the change knows only the new key and refuses old tickets, so avoid restarts within `file.ticket_ttl` after a rotation; a refused player asks for a new ticket. While processes switch, a ticket minted by a process that already switched may be refused by one that has not, for at most `secrets.cache_ttl`; the player then asks for a new ticket. A second rotation within `file.ticket_ttl` invalidates the tickets of the key two versions back.
- **Session rule.** `IssueTicket` sets the descriptor fact `IssueTicket`, so `authz` refuses a principal without a login session with `403 forbidden` `step_up_not_possible` after visibility (D-M3-05-2); the use case also checks readiness (D-M3-05-7) and that the thumbnail variant exists. `file.read` follows the purpose of the file (D-M3-05-18, `internal/authz/README.md`).
- **Transcript.** `Transcript` needs normal authentication (a ticket is never read there); after `file.read` and readiness it returns the status of every deliverable file, with text, language and source only when the status is `done` (D-M3-05-8).
- **Table.** `file_thumbnails` (migration `00056_files_thumbnails.sql`, exactly as 03 4.7, D-M3-05-16); the image job of M3-06 writes it. `files.GetFileForDelivery` and `files.GetThumbnail` are keyed by the file id.
- **Tests.** Unit tests in `domain` (ticket codec with `FuzzDecodeTicket`, ranges with `FuzzParseRange`, presentation, `FuzzContentDisposition`, names, readiness); the use cases are tested as integration tests in `test/download` through the real server: `cd services/server && go test ./test/download/`.

## Images: metadata and thumbnails (M3-06)

Normative: [12-files.md](../../../../docs/spec/12-files.md) sections 2, 3.4 and 7, [ADR 0047](../../../../docs/adr/0047-remove-image-metadata-losslessly.md), the rulings D-M3-06-1 to D-M3-06-16 in [docs/DECISIONS.md](../../../../docs/DECISIONS.md).

- **Job.** `files.thumbnail` (args `ThumbnailArgs{FileID}`; queue `files`; River timeout `file.image.processing_timeout`, River's default attempts and backoff) is inserted by the final unit of work of `files.scan` for a clean or skipped JPEG, PNG (also `image/apng`), GIF or WebP, which stays `upload_state = 'pending'`, and for MP4 and QuickTime files, which are `complete`. It is a finalizing job: T1 and the failure transaction publish `files.FileFinalized` for the image types, the scan does not. The use case `app.ImageProcessor.ProcessImage` takes a slot of the per-process limit `file.image.max_concurrent` first.
- **Phases.** Original: JPEG and PNG run through the allow-list filter twice (first into SHA-256 and a counter, then into `Put(orig-2)`; a JPEG is scanned once more before, because the rewritten `APP0` and the new `APP1` come first), so no spool file exists (12 3.2, 4.2); GIF and still WebP are decoded and encoded in memory; then T1 sets `object_key`, `sha256`, `size_bytes`, `mime_type`, the display `width` and `height` and `complete`, and `orig-1` is deleted after the commit. A broken JPEG or PNG fails with `image_malformed` and loses its objects. Thumbnails: `small`, `medium`, `large` from the stored original, then T2 inserts the `file_thumbnails` rows (`ON CONFLICT DO NOTHING`). Container: `mvhd`, `tkhd`, `hdlr` and `mehd` through ranged `Get` calls, then T3 where a value is new. Every unit locks only the `files` row and writes one `file.updated` when it changed something; no object store call runs inside a unit.
- **Revision marker.** Every processed original is revision 2; `domain.ParseOriginalKey` returns the revision (no separate `OriginalRevision`). Objects are never overwritten: only keys no row refers to are written, and a run whose precondition fails deletes what it wrote unless the locked row refers to it.
- **Pixel guard.** Before any decode the codec reads only headers (segment scan, IHDR, GIF block scan, RIFF chunks) and refuses more than `file.image.max_pixels` (times frames for GIF); JPEG and PNG above it are still cleaned, a GIF or WebP above it stays unchanged.
- **Vendors.** `golang.org/x/image` (vendor group `ximage`) for WebP decoding and Catmull-Rom; depguard narrows it to `adapters/imaging`. No cgo: `TestStandardBuildWithoutCgo` fails for any non-standard package with cgo files in the dependencies of `cmd/bothy`.
- **Logs.** Only `bothy.file.id` and an error class; never a name, metadata value, profile or image byte.
- **Tests.** Unit tests in `domain`, `app` (fakes), `adapters/imaging` (test images built in code, fuzz targets `FuzzStripJPEG`, `FuzzStripPNG`, `FuzzEXIFOrientation`, `FuzzGIFScan`, `FuzzWebPScan`), `adapters/isobmff` (`FuzzReadMovieInfo`); integration tests in `test/images` through the harness with the seam `wire.Deps.FilesImageHooks` (needs a Docker-compatible runtime).

## Avatar and logo (M3-10)

Normative: [12-files.md](../../../../docs/spec/12-files.md) sections 3.7, 12 and 13, the rulings D-M3-10-1 to D-M3-10-23 in [docs/decisions.d/M3-10.md](../../../../docs/decisions.d/M3-10.md).

- **Source ports.** `identity.AvatarFiles` (`Stage`, `Attach`, `Release`) and `instance.LogoFiles` (`Stage`, `Attach`, `Release`, `OpenVariant`), implemented by `adapters/profileimages` (`Avatar`, `Logo`) as thin delegation to `app`; `internal/wire` hands them to `identity` and `instance`, whose handlers own the actions `self.profile.update` and `instance.branding.update`. This is the reason for the dependency on `instance`.
- **Purpose rules.** `domain/purpose.go`: `Purpose` (`attachment`, `avatar`, `branding`, `gdpr_export`), `DeclaredImageTypeAllowed` (`image/jpeg`, `image/png`, `image/webp`), `StoredOriginalAllowed` over `OriginalKind` (only filtered JPEG, filtered PNG and converted still WebP for `avatar` and `branding`; `attachment` is never refused), `FixedOriginalName` (`avatar`, `logo`) and `ImageCap` (the smaller of `file.max_upload_bytes` and `file.upload_part_bytes`).
- **Use cases.** `app/profileimages.go`: `StageImage` runs outside any unit of work after the caller's `authorize`: declared type, the part read into memory up to `ImageCap` plus one byte while counted and hashed, open sessions and free space (no quota), then the `files` row (`scope_channel_id` NULL, fixed `original_name`), a session in mode `direct` with the counted size and SHA-256 and the one part. `CompleteStagedImage` (in the caller's unit of work) completes the session and inserts `files.scan`; `ReleaseImage` sets `deleted_at` on the previous file of the same purpose and uploader through `markDeleted` (M3-07); `OpenImageVariant` opens the variant `medium` of a deliverable `branding` file, `not_found` otherwise.
- **Pipeline.** The purpose rule runs in the scan pass (a detected type whose original would be stored unchanged or as a re-encoded GIF) and in `files.thumbnail` (a WebP that stays unchanged, animated or above `file.image.max_pixels`): such a file ends `failed` with `failure_reason` `file_type_denied` before it is deliverable.
- **Reads and events.** Every `file` descriptor carries the purpose and `OwnerID`; `authz` decides `file.read` by purpose (07 4.3). `file.updated` of an avatar or logo file is a personal event of the uploader (`audience_principal_id = uploaded_by`).
- **Not here.** The objects of released files go with `files.purge_objects`, abandoned staged sessions expire with `files.cleanup_pending` (M3-08). Agent avatars have no operation in `openapi.yaml` yet.

## Attachments (M3-07)

Normative: [12-files.md](../../../../docs/spec/12-files.md) sections 2, 10 and 12, 03 4.7 `message_attachments` (R-DM-22, R-DM-43), 05 2.2 rows `file`, the rulings D-M3-07 in [docs/decisions.d/M3-07.md](../../../../docs/decisions.d/M3-07.md).

- **Table.** `message_attachments` (migration `00066_files_message_attachments.sql`, retention class `content`, exactly as 03 4.7): `message_id`, `file_id`, `position`, and the copies `thread_id` and `channel_id` of the message's place without a foreign key (R-DM-43); PK `(message_id, position)`, UNIQUE `(file_id)`, index `(thread_id)`; the rows go with their message (`ON DELETE CASCADE`), an attached file cannot be deleted (`ON DELETE RESTRICT`). `files` writes the copies from the message `messaging` inserted and never reads `messages` (03 principle 12).
- **Port.** `Attachments`, implemented by `app.Service` (`internal/wire` passes the files use cases to `messaging` and `runs`); no method calls `authorize`. `Attach` locks the `files` rows of the distinct ids `FOR UPDATE OF files` in ascending id joined with the state of their session (the session row stays unlocked), then reads `message_attachments` of these files in a later statement, walks the list in request order with `domain.Attachable` and inserts one row per file with position = index + 1. Every refusal (unknown, foreign, deleted, other channel, open, aborted, expired or failed upload, another purpose, attached already, listed twice) is the same `409 conflict` with reason `file_not_attachable` and detail `<Pointer>/<index>`; a unique violation on `file_id` at the insert is the same answer with detail `<Pointer>`. Blocked and pending files are attachable. `ForMessages` reads the rows of many messages with their files and, in one more statement, their thumbnails. `DeleteForMessage` locks the files of the message in ascending id, deletes its rows and marks the files deleted. `MessageOf` reads the row of one file; `Pending` reports an attached file that is not final (`domain.Final`). `Attach`, `DeleteForMessage` and `Pending` need the caller's unit of work (internal error otherwise); `ForMessages` and `MessageOf` read in the ambient transaction or on the pool.
- **Attached form.** An attached `File` has no `scope_channel_id` (it names a channel the reader may not see after a move) and `sha256` only for a complete file; `getFile` answers it so too.
- **Reading.** `app/resource.go` `fileResource(f, ref)` is the one builder of the `file.read` and `file.delete` descriptors: unattached on the path of `scope_channel_id` with the uploader as owner, attached on the path of the copies (`ChannelID`, `ThreadID`) with `Attached: true`. `getFile`, downloads, tickets, transcripts and the abort read the attachment row next to the file row. `files.scope_channel_id` never changes and counts only before attaching.
- **`recordFileChange`.** `app/filechange.go` is the one place that appends `file.updated` for a change of `upload_state`, `scan_status`, thumbnails, media values or transcript: the abort of M3-03, the scan outcome of M3-04 and every unit of the image job of M3-06 call it with the file row locked. It reads the attachment row: unattached goes to the uploader in the scope of `scope_channel_id`; attached goes without audience to `{space, channel, thread}` of the message (space from `ChannelLocator.SpaceOf` of the copy channel) in the attached form. In the same step it publishes `files.FileFinalized` exactly when `domain.BecameFinal(before, after)`, so the scan outcome, the abort (failed is final) and T1 or the failure transaction of an image each publish it once, and `runs.OnFileFinalized` commits with them.
- **Deletion.** `app/deleted.go` `markDeleted` is the one write of `files.deleted_at` (repository `MarkFilesDeleted`); its callers and further steps are in the section "Cleanup and deletion (M3-08)". A deletion with the message writes no `file.updated`.
- **Thread move.** `app.Subscribers.OnThreadMoved` (constructor `app.NewSubscribers(rows ThreadAttachments)`, built over `adapters/postgres.NewRepository` with a pool that may be nil) sets `channel_id` of every row of the thread to the target channel in the transaction of the move, after the subscribers of `messaging` and `sync`; no version, no event.
- **Lock order.** files rows in ascending id, then `message_attachments` (03 6.3): attach, delete and the move follow it.
- **Query exceptions (AZ-P12).** In `tools/lint/sql_visibility.yaml`: `after_authorize` for `files.LockAttachTargets` and `files.AttachedFileIDs` (the files the author listed after `message.create` was allowed), `files.ListMessageAttachments` and `files.ListThumbnailsOfFiles` (messages the caller already read, the files of one attach), `files.ListAttachmentStates` (one message whose creation or run was decided) and `files.LockMessageAttachmentFiles` (after `message.delete`); `authorize_resolution` for `files.GetAttachmentByFile` (the row by file id that builds the `file.read` descriptor and that `MessageOf` and `recordFileChange` reuse). The inserts, the delete, the move and `MarkFilesDeleted` are writes.
- **Tests.** `domain/attach_test.go`, `app/attach_test.go` (fakes), `adapters/postgres/attachments_test.go` (pgtest: rows and copies, every refusal, the concurrent attach of one file, deletion, the thread move with a veto), `migrations/attachments_test.go`.

## Search reads (M3-14)

Normative: [14-search.md](../../../../docs/spec/14-search.md) sections 4.3 to 4.8 and 10, brief M3-14 design notes 6 and 15. `search` owns no tables and reads files only through the port `SearchReads`, implemented by `app.Service` (the value of `Files.Service` in `internal/wire`); neither operation authorizes, the coordinator passes the visible channels of `Authorizer.Scope` and checks every delivered item with `file.read`.

- **`SearchFiles`.** One statement (`queries/search.sql`, `SearchFiles`) over `files` joined with `message_attachments` on `file_id`, inside the coordinator's unit of work: candidates match `files.search_vector @@ tsq`, hang in a visible channel (`a.channel_id = ANY(@channel_ids)`, the channel of the attachment, never `files.scope_channel_id`), are deliverable (`upload_state` complete, `scan_status` clean or skipped, not deleted, purpose attachment), pass `ThreadIDs` (against `message_attachments.thread_id`; nil restricts nothing, empty matches nothing), `AuthorID` (`files.uploaded_by`), `After` and `Before` (half-open on `files.created_at`) and `created_at <= RefTime`; the newest `search.max_candidates` of them by `created_at, id` are ranked, one more row only sets `CandidatesCapped`, also on an empty page. `relevance` scores `ts_rank` with `search.rank_normalization` over `1 + age / search.recency_scale` with the age from `RefTime`, ordered by score then id; `newest` orders by `created_at` then id with score 0. The keyset is strictly after `From`; the statement returns the page size plus one row, and `Next` is the position of the last returned hit while a further row exists. `ts_headline` in `simple` runs only for the page rows over the name followed by the transcript, cut at `search.headline_input_max_chars`, with the options of `Limits.HeadlineOptions`; `searchkit.Split` turns it into segments (ts_headline replaces an XML tag by a space, an entity stays verbatim). `Query.Thread` and `Query.HasFile` are ignored. A statement timeout is `searchkit.ErrTimeout`, an ended context its error.
- **One row per file.** `message_attachments` has UNIQUE `(file_id)`, so a file is at most one candidate with the message, thread and channel of its one attachment row. `DeleteForMessage` deletes the rows of a deleted message and marks its files deleted, so no file of a deleted message is a hit.
- **`HitFiles`.** The attached form of `getFile` (`attachedView` with thumbnails) of the deliverable files attached in the given channels, in input order, the rest absent; two statements (`HitFiles`, `HitFileThumbnails`), both with `a.channel_id = ANY(@channel_ids)`, so the AZ-P12 lint needs no new exception.

## Text extraction (M3-15)

Normative: [14-search.md](../../../../docs/spec/14-search.md) section 5, [12-files.md](../../../../docs/spec/12-files.md) 3.4, [19-security.md](../../../../docs/spec/19-security.md) SEC-UP-5 and SEC-UP-7, the rulings in [docs/decisions.d/M3-15.md](../../../../docs/decisions.d/M3-15.md).

- **Table.** `file_text_extracts` exactly as 03 4.7 with the stored generated `search_vector` of 03 5 (stems weight C, words weight D); retention class `content`. Only this module reads and writes it.
- **Trigger.** `recordFileChange` runs `ExtractTrigger.schedule` for every change that makes a file deliverable (the result of the scan pass, the stored original of `files.thumbnail`), in that unit of work: an attachment whose detected type an extractor supports gets its row (`pending`, the language of `locale.default` through `identity.Directory.InstanceSearchLanguage`, taken once) and the job `files.extract_text`. An unsupported type, another purpose or a blocked file gets nothing.
- **Job `files.extract_text`** (queue `files`, no River job timeout, args only the file id). `ExtractText.Run` reads the row and the file facts without a transaction; a row that is not pending does nothing; a deleted or no longer deliverable file loses its row; a type no extractor supports writes `unsupported`; a file above `search.extract.max_input_bytes` fails `input_too_large` without a read. Otherwise it opens the object outside every unit of work under `search.extract.timeout`, limited to `search.extract.max_input_bytes`, runs the port `TextExtractor` and writes `done` (text, `truncated`, extractor version, `extracted_at` from the clock), `failed` with a code (`input_too_large`, `archive_invalid`, `archive_entries_exceeded`, `archive_size_exceeded`, `xml_doctype`, `xml_invalid`, `timeout`, `object_missing`) or returns a transient error to River with the row still pending. When PostgreSQL refuses the search vector (SQLSTATE 54000) the text is halved at a rune boundary and written again with `truncated`.
- **Job `files.extract_text_refresh`** (queue `maintenance`, periodic every `search.extract.refresh_interval` and once at the start of a worker, args the last file id). One unit of work per batch of `search.extract.refresh_batch_size` deliverable attachments by id: `domain.RefreshDecision` resets rows of another extractor version or rows that failed only for their size when they now fit (compare-and-set, the old text stays findable), creates missing rows of supported types, re-enqueues pending rows (a job River discarded), and deletes rows of deleted files; a full batch inserts the next run.
- **Adapter `extract`.** `Registry` maps the detected type to `builtin-text/1` (every `text/*` except `text/html` and `text/rtf`, plus `application/json`), `builtin-html/1` (`text/html`, the tokenizer of `golang.org/x/net/html`), `builtin-ooxml/1` (DOCX, XLSX, PPTX) and `builtin-odf/1` (ODT, ODS, ODP). Pure Go, no cgo, no process, no network package (`TestExtractImportsNoNetwork`). Archives are read into memory and opened with `archive/zip`: entry count, declared sizes of the read parts and a shared inflation counter against `search.extract.max_archive_entries` and `search.extract.max_uncompressed_bytes`; duplicate names, encryption and methods other than store and deflate fail. XML through `encoding/xml`, strict, predefined entities only, UTF-8 only; a document type declaration fails `xml_doctype`; a run guard ends the part `truncated` when one token (text, start tag with its attributes, comment, processing instruction, CDATA section) grows beyond `search.extract.max_text_bytes`, and open start tags of more than `search.extract.max_text_bytes` together or a nesting deeper than `search.extract.max_xml_depth` fail `xml_invalid` (the decoder keeps the name, attributes and namespace declarations of every open element).
- **Golden rule.** `testdata/golden/<adapter>.txt` holds each adapter's version and the SHA-256 of its output over the fixtures of `extracttest`; `TestExtractorGolden` fails on a changed output, and `-update` refuses to write it under an unchanged version. So every output change raises the version and the refresh job re-extracts.
- **Memory bound.** One extraction holds about `search.extract.max_input_bytes` (the whole archive in memory, because `archive/zip` needs random access) plus a small multiple of `search.extract.max_text_bytes` (the text, one token and the open start tags with the decoder's entries for them); at most `jobs.queue.files.max_workers` run per worker process.
- **Deletion.** `markDeleted` deletes the rows of the files it marks deleted in the same unit of work (`DeleteTextExtractsOfDeleted`); the job and the walk remove rows of deleted files they meet; `ON DELETE CASCADE` removes the row with the `files` row.
- **Search.** `SearchFiles` takes the files matched by their own vector and those matched by their text vector through two indexed branches, unions them under the one candidate limit and ranks the joined vector; the headline reads name, transcript and text in the language of the text.
- **Logs and content.** The text is content of class `content`: never in logs, spans, metrics, job arguments, events or errors. A failed extraction logs one Warn with `bothy.file.id` and `bothy.reason` (the code), a missing object one Error; no metric of its own (signals.md names none).
- **Query exceptions (AZ-P12).** `files.GetExtractTarget` and `files.ListRefreshCandidates` stand as `system_job` in `tools/lint/sql_visibility.yaml`.
- **Residuals.** Fixed part names instead of package relationships: a document whose producer uses other part names gives `archive_invalid` or empty text. PDF, RTF, EPUB and the older Office formats wait for the Tika adapter (V3). A change of `locale.default` does not reassign the language of existing rows.
- **Tests.** Unit tests in `domain`, `app` (fakes) and `adapters/extract` (with the fuzz targets `FuzzExtractText`, `FuzzExtractHTML`, `FuzzExtractOOXML`, `FuzzExtractODF`, the golden test and every zip bomb and XML variant built at test time); the repository and `SearchFiles` against PostgreSQL in `adapters/postgres`; integration tests through the real server and directly over the use cases in `test/textextract` (`go test ./test/textextract/`, needs a Docker-compatible runtime).

## Object storage (M3-01)

Normative: [12-files.md](../../../../docs/spec/12-files.md) sections 4.1, 4.2 and 4.4, [ADR 0010](../../../../docs/adr/0010-object-storage-behind-an-s3-interface-local-driver-as-default.md), rulings M3-01/1 to M3-01/19 in [docs/DECISIONS.md](../../../../docs/DECISIONS.md).

- **Port.** `app.ObjectStore` is an outgoing port of the application layer with exactly `Put`, `Get` (whole object or one byte range), `Head`, `Delete`, `CreateMultipart`, `UploadPart`, `CompleteMultipart`, `AbortMultipart` and `PresignUploadPart`. Other modules never see it. Every operation checks the key first (`ErrInvalidKey` before any storage call). Sentinel errors: `ErrNotFound`, `ErrInvalidRange`, `ErrSizeMismatch`, `ErrUploadNotFound`, `ErrInvalidPart`, `ErrNotSupported`; every other error is a storage failure that callers answer with `503`. `Delete` of a missing object and `AbortMultipart` of an unknown upload succeed.
- **Key schema.** `domain.OriginalKey` (`f/<aa>/<bb>/<file_id>/orig-<n>`), `domain.VariantKey` (`small`, `medium`, `large`, `poster`) and `domain.UploadPartKey` (`uploads/<file_id>/<n>`) take only an `ids.ID`, an `int` and the closed type `Variant`, so no name, channel ID or space ID can reach a key (`TestObjectKeysCarryNoContext`, `TestKeyBuildersTakeOnlyIDsAndNumbers`). `domain.ValidateKey` is the one grammar of all drivers: segments of `[a-z0-9-]` joined by single `/`.
- **File system driver.** `fs.Open(fs.Config{Root})` refuses a root that is not an absolute, clean path of an existing directory (not a link) owned by the server user with mode `0700`; errors name `file.fs.root`, not the path. It creates `<root>/.tmp` and never the root itself. All operations go through an `os.Root`; no symbolic link is followed at any level (`Lstat` of every component before an operation and before a rename; because `os.Root` follows a link inside the root even with `O_NOFOLLOW`, a read checks the path again when the opened file is not the one it checked), and a link is a storage failure. An existing `.tmp` must also be a directory of the server user with mode `0700`. A new directory is synced in its parent. Directories get mode `0700`, files `0600`.
- **Writes.** Temporary file in `<root>/.tmp` (no key can address it, keys have no dot), exactly `size` bytes with a bounded buffer, `fsync`, rename, `fsync` of the directory. A directory sync that the platform refuses as "not supported" counts as success (Linux and macOS support it). A reader never sees half an object; a failed write leaves nothing. `Put` on an existing key replaces it atomically; the module, not the driver, never overwrites an object (next revision).
- **Delete.** Removes the file and then the file directory (`f/<aa>/<bb>/<file_id>` or `uploads/<file_id>`) if it is empty; writers create a vanished directory again. `Delete` of an original key also removes `uploads/<file_id>/`, so parts that a completion could not remove go with the file.
- **Multipart.** `CreateMultipart` takes only original keys and returns the upload ID `""`; parts lie at `uploads/<file_id>/<n>` with the ETag `"<sha256 hex>"` of their bytes and are readable objects while the upload is open. `CompleteMultipart` reads each listed part once, checks it against its ETag and removes the upload directory; `AbortMultipart` removes it. `PresignUploadPart` gives `ErrInvalidPart` for a part number below 1, `ErrSizeMismatch` for a size below 1 (M3-02) and otherwise `ErrNotSupported`.
- **Conformance suite.** `filestest.RunObjectStoreConformance(t, newStore, filestest.Options{PartSize: ...})` runs the cases of 12 "15. Tests" against a fresh store per case. A new driver calls it from its own `_test.go` with the smallest part size it accepts (the file system test passes a small size, the S3 driver the S3 minimum).
- **Configuration.** `file.storage.driver` (`fs` or `s3`, default `fs`) and `file.fs.root` (default `/var/lib/bothy/files`); cross-check `file_fs_root_absolute`. `wire.FilesObjectStore(ctx, values, wire.FilesDeps{Secrets, Egress})` opens the driver.
- **Observability.** None: the driver logs nothing and adds no metric or span; callers log.
- **Open points.** A temporary file left in `.tmp` by a crashed process stays (no rule in the specification yet; proposed for M3-08). The readiness check "the object storage answers" (16 "4.2") has no ticket yet. Since M3-03 every role opens the store in the start step `files`, and the server image holds the directory `/var/lib/bothy/files` (D-M3-03-24).

## S3 driver (M3-02)

Normative: [12-files.md](../../../../docs/spec/12-files.md) sections 3.3 and 4.3, [ADR 0010](../../../../docs/adr/0010-object-storage-behind-an-s3-interface-local-driver-as-default.md), ADR 0048, rulings M3-02/1 to M3-02/14 in [docs/DECISIONS.md](../../../../docs/DECISIONS.md).

- **Core S3 only.** `s3.Store` holds the interface `coreAPI` (`PutObject`, `GetObject`, `HeadObject`, `DeleteObject`, `CreateMultipartUpload`, `UploadPart`, `CompleteMultipartUpload`, `AbortMultipartUpload`) and `presignAPI` (`PresignUploadPart`), nothing else of the SDK. No request sets encryption, ACL, tagging, object lock, storage class or conditional headers.
- **Vendor rule.** The vendor group `awssdk` is granted to the adapters of `files` in `architecture/modules.yaml`; depguard in `.golangci.yml` narrows it to `internal/files/adapters/s3` (production and test files), forbidigo forbids `s3.Client.DeleteObjects` and `s3.PresignClient.PresignGetObject`, and `TestS3SDKOnlyInAdapter` checks the imports with `go list`.
- **Keys.** `file.s3.endpoint` (required, absolute `http` or `https` URL without path), `file.s3.region`, `file.s3.bucket` (required), `file.s3.prefix` (optional, key grammar, joined with `/`), `file.s3.use_path_style`, `file.s3.checksum_mode` (`when_required` or `when_supported`, the latter only with an `https` endpoint), `file.s3.access_key_ref` and `file.s3.secret_key_ref`; cross-check `file_s3`. `file.s3.presigned_upload` and `file.s3.presign_ttl` follow with the presigned mode.
- **Egress and secrets.** One egress client with purpose `objectstore`, the host policy of exactly the request host and port, no redirects, the time limit `http.transfer_timeout` and the body limit `file.max_upload_bytes`; an `http` or private endpoint needs an `egress.allowed_hosts` entry with `allow_private`. The keys come only from the secret provider and are resolved again on every refresh of the SDK credential cache, so a rotation works after `secrets.cache_ttl`; the SDK default configuration and credential chain are never used. No SDK retries.
- **Bodies.** `Put` and `UploadPart` stream the reader as `UNSIGNED-PAYLOAD` and hold back the last byte until the reader ends, so a body of another length gives `ErrSizeMismatch` and stores nothing.
- **Errors.** `files/s3: <operation> <key>: <detail>` with the S3 code, the status or a fixed text; never a URL, query, presigned URL, endpoint or credentials. `Head` on a missing bucket reads as `ErrNotFound` (a HEAD answer has no body).
- **Tests.** Unit tests run against an `httptest` fake behind the real egress client and secret provider. The conformance suite and the integration tests (`TestS3Conformance`, `TestS3RequestsAreCoreS3`, `TestPresignedPartBindsLength` and others) run against SeaweedFS in a throwaway container from the image of the Compose service (`seaweedImage`, pinned by digest; `TestSeaweedImagePinned` holds the version equal to `BOTHY_SEAWEEDFS_VERSION`). They need a Docker-compatible runtime and fail without one: `cd services/server && go test ./internal/files/adapters/s3/`. A container left by a killed test binary carries the label `org.bothy.test=seaweedfs`.

## Cleanup and deletion (M3-08)

Normative: [12-files.md](../../../../docs/spec/12-files.md) sections 2, 4.2, 12 and 14, [20-privacy.md](../../../../docs/spec/20-privacy.md) 4.2 and 4.3, R-DM-45 and R-DM-46, the rulings D-M3-08 in [docs/decisions.d/M3-08.md](../../../../docs/decisions.d/M3-08.md).

- **The deletion function.** `app/deleted.go` `markDeleted` (`deletion.mark`) runs in the caller's unit of work after the caller locked the rows: `MarkFilesDeleted` (`UPDATE ... RETURNING id`) and, only for the files it marked, `AbortOpenSessions` (an open session becomes `aborted`, no `file.updated`), `eventlog.Redactor.Redact(ctx, "file", id, domain.RedactFileEvent)` and `PurgeQueue.Enqueue`. Callers: `DeleteForMessage` (M3-07), `ReleaseImage` (M3-10), `Delete` (`deleteFile`) and the cleanup steps b and c. `TestOneDeletedAtWriter` holds that one sqlc statement writes `deleted_at`.
- **Redaction.** `domain.RedactFileEvent` keeps `id`, `uploaded_by`, `purpose`, `upload_state`, `scan_status`, `transcript_status` and `created_at` of a stored `file.updated` v1, sets `original_name` `""`, `size_bytes` `0`, `mime_type` `application/octet-stream`, `thumbnails` `[]` and drops every other member; another type or version fails the unit of work.
- **Purge.** `app/purge.go` `Purge.Run`, job `files.purge_objects` (`adapters/jobs/purge.go`, args `PurgeObjects{FileID}`, queue `maintenance`): the facts without a transaction and `domain.PlanPurge` (no row, live file: nothing; failed or blocked: objects; deleted: objects and row), then outside every unit of work `PartStore.Discard` and `ObjectStore.Delete` of every key of `domain.ObjectKeysOf` (`orig-1` to `orig-(r+1)`, the four variants); the first error is returned so River retries, a missing object counts as deleted. A deleted row is removed in one unit of work after its lock when it has no attachment row (an attachment row is an internal error with one Error line carrying `bothy.file.id`); sessions, parts, thumbnails and text extracts go by `ON DELETE CASCADE`.
- **Failed and blocked files.** `recordFileChange` inserts the purge whenever a change makes the file final without making it deliverable (abort, verify failures, `infected`, `error`, expiry, image failure); the deletes after the commit of M3-03 and M3-04 stay.
- **Cleanup.** `app/cleanup.go` `Cleanup.Run`, periodic job `files.cleanup_pending` (`Interval` = `file.gc_interval`, `RunOnStart`), steps in order with batches of `file.gc_batch_size` keyed by (time, id) and one unit of work per candidate: a) expired open sessions (`ExpireSession`: session `expired`, file `failed`, part rows gone, then `recordFileChange` without actor), b) never attached files after `file.unattached_ttl` unless `DraftFileSource.HeldByUploader` holds them, c) unattached failed or blocked attachment rows after `file.failed_row_ttl` (avatar and branding rows never), d) the catch-up of every deleted row inline, which stops at the first storage error, e) `TempSweeper.SweepTemp` with `now - file.upload_session_ttl` (`adapters/fs/sweep.go`; none with S3), f) `PurgeBacklog` to the gauge `bothy.file.purge.backlog` (`adapters/otelmetrics.PurgeBacklog`) and one Warn line when the oldest mark is older than `privacy.object_delete_delay`. Ages count from `domain.LastChange`. Log lines carry at most `bothy.file.id`, step names and counts.
- **`deleteFile`.** `app/delete.go` `Service.Delete`, handler `DeleteFile` in `adapters/httpapi/files.go`: no row `404`; deleted `204` for its uploader, `404` for everyone else; `authorize` `file.delete` on `fileResource`; `409 conflict` with `reason` `file_attached` or `purpose_not_deletable`; then lock, read again and `markDeleted`. No event and no audit.
- **Ports.** `PurgeQueue` (`adapters/jobs.Purges` over the inserter of the scan queue), `TempSweeper`, `CleanupStore` (`adapters/postgres` `cleanup.go`, queries `queries/cleanup.sql`), `PurgeMetrics`; the source port `files.DraftFileSource` is implemented by `sync`.
- **Query exceptions (AZ-P12) and indexes.** `system_job` for `ExpiredOpenSessions`, `UnattachedCandidates`, `FailedRowCandidates`, `DeletedRows`, `PurgeBacklog`, `PurgeFacts`, `LockFileForCleanup` and `CleanupFileFacts`; `authorize_resolution` for `FileForDelete`, `after_authorize` for `LockFileForDelete`. No index is added: expired sessions use `(expires_at) WHERE state = 'open'`; the candidate steps may scan `files` once per step and run, bounded by the prefilter on `created_at` and the batch.
- **Tests.** `domain/purge_test.go`, `domain/cleanup_test.go`, `domain/redact_test.go`, `app/cleanup_test.go` (fakes, both strategies), `adapters/fs/sweep_test.go`, `adapters/jobs/purge_test.go`, `adapters/otelmetrics` and the integration suite `test/filecleanup`.

## Statistics source (M6-05)

`files.StatsSource` (`stats.go`, implemented by `app.Stats` over
`adapters/postgres/queries/stats.sql`) serves the statistics of `stats`: `StorageBytes` sums the
complete attachments not deleted of the visible channels per space, and `ScanStats` counts the scans
that ended with `error` or `infected` per bucket of `scanned_at` over every file; the stats use case
calls it only for an owner on the instance. Only sums and counts leave, never a file name or
uploader.
