### Added

- Follow-ups with steer and queue (M2-11, 09 section 7, AG-13): a human message that would
  trigger the agent of the thread's active run becomes a follow-up of that run instead of a second
  run: one row `queued` in the new table `run_followups` (migration `00060`), `trigger_state =
  received` and one step of `runs.version`. `run.followup.create` is a real requirement ("write
  and `agent.invoke`" with the guard of `agent.invoke`) and no longer deferred. With the effective
  capability `followups = steer` (the owner's `supports_followups` and the adapter's reported
  capability) the server writes `agent.followup`, delivered with a fresh token for the follow-up's
  author; with `queue` or without the capability only a follow-up to a run in `waiting_input` gets
  it. The adapter acknowledges `delivered` and `absorbed` with a run patch, forward only (a backward
  move gives 409 `invalid_state_transition`); the first move sets `followup_delivered`. At the end
  of a run open follow-ups become `deferred` and the first allowed one in thread order triggers a
  follow-on run whose follow-ups are the rest; after a stop by a person they become `discarded`
  with `cancelled` / `user_cancelled`. A refused delivery, a refused follow-on trigger and a
  deleted message discard the follow-up. The run document lists the follow-ups.
