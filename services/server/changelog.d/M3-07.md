### Added

- Attachments and release of the agent invocation (M3-07, 12 section 10, SEC-UP-9, R-DM-22,
  R-DM-43, R-FI-09): `createMessage` and `createThread` (`first_message`) accept
  `attachment_file_ids` (no longer `400 validation_failed` with `errors[].code` `not_enabled`) and
  require `+upload`. Every file must be the author's own, uploaded with `purpose = attachment` for
  the channel of the message, with a completed upload session, not failed, not deleted and not yet
  attached; every other file answers one `409 conflict` with `reason` `file_not_attachable` and
  the pointer of the entry in `detail`, and more than `message.max_attachments` answer `400
  validation_failed` with `errors[].code` `limit_reached`. With an attachment `content_md` may be
  empty. The new table `message_attachments` binds each file to one message with the copies
  `thread_id` and `channel_id` of that message (migration `00066`), and `messages.has_attachments`
  with its CHECK against deleted messages (migrations `00067` and `00068`) marks messages with
  attachments. Every representation of a message (`Message.attachments`, `message.created`,
  `message.updated`) lists its attachments in position order; an attached file is read through
  the channel and thread of its message and shows no `scope_channel_id`. A message that triggers
  an agent while an attachment is not final keeps `trigger_state = received` and writes no
  `agent.invocation`: the transaction that makes the last attachment final writes it
  (`ReleaseInvocation`, subscriber of `files.FileFinalized`), and the new job
  `runs.invocation_hold_timeout` writes it after `file.invocation_hold_max` with the attachments
  in their current state, exactly once either way, without `actor`; `runs.invocation_held_until`
  marks a held run. An agent whose owner set `supports_files_out = false` gets `403
  feature_disabled` for a message with attachments.

### Changed

- Files of a message (M3-07): moving a thread moves the `channel_id` copies of its attachments in
  the same transaction, and deleting a message removes its attachment rows, sets
  `has_attachments` back to `false` and marks its files deleted in the same transaction, without
  `file.updated`. `file.updated` of an attached file carries the scope `{space_id, channel_id,
  thread_id}` of its message and no audience; before attaching it still goes to the uploader only.
  `files.FileFinalized` is published from one place, the write that appends `file.updated`, exactly
  when a file becomes final: the scan outcome, the abort of an upload (newly) and the image
  transactions.
