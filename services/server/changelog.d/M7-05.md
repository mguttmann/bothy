### Added

- Retention per class (M7-05, 20 section 4.1, R-DP-01): the worker runs the periodic jobs
  `retention.security`, `retention.content`, `retention.transient`, `retention.audit` and
  `retention.cost` on the queue `maintenance` every `retention.job_interval`, in batches of
  `retention.batch_size` rows per table in short transactions. Each module removes only its own
  tables through a participant of the new kernel port `retention`: login sessions, refresh
  tokens, API tokens, revoked devices, device keys and passkeys, used or expired enrollment codes,
  retired signing keys (never those of the audit checkpoints), disabled push registrations,
  closed terminal sessions and retired hosts after `retention.security_after_end`; finished
  webhook deliveries after `retention.webhook_deliveries`; cost entries and closed price rows
  after `retention.cost`. A row another row still holds by a foreign key stays until that row
  is gone.
- With a period in `retention.content`, messages created before it are deleted through the
  deletion of a message (tombstone, redacted event payloads, attachments through the file purge),
  without an actor: no audit entry and `message.deleted` without `deleted_by`. The default `none`
  deletes nothing.
- The audit trim: as the database role `bothy_maint`, connected only for it, the job
  `retention.audit` writes the anchor entry `audit.retention_trim` (last removed `seq` and hash)
  and removes the rows and checkpoints before it in one transaction, never past the newest
  checkpoint stored at `audit.checkpoint_sink` (without a sink the log is not trimmed).
  `audit.verify`, the restore test and `audit.chain_verify` start at the anchor; `audit.verify`
  reports `checkpoint_mismatch` when a checkpoint of the sink below the anchor is younger than
  `retention.audit` or the newest one lies at or below it. IP
  keys are destroyed after `privacy.audit_ip_key_retention` (key emptied, row kept, DP-T06).
- `identity.auth_cleanup` deletes the completed, rejected and expired device pairings past their
  expiry (02 12.3), so a device that came in through a pairing can leave with its period.
- `bothy config check` and the start log warn when `retention.content = none` and
  `retention.content_none_reason` is empty; otherwise the start log names the effective value
  (DP-T13).
- Metric `bothy.retention.deleted` (rows per class, no IDs) and the configuration keys
  `retention.content`, `retention.content_none_reason`, `retention.security_after_end`,
  `retention.cost`, `retention.webhook_deliveries`, `retention.job_interval` and
  `retention.batch_size`.
