### Added

- Deletion journal (M7-07, 20 4.6, R-DP-04): the worker consumer `privacy.journal` writes one
  content-free entry `{resource_kind, resource_id, deleted_at, reason, seq}` per deleted message
  (`message.deleted`) and per deleted account (`user.updated` with the status `deleted`, reason
  the content mode of its request) as an object `deletion-journal/<number>` in the object storage
  of files, numbered densely by the new table `deletion_journal_state` (migrations `00080` and
  `00081`, R-DM-52). The object is stored before the cursor moves; a redone round that finds the
  same bytes counts it as stored. The object backup copies the journal with the files.
- `bothy restore finalize` applies the journal before the epoch step (SEC-BAK-3, SEC-T15, DP-T07):
  every message, file and account the restored database holds again is deleted through the
  normal deletion, the account with its recorded content mode; then the permission version rises
  once and the number after the last object is stored. The command prints the counts per kind and
  needs the configuration and secrets of the server; a second run changes nothing. Journal
  objects lost with a host loss get a placeholder, so later restores read past them.
- `privacy.deletion_journal_retention` (default `400d`) is active: the job `retention.privacy_job`
  removes older journal objects, never one that a kept backup needs, and `api`, `worker` and
  `bothy config check` refuse a value shorter than the longest backup period (DP-T08).
- The backup manifest names `deletion_journal.next_number`.

### Changed

- `retention.privacy_job` keeps an account deletion until its journal entry is written.
