### Added

- FCM adapter with Fake-FCM (M3-21, 13 sections 5.2, 6.2, 7.2, 11 and 17): the package
  `internal/notify/adapters/fcm` implements the provider port `PushProvider` for `provider = fcm`
  and sends one FCM HTTP v1 data message per hint, only through the egress client (purpose
  `push_fcm`, HTTP/1.1, `https` on port `443` to exactly `fcm.googleapis.com` and
  `oauth2.googleapis.com`, no redirect). It authenticates with an OAuth 2.0 access token of the
  service account behind `push.fcm.service_account_ref`: an `RS256` assertion signed with
  `jose.RS256Signer` goes with the JWT bearer grant to the fixed token URL
  `https://oauth2.googleapis.com/token` (a service account with another `token_uri` is refused at
  start), the account is read again at each token request so a rotated key needs no restart, and
  the access token is reused for half its `expires_in` with at most one token request in flight.
  A `401 UNAUTHENTICATED` renews the token and retries once; credential errors pause the adapter
  for `push.retry_cap` and then probe once. The payload holds only the string keys of 13 6.2 with
  `badge` on every message and the sync form `k = "sync"` with `cleared` complete or absent, never
  a `notification` block or a `collapse_key`, and stays under the FCM data limit. Every answer of
  13 7.2 maps to one result class, `Retry-After` is honoured, `QUOTA_EXCEEDED` waits at least one
  minute, and configuration and program errors write one Error record with `bothy.push.provider`
  and `error.type`. `internal/wire` builds the adapter in the roles `worker` and `all` when
  `push.fcm.project_id` is set. New: the Fake-FCM `fcmtest.Server` (token and send endpoint with
  TLS on loopback, assertion and bearer checks, scripted answers), the cross-check
  `push_fcm_project_id`, the bounds of `push.ttl` (1 second to 28 days), the default
  `file:<secrets.dir>/fcm_service_account.json` of `push.fcm.service_account_ref`, and
  `bothy config check --secrets` resolves that key only when FCM is enabled.
