### Added

- Cost reconciliation (M2-28, BR-10 server part, ADR 0055): `reconcileCosts` (owner with step-up;
  app, agent and personal tokens get `403 forbidden` with reason `owner_only`) and `submitCostReconciliation` (only an app
  with the scope `costs:reconcile`, no step-up) store new `reconciled` entries next to the
  estimates and never change or delete an entry. An entry is matched when its run has valid entries
  of mode `organization`, the given provider and the entry's currency in the half-open period; the
  amount is split over them in proportion to their amounts with the remainder on the largest, every
  one gets exactly one successor with the copies and tokens of the entry it replaces, a repeat with
  the same sum writes nothing, and unmatched run IDs are answered in `unmatched_run_ids`. Both
  operations insert the job `billing.reconcile` (queue `default`, never periodic, arguments only
  run IDs), which publishes the valid totals in its transaction (`billing.CostsReconciled`); `runs`
  sets `cost_micros`, `currency` and `cost_is_estimate` and `agents` sets
  `cumulative_cost_micros` and `cost_is_estimate` of the sessions (`ApplyCostTotals`), each with
  `version + 1` only on a change. The audit entry holds the period, the counts and one sum per
  currency. `listCostEstimates` (`cost.reconcile.read`, an owner in a session or the app, R-AZ-28)
  lists per run the estimate before any reconciliation and whether the run is reconciled, of mode
  `organization` only and without channel, thread or content. The server has no configuration key,
  column, job argument or log field for a provider key; the reconciliation app with the admin key
  lives in `plugins/cost-reconciler`.

### Changed

- API contract: `reconcileCosts` answers `409` (`request_in_progress`), `submitCostReconciliation`
  `422` (`idempotency_key_reuse`); `CostReconcile.provider` has `minLength: 1`,
  `ReconcileEntry.amount_micros` `minimum: 0` and `ReconcileEntry.currency` the pattern of an
  ISO 4217 code.
