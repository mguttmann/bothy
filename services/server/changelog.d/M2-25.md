### Added

- Commands and interactions for apps (M2-25, 11 section 9, 09 sections 10 and 11, 05 section 5,
  R-AZ-18, R-AZ-29, E-EX-05): an installed app owns slash commands and message components like an
  agent and never triggers one (no run, no invocation token, no `agent.invoke`, no I2, no
  `trigger_state`). The commands of the manifest are instance-wide (no `scope_id`, `scope_kind`
  absent or `instance`, names not reserved, at most `command.max_per_principal`, descriptions within
  `command.description_max_chars`; `validateManifest` and `installApp` answer `400
  validation_failed` with the pointer below `/manifest/commands/<i>`). `installApp` writes them in
  the install transaction, `upgradeAppManifest` applies a case-insensitive diff by name (commands
  the app registered through the API stay), `uninstallApp` removes them; `app.suspend` and
  `app.uninstall` disable the app's active components (one `message.updated` per card), which stay
  `disabled` after `app.resume`. The audit details of these owner actions gain `commands_added`,
  `commands_changed`, `commands_removed` and `components_disabled`. A manifest address matches
  `webhook.allowed_hosts` by canonical host and port; an entry without a port allows only the https
  default port.
- The app-owner guard `AppOwnerReachable` in `authz` (active installation, the scope of the
  feature, `write` on the channel where one is resolved; `getCommand` without a channel checks only
  the installation and `commands:write`) reads the owner's facts and decides `command.read`,
  `command.invoke` and `command.autocomplete` (a false guard answers `404 not_found` like an unknown
  command) and `interaction.create` on an app card (`409 component_used`). `authz.PrincipalFacts`
  gains `AppGrantedScopes` (filled by the identity principal source from the active installation),
  `authorize.CommandFacts` gains `OwnerID` (the thread creator for `command.invoke` and
  `command.autocomplete`). The re-check principal of a check without a request (R-AZ-29) is also
  allowed for `command.invoke` and `interaction.create`.
- Receive rule for apps: in filter mode `agent.events.consume` admits the audience app with an
  active installation and `events:subscribe` (domain `AppReceive`: `not_self`,
  `app_not_installed`, `scope_missing`, `allow`), so `command.invoked`, `interaction.created` and
  the ephemeral `command.autocomplete_requested` reach the owning app through its gateway
  connection, `listEvents` and webhook subscriptions; sync passes the audience of a personal event
  for an app receiver as for an agent consumer. The agent consumer operations keep `403 forbidden`
  with `subject_kind_not_allowed` for apps.
- `invokeCommand` on an app command writes `command.invoked` with the app as audience into the
  given thread, else the main thread of a text channel, else none (forum), and answers `202` with
  `accepted: true` and without `run_id`; `control` changes nothing. `createInteraction` on an app
  card answers `201` with `state = received` and writes `interaction.created` for the app; no run
  is opened. Both insert the job `runs.app_dispatch` (queue `default`, roles `worker` and `all`,
  arguments IDs only) in the same unit of
  work. The job takes the way of the manifest (gateway: nothing; inactive installation: the
  interaction becomes `failed`), re-checks the invoking principal in filter mode without audit,
  sets the interaction `dispatched` and posts the stored event once to `delivery.interactions_url`:
  the webhook envelope with `sync_epoch`, `webhook-id` equal to the event `id`, a `v1a` signature
  with the `webhook_out` key and no `v1`. The host must be in `webhook.allowed_hosts` before the
  egress client (purpose `app_interaction`, no redirects, `app.interaction_timeout`,
  `http.max_json_body_bytes`) is called. A `200` with a `MessageCreate` is written in the app's
  name with `origin = app` (idempotent by `client_msg_id`) and sets `acknowledged`, a `202` keeps
  `dispatched` until `respondToInteraction`, every other outcome sets `failed`. Faults before the
  request use River's default attempts; after the request the job always returns `nil`. One log
  line per request carries only allowlisted attributes (`bothy.job.kind`, `bothy.event.type`,
  `bothy.principal.kind`, `bothy.outcome`, `bothy.reason`, `server.address`), never the URL path,
  a header value, a body, an option or form value, a reply text or a signature.
- Autocomplete for app commands: an app with an interaction address is asked with a deadline of the
  earlier of `command.autocomplete_timeout` and `app.interaction_timeout`; `202` waits for
  `answerAutocomplete` until `command.autocomplete_timeout`; an app without one gets
  `command.autocomplete_requested` without a token over its gateway connection and answers with the
  op `command.autocomplete_result`; an inactive app gives an empty list at once.
- New ports: the source port `runs.AppDispatcher` (implemented in `apps/adapters/appdispatch`), the
  port `agents.OwnedCommands` (`UpsertOwned`, `RemoveOwned`, `RemoveAllOwned`, implemented by
  `agents/app.CommandService`), `runs.Interactions.DisableAuthoredBy` and
  `messaging.Messages.Authors`; `apps` now depends on `runs`. The canary scenario covers form
  values, options and the reply text of the app way. No new metric. No new configuration key:
  `app.interaction_timeout`, listed as planned, is registered and now active.

### Changed

- Apps may post cards: `createMessage` with `kind = card` from an app needs `write` and
  `messages:write` (not `components:write`) instead of answering `not_enabled`; `run_id` on an app
  card gives `400 validation_failed` with `run_mismatch` on `/run_id`. `updateComponent` and
  `respondToInteraction` by an app need `components:write`.
- App commands are listed by `listChannelCommands` for apps with `write` on the channel, resolved
  and invoked instead of being hidden and answering `404`; autocomplete for an app command asks the
  app instead of answering `404` or an empty list.
