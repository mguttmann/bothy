### Added

- The Hermes platform plugin `bothy_hermes_adapter` (M2-33): one Hermes profile is one agent of
  the server. Runs start only after the SDK checked the invocation token and the server answered
  `200` on `startRun`; the actual billing mode comes from the kind of credential Hermes resolves
  (never its value) before every start and in every heartbeat, and an undeterminable mode fails
  the run with `billing_mode_mismatch`. Status sentences and drafts fill the live box, the answer
  is one message with buffered edits, the run ends with `finishRun`, metrics and costs. The run
  context reaches Hermes as a fixed system part with trust marks and data blocks; follow-ups follow
  `busy_input_mode`; clarify, approval and slash confirmations become single-use cards resolved
  exactly once; stop interrupts the turn; each thread keeps one Hermes session that the adapter
  reports. The installer (`python -m bothy_hermes_adapter install|switch-mode|check`) sets up a
  profile and switches the billing mode without reading a value or restarting a process.
- Type stubs of the Hermes symbols the adapter uses, held equal to the pinned version.
- Fake-Hermes tests: the pinned Hermes in a subprocess with the fake model and the SDK's
  FakeServer (AG-08, AG-11, AG-13, AG-15, AG-20, AZ-P6, BR-13, the installer, the plugin
  discovery, the stub contract and the unchanged pin).

### Changed

- The Python project is named `bothy-hermes-adapter`; its runtime dependencies are those of the
  SDK, with lower bounds the pinned Hermes environment meets.
