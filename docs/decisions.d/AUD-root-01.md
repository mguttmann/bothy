# AUD-root-01 Gradle lock files in the advisory and license gates, lint scope, first steps

Work package of the audit of 2026-11-11 for the root of the repository (`Makefile`,
`CONTRIBUTING.md`, `README.md`). Findings: `deps-1` and `licensing-3` (one cause, rulings 1 to
6), `config-devex-3` (ruling 7), `docs-onboarding-1` (ruling 8), `docs-onboarding-4` (ruling 9).

| AUD-ROOT-01/1 | 2026-11-11 | `make osv` reads every tracked Gradle lock file (`GRADLE_LOCKS`, `*.lockfile`), in a pull request together with the other lock files and in the full scan in a step of its own, both through `tools/ci/advisories.py`, which without `--base` fails for every finding that counts. `make licenses` reads those under `apps/` and `packages/` (`DART_GRADLE_LOCKS`) whenever it reads `pubspec.lock`. A variant such as `gradle-firebase.lockfile` goes to OSV-Scanner as `gradle.lockfile:<path>`. `tools/ci/tests/test_lock_file_gates.py` lists the tracked lock files by the naming conventions of the package managers, runs the real recipes with a recording scanner and compares; two kinds of lock file are named there as no package locks (OpenTofu provider pins, the pins of release binaries). | `LOCK_NAMES` held five file names, and the six Gradle lock files of the Android builds matched none: the Maven packages of the Android app had no advisory and no license check, although gates.md promised all lock files. OSV-Scanner 2.6.0 picks its parser by the file name and ends with exit code 127 for `gradle-firebase.lockfile` under its own name (run with the pinned binary). The test failed on the commit before the change for exactly the six files, and one of its cases runs the pinned scanner offline against a generated advisory database over the tracked lock files. |
| AUD-ROOT-01/2 | 2026-11-11 | Both gates judge a package of a Gradle lock file only when it ships: on the runtime classpath of a release build (`releaseRuntimeClasspath`, `<flavor>ReleaseRuntimeClasspath`, `runtimeClasspath` of a module without build variants) or as `coreLibraryDesugaring` (`tools/ci/gradle_locks.py`). The other packages with a finding are counted in one line per lock file. A lock file that names none of these configurations fails; a `buildscript-gradle.lockfile` ships nothing. No package of a build or test configuration gets an entry in an `osv-scanner.toml`. | A Gradle lock file lists every configuration of a build, and OSV-Scanner reads it as a flat list. On the day of the change the scanner reported a known vulnerability for 20 packages of `apps/client/android/gradle.lockfile` and a license outside the list for 30 that only the build and its tests resolve: netty, grpc, bouncycastle and others in the test platform of the Android Gradle Plugin, lint, test libraries. SEC-ALERTS/9 already ruled that these follow the updates of the plugin. One accepted entry per package and version would be a list of that size in three folders, to be written again with every plugin update, and it would say nothing a rule on the configuration does not say. The license list applies to shipped parts only (licenses.md), as for the tools under `tools/`. The rule fails closed because product flavors or another build type would otherwise make the gates read nothing, which is the defect this package fixes. Not covered, and written down in gates.md ("What the gates do not cover"): advisories in the build and test configurations. |

| AUD-ROOT-01/5 | 2026-11-11 | `com.android.tools:desugar_jdk_libs` 2.1.5 (GPL-2.0 with the Classpath Exception, compiled into the app by `coreLibraryDesugaring`) is accepted by the license gate until the date of its entry in `apps/client/android/osv-scanner.toml`; the question whether the project accepts this license is the open owner question OQ-27 with the recommendation to accept it by an ADR. ## Open minors

- `tools/design-tokens` is outside mypy (93 errors under `strict` in 14 files, measured
  2026-11-11); `NOT_TYPE_CHECKED` in `tools/ci/tests/test_lint_scope.py` names it. Typing the
  generator belongs to the run that settles its place in `testpaths` and coverage too.
- No `Package.resolved` of the Apple apps is tracked (ruling 6).
- `make licenses` prints the path of a lock file as OSV-Scanner reports it, absolute; `make osv`
  prints it relative to the repository.
- A vulnerable package that a debug or profile build ships to a test device (today http4k
  through `patrol`, Okio 1 in the profile build) fails no gate (ruling 2).
- `tools/ci/tests/test_gradle_locks.py` still asks only for the `gradle.lockfile` of a settings
  root: a missing lock file of a subproject or of the build script passes, and the gates then
  have nothing to read for it.
