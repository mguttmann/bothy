# FIX-access-on-created A space or channel created by event gets the person's access

| No | Date | Ruling | Reason |
|---|---|---|---|
| FAOC/1 | 2026-11-05 | The sync engine loads the view of a space or channel whose stored row has no level: after `space.created`, `channel.created` and every later `space.*` or `channel.*` event of such a row it queues `loadStructureOf` for the target after the commit (`queueAccessLoad`, at most one load per target through `SyncContext.accessLoads`), and it stores level and capabilities from the `SpaceView` or `ChannelView`. Server, API and events stay unchanged; the client sync section of the specification says it (15 7.3 item 6). | Owner report: the owner saw neither "Rename project" nor "Delete project..." in the sidebar menu of a project forum created after the device's last full snapshot. The forum row on the device had no level: only `ChannelView` and `SpaceView` carry the access, `channel.created` carries only the channel, and the server sends no `access.changed` to an owner, who holds every capability through the owner rule (07). The menus and `threadPermissions` read no access and hid the entries. The gap dates from M4-14 (access only from views). Chapter 04 says nothing about the view after `*.created`, so the client rule is enough and no server change is needed. |
| FAOC/2 | 2026-11-05 | A connection from the cursor (`ready` with a stored cursor, `applyNonEvent`) queues the same load, one read per target, for every stored space and channel without a level (`StructureDao.spacesWithoutAccess`, `channelsWithoutAccess`). A failed load is logged without content (`background read failed`), the row stays without access, and the next event of the target or the next connection from the cursor tries again. A `resumed` session does not run it. | Devices that already hold such rows recover on the next start of the app without a resync. One read per target keeps one failure (for example a deleted channel answering `404`) from holding back the others. A resumed session continues the same process, whose earlier events already queued their loads. |
| FAOC/3 | 2026-11-05 | The fake world creates spaces and channels with their events as the server does (`createSpace`, `createChannel` in `world_structure.dart`): the payload carries only the object, no level and no capabilities, and no `access.changed` goes to the creator. `createSpace` adds the first channel before the events, because the fake's visibility of a space follows its channels. | The earlier fake had only `addSpace` and `addChannel` without events, so no test could reach a channel that first arrived by event. The catch-up test device with a cursor now holds the access its views reported (`World.connect`), as a real device does; before, its rows had no level, unlike rows a real device stored from a snapshot. |
