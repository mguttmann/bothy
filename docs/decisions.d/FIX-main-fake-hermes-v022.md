# FIX-main-fake-hermes-v022 Fake-Hermes gateway start without Hermes' import race

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-FH22/1 | 2026-10-30 | The Fake-Hermes harness starts the gateway through a launcher it writes next to Hermes' own entry (`bin/bothy-hermes-gateway`): it imports `hermes_cli.main` as `bin/hermes` does, replaces `hermes_cli.plugins.start_background_plugin_discovery` with a no-op, sets `argv[0]` to `bin/hermes` and runs `main()`. The gateway then runs the same plugin discovery on its main thread at its first `discover_plugins` call. The launcher exits with an error when Hermes no longer has that function. The retries of D-M2-33-14 stay for the other start failure (a start without the platform). The live recording keeps Hermes' own entry: it records Hermes as it runs. Place: `tests/fake_hermes_kit.py` (`write_gateway_launcher`). | Hermes `v0.22.5` starts its plugin discovery in a background thread while the main thread still imports the gateway (`hermes_cli/main.py`, `_prepare_agent_startup`); every gateway consumer joins that thread (`discover_plugins`), so it only overlaps the two. The bundled platform plugins import `gateway.platforms` in that thread, and the overlapping first imports of Hermes' own modules ended in a `KeyError` of the import system (`gateway.platforms.base_exec_approval`, `gateway.platforms.base_streaming_tts`, `hermes_cli.observability.shared_metrics_process`) or an `AttributeError` of a partly imported module, so the gateway exited before any platform started. On the main branch's CI run of 2026-10-29 two tests failed all five starts; locally under CPU load 3 of 12 first starts failed the same way. This is a condition of Hermes, not of the adapter (D-M2-33-13 keeps the adapter's own entry import-free for real Hermes). |
