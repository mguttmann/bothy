# SERVER-AGENT-TRIGGERERS Server side of the adapter allow list

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-SAT-1 | 2026-10-30 | Cause: `getAgentTriggerers` stood under `later` in `services/server/api/operations.yaml`, so the server registered no route and answered `404 not_found`; the SDK maps that to `AllowlistUnavailable` and refuses every event with `adapter_error` (D-M2-33-3). The brief of M2-33 named the gap; no ticket built it. Reproduced with the scenario `rag19_allowlist_from_server` against the real server: `getAgentTriggerers: 404 not_found` before, passing after. | A reproduced failure before the fix. |
| D-SAT-2 | 2026-10-30 | The set is computed in `authz` (`Authorizer.Triggerers`, port `authorize.AgentTriggerers` in `kernel/authorize`, like `TriggerHolders` of M2-13) and served by `agents` (`Service.Triggerers`, handler `GetAgentTriggerers`), which authorizes `agent.triggerers.read` on the calling agent and never derives a level. `wire.NewAgents` refuses an `Authorizer` without the port. | 02 assigns the action to `agents`; 05 rule 1.1 keeps levels in `authz`. A start without the port would serve the route with `internal_error`. |
| D-SAT-3 | 2026-10-30 | The set is T(A) of 07 section 6 from `domain.Triggerers` over `triggerWorld`, the same function and facts as the I1 check and `access.explain`: active owners and active people with effective `trigger` on a served target, without those SR2 blocks for the effective tool class. | One definition of T(A); the I1 check and the explanation already hold it with tests. |
| D-SAT-4 | 2026-10-30 | An agent with billing mode `organization` adds its guest channels (05 section 5 point 3: `allow_mentioned_agents`, not archived, not read-only, the agent's own snapshot reaches `write`) to its served targets. Spec gap: the description of `getAgentTriggerers` in openapi.yaml says "a channel the agent operates", 05 4.10 says "the people who may trigger this agent". | The adapter refuses every `sub` outside the list; without the guest channels a mention of a guest agent that the server accepted would fail in the adapter. The wider wording of 05, the core contract, wins. The openapi description stays until the next change of the contract, because its text is copied into the generated clients of four languages. |
| D-SAT-5 | 2026-10-30 | An agent with billing mode `personal` keeps only its credential holder (05 section 5 point 4); a holder outside T(A) gives the empty set. An unknown, inactive or policy-less agent has the empty set. | I2 lets only the holder trigger; the list must not admit more than the server does. |
| D-SAT-6 | 2026-10-30 | `permission_version` is the rights version of the request (the memo the authorization read), read before the set; every read of the set is fresh, never from the snapshot cache. | The set then holds every change up to the version it names, so a token with a higher version makes the adapter reload, and a reload never returns a set older than its version. |
| D-SAT-7 | 2026-10-30 | Contract test: the shared scenario `rag19_allowlist_from_server` (Python) and `rag19AllowlistFromServer` (TypeScript) runs against both FakeServers and the real server of `services/server/test/sdkserver`, with the agent's API token and DPoP. The name carries the requirement ID R-AG-19 because 09 16.2 has no scenario row for the allow list. | ADR 0026 "Confirmation": the same scenario against fake and real server; the Hermes adapter uses the Python SDK's allow list unchanged. |
| D-SAT-8 | 2026-10-30 | Other routes: every operation the Python and TypeScript SDKs and the Hermes adapter call (generated API modules, `client.GET` paths and the FakeServer route tables) is enabled on the server; `getAgentTriggerers` was the only one under `later`. | Checked against `operations.yaml` in this change. |
