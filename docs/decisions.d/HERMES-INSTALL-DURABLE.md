# HERMES-INSTALL-DURABLE Hermes adapter install that survives a new Hermes environment

Live finding of 2026-10-30: Hermes `v0.22.5` creates a new Python environment on almost every
CLI command and collects the superseded ones. The `.pth` file and `attrs` an operator put into
the gateway's environment were gone in the next one, and a gateway restarted after that ran
without the adapter: the agent was offline without any error.

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-HERMES-INSTALL-DURABLE-1 | 2026-10-30 | The install uses Hermes' discovery of directory plugins (`<profile home>/plugins/<platform key>`, read at every start), which the installer already used for the entry, and makes that folder self-contained: `packages.json` names the directory of `bothy_hermes_adapter`, `bothy_sdk`, `attr` and `attrs`; the plugin entry (`__init__.py`) puts one finder for the adapter's own names first on `sys.meta_path` and one for `attr` and `attrs` last, each serving exactly its names. Nothing goes into Hermes' environment. Place: `installer.py` (`locate_packages`, `packages_manifest`, `plugin_entry`, `install`), `__main__.py`. | Hermes' other mechanisms do not survive or do not fit: an entry point is metadata of a distribution in the environment, so it is gone with the environment; `python_dependencies` of a plugin are installed into each new environment only through Hermes' plugin admission and an index, and the adapter and the SDK are not published before M7. A finder per name, unlike a `sys.path` entry, cannot shadow a package of Hermes' environment with whatever else lies next to the adapter's packages. |
| D-HERMES-INSTALL-DURABLE-2 | 2026-10-30 | An own package that lies inside the installing Python's environment (`sys.prefix`) is copied into `vendor/` of the plugin folder, one outside it (a source tree of a checkout) is named by its absolute directory; `attr` and `attrs` are always copied. A second `install` replaces each copy. | A source tree is what the operator updates and keeps; whatever lies in an environment goes with it. `attrs` is the one dependency Hermes does not ship (11 11.3), and the directory it was installed into for the installer need not outlive the install. |
| D-HERMES-INSTALL-DURABLE-3 | 2026-10-30 | A package that `packages.json` names but that is missing, or an unreadable `packages.json`, stops the plugin entry with an `ImportError` after one error line in the gateway log (`bothy_hermes_adapter: missing package(s) <names>; run ... install ... again`). `check` reports `adapter: loadable` or `adapter: not loadable: <reasons>` (plugin not in `plugins.enabled`, a file of the entry or a named package missing, `cryptography`, `httpx`, `jwt` or `websockets` not importable in the profile's Python) without a value, and exits with `1` then. Place: `installer.py` (`adapter_problems`, `check`, `loadable`). | The brief asks for a check that detects the missing adapter. An offline reason in the server's presence is not built: with the discovery above the plugin no longer goes missing when the environment changes, and a plugin that cannot load cannot report anything to the server; the gateway log and `check` name the cause. |
| D-HERMES-INSTALL-DURABLE-4 | 2026-10-30 | The Fake-Hermes test `test_install_survives_a_new_hermes_environment` installs with the harness's `.pth` file and `attrs` in the environment, then moves both out of it (`new_environment`) before the gateway starts, serves a turn, and checks `check` before and after a vendored package is removed; both move back afterwards, so the integrity snapshot holds. The other Fake-Hermes tests keep the additions of D-M2-33-14. Place: `tests/fake_hermes_kit.py`, `tests/fake_hermes/test_installer_and_contract.py`. | Creating a second Hermes environment per test would cost a provisioning; removing exactly what the old install relied on is the state a new environment of Hermes leaves. |
