# RUNNER-CLI-PIN Claude Code pin 2.1.288, CLI too old for the model, model notation

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-RUNNER-CLI-PIN-1 | 2026-10-29 | `PINNED_CLAUDE_CODE_VERSION` of the claude-code-runner is `2.1.288` (was `2.1.259`, D-M2-34-12); `MIN_CLAUDE_CODE_VERSION` stays `2.1.259`, the version 09 18.2 names for `--permission-prompts none`. Checked against 2.1.288 without a session and without a model call: level one of the real-CLI suite (version, flags of `--help`, every `ERROR_TEXTS` fragment and stream token in the files of the CLI) passes; the recording `stream_fields_2.1.288.json` was read again from the files (every field the mapping reads is unchanged; new are `reason` of `task_notification`, `task_id` of `tool_progress` and the task type `local_memory_import`, none of them mapped); the captured API errors were written again by 2.1.288 against a local stand-in for the API (context full and refused key classify as before; a refused key is now retried ten times, about three minutes, before the CLI gives up); the texts of a missing and of an existing session and `/compact` with `supportsNonInteractive` were checked again. The Fake-Claude fixtures name 2.1.288; their message shapes did not change. Not checked again: the folding of a queued line into a notification turn and the success `result` of a failed compaction (D-M2-35-25), both need a model call. | In operation on 2026-10-29 the API refused current models to 2.1.259 ("version 2.1.280 or newer is required"); a host with 2.1.288 reported `runtime_version_untested`. |
| D-RUNNER-CLI-PIN-2 | 2026-10-29 | A CLI below the model's minimum is a recognised end (`ErrorKind.VERSION_UNSUPPORTED`, outcome `runtime_version_unsupported`): the fragments `does not support this model; version` and `is older than the minimum version required by your organization's policy` in the API error channel (the pattern of the CLI's own error kind `claude_code_version_too_old`). The run ends `failed` with `runtime_error` and no recovery; its box note carries a text of the runner that names the required version (only its digits are taken from the API's text) and says to update Claude Code. The runner raises its supported minimum to that version (without one: one patch past the probed version), reports `degraded` with `runtime_version_unsupported` at once with an immediate heartbeat, and prepare refuses runs until a probe finds a CLI at that version; the raised minimum lives in memory, a restart forgets it. No new reason code of 5.2 and no new degraded reason. | The live failure ended as a bare `runtime_error` while the heartbeat stayed `online`; every further run would cost a turn and fail the same way. The existing reason `runtime_version_unsupported` already means "update the CLI" and already blocks runs; a new server code would change the API for a runner-local fact. |
| D-RUNNER-CLI-PIN-3 | 2026-10-29 | The runner maps the model; the server keeps the pattern `^[A-Za-z0-9._:/@-]+$` of 09 2.2. `runner.default_model` and `runner_config.model` may use the CLI notation `<model>[<selector>]`; `--model` gets the value unchanged, and `startRun` and `agent_session.report` get the value without a trailing `[...]`, or no `model` when the rest does not match the pattern (the run goes on). Tested in `test_commandline.py` against the pattern read from 09 2.2 and in the scenario `test_cli_model_notation_reported_as_model_name`. | 09 2.2 defines one model name for `operator_config`, sessions and `run.start`, shown in the session column and carried in every invocation; the bracket is a selector of the CLI, not part of the model: 2.1.288 sends `claude-opus-5-5` plus the 1M context option to the API for `claude-opus-5-5[1m]` (checked against a local stand-in). Widening the server pattern would change the API schema and every client for a CLI detail. |
| D-RUNNER-CLI-PIN-4 | 2026-10-29 | The `timeout` parameter of `heartbeat.probe_version` stays and carries `NOSONAR` for SonarCloud rule S7483 (use a timeout context manager). | The probe turns a CLI that does not answer in time into the outcome `runtime_unreachable` and reaps the process itself; a timeout scope at the caller would end the probe by cancellation and leave each caller to map the error. The parameter predates this ticket; the finding came from the changed signature lines. |
