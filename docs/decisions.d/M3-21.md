| D-M3-21-3 | 2026-10-21 | The service account is a JSON object with `type = service_account`, non-empty `client_email` and `private_key_id`, a `private_key` of exactly one PKCS#8 PEM block holding an RSA key and an optional `token_uri` equal to the token URL; other fields are ignored, and no error text holds a byte of a value. The assertion is signed with `jose.RS256Signer` of `kernel/jose` (no own signer): header exactly `alg = RS256`, `typ = JWT`, `kid` = `private_key_id`; claims exactly `iss` = `client_email`, `scope = https://www.googleapis.com/auth/firebase.messaging`, `aud` = the token URL, `iat` and `exp` = `iat` plus one hour; it is posted with the JWT bearer grant (RFC 7523 2.1). Every token request resolves and parses the service account again. Place: `internal/notify/adapters/fcm/account.go`, `internal/notify/adapters/fcm/token.go`, 13 5.2. | 13 5.2 and 11 [13 Q8]; one hour is the longest assertion lifetime Google accepts [13 Q17]; ADR 0067 item 2 lists `RS256` for signing assertions and the merged `kernel/jose` already exports the signer; reading the key at each token request makes a rotation work without a restart (16 5.2). |
| D-M3-21-4 | 2026-10-21 | The access token is reused while now is before its time of issue plus half its `expires_in`; one mutex guards the cache and the token request runs under it, so at most one token request is in flight however many sends run in parallel, and a failed request stores nothing. A `401` without `THIRD_PARTY_AUTH_ERROR` (`UNAUTHENTICATED`) for the current token drops it, gets a new one (parallel sends reuse the replacement) and sends the same message once more; a second `401` for the replacement is a configuration error. Place: `internal/notify/adapters/fcm/token.go`, `internal/notify/adapters/fcm/adapter.go`, 13 5.2. | Half the lifetime leaves a wide margin for clock skew and request time without a new configuration key, and the ratio derives from the provider's own answer; a revoked or expired token heals with one request instead of losing the hint. |
| D-M3-21-5 | 2026-10-21 | A configuration error of the credentials (`401` twice, `403 PERMISSION_DENIED`, `404 NOT_FOUND`, a token request refused with a `4xx`, a failed resolve or parse of the service account at that time) drops the token, writes one Error record and pauses the adapter for `push.retry_cap`: meanwhile `Send` returns `config_error` without a request and without a log record. The first send at or after the end probes once with a new token, reading the key again; any other result ends the pause with one Info record, a configuration error starts the next pause. `SENDER_ID_MISMATCH` and `THIRD_PARTY_AUTH_ERROR` never pause; a token endpoint answering `429`, `5xx` or not at all gives a transient Go error and no pause. The pause lives in the process. Place: `internal/notify/adapters/fcm/token.go`, 13 5.2. | 13 7.2 asks for an alert and no repetition, but without a pause every hint would ask the token endpoint again with a revoked key; `push.retry_cap` is the longest wait the push path already names, so a rotated key or a fixed project heals within it without a manual step, and dropped hints are carried by the unread counts (13 7.3); answers about one registration or a transient endpoint do not show the credentials wrong. |
| D-M3-21-6 | 2026-10-21 | The message is built from structs in the key order of 13 6.2: `message` with `token`, `android` (`priority` `high`, `normal` for quiet hints and the sync form; `ttl` = `push.ttl` in whole seconds plus `s`) and `data` with only `v`, `nid`, `k`, `i`, `t`, `m`, `badge`, `quiet`, every value a string; `t` and `m` are absent without thread or message, `badge` is always present, `Count` and `TargetID` are not carried, and no `notification`, `collapse_key`, `apns`, `webpush` or `fcm_options` key exists. Pre-checks without a request: wrong provider, unknown kind, zero `nid` or instance ID, or no badge give `program_error`; an empty token or one with a byte outside printable ASCII or a space gives `disable` with `token_invalid`; `environment` and `app_id` are not read. `data` above the FCM limit of 4096 bytes gives `program_error` and is never truncated. The sync form has `v`, `nid`, `k = "sync"`, `i`, `badge` and `cleared` (comma-separated, in the order given), without `t`, `m` and `quiet`; when `cleared` would exceed the limit it is left out entirely. Place: `internal/notify/adapters/fcm/payload.go`, 13 6.2. | ADR 0031 and 13 1 point 1: no content at Google, an allow list of keys and value types; R-PN-08 and D-PN-06: no `collapse_key`; the limit is Google's [13 Q9]; a partial `cleared` list would leave the app unable to tell which notifications remain, so the list is complete or absent, the same limit 13 8 states for iOS. |
| D-M3-21-7 | 2026-10-21 | The answer table of 13 7.2 is a pure function of status, body, header and time; the FCM error code is `errorCode` of the `FcmError` detail and the token cause of `INVALID_ARGUMENT` a `fieldViolations` entry on `message.token` in the `BadRequest` detail or the `FcmError` code `INVALID_ARGUMENT` without a violation on another field (D-M3-21-17); `error.message` is never read into a log or an error text. Unlisted answers follow the nearest listed answer of the same status: any other `400`, `4xx` or status outside `2xx`, `4xx`, `5xx` is `program_error`; `401` otherwise renews (D-M3-21-4); `403` and `404` otherwise are `config_error` with pause; any `429` is `throttled`; any `5xx` is `retry`. `Retry-After` is read as delta seconds or as an HTTP date against the clock, a negative, unreadable or past value counts as absent; `429` waits at least one minute; without `Retry-After` the job's `domain.RetryDelay` applies with its jitter in [0.5, 1], so the first retry comes between half of `push.retry_base` and `push.retry_base`, every retry at most `push.retry_cap` later, and a `Retry-After` beyond `push.max_age` ends the hint as `expired`. Place: `internal/notify/adapters/fcm/classify.go`, 13 7.2. | Google documents the HTTP status as the class and the error code as its detail, and the one minute minimum after `QUOTA_EXCEEDED` [13 Q16]; `error.message` may echo request values; "backoff between `push.retry_base` and `push.retry_cap`" in 13 7.2 is read with the jitter of 13 7.3. |
