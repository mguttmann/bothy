# AUD-srv-platform-01 Client IP from one forwarding header

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-SP1/1 | 2026-11-11 | `ClientIP` reads the one forwarding header that a request from a trusted peer carries, `X-Forwarded-For` or `Forwarded`; for a request with both headers the peer is the client. This replaces "`Forwarded` when present, else `X-Forwarded-For`" of M1-18 (06 section 2, 08 section 13 with ID-T25, 16 section 4.3). | A proxy that sets one header passes the other one through as the client sent it (nginx and the example edge did so with `Forwarded`). With the old order an anonymous client chose the address for `rl.public_auth` and the audit and could empty the bucket of another address. The server cannot tell which of two headers the proxy wrote, and preferring `X-Forwarded-For` would open the same hole behind a proxy that sets only `Forwarded`. |
| AUD-SP1/2 | 2026-11-11 | No configuration key names the header to trust. | Counting the peer for a request with both headers closes the hole in every setup, without a key that the operator has to match to the proxy and whose wrong value would trust the passed-through header. A proxy that sets both headers sends one of them after this change (16 section 4.3). |
| AUD-SP1/3 | 2026-11-11 | The example edge removes `Forwarded` in each of its locations (`proxy_set_header Forwarded "";`), and 16 section 4.3 and `docs/operations/install-compose.md` section 5.1 ask the same of the operator's proxy. The TLS fronts of the demo and of the test stacks stay as they are. | Without the header no request reaches the server with both, so a client behind a forward proxy that adds `Forwarded` keeps its own limit. The demo and test fronts publish on loopback only, and for a request with both headers the server counts the front. |
