# FIX-run-retry-and-orphan-operator Retry of a run and thread operators outside their channel

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-RRO/1 | 2026-10-30 | Cause: imported threads carry `planned_operator` as their fixed operator (R-IM-08), and a thread operator gets `write` on its thread by the operator rule (07 2.9) whatever the channel's operator is. After a switch-over that left the channel without that operator (or with another one), every message in such a thread passed `agent.invoke` and started a run that the runtime ended at once (`adapter_error`), and nothing let the person start the run again once the cause was fixed. | Reported from live use on 2026-10-30; reproduced with `TestThreadOperatorOutsideChannel` and `TestAccept_ThreadOperatorOutside` (the thread operator is an agent that is not the channel's operator; with the rule switched off the retry answered `202` and opened a run). |
| FIX-RRO/2 | 2026-10-30 | "Allowed in the channel" for a fixed thread operator (09 3.4 step 4a, R-AG-36): it is the channel's effective operator, or it has `write` of its own on the channel (a grant, decided as `thread.create` on the channel for the agent in filter mode, which the thread-level operator rule of 07 2.9 does not reach), or it has the active run of the thread, or it completed a run in the thread. Otherwise a message that would trigger it is rejected with the new acceptance reason `operator_not_in_channel` and no run; a failed run of it does not count. | An operator change of a channel must not silence threads its former operator has worked in (R-DM-12, the session of the thread); a thread it never served successfully (an imported thread, or a thread whose only runs failed) is exactly the live case. A completed run is the one durable sign that the agent works there. An agent the owner granted `write` on the channel is allowed there like a guest (09 3.6); the import tests that give the planned operator a grant instead of the channel operator keep working. |
| FIX-RRO/3 | 2026-10-30 | The rule lives in the trigger decision of `runs` (`domain.Decide`, input `ThreadOperatorOutside`, step `thread_operator` after `trigger_right` and before the voice rule), not in the `agent.invoke` guard of `authz`. Like `voice_unsupported`, the rejection is written without `agent.invoke` in request mode (no audit entry); a person without trigger who did not mention the agent still gets nothing (R-AG-05). Mentioning the operator does not make it a guest. | The guard also decides deliveries, follow-ups and the session switches; changing it would cancel running runs and change permissions (07 2.9). The rule concerns only whether a new run starts. The check of the grant and the read "completed a run in the thread" (`runs.CompletedRunOfAgent`) run only when the operator is neither the channel's operator nor the active run's agent. |
| FIX-RRO/4 | 2026-10-30 | `retryRun` (`POST /runs/{run_id}/retry`) uses the catalogue action `agent.invoke` as its route action instead of a new action: the use case checks `run.read` in filter mode (an invisible run is `404`), then the state rules, then the thread operator rule (`403 agent_invocation_denied` with `reason = operator_not_in_channel`) and `agent.invoke` in request mode for the caller with the run's agent, the mention of the triggering message and `NewThread` for a run in the auto thread of a main-thread message. | The brief asks for "the same rights as triggering"; that is `agent.invoke` with its guard and its audit of denials, and the chain proves the route action was checked. A new action would only repeat it. |
| FIX-RRO/5 | 2026-10-30 | Only the newest run of its thread (`queued_at`, then `id`), only `trigger_kind = message`, only `failed` or `cancelled`; otherwise `409 invalid_state_transition`. Idempotent: when the newest run of the thread is a run of the same agent for the same message, the answer is that run without a write, after the same rights check (the route proof needs it, and the answer must not reach someone who could not retry). | "The last trigger message in a thread": a retry of an older message would answer out of order. The natural key (message and agent) makes a second click or a second device harmless also after `sync.idempotency_key_ttl`. |
| FIX-RRO/6 | 2026-10-30 | The new run is opened like an acceptance (`invokeOrHold`): same thread and agent, the old `triggering_message_id`, `triggered_by` = the caller, a new anchor, `run.state_changed`, `trigger_state = received`, `agent.invocation` (held while an attachment is not final). The delivery re-check uses `triggered_by` as before. | The caller is the person who decided to run it again; I2 and SR2 are decided for that person, as for a trigger. |
| FIX-RRO/7 | 2026-10-30 | Apps: "Retry" ("Erneut versuchen") on the run line of the newest `failed` or `cancelled` run of a thread, in the one Flutter thread view used by macOS, Windows, iOS and Android. It enqueues `retryRun` without a thread in the lane `run:<id>` (like `cancelRun`), stays disabled while the entry waits, and on a refusal discards the entry and shows "Could not retry: <reason>" with the translated reason. After `interrupted` and `stale` the line keeps "Send again" only (09 5.5). The app does not know `trigger_kind`; a command run gets the server's `409` as its refusal text. | Writes go through the outbox (15 1 principle 3). A failed retry entry left in the outbox would show nowhere, so the button owns it. `RunSummary` has no trigger kind, and adding one is outside this fix. |
| FIX-RRO/8 | 2026-10-30 | `bothy import discord switch` reads the threads of the channel after its preconditions and before the mirror round; threads whose operator is not the agent of `planned_operator` (or any operator while the mapping plans none) end the command with exit `2`, no write, and a text with the count per agent ID, the operator the channel will get and the two ways on; `--force` prints it as a warning and goes on. | "The channel will have" the planned operator: step 3 tells the owner to set exactly it (22 13.3). The tool cannot read the future operator, so the mapping is the source; the server rule of FIX-RRO/2 covers an owner who ignores it. IDs and counts only (22 10.2 rule 4). |
| FIX-RRO/9 | 2026-10-30 | The fake server of `sync_engine` answers `retryRun` with the same state and idempotency rules and `403 agent_invocation_denied` (`no_trigger_right`) without trigger; it has no thread operator rule, which a test scripts with `faults.onRequest`. | The client tests need the operation; the operator rule depends on server facts the fake does not model. |
| FIX-RRO/10 | 2026-10-30 | Out of scope: a forum operator without a project folder binding still fails its run with `adapter_error` and the summary of R-AG-35; the person now retries it after binding the folder. Model commands of a thread operator outside the channel are not covered by step 4a (they name their owner explicitly). | The brief names the missing binding as the cause of the failed run, which retry now handles; the command path triggers by an explicit choice of the person. |
