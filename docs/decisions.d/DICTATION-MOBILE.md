# DICTATION-MOBILE External dictation into the composer on iPhone and Android

| No | Date | Ruling | Reason |
|---|---|---|---|
| DM/1 | 2026-10-31 | The paths covered on iOS are `insertText:` of the focused `UITextInput` (whole and in pieces after reading the text before the cursor, as a keyboard extension's `textDocumentProxy` does), `setMarkedText:` then `unmarkText` (the system dictation), the action `paste:` sent to the first responder (the system edit menu), the app's own Paste button and Cmd+V; on Android `commitText`, `setComposingText` ended by `commitText` or `finishComposingText` (input methods and voice typing), `performContextMenuAction(paste)` (an input method's clipboard), the Paste button and Ctrl+V. | A dictation app on iOS can only reach another app's field through a keyboard extension (an insert through the document proxy) or the pasteboard; the desktop sources of the dictation app in question record its iOS transcripts with the source "iOS Keyboard" (a keyboard extension); its iOS sources were not available, so both the insert and the paste path are covered. On Android these are the ways input methods, voice typing and the clipboard edit a field. |
| DM/2 | 2026-10-31 | The native side of the device tests is a method channel `bothy/text_input_probe` that only debug builds register: on iOS under `#if DEBUG` with `SWIFT_ACTIVE_COMPILATION_CONDITIONS = DEBUG` set in `ios/Flutter/Debug.xcconfig` (the Runner target had no such condition), on Android in `src/debug/kotlin` with a no-op object in `src/probeoff/kotlin` for every other build type. | The phone suite runs the debug build with `flutter test -d`, so the probe needs no new runner or target; a release or profile build carries none of it. A test that only fed editing values to the framework would not show whether the platform's text input and the field stay in step. |
| DM/3 | 2026-10-31 | No change of the composer: every path passed on an Android emulator (API 36) and at the framework level; the iOS paths run in the `apps-ios` CI job. An insert counts by what it inserts at once: over `ui.composer_paste_file_chars` or `ui.composer_paste_file_lines` it becomes `paste.txt` (also when an input method sets it as composing text), a dictation that grows in small steps stays text as typing does. 01 6.13 item 1 says so. | Text that arrives at once cannot be told from a paste, and a long dictation typed out word by word is typing; the rule of M4-47 compares each change of the field, which gives exactly this. |
| DM/4 | 2026-10-31 | The file paste of `AttachPasteShortcut` stays as it is on iOS (Ctrl+V, no Cmd+V). | Package `pasteboard` has no iOS implementation, so reading files from the clipboard there fails; the text of Cmd+V pastes through the field's own shortcut, which the tests check. Open minor: a file paste on iOS first needs a clipboard source for iOS. |
