# AUD-srv-importer-01 Import findings of the audit of 2026-11-11

Work package of the audit of 2026-11-11 for the importer module of the server, findings
`srv-import-2`, `fn-import-migration-5`, `srv-import-5`, `srv-import-1` and
`fn-import-migration-9`.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-SIM1/1 | 2026-11-12 | `import.progress` follows payload rule 2 of 04 section 2.2. It carries the whole source while its payload is smaller than `sync.event_payload_max_bytes`; otherwise the reduced payload with `id`, `kind`, `name`, `state`, `stats` and the times, `config` empty (`{}`) and no `cursor`, and `truncated` in the envelope, so a receiver reads the source with `getImport` (`importer/app.progressPayload`). The importer reads the key of `sync`; it adds none. A reduced payload that does not fit either (counters of the tool larger than the limit) stays an internal error and writes nothing. The schema `ImportProgressPayload` is unchanged: `cursor` was optional in `ImportSource` already and `{}` is a valid `config`. | `srv-import-2`: `changed()` put config, counters and cursor whole into every event, and the appender refuses a payload at the limit as an internal error. The tool adds two entries per thread to its cursor and never removes one, so `setImportCursor` answered `500` once the cursor passed the limit and every new run stopped at the same place (reproduced on a started server with a cursor of some thousand threads, `TestProgressOfLargeSource`). The envelope member `truncated` exists for exactly this case and `messaging` uses it; a payload schema without `config` would change the contract of every generated client for an event that only the console reads. |
| AUD-SIM1/2 | 2026-11-12 | Not built for `srv-import-2`: the progress per thread in rows instead of one cursor document, and fewer reads of the source per batch by the tool. The stored cursor is bounded by the body limit of `setImportCursor` (`http.max_json_body_bytes`), which answers `413 payload_too_large` and leaves the stored cursor; the operator raises the key for a larger import. | The finding is the `500` at the event limit, which AUD-SIM1/1 removes for every size the body limit admits. Rows per thread are a new layout of the cursor that the tool owns (D-M8-04-8, 22 7.3) with a new interface between tool and server; the reads per batch are in the tool, not in this module. Open minor for the next run in the console: `ImportController.applyProgress` of `packages/admin_ui` takes a payload as a whole snapshot and has no caller yet (the console has no gateway, D-M8-08-1); a caller with a gateway reloads with `getImport` when the envelope says `truncated`. |
| AUD-SIM1/3 | 2026-11-12 | The retention class `import` gets its job. The server knows `retention.import_after_completion` (duration, at least one day, default of 20 section 13) and runs `retention.import` like every class job of the kernel port `retention`. The participant `importer/adapters/postgres.Retention` removes, in batches, the items of a source in the state `completed` or `failed` whose `finished_at` lies before the cutoff, and then the row of the source once it has no item left; a `draft`, `running` or `paused` source has no end time and keeps every row. The imported spaces, channels, threads, messages, files and people stay; a message only loses `import_item_id` (`ON DELETE SET NULL`). The job writes no audit entry and no event, like the other class jobs without an actor; the removed rows count in `bothy.retention.deleted`. Migration `00105` builds the partial index on `messages (import_item_id)` concurrently, so deleting an item does not read the table `messages`. | `fn-import-migration-5` and `srv-import-5` (one cause): 20 sections 2, 4.1 and 13, 22 13.5 and 14, the guide and the confirmation of the console promised the deletion, the key was `planned`, `JobClasses` had no `import`, and M7-05 and M8 each left the job to the other. Identifiers of the source system, also IDs of people who never used this server, stayed without a period (on a started server the items of a source completed before the period stayed whole, `TestRetention_ImportAfterCompletion`). The source row goes too, because 20 section 2 names both tables and the stored mapping holds the Discord IDs of the mapped people. Items go before the source so that no transaction cascades over the items of a whole import. The index is the class of audit finding `data-layer-3` (00104): a foreign key without an index on the referencing column reads the child table for each deleted row. |
| AUD-SIM1/4 | 2026-11-12 | No step of the owner deletes the import state before the period. 22 13.5 and the guide no longer say "by the owner"; a shorter period is set with the key. | No operation, action or console step for it exists, and the text of the console confirmation never named one. An early deletion would be a new operation with step-up, a catalogue action and a console step; the audit asked for the job or that step, and the job keeps the promise of 20. |
| AUD-SIM1/5 | 2026-11-12 | A posted thread item applies the mirror rules of 22 12.2 step 3 only while the stored mapping gives the channel of its `channel_origin_key` the lead `discord`. In a channel with the lead `bothy` it answers with its target and changes nothing (no rename, no close, no reopen, no `last_activity_at`, no event); `earlier_session` is still applied. A channel the mapping does not name keeps the earlier behaviour. `import.apply` itself does not look at the lead: a full run still writes new messages into a channel led here. 22 7.2 and 12.1 and the guide say so. | `srv-import-1`: after the switch-over the Discord channel is locked and its threads are archived there after a while, so a full run closed threads that people work in here, reopened threads closed here and renamed threads with an `auto` title (reproduced on a started server, `TestPostedThreadWhereThisServerLeads`). 22 12.1 says "no mirror" for such a channel. The `409` the audit proposed for every batch into such a channel is not built: importing a channel with the lead `bothy` from the start and taking over late messages are intended and held by `TestImportedMessagesNeverTrigger`. The lead is read from the item's `channel_origin_key`, the member that already decides the channel and the planned operator of a new thread; a Discord thread never changes its channel. Unchanged and now written down: messages a full run takes over after the switch-over are appended behind the messages written here, and the batch end moves `unread_floor_seq` (D-M8-11-4). Open minor for the next run in the import tool: a full run stores the fingerprint of every thread item it posts in its cursor, also where this server leads; after a revert of such a channel the read mirror posts a thread item again only when Discord shows the thread differently than at that run or has new messages for it, so until then the thread keeps the state it has here. That errs to the side of R-IM-11 (a thread left open does no harm). |
| AUD-SIM1/6 | 2026-11-12 | `fn-import-migration-9` is confirmed and not built here: no code path writes the item state `failed` or the column `error`, so the section "Failed items" of the console is always empty. The module README and 03 4.11 now say that both are reserved and that the failures the tool counts are in `stats.tool`. | Either fix is a decision about the product and larger than this package. Storing a refused or failed single item as `failed` and going on changes the rule "a batch is one transaction" of 22 8, the answers of `applyImportBatch` and the tool. Removing the state, the column, the member `error`, the state filter and the console section changes the API contract, every generated client and the console, and dropping the column needs two releases (upgrade.md, expand and contract). Question for the owner: shall the import record single failed items on the server and go on, or shall the state and the console section go and the counters of the tool stay the only place? |
| AUD-SIM1/7 | 2026-11-12 | The attribute `bothy.retention.class` of `bothy.retention.deleted` takes the value `import` (catalogue and signals.md 4.4), so the rows of the new job are counted under their class. Nothing else of the metric changes. | A class outside the closed set is recorded as `other`. Open minor, found here and left as it is because it lies outside the findings of this package: the classes `ops` (M7-09) and `privacy_job` (M7-06) are missing in the same set, so their rows are counted as `other`; the next run in the observability catalogue adds them and a test that holds the set against `retention.JobClasses`. |
