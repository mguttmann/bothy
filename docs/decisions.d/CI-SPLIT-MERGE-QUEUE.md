# CI-SPLIT-MERGE-QUEUE Fast pull request checks and the full suite in the merge queue

Owner request: pull requests wait for hours because each runs the full suite of
every platform on the few macOS runners; split the CI and run the full suite once per batch in
GitHub's merge queue.

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-CSMQ-1 | 2026-10-31 | `ci.yml` has a fast stage for pull requests (`ci-plan --stage pr`) and a full stage for `merge_group` (`--stage queue`: every job of a push to main plus the trials of the diff); a push to `main` keeps the full run. | The full suite runs once per batch before the merge instead of once per pull request; the watcher keeps its run on `main`. |
| D-CSMQ-2 | 2026-10-31 | The fast stage narrows only the platform jobs: a native folder runs its own platform (`ios/` also macOS, which runs ClientKit; `android/` also `test (apps)` for the JVM tests); other Dart changes and shared inputs run `apps (Windows)` and `apps (Android API 36)`; dependency manifests, the lock file and `platform-tests.json` run all five. | The platform jobs are the slow and scarce ones; dependencies reach every native build, so failing those early is cheaper than a split batch. |
| D-CSMQ-3 | 2026-10-31 | The stages are switched by the repository variable `BOTHY_MERGE_QUEUE`, which `tools/ci/merge_queue.py apply` sets only after the ruleset exists and `disable` resets first. | Without a queue behind it the fast stage would let pull requests land without the full suite. |
| D-CSMQ-4 | 2026-10-31 | Ruleset (`QUEUE_PARAMETERS` in `tools/ci/merge_queue.py`): squash, groups of 1 to 5 (`min_entries_to_merge`, `max_entries_to_merge`), two groups built at a time (`max_entries_to_build`), only the head of a group must pass (`HEADGREEN`), timeout 360 minutes (`check_response_timeout_minutes`); the required check stays `ci-ok` of the branch protection. | Two builds hold most of the macOS jobs that may run at once, the push to `main` needs the rest; the contract test may take 240 minutes. |
| D-CSMQ-5 | 2026-10-31 | `sonar` does not run in the merge queue; the queue compares flakes and advisories with the base of the group. | The pull request's scan is the gate of its new code; a new advisory that `main` has too must not stop unrelated pull requests (the daily scan and the push to `main` report it). |
| D-CSMQ-6 | 2026-10-31 | The repository is owned by a user account, not an organization, and GitHub offers merge queues only to organizations (D-W-34; the ruleset API answers 422 "Invalid rule 'merge_queue'"). The workflow and the tool are ready; the queue starts when the repository moves to an organization and `merge_queue.py apply` runs. Until then pull requests keep the full plan of their diff (D-CSMQ-7). | Owner decision: moving the repository changes its owner and URL. |
| D-CSMQ-7 | 2026-11-06 | A pull request whose diff holds only documentation that no component reads runs no conditional job, only the jobs of every change (the three `gates` jobs with the docs and contracts gate, `test (tools)`, the deny list, `sonar`, `ci-ok`); any other file keeps the plan of its diff, and a push to `main` the full run. The stage `full` already read the diff; PR #555 ran every job because `mkdocs.yml` was outside the component map, a shared input. `mkdocs.yml` is now documentation (`make docs` and the tools tests read it; the guide test of the server only looks for it to find the root). A file under `docs/` that a test, build or generator of a component reads is an input of that component (`GATE_COMPONENT_INPUTS`, `GATE_COMPONENT_INPUT_PREFIXES`): `docs/spec/` for `server` and `apps`, `docs/operations/` for `server`, and single files such as `docs/operations/configuration.md`, `docs/observability/signals.md`, `docs/PLAN.md`; `tools/ci/tests/test_components.py` scans the code of every component, and the tool folders whose target runs only in the job of one component (`tools/lint/` and `tools/contract/` in the server jobs, `tools/api-checks/breaking.py` for `make api-breaking`; I569), for the docs paths it names and fails while one does not select its reader. Not covered: a component that builds a docs path at run time from pieces the scan cannot see; a path split over several lines, because the scan reads line by line (no such case when I569 was built); and the other tool folders. Those run in the jobs of every change (the `gates` jobs, `test (tools)`), except `tools/console-e2e/`: its job is not selected by `docs/operations/configuration.md`, which it reads for the desktop targets it records next to the measurement; its test in `test (tools)` parses that file on every change, and a value outside the target is recorded, not a failure. | Pull requests that only change docs waited about an hour on macOS runners that their diff cannot affect. The spec chapters were not inputs before, so a pull request of only spec changes skipped the tests that read them; they now run on Linux runners, the platform jobs still do not. |
