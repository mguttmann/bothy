# M4-47 Long pastes become a file and long texts stay one message

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-M4-47-1 | 2026-10-29 | A paste is long above the App keys `ui.composer_paste_file_chars` (default 4000 characters) or `ui.composer_paste_file_lines` (default 100 lines; a trailing line break starts no line). The composer finds a paste as the text one change of the field inserted (common prefix and suffix of the old and new text), so every paste path counts: keys, context menu, phone keyboard, a dropped text. Text the composer sets itself (templates, quotes, another device's draft, "Insert as text") is marked as seen and never becomes a file. | Owner decision 2026-10-29: a person never hits a length limit. A key handler misses the context menu and the phone keyboards; the change itself is the same on every platform. The defaults match the brief ("for example 4000 characters or 100 lines"). |
| D-M4-47-2 | 2026-10-29 | A long paste becomes the attachment `paste.txt` with the text as it is. One fenced block with a known language becomes `paste.<extension>` with the code of the block without the fence (a fixed table of common languages; an unknown one keeps `txt`); a script with `#!` (python, node, shell), JSON that parses, XML, HTML or a diff gets that extension. The declared type is `text/plain` (`application/json` for JSON, `text/markdown` for Markdown). The attachment keeps the pasted text in memory for "Insert as text", which removes the file and its upload entry and inserts the original text at the cursor. A paste the attachment rules refuse (count, size) goes back into the field as text and the refusal shows. | A code file opens in an editor with highlighting, which a `.txt` of a fenced block does not; the upload deletes its copy after sending, so the text for "Insert as text" must live with the attachment. |
| D-M4-47-3 | 2026-10-29 | A text above `message.max_content_bytes` goes out as one message: the head as its text and the rest as one attachment, `message.txt` from a person and `answer.txt` from an agent. The cut is the longest prefix within the bytes that never splits a character, back to its last line break, and back before the opening line of a fenced code block the cut lies in (unless that block starts the text, then it stays cut); head and attachment together are exactly the text. Dart (`long_text.dart`), Python (`bothy_sdk.long_answers`) and TypeScript (`sendLongMessage`) cut by the same rule. While the composer's text is above the limit a note says so before sending. | One message keeps a reply readable, quotable and searchable as one; a code block cut in two renders as two broken blocks (01 6.4). |
| D-M4-47-4 | 2026-10-29 | The composer refuses with the limit text only when the rest cannot become an attachment (the count of attachments is full, a file over `file_max_upload_bytes`, no file support); the text stays. Editing a message keeps the limit, because `MessageUpdate` carries no attachments. The server limits (`message.max_content_bytes`, `http.max_json_body_bytes`) are unchanged. | The attachment is the only way to carry more than one message may hold without a server change; an edit that silently moved text into a new file would change what others already read. |
| D-M4-47-5 | 2026-10-29 | The Hermes adapter gives Hermes `MAX_MESSAGE_LENGTH` and `max_message_length` 2^31 - 1 and `splits_long_messages = True`, so Hermes neither splits an answer into several sends nor cuts cron output; it applies `hermes_adapter.max_message_bytes` itself through `send_long_message`. An edit of an answer stays cut to the limit (no attachments on an edit); with draft streaming the finished reply arrives through `send`. | Before, the adapter cut an answer above the limit (data lost) and Hermes split an answer above `MAX_MESSAGE_LENGTH` characters into several messages; both break "one answer, one message". |
| D-M4-47-6 | 2026-10-29 | The Claude Code runner reads `message_max_content_bytes` with `getInstance` only for an answer text above 4096 bytes (`LIMIT_READ_FLOOR_BYTES`); above the limit the rest becomes the last file `answer.txt` of the answer's set, staged by the runner itself (not checked against the roots and patterns, which guard files of the turn) and counted against `message_max_attachments` and `file_max_upload_bytes`. The set stays all or none: when it fails the head goes out with the notice naming `answer.txt`. A failed read of the limit sends the answer as it is. | Most answers are short and cost no request; an instance limit below 4096 bytes is not a supported setup. Reusing the staged and persisted set keeps the crash recovery of M3-12 for the rest too. |
| D-M4-47-7 | 2026-10-29 | Both SDKs offer `send_long_message` (Python) and `sendLongMessage` (TypeScript): within the limit one message as it is; above it one message with the head and the rest uploaded in mode `direct` as `answer.txt`; when that upload fails, the head (cut shorter so the note fits) with a short note, still one message. The Python FakeServer refuses a `content_md` above `message_max_content_bytes` with `400 validation_failed` `too_long`, as the server does. The TypeScript `sendMessage` gained `attachmentFileIds`. | Every agent built on the SDKs gets the rule without its own upload code; a FakeServer that accepted any length would let a cut or split answer pass the tests. |
