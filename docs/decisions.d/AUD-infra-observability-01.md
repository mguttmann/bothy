# AUD-infra-observability-01 Backup alerts fail closed on a missing value

Work package of the audit of 2026-11-11 for the hand-written alert rules
(`infra/observability/prometheus/rules/bothy-alerts.yaml`). The findings `fn-operations-backup-2`,
`srv-stats-status-1` and `srv-instance-ops-2` share one cause: the alerts on the backups, the WAL
archive and the restore test compare a time that only `bothy-backupd` reports, and stayed quiet
when that value was missing (rulings 1 to 4). Ruling 5 names the parts of these findings that
this package does not build.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-IO1/1 | 2026-11-12 | `BothyBackupStale`, `BothyWalArchiveStale` and `BothyRestoreTestStale` also fire when their gauge had no value in a window as long as their threshold: `... > <threshold> or absent_over_time(<gauge>[<window>])`, with `[26h]` once per backup kind (`physical`, `logical`, `objects`), `[15m]` for the WAL archive and `[8d]` for the restore test. Level, `for` and texts stay. The rule tests hold every window and every kind (`bothy-alerts.test.yaml`, and for the two long windows `bothy-alerts-windows.test.yaml` with one evaluation every 15 minutes). | `time() - max(<gauge>)` over no series is empty, not large, so each alert was quiet exactly when it mattered: `bothy-backupd` down or unable to export, a backup kind or a restore test that never succeeded, and a service that could not read `backup_runs` when it started. The same class was fixed for `BothyMalwareScanFailing` (M1-04/10). A window and not `absent()`: a run by hand reports its value from a short-lived process, so that series ends minutes later, while the service learns of the run only at its next start; with `absent()` the alert would fire shortly after the first backups of a new installation succeeded, and after every longer restart. With a window as long as the threshold the summary stays true in both halves: no success was reported in that time. The kinds are named one by one because `absent_over_time` takes its labels from equality matchers; they are the closed set of `bothy.backup.kind` on the last success (signals.md 4.6). |
| AUD-IO1/2 | 2026-11-12 | Two consequences of ruling 1 are accepted and documented (`docs/operations/install-compose.md` section 4, the runbook anchors of alerting.md). On a new installation with the profile `observability`, `BothyBackupStale` fires after its `for` for every kind that has not succeeded yet, and `BothyRestoreTestStale` likewise. With the driver `s3` and no off-site target the alert stays for the kind `objects`. | Both are the case the findings name: a kind that has failed since its first run. Without an off-site target the object mirror of the driver `s3` cannot run, and `bothy-backupd` itself records each of these runs as failed (D-M7-02-5), so no object backup exists. An exemption would need the rule to know the configuration, which Prometheus cannot read; an operator who backs the bucket up outside Bothy silences the alert for that kind in Alertmanager. |
| AUD-IO1/3 | 2026-11-12 | New alert `BothyBackupTelemetryMissing` (`page`): `absent_over_time(target_info{job="bothy/bothy-backupd"}[10m])` for 5 minutes, the window and `for` of `BothyServerTelemetryMissing`. `BothyVolumeFull` gets no branch for a missing value, and Alertmanager gets no inhibit rule. | `bothy-backupd` sends every value the backup, WAL archive, restore test and volume alerts read, and it is the repository host PostgreSQL archives its WAL to, so its silence is a `page`. The volumes it measures depend on the configuration (`files` only with the driver `fs`), so a rule that names each volume would fire for a volume an installation does not have; the telemetry alert covers the case of the findings, a stopped process or export. |
| AUD-IO1/4 | 2026-11-12 | The default command of `bothy-backupd` reads the last successful runs again before every tick until that succeeded once (`schedule` in `services/server/cmd/bothy-backupd`), and never after that. | It read them once, at its start, next to the creation of the stanza and without waiting for the database. After a restart of the host the containers start without an order, and at the first start of a stack `bothy migrate` may not have created `backup_runs` yet; the gauges then stayed empty until the next successful run of each kind, up to a week for the restore test. The alert of a kind that had been failing ended with such a restart and came back only after the window of ruling 1. Reading on every tick was not chosen: the table holds the start of a run and the gauge of a run of this process its end, so every read would move the gauge back, and the window of ruling 1 already covers a run by hand. |
| AUD-IO1/5 | 2026-11-12 | Not built in this package. (a) Rules on a failed backup run and on a failed check of the restore test, with the sentence of `docs/operations/backup-restore.md` section 4 that promises them (third part of `fn-operations-backup-2`): they are the finding `srv-stats-status-3` of the work package of the module `status`, which adds the failure counters such rules read. (b) A view of `backup_runs` in the admin console and on the status page (second part of `srv-instance-ops-2`): the status page leaves backups out on purpose (16 section 12), and the missing console view is the fact of the findings `docs-accuracy-6`, `fn-operations-backup-3` and `srv-stats-status-4`. | One cause gets one fix: two packages that add a rule under the same name fail the check `alert-thresholds` ("defined twice") once both have landed. Reading the age of the backups from `backup_runs` in the server needs a new API operation with its authorization action and a console view, a feature of its own and not a change of the alert rules. |

## Open minors

- While `BothyBackupTelemetryMissing` fires, `BothyWalArchiveStale` follows five minutes later and
  `BothyBackupStale` after 26 hours for the same cause. An inhibit rule like the one of
  `BothyServerTelemetryMissing` in `alertmanager.yaml` could keep them quiet.
- The check `alert-thresholds` reads only the number after `>`; that the window of each
  `absent_over_time` equals it is held by the rule tests alone, for the two long windows in
  steps of 15 minutes.
- `bothy-backupd` does not learn of a run by hand before its next start. After such a run ends a
  stale state, `BothyBackupStale` resolves for the minutes the value of the short process is
  visible and then fires again until the next scheduled run of the kind succeeds (unchanged by
  this package).
- `BothyVolumeFull` stays quiet for a volume whose sample fails while `bothy-backupd` runs (its
  log holds `backup sample of a volume failed`).
