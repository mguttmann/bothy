# CU-05 MCP server bothy-computer-mcp

Rulings of the ticket that builds the MCP server of computer use (building block C1 of
[27-computer-use.md](../spec/27-computer-use.md), brief
[CU-05](../briefs/CU-05-computer-mcp-server.md)). Owner ruling OR-1 of 2026-11-26 applies
(D-CU-01-1).

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-CU-05-1 | 2026-11-26 | No MCP library: JSON-RPC over stdio by hand in `services/host/internal/computermcp` (`mcp.go`), Go without cgo. The server speaks the protocol revision `2026-07-28` of the Model Context Protocol (no handshake, `server/discover`, the version in `_meta` of every request, `resultType` in every result, unsupported versions `-32022`) and the earlier revisions with `initialize` (`2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`; another requested version gets `2025-11-25`). A request with neither a version in `_meta` nor an earlier `initialize` is refused with `-32602`. Specification read at https://modelcontextprotocol.io/specification (retrieved 2026-11-26). The pinned CLI of the runner contains both eras (its binary names `2026-07-28` as the latest version and still `initialize`); which one it sends is not probed without a login. | The host module has no MCP dependency, and the protocol surface needed (three methods and two notifications per era) is small; a library would add a license and supply-chain review for little code. Speaking both eras keeps the server working whichever revision the pinned CLI picks. |
| D-CU-05-2 | 2026-11-26 | A fifth variable `BOTHY_COMPUTER_SERVER` in the per-turn MCP file: the value of `runner.server_url`, the origin that `attach_path` is relative to (https, http only for `127.0.0.1`, no path). C1 accepts only an `attach_path` that is an absolute path on that origin. Chapter 27 10.1 and the brief of CU-06 name it now. | 27 10.1 gave C1 the request folder, the nonce, the timeout and the pin file but no way to reach the server; `attach_path` is a path (openapi `ComputerSessionGrant`). The origin is no credential; checking the path keeps an answer from sending the attach token to another host. |
| D-CU-05-3 | 2026-11-26 | The timeout reaches the process as `BOTHY_COMPUTER_TIMEOUT_MS` (27 10.1) and bounds the wait for an answer file and every step of the attach (dial, `hello`, `identify`, message 2, the first `cu_state`) and the wait after `done`; the wait for the result of an action has no bound of its own, because an action may take up to `computer.wait_max` plus `computer.settle`, and the host or the end of the run ends a stuck session. | One named value for every wait of C1 instead of new keys; the action wait is bounded by the host's settings and by the session's end. |
| D-CU-05-4 | 2026-11-26 | Tool parameters are the arguments of 27 6.4 (`keys`, `direction`, `amount`, `duration_ms`, `modifiers`), plus an optional `scale_id` for every action with `coordinate` or `region`; without it C1 sends the `scale_id` of the last image of the session, and before any image it answers `invalid_action`. Anthropic's computer tool set of 2026-08-01 names some of them differently (`text` for keys and modifiers, `scroll_direction`, `scroll_amount`, `duration` in seconds); 27 7 binds the tools to the arguments of 6.4, so those names are not taken. | The host contract (6.4, D-CU-03-2) fixes the argument names; a second spelling would make two schemas for one action. The default `scale_id` lets the model click on what it just saw without copying a number. |
| D-CU-05-5 | 2026-11-26 | Pin file `{"v": 1, "hosts": {<host ID>: {"noise_public_key", "key_generation", "pin_changed"}}}`, mode `0600`, written through a temporary file in the same folder and a rename, its folder created with `0700` when missing. A replaced pin keeps `pin_changed` until an open request of the host carried it and the answer's key matched. An unreadable or malformed pin file refuses the open with `host_key_mismatch`. | 27 10.4 says "the next open request", and the next open may run in another turn, that is another C1 process; the mark must survive in the file. Re-pinning after a damaged file would turn a broken pin into trust on first use. |
| D-CU-05-6 | 2026-11-26 | The request client looks for the answer file at a short fixed interval (the constant `answerPoll` of the binary, not a configuration key) and deletes the request file before the answer file. | The poll interval only sets how soon an answer is seen, within the named timeout. A request file left without its answer for a moment would be answered a second time by the runner. |
| D-CU-05-7 | 2026-11-26 | Code mapping: a refusal of the runner as 27 12.4, with `request_refused` (wrong nonce or malformed request) as `not_owner_run` and every other refusal as `host_offline`; a close of the attach connection before the session started by its reason (`not_enabled`, `helper_absent`, `helper_untrusted` as `not_enabled`; `busy` as `busy`; the SR13 reasons as `not_owner_run`; `4102` as `host_offline`; every other as `stopped`); after an end other than `done` every action answers `stopped` with the reason; after `done` `no_session`. A second `open_session` while a session is live answers `busy` without asking the runner. | The codes of 27 7 are a closed list; each mapping names what the agent can do next (open again, ask the owner, give up). |
| D-CU-05-8 | 2026-11-26 | The end-to-end test of C1 against the real host side (`internal/computer` with the control client and the data connection) and the Linux test backend in Xvfb is `services/host/test/computermcp` (build tag `computere2e`), run by `make -C services/host computer-mcp-e2e` in a throwaway Debian container; the server side is a stand-in (the fake server of the session tests, an attach relay and a request-folder runner). It is not a job of the pull request CI in this ticket. | The Compose end-to-end test with the real server and runner is CU-T24 of CU-06; this test proves the protocol of C1 against the real host code now. |
| D-CU-05-9 | 2026-11-26 | `bothy-computer-mcp_<v>_<os>_<arch>[.exe]` ships as five release binaries of the host release (`tools/distribution/hostdist.py`, the signing step of `release.yml`, the release trial); the `.deb`, `.rpm`, `.pkg` and MSI packages do not carry it. | The binary runs next to the Claude Code runner, which may sit on another machine than any desktop; `runner.computer_mcp_bin` names an absolute path the operator chooses. Packaging it into the host service's installers would put it on every desktop that never runs a runner. |
| D-CU-05-10 | 2026-11-26 | `bothy-computer-mcp` reads the optional `BOTHY_COMPUTER_CA_FILE` of D-CU-06-12 into `Config.RootCAs` (system roots plus the file) and dials the attach connection with it; the other five variables stay required. | The attach connection needs the private CA of the server the runner already trusts. |
