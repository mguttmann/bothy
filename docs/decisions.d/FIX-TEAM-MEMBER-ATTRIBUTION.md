# FIX-TEAM-MEMBER-ATTRIBUTION Team copies name the one member they came from

Owner report of 2026-11-22: in a team channel the same agent can be a member several times with
different home channels (in the live channel three members are the one Claude Code runner agent).
The runner labelled a member's input "Input from team member @a / @b / @c", because it mapped the
author agent to every member that agent is; the Hermes adapter fell back to the agent's own handle
when the agent was more than one member; the app labelled the mirror "from @a, @b, @c". In the
work thread of one of them it then read as if that member had written the input itself. Wanted:
the mirror and a handed-on input name exactly the member whose work thread the reply came from,
never derived from the agent, and a reply never goes back to the member that wrote it.
Specification: [09-agents.md](../spec/09-agents.md) 3.9.2, 3.9.4, 3.9.9, 17.14 and 18.5,
[03-data-model.md](../spec/03-data-model.md) `messages.team_handle`,
[01-product.md](../spec/01-product.md) 6.23 item 3.

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-TMA-1 | 2026-11-22 | The server stores the source member's handle on every team copy whose source is a member, in the new nullable column `messages.team_handle`: the mirror of a member's reply in the team channel and a member's input in another member's work thread. `messaging.CopyCmd.TeamHandle` carries it; runs sets it from the member of the reply's work thread (`mirrorReply`: `member`, `teamDeliver`: `src.member`). An owner's copy and every other message have none. The API `Message` gets the optional read-only `team_handle`, in REST and in every event that carries a message. | Only the server knows the member at copy time (the work thread decides it, 3.9.4); a field of the message reaches the runner (`getMessage`), the adapter (`getMessage`) and the app (sync events and history) through the paths they already read, so all three name the same member. A smaller design was weighed and rejected: the run's facts (`team.source_handle`) name the source only for the input that started a run, not for a follow-up, and the app reads no facts at all; a lookup through `team_mirrors` and `team_inputs` at read time would make messaging read tables of runs. |
| D-TMA-2 | 2026-11-22 | The runner names the member by `team.source_handle` in the team part of a run's first message and by the message's `team_handle` in the lead-in of a later input; the Hermes adapter names a follow-up's member by its `team_handle` (the trigger already used `source_handle`); the app's mirror label is "from @handle" with that one handle. Each falls back to the earlier behaviour (every member the author's agent is, or the agent's handle) only when the server sent no handle. For a mirror with `team_handle` this replaces "an agent that is a member twice names both handles" of D-TEAM-APP-5. | Exact attribution where the server has it; the fallback keeps a runner or adapter working against a server before this change, and a mirror the app stored before it. |
| D-TMA-3 | 2026-11-22 | Migration 00110 adds the column without a default and fills it in the same migration for the copies written before it: a mirror through `team_mirrors.member_id`, a member's input through `team_inputs.source_member_id` (with `source = member`), each joined to `team_members` while that member exists. This deviates from upgrade.md rule M7 (backfills as background jobs). | The rows are only the team copies, reached through the primary keys of the two team tables of 00106 on the same release line (team channels went live on 2026-11-21), so each UPDATE is one short statement; a background job would add code for a backfill of a day's copies. A copy whose member was removed since keeps NULL and the readers fall back (D-TMA-2). |
| D-TMA-4 | 2026-11-22 | The client database gets schema version 17 with the nullable column `messages.team_handle`; no row moves and the cursor stays. | A message the client stored before keeps no handle until the server sends that message again (the backfill of D-TMA-3 raises no version and emits no event); its label falls back to every member of the agent, which is exactly the earlier label, so nothing gets worse. A resync for a label was judged out of proportion. |
| D-TMA-5 | 2026-11-22 | A reply is never handed back to the member that wrote it: the hand-on skips the source member by its member id, which the work thread of the reply decides. Two members of one agent are two members; a reply of one that mentions the other reaches the other, and its mention of its own handle reaches nobody. | This was already the server's behaviour (`handOn` compares member ids, never agent ids); the brief asked for proof, which `TestTeam_SameAgentMembersAreNamedByTheirOwnHandle` (app and integration) gives. |

Not covered: the app still shows the agent's display name as the author of a mirror; the member's
handle is the "from @handle" line under it (01 6.23 item 3), as before this change.
