# FIX-macos-keychain The macOS app without keychain entitlements

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-KC/1 | 2026-10-27 | A macOS process without the keychain entitlements (an app with an ad-hoc signature, no team and no provisioning profile, as the local build of the README) keeps its device keys and its app secrets in the login keychain instead of the Data Protection keychain. Each store decides once per process with one write to the Data Protection keychain: `errSecMissingEntitlement` (-34018) means the login keychain, any other answer keeps the Data Protection keychain, so a signed build behaves as before. In the login keychain the items have no access group (the shared group of the extensions needs a team), the device key items carry their accessibility in their own attributes (format 2 of `kSecAttrGeneric`, because the login keychain keeps no accessibility class), and the keys report `hardwareBound = false`, as software keys do, so the server records the downgrade. The app logs the downgrade of the secrets once. `KeychainKeyStore` (device keys) and `FlutterSecureBackend` (secrets) apply the same rule, each at its own store boundary. | Reproduced on a Mac with `swift test` (a process without entitlements): every write to the Data Protection keychain returns -34018 and every read returns `errSecItemNotFound`, so the device keys failed with `not_available` and `InstanceServices.open` failed. Because reads only find nothing, the choice must come before the first read; a per-call fallback would create a new key at every start. |
| FIX-KC/2 | 2026-10-27 | In the login keychain a Mac without a Secure Enclave has no step-up key: the login keychain refuses an item with user presence (-34018), so `ensure` fails with `not_available`. With a Secure Enclave the confirmation sits on the enclave key and the step-up key works. | 08 6.1 requires a confirmation per signature that code in the process cannot give; an item without user presence would not keep that promise. |
| FIX-KC/3 | 2026-10-27 | A failure of `InstanceServices.open` (after discovery found the instance, or on a start from the stored instance) no longer shows "No instance at this address": a `DeviceKeyException` or a keychain `PlatformException` of `flutter_secure_storage` (code `Unexpected security result code`) shows `keychainUnavailable` ("this device's keychain refused the app's keys"), anything else, also a failure of the file protection, `openFailed` ("could not open its local data"); neither text claims that the instance answered; the exception and its stack go to the developer log (`onboarding`). | The person saw a wrong cause and could not act on it; discovery had answered 200. |
