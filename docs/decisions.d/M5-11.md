| D-M5-11-1 | 2026-10-26 | Compose overlay and fake providers (Design note 1): `infra/compose/test/compose.e2e-mobile.yaml` runs `api` and `worker` on the E2E server build (target `e2e-server` of `services/server/Dockerfile`, the production base and layout without the console) and adds the service `fakepush` (target `fakepush`): Fake-APNs of M3-20 on `https://fakepush:8443` over HTTP/2 and Fake-FCM of M3-21 on `https://fakepush:8444`, both only on the Compose network. At start it writes into a named volume (owner 65532, keys mode 0600, so the secret file driver of the server accepts them) a generated APNs key, an FCM service account whose token URI is the fake's and a per-run CA of its TLS leaf, which the server trusts through `SSL_CERT_FILE`; it verifies the JWT and the assertion like the providers, answers every valid send 200 and captures it. Only the E2E build reads `E2E_PUSH_APNS_URL` and `E2E_PUSH_FCM_URL` (both required, so it never reaches Apple or Google with test keys) and sets the test-only endpoints of `wire.Deps` (`APNsEndpoints`, the new `FCMEndpoints`); the release build has no such code and no configuration key redirects push (a test lists the files of `cmd/bothy` with and without the tag and finds the variables in no other file; another holds the Dockerfile's production stage last and the tag only in the E2E stage). This is the exception to D-M3-24-1 ("no environment variable reaches the overrides"): it exists only in the tagged test build. The overlay sets `notify.default_preview_mode` `full`, a short `notify.coalesce_window`, `notify.mobile_delay_when_desktop_active` 0 (an active desktop session of Alex would delay the mobile push) and `egress.allowed_hosts` entries for the two fake ports; the capture API (plain HTTP, `/healthz`, `/captured?after=<seq>`) is the only extra published port, on `127.0.0.1`. | Brief Design note 1; 13 5.1, 5.2; SEC-NET-2. |
| D-M5-11-2 | 2026-10-26 | Push handover (Design note 2): the runner's relay polls the capture API and hands each capture to the device as the provider would: on iOS `xcrun simctl push` with the captured body, on Android an explicit broadcast through `adb shell am broadcast` to `E2ePushReceiver` with the captured `data` as base64 of its JSON object; the suites never run adb or simctl. Android without Firebase has no push token, so the Gradle property `e2ePush=true` gives the debug build a push backend that is available without Firebase and returns a random token per install, and the receiver, declared only in that build, exported and protected by `android.permission.DUMP` (held only by the shell and the system), hands the data to the same `PushReceiver` as the FCM service. Its context comes from a non-exported content provider of the same build; the stand-in `PushMessagingService` of the build without Firebase moved to `src/nofirebase/service`, so the debug test build keeps it. Release and profile builds are unchanged (a Gradle check on every assemble refuses the E2E classes and manifest entries; release APKs with and without the properties are identical). On the iOS simulator the system drops a simulated push for an app without a push registration, and an unsigned build has no `aps-environment`; `CLIENTKIT_SIMULATOR_GROUPS=PUSH` (generated by `tool/branding_defines.dart` next to `YES` of M5-06) gives the simulator build the groups of M5-06 plus `aps-environment` `development` (`SimulatorPush.entitlements`), so the app registers for remote notifications like a signed build. `xcrun simctl push` hands the notification to the system without running the Notification Service Extension (Xcode 27), so on iOS the suite checks the notification with the payload's own text and the tap to the thread; the fetch of the text by the extension is proven by the ClientKit tests of M5-04 and on Android by the suite, not on the iOS simulator. The relay skips an APNs badge sync without an alert, which the simulator refuses. | Brief Design note 2; D-M5-05-5. |
| D-M5-11-3 | 2026-10-26 | Suites and server preconditions: the default thread level is `mentions`, so the push suite creates a forum post and sets Alex's level of it to `all` through the API before Sam writes; the app goes to the background first (only then does the phone close the gateway and the server push), and Sam writes again when no notification came within a presence flush, a pace, not a bound. Login uses the address, password and TOTP of Alex (a TOTP step after the one the world used), the device waits, and a second session of Alex confirms it through the API. Each suite runs in its own process; the first one redeems the enrollment code of the world, later ones sign the same known device in with password and TOTP. Offline cuts the app's connections to the server inside the process (the CONNECT tunnel of M4-34 for the server's host and port only), so patrol's own connection keeps working: the suite needs no runner signal and cuts the gateway and REST alike. Each Android suite starts from a fresh install, so the permission dialog appears again (API 33 and later). | Brief Design note 2; 13 12; 08 2.5. |
| D-M5-11-4 | 2026-10-26 | Runner and teardown (Design note 3): `tools/e2e/mobile_e2e.py` prints a SKIP line per platform whose tools are missing and fails when none can run; it creates an iOS simulator (newest iOS runtime, its first iPhone type) and starts an emulator from an AVD on a free console port, or uses the ones named by `MOBILE_E2E_UDID` and `MOBILE_E2E_SERIAL` and leaves them as they were; it picks free loopback ports (never a reserved port of the host rules) for the capture endpoint and for patrol's two host servers, whose defaults are reserved; `infra/compose/e2e.sh` builds the overlay's images (new input `E2E_BUILD`) and removes every image tagged with the run ID. The relays and suites log to `MOBILE_E2E_LOG_DIR` without message content or token; after the run, also after a failure, the relays stop, the emulator it started is killed by serial and PID, the simulator it created is shut down and deleted by UDID, and e2e.sh removes the stack. | Brief Design note 3. |
| D-M5-11-5 | 2026-10-26 | CI (Design note 4): `.github/workflows/e2e-mobile.yml` runs the Android suites every night and by hand on `ubuntu-24.04` with KVM, the pinned emulator runner and Docker, read-only, without secrets, guarded like the other scheduled workflows; it is not a check of pull requests. GitHub-hosted macOS runners have no Docker engine, so the iOS suites run on a macOS host with Docker and Xcode before every release and at the close of M5. `e2e-mobile` is part of neither `check` nor `gates`. | Brief Design note 4 and requirement 14; ADR 0039. |
| D-M5-11-6 | 2026-10-26 | Measurement (Design note 5): profile builds run only on physical devices, so `tool/mobile_perf.sh` measures only when one is attached and otherwise prints `SKIP perf-mobile: no physical reference device attached (targets not proven)`; `make perf` calls it. The measurement runs against the in-app fake server on its own isolate, not the Compose stack: a profile build does not trust the stack's test CA, and the fake isolates the client. It uses the release ports of the app (platform device keys and secure storage, the encrypted database), reads the device model and OS inside the app, and measures with frame callbacks, `FrameTiming` and the process start from the kernel like the desktop level (D-M4-34-5), not `traceAction` summaries; memory is `ProcessInfo.currentRss` (the resident set), with five open threads. Reference devices: `iPhone17,3` and `iPhone17,4` (iPhone 16 and 16 Plus, two generations before the current one; the Pro models are left out, their faster chip would flatter the values) and the Pixel 6a (only made with 6 GB RAM). Any other device ends `not_proven` (exit 3), which fails `make perf` (ADR 0063: it does not end green); a missed target on a reference device fails. The phone needs a screen lock for its step-up key (D-M5-01-3). | Brief Design note 5; 15 19; ADR 0063. |
| D-M5-11-7 | 2026-10-26 | Reaching the stack (Design note 6): the TLS front and the per-run test CA of M4-34 (`e2e-tls`) serve `https://localhost:<port>`; the iOS simulator trusts the CA through `xcrun simctl keychain add-root-cert`, the Android emulator reaches the port through `adb reverse` and trusts the CA through the Gradle property `e2eCa`, which generates a network security configuration with the CA under `debug-overrides` into the debug build only. No second sidecar or CA generator was added. | Brief Design note 6; SEC-TLS-1. |
