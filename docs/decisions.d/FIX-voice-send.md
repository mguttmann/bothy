# FIX-voice-send Voice messages from every platform

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-VS/1 | 2026-10-31 | Cause of the live report (a voice message refused with "Some inputs are invalid"): the recording came from the Windows app, whose recorder writes the MP4 brand `mp42` (compatible `mp41`, `isom`). The pinned type detection names an MP4 by its major brand only, so the scan pass stored `video/mp4` although the app declared `audio/mp4`, and the voice check answered `400 validation_failed` with `voice_format_unsupported`. Fix: the scan pass stores `files/domain.RefineMP4Type(detected, declared)`, which is `audio/mp4` when the detected type is `video/mp4` and the declared type is `audio/mp4` or `audio/x-m4a`, else the detected type (12 6.1). Place: `files/app/scan.go`, `files/domain/voice.go`. | 12 8.1 allows AAC-LC in MP4 from the apps; the refusal came from the detector's naming, not from the bytes. The declaration only picks between the two MP4 names: it never turns another type into audio, `DeferContainerComplete` then holds the file `pending` until its duration is read (D-M3-09-6), and the container phase still reads width and height, so a declared-audio file with a video track fails rule 4 as before. |
| FIX-VS/2 | 2026-10-31 | `file.denied_mime_types` is checked against the detected and the stored type, so declaring audio cannot pass a deny entry for `video/mp4`. | The refinement must not open a way around an operator's deny list. |
| FIX-VS/3 | 2026-10-31 | The client outbox classifies `409 file_not_ready` as `retry` (same `client_msg_id`, at least `Retry-After` plus the full-jitter backoff); `409 file_blocked` stays final. The fake server of `sync_engine` answers a voice message whose file is not ready with `409 file_not_ready` and `Retry-After`, or `409 file_blocked`, as the server does. Place: `packages/sync_engine/lib/src/outbox/classify.dart`, `world_files.dart`. | The message is released when `completeUpload` answers `200` (15 7.5), while the server accepts a voice message only after scan and container phase (12 8.1 rules 1 and 4); the outbox treated the `409` as final, so every voice message sent in that window failed, on every platform. The fake accepted it, which hid the gap. `createMessage` is idempotent by `client_msg_id` and stores nothing on a refusal (06 7), so the retry is safe. Waiting for `file.updated` instead of the backoff would need a second wake-up path into the outbox; the backoff is bounded by `client.outbox_retry_cap`. |
| FIX-VS/4 | 2026-10-31 | `audio/x-m4a` (the detected name of brand `M4A `, the recordings of macOS and iOS) is in the inline list of downloads (12 9.3) and is audio for the client's player, like `audio/mp4`. | The voice check accepts both names (D-M3-09-3), but downloads served `audio/x-m4a` as `application/octet-stream` and the app showed no voice player for it. Widening the readers covers the files already stored with that name without a backfill (upgrade rule M7). |
| FIX-VS/5 | 2026-10-31 | Same class for images and files (multi-photo M5-16, paste as file M4-47): no change. A text message with attachments whose check has not ended is stored at once (12 10 rule 1); only the agent invocation waits (R-FI-09). `TestAttachments_PendingFilesAreAttachable` holds it. | Only `kind = voice` checks readiness and type at send. |
| FIX-VS/6 | 2026-10-31 | No backfill of files stored before the fix: a generic-brand MP4 declared as audio keeps `video/mp4` in `files.mime_type`. The voice checks (attach of a voice message, transcription) read the stored type refined by the declared one (`RefineMP4Type`), so such a row passes as MP4 audio and "Send again" of the refused message works. | Upgrade rule M7 forbids a data backfill in a migration, and a background job for a handful of recordings costs more than refining on read. A legacy row with a video track has a width or height and still fails rule 4. "Send again" also works for every voice message refused while its file was checked, because `409 file_not_ready` no longer fails the entry and the payload keeps the file IDs. |
| FIX-VS/7 | 2026-10-31 | Not verified: the brand Android's `MediaMuxer` writes (probably a generic one, covered by FIX-VS/1 either way) and Linux (ffmpeg to a `.m4a` path, probably `M4A `). | No device of these platforms was checked; both paths end in one of the two stored names. |
