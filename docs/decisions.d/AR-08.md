| No | Date | Ruling | Reason |
|---|---|---|---|
| D-AR-08-1 | 2026-11-07 | The API gives clients no capability `wakes` of an agent (`AgentRuntimeStatus` has no `capabilities`), so every wake-up view is driven by the server's records: the pending list, Cancel, "Woke up" and the usage-limit notices show only for wake-ups that exist, which the server creates only for a runner that reported `wakes`; a pending wake-up of a runner that turned `runner.wakes` off stays with its Cancel, and the end state shows for every run that carries one. | 01 6.21 names no wake-up control that exists without a wake-up record, so the record is the exact signal; a client-side capability flag would need a server change outside this ticket and could only hide what 6.21 keeps visible. |
| D-AR-08-2 | 2026-11-07 | A message with origin `system` and a kind other than `system` or `run` is a note of the thread: one line with an info icon, no author, avatar, reactions or menu. The client translates the lines of `domain.WakeNoteText` and `domain.AutonomyNoteText` (AR-04, D-AR-04-6) by reading them back into kind, label and reason (`decodeWakeNote`); a line it does not know shows as the server wrote it, still as a note. | Only the server writes origin `system` (SEC-OUT-3), so no person or agent can make a message look like a note; the note carries no system code with parameters (D-AR-04-6), and `run.wake_changed` names the note only live, not after a reload. |
| D-AR-08-3 | 2026-11-07 | The collapsed line of an ended run loads its document (`getRun`) when it is built, not only when it is expanded, and reads `metrics.end_state` and `metrics.wake_pending_until` from it; expanding loads again when the first load found nothing. | 03 `runs.metrics` holds the end state, and `RunSummary` (the source of the collapsed line) has no metrics; the list builds lines lazily, so the loads follow what is on screen. |
| D-AR-08-4 | 2026-11-07 | `RunMetrics` of `docs/api/openapi.yaml` gets the members `end_state` and `wake_pending_until` of 03 `runs.metrics` (09 18.19.11); the clients of `make api-clients` and the server's generated code are regenerated. The server's patch rules are unchanged. | The fake checks every response against the contract and the Dart client drops a member it does not know, so the end state could not reach the line otherwise; the members are optional, so the change is additive (06 13). |
| D-AR-08-5 | 2026-11-07 | Layout of the pending list: a strip between the history and the composer, titled "Continues on its own", one row per pending wake-up in the order they fire: the name (the label isolated as agent content, or "Wake-up"), below it the condition, the earliest fire and the deadline (the time alone for today, else day and time), and "Cancel" at the end of the row; a usage-limit wake-up reads "Usage limit of the account reached; continues at <time>". Nothing shows without a pending wake-up. | 01 6.21 item 1 places the list above the composer; one row per wake-up keeps Cancel next to what it cancels, also in the narrow phone window. |
| D-AR-08-6 | 2026-11-07 | Cancel is offered to the wake-up's person and to a person with `manage` on the channel (07 2.14 item 5, the server's `run.wake.cancel`); the agent's owner gets it through `manage`, which owners hold. | 01 6.21 item 1 also names the agent's owner; the brief binds the offer to 07 2.14 item 5, which the server checks, so the button never invites a refused cancel. |
| D-AR-08-7 | 2026-11-07 | The answer to a nudge (09 18.19.11, design note backlog item 15) is not grouped with the run's answer: it is an agent reply like a follow-up answer and stands as its own message, joined only by the ordinary grouping of consecutive messages of one author. | The message carries no mark that tells a nudge answer from another reply, so a client grouping would guess; the ordinary grouping already shows both under one header. |
| D-AR-08-8 | 2026-11-07 | "Ended waiting, but nothing will wake this thread" is drawn under the line of an ended run whose end state is `waiting` without `wake_pending_until`; the usage-limit notice under the line of a run that ended `failed` with `usage_limited`: "continues at" its pending usage-limit wake-up, "Reply after <time> to continue" when that wake-up was refused or expired, "Reply after the reset to continue" without one. | 09 18.19.11 and 18.19.10 name the notes but no message for them; an agent's message would look like the agent speaking, while the run's end state and the wake-up records carry exactly the facts the notes state. |
| D-AR-08-9 | 2026-11-07 | The channel switch lives in the channel menu (sidebar on desktop and phone, the header of a text channel's main history) as "Let agents continue on their own...", which opens a dialog with the switch and the sentence of 01 6.21 item 5; it is offered with `manage` when the channel carries `allow_autonomous_runs` (a server of stage AR) and is neither a DM nor archived. | The apps have no channel settings screen; the menu already holds the channel actions of `manage`, and the server refuses a DM (`dm_channel`) and an archived channel. |
| D-AR-08-10 | 2026-11-07 | The local table `run_wakes` (schema version 14) lives in `packages/local_store` with the other mirror tables and mirrors every column of 03 `run_wakes`; `channels.allow_autonomous_runs` is nullable (null: an older server), and the migration clears the cursor so the next snapshot fills it. The sync engine applies `run.wake_changed` (the state at once, then `listThreadWakes` after the commit) and loads a thread's wake-ups when its view opens. | The brief names `packages/sync_engine` for the table, but the drift database of the apps is `local_store` (D-W-100: follow the code); the payload of the event carries no label or condition (D-AR-04-5). |
