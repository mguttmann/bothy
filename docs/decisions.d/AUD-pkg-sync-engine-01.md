# AUD-pkg-sync-engine-01 Fake server held to the real server, failed commits, read deadlines

Five findings of the audit of 2026-11-11 against `packages/sync_engine` (`sync-fake-server-1`,
`fn-sync-offline-2`, `sync-engine-store-1`, `sync-engine-store-2` and `sync-engine-store-3`).
One is a class of faults: the fake server of the client tests copies rules of the server by
hand, and nothing compared the two, so a difference showed only in a live app (the rulings
FIX-DCB/3, FIX-SU/5, FIX-SSS/3, FIX-VS/3 and FAOC/3 each name it as the reason why no client
test failed). Two name one cause in the sync engine: a page that could not be applied left the
sync standing still on an open connection. One is about REST reads without a deadline, one
about follow-up reads that are lost when the process ends. Normative text: 04 sections 7.3, 9
and 14, 15 sections 7.2, 7.3 and 22, the package README.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-SE1/1 | 2026-11-12 | The behaviour of the fake is held to the real server by scenario files, one per rule, in `packages/sync_engine/test/fixtures/conformance/`. A file names the requests of the rule (person, method, path, body), the members of each answer to record, the event types of the rule and the members of their envelopes; under `expect` it holds what the real server answered: status, the problem code with its field errors, the picked members and the events of those types the step appended, in order. Two tests read each file. `TestFakeConformance` (`services/server/test/fakeconformance`) sends the requests to the server of the tree through `test/harness` (the real wire graph on PostgreSQL, real HTTP with DPoP), reads the events from `event_log` as the envelopes the gateway delivers (`sync.Event.Envelope`), and fails when the file differs; `-update-conformance` rewrites the recorded part. `test/fake_server/conformance_test.dart` sends the same requests to the fake and compares with the same file. Both build the same small world (Alex and Sam with `write` on one text channel and a thread of it); IDs are written as placeholders. Not chosen: one suite that runs against the Compose stack and the fake, and a golden file per event like `file_updated_after_scan.json`. | Both tests run where the code they guard is tested: the server test in the server shards, the fake's test with the package, each in the required check, and neither needs the other's tool chain. A change of the server fails the server test until the file is recorded again, and the new file fails the fake's test until the fake follows; a change of the fake alone fails its test at once. A suite against the Compose stack would run in the desktop E2E track, which needs a desktop session and the Compose stack and is no required check, so nothing would hold it green. The scan golden holds the shape of one event for the client's decoder; it says nothing about what the fake answers. |
| AUD-SE1/2 | 2026-11-12 | The first two scenarios are `read_state_advance` (`putReadState`: forward only, inside the messages of the thread, an event only for a change; 04 14, R-SY-13) and `thread_draft_put` (`putThreadDraft`: an empty draft deletes the stored one with `draft.deleted`; 04 14). The fake failed both and is changed to pass them: `FakeWorld.putReadState` checks the range (`400 validation_failed`, `/last_read_seq`, `out_of_range`), keeps the greater position and answers the current state without event and version for no change (position and version `0` without a row); `FakeWorld.putDraft` deletes an empty draft like `putChannelDraft` already did. `markThreadUnread` keeps its own write (`FakeWorld.setReadState`), unchanged. Every other rule of the fake stays a hand-written copy until it has a scenario; the README says so. | A mechanism that had found nothing would prove nothing: these two rules are among those the audit read as different (`sync-fake-server-5` and `sync-fake-server-6`), both are personal state every client writes, and R-SY-13 is a core rule. The remaining differences the audit lists (the move of a thread, `Idempotency-Key`, `createThread` without a transaction, the gateway's `resume`) belong to the work packages that hold those findings; each fix there starts with its scenario. Rules of the gateway need frames, which the scenario form does not have (see "Open"). |
| AUD-SE1/3 | 2026-11-12 | A commit that fails ends the session instead of halting the listener on an open connection: the listener applies nothing more of that session and calls the new `SessionControl.reconnect`, which closes the socket from the client side and connects again after the wait the listener names. The waits follow `sync.reconnect_backoff_base` and `sync.reconnect_backoff_cap` with full jitter, counted over failed commits and started again by a commit that works; the connection's own backoff is not used, because it starts again with every `ready`. This holds for a page, for the snapshot of `ready` (mapping or storing) and for the snapshot of a resync that cannot be stored. Rows and cursor stay as they were, as before. Replaces the second half of the first sentence of D-M4-14-8 ("applies nothing until the next `ready` or `resumed`") and its reason "`SessionControl` has no close". | After a failed page the phase stayed `live` or `catchingUp`, heartbeats and the outbox went on, and nothing started the session D-M4-14-8 waited for, so a desktop app received nothing until the socket broke for another reason. A failing `ready` left the phase at `catchingUp` for good, with the frames of the catch-up collecting in memory. With the reconnect the app shows `Backoff`, and a failure that passes (a busy database) heals with the next session. Without a wait that grows, a failure that stays (a full disk) would reconnect about once per base interval for good. |
| AUD-SE1/4 | 2026-11-12 | A page that fails again at the same stored cursor is passed by a snapshot: the listener replaces the mirror as after `resync_required` (`getSnapshot`, cursor to its `head_seq`, frames held meanwhile, drafts and outbox kept), on the connection that delivered the page, and reports `Resynced` with the reason `page_failed` (`Resynced.pageFailed`). The count is per cursor: a commit that works clears it. A catch-up that ends inside such a resync does not set the session live; the snapshot does. Not chosen: skipping the event, and dropping the cursor so that the next `ready` replaces the mirror. | An event that breaks its mapping fails on every session at the same place, so the reconnect alone would repeat it for good, now visibly. The snapshot is the state after the event, so it passes it without the cursor moving over something that was never applied (the reason of D-M4-14-8 against skipping). When the event is newer than the snapshot, the next two failures at the new cursor lead to the next snapshot, which then holds it. Dropping the cursor needs a method the local store no longer has (AUD-LS1/8) and a further connection; the resync path exists and keeps the connection. |
| AUD-SE1/5 | 2026-11-12 | What the app sees of a failed commit is the connection phase (`Backoff`, or `Resyncing` for the snapshot) and the `Resynced` notice; no new notice and no new counter are added. The engine logs one line per failure through `logHook`. | The phase is what the app's connection banner reads, and the app's metrics already count reconnects by close code (`client.reconnects`) and resyncs (`client.resync`). The app passes no `logHook` to `SyncEngine.create`; wiring it belongs to the app (see "Open"). |
| AUD-SE1/6 | 2026-11-12 | Every REST read of `ApiFetcher` has the deadline `client.sync.read_timeout` (new key of place `App`, default `30s`, 15 22). `ApiFetcher` takes it as `readTimeout` and passes it with each generated operation as the request option `requestTimeoutExtra` of `packages/auth`, now exported, which the DPoP interceptor of the session's client sets as the connect, send and receive timeout of that request (FIX-DPL/2 built this for the refresh). A read that passes it fails like a network error and is retried by the read retry like one. Not changed: the writes of the outbox, the read of a run document (`getRun`) and the reads the app makes itself. | The session's client has no timeouts, so a read whose answer never came waited for good: the one chain of background reads stood behind it, and so did everything queued after it. The value bounds the time without data, not the size of an answer. Writes are not covered because the app registers its own executors over the built-in ones and uploads use the same path, whose send time is legitimately long (FIX-DPL/2); a write that waits shows "Sending delayed" after `client.outbox_stuck_after`, a read showed nothing. |
| AUD-SE1/7 | 2026-11-12 | The first snapshot attempt of a resync runs outside the frame queue of the connection, like its retries (D-M4-14-9, D-M4-14-14): `resync_required` sets the phase, marks the resync and returns; the frames that arrive meanwhile wait as before. The background reads stay one chain. | The first `getSnapshot` was awaited inside the frame queue, so while it had no answer the close of the socket and `dispose` waited behind it and the phase stayed `resyncing` on a dead socket. The attempt already checks its session after every await, because the retries always ran outside the queue. Reads per target instead of one chain would change the order in which follow-up reads store their results; with a deadline on every read the chain can no longer stand for good, so the order is not touched. |
| AUD-SE1/8 | 2026-11-12 | `sync-engine-store-3` (follow-up reads after the cursor commit are neither durable nor repeated across sessions) is not built in this ticket. | The reads are retried while the process runs (the read retry of the REST client, with its backoff), rows without access, gaps and unknown threads are loaded again later, and the audit reproduced no loss. What is left is the process that ends between the commit of a page and the end of its reads, and a read that fails for longer than its retries. Closing that needs the pending reads stored in the same transaction as the page: a new table in `packages/local_store` with a schema step, a typed description for each place that queues a read today (they are closures in the appliers, the snapshot applier and the listener), their replay at every `ready` and `resumed`, and rules for a read that can never succeed. That is a design of its own across two packages, larger than the rest of this ticket together, and the local store just had a schema step in another work package (AUD-LS1/3). |

Evidence:

- AUD-SE1/1 and AUD-SE1/2: `packages/sync_engine/test/fake_server/conformance_test.dart` over
  the two scenario files, whose `expect` parts `TestFakeConformance` recorded from the real
  server and holds. Against the fake before its change the Dart test failed for both files:
  in `read_state_advance` an older, an equal and a zero position each moved the position and
  wrote an event with a new version, and a position after the last message was stored; in
  `thread_draft_put` an empty draft was stored with `draft.updated` and listed.
- AUD-SE1/3 to AUD-SE1/5: `packages/sync_engine/test/catch_up/page_failure_test.dart`
  (reconnect and repeat from the cursor, the snapshot after the second failure at the same
  cursor, no early `live`, a failure at another cursor, the snapshot of `ready`, the growing
  waits, a resync snapshot that cannot be stored).
- AUD-SE1/6: `packages/sync_engine/test/scenarios/read_deadline_test.dart` runs the engine over
  the real auth session and HTTP against the fake server, which holds one answer back: the read
  ends after the deadline. `test/catch_up/read_deadline_test.dart` holds that every read of
  `ApiFetcher` carries the value and that the engine passes the configured one.
- AUD-SE1/7: `test/catch_up/read_deadline_test.dart` (the close of the socket is handled while
  the snapshot read has no answer).

## Open

Collected, not built in this ticket:

- `sync-engine-store-3`: durable follow-up reads (AUD-SE1/8).
- The app passes no `logHook` to `SyncEngine.create` (`apps/client/lib/app/bootstrap.dart`), so
  the lines of the engine, the one of a failed commit included, reach no log of the app. The
  app's own parts write such lines to the developer log, which a release build does not keep;
  what leaves the device about a failed commit today are the two metrics of AUD-SE1/5, when
  the app sends its metrics. Which log the engine's lines go to is a decision of the app.
- The writes of the outbox and `getRun` have no deadline (AUD-SE1/6). A deadline for writes
  needs a rule that leaves uploads out.
- Scenarios cover REST requests and their durable events. A rule of the gateway (for example
  what `resume` of a session that is still bound does) needs frames in the scenario form and a
  gateway client in both tests.
- The fake's `markThreadUnread` is not held by a scenario. Read in the code, not run: it writes
  an event also for an equal position and accepts a position above the current one, where the
  server's `MarkUnread` answers an equal one without an event and refuses a greater one.
- While a resync retries its snapshot, the held frames have no bound (the audit lists it as
  `sync-engine-store-12`).
