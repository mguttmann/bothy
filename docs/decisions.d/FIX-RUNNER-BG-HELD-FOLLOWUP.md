# FIX-RUNNER-BG-HELD-FOLLOWUP Background sessions: a value of the host user's crossSessionInbound

Reproduction condition: the host user's own `~/.claude/settings.json` holds
`"crossSessionInbound": "hold"`, and the settings file of a run sets no value (FIX-RUNNER-BG-INBOX-AUTH
ruling 2). Result with Claude Code 2.1.325: every follow-up the runner wrote into a running
background turn was held ("Held peer message ... not delivered to Claude (n held). Your
"crossSessionInbound" setting is "hold"", the CLI's cause `explicit-setting`), no echo came, the
follow-up stayed `delivered`, and the server deferred it into a run of its own and offered it to
each later run of the thread as a follow-up again, so the same message was answered in several
runs. No background session took a line of the runner. Print mode has no inbox socket and is not
affected.

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-FIX-RUNNER-BG-HELD-FOLLOWUP-1 | 2026-11-17 | The settings file of a run sets `crossSessionInbound` `accept` when the host user's own `settings.json` in the turn's configuration folder (`CLAUDE_CONFIG_DIR`, else `$HOME/.claude`) gives that setting a value that is not `null`, also an unknown one; otherwise it sets none, as before. The runner reads the file at every launch. This replaces, for a host whose settings have a value, the sentence of D-FIX-RUNNER-BG-INBOX-AUTH-2 that the settings file sets no value, and the part of D-FIX-RUNNER-BG-INBOX-AUTH-8 that a follow-up then waits for a run of its own. Evidence: level one `test_the_token_of_a_session_s_own_child_is_no_narrower_way_in` with 2.1.326 and 2.1.325 (the runner's line in its envelope is held under the user's `hold` without the run's value and taken with its `uuid` with it; red with the code before this change), the scenarios `test_a_hold_in_the_host_user_s_settings_does_not_keep_the_runner_s_follow_up` (`host` and `scoped`: the follow-up is `absorbed`), the unit tests of `settings_document`. | A value of the user's settings switches the CLI's rule per message off for every session, so there is nothing narrower left to keep: `hold` and `refuse` keep the runner out entirely, an unknown value holds every message, and `accept` takes every message anyway. A value of `--settings` goes before one of the user's settings, and only `accept` lets the runner's lines through. Changing the host user's settings is not the runner's to do (they are the operator's, shared by every session of that user), and an operator rule in the README alone does not hold: the value is often set before a host enables background mode. What the run's `accept` widens: a runner session on such a host takes every message of every sender; the runner logs each one it did not write (FIX-RUNNER-BG-FOREIGN-LOG), and the model acts on it with the rights of its tool class. A value of managed settings still goes first and is not overridden. |
| D-FIX-RUNNER-BG-HELD-FOLLOWUP-2 | 2026-11-17 | Narrows ruling 1: the settings file of a run sets `crossSessionInbound` `accept` only when the host user's own value is `hold`. Any other value (`refuse`, `accept`, one the CLI does not know) stays in force and the file sets none; with `refuse` the runner's follow-ups are refused too and each waits for a run of its own (D-FIX-RUNNER-BG-INBOX-AUTH-8). Evidence: the unit tests `test_a_hold_of_the_host_user_s_settings_is_replaced_by_accept` and `test_any_other_value_of_the_host_user_s_settings_stays_in_force`, the scenario `test_a_refuse_in_the_host_user_s_settings_is_never_overridden` (the CLI refuses the runner's line, the follow-up is never `absorbed`), each red with the code of ruling 1. | The security review of ruling 1: a `refuse` is the operator's deliberate choice to take nothing from other sessions, and overriding it widens what every runner session takes beyond what the operator set. `hold` was the reproduced cause of the repeated answers; an unknown value has no reproduced harm, and lifting it would guess the operator's intent. Stopping a turn on a foreign input stays rejected (D-FIX-RUNNER-BG-FOREIGN-LOG-1). |

Deploy note: none beyond the runner's restart. The next launch of each background turn reads
the host user's settings; a turn that runs at the restart keeps the settings file it was
launched with until it ends.
