# AUD-client-onboarding-01 Start from the local data, unreadable local data and the end of an account

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-CO1/1 | 2026-11-11 | A cold start with the stored session of an active device opens the local data of the remembered instance and shows the main view before the network is asked (`_startFromLocalData` of the onboarding controller), exactly as the start without network of D-M4-18-13 does. What `getDiscovery` and `getDevice` answer afterwards is applied by `_catchUpStart` with the one routing rule `routeStart`: a certificate error, `setup_required` and a too old app close the services and show E1 with their text, another instance at the address and a device the server still holds for confirmation go the way of "Connect" (E2 or E4), a found instance replaces the remembered description, and without a usable answer the main view stays. Until the app has read what is stored it shows the start screen (`OnboardingState.starting`, `StartScreen`: the card with the mark alone, which a screen reader announces with the name of the build, no field, no button, no animation) instead of E1. A waiting device keeps the order of "Connect" (discovery, then `getDevice`, then E4), and so does every "Connect" from E1. This refines D-M4-18-13 and D-M4-18-15: the end screen of every stored state and network answer is the one `routeStart` names, only the main view no longer waits for the answer. | Audit finding client-shell-5: the start waited for `getDiscovery` and then for `getDevice`, both without a limit of their own, on E1 ("Connecting", locked) and then on E2 with active buttons. With answers that never arrive (a VPN or tailnet that is off) a signed-in person saw their cached data only after the connect timeout of the system and the refresh limit, although 01 3.6 and D-M4-18-15 give them the local data whatever the network answers. `test/onboarding/cold_start_test.dart` starts the app against a listener that accepts every connection and never answers. |
| AUD-CO1/2 | 2026-11-11 | A build that an instance refused as too old is remembered outside the instance (`app/refused_min_version`, written by "Connect", by the catch-up of the start and when the connect gate refuses while the app runs; deleted when discovery finds an instance again). While it is set, the start asks the instance first, as before this ticket. The first start after an instance raised its minimum behaves like a raise while the app runs: the main view shows until the answer arrives, then the services close without deleting anything and E1 shows "App too old". | Brief M7-13 requirement 13 and 18 9 item 2: a build below the minimum opens no gateway connection and sends no authenticated request. Without the entry a refused build would open its local data at every start and close them a moment later. The gateway is closed to it either way, because the connect gate asks before every attempt. |
| AUD-CO1/3 | 2026-11-11 | No timeout is added to the discovery client or to the REST client of an instance. | The start no longer waits for either, so the limit the finding asked for has nothing left to bound there. A limit for every REST request was ruled out by FIX-DPL/2 (uploads and long reads are legitimately long). "Connect" on E1 for a person without a session still ends with the connect timeout of the system; that is outside the finding (the start of a signed-in person) and stays as it is. |
| AUD-CO1/4 | 2026-11-11 | A local database that the stored key does not open (`LocalStoreKeyError`) is no dead end any more. Without a stored session `InstanceServices.open` deletes the folder of the instance and creates the database anew, so E1 leads on to the login. With a stored session nothing is deleted: E1 shows the new result `ServerStatus.localDataUnreadable` with the action "Reset local data" (`resetLocalData`), which deletes the folder of the instance (database files and file cache), keeps the session, the device keys and the secrets and connects again, so the engine loads everything anew. "Connect" stays the main action and tries again without deleting. | Audit finding client-shell-2: the services, and with them the database, open before the login; when the secret store lost its entries (the Windows secrets file deleted after a DPAPI error, another keychain, a moved device) the key source creates a new key, the stored file fails with `LocalStoreKeyError` and every "Try again" failed the same way, before the person could even log in. Without a session nothing in the folder belongs to an account, so deleting it loses nothing. With a session the file holds what no server has (the outbox, the drafts, the view states of the device, the pinned host keys of the terminal), and the error also covers a file the device cannot read at that moment (the iOS file protection of a locked device, 15 6.3), so the app never deletes it by itself; the person decides, and the text names what is lost. A database written by a newer app is not part of this: it opens (drift runs no step for it), so it is no dead end on E1. |
| AUD-CO1/5 | 2026-11-11 | A wipe step that fails is logged (`developer.log`, name `onboarding`), and the app remembers the instance and the scope of its device keys as `app/unfinished_wipe` (`UnfinishedWipe`, outside the instance's secrets, the instance ID only as a UUID as in D-M4-18-20). E7 then says "Not all data of this device could be deleted. The app deletes the rest the next time it starts." instead of the deletion sentence. The rest (folder, device keys, push and share items, secrets) is deleted by `InstanceServices.leftoverWiper` at the next start, before anything else, and before the services of an instance are composed again ("Log in again", "Connect"); a failure there is logged and the entry stays. The entry goes when the rest is gone, or when a session begins on that instance again, because what was left is then in use and a later start must not delete a live session. | Audit finding client-shell-1: the controller swallowed the error of `AccountWiper.wipe`, E7 always said "The data of this device has been deleted", and nothing tried again, so R-SY-14 was neither met nor visible when a step failed (the file cache lies unencrypted in the instance folder). No failing step is known in the field (D-M4-40-11 is fixed), so this is the honest text and one more attempt per start, not a guarantee: a step that keeps failing is logged at every start. |
| AUD-CO1/6 | 2026-11-11 | The server part of a logout (`unregisterPush`, then `logout`) has the limit `AppPorts.serverLogoutLimit` (`defaultServerLogoutLimit`; tests shorten it). At the limit the controller cuts the connections of the session's REST client (`Dio.close(force: true)`), waits for the two calls to end, which they then do at once, and runs the wipe. The limit is not a timeout around the future alone: the logout of `packages/auth` clears the stored refresh token when its call ends, and a call that ended after the wipe could clear the session of a login that followed it. No screen "logging out" is added, and the order of every end of an account stays: the services close and the data go first, then E7 shows. | Audit finding client-shell-4: with a valid token the logout call had no limit of its own, so with answers that never arrive "Log out" did nothing visible and kept the data on the device until the connect timeout of the system. The second half of the finding (services closing under the main view) has no reproduced defect (D-M4-40-11 is fixed) and showing E7 before the wipe would change the order that every sign-out path and the device tests rely on; with the limit the wait is short, so the intermediate screen is not built. |
