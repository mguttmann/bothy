# V1-14 Own sign-in methods in the apps and the console

Design note: [sign-in-methods.md](../design/sign-in-methods.md). Owner decision of 2026-11-25 on
issues #1426 and #677.

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-V1-14-1 | 2026-11-26 | One view `MySignInView` in `admin_ui` serves the settings of the apps and the console page; the hosts pass a `PasskeyCreator` and an `IdentityLinker` or null. | The same states, errors and tests on every client, as the own devices and sessions (`MyDevicesView`). |
| D-V1-14-2 | 2026-11-26 | The QR code of the one-time code comes from the Dart package `qr` (BSD-3-Clause, pure Dart, no platform code); the view paints its modules with the text color of the light theme on its canvas in every theme. | A QR encoder of our own is more code to hold than a small licensed dependency; authenticator apps read dark on light best. |
| D-V1-14-3 | 2026-11-26 | The Windows app gets a passkey port over the Win32 WebAuthn API (`webauthn.dll`) behind the runner's method channel `bothy/webauthn`; Dart writes the client data with the origin of the instance and builds the JSON forms the server parses; the runner only fills the Win32 structs and runs each ceremony on a worker thread. The Mac app keeps no passkey port (D-M4-18-9). | Windows Hello is the step-up the owner chose for the Windows terminal (#677); a Mac has the step-up key and needs no passkey for the terminal. |
| D-V1-14-4 | 2026-11-26 | On a device without a step-up key with a passkey port, a step-up first creates one challenge to learn whether `passkey_options` are there; with them it asks the prompt, creates the challenge the passkey signs and completes with `completeStepUpWithPasskey`; without them an ordinary step-up falls back to password and TOTP, and the fresh step-up of the terminal ends with `StepUpUnavailable`. A cancelled Windows Hello prompt cancels the step-up, with no fallback to the password. | Only the challenge tells whether the person has a passkey; the signed challenge is created after the prompt because it lives only `auth.step_up_challenge_ttl`, as on the key path. The probe costs one challenge and its audit entry on such a step-up. |
| D-V1-14-5 | 2026-11-26 | The console page "Sign-in" is an administration page (it needs the console's first step-up), at the end of the navigation; `consoleStepUpNoMethod` sends a person without a step-up method to Settings, Sign-in of an app. | Before its first step-up a console session may only read its own profile (08 7.5); an app session sets up the first factor without a step-up when it has nothing to confirm with. |
| D-V1-14-6 | 2026-11-26 | A console session links an identity back to `/console/sign-in/callback`; the server takes exactly that redirect for a console session, as for the console login, without an entry in the provider's `app_redirect_uris`. The verifier and the name of the login service wait in the tab's `sessionStorage`. | The console has no other way back from the login service; the provider knows only the server's callback. |
| D-V1-14-7 | 2026-11-26 | E3 is not changed: the API has no operation that sets a password while a code is redeemed (D-M4-18-9); 01 5.6 now says the password comes afterwards under Settings, Sign-in. | The owner decision allowed either; changing the contract for E3 was not needed once the settings set the password. |
| D-V1-14-8 | 2026-11-26 | Not in this ticket: revoking an own passkey and unlinking an identity from the view, passkeys on macOS, a console E2E test that registers a passkey through the page, handlers for the four operations in the fake server of `sync_engine`. | None of them is needed for the dead ends of #1426 and #677; the view tests use their own fakes. |
