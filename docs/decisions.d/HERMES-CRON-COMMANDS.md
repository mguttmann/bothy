# HERMES-CRON-COMMANDS Hermes commands and cron reports in the Hermes adapter

M2-33 left two rows of spec 09 section 17 unbuilt: the Hermes commands (17.3) and the reports of
Hermes cron jobs (17.9, on section 14). This ticket builds both on the pinned Hermes Agent
`v0.22.5` and proves them with the fake runtime and against the pinned Hermes (Fake-Hermes tests).

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-HERMES-CRON-COMMANDS-1 | 2026-10-29 | The adapter declares its commands at every connect (`AdapterConfig.commands`, reconciled by the SDK, D-M2-29-12). Hermes' commands that the server has as built-in commands (`/stop`, `/new`, `/resume`, `/title`, `/status`, 09 10.1) are never registered: the server's built-ins and the adapter's stop and session paths already carry them out. A closed table (`hermes_commands.COMMAND_CLASSES`) names every gateway command of the pinned version (`COMMAND_REGISTRY` entries that are not CLI-only or have a config gate) with its class and reason; `test_command_table_covers_pinned_commands` holds it equal to the pinned version. Commands of other Hermes plugins are never offered. Place: `hermes_commands.py`, `platform.py` (`connect`), `tests/fake_hermes/test_installer_and_contract.py`. | Every Hermes command goes out from the adapter's control sender, a slash-command admin (17.4); offering a command therefore grants what the admin may do. Fail closed like the toolset table: a command a later Hermes version brings stays refused until the table names it. |
| D-HERMES-CRON-COMMANDS-2 | 2026-10-29 | Only `/context` and `/version` are control commands (instance-wide, no options). Every other command is refused with one of these reasons: it calls the model outside a run (`/retry`, `/compress`, `/plan`, ...), changes the thread's session outside the server's session record (`/branch`, `/sessions`), bypasses the server's follow-up, approval or card rules (`/queue`, `/steer`, `/busy`, `/approve`, `/yolo`), reaches the host (`/save`, `/diff`, `/debug`, `/profile`), acts on the whole profile (`/model`, `/pause`, `/restart`, `/sethome`, `/usage`, ...), lists commands this platform does not offer (`/help`, `/commands`) or belongs to another platform (`/start`, `/topic`). | A control command never reaches the model (09 10.1, 10.4) and must not let a person with `trigger` change the profile, the host or the billing of everyone else. The two kept commands only read the thread's Hermes session or Hermes itself. |
| D-HERMES-CRON-COMMANDS-3 | 2026-10-29 | A control command is the bare `/<name>` (never an option value) via `handle_message` from the control sender in the thread's session. Hermes answers it through its normal processing when the session is idle and inline when it is busy, both times with `reply_to` = the command's message; the platform collects these sends (and their edits) instead of posting them, waits for the end of the processing only when Hermes admitted the event, and the handler posts each non-empty text as a message of the agent without a run (`createMessage` without `run_id`, unbound). Place: `platform.py` (`run_command`, `send`, `edit_message`), `handler.py` (`on_command`). | 09 10.4 makes the answer of a control command a message of the agent and keeps every run unchanged; the inline reply during a turn never ends with `on_processing_complete`, so waiting for it would hang (measured in the Fake-Hermes test). |
| D-HERMES-CRON-COMMANDS-4 | 2026-10-29 | Each skill command Hermes offers for the platform (`get_skill_commands` without `get_disabled_skill_names(platform=<key>)`) is a model command with one optional `string` option `input`; names that are no valid command name, built-in names, table rows and control names are left out, the list is capped at `command.max_per_principal`. A command run (`trigger_kind = command`) is a turn whose text is `build_skill_invocation_message("/<skill>", input)`, the run context stays the system part, the turn's event ID is the run ID and the answer has no reply anchor; a command run that is no skill now fails before the start (`adapter_error`). Place: `hermes_commands.py`, `handler.py` (`prepare`), `platform.py` (`skill_commands`, `skill_text`), `typings/agent/skill_commands.pyi`, `typings/agent/skill_utils.pyi`. | 17.3 asks for skill commands as model commands. Building the text with Hermes' own function keeps the person's text out of Hermes' command parser (the turn stays `allow_gateway_control` off) and matches what Hermes' gateway sends for `/<skill>`; a command run has no triggering message to answer. |
| D-HERMES-CRON-COMMANDS-5 | 2026-10-29 | `send` decides by its context: a running control command's reply; a send whose `reply_to` names a turn's message this process handed to Hermes is that turn's run's answer only while that run is active, else it fails, and one naming an ended adapter command's message fails (Hermes sends the final answer after it cleared its session variable); a send that belongs to a turn of its thread (inside a turn only the turn's own thread, outside any turn only a thread whose run is active, and only in the channel of that thread's turns) is the run's answer as before, and a late send of an ended run fails; every other send is a report without a run. Place: `platform.py` (`send`, `_turn_send`, `_turn_messages`, `_control_messages`). | Hermes delivers cron jobs of its scheduler, background notices and sends into other channels through the live adapter's `send`; before, every such send failed with "no active run", and the old fallback (the only turn of a channel) could have attached a cron report to an unrelated run. A late answer of a cancelled turn must still never be posted. |
| D-HERMES-CRON-COMMANDS-6 | 2026-10-29 | Reports: the plugin registers `cron_deliver_env_var` (`<KEY>_HOME_CHANNEL`), `parse_target_ref_fn` (`<channel ID>` or `<channel ID>:<thread ID>`) and `standalone_sender_fn`. Without a fixed thread a forum gets a new post per report (`createThread` with the report's first line as title and the report as first message, a fresh `Idempotency-Key`), a text channel its main thread; other channel kinds are refused. The installer's `--report-channel` (and `--report-thread`) set Hermes' home channel; without it the placeholder `unassigned` stays and every report to it is refused. Place: `reports.py`, `entry.py`, `installer.py`, `__main__.py`. | 09 14 and 17.9; a support job opens one post per ticket in a forum. Hermes resolves `<key>:<id>` only through the plugin's parser; `deliver=<key>` needs the home channel variable or the configured home channel. |
| D-HERMES-CRON-COMMANDS-7 | 2026-10-29 | Command replies and reports are one direct `createMessage` (or `createThread`) each, unbound, not an outbox entry; the client repeats the same `client_msg_id` or `Idempotency-Key` on a transient failure. A refusal comes back to Hermes at once as a failure with the problem code; a transport failure after the client's retries as "not reachable". The standalone sender builds its client from `PlatformConfig.extra` with the `User-Agent` adapter name `hermes-adapter-standalone`, refuses attachments and sends nothing then. Place: `reports.py`, `handler.py` (`_post_own`). | The outbox keeps a `403` pending and sends it again at every reconnect, so a refused report would neither fail for Hermes nor ever stop; Hermes reports a failed delivery itself. The adapter name tells the server's logs which lane posted. |
| D-HERMES-CRON-COMMANDS-8 | 2026-10-29 | The SDK's FakeServer answers `getChannel` (a `ChannelView`: Allgemein is a text channel with a main thread, a channel of `add_forum` is a forum) and `createThread` (a forum post by Lotse with its first message, `ThreadCreated`), lists commands for every served channel, and `trigger(command=..., options=...)` and `invoke_command(..., options=...)` carry a command's name and option values. Place: `sdk/python/src/bothy_sdk/testing/`. | The adapter's tests need the channel kind, the new forum post and model command runs; the fake follows the shapes of the API (`ChannelView`, `ThreadCreated`, `AgentInvocationPayload`). |
