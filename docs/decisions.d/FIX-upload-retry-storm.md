# FIX-upload-retry-storm Uploads under the rate limit

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-URS/1 | 2026-10-30 | Cause: one message with four attachments from the phone hung for minutes against `rl.upload` (30 per minute, burst 10). Every outbox retry of an upload restarted at `createUpload`, whose idempotent replays count against the bucket like new requests; `getUpload` was retried by the read retry of `api_client` inside the attempt (up to nine attempts with the outbox values) and by the outbox around it; the outbox and the read retry waited exactly `Retry-After`, which the server computes as the seconds until one token is back, so every upload lane woke together and used up the bucket again; and every upload had its own lane, so all files ran at once. | Reproduced against the fake server with a token bucket over the upload operations (`upload_retry_storm_test.dart`): before the fix the four files took 27 `201` answers of `createUpload` in one run, after it four. |
| FIX-URS/2 | 2026-10-30 | One session per file for its whole life: the executor keeps `upload_session` (`entry`, `file_id`, `mode`) in its entry through the new `ApiCallContext.checkpoint` right after the announcement, and every later attempt of that entry resumes the kept session with one `getUpload` instead of announcing again. A session announced in the same attempt (no `Idempotent-Replay`) skips the status read. The kept session counts only for the entry ID it names, so "Upload again", which copies the payload into a new entry, starts a new session. A presigned session that resumes reads its part URLs from the replay of the same key, as before. | The `Idempotency-Key` alone gives the same session only while the server keeps the key; the kept `file_id` does not depend on that and saves one request of the bucket per retry. A session after a final failure (`410 gone`, `part_conflict`) cannot be resumed, so a fresh entry must not inherit it. |
| FIX-URS/3 | 2026-10-30 | The checkpoint writes into the stored payload under the outbox lock and does nothing for an entry that left the outbox or is final; a null value removes a member. It is the only way an executor changes its own entry. | A discarded or echo-confirmed entry must not come back through a late write. |
| FIX-URS/4 | 2026-10-30 | One retry layer: `api_client` gets the request option `noReadRetryExtra`, and the upload executor passes it to `getUpload` and `getFile`; a refused read ends the attempt and the outbox retries the entry. | The outbox already retries the whole entry; a second layer inside it multiplied the reads (60 refused reads against 37 announcements in the live log). |
| FIX-URS/5 | 2026-10-30 | `Retry-After` is a floor for every outbox entry and every read retry: the wait is `Retry-After` plus the full-jitter backoff of the attempt (`retryWait`; `client.outbox_retry_base`, `client.outbox_retry_cap`), the backoff alone without the header. The jitter bound doubles with the attempts, so a lane that keeps hitting the limit backs off further. | 06 9 item 3 asks clients to wait at least `Retry-After`; waiting exactly that long synchronised the lanes. A wait longer than the header is always allowed. |
| FIX-URS/6 | 2026-10-30 | The uploads of a channel share one lane `upload:<channel id>` (was `upload:<entry id>`), so the files of a message upload one at a time in the order they were attached, each with its two parts in flight; uploads of other channels run in parallel. The lane stays separate from the thread's lane, so an upload never holds the other writes of the thread (D-M4-22-1 otherwise unchanged). | The upload entry does not know its message, and the files of one conversation are the ones that compete for the same person's bucket; a lane per message would need a new payload member for no gain. The lane is computed from the payload on each schedule, so entries stored before the update take the new lane at once. |
| FIX-URS/7 | 2026-10-30 | No status polling: the executor reads `getUpload` once per attempt that resumes a session and never in a loop; after `completeUpload` the states follow `file.updated`. | The live log showed no polling loop; the reads came from the retry layers of FIX-URS/4. |
| FIX-URS/8 | 2026-10-30 | A visible state: an upload entry in `waiting` or `delayed` (a refused attempt, waiting for the next) shows the new state `retrying` ("Paused, trying again shortly"); `pending` stays "Waiting to upload". A retry keeps the confirmed bytes of the last attempt in the progress until the server's state is read. | The live report showed "Uploading 0 %" for minutes: the inner read retry held the entry in `sending`, and a waiting entry looked like one that had not started. |
| FIX-URS/9 | 2026-10-30 | Server defaults of `rl.upload`: `per_minute` 300 and `burst` 60 (were 30 and 10). The burst holds the requests of two batches of `message.max_attachments` files of one part (announce, part, complete); `TestUploadBurstHoldsTwoAttachmentBatches` holds the relation to the defaults. The status read uses `rl.upload` too (12 13) and needs no other class; `getFile` uses `rl.read`. | Brief M5-16 assumed about three requests per file; ten files are 30 requests, three times the old burst. Larger files take seconds per part, so a refill of five tokens per second is far above what one person's parts can use. An instance that set its own values keeps them. |
| FIX-URS/10 | 2026-10-30 | The fake server of `sync_engine` gets a token bucket over a set of operations (`FaultPlan.rateLimit`), answering `429 rate_limited` with `Retry-After` in whole seconds, at least 1, as the server does, and it now sends `Idempotent-Replay: true` on a replay of an `Idempotency-Key`, as the server does (06 7). | The client tests need the same limit and replay signal as the server; the fake must not drift from it. |
| FIX-URS/11 | 2026-10-30 | Out of scope: the share extension of iOS (`ClientKit`) already hands a `429` to the app's outbox through `share_inbox` instead of retrying, and the SDKs upload agent replies outside the app. | They do not retry uploads in a loop. |
