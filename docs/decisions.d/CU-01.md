# CU-01 Specification of computer use

Owner request and ruling of 2026-11-26 (OR-1): an agent operates a desktop of the owner fully,
started from any Bothy client. Design note: [computer-use.md](../design/computer-use.md). Decision:
[ADR 0078](../adr/0078-agent-computer-use-on-a-paired-desktop.md). Normative:
[27-computer-use.md](../spec/27-computer-use.md), 07 2.15 and SR13, 03 `computer_sessions` and the
computer columns of `hosts`, threat model 5.18 and 6.10; plan: [PLAN](../PLAN.md) section 23.

OR-1 in the owner's words (translated from German; the original is in the private operations
repository): "What bothers me in the draft is that it has restrictions. It should be able to
control everything. And I also want to be able to tell it, for example from the phone, to do XY on
the Mac or on the Windows computer, without restrictions. It should also be able to operate the
terminal, operate the browser, operate any app and so on. It should also be able to change Mac
settings. So it should really be able to operate the computer completely."

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-CU-01-1 | 2026-11-26 | Full operation for the owner: no app tiers, no view-only browser, no click-only terminal, no blocked app category, no list of blocked keys or key combinations, no confirmation per consequential action; system settings and the Bothy windows are not locked. What stays is protection that removes no capability: owner only, a visible indicator while the agent controls, stop from every client and with Esc at the machine, pause while the screen is locked, one controller per host, the session bound to its run, audit without screen content, no screenshot on the server. | OR-1. A lock on the Bothy windows would only keep the agent from stopping itself, which is the safe direction. |
| D-CU-01-2 | 2026-11-26 | Architecture "tool first": a `stdio` MCP server next to the runner terminates Noise to the host; the server relays ciphertext only; a separate signed helper per platform in the owner's desktop session executes; the session is bound to exactly one run (design note E1). | Only this keeps "the server reads nothing" (R-TM-02, SEC-TERM-1) and reaches Windows without a new host mode. |
| D-CU-01-3 | 2026-11-26 | Bothy ships its own MCP server `bothy-computer` with the tool names and parameters of Anthropic's computer tool set, not Claude Code's built-in computer use. | The built-in tool acts on the runner's own machine and needs an interactive session (design note E2). |
| D-CU-01-4 | 2026-11-26 | The owner's own message in the thread is the consent for a session; there is no card, no lease and no confirmation at the target per session. A desktop is reachable only after a one-time local enablement on that machine by the owner (operating system permissions and the switch "Allow computer control" of the helper), which any client can switch off and only the machine can switch on again. | OR-1 asks for a start from the phone without a confirmation at the target; the local enablement keeps every remote start on a machine the owner prepared in person. |
| D-CU-01-5 | 2026-11-26 | A session opens only in a run of an active owner that the owner's own message started (`trigger_kind` `message` or `command`, the trigger an `origin = 'human'` message of that owner); wake runs, team runs and runs of other persons never open one (SR13). | A prompt injection in another run (another trigger, an automatic input, another agent) reaches no desktop. |
| D-CU-01-6 | 2026-11-26 | One helper process per platform ("Bothy Computer Helper"), in the owner's desktop session: Swift on macOS (Developer ID, hardened runtime, no sandbox, LaunchAgent in the GUI domain), C++ with Win32 on Windows (Authenticode, `uiAccess`, installed under `Program Files`, started at login); a Linux backend with Xlib and XTest in Python exists only as a test fixture. | `bothy-host` runs as a service user outside the desktop session (R-TM-12) and is built without cgo (`services/host/Makefile`), so it can neither capture nor inject there; the desktop app is sandboxed (`Release.entitlements`). The design note's claim that `bothy-host` is unsigned is wrong: `release.yml` signs and notarizes it (`build-apple`) and signs its MSI (`build-windows`). |
| D-CU-01-7 | 2026-11-26 | Foreground only in the first stage: the agent moves the real pointer; input by a person at the machine does not hold actions back; a stop ends the session for good; a screen lock pauses it and an unlock resumes it. | A background mode without the pointer is unverified (CU-11); holding back on activity would be a restriction without protective value, because Esc always works. |
| D-CU-01-8 | 2026-11-26 | Limits only as named configuration values (27 section 18); no limit on actions, action rate or session duration; a session lives at most as long as its run. | `.coderabbit.yaml` and the repository rule on fixed numbers; a budget per session would cut capabilities (OR-1); costs run through the run's cost control. |
| D-CU-01-9 | 2026-11-26 | No external penetration test of its own for stage CU; the red team over the stage and the attack tests on T-CU-01 to T-CU-08 are mandatory before the stage merges. OQ-11 (the test before the publication) is unchanged. | The owner asked for none for this feature; the design note's reference to a ruling of 2026-11-06 is not recorded in the repository, so this row is the record. |
| D-CU-01-10 | 2026-11-26 | F13: the agent never unlocks a locked machine, and Bothy stores no login password. While a session is open the helper keeps the display awake; a lock pauses the session and the agent reports it in the thread. | Unlocking would need a system service and a stored login password, a new and large attack surface. |
| D-CU-01-11 | 2026-11-26 | F3: no screenshot in the thread in this stage; the thread shows a status line from metadata only. | A screenshot in the thread would lie on the server and on every device of the owner. |
| D-CU-01-12 | 2026-11-26 | F14: no system service on Windows in this stage; a UAC prompt on the secure desktop and the secure attention sequence stay out of reach, the helper reports them as `secure_desktop` and the agent asks the owner in the thread to answer them. A service as SYSTEM, if ever, is CU-13 with its own ADR. | A SYSTEM service on the secure desktop is a large new attack surface. |
| D-CU-01-13 | 2026-11-26 | The normative text is a new chapter [27-computer-use.md](../spec/27-computer-use.md), not a section of 24 as the design note proposed; 24 gets cross references only. | Computer sessions have their own rules, frames, tools, tests and keys; a chapter of their own keeps the rule IDs `R-CU-nn` and test IDs `CU-Tnn` apart from the terminal's, as 26 did for stage A1. |
| D-CU-01-14 | 2026-11-26 | Catalogue rows, operations, host control ops, events and problem reasons enter their machine-read places (`actions.yaml`, `openapi.yaml`, `asyncapi.yaml`, `services/server/api/operations.yaml`) with the CU ticket that builds them, CU-04; chapter 27 section 12 and 07 2.15 fix them until then. | The pattern of D-AR-01-8 and R-AZ-37: the server generates its route table and action catalogue from these files and `make codegen-check` holds the generated copies; the enable list accepts an operation without a handler only as `later` for a V2 or V3 feature (`TestEnableListComplete`), so an entry without its code would fail the gates. |
| D-CU-01-15 | 2026-11-26 | The server side lives in the module `terminal` (tables `computer_sessions` and the computer columns of `hosts`), not in a new module `computer`. | Computer sessions use the hosts, the host control connection, the relay, the signing keys and the revocation subscriptions that `terminal` owns; a separate module would need ports into all of them (02, rule "Strictly modular"). |
| D-CU-01-16 | 2026-11-26 | Threats go into a new threat model section 6.10 (T-CU-01 to T-CU-08) with a STRIDE section 5.18; T-TM-09 is reworded for the terminal and points to T-CU-02. | The design note named 6.8, which holds the visualization threats; 6.9 holds those of the built-in agents. |
| D-CU-01-17 | 2026-11-26 | Rule references of the design note corrected at the source: the "no tool without an open run" check is the run binding of SR9 (`invocation_token_invalid` with `reason: run_inactive`), not R-AG-44 (which is about background work of Hermes runs); "`stdio` forces `host`" is R-BA-05 and R-BA-06, not R-BA-07; the host control op of the terminal is `session.open`, and `terminal.open` is the action. | Read in 07 SR9, 09 section 19, 26 section 13 and `services/host/internal/control/frames.go`. |
| D-CU-01-18 | 2026-11-26 | `bothy-computer-mcp` pins the host's Noise key per runner on first use (`<runner.state_dir>/computer/pins.json`) and accepts a different key only with a higher `key_generation` (a re-pairing), recorded with `pin_changed` in the audit of the open; a different key with the same generation refuses the session (`host_key_mismatch`). | Devices pin on first use at their first opening (24 5.5); the design note's "pinned with the fingerprint from `Pair`/`Confirm`" does not exist. A runner has no person to confirm a key change, so only a re-pairing that the server reports may change it. |
| D-CU-01-19 | 2026-11-26 | The runner loads `bothy-computer-mcp` only with `runner.computer_use` and only in `host` turns, through its own per-turn MCP file, not through `runner.mcp_stdio_runners`; the server decides SR13 at `computer.open`. The MCP server reaches the server only through the runner, in the request-folder-and-nonce pattern of `bothy-wake` (09 18.19.8): the runner calls `computer.desktops.list` and `computer.open` with the run's agent token and invocation token, and only the single-use attach token reaches the MCP process. | `runner.mcp_stdio_runners` is the allow list of launcher commands (`npx`, `uvx`) for `stdio` servers of a definition (`config.py`, 26 5.6), not a switch for a runner tool. The pattern keeps the agent's credentials out of the turn. |
| D-CU-01-20 | 2026-11-26 | Screenshots leave the runner host's disk at the end of the run: after a run that opened a computer session, the server ends the thread's agent session with the new `end_reason` `computer_use` in the transaction that ends the run (the next run starts a new Claude Code session with the thread context of 09 4.6), and the runner deletes the old session's transcript and tool result files once its process is gone. The file layout is probed against the pinned CLI in CU-06. | No transcript cleanup exists today: `claude rm` removes the list entry and keeps the transcript (`bgsession.py`). Rewriting a transcript in place would change history the API may check (thinking blocks), which no free test can prove; a new session is deterministic and testable. |
| D-CU-01-21 | 2026-11-26 | Native tests run in `host-platform.yml` on `macos-15` and `windows-2025` after a probe job (CU-02) shows whether hosted runners allow screen capture and input without a dialog; a negative probe leaves that platform with build, signature and doctor tests and an open, documented gap. | Both `host-platform.yml` and `e2e-desktop.yml` run only on a public repository (`if:` of their jobs); the repository is public (checked 2026-11-26). The design note's "without the visibility gate" was wrong. |
| D-CU-01-22 | 2026-11-26 | Superseded by D-CU-01-29 (owner decision, the same day). The helpers are signed in the existing release jobs (`build-apple`: Developer ID, notarization; `build-windows`: the publisher certificate with `signtool verify /pa`) with the same secrets; which certificates an instance uses is OQ-08 and ADR 0037 (each organization signs itself). A build without a signing identity is for development only; the doctor reports it. | The release chain exists; only its inputs are open. |
| D-CU-01-23 | 2026-11-26 | No grant and no capability for computer use: it is owner-only by SR13, and R-TM-04 (target `host` carries only `terminal`) stays unchanged. A later extension to other persons (CU-12) needs its own ADR. | OR-1 applies to the owner only; a capability without a holder other than the owner would be dead weight. |
| D-CU-01-24 | 2026-11-26 | The channel between host service and helper admits a peer only when it is the user of the active console session, its executable is the installed helper whose path and folder chain belong to a trusted owner (the rule of HD10), and, when the build carries a code signing requirement, its signature satisfies it. | `localchan` and the confirmation endpoint check only user and process IDs today (`peer.go`, `confirm/server.go`); the design note's Team ID check does not exist and is built here. |
| D-CU-01-25 | 2026-11-26 | A remote disable is sticky: the helper's enablement carries a generation that grows with every local switch-on; the server stores the generation it disabled, and a desktop counts as enabled only when the host reports it enabled with a higher generation. | A host that misses the disable op must not stay listed; only a new local switch-on lifts it. |
| D-CU-01-26 | 2026-11-26 | Computer use is refused in the owner account mode of ADR 0073: the host service refuses to start with `host_service.computer_use` and `host_service.owner_account` together. | There the host service runs as the console user, which the peer rule must refuse, and its install runs without root, so it cannot create the endpoint folder; supporting it would need a second peer rule for that mode (review of CU-01). |
| D-CU-01-27 | 2026-11-26 | SR13 item 5: a run whose `run_feeders` rows of `source` `trigger`, `followup`, `interaction`, `command` or `wake_input` name anyone other than `triggered_by` (NULL included) never opens or attaches a session; `context` rows do not count; while a run holds a session no follow-up of another principal is delivered into it (it stays `queued`, then `deferred`) and interactions of others with its components are refused. The `command` form of item 2 is a command `triggered_by` invoked in a session (`triggering_command_id`), because a command run has no triggering message. | Follow-ups with `followups = steer` would otherwise let any person who may trigger the agent type orders into the owner's computer run (review of CU-01). |
| D-CU-01-28 | 2026-11-26 | The helper state reaches the server only in the `report` object `computer`; `bothy-host doctor` shows it as a section `computer`, not as a check HD12. | The server accepts exactly HD1 to HD11 in `report` (24 3.5, `control.go`), and every report with another check would be refused (review of CU-01). |
| D-CU-01-29 | 2026-11-26 | Owner decision on signing, replacing D-CU-01-22: the computer helpers are not published and `release.yml` neither builds nor signs them; no signing secret for them goes to GitHub, and the published host packages carry no helper. The macOS helper is signed on the owner's own Mac with the owner's existing Developer ID Application identity, through the same local path that signs the owner's own app builds today: a one-shot job in the owner's logged-in GUI session, where the login keychain is open (nothing unlocks it), started by `make -C services/host helper-sign-macos`. It is not notarized: a file built and installed on the same machine carries no quarantine flag, so Gatekeeper does not assess it. The Windows helper is signed with a self-signed code signing certificate created on the owner's Windows computer and trusted only there (`LocalMachine\Root` and `LocalMachine\TrustedPublisher`, private key not exportable), by `tools/distribution/hostdist.py helper-sign-windows`. The host package with the optional helper component is built on the same machine from the signed helper (`helper-package-macos`, `helper-package-windows`). A helper without a signature that verifies stays a development build (`signature: development`). Amended the same day (coordinator ruling after the first signing run, D-CU-02-22): where the owner's login keychain holds no Developer ID Application identity, the macOS helper is signed with the owner's Apple Development identity of that keychain; its designated requirement names the bundle ID and the team of the leaf certificate. | The helper serves only the owner's own desktops (OR-1); a Developer ID signature keeps the designated requirement, and with it the screen recording and accessibility grants, stable across builds; `uiAccess` needs only a signature that chains to a root the machine trusts. Keeping the keys on the owner's machines removes the release secrets and the publication from the stage. Which certificates another instance uses stays OQ-08 and ADR 0037. |
