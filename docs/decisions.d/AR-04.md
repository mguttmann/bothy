| D-AR-04-1 | 2026-11-07 | Rollback (requirement 19): the runs README says to let pending wake-ups fire or cancel them and to switch `runner.wakes` and `runner.turn_handover` off before a server rollback below AR-04; the down step of 00099 refuses while a run with `trigger_kind = wake` exists and names the count (`TestMigration_WakesDown`). | An older server neither fires nor shows wake-ups and does not know the trigger kind `wake` in its run reads; the expand-only migrations stay for a binary rollback, and a schema rollback must not break the old check. |
| D-AR-04-2 | 2026-11-07 | The job `runs.wake_due` has no interval: it is scheduled per wake-up at `not_before` (kind `at`) and at the deadline, and the end of a run schedules it for the ready wake-ups of its thread (`onThreadFree`). | A periodic job would delay every fire by up to its interval and would need a new key; the scheduled form fires on time and costs nothing while no wake-up exists, like `runs.component_expiry`. |
| D-AR-04-3 | 2026-11-07 | Names that 09 5.8 leaves open: `run.wake.fire` takes `outcome` `fired`, `failed` or `input_skipped` (the report of a skipped wake input, with `run_id`); the reason codes `wake_not_pending`, `wake_not_due` (a check or fire before `not_before`; the wake-up stays pending), `wake_fired_by_server` (a fire of an `at` wake-up), `run_not_active`, `run_not_ended`, `run_not_running`, `deadline_passed`, `cancelled_by_agent`, `cancelled_by_person`, `wake_check_failed`, and the pending marks `condition_met` (a reported condition that waits for another person's run) and `wake_input_skipped`; the paths `/runs/{run_id}/wakes`, `/runs/{run_id}/wakes/recover`, `/runs/{run_id}/launch-check`, `/agents/me/wakes`, `/wakes/{wake_id}/check`, `/wakes/{wake_id}/fire`, `/wakes/{wake_id}/cancel`, `/threads/{thread_id}/wakes` and `/channels/{channel_id}/autonomous-runs`. | 09 5.8.3 says the runner reports the skip but names no operation; one operation per wake-up outcome keeps the runner's calls in one place. The codes make every refusal its own answer (06 R-API-30). |
| D-AR-04-4 | 2026-11-07 | A wake input goes only into a run in state `running` of the same person and agent; a queued or waiting run keeps the wake-up pending, and a wake input whose run no longer runs at its delivery returns its wake-up to pending (`run_not_running`). | A queued run has no process to write into, and a waiting run waits for its person's answer, which a wake-up must not give; returning the wake-up keeps it from being lost between fire and delivery. |
| D-AR-04-5 | 2026-11-07 | The payloads: `run.wake_changed` carries `wake_id`, `thread_id`, `agent_id`, `triggered_by`, `state`, `state_reason` and, for an end other than `fired`, `note_message_id` and `note_thread_seq`; its resource is the thread and its receive action `run.wake.read`, so the readers of the thread and the agent (operator rule) receive it. `agent.wake_input` and the `agent.invocation` of a wake run carry `wake_id` and `wake` (`kind`, `reason`, `label`, `result_text`). The run context of a wake run is that payload; `getRunContext` keeps its message trigger. | 09 5.8.2 names wake-up id, thread and state; the agent filters by `agent_id`, notify needs the person and the note to address `wake_ended` without a read across modules; the brief names label, reason and result for the input, and the first input of a wake run needs the same. |
| D-AR-04-6 | 2026-11-07 | The note of 09 5.8.4 is a message with origin `system`, kind `text`, silent, authored by the agent, whose content names the label and the reason (`messaging.AppendSystemNote`). | 03 `messages.system_code` is a closed list of the core contract without a code that carries parameters; origin `system` never triggers and creates no hint, and the content can name the label as 5.8.4 requires. A code with parameters is a follow-up of the data model. |
| D-AR-04-7 | 2026-11-07 | `run.wake.check` ends a wake-up only for the checks 5.8.3 lists (the autonomy rule, the kind's rule, and `agent.invoke` of the person: trigger, reachability, archived or read-only channel, SR2, dev environment); the denials `billing_mode_personal_not_holder`, `project_not_ready`, `operator_cannot_serve_project` and `run_active_other_agent` are left to the fire, which checks them. | A transient project state must not end a wake-up whose fire would still check it; the host execution needs only the person, agent, channel and tool class checks. |
| D-AR-04-8 | 2026-11-07 | A wake-up acts with the agent counted as addressed: `agent.invoke` runs for the person with `MentionsAgent` true, as for the component of the agent's own card. | The wake-up is the agent's own address to the person; the agent stays allowed in the thread as its operator or as an allowed guest. |
| D-AR-04-9 | 2026-11-07 | The idle flag of `/metrics/autonomy_last` creates the row of `run_autonomy` on demand; a notification turn of a run without an earlier autonomous input counts there too. A skipped wake input keeps its count. | 09 5.8.6 counts notification turns in the idle count; the stored `autonomy_last` is the memory of the last input, so a repeated patch never counts twice; keeping the count is the safe side of the cap. |
