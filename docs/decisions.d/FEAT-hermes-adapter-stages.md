# FEAT-hermes-adapter-stages The stage events of a coding chain show as steps of the Hermes run

Owner order of 2026-11-20: a Hermes profile runs a coding chain per ticket from a run its owner
triggers in Bothy. The chain command appends one JSON line per stage event to `stages.jsonl` in
its run folder (start, further pass and end of each stage and of the chain's own run), and Bothy
must show these events as the steps and the status line of the run the Hermes turn belongs to.
Rule: 09 17.12 point 9.

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-FEAT-HAS-1 | 2026-11-20 | The adapter inside the gateway follows the file; the chain does not talk to the server. A tool call of the run registers the file for its thread with the helper `bothy_hermes_adapter.stages` (`python -m bothy_hermes_adapter stages register --profile-home <home> --thread <thread ID> --file <path> [--ticket <key>]`, also `deregister` and `list`), and the handler reads the thread's sources every `hermes_adapter.background_poll_interval` while a run of the thread is open, during the turn and during the hold of 17.12, and once more right before `run.finish`. Rejected: a separate `stages follow` process that patches the run itself. | Only the adapter holds the run's patch channel (the run's invocation token, the base version, the throttled patcher); a second process would need the run's token and would race the adapter's own patches. The registration follows the external jobs of point 8, so a script keeps one contract and the thread (from `HERMES_SESSION_THREAD_ID`) ties the file to the run of the turn that runs the command. It works with a gateway started per run: nothing runs outside the gateway. |
| D-FEAT-HAS-2 | 2026-11-20 | Reading starts at the file's size at the registration, and each source keeps a cursor (offset, the file's device and inode, a flag for a too long line being skipped, the run and the steps it opened there) in `<source ID>.cursor`, saved after its lines were applied. A partial last line waits for its newline; a file that was replaced or truncated is read from its start; the open steps of the cursor count only for the run that opened them. A later run of the same thread goes on from the cursor, so the lines written while no run was open (for example after a gateway restart) show in that run, and no line shows twice. | The chain appends to one file per ticket across its calls, so lines of an earlier call must not show again. A restart of the gateway ends the run (17.12, "Limits"); going on from the saved offset in the thread's next run is the only way such lines are not lost or repeated. |
| D-FEAT-HAS-3 | 2026-11-20 | Only checked words reach the run: the stage and the state from closed lists (the chain's `STAGES` and `run`; `started`, `pass`, `ended`, no `pass` of `run`), the outcome from the chain's closed lists or `unknown`, a ticket key of the form `<letters/digits/_>-<digits>`, a pass number read from the text by a strict pattern (`_pass_no` in `stages.py`). The shown text is rebuilt from these words, never copied. A line that is no JSON object, longer than `LINE_MAX_BYTES`, of an unknown stage or state, of a bad ticket key or of another ticket than the registration names is skipped and logged as `run <ID>: stage source <ID>: <reason code>`; the log never carries the line or the path. The file is opened without following a link, and records and cursors follow the rules of the job records (D-FIX-HEJ-2). | The file is written by a command of the host; whatever it holds must not leak into the run or the logs (SEC-LOG-2). An unknown event type of a later chain version is ignored, not fatal. |
| D-FEAT-HAS-4 | 2026-11-20 | Mapping: a stage is one step `workflow` named `chain_stage` (title the stage, `<stage> (pass <n>)` for a further pass, `<stage>: <outcome>` once ended; detail `stage`, `pass`, `outcome`). A stage's `started` or `pass` first ends every open step of another stage `completed`; `ended` ends the stage's step `failed` for `failed`, `base-red` and `red`, else `completed`; `run` `ended` ends the open steps `failed` for `failed` and `base-red`, `cancelled` for `halted`, else `completed`, and retires the source. Every line sets `/status_line` to `<ticket>: <text>`. When the Bothy run ends, the steps a source left open end `cancelled`. | Read from the chain's own code (`stage-events.ts`, `stageEvents`) and a sample its runner (`runTicket` with `withStageEvents`) wrote: the chain runs one stage at a time and writes an `ended` line for each stage (the runner clears `ended` at every stage start). The implicit end keeps a step from staying open behind the chain when an end line is lost or a writer leaves it out. `workflow` is the step kind for a phase of a process that is not a tool call, subagent or background job (09 5.3); one open stage at a time keeps the count of 5.4 at one. |
| D-FEAT-HAS-5 | 2026-11-20 | A stage file does not hold the run: it is shown while the run is open. The command itself keeps the run open as the tool call's foreground process, or as background work of 17.12 points 1 or 8. A source is retired at its `run` `ended` line, by `stages deregister`, by a newer registration of the same file in the same thread, and at the next registration once it is older than `SOURCE_MAX_AGE_S`. | A file says nothing about whether its writer still runs; holding the run on it could keep a run open for ever after a crash. The age bound keeps the folder small without a sweep of its own. |
| D-FEAT-HAS-6 | 2026-11-20 | The handler keeps each source's cursor in the turn and passes it to the next read, so the saved cursor is read only once per run. The open steps of a source that is no longer listed (deregistered, or replaced by a new registration of its file while the run is open) end `cancelled` at the next read, also at the last read before `run.finish`, and a failure of that last read is logged and never keeps the run from finishing. | Red team r1 of this change: a second registration of the file in the same run left the first source's step `running` after the run ended, and a cursor that could not be saved made every poll show the same lines again (both reproduced, both now tests in `tests/unit/test_stages.py`). |

Limits: lines written after the last read and before `run.finish` of a run are shown by the
thread's next run, not by that run; a chain that never writes its `run` `ended` line leaves its
source until the age bound; the order and the timing of the lines are shown as written.

Open minors (for the next run in this area): after a stop of the run the last lines are not read, so
the thread's next run shows the stopped chain's last lines (within one poll interval); a chain that
returns while a stage waits (the plan approval, for example) shows that stage's step as `cancelled`
at the end of the run; a broken stages folder writes one warning per poll; an `OSError` text in a
warning can name the path of the adapter's own stages folder; the chain's status line and the live
box's status sentence replace each other; when the last read before `run.finish` fails (a stages
folder made unreadable mid-run), the open steps stay `running` in the ended run (close every entry
of the turn's open steps then). Fixed on the pull request (CodeRabbit): a stage file that is
unreadable for a moment stays listed with its cursor instead of counting as a retired source, a
deeply nested line is a malformed line, and a failed write removes its temporary file.

Deploy note: nothing to configure. The adapter creates the folder `stages` at its next connect. The
profile's command registers the run folder's `stages.jsonl` right before it starts the chain.
