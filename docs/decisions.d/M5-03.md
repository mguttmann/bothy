| D-M5-03-1 | 2026-10-25 | Build configuration and backups: `tool/branding_defines.dart` writes `android/branding.properties` (application ID, label, URL scheme, App Links host), which `android/app/build.gradle.kts` reads; the optional branding key `application_id` defaults to `bundle_id` and must be lower-case letters and digits in segments that start with a letter, because it is also the private-use scheme of the OIDC redirect (a bundle identifier with a hyphen needs its own `application_id`). | D-M5-03-2 | 2026-10-25 | App Links only with a configured host: the branding key `associated_domain` is the public domain of both phone builds (the associated domain on iOS, the App Links host on Android). | D-M5-03-3 | 2026-10-25 | Login and passkeys: one Custom Tab per login (`androidx.browser`), the default browser where no Custom Tabs provider exists, never a web view. Every link from outside reaches `LinkActivity`, which hands it with `CLEAR_TOP` and `SINGLE_TOP` to the running `MainActivity` (single top), so the tab above it closes and no second Flutter engine starts; the OIDC redirect `<application ID>:/oidc/callback` goes to the waiting login, every other link to the router. Android delivers a new intent before `onResume`, so a login that still waits when the app is in front again was cancelled (`error=cancelled`). Passkeys through the Credential Manager (`androidx.credentials`) with the platform provider only, which exists from API 34: the Play services provider library is proprietary and not on the license list, so devices below API 34 get no passkey button. Passkeys are offered only when the App Links host equals the instance's host (the relying party ID); the instance lists `android:apk-key-hash:<hash>` in `auth.webauthn_origins` and the host serves the Digital Asset Links (README). Secrets use `flutter_secure_storage` with AES-GCM and the key wrapped by an RSA key of the Android Keystore, without a biometric prompt (the step-up is the device key's of M5-01); the app's activity is a `FlutterFragmentActivity` because that step-up prompt needs one. | 15 8, 9; 08 2.2, 2.5, 18; quality/licenses/allowed.txt; brief Design notes 2 and 3. |
| D-M5-03-4 | 2026-10-25 | Notification channels: the stable IDs `mentions`, `questions`, `messages`, `runs`; `mentions` and `questions` start with high importance, `messages` and `runs` with default. Kinds: `mention` and `dm` to `mentions`; `input_needed`, `security` and `admin` to `questions` (each asks the person to act); `message` to `messages`; `run_done` and `run_failed` to `runs`; a kind the build does not know to `messages`. Names and descriptions come from `l10n` in the device language and are handed over through Pigeon at every start, which creates missing channels and updates the texts of existing ones (the importance stays the person's). A quiet notification goes into the same channel with `setSilent(true)` (M5-05). The runner keeps the mapping in its private preferences for the push service of M5-05. The runtime permission for notifications (API 33 and later) stays with M5-05. | 01 10.3; 13 2, 3.4; 15 10.2; brief Design note 4. |
| D-M5-03-5 | 2026-10-25 | Recent apps protection per API level, the narrowest rule that hides the content: API 33 and later `setRecentsScreenshotEnabled(false)` from the start (no picture at all; screenshots of the open app stay possible); API 26 to 32 `FLAG_SECURE` on the window from `onPause` (before the system takes the picture) until `onResume`, so it blocks screenshots and screen recording only while the app is not in front. The privacy cover of M5-02 is drawn on `inactive` in addition; the gateway is suspended on `paused` and resumed on `resumed` by the lifecycle mapping of M5-02. A permanent `FLAG_SECURE` for the app lock (M5-08) and the terminal (M5-12) is theirs to set. | 01 5.6 E6; 15 7.2; R-PR-12; brief Design note 5. |
