# AR-02 Runner: orderly stop never orphans a turn

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-AR-02-1 | 2026-11-06 | An orderly stop of the runner (SIGTERM or SIGINT) first stops every turn it started itself whose process runs, as in 09 18.6 (SIGINT, stdin closed, SIGTERM and SIGKILL with `stop_escalated`) and waits until each run ended, at most `runner.stop_grace` plus `runner.kill_grace` plus `runner.cli_probe_timeout`, as the stop of a deleted forum does (18.15); only then does the SDK shut down. Each such run finishes `cancelled` with the reason `adapter_stopped` and a summary that names the cause for the thread, with the costs of the last `result`. A run between two processes (its answer being posted, a recovery being prepared) is not stopped there, so an answer in flight is not cut off; the SDK's cancellation covers it (D-AR-02-2). Adopted turns keep running with their records (18.9), and a run without a turn yet starts again from the inbox (09 4.9). | D-AR-1 of [autonomous-runs.md](../design/autonomous-runs.md#4-decisions-restart): a restart cancelled every run task, the cancel path had already lost the process handle, and the record and run files were removed while the CLI lived on, holding the thread's locks (reproduced by `tests/scenarios/test_orderly_stop.py` against a real runner process before the fix). Stopping through the existing stop path reuses its escalation, its read of the last `result` and its finish, instead of a second stop path. |
| D-AR-02-2 | 2026-11-06 | The cancel path of `RunTurn.run` stays as the safety net for a turn that the stop of the turns did not reach (it started in between, or outlived the wait): `_run_process` keeps the process handle while a process of its group lives, the cancellation stops the group as in 18.6 and finishes the run `cancelled` with `adapter_stopped` (or the reason of a stop already requested; nothing for a run the server ended), and the turn record and run files are removed only when no process is left. A second cancellation during that stop leaves the record for the next start, which adopts or stops the turn (18.9). | The design note requires that the handle is kept until the turn is known to be gone and that the record goes only after the process exited; a record of a live turn is what lets the next runner find it, so keeping it is never an orphan. |
| D-AR-02-3 | 2026-11-06 | New reason `adapter_stopped` of `runs.state_reason` (09 5.2): state `cancelled`, set by the adapter. `finishRun` accepts for `cancelled` the five reasons of a cancel request and `adapter_stopped` (`domain.AdapterCancelReasons`); `adapter_stopped` is no reason of a cancel request (`run.cancel_requested` is unchanged). Like every `cancelled` reason other than `user_cancelled`, it defers open follow-ups, so a follow-up written before the restart starts the next run. The fakes of the SDKs accept it, and the metric `bothy.run.finished` lists it. | D-AR-1 asks for `cancelled` with a reason the thread shows, and the server took only the reasons of a cancel request for `cancelled` (brief M2-09 note 6c), so no existing code fits: `user_cancelled` would say a person stopped the run and discard its follow-ups. A server that does not know the reason answers `400` and the run ends `interrupted` after `agent.presence_timeout` as before; the server and the runner of this change ship together. |
