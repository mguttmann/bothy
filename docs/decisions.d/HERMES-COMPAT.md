# HERMES-COMPAT Hermes adapter on the current Hermes Agent release line

Hermes Agent changed its release tags from dates (`v2026.9.24`) to versions (`v0.22.x`) in
October 2026. The adapter was pinned to `v2026.9.24` and required Python 3.12, while Hermes
installs of the new line still run on Python 3.11 during their update. This ticket moves the
adapter to `v0.22.5` (spec 09 section 17).

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-HERMES-COMPAT-1 | 2026-10-29 | A Hermes release tag is `v` and dot-separated numbers only; release candidates (`rc.1-v0.22.5`, `abandoned-rc.*`), canaries (`v0.22.5+canary.<stamp>`) and other refs never count. Every version tag (first number below 2000) ranks above every date tag (`vYYYY.M.D`); within a scheme the numbers decide. Renovate gets `allowedVersions: <2000` for the pin. Place: `tests/fake_hermes_kit.py` (`newest_release`), `renovate.json`, `tests/unit/test_newest_release.py`. | `v0.22.5` descends from `v2026.9.24`, but a numeric comparison of the tags ranked the old date tag first, so `--hermes-version=latest` tested the pin again and Renovate would have proposed the date tag as an update. |
| D-HERMES-COMPAT-2 | 2026-10-29 | The adapter's `requires-python` is `>=3.11`, ruff targets `py311`, mypy `3.11`, and `plugins/hermes-adapter/.python-version` is `3.11`, so its own tests run on 3.11 locally and in CI (uv picks that version); a unit test keeps the four equal and a Fake-Hermes test checks that the adapter admits every Python the pinned Hermes admits. The pin's Python is `3.14`: the lock of `v0.22` supports only 3.14 (`supported-markers`), so the Fake-Hermes tests and the recording run the adapter on 3.14. Nothing in the adapter needs 3.12. | Hermes admits `>=3.11,<3.15` so that installs on an older Python can still run their update; the adapter must load in such an install. The SDK already supports 3.11. |
| D-HERMES-COMPAT-3 | 2026-10-29 | Pin `v0.22.5`, commit `bf0203a794a07aac3ff764972ab9087baa4e4f4e` (the commit the annotated tag points to), recorded on 2026-10-29. The tag is six days old on the recording day, one day short of `deps.min_release_age`; the ticket names this release, no newer release or withdrawal of it exists, and the next Renovate proposal follows the cooldown again. | The current release line is what Hermes installs run; the newest version tag was the one to support. |
| D-HERMES-COMPAT-4 | 2026-10-29 | The platform declares `authorization_is_upstream = True` while Hermes sees no `<KEY>_ALLOWED_USERS` (the list `switch-mode personal` writes, 09 17.7 layer 3), read on every call with Hermes's own gate reader `platform_gate_env` (profile `.env` and process environment); with that list it is `False`. Fake-Hermes tests show that the list, in `.env` or only in the gateway's environment, still refuses another person with a valid token. Place: `platform.py`, `typings/gateway/platforms/base.pyi`, `typings/gateway/platforms/_shared.pyi`. | Hermes `v0.22` checks every message again at admission and trusts an own access policy there only with this declaration (measured: `access_policy_own.json`, `access_policy_upstream.json`); without it no message of an organization profile reached a turn. With the declaration Hermes skips its own allow list, which must stay in force for a personal profile; a read at the adapter's start missed a list set only in the process environment or written before the restart. |
| D-HERMES-COMPAT-5 | 2026-10-29 | After every command it sends (`/new`, `/resume`), the adapter waits until Hermes' processing task of that command has ended (`BasePlatformAdapter._session_tasks` under `_event_session_key(event)`, both in the stubs and held by the stub contract test), not only for `on_processing_complete`. Place: `platform.py` (`_command_settled`). | Hermes `v0.22` reports the completion of a command before its processing ends; the bound turn sent in that gap ran without a completion, so the run never finished (measured in the Fake-Hermes bind test). No public surface tells when the processing ended. |
| D-HERMES-COMPAT-6 | 2026-10-29 | For `session.mode = bind` the adapter sends no `/resume` when the target session ran a turn in another thread of the same gateway process (remembered from `pre_llm_call`, not kept across restarts); it fails open with the new session and `bind_failed: session_missing` (09 9.5 item 4). After a restart the takeover works (Fake-Hermes test). | Hermes `v0.22` keeps such a session live on the other thread's route: `/resume --all` does not move it (`session_resume_admin.json`), and a turn of the binding thread on it paused with `admission_conflict`. Failing open is the documented answer when the old session cannot be continued. |
| D-HERMES-COMPAT-7 | 2026-10-29 | The recording accepts exactly one listener of the Hermes process tree: a TCP port on `127.0.0.1`, Hermes' local runtime API (`gateway/run_api.py`), which `v0.22` always starts; any other listener, and every loopback one when there are more, fails the run. Scenario homes keep the loop-tick socket within 100 bytes, the bound Hermes `v0.22` binds a Unix socket below (beyond it, it listens on TCP loopback instead). The scenario `busy_queue_global` no longer waits for `on_processing_complete` of the follow-up, which `v0.22` steers into the running turn. The Fake-Hermes harness starts the gateway up to five times instead of three (D-M2-33-14). Place: `tests/hermes_harness/gateway.py` (`unexpected_listeners`), `scenarios.py`, `tests/recording/scenarios/busy_queue_global.json`, `tests/fake_hermes_kit.py`. | M2-32 Design note 5 disables every server component of Hermes; the runtime API of `v0.22` has no setting that turns it off, is bound to loopback only and needs a ticket of the control socket. The scenario change follows measured `v0.22` behaviour, not a weaker check: the observations still classify the follow-up. `v0.22.5` exited at start with a `KeyError` of its own import system (its plugin discovery thread races the main thread's imports; one of its own plugins fails the same way) three times in a row more than once in the runs of this ticket on a loaded machine. |
| D-HERMES-COMPAT-8 | 2026-10-29 | The point `own_access_policy` gets the scenario `access_policy_upstream` (own policy plus `authorization_is_upstream`) as evidence; its verdict stays the own policy's alone, so `v0.22.5` reads "adapted". The probe records reads of `authorization_is_upstream`.
