# AUD-srv-status-01 Backup runs, their failure signal and the limits of the status module

Work package of the audit of 2026-11-11 for the status module, findings srv-stats-status-2,
srv-stats-status-3, srv-stats-status-5, srv-stats-status-10, fn-operations-backup-7,
fn-operations-backup-13, fn-console-stats-viz-7 and architecture-4.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-SS01/1 | 2026-11-12 | The default command of `bothy-backupd` handles at its start what a run left behind whose process ended without its cleanup: `app.Service.ClearDumpDir` removes every entry of the dump directory (the directory stays), and `app.Service.CloseInterrupted` moves every `backup_runs` row that is still `running` and was started before the start of this process, of a backup or of a restore test, to `failed` with `finished_at` and the code `interrupted` (new port method `BackupRuns.FailRunning`, query `FailRunningBackupRuns`, role `bothy_backup`). The directory is emptied once; the rows are tried again before every tick of the scheduler until one call succeeded, always with the start time of the process. No metric is recorded for such a row. The short commands (`backup`, `restore-test`, `expire`) never run this step. | A run finishes its row and removes its dump itself, also when it is canceled, but only inside its process: after a kill, an out-of-memory stop or a crash of the host the row stayed `running` until `retention.ops` removed it, and the dump with the whole content of the database and the directory with the password file of `pg_dump` stayed in the volume `backup-scratch`, because no later run looks at either (findings fn-operations-backup-13 and srv-stats-status-10, one cause). The step belongs to the default command alone, because it is the first process of its container, so nothing else runs a backup at that moment; a short command runs next to the service (`docker compose exec`) and would close the rows of the service and delete its dump. The start time as the bound keeps a run that this process started in between out of a later attempt, which is needed because the database may not answer at the start. The dump directory is also the scratch directory of the object mirror, whose copy of an object is a leftover of the same kind. Tests: `TestRunsFailRunning` (PostgreSQL, role `bothy_backup`), `TestCloseInterrupted`, `TestClearDumpDir`, `TestScheduleClosesInterruptedRunsUntilItSucceeds`, `TestBackupDaemonHandlesWhatAnEarlierProcessLeft` (the configured daemon on PostgreSQL). |
| AUD-SS01/2 | 2026-11-12 | Not covered by AUD-SS01/1: the scratch directory of the restore test is not emptied at the start, and two containers of the service at once are not told apart. | Every restore test empties its directory first (backup-restore.md section 4), so a copy left by a killed test goes with the next test; the finding names the dump and the password file, which nothing removed. A second container that runs a backup while the service starts (`docker compose run` instead of `exec`) would lose its row and its dump to the step; the runbook runs `backup` and `restore-test` with `exec`, backup-restore.md section 1 now says why, and D-M7-03-11 decided against a lock across processes. |
| AUD-SS01/3 | 2026-11-12 | `bothy-backupd backup`, `restore-test` and `expire` run with a context that `SIGINT` or `SIGTERM` ends (`interruptible` in `cmd/bothy-backupd`). A canceled run ends as before a stop of the service: the row `failed` with the code `canceled`, the dump removed, exit code `1`. | The short commands handled no signal, so Ctrl-C ended the process at once and left the row `running` and the dump and the password file in the scratch volume until the next start of the service (finding srv-stats-status-10). The use cases already finish a canceled run cleanly (D-M7-03-11), they only never saw the signal. Test: `TestInterruptibleCancelsOnSignal`. |
| AUD-SS01/4 | 2026-11-12 | A failed backup run adds one to the new counter `bothy.backup.failures` with `bothy.backup.kind` the kind of its `backup_runs` row (`pg_full`, `pg_diff`, `logical`, `objects`); a run with the code `canceled` and a row closed as `interrupted` do not count, and the restore test keeps its counter per failed check. Every series of both failure counters starts at 0 when the recorder is created. Three alerts read them: `BothyBackupRunFailed` (`ticket`, per kind), `BothyRestoreTestFailed` (`ticket`, per check except `audit_chain`) and `BothyRestoreTestAuditChainFailed` (`page`), each over the last 24 hours. The error code of a run is no attribute. Amends the reason of D-M7-03-8: the escalation "two failed tests in a row" is not built; `BothyRestoreTestStale` reports the missing success. | backup-restore.md section 4 and D-M7-03-8 promised a `ticket` per failed restore test and a `page` for the audit chain, but no rule read `bothy.backup.restore_test.failures`, and a failed backup run recorded only its duration, so a failure showed only through the age of the last success (finding srv-stats-status-3). The gauges put `pg_full` and `pg_diff` under `physical`, where differential backups that succeed hide a full backup that keeps failing; the counter uses the kind of the row. A canceled run is a stop of the process, not a failed backup (D-M7-03-11). A rule sees a failure as the increase of a series that exists, so a series that first appears with its first failure would raise nothing after each start. The codes are an open set (`<tool>_exit_<n>`), which signals.md "Cardinality" rules out for an attribute; the row and the log name the code. Two failures in a row cannot be told from one test with two failed checks by this counter, and every failed test already raises its own alert. Not covered: a failure before the first metric export of its process reaches Prometheus as the first value of its series, which is no increase, so it raises no alert. That is a scheduled run that fails right after a start of the service, or a command run by hand that fails before its first periodic export, so that the export at its end is its only one; the row, the log and the exit code still report it, and `BothyBackupStale` and `BothyRestoreTestStale` the missing success. A forced export of the zero series before the first run would close the window; it changes the start of every command and is not built in this package. Tests: `TestRunFailed`, `TestFailureCountersStartAtZero`, `TestRunFailureRecordsCode`, the rule tests of the three alerts in `bothy-alerts.test.yaml`. |
| AUD-SS01/5 | 2026-11-12 | The automatic restore test keeps its scope: repo1 only, no restore of the logical dump, no `restic check`, no file sample with the driver `s3` (D-M7-03-1, D-M7-03-4, D-M7-03-7). The overview of backup-restore.md names per backup only the checks that exist, and its section 7 item 5 and 16 8.3 "As built" item 6 name what the test does not prove. | Finding srv-stats-status-2: the facts hold, and they are the rulings above; what was wrong is the runbook, whose overview named `pgbackrest verify` for both repositories, the restore test for the dump and `restic check --read-data-subset` for the objects. A verify or a restore of repo2 and a read of the restic repository download the off-site copy in whole or in large part on every test: transfer cost and time on the owner's storage account, which is the owner's decision, and 16 8.3 asks for none of it. |
| AUD-SS01/6 | 2026-11-12 | The window of a point-in-time restore from repo1 is written down: backup-restore.md section 7 item 4 and upgrade.md sections 1 and 3. `backup.pg.local_retention_full` keeps its default `1`, and no configuration check warns. | Finding fn-operations-backup-7: after every physical run the service expires repo1 to that many full backups, and pgBackRest expires a full backup with its differential backups and the WAL of expired backups (options `repo-retention-full` and `repo-retention-archive`, https://pgbackrest.org/configuration.html, retrieved 2026-11-12). Without an off-site target a time before the newest full backup is gone from the repository, which no guide said, while upgrade.md recommends a full backup before an upgrade and names a point-in-time restore as the way back. The default is a tested, documented value of the configuration reference, and a larger one costs repository space on every instance; the guides now name the trade. |
| AUD-SS01/7 | 2026-11-12 | Deferred, finding srv-stats-status-5: the status page still shows the last automatic states while no `worker` runs `status.probe`, and the last state of every component of the measured checks (`api.http`, `sync.fanout`, `push.apns`, `push.fcm`) while the own measurement is not written; the other checks read other sources and still run. 16 section 12 "Limit" now says so. Open question for the owner: should the page show that its states are stale, and as what: a new value such as `unknown` in the state of a component, which every app and SDK has to render, or an existing state. | The facts hold (D-M7-09-1: a window without rows is no evidence). A page that knows its age needs a stored time of the last round (a migration and 03 4.12), a new member or state in the status contract and its display in three clients: a feature of its own, not a correction of this module. The stored round state is the same change that the per-process memory of `status.probe` needs (D-M7-09-3), so both are designed together. A stopped worker is reported today by `BothyEventConsumerLag`, whose gauge the `api` processes export as well (signals.md 4.2). |
