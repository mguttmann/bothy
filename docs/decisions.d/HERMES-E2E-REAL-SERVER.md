# HERMES-E2E-REAL-SERVER Adapters end to end against the real server

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-HERMES-E2E-1 | 2026-10-30 | Cause of the instance: in a text channel with `auto_thread` the triggering message M stays in the main thread and the run lives in the thread opened on M (09 3.4 point 5), but the adapter quoted M (`reply_to_message_id`) in its answer; the server refuses a reply to a message of another thread (`checkReply`, `400 validation_failed` `not_in_thread`), the outbox dropped the answer and Hermes later sent it again as a report. Reproduced by `test_mention_in_the_main_thread_answers_in_the_auto_thread` against the real server (`outbox entry 1 failed code=validation_failed`, no answer in the thread) before the fix. | A reproduced failure before the fix. |
| D-HERMES-E2E-2 | 2026-10-30 | The adapter reads the triggering message once in `prepare` (`getMessage`, `message.read`) and quotes it only when its `thread_id` is the run's thread; a follow-up passed into the turn is always quoted (it lies in the run's thread); a command run quotes nothing. A failed read quotes nothing. | 03 `messages` (`reply_to_message_id`: same thread) is the rule; the run context names no thread of its messages, and an answer without a quote is always accepted. One read per run is cheaper than a refused answer. |
| D-HERMES-E2E-3 | 2026-10-30 | Recovery path: a `send` whose text starts with the notice of Hermes' delivery ledger ("Recovered reply", restart, reconnect and rate limit variants of `gateway/delivery_ledger.py` in `v0.22.5`) is acknowledged without a post when its reply was taken over as an answer in the same thread; the adapter keeps a SHA-256 digest of thread and text of every answer for `ANSWER_RETENTION_SECONDS` (`store.py`), longer than Hermes keeps an obligation (`_RETENTION_SECONDS` of `gateway/delivery_ledger.py`). Any other recovered send (for example a report) goes the normal way. | The outbox owns the delivery of an answer, also after a restart; an answer the server refused ended its run with the error, so a copy without a run would be a duplicate or a detached text. No content is stored. |
| D-HERMES-E2E-4 | 2026-10-30 | Third instance found by the new suite: a skill command run failed before the start, because the adapter read the run context and the server answers `getRunContext` of a run whose trigger is not a message with `500 internal_error` (`runs/app/runcontext.go`, 09 4.6 defines the context for a triggering message only). The adapter reads no context for a command run: the system part is the fixed note and the channel instructions. The FakeServer of the SDK now answers `getRunContext` of such a run with `500 internal_error` too. | The server's rule is the contract; the FakeServer served a context the server never serves, which hid the break. Defining a context for command runs would change the API of every client. |
| D-HERMES-E2E-5 | 2026-10-30 | The class fix is two checks. (a) End-to-end suites `plugins/hermes-adapter/tests/realserver` (the adapter's own handler and SDK loop with the fake Hermes runtime) and `plugins/claude-code-runner/tests/realserver` (the runner with Fake-Claude) against `services/server/test/sdkserver`: mention with `auto_thread`, reply in a thread, forum post, reports into a text channel, a fixed thread and a forum (new post), files and voice out, voice in with transcript, control and skill commands, a card answered by a click, a follow-up steered into the turn, an edited answer and the title, cancel, retry, and the recovery path. (b) The rule `client-routes` of `make api-checks`: every generated operation the Python SDK or a Python plugin imports exists in `openapi.yaml`, is enabled in `operations.yaml` and registered in `routes.gen.go`. | (a) finds what only the running server shows (a refused request, a missing route, an undefined answer); (b) finds a documented but unserved operation without a server, on every change, like SERVER-AGENT-TRIGGERERS. |
| D-HERMES-E2E-6 | 2026-10-30 | The suites carry the pytest marker `e2e`, which `make test` deselects; `make adapters-e2e` runs them, and the CI job `test-adapters-e2e` (in `ci.yml` and `build-verify.yml`, required through `ci-ok` and `build-verify-ok`) runs it whenever the plan selects the components `sdk-python` or `plugins` (both own `services/server/`) or the API contract changes. | The suites need Go and a container runtime; a job of their own names the contract break in the check list instead of hiding it in the long SDK and plugin test job. |
| D-HERMES-E2E-7 | 2026-10-30 | Test support: the driver of sdkserver moved from the SDK's real-server conftest into `bothy_sdk.testing.sdkserver` (`RealServer`, `build_sdkserver`, `start_sdkserver`, `m4a`), shared by the SDK and both adapters. sdkserver gained the `world` of `ready`, the op `wait_run` (the run of a message, also in an auto thread) and a raw body with headers for `call` (`uploadPart`); the suites start it with `file.scan.mode` `off`, because no virus scanner runs in the test. | One home for the driver; the scan is not under test here and would keep every upload `pending`. |

| D-HERMES-E2E-9 | 2026-10-30 | Fourth instance found by the new suite: a follow-up never reached the running turn (and an answer typed to an open card never reached it either), because the adapter looked its text up in the run context, which holds only the messages before the triggering message (09 4.6 `thread_context`); the adapter logged "follow-up not in the context" and passed nothing. The adapter now reads the follow-up with `getMessage` under the run's token, as the Claude Code runner does. The FakeServer's context now holds only the messages before the trigger too. | The FakeServer had put every message of the thread into the context, which hid the break; the real server's rule is the contract. |
