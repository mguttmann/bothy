# FIX-RUNNER-BG-INBOX-AUTH Background sessions: whose input, whose account, whose environment

The automated review of FEAT-RUNNER-BG-SESSIONS on 2026-11-16 found three ways in which a
background turn of the Claude Code runner could act for the wrong party: a session took a
message of any other Claude Code session of the host user as the runner's, the counter-check
of 09 18.3 was open when it found nothing, and a value of one run's environment could reach
the session of another. The review of the first version of this change found a fourth, in the
new rule itself: the content of a transcript record was read before its origin (ruling 9).
The review of the second version found three more: the next run continued the conversation
that had taken the foreign input (ruling 10), a delivery of another sender that the CLI
records as a notification passed as the session's own (ruling 11), and a third tool that
reaches other sessions was not denied (ruling 3).
Background mode was not switched on anywhere before this change. The
design with the evidence, the alternatives and what stays open is
[runner-background-sessions.md](../design/runner-background-sessions.md) sections 4.14 to 4.16,
5 item 12 and 10; normative text: 09 18.2, 18.3, 18.4, 18.5 "Whose input" and 18.9.

Everything about the CLI below was run with the pinned Claude Code 2.1.325 against the local
stand-in for the API with a configuration folder of its own (the method of
D-FEAT-RUNNER-BG-SESSIONS-14): no login and no model call. Where a rule of the CLI is given,
it was also read in the file of that version.

Deploy note: none. The default is `print`, and nothing here enables the mode anywhere. A turn
record that a runner before this change wrote for a background turn names no line of the
runner and no passed counter-check: a runner with this change that adopts such a turn ends it
`failed` at the next line the session takes (`background_foreign_input`) or at its next output
without a new request record (`billing_mode_mismatch`). A host user whose own Claude Code
account or configuration delivers inputs into every session (a plugin, a channel, a scheduled
prompt, a relay) sees runs of this mode end with `background_foreign_input` (rulings 9 and
11). A session that ended a run with that cause is not continued by a later run in either
launch mode: the thread goes on in a new session (ruling 10), and the mark lies in the
runner's state folder, so a runner with another state folder does not know it.
