# AUD-adminui-misc-01 Grants for apps, the audit export, faults of the app, same names and the import page

Five findings of the audit of 2026-11-11 against `packages/admin_ui` outside the agent screens
(`fn-extensions-sdks-1`, `admin-ui-access-audit-stats-2`, `admin-ui-access-audit-stats-5`,
`admin-ui-access-audit-stats-6` and `admin-ui-core-instance-3`). Each was read again in the code of
main before the change. One is a way that was missing: after its installation an app could get an
access grant only through a hand-made request, although the update dialog sends the owner to
"Access grants". The other four concern what a screen saves, says or reads: an audit export that
failed before it began still left a file, a fault of the app read as a fault of the server and
reached no error handler, a choice between people showed only the display name, which is not
unique, and the page of an import source read every imported item at every refresh. Normative
text: 01 section 9; 03 `users`; 06 sections 2 and 5; 07 sections 2 and 9; 11 sections 4.1 to 4.3;
22 section 13; the package README.

| AUD-AM1/5 | 2026-11-12 | The page of an import source reads what it shows, one pass at a time. `ImportController.refresh` runs one pass per source: a call while a pass runs gets the future of that pass, and one more pass follows it, so an action, the refresh control and a tab that becomes visible never read side by side and what changed meanwhile still reaches the view. A pass reads the failed items with the state filter of `listImportItems` and the posted items page by page, oldest first, only until every mapped channel has its channel item (`ImportRepository.importItems` with `enough`); pending and skipped items are never read. While a mapped channel has no posted item, the pass still reads every posted item. Not built: a filter by item kind in `listImportItems`, the state of the channels in one answer, and a retry after `429`. | Audit finding admin-ui-core-instance-3, verified at the source and computed, not measured: every refresh read every item of the source in pages of the page size of the repository, although the page shows the posted channel items and the failed items, then read each channel, and nothing kept two refreshes from running at once. The import tool writes the channels before their content and the server lists by ascending ID, so the channel items are the first pages of an import whose channels exist. A filter by item kind is a change of the contract, the server and every generated client (D-M8-08-1 names its absence), and one answer with the state of the channels is a new operation; both belong to the importer of the server and are noted for its next change of the API. The console repeats no read (`createConsoleApiClient` asks once), so a refused read shows as the failure of the page; reading less is what keeps the page away from the limit, and a retry in the console is a change of its client for every page. `test/import/import_controller_test.dart` holds the pages that are read and the one pass; `test/import/api_import_repository_test.dart` holds that the next page is not asked for. |

## Open

For the next run in each area. None of these is a known wrong result of the product.

- Side reads that leave a list empty (AUD-AM1/3): `AccessNames.load` and the optional lists of a
  page (the names behind IDs, the agents of the import page, the groups of the people filter)
  catch every error and say nothing, so a fault of the app in them stays silent and a failed
  connection reads like an empty directory. Telling a refusal from a fault there needs each read
  to be looked at, and the test doubles of `apps/client` and `apps/console` that answer such
  reads with errors of their own need real answers first.
- "New agent" (AUD-AM1/3): `newAgentFailureOf` passes an error that is neither an answer of the
  server nor an error of the login layer on as it is, and the callers read it as offline or as
  `internal_error`; it does not go to `reportAppFault`.
- `listImportItems` has no filter by item kind (AUD-AM1/5, D-M8-08-1). With it the page of an
  import source could ask for the channel items alone; today it reads every posted item while a
  mapped channel has none. The filter changes the contract, the importer of the server and every
  generated client. Each imported row of the page still costs one `getChannel` and one `getSpace`,
  read one after the other (`ApiImportRepository.importChannel`); one answer with the state of all
  channels of a source and a retry of the console after a refused read belong to the same change.
- The integration tests of the desktop app (`apps/client/integration_test`) and the patrol suites
  of the console pick people in the dropdowns this package changed. They were read, not run, for
  this change: the entries keep their keys and the display name as a text of its own.
