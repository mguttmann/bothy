# FIX-macos-ax-text-insert Accessibility writes into text fields on macOS

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-AX/1 | 2026-10-31 | The macOS runner adds `setAccessibilitySelectedText(_:)` and `setAccessibilityValue(_:)` to the engine's private class `FlutterTextInputPlugin` (`AccessibilityTextInput.install()` in `MainFlutterWindow.awakeFromNib`, before the plugins register): the selected text goes through `insertText(_:replacementRange:)` with the view's selected range, the value through the same method over the whole string; a value that is neither a string nor an attributed string changes nothing, nil inserts the empty string. The legacy `accessibilitySetValue(_:forAttribute:)` routes `AXSelectedText` and `AXValue` to these two setters and every other attribute to the superclass. A selector the class implements itself is left alone (a later engine may fix this itself); without the class the runner logs once and changes nothing. | The focused element of a Flutter text field is that plugin, an `NSTextView` whose model hears edits only through `insertText(_:replacementRange:)` (Flutter 3.47.7, `FlutterTextInputPlugin.mm`). AppKit's setters write into the view's text storage directly, so the tool read its text back as `AXValue` and skipped its paste fallback while Flutter's model, and the composer, stayed empty. `insertText` is the path of typing and of the input methods, so the framework gets the usual edit and delta. |
| FIX-AX/2 | 2026-10-31 | Evidence: `apps/client/macos/AccessibilityTextInputTests/run_tests.sh` (a stand-in text view with its own model; it also shows that AppKit's unpatched setter bypasses `insertText`), and `integration_test/composer_ax_insert_test.dart` against the real engine through the debug channel `bothy/a11y_probe` (`axInsert` on the window's first responder, through the setters and the legacy setter; "ab" with the cursor at 1 plus "Hallo" gives "aHallob" with the cursor at 6, the value "X" gives "X", without a focused field nothing changes). The write of another process (`AXUIElementSetAttributeValue`, `macos/AxWriteProbe/ax_write_probe.swift`) runs in `tool/run_composer_ax_insert_test.sh` only when that process has the Accessibility permission; otherwise the test reports the case skipped and the cross-process path is unproven on that host. With VoiceOver on, the focused element is the engine's `FlutterTextField` with the plugin as its field editor; that path is not tested. | An AX client in another process needs a permission that the CI runner may not grant (D-M4-32-2); the in-process calls hit the same methods that AppKit's accessibility server calls for such a write. |
| FIX-AX/3 | 2026-10-31 | Not changed: other attributes that write text state (`AXSelectedTextRange`, `AXVisibleCharacterRange`) keep AppKit's behaviour, and Windows is investigated separately. | The reported failure is the selected text and value path of dictation tools; a selection set from outside is not part of it. |
