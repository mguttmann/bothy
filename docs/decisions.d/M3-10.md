| D-M3-10-2 | 2026-10-20 | An avatar or logo is staged by the server in a session it opens itself, mode `direct`, with exactly one part, outside any transaction and only after `authorize` allowed the action: first part `file`, declared type `image/jpeg`, `image/png` or `image/webp` (a type in `file.denied_mime_types` gives `415` with `reason` `file_type_denied`), the part read into memory up to `ImageCap` (the smaller of `file.max_upload_bytes` and `file.upload_part_bytes`) plus one byte while it is counted and hashed, `413` whose `detail` names the key that set the cap, no further part; then the `files` row, the session with the counted size and SHA-256 as declared values, and the one part. A failure stores nothing; a staged file whose unit of work fails stays an open session until `file.upload_session_ttl`. Place: `files/domain/purpose.go`, `files/app/profileimages.go` (`StageImage`), `platform/httpserver.ImagePart`, 12 3.7. | The database must know size and SHA-256 before the first object write (03 `file_upload_sessions`, 12 4.1, D-FI-11); one part is the memory bound every part upload already has (12 3.2); no type detection or decoding runs in the API process (SEC-UP-5). |

| D-M3-10-5 | 2026-10-20 | The new file is linked in the unit of work of the upload, before it is deliverable: lock the anchor row (the principal row, or the setting row `branding.logo_file_id` under the settings lock of M1-46, inserted when absent), complete the session and insert `files.scan` (`CompleteStagedImage`), write the new id, set `deleted_at` on the previous file of the same purpose and uploader (`ReleaseImage`), append `user.updated` or `instance.updated`. Place: `identity/app`, `instance/app`, `files/app/profileimages.go`, 12 3.7 and 12. | One unit of work keeps link and release consistent and the lock order of 03 6.3 (anchor row, then `files`); a client sees the change at once and retries the bytes, the login screen shows the product mark meanwhile (01 12). |
| D-M3-10-6 | 2026-10-20 | Purpose rule: a file with purpose `avatar` or `branding` is kept only when its original is stored as filtered JPEG, filtered PNG or converted still WebP (`StoredOriginalAllowed` over `OriginalKind`). The scan pass fails a detected type whose original would be stored unchanged or as a re-encoded GIF, and `files.thumbnail` fails a WebP that stays unchanged (animated, or above `file.image.max_pixels`); both set `upload_state = 'failed'` with `failure_reason` `file_type_denied` and `file.updated` before the file can become deliverable, and the objects go like those of every failed upload. A JPEG or PNG above `file.image.max_pixels` is filtered without decoding, stays deliverable and gets no thumbnails. Attachments are unchanged. Place: `files/domain/purpose.go`, `files/app/scan.go`, `files/app/images.go`, 12 3.7. | `ImageUpload` admits JPEG, PNG and WebP, and the promise "without metadata" holds only for originals the server filtered or converted (12 7.1, the limit of the promise). |
| D-M3-10-7 | 2026-10-20 | `file.read` chooses its requirement by purpose: `attachment` keeps the read right on the path (M3-03); `avatar` and `branding` need only `auth`, so every active, signed-in principal that passes step 1 of 07 4.2 reads them (apps still need the scope `files:read`), and anonymous callers are answered `unauthenticated` in step 1 because `file.read` is not public; `gdpr_export` is never visible through `file.read` (`not_found`, its path is `gdpr.export.download`).
