# M2-41 Pairing, confirmation and re-pairing of hosts

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-M2-41-1 | 2026-10-15 | A pairing code is stored as HMAC-SHA-256 with the pepper of `auth.token_pepper_ref` over the full code string, the same derivation as `api_tokens.token_hash`; `identity.Tokens.HashHostPairingCode` parses form, checksum and kind `hpc` first and returns `identity.ErrTokenMalformed` before any HMAC. | One derivation for every token of ADR 0061; the prefix `bothy_hpc_` already separates the kinds, so no extra label is hashed. |
| D-M2-41-2 | 2026-10-15 | One issuer for `createHost`, `issueHostPairingCode` and the fallback of `confirmHost`: `app.Service.issueCode` over `PairingCodes.Issue` (bound to `identity.Tokens.NewHostPairingCode`). | D-M2-41-3 | 2026-10-15 | `pairHost` runs its write as the rights change `host.pair` (with the people of the valid assignments), although 05 gives `host.pair` Permissions `no`. | 03 counts `reported_session_users` as rights state (D-M2-40-9), so the rights version rises first. |
| D-M2-41-4 | 2026-10-15 | A redeemed code leaves `pairing_code_hash` and `pairing_expires_at` NULL. | The index on `pairing_expires_at` serves only `pairing`, and a used code must never match again. |
| D-M2-41-5 | 2026-10-15 | The key and report rules of `pairHost` with their `errors[].code` values: `invalid_key` (Noise key not strict base64url of 32 bytes or a low-order point; JWK `kty`, `crv` or `x` wrong), `unknown_member` (any JWK member besides `kty`, `crv`, `x`), `empty`, `duplicate`, `too_long`, `pattern_mismatch`, `limit_reached`, `invalid_format`, the textcheck rules for labels; every finding is returned, in body order. | The host service is untrusted input, and a host without session users can never give a terminal (HD1). |
| D-M2-41-6 | 2026-10-15 | Only a well-formed prefix (upper-cased, exactly `terminal.fingerprint_confirm_chars` characters of the Crockford alphabet) counts as an attempt; `I`, `L`, `O` and `U` are not mapped. | A typo of the form must not burn an attempt; the client may normalise before sending. |
| D-M2-41-7 | 2026-10-15 | `409 fingerprint_mismatch` of `confirmHost` keeps its effect under an `Idempotency-Key`: the handler calls `idempotency.KeepEffectOnFinal`, and the stage stores the answer with `Store.Complete` in the same unit and commits; only this answer is ever marked, a marked `401` or `5xx` still rolls back. | D-M2-41-8 | 2026-10-15 | `confirmHost` compares the prefix before anything of the body that needs the database (the people of `session_users`, the credential holder, the assignment rows); it writes one `confirm` audit entry that also carries the declaration, plus one `session_user` entry per assignment, all with the same correlation. A replay with the same key gets the stored answer and never burns a second attempt. | A wrong host must never reach an assignment or a declaration. |
| D-M2-41-9 | 2026-10-15 | The fallback after `terminal.fingerprint_max_attempts` failures: state `pairing`, the three key columns NULL, `key_fingerprint` kept, `pairing_code_hash` the HMAC of a fresh code that is never shown with `pairing_expires_at` now, `fingerprint_failures` 0, the next version, `host.updated` with `key_changed`. | 03 demands a hash exactly in `pairing`, and no code may work until the owner issues one. |
| D-M2-41-10 | 2026-10-15 | Dropping keys keeps `key_fingerprint`; `Host` and `host.updated` omit `key_fingerprint` and `noise_public_key` while the host has no keys; `pairHost` with the retained fingerprint is `409 conflict` `host_key_reused`, with the login key of another host `host_key_in_use`. | Refuses a re-sent key pair (T-TM-05). Honest limit: the server keeps no dropped key, so a host service that keeps one of its two keys is not detected; M2-42 generates both anew. |
| D-M2-41-11 | 2026-10-15 | The visibility of `host` adds: any principal when the requirement of the action is exactly `Public` (only `host.pair`). | The pairing code is the proof, checked by the use case before `authorize`, as for the refresh token. |
| D-M2-41-12 | 2026-10-15 | `key_changed` is set exactly when stored keys were dropped (re-pairing from `confirming`, `active` or `disabled`, and the fallback); `key_generation` rises only at `pairHost`. Audit details: `pairing_code` with `from_state`, `to_state`, `old_fingerprint`, `key_generation`, `sessions_ended`, `reason`; `confirm` with `result`, `fingerprint`, `key_generation`, `attempts_remaining`, `llm_credentials`, `credential_holder_id`, `declared_server_host`, `reason`; `host.pair` with `fingerprint`, `old_fingerprint`, `key_generation`, `platform`.
