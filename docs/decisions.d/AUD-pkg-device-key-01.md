# AUD-pkg-device-key-01 Registered device keys, the threads of the plugin and the Windows key store

Six findings of the audit of 2026-11-11 against `packages/device_key` and its callers
(`client-core-packages-3`, `-7`, `-12`, `-13`, `-14`, `-15`). The first is a fault a person runs
into: a device that lost a key of its registration got another key without a word and kept a
session the server refused for good.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-DK1/1 | 2026-11-12 | The app creates device keys only while no session is stored for the instance (`RegisteredDeviceKeys.forLogin` in `apps/client/lib/platform/device_key_signer.dart`), and writes their RFC 7638 thumbprints into the instance's secrets (`device_keys`: `dpop` and, for a device that has one, `step_up`). With a stored session `InstanceServices.open` only reads the key storage (`DeviceKeyStore.existing`, the plugin's `keyInfo`, which never creates a key) and compares (`ofSession`). A missing DPoP key, a missing recorded step-up key, another thumbprint than recorded and `key_invalidated` throw `DeviceKeyLost` before anything of the instance is open. The onboarding controller then ends the account on the device: the wiper of an unfinished wipe deletes the folder, the keys, the push and share items and every secret (R-SY-14; a failed step is remembered as after every sign-out), and E7 shows the new cause `SignOutCause.deviceKeyLost` with the text "The key of this device can no longer be used, for example because its screen lock or biometrics changed. Log in again to register this device anew, then remove its old entry under Devices." "Log in again" creates new keys, so the login registers a new device and the old registration stays for the person to revoke (08 5.4). The server is not asked at that end: without its keys the session cannot prove itself. | Audit finding client-core-packages-3: `ensure` ran at every start and created a missing key on iOS, macOS and Android, and nothing compared it with the registered one. The step-up item is `WhenPasscodeSetThisDeviceOnly`, so turning the device passcode off and on left a new key whose every confirmation counted as wrong until the server revoked the session (08 6.2); another DPoP key made every refresh answer `invalid_dpop_proof`, which the session rightly treats as temporary (08 7.3), so there was no sign-out and no hint. 08 5.4 and the README of the plugin promised the new registration; nothing built it. The record lies with the session because the keys are created in the same `open` that later logs in, so the recorded keys are the registered ones. |
| AUD-DK1/2 | 2026-11-12 | Only a definite answer counts as a loss. `keyInfo` returns null only when the storage holds no such key; a storage that cannot answer right now (a locked device, a locked keychain) throws `not_available` or `internal`. For the DPoP key that failure is an open failure as before (E1 with the keychain text, nothing deleted); for a recorded step-up key `not_available` means this run has no step-up key, as before this ticket, and the next start looks again. A device recorded without a step-up key (Windows, a Mac without a Secure Enclave in the login keychain, Android API 26 to 29 without biometrics) has none, whatever the storage holds, because a key the server does not know must not sign confirmations. A session of a build before the record keeps the keys the storage holds and gets its record at its next start, and so does a session whose record cannot be read; without its DPoP key it ends like any other. On Android the lookup itself is made definite: `KeyStore.getCertificate` answers null also when the Keystore failed, so `AndroidKeyStoreAccess.publicKey` asks `getKey` before it reports a missing key, which from API 31 answers null only for a missing key and throws for a failure. Not covered: Android API 26 to 30, where both calls answer a failed Keystore like a missing key; a session whose key was already replaced before the record existed (the record then names the wrong key, and the session fails as before, until the person logs out or the server revokes it), and the device entry of the server, which the app does not compare (`Device.key_thumbprint`, `Device.step_up_key_thumbprint`). | A wipe deletes what only the device holds (the outbox, the drafts), so a guess must never start one; the tests of the locked device hold that. The Android behavior is read from the platform source (`AndroidKeyStoreSpi.getKeyMetadata` and `engineGetKey` of the `keystore2` and of the Android 11 implementation, android.googlesource.com, retrieved 2026-11-12 [verified]); before this ticket the same null made `ensureKey` create a key over the registered one. The comparison with the server's device entry would also cover old sessions with a working DPoP key, but adds a second end of the account that depends on a network answer; the finding asks for the comparison at the start. |
| AUD-DK1/3 | 2026-11-12 | `key_invalidated` has two more places. A signature that answers it while the app runs (Android after a new fingerprint or face was enrolled: the Keystore keeps the key and refuses to sign; an enclave key bound to the biometrics of before; a key that vanished under a running app) ends the account like a key lost at the start: `InstanceServices` wraps both signers (`watchInvalidation`) and the controller listens (`deviceKeyLost`). Without a stored session `key_invalidated` from `ensure` (Windows: a marker whose key is gone) no longer stops on E1: nothing is registered with what is left, so it is deleted and new keys are created. | The finding: no code read `keyInvalidated`, and on Windows a cleared TPM left the app on E1 with the keychain text at every start, because the plugin never recreates a key whose marker exists and nothing deleted the marker. The error of the signature itself still reaches its caller; how the step-up flow words it is finding client-core-packages-2 of the `auth` package. |
| AUD-DK1/4 | 2026-11-12 | Every method of the Pigeon channel is `@async`, and no call works on the platform thread. iOS and macOS: `DeviceKeyQueues` of `DeviceKeyCore` runs `ensureKey`, `keyInfo`, `attestation` and `deleteKeys` on a serial queue in the order of the calls, DPoP signatures on a concurrent queue and step-up signatures on a serial queue of their own. Android: `DeviceKeyCalls` of `devicekeycore` runs the four key calls on one thread of its own; the DPoP signature stays on `Dispatchers.Default` and the step-up prompt starts on the main thread, as before. Windows: every call is a job of the plugin's one worker thread and answers through `PlatformThreadRunner`. | Audit findings client-core-packages-12 and client-core-packages-7: the four key calls were synchronous, so a StrongBox or TPM key was created on the thread that draws the app, although the same files moved `sign` off it for exactly that reason; and the Apple plugin signed both purposes on one serial queue, so every DPoP signature (requests, the refresh, the gateway) waited while a Touch ID or password prompt was open. The key calls keep one worker and their order, because that is how they ran before; only signatures are allowed side by side. `DeviceKeyQueuesTests.swift` holds a step-up signature back and signs a DPoP proof meanwhile; `DeviceKeyCallsTest.kt` holds a key generation back and checks that the call returned. The Windows glue has no unit test (it needs the Flutter headers); the Dart test that compares the plugin's overrides with the generated header covers the signatures. |
| AUD-DK1/5 | 2026-11-12 | Windows takes over a key under its name without a marker only when `NCRYPT_EXPORT_POLICY_PROPERTY` reads `0`, the policy the plugin sets before `NCryptFinalizeKey`. A key that allows export, or whose policy cannot be read, is deleted and counts as missing, in every call (`Ensure` then creates a new key; `Info`, `Sign` and `Attestation` find none). | Audit finding client-core-packages-14: the name is derivable from the app identity and the instance ID, so a process of the user could create an exportable key there before the registration, keep a copy, and the app would register it. Not covered, as before: a key imported from known material with policy `0`, and a process of the user that signs with the key in place; both need more than a property check. A key without a marker was never returned to Dart by the plugin, so replacing it loses no registration, with one exception that keeps working: a software key that followed a roaming profile without its marker has policy `0` and is taken over. |
| AUD-DK1/6 | 2026-11-12 | `DeviceKeyStore::Sign` keeps the opened provider and key of a name (`kept_`, guarded by a mutex) instead of reading the marker and opening both for every signature. `Delete` drops the kept key. A signature that fails with a kept key (any status but `NTE_USER_CANCELLED`) drops it and is tried once more with a fresh lookup, so a key lost behind the plugin still answers `key_invalidated` and a missing one `not_available`; a key that failed is never kept. `Ensure`, `Info` and `Attestation` always look the key up. The signature time on a TPM is not measured and no perf value is added. | Audit finding client-core-packages-13: every REST request needs a DPoP signature, and each one cost a `CredReadW`, an `NCryptOpenStorageProvider` and an `NCryptOpenKey` on the one worker. The retry keeps the answers of a store that keeps nothing, which `marker_without_key_is_invalidated` and the new tests hold. The measurement the finding also asks for needs a machine with a TPM: the CI runners have none (`tpm_path_when_available` skips there), so a named perf value would have no run that fills it. |
| AUD-DK1/7 | 2026-11-12 | Of the members the audit found without a caller: `DeviceKeyClient.keyInfo` and `DeviceKeySigner.thumbprint` now carry the comparison of AUD-DK1/1. `TokenState.refreshToken` of `packages/auth` is removed: nothing read it, the session reads the refresh token from the `SecretStore` for every refresh, and the field kept it in memory and handed it to the caller of a login (`LoginSignedIn.tokens`). The type `StepUpPrompt` of `device_key` (the texts of the Android prompt) is renamed `StepUpPromptTexts`; `StepUpPrompt` now names only the port of `auth` that asks the person. `DeviceKeyClient.attestation` and `jwkThumbprint` of `auth` stay. | Audit finding client-core-packages-15. `attestation` is a decided part of the interface (D-M5-01-2) for the planned requirement `auth.require_key_attestation` (08 6.1), and whether the app sends it at registration is finding client-core-packages-4 of the `auth` package. `jwkThumbprint` is what an implementation of `DeviceKeySigner` outside the plugin computes its thumbprint with (the software signers of the tests); `auth` may not depend on `device_key` (15 3.1), so the two packages cannot share one function. D-M5-01-7 and D-M4-18-0 name the old type name; they are records of their tickets and stay as written. |
| AUD-DK1/8 | 2026-11-12 | `package:device_key/testing.dart` (test support, rule 10 of 15 3.1) holds `FakeDeviceKeyHost`: the native side of the plugin in memory behind a real `DeviceKeyClient`. Calls travel through the generated channel code and its codec in both directions, errors as the stable codes, and the host loses keys the way the platforms do (an item the system deleted, another key under the name, a marker without its key, a key that no longer signs, a storage that cannot answer). The key material comes from the test, so the plugin gets no elliptic curve dependency. `apps/client/test/onboarding/device_key_lost_test.dart` runs the app on it: `PlatformDeviceKeyStore`, `InstanceServices.open`, the onboarding controller, the auth session and the engine against the fake server over HTTP, which binds a session to the thumbprint of its DPoP key. | The fix of AUD-DK1/1 lives between the plugin and the server, and the fakes the app tests had sat above the plugin's Dart half (`DeviceKeyStore`), so the mapping of `key_invalidated` and the difference between `ensure` and `keyInfo` were not on the tested path. Not on it either: the key stores of the platforms themselves, which the Swift, Kotlin and C++ tests of the plugin cover, and an app run with a real plugin, which the platform jobs have only for the login (`device_keys_windows_test.dart`). |
