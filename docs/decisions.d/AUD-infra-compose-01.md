# AUD-infra-compose-01 Virus scan choice of the wizard, push in the Compose stack, bundle upgrade

Work package of the audit of 2026-11-11 for `infra/compose` (`compose.yaml`, `install.sh`).
Findings: `docs-accuracy-1` and `docs-onboarding-2` (one cause, rulings 1 and 2),
`fn-push-notifications-5` (rulings 3 and 4), `infra-release-1` (ruling 5).

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-IC1/1 | 2026-11-12 | The virus scan of an installation is two lines of `.env` that go together: the profile `scan` in `COMPOSE_PROFILES` and the new Compose variable `BOTHY_SCAN_MODE`, which `x-server-env` of `compose.yaml` passes as `file.scan.mode` (fallback `required`, the default of the key; template value `required`). `install.sh` writes both from its one answer: on is the profile with `required`, off is no profile with `off`. With the scan off it says on standard error that uploads are delivered unscanned, and the help text and the prompt name it. The anchor of the smoke overlay and the copy in `test/compose.terminal-twonode.yaml` carry the same line, with no effect on those stacks (the fallback is the default of the key, and the demo and E2E overlays keep their own `off`). | With `--scan off`, which is also the default below 4 GiB of Docker memory, the wizard only left the profile out: `file.scan.mode` stayed `required`, no clamd answered, and every completed upload of such an installation stayed pending for good (12 5.3, fail closed). `compose.yaml` had no way to set the key, so the manual path had none either. One answer must not produce a stack that cannot work, and Compose cannot derive a value from a profile, so the wizard writes the second line. `tools/ci/tests/test_compose_smoke.py` holds the anchor of the smoke overlay equal to `x-server-env`, and `TestComposeTerminalOverlay` holds `api-2` equal to `api`; it failed without the copy. |
| AUD-IC1/2 | 2026-11-12 | The proof follows the real path: `TestInstallWithoutVirusScan` (`services/server/test/scan`) runs the real `install.sh`, rendered as a release ships it, against the real `.env.example`, renders the real `compose.yaml` with the `.env` it wrote through the Docker CLI (`docker compose config`), loads the environment of `api` and `worker` with the configuration loader of the server and, for the scan off, starts a server with the loaded scan mode and follows an upload to `skipped` and `complete`. For the scan on it requires the service `clamav` and the mode `required`. The only stand-ins are the stubs of the install tests for `docker`, `curl` and `cosign` while the wizard runs. The install tests (`test_scan_off_sets_scan_mode_off`, `test_scan_default_follows_memory`, `test_terminal_prompts`) hold what the wizard writes and says. | A test of the wizard alone would pass with a variable name that `compose.yaml` does not read, and a test of `compose.yaml` alone with a line the wizard never writes: only one test over both files and the loader sees the fault the finding describes. It failed on the commit before the change with the message that `api` runs with `file.scan.mode = "required"` while the stack has no clamav, and the two install cases failed with an empty `BOTHY_SCAN_MODE`. The wizard writes `.env` before it starts anything, so stubs in that step hide nothing of the path. |
| AUD-IC1/3 | 2026-11-12 | Push is switched on in `.env`: `BOTHY_PUSH_APNS_TEAM_ID`, `BOTHY_PUSH_APNS_KEY_ID` and `BOTHY_PUSH_APNS_TOPICS` for APNs, `BOTHY_PUSH_FCM_PROJECT_ID` for FCM, all empty in the template, passed by `x-server-env` to every server service. `compose.yaml` names the supplied file as `push.apns.private_key_ref` (`file:/run/bothy/secrets/apns_key.p8`), because that key has no default; the service account of FCM is the default of the server in the same directory. `docs/operations/install-compose.md` section 9 describes the steps and the check `bothy config check --secrets`. The wizard asks nothing about push. `TestComposePushPassthrough` (`services/server/internal/wire`) holds the lines of `compose.yaml` and `.env.example` and loads them: both providers off with the template, both on with the variables set, and a partial APNs set refused. | The guide named only the two key files. APNs is on with three keys and a key reference, FCM with one key, and `compose.yaml` passed none of them, so an operator had to find the variable names in the configuration reference and write an override file. With empty values the server behaves as before: no adapter is built and no key is read (D-M3-20-2, D-M3-21-2), and `check --secrets` skips both references. The key reference is no secret and has one sensible value in this stack, the place where `secrets-init` puts the file. Push needs keys of the operator's own Apple team and Firebase project (13 section 11), which a first installation rarely has, so a prompt would be asked of everyone for the few. |
| AUD-IC1/4 | 2026-11-12 | Not built here: the settings of the apps do not show that the instance has a push provider switched off (the reason `push_provider_disabled` of `registerPush`). | The finding names it as the second half of the same gap. It is a change of the app, not of the installation, and whether the settings show the push state is the product question already left to the owner with the audit finding `client-phone-background-3` (work package AUD-client-notifications-01). The operator's side is covered: section 9 of the guide says what the server answers while a provider is off and how to check the configuration. |
| AUD-IC1/5 | 2026-11-12 | Deferred: a step that upgrades an installation made from a bundle. Nothing is built; `docs/operations/upgrade.md` section 2.1 now says that the procedure replaces only the images, what stays behind and that neither `install.sh` nor the OpenTofu modules upgrade, and `install-compose.md` section 5.4 no longer promises the plugin of a new release through an upgrade. Question for the owner: shall the upgrade of a bundle installation be a mode of `install.sh` (one command, as the installation) or a documented manual procedure, and must it exist with the first product release or only before the second. | The facts of the finding hold on the current `main`: `install.sh` refuses a folder of another version on purpose (the comment at its marker check, test `test_other_version_in_the_folder_is_no_upgrade`), the guide sets only `BOTHY_VERSION`, the cloud modules ignore a changed `bothy_version` on an existing server and the SSH path ends in that refusal. The fix is a feature of its own, not a correction: verify the new bundle, replace its files including the ones a release removed (which needs a list of the installed files), add the new lines of `.env.example` to `.env`, set `BOTHY_VERSION`, move the marker and keep the way back, then tests for each of these, 16 section 3.1 rule 1 and section 10, the four OpenTofu modules and the path from one release to the next in the portability test, which needs two releases to exist. No release and no bundle exist yet, so no installation is affected today. |

Removing the entry changes the documented list of dropped keys (M1-73/3) and its test. |
