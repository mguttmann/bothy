# FIX-secure-store-migration The update into the app scope signs no one out

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-SSM/1 | 2026-10-31 | Amended by FIX-MMD/1 (docs/decisions.d/FIX-macos-migration-denied.md): by name the move reads only `app/server_address` and `app/update_notice_dismissed` of the app keys, never `app/instance`, and the session keys only under the origin of the remembered server address. `FlutterSecureBackend` never calls `readAll` on the macOS login keychain. There the app scope keeps the list of its keys in the item `app/secret_index` (written with every write and delete of the backend), and the secrets of a build before the scope are read by their names: the app keys `app/server_address`, `app/instance`, `app/update_notice_dismissed`, and per instance the keys of that build (`database_key`, `app_lock/enabled`, `push/apns_token`, `push/fcm_token`, `onboarding/pending_device`, `auth/<origin>/refresh_token`, `auth/<origin>/device_id`, the origins of the remembered server address and instance). The list is frozen with that build; a test pins it to the constants of the keys. The Data Protection keychain, iOS, Android and Windows keep `readAll`. The storage fakes of the tests answer `readAll` in the login keychain with -50 as the system does. | Live report of 2026-10-31: after the update of FIX-app-logout a macOS build that keeps its secrets in the login keychain (an ad-hoc signature, a debug or profile build) started on the connect screen although its device was active on the server. Reproduced with a Swift process on macOS: `SecItemCopyMatching` with `kSecMatchLimitAll` and `kSecReturnData` returns `errSecParam` (-50) in the login keychain, and `flutter_secure_storage_darwin` 0.4.3 builds `readAll` exactly so. The move of the old secrets therefore threw before the first call, every read of the store failed with it, and the start found no remembered server. The fakes of FIX-app-logout listed the login keychain, so its tests passed. `InstanceSecrets.isEmpty` and `deleteAll` (the device key scope, the wipe) needed the list as well. |
| FIX-SSM/2 | 2026-10-31 | Amended by FIX-MMD/3: an instance counts as moved only when the scope holds its session; until then the old values replace what an earlier move left, and the marker ends the move only while the scope holds a session. In the login keychain the remembered server belongs to the own instance with an old session under its origin (FIX-MMD/1). The old secrets are copied per instance and only for an instance without any secret in the scope yet ("no session in the new namespace"); a value already in the scope wins. In a shared store (the login keychain, Windows) only the instances with a folder under this app's data root (`InstanceServices.localInstances`) are copied, and the app keys only when the remembered instance (`app/instance`, its `instance_id`) is one of them; without such an instance the old store is not read at all. In an app-owned store (iOS, Android, the Data Protection keychain) every instance is the app's own. In a shared store the copy also records `device_key_scope` = `instance_id` for each copied instance, the scope of the old build's device keys, so the session keeps signing with its key (a Secure Enclave or TPM key cannot move). The marker `app/secret_scope` holds the app identity. Replaces the "app has any instance folder" rule of FIX-AL/2. | The brief requires that no app identity takes another's session: the instance folder under the app's own data root (its container on macOS) is the only proof of ownership an old item has, since a build before the scope wrote no identity marker. Recording the scope instead of deriving it from "the instance has secrets" makes the key choice independent of the order of writes. |
| FIX-SSM/3 | 2026-10-31 | The old items stay at the old place until the first successful refresh of their instance, that is the first write of that instance's refresh token into the scope (`app/legacy_pending` names them); then they are deleted, the old app keys with the last instance. A failed copy is logged (`secure_store`), does not fail the store, writes no marker and is tried again at the next start; the app then starts without the old session (enrollment, as before). A failed delete is logged and tried again at the next refresh. | A copy that is deleted at once loses the session when the copy turns out incomplete; after the first refresh the old refresh token is used up (rotation, 08 7.4), so keeping it longer would only leave a token behind that another build could send. |
| FIX-SSM/4 | 2026-10-31 | Not covered: a change of keychain between the builds (a build that used the login keychain updated by one that uses the Data Protection keychain, or the reverse) finds no old secrets and starts with enrollment; in the login keychain only the remembered server's origins are tried, so a second instance at another address signs in again; on Windows every branding of the runner shares the data root (FIX-AL/2). The data root itself did not change with FIX-app-logout (`getApplicationSupportDirectory`, `instances/<instance_id>`), so no data folder moves. | The keychains are separate stores with separate access rules, and a build of another kind is a new installation in practice; the other two cases sign in again through enrollment, the documented fallback. |
