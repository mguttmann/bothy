# FIX-android36-dds-start The Android phone suite runs as an instrumented test

| No | Date | Ruling | Reason |
|---|---|---|---|
| FADS/1 | 2026-11-02 | `apps/client/tool/run_android_tests.sh` runs the phone integration tests (`integration_test/phone_suite_test.dart`) as the instrumented test `PhoneSuiteTest` (`android/app/src/androidTest`, `@RunWith(FlutterTestRunner::class)` of the `integration_test` plugin) through Gradle `:app:connectedDebugAndroidTest` with `-Ptarget=<suite>` and `-Pandroid.testInstrumentationRunnerArguments.class=com.example.client.PhoneSuiteTest`, instead of `flutter test integration_test/phone_suite_test.dart -d <serial>`. The app reports the result of each Dart test to the runner, which reports it as a JUnit test; the host holds no connection to the VM service of the app (no `adb forward`, no Dart Development Service). The input methods stay disabled around the run as in FMR/2 and FMR/4. Every other instrumented run of the client names its classes or package or leaves `PhoneSuiteTest` out (`notClass`), because in a build of another entry point it would wait for results that never come. The suite creates its `IntegrationTestWidgetsFlutterBinding` in its own `main` before the first group, and the script fails when the report of the run lists fewer tests than the suite has groups (each group has a test), and prints the count otherwise. The iOS simulator keeps `flutter test`. | Second occurrence of the same class on main: run 41443318002 (commit 4c2c8d6f1) failed `apps (Android API 36)` in all three starts that FAPS/1 allows, after run 41308492022; PL/44 (run 40209199826) and PL/51 (run 40318886842) answered earlier ones. Not the DDS port (each attempt binds an ephemeral one and the first failure came after DDS had started), not a leftover process (the first attempt of a job fails as well), not memory (no `lowmemorykiller` line in the device logs). Why the host side ends the connection is not shown by any log of the runs, so FADS/2 prints it next time; the ruling removes the dependency on that connection instead of guessing at its cause.
