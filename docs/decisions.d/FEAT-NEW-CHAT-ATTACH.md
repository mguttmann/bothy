# FEAT-NEW-CHAT-ATTACH Files in a new chat before it exists

Owner request from daily use (2026-11-13): in a new chat (the composer of a chat that does not
exist yet, for example a new chat with an agent) the person could neither paste a screenshot nor
attach a file; the chat had to be created with text first. Wanted: paste or attach before typing,
with or without text, and the first message carries the files. Normative text: 01 6.8 item 8,
15 7.5 and 15 14. The line numbers name the files of `main` before this change.

| No | Date | Ruling | Reason |
|---|---|---|---|
| FNCA/1 | 2026-11-13 | Cause, in the client only. The composer of the new chat view was a bare `DsComposer` (`apps/client/lib/forum/new_chat_view.dart:456-473`): no `onAttach`, so no attachment button (`DsComposer` shows it only with `onAttach`, `packages/design_system/lib/src/components/ds_composer.dart:448`), no `AttachDropTarget` and no `AttachPasteShortcut` around it, so neither a drop nor Cmd+V or Ctrl+V of a file or an image did anything (the field takes only text), and no attachment menu on the phone. The composer of an existing chat has all of them (`apps/client/lib/composer/thread_composer.dart:335-348` drop area and paste key, `:792-798` the button, `:233-306` the phone's menu). The view followed D-M4-41-3 ("The first message of the view has no attachments, as the dialog had none"); its only files came from M4-47 (a long paste, the rest of a long text). The contract did not stand in the way: `createUpload` is `POST /channels/{channel_id}/uploads` with `file.upload` on the channel and the channel as the file's `scope_channel_id` (12 3.1), and `createThread` attaches files to its first message by `first_message.attachment_file_ids` when their scope channel is the forum (12 10 rule 1; server test `TestAttach_CreateThreadFirstMessage`). An upload needs the forum, never the thread. No server or contract change. | The owner's report, read at the code of `main` (409387007). The last sentence of D-M4-41-3 no longer holds; this ruling replaces it. |
| FNCA/2 | 2026-11-13 | Files of a new chat are staged in the composer and go with the send. The view's `AttachController` (`newPostAttachmentsProvider`) gets a staging folder, `<instance folder>/staged/<forum>/<key>/`: a file passes the checks of a thread's composer (count against `message_max_attachments`, size against `file_max_upload_bytes`, a readable file of at least one byte) and is copied there, and nothing is written to the outbox. The send moves the copies into `outgoing/<key>/` (D-M4-22-5) and writes one upload entry per file (its ID the attachment key) and the `createThread` that waits for them (`depends_on`, the attachment keys and slots of `MessageAttachments`) in one transaction, `Outbox.enqueueAll` of the sync engine. The uploads go one at a time in attach order in the forum's upload lane, the post after every upload is confirmed (D-M4-22-1, 12 3.8), offline after the reconnect. A long paste and the rest of a long text (M4-47) are staged the same way. The server's type check (`415`) stays where it is for every chat. | The variant that leaves nothing behind when the person drops the draft: nothing reaches the outbox or the server before the send. Uploading at once, as the composer of a thread does and as the view did for M4-47, leaves sessions and files that the server removes only after `file.upload_session_ttl` and `file.unattached_ttl` whenever a file is removed, the draft is dropped or the app quits, and upload entries without their post. Creating the chat at the first file is not needed by the contract and would leave a chat behind. The batch keeps the uploads and their post together through a crash. Price: the upload starts at the send, so a large file makes "Sending" longer than in a thread. |
| FNCA/3 | 2026-11-13 | Before the send. A file removed from the composer ("Remove", or "Insert as text" of a long paste) deletes its copy; nothing else exists. Leaving the view keeps the files while the app runs, as a thread's composer keeps its attachments (M4-22 Design note 2), and the next "+" shows them; an empty text draft is still deleted on leaving (01 6.8 item 8). A send that does not go keeps text and files and writes nothing: a forum without an operator agent needs a title also for a post of files only (the note "add a title" shows), a text over the limit whose rest cannot become a file is refused (D-M4-47-4), and a copy that cannot be moved puts the moved ones back. The app closing before the send: nothing is in the outbox or on the server; after the restart the text draft is back (04 14) and the files are not; the staged folder is emptied the first time a run uses it, before it stages anything, and the wipe deletes it with the instance folder. | The person's files are never half sent: before the send they exist only on the device, and a send is all or nothing. Keeping staged files across a restart would need a stored list of them; the thread's composer does not keep its attachments either. |
| FNCA/4 | 2026-11-13 | After the send. The post is created only after all its uploads were confirmed, so a chat never exists without its files ("an upload that fails after the chat was created" cannot happen). An upload that fails for good holds the post; it no longer reads "Sending" for ever: the sidebar row says "Not sent", the post list and the view of the sent post show the notice with the upload's reason, and the view shows the files with their state and "Upload again". "Try again" of such a post (and "Upload again" of a file) releases on the server the session the failed upload ended with and sends it again with a new entry and session (12 3.8 item 1). "Discard" removes the post, then every upload it waits for with its copy, and writes one `releaseUpload` entry per upload that may have something on the server (a kept session, a file ID in the post's slot of a confirmed upload, an attempt made or under way). `releaseUpload` (lane `upload:<forum>`, so after an attempt under way, whose file ID it then takes from the upload progress of the run) calls `deleteFile`, which aborts an open session and deletes a completed file that no message attached (12 12); every final answer ends it (`404` gone, `409 conflict` with `reason` `file_attached` when the post was created after all and its answer was lost, a refusal), only transient errors are tried again. A post the server refused after its uploads offers "Try again" and "Discard" as before; "Edit" is not offered for a post with files, because the uploads deleted their copies and the files cannot go back into the composer. The app closing after the send: the batch stays in the outbox, the uploads resume with their sessions and the post follows. The same applies to a new post shared from another app (M5-06). | Nothing is dropped silently (04 13.2 item 5) and no upload of a discarded post stays behind. Limit: a session announced by an attempt that was under way at the discard, whose answer had not reached the entry, stays until `file.upload_session_ttl` when the app quits before the release ran; the server's cleanup removes it. The composer of an existing chat is unchanged: a removed attachment, a discarded waiting message and "Upload again" there keep what they did. |
| FNCA/5 | 2026-11-13 | Platforms: the paths of an existing chat, through the same code (`apps/client/lib/composer/attach_actions.dart`, now used by both composers). Desktop (macOS, Windows): the attachment button opens the file dialog, files dropped on the composer and files or a bitmap pasted with Cmd+V or Ctrl+V are attached (a pasted bitmap goes as JPEG under the rule of FIX-scan-state-stale), with the drop hint while files are dragged. Phone (iOS, Android): the attachment menu with camera, photo library and file (the multi-select library of M5-16, the photo notices of M5-07); it has no templates entry, because the new chat view has no templates. Sharing from another app into a new post of a forum exists since M5-06 and is unchanged. Not built: a voice message as the first message and templates in the view, which existing chats have but which are not attaching a file. | Existing chats define the paths; no path is new to a platform. |
| FNCA/6 | 2026-11-13 | The agent gets the files exactly as in an existing chat. The first message carries their IDs in `first_message.attachment_file_ids`, and the server opens or holds the run of the first message through the same acceptance as every message (`services/server/internal/runs/app/accept.go:488`: `invokeOrHold` with `HasAttachments`, held until the files are final, 12 10). Proof in the client: `apps/client/test/forum/new_post_files_test.dart` sends a new chat and a message of an existing chat, each with two files and a mention of the agent, to the fake server, whose agent opens one run per message; both triggering messages carry their two files in order, and the fake checks every request and answer against the contract. | The server needs no change; what the client must prove is that the files are on the first message, which is the message the run starts from. |
