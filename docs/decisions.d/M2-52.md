# M2-52 Active threads in the snapshot and the project mark of a forum

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-M2-52-1 | 2026-10-28 | The active threads are one statement of chat (`ActiveThreads` in `queries/threads.sql`): a CTE of the pinned threads read through the primary key (`id = ANY`, open, kind `thread`, in the listed channels) and per listed channel a `LATERAL` read over `threads_channel_state_activity_idx` of the open threads with `last_activity_at >= now - sync.snapshot_thread_window`, `ORDER BY last_activity_at DESC, id DESC`, `LIMIT` the bound minus the pinned threads of that channel (never below zero), the pinned ids excluded; both parts carry the whole row and are joined with `UNION ALL`, ordered by the position of the channel in the snapshot, then by descending activity. On 32 000 seeded threads in eight forums the plan reads `threads` only by `threads_pkey` (bitmap) and `threads_channel_state_activity_idx` (index scan with an incremental sort for the id tie break); `TestActiveThreads_QueryPlan` holds it. | Design note 1; a first shape that read the ids of both parts and joined back to `threads` by id planned a hash join over a sequential scan of all threads. |
| D-M2-52-2 | 2026-10-28 | The pinned threads are the threads of `active_runs` and `unread_threads` of the same snapshot: the active runs come from the runs module through the existing `RunSummarySource` (the pipeline of `listActiveRuns`), the unread threads from the read state computation the snapshot already makes; sync passes their ids to chat. No second read state computation and no access to the tables of runs. | Design note 2; both reads agree by construction, and a thread whose run ended between the two reads is still correct by its activity. |
| D-M2-52-3 | 2026-10-28 | The port is `chat.ActiveThreads.ActiveThreads(ctx, a, ActiveThreadsQuery{ChannelIDs, PinnedIDs, Window, PerChannel})`, a port of its own beside `Threads` (as `ThreadsByParent`); chat measures the window from the clock of its service, and each thread passes `thread.read` in filter mode like the unread threads. The brief named `ActiveThreads(ctx, channelIDs, window, perChannel, now)`. | The implementations of `Threads` stay unchanged; the server time of the read is the clock the threads were written with. |
| D-M2-52-4 | 2026-10-28 | The window is inclusive (`last_activity_at` not older than the server time minus the window); threads of equal activity are ordered by descending id. | A deterministic order for equal times; 04 6.3 says "within". |
| D-M2-52-5 | 2026-10-28 | Only a created and a deleted binding raise `channels.version` (one step) and append `channel.updated`, after `channel.settings_changed` and `agent.config_changed` of the same unit, under the channel lock the binding use cases already hold; the payload carries the new `project_bound`, `version` and `settings_version`. A replaced binding, an identical PUT and a readiness report write none. | R-DM-54 and 05 `channel.updated`: only `project_bound` is a member of `Channel`; the binding values stay out of every event. |
| D-M2-52-6 | 2026-10-28 | The fake server of `sync_engine` fills `active_threads` with the same selection without a window (every open thread counts as recent) and the default bound; the fake gateways of the Python and TypeScript SDK list no channels and send an empty list. | The fakes validate every frame against the contract; the apps start to read the member in M4-40. |
| D-M2-52-7 | 2026-10-28 | `ready` and `getSnapshot` are compared in `TestGatewayDelivery` (one started api process for the delivery suite) rather than in a new process. | The package `internal/wire` is near its package timeout; a subtest of an existing world adds seconds, not a process start. |
