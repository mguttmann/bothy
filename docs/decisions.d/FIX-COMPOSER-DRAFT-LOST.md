# FIX-COMPOSER-DRAFT-LOST The text of a composer after a switch to another chat and back

Owner report from daily use (2026-11-13): text typed or pasted into the composer of a chat was
gone after a switch to another chat and back. The server stored the drafts (its log showed the
draft writes answered with `200`), so the loss was in the app. Normative text: 04 14 (addendum of
2026-11-13).

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-CDL/1 | 2026-11-13 | Cause. The server keeps one draft per person and thread (and one per person and forum for a new post) and deletes that row when the message is sent with `clear_draft` and when the draft is emptied (`putDraft` and `OnMessagePosted` in `services/server/internal/sync/app`); the next draft of the same thread is a new row with a new `id` whose `version` starts at 1. The device stored drafts by `id` alone (`upsertDraftIfNewer` in `packages/local_store/lib/src/daos/personal_dao.dart`), so a row the server had deleted stayed whenever the device did not take the delete, and the next draft was stored beside it. Two cases left such a row: (a) `draft.deleted` of the device's own send arrived while the person typed the next message and was not applied, by the typing rule of 04 14 (`_draftDeleted` in `packages/sync_engine/lib/src/appliers/personal_appliers.dart`); (b) the answer to an empty draft write, the empty final state of a deleted draft, was stored as a row (`storeDraftPutResult`, same file). With two rows of one thread the read of the composer (`watchDraft`, a read of exactly one row) failed, the draft provider gave an error, and a composer opened again got no draft and showed an empty field. Where only the old row was left (the next message was sent before its draft was stored), that row came back as the draft: an already sent text returned. | Reproduced with the app as it ships against the fake server, as the desktop app and as the phone app (`apps/client/test/composer/draft_switch_test.dart`): before the fix "the message typed after a send", "a text typed after the field was emptied", its new chat variant and "a sent text never comes back" failed with an empty field or with the sent text in it, on both. The server side was read in its code: the upsert of `services/server/internal/sync/adapters/postgres/queries/drafts.sql` inserts a new row with a new `id` and version 1 and raises the version of an existing one, and the deletes are held by `TestClearDraftSameTransaction`, `TestClearDraftForumPost` and `TestEmptyDraftPutDeletes`. The owner's devices were not read: the app writes no log of a failed read, and its database is encrypted on the device. |
| FIX-CDL/2 | 2026-11-13 | Not the cause. A switch right after typing loses nothing: every change of the field goes into the outbox at once (D-M4-20-2, no timer), and a composer opened again takes the text of the unconfirmed write from the outbox before any stored draft. The composer loads the stored draft when it opens. The draft is keyed by its thread, or by its forum for a new post, in every read and write of the app; no draft of one chat reached another. | The tests "a text typed in a chat is there after a switch", "a quick double switch keeps the text", "the text of a new chat is there after a switch" and "a text typed right before the app quits is there after the next start" passed before the fix. |
| FIX-CDL/3 | 2026-11-13 | The store keeps one draft per target (a thread, or the new post of a forum). `upsertDraftIfNewer` compares versions only under the same `id`; a stored row of the target with another `id` is the draft before and goes, unless it was written later by the server's `updated_at`: then the incoming draft is a late change of a draft that was replaced already and is not stored. `deleteDraft` removes the row of the deleted `id` and every row of its target that is not later. `watchDraft` gives the row written last instead of failing on several. | The server's rows of one target have different IDs over time and each starts at version 1, so only the server's time orders them. A late answer of an own draft write may arrive after a later event of another device. |
| FIX-CDL/4 | 2026-11-13 | The answer to an empty draft write stores no row: it is the empty final state of a draft the server deleted, and it ends the stored draft of its target up to the time of the answer (`storeDraftPutResult`); a draft another device wrote after it stays. No further end of the stored draft on the device's own send: once its `draft.deleted` was skipped because the person types, every change after the send writes the next draft, and that draft replaces the stored one by FIX-CDL/3. The only sequence that keeps the draft of a sent message is a next draft write that fails for good; nothing of the report points to one, and a draft write refused with `429` is retried without end (`packages/sync_engine/lib/src/outbox/classify.dart`). | 04 14: an empty draft is deleted. The minimum that fixes the loss; a device-side end of the draft on the own send would have been a second path for the same rule. |
| FIX-CDL/5 | 2026-11-13 | The typing rule of 04 14 and D-M4-14-7 stays: `draft.updated` and `draft.deleted` are still not applied while the person types in that draft here, and the snapshot path is unchanged. No change of the server, of the API or of what the device sends. | Core goal of the ticket: no change to the draft sync between devices. |
| FIX-CDL/6 | 2026-11-13 | Rows an earlier version of the app left need no migration: `watchDraft` shows the newest row of a target, and the next draft write, the next emptied draft or the next send in that chat removes the others. A chat whose only stored row is such a leftover shows that text once more; emptying the field or sending removes it for good. | The store cannot tell a leftover from a current draft without asking the server, and a migration that deleted the rows would lose current drafts (15 6.2: drafts are migrated without loss). |
| FIX-CDL/7 | 2026-11-13 | The fake server of `sync_engine` deletes the draft of a thread on an empty write and answers the empty final state, as the server does and as the fake already did for the draft of a new post. Before, it kept the row and its `id`, so no app test met a draft that comes back as a new row. | The fake must not drift from the server (brief M4-17 Design note 5, FIX-DCB/3). |
| FIX-CDL/8 | 2026-11-13 | A composer that was closed while it read the outbox for the stored draft or for an unconfirmed write sets no text (`ComposerController.applyStored` and `restoreUnsent`). | A quick double switch closed the composer during that read; a debug build then failed an assertion on the disposed text controller (`a quick double switch keeps the text` on the desktop, and a controller test). A release build ignored the write. |
