| D-M5-06-2 | 2026-10-25 | Items (Design note 2): `NSItemProvider` items are loaded as file representations and copied with coordinated reads (`NSFileCoordinator`) in chunks into `ShareStaging/<uuid>/` of the App Group, never read whole into memory; text and links become the comment; data-only items are written to a file in chunks. A photo as HEIC or HEIF is converted to JPEG with `CGImageSource` and `CGImageDestination` in bands of rows from an uncached source (orientation kept, every other metadata dropped); when the provider offers the system's JPEG representation, that is taken. Other images (JPEG, PNG, GIF, WebP) and all other files are sent unchanged, because the server strips their metadata losslessly (12 7.1, 15 14). Measured with the real loader in a fresh process (`ShareMemoryProbe`): converting an 8000 x 8000 HEIC peaks at about 64 MB of footprint on macOS 26 (the decoded image would be 244 MB) and at about 282 MB on the macOS 15 CI runner, whose HEIC decoder holds whole-image surfaces that count in the footprint but not in the resident memory (about 69 MB there); copying a 256 MB file peaks at about 3 MB. The test therefore asserts the resident growth and records the footprint; whether an extension on an older system or device stays inside its memory limit with such a photo is not proven. | Brief Design note 2; 15 12 (memory limit of the extension), 15 14, ADR 0047. |
| D-M5-06-3 | 2026-10-25 | Child session (08 7.4; Design note 3): the app calls `createExtensionSession` with `client_component = share_ext` after the login (the session's `SignedIn` event) and at every start and return to the foreground when the shared keychain holds no child whose refresh token is still valid; the child is one keychain item `<sha256 of the instance ID>.share_session` of the service `clientkit` in the shared access group (`AfterFirstUnlockThisDeviceOnly`, never synchronizable), a JSON object with the server address, the session ID, both tokens and their expiry, written whole so a refresh replaces everything at once. `ExtensionSession` in the extension uses the access token until 30 seconds before its expiry, then refreshes with the same `dpop` device key; a `401 token_expired` refreshes once; the refresh is single flight in the extension's process (an actor) and writes the new item before the new access token is used. A `401` on the refresh or a `401 session_revoked` deletes the item and the send goes to the inbox; the app creates a new child at its next start. The app never refreshes the child, and the extension never reads the app's tokens. Plain `http` is sent only to a loopback address (`127.0.0.1`, `::1`, `localhost`), where the fake server of the device tests runs; every other address must be `https`, and the extensions' `NSAllowsLocalNetworking` allows nothing else. | Brief Design note 3; 15 8 and 9; R-CL-07; ID-T16. |
| D-M5-06-4 | 2026-10-25 | Send and inbox (Design note 4): the extension makes the `client_msg_id` (UUIDv7) when Send is tapped, uploads each item (create with `Idempotency-Key`, parts read from a file handle at their offsets with `Content-Digest`, resumption by `getUpload` after a failed part, complete), then sends `createMessage` with the comment and the attachments, or `createThread` with `first_message` for a new post. Into the inbox go: no network, a timeout, every `5xx`, `429`, `409 request_in_progress`, a missing child, a refresh answered with `400` or `401`, and `401 session_revoked`. Every other `4xx` (for example `403` without write permission, `404`, `410`, `413`, `415`, `422`) is shown in the sheet with its reason and nothing is kept. An inbox entry is the folder `ShareInbox/<client_msg_id>/` of the App Group with the files under `files/` and `manifest.json` (version, `client_msg_id`, instance, target, comment, title, creation time, per file name, type, size and the ID of an upload that completed already; never a token), written in a hidden temporary folder with the manifest last and then renamed, so the app never reads half an entry. After a successful send the extension records the target in the recent targets and deletes its staged copies; it completes the request once the send or the inbox write is done. | Brief Design note 4; 04 13.2; 15 12. |
| D-M5-06-5 | 2026-10-25 | Takeover (Design note 5): at start and on every return to the foreground the app reads the complete inbox entries of the signed-in instance; entries of another instance stay until an end of an account clears the inbox (D-M5-06-7). Each entry goes through `ShareOutbox`, the same path as the Android sheet: files without a completed upload are copied into the outbox's own folder, upload entries get IDs derived from the `client_msg_id` and the message or post the `client_msg_id` itself, an existing entry is not written again, completed uploads are attached by their file ID; then the `share_inbox` row is written and the App Group folder deleted. A takeover that stopped half way therefore sends nothing twice when it runs again, and a replay the server answers with the original (`200`) completes the entry. The `share_inbox` row is deleted once its outbox entry is confirmed or discarded; a failed entry keeps it. `share_inbox` needed no new column: the target, comment and title are in its JSON payload. | Brief Design note 5; 15 6.1, 6.2, 7.5; 04 13.2. |
| D-M5-06-6 | 2026-10-25 | Android (Design note 6): a translucent `ShareActivity` (`noHistory`, `excludeFromRecents`) carries the filters for `ACTION_SEND` and `ACTION_SEND_MULTIPLE` with an explicit list of concrete MIME types (`ShareTypes.MIME_TYPES`: text, images including HEIC, HEIF and WebP, PDF and office documents, archives, audio and video; no `*/*`, no `type/*`, no `application/octet-stream`) and hands the intent with its read grants to the running `MainActivity` (`CLEAR_TOP`, `SINGLE_TOP`), so one Flutter engine shows the route `/share`; a filter on `MainActivity` would start a second instance in the sending app's task. Android also matches a wildcard intent type (`image/*` from a gallery) against concrete filters, so such an intent still reaches the activity; each item's own type then decides. After the outbox took the files into its own folder the app deletes the cache copies. | Brief Design note 6 and fixed requirement 17; 15 12. |
| D-M5-06-7 | 2026-10-25 | Recent targets (Design note 7): the app derives the last `client.share.recent_targets` targets from the person's own messages in its database (newest first, one per thread, only writable channels, from any send path including other devices and the extension) and writes them as `{kind, channel_id, thread_id, path}` to the App Group at start, after every confirmed send and whenever the stored channels change (`access.changed` that removes a level removes the target); a thread the database lacks is loaded once with `getThread`.
