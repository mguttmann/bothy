# AUD-host-01 Install over a running installation, the log of the host service, the peer check limit

Work package of the audit of 2026-11-11 for the host service (`services/host/internal/install`,
`services/host/internal/buildinfo`). Findings: `fn-terminal-hosts-5` and `host-service-5` (one
cause, ruling 1), `errors-observability-6` (rulings 2 and 3), `fn-terminal-hosts-1` (ruling 4).

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-HOST-01/1 | 2026-11-11 | On macOS every plan that loads a service (`install`, `install --owner-account`, `session-user add`) waits between `launchctl bootout` and `launchctl bootstrap` until `launchctl print` no longer knows the label. The new step kind `until-gone` runs its command again, with a pause, until it fails; after the bound of the executor (the time the Windows executor gives a service to stop) it ends the command with `the service did not unload`, and no later step runs. | `bootout` returns while launchd still ends the job (state `SIGTERMed`); `print` knows the label for that time, and a `bootstrap` of it fails with exit code 5 (`Input/output error`). `install` stopped there, the service stayed unloaded and the terminal was off until someone repeated the `bootstrap` by hand. Measured against launchd of macOS 26 with a scratch job that needs a moment to end after SIGTERM: a `bootstrap` right after the first failed `print` loads the job (`TestReloadOverARunningLaunchdJob`, run on request with `-launchd`). Waiting for the exact condition was preferred to repeating `bootstrap`, because a `bootstrap` that fails for another reason still fails at once. The LaunchDaemon plan uses the same steps; for the system domain they are covered by the test with the model of launchd (`TestInstallOverARunningService`), not by a run with administrator rights. |
| AUD-HOST-01/2 | 2026-11-11 | On macOS and Windows `bothy-host run` writes every log line also to `bothy-host.log` in the state directory (mode `0600`). A line that would grow the file past `logFileMax` first moves it to `bothy-host.log.1`, replacing that file, and starts a new one; a line is never split. Linux gets no file. When the file cannot be opened the service logs `log file unavailable` and runs on with standard error alone. | launchd drops the standard error of a job that names no `StandardErrorPath`, and a Windows service has no standard error, so the log of the host service was lost on both systems and a failed opening could not be traced to a step; systemd keeps the lines in the journal. A file the service writes itself has a bound, needs no second mechanism for Windows and lies in the one folder that only the service user and administrators read (the owner account in its mode). `StandardErrorPath` was not used: launchd never rotates such a file, and for the LaunchDaemon it would be a file outside the state directory whose owner and mode launchd decides. The bound is a constant of the program, a limit of a diagnostic file and not a product window. |
| AUD-HOST-01/3 | 2026-11-11 | The file holds the lines of the host service from the moment the configuration is read. The line `config_invalid` before that and the lines of a PTY helper (its start failures, `pty not started`) go to standard error only. `doctor` does not print the place of the log; README and 16 4.4 name it. | Without a configuration there is no state directory to write to. A PTY helper runs as its session user, who must not write into the state directory (HD8), and its failures already reach the host service as the code of the session end. `doctor` prints codes and names, never a path (24 2.2), and the place is fixed per platform. |
| AUD-HOST-01/4 | 2026-11-11 | The list of platforms with a proven peer check stays empty. The "Known limits" of the root README, `services/host/README.md` and 16 4.4 now say that a release build therefore gives a terminal only in the owner account mode; `TestKnownLimitNamesThePeerCheck` holds the README text against the list. | D-M2-42-11 and D-M2-42-19 allow a platform on the list only with a recorded platform run (RK-23: no terminal without proof), and this ticket has no such run. The audit found the rule documented but the state missing where a reader looks first. |
