# AUD-srv-runs-01 Run findings of the audit of 2026-11-11

Work package of the audit of 2026-11-11 for the runs module of the server, findings
`srv-runs-core-1`, `privacy-2`, `srv-runs-core-2`, `srv-runs-app-1`, `data-layer-5` and
`fn-agents-runs-12`.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-RUN1/1 | 2026-11-12 | The two texts of an adapter that every `run.state_changed` carries get a named length: `run.status_line_max_chars` for `status_line` (a patch and `awaitRunInput`) and `run.summary_max_chars` for the `summary` of `finishRun`, both in 03 section 9. A longer text keeps its first runes (`domain.CutText`); it is not refused with `400`, as the audit proposed. The cut value is what the server stores, answers and sends in the normalized ops. The schemas of the API are unchanged. | `srv-runs-core-1`: a status line above `sync.event_payload_max_bytes` was stored whole, and from then on every state change of the run failed, because the appender refuses the oversized `run.state_changed`: `finishRun`, `awaitRunInput`, `runs.cancel_timeout`, `runs.stall_check` and `agent.disable` answered `internal_error` and the thread stayed busy. Agent output is cut everywhere else (09 5.3: the excerpt, a step detail), a refusal would fail a whole patch or keep a run from ending because of its summary, and adapters send these texts without knowing a limit. The start is kept because both texts are read from their first word. |
| AUD-RUN1/2 | 2026-11-12 | `run.state_changed` follows payload rule 2 of 04 section 2.2: the whole summary while its payload is smaller than `sync.event_payload_max_bytes`, otherwise the payload without `status_line` and `summary` and with `truncated` in the envelope (`runs/app.stateChangedPayload`); `getRun` returns the texts. A reduced payload that does not fit either stays an internal error. The schema `RunStateChangedPayload` is unchanged, both members were optional. | The limits of AUD-RUN1/1 bound new writes only. A row that holds a longer status line from before the limits is exactly the run this finding left unendable, so it must be able to end, and a lower `sync.event_payload_max_bytes` must not bring the failure back. Open minor, outside this module: the sync engine of the app reloads a truncated event only for the resources message, thread, channel and space; a truncated `run.state_changed` is logged and skipped, so the device shows the new state with its next read of the run. The next run in the sync engine adds the read for the resource `run`. |
| AUD-RUN1/3 | 2026-11-12 | Not built for `srv-runs-core-1`: lengths for `model`, the plan, step names and titles and `last_api_retry.error`, and a `runs.stall_check` that goes on after the failure of one run. | Only `status_line` and `summary` travel in a durable event. The other texts are in the run document and in `run.updated`, which already goes out without ops and with `truncated` above the limit (`app.updatedPayload`), and the body limit of the request bounds them. With AUD-RUN1/1 and AUD-RUN1/2 no run fails a state change because of a text, so the check has no run of this kind to step over; another error of one run still retries the job, as its contract says. |
| AUD-RUN1/4 | 2026-11-12 | `privacy-2` and `srv-runs-core-2` (one cause) are confirmed and deferred: no path clears the texts of a run. `runs.status_line`, `last_text_excerpt`, `summary` and `plan`, the titles and details of `run_steps` and the label, condition and result of `run_wakes` stay after the purge of a deleted chat, after a content period, after the deletion of the answer message and after an account deletion in the mode `delete`. 20 4.2a now says so; before, 20 named only the event payloads and the drafts as left over. | The fix is a deletion rule for run texts, which D-M7-05-7 left to the planning, and it needs the owner: which members count as content (also `model`, step names, `last_api_retry.error`), when they go (with the purge, with `retention.content` and from which time of the run, with the answer message, with the account), and what a reader and a stored event show afterwards (a tombstone of the run in `getRun` and the lists, an event for devices that hold the texts, the redaction of stored `run.state_changed` payloads). Size: a migration with a marker and an index for the job, a participant of the class `content` in runs, a step of `messaging.purge_deleted` towards runs, a hook on the message deletion, the erasure step of runs, the chapters 03, 04, 09 and 20 and the tests DP-T01, DP-T02 and DP-T05; a ticket of its own, with parts in messaging and the app. Today a run of a deleted chat answers `404`, so only the texts of runs in live chats are readable. |
| AUD-RUN1/5 | 2026-11-12 | `srv-runs-app-1` is confirmed and deferred: one `Service` carries every responsibility of the module, and `New` requires only a part of its collaborators. The counts of the finding hold on the tree of this ruling. | Cutting the service into part services with required collaborators is a redesign of the module and of every test world that builds it, far larger than this package. No wrong behaviour is reproduced: the wiring of the server sets every collaborator, a missing one answers `internal_error`, and the integration world builds the real wiring. One service per module is the style of the other modules too. Size: one ticket per responsibility (triggers, lifecycle, delivery and tokens, follow-ups, wake-ups, reads), each replacing the nil paths of its part by fakes in the test worlds. |
| AUD-RUN1/6 | 2026-11-12 | `data-layer-5` is real as described and changes nothing: the run history and the statistics read the threads of the visible channels and pass them to the queries of runs. | A recorded decision: `runs` has no `channel_id`, because the copy would go stale when a thread moves (D-M2-05-9, taken up by D-M6-05-7). No measurement shows a cost; a channel copy is a migration, the maintenance on every move and a change of the visibility rule of 07 7.4. |
| AUD-RUN1/7 | 2026-11-12 | `fn-agents-runs-12` is real as described and changes nothing: `getRunContext` of a run whose `trigger_kind` is not `message` answers `internal_error`, and the reference adapters refuse the triggers they do not serve. | A recorded decision: the context is defined for a triggering message only and fails closed for every other trigger until its context is defined (D-M2-13-12, 09 4.6); the Hermes adapter does not read the context of a command run (09 17), and the runner ends another trigger with the cause `trigger_kind_unsupported`. A context for commands, interactions and wake-ups, or a card that starts no run at an adapter without interactions, is a new part of the contract (`run_context.v1`, a capability of the adapter), not a fix in this module. |
