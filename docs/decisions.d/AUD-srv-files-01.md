# AUD-srv-files-01 Memory rules of the pixel guard and body limits of the S3 driver

Work package of the audit of 2026-11-11 for the files module, findings srv-files-adapters-1,
srv-files-adapters-2 and srv-files-adapters-4.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-SF01/1 | 2026-11-11 | The pixel guard also refuses an image with an edge longer than 65535 pixels (`domain.MaxImageEdge`, `domain.ExceedsEdgeLimit`, checked in `checkPixels` of `adapters/imaging`). The refusal is `ErrTooManyPixels` with the log class `too_many_pixels`, so such an image is treated exactly like one above `file.image.max_pixels`: a JPEG or PNG is still cleaned and gets no thumbnails, a still WebP stays unchanged (12 7.2). The limit is a constant, not a configuration key. Amends D-M3-06-5. | `file.image.max_pixels` bounds width times height, but `draw.CatmullRom.Scale` of `golang.org/x/image` builds weight tables with about four entries per source pixel of each edge and an intermediate buffer of destination width times source height. A PNG of one pixel by many millions of pixels passed the limit with a small file and made every variant ask for gigabytes; the worker has no memory limit and River retried the job. With the edge bounded, the tables are bounded by the edge limit, and the intermediate buffer by the variant edge times the shorter edge of the source (or by the longer edge alone when the variant is one pixel wide), which the pixel limit and the edge limit bound together. 65535 is the longest edge a JPEG or a GIF can store and above what `x/image/webp` decodes, so in practice only a PNG exceeds it, and no operator has a reason to raise it: the file is still stored, cleaned and downloadable. Tests: `TestExceedsEdgeLimit`, `TestPixelGuardDoesNotDecode` (cases `png tall`, `png wide`), `TestLongEdgeGetsNoThumbnails` (real decoder and scaler), `TestImages/ImageGuardedBelowPixelLimit` (server). |
| AUD-SF01/2 | 2026-11-11 | A GIF that is re-encoded counts every frame with the pixels of the logical screen plus `gifFrameOverhead` (`checkGIFFrames` in `adapters/imaging`): the bytes of the largest palette as `image/gif` keeps it and of the frame record, counted as that many paletted pixels; the constant carries its derivation. Above `file.image.max_pixels` the GIF is not decoded and stays unchanged as revision 1, as before. The guard of the thumbnails is unchanged: `gif.Decode` keeps only the first frame, and only a re-encoded GIF gets thumbnails. No separate frame limit and no bound of the output against the input. Amends D-M3-06-5. | `gif.DecodeAll` keeps a palette per frame as soon as the frame has a transparency index (a copy of the global table, enlarged to the index when the index lies outside it) or a local colour table, and `gif.EncodeAll` then writes a local colour table per frame. A screen of one pixel admitted as many frames as the limit has pixels, at a few bytes of file each: the decoded frames held a multiple of the upload in heap, and the stored object was a multiple of the upload as well. With the overhead the decoded frames need at most about one byte per pixel of the limit, and the output grows by at most one colour table per admitted frame, which the same count bounds. One knob stays: an operator who raises `file.image.max_pixels` raises both. A frame limit would be a second arbitrary number, and a GIF whose re-encoding is larger than the upload must still be re-encoded, because only that removes its comments and application blocks (12 7.1); a converted WebP can be larger than its upload as well, and the stored size counts against the quota of the uploader (`files.size_bytes` describes the stored object). Tests: `TestGIFTinyFramesNotDecoded` (real decoder, allocation bound), `TestGIFFrameOverheadBoundary`, `TestGIFCleanOriginal`, `TestImages/ImageGuardedBelowPixelLimit` (server). |
| AUD-SF01/3 | 2026-11-11 | The S3 driver bounds every answer body itself (`answerBodies` around the HTTP client of the egress client, whose own body limit is lifted): the body of a successful `GetObject` is as long as the storage announces (`Content-Length`, which `net/http` enforces) and has no other limit; an object answer without a length is a storage failure with the detail `no length in the answer`; every other body (an error document, the result of a multipart call) is at most `egress.max_response_bytes` and fails above it with `egress.ErrResponseTooLarge`. `s3.Deps.MaxObjectBytes` is removed and `wire.FilesObjectStore` no longer passes `file.max_upload_bytes`. Amends M3-02/1 and M3-02/14. | M3-02/1 assumed that no stored object is larger than `file.max_upload_bytes`. That is wrong: an export package (20 5.2) is written through the same store without a size limit, a still WebP converted to PNG and a re-encoded GIF can be larger than their upload, and the key may be lowered after objects were stored. Every such object failed on `Get` with `response too large` on the driver `s3`, while the driver `fs` has no such limit. The length the storage announces is the stored size and so the right bound of one read, and `http.transfer_timeout` still bounds its time. The other answers stay bounded because the SDK reads an error document into memory completely; the general egress limit fits them, and `file.max_upload_bytes` never described them. The S3 interface returns `Content-Length` for `GetObject`; an answer without it is refused, because an unbounded body would break 19 SEC-NET-5. Tests: `TestS3ReadsObjectAboveBodyLimit` (SeaweedFS, whole and by range), `TestWireS3ReadsObjectAboveMaxUploadBytes`, `TestObjectBodyIsNotCapped`, `TestOtherAnswersAreCapped`, `TestObjectWithoutLengthRefused`. |
| AUD-SF01/4 | 2026-11-11 | Not built in this package: a memory limit for the worker container of the Compose stack, a configuration key for the longest edge, and writing export packages by multipart upload. Carried over to the status module: the object mirror of the backup service (`internal/status/adapters/s3mirror`) still passes `file.max_upload_bytes` as the body limit of its reads, as the files driver did before AUD-SF01/3 (read in the code, not run). | The rulings above bound the memory of an image job by `file.image.max_pixels` again, which is what the limit promises; a container limit is a sizing decision of the operator and belongs to the deployment files. A key for the edge would have no use (AUD-SF01/1). An export package is one `PutObject`, which core S3 accepts far beyond `file.max_upload_bytes`; the finding was the read limit, and no failing write is known. |
