| D-M4-10-1 | 2026-10-15 | `device_key` is one Flutter plugin package with a folder per platform and a Pigeon interface (`DeviceKeyHostApi`: `ensureKey`, `keyInfo`, `sign` (async), `attestation`, `deleteKeys`), not a set of federated packages. Errors cross the channel only as the codes `user_cancelled`, `key_invalidated`, `not_available` and `internal` with a fixed text; the Dart side keeps only the code, and a platform without the plugin (Pigeon's `channel-error`, or `MissingPluginException`) reports `not_available`. A missing key on `sign` or `attestation` is `not_available`; an enclave key the Secure Enclave no longer accepts is `key_invalidated`: the enclave loads any blob and rejects it only when it signs, with CryptoTokenKit `corruptedData` or `objectNotFound` (canceledByUser is `user_cancelled`), and a blob that no longer yields the registered public key counts the same (red team M4-10). Which code a real biometrics change produces is not measured on a device with Touch ID. | 15 3 names one member `device_key`; the Pigeon interface is the boundary federation asks for. Fixed texts keep key material and server addresses out of logs. |
| D-M4-10-2 | 2026-10-15 | The public JWK (`crv`, `kty`, `x`, `y`, base64url without padding) and the RFC 7638 thumbprint are computed in Dart from the coordinates the native side returns; the native side returns signatures as `R \|\| S` (CryptoKit's `rawRepresentation`, so no DER conversion is needed), and the Dart side rejects any other length. | One implementation for every platform (M4-11, M5-01 reuse it). |
| D-M4-10-3 | 2026-10-15 | Access control: `dpop` with `[.privateKeyUsage]` and `AfterFirstUnlockThisDeviceOnly`; `step_up` with `[.privateKeyUsage, .biometryCurrentSet]` when biometrics are enrolled, otherwise `[.privateKeyUsage, .userPresence]`, and `WhenPasscodeSetThisDeviceOnly` on iOS and macOS (the Data Protection keychain knows the same class). Without an enclave the software key's keychain item carries `.userPresence` for `step_up`, with the same accessibility classes, and `hardwareBound` is false. Biometrics count as enrolled unless the device has no sensor or reports `biometryNotEnrolled`, so a key created while the lid is closed or the sensor is locked out is still bound to them (code review M4-10). 15 9 is updated to this. | 08 6.1 requires invalidation on new biometrics, while a Mac without Touch ID must still confirm with the device password (brief note 3). |
