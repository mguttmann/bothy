| D-M4-11-1 | 2026-10-15 | Provider choice per key at creation, never migrated: a new `dpop` key goes to `MS_PLATFORM_CRYPTO_PROVIDER` when it opens and `NCryptIsAlgSupported(BCRYPT_ECDSA_P256_ALGORITHM)` succeeds, otherwise to `MS_KEY_STORAGE_PROVIDER` with `hardwareBound = false`. A marker (generic credential in the user's Credential Manager, `CRED_PERSIST_LOCAL_MACHINE`, target name = key name, blob `platform` or `software`) records the provider; a key is opened only there. Without a marker (a stop between `NCryptFinalizeKey` and writing it) an existing key is looked up in the platform provider, then the software provider, used where it is and the marker written. A marker without an openable key (`NTE_BAD_KEYSET`, `NTE_NO_KEY`, `NTE_NOT_FOUND`) is `key_invalidated` and nothing is recreated; a marker whose provider no longer opens is `not_available`. Keys are per user (no `NCRYPT_MACHINE_KEY_FLAG`), ECDSA P-256, export policy `0` set before `NCryptFinalizeKey`. | A key moved between providers would change the JWK and need a new device (08 5.4); the marker is how the plugin tells "not created yet" from "lost" (brief note 4). Which status a real TPM clear produces is not measured. |
| D-M4-11-2 | 2026-10-15 | No step-up key on Windows: `Ensure(step_up)` fails with `not_available`, and the plugin never offers a key whose confirmation only the plugin enforces. The DPoP key signs with `NCRYPT_SILENT_FLAG`. Sources, retrieved 2026-10-15: strong key protection (`NCRYPT_UI_FORCE_HIGH_PROTECTION_FLAG`) prompts for a password whose "exact behavior is specified by the KSP" (learn.microsoft.com, `X509PrivateKeyProtection`); the Microsoft KSPs accept that password from the process through `NCRYPT_PIN_PROPERTY` and "cache this value so that the user is only prompted once per process" (Key Storage Property Identifiers); a Microsoft answer on per-use reauthentication for Platform Crypto Provider keys names only a PIN or a custom KSP (Microsoft Q&A 1076208); Windows Hello keys (`KeyCredentialManager`) are RSA and sign with SHA-256 and PKCS #1 (Windows Hello for apps). Not checked on a Windows host: no Windows machine was reachable. Recommendation (08 6.1): a Windows Hello `RS256` step-up key needs `RS256` or `PS256` in 03 `device_keys.alg` and in the JOSE profile of ADR 0067, a core contract change; until then the step-up of a Windows client uses the other methods of 08 6. | 08 6.1: the confirmation must come from the person, not from code in the process; a password the process can set or that is cached per process does not meet that, and `ES256` is the only algorithm of the contract (R-CL-04). |
