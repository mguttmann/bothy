# RED-RUNS-1128 Red runs of main up to 2026-11-27: job limits and a race of an SDK test

The red-run issues of `ci.yml`, `advisories.yml`, `hermes-pin.yml`, `red-runs.yml` and
`e2e-mobile.yml` were read run by run (the logs of every failed job). This ticket changes what
comes from the repository; the rest has an outside cause and is listed in RED-RUNS-1128/3.

| No | Date | Ruling | Reason |
|---|---|---|---|
| RED-RUNS-1128/1 | 2026-11-28 | The time limits of four jobs of `ci.yml` and `build-verify.yml` rise to about one and a half times their longest passing run (PL/6): `test (apps)` from 60 to 90 minutes, `test (SDKs and plugins)` from 75 to 110, `apps (macOS)` from 75 to 105, `apps (iOS)` from 90 to 120. Both copies stay equal (AUD-CG1/2). | Each of the four was cancelled at its limit on `main` after its tests had passed or while they still ran: `test (apps)` in run 45667091036 (upload of the coverage after 60 minutes), `test (SDKs and plugins)` in run 46054354782 (every test passed, cancelled in the cache step after 75 minutes), `apps (macOS)` in run 45455957036 (75 minutes in `make apps-platform`), `apps (iOS)` in run 45829774544 (every entry passed, cancelled in the cache step after 90 minutes). Passing runs of the last 25 to 40 CI runs (pull requests and `main`) took 36 to 59 minutes for `test (apps)`, 63 to 73 for `test (SDKs and plugins)`, 47 to 70 for `apps (macOS)` and 42 to 74 for `apps (iOS)`, so the old limits left 1 to 16 minutes. A cancelled job leaves `ci-ok` red without a finding. The runners are the free GitHub-hosted ones; a higher limit only lets a hung job run longer. `ci-ok` starts after the jobs it needs, and the 240 minutes of `test (server contract)` stay the longest limit of the run. Not covered: nothing warns when a job creeps towards its new limit; the next creep shows up again as a red run (docs/backlog/RED-RUNS-minors.md). |
| RED-RUNS-1128/2 | 2026-11-28 | The test `keeps running and leaves the cancel unsettled when the end of a waiting run got no answer` (`sdk/typescript/test/loop.test.ts`) sends the cancel only after the handler work of the run returned (the task of the run in the adapter is done), and its handler returns 50 ms after `awaitInput`, so the old order fails every time. The SDK does not change. | Main run 45496359780 failed the test with `expected 1 to be greater than 1` (one `run.cancel_requested`, no redelivery). The test waited for the server state `waiting_input`, which the server sets while `awaitInput` is still on its way back to the handler. A cancel that arrives before the handler returned aborts the running work (`Adapter.onCancel`), and the adapter then sends the lost end again itself (`resendEnd`) and acknowledges the cancel, so the redelivery the test counts never comes. Both paths end the run `cancelled` and keep the adapter running. With the handler delayed by 200 ms the old test failed with the same message locally; with the wait for the task it passes. |
