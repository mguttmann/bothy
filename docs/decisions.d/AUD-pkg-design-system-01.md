# AUD-pkg-design-system-01 Font weight, control outline and test dependencies of the design system

Five findings of the audit of 2026-11-11 against `packages/design_system` (`design-system-1`,
`design-system-2`, `design-system-3`, `design-system-5` and `a11y-9`). Two are faults a person
sees: bold set on a text style of the design system never reached the font, and Material drew the
edges of its controls in the color of decorative borders. Two say the same about the test
levels: the platform goldens and the measured text contrast run in no CI job, while the
specification read as if they did. One concerns the dependencies: the golden test library was a
dependency of every app. Normative text: 01 section 8 (contrast), 15 section 20 (test levels),
`docs/design/typography.md` "Integration", the package README.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-DS1/1 | 2026-11-11 | `dsTextStyle` sets no font variation. The weight of a text is its `fontWeight` and nothing else: a role keeps the weight of its token, and a caller changes it the usual way (`copyWith(fontWeight: ...)`, a `Text` with a bold style below the theme). No library code of the apps and packages sets `FontVariation.weight` (searched on 2026-11-11); only the test of this ruling sets it by hand, as its reference. This replaces "sets the `wght` axis from the weight" of D-M4-04-3. No helper for a change of weight and no ban of `copyWith(fontWeight:)` is added. | The engine of the pinned Flutter sets the `wght` axis of a variable font from `fontWeight` unless the style carries a `wght` variation, which then wins over every `fontWeight` (documented at `FontVariation.weight` in `dart:ui`; the paragraph builder of the engine and both web renderers follow it). `dsTextStyle` fixed the axis at the weight of the role, so the places that set a weight afterwards (the unread title of a thread row, the unread name of a channel row, of a sidebar thread row and of "All posts", Markdown bold and a mention) and every bold `Text` below the theme were drawn at the weight of the role; in the thread row bold is the only visible mark of an unread entry. Without the variation the usual way works, so a helper or a ban would guard a state that no longer exists. |
| AUD-DS1/2 | 2026-11-11 | `ColorScheme.outline` is `color.border.control`; `outlineVariant` and `dividerColor` stay `color.border.subtle`. This replaces "outline `color.border.default`" of D-M4-04-3. The theme gets no component themes for switch, checkbox, chip, segmented button or input decoration for this. | Material 3 draws with `outline` the edges that identify a control: the ring and the thumb of a switch that is off, the underline or the border of every text field that is not filled (also of `DropdownMenu`), and the border of a segmented button, of an outlined icon button and of the day period control of the time picker. `color.border.default` is the border of columns and cards and no pair of the contrast rules; on the canvas and on the overlay surface it stood far below the 3:1 that 01 section 8 and WCAG 1.4.11 ask for, in both themes (the test of this ticket measured it on the rendered widgets before the change). `color.border.control` is the token for the border of input fields, and `design/design-rules.json` declares it with 3:1 on canvas, list, raised and overlay. With the role right, the defaults of Material draw every such control with it, so component themes would repeat the same color once per control. |
| AUD-DS1/3 | 2026-11-11 | 15 section 20 says where the platform goldens and the measured text contrast run: in `flutter test` of a member on a macOS host, in no CI job; the shared screen audit `dsExpectAccessible`, the component sheets and the Spaces page of the phone measure the contrast only there (D-M4-07-10 stays), a few screen tests call the guideline on every host. No step is added to the job `apps (macOS)`, and the contrast guideline is not rebuilt to read colors from the render tree. On every host the gate holds the CI goldens, every declared token pair and, new, the edges Material draws from the color scheme (AUD-DS1/2). | The table of 15 section 20 named a "macOS runner (platform goldens)" and the contrast guideline in "every run"; neither exists: `test (apps)` runs on Linux, and `apps (macOS)` runs only the entries of `platform-tests.json`. The finding leaves the choice between a CI step and an honest specification. A platform golden must match exactly (PL/5) and is recorded on the Mac of whoever changes a screen; whether the hosted macOS image draws the same glyph pixels is not known, and a step that cannot be tried before it gates every pull request of the apps is no part of a fix package. A guideline that reads the text color from the render tree would be a new check over every screen of every member. The gap that stays is named in the specification: a screen behind the shared audit that pairs two colors no rule declares is found only by a run on a Mac. Not tried: measuring the contrast of the screens of the other members on Linux too, where their text is drawn as blocks (AUD-DS1/5) and so has no anti-aliased glyphs; it needs a run on the Linux runner. |
| AUD-DS1/4 | 2026-11-11 | `alchemist` and `flutter_test` are dev dependencies of `design_system`. `lib/testing.dart` and `lib/src/testing/` stay in the package and import both; the four files ignore the lint `depend_on_referenced_packages` with the reason at the top. The members that run goldens keep `alchemist` as their own dev dependency, as D-M4-04-5 rules. This replaces "`alchemist` is a regular dependency" of D-M4-04-5 and "`flutter_test` becomes a regular dependency" of D-M4-05-5. The test helpers do not move to a package of their own. | As regular dependencies both were dependencies of every app: the Flutter tool bundles the assets and fonts of every package an app reaches through regular dependencies, so each app bundle carried the Roboto files alchemist declares, and the golden test library stood in the dependency graph of the product. The library is test support: only the folders `test` and `integration_test` of a member may import it (`make arch`, rule 10), the workspace has one resolution, so its imports resolve for every member, and `flutter test` keeps the assets of dev dependencies. A package of its own would give the same bundle and the same graph, but move the whole library and change the import in the tests of every member that uses it. |
| AUD-DS1/5 | 2026-11-11 | The goldens that the two changes touch are rerecorded, the CI and the macOS variant: in `design_system` the sheets with unread rows (rows, sidebar channels, sidebar threads, sidebar status), in `admin_ui`, `apps/client` and `apps/console` the sheets with a text field, a dropdown, a switch that is off or a segmented button. The goldens of `bothy_viz` and `terminal_ui` are unchanged. | In `design_system` only AUD-DS1/1 shows: bold text is heavier and wider (in a CI golden its block is wider). In the other members only AUD-DS1/2 shows: every changed pixel of their images lies on an edge that moved from `color.border.default` to `color.border.control`. Their tests draw the text of the design system in the test font of `flutter test`, as blocks, also in a platform golden: the roles name the plain family, which only `design_system` registers, and `flutter test` answers a family it does not know with its test font before it reads the fallback list with the name `packages/design_system/<family>` (measured in the tests of the client: a role lays out every glyph one em wide, the same style with the package name as its family lays out the bundled font and follows the weight). So no golden outside `design_system` shows a weight; that is how the tests were before this ticket and is not changed here. |

Evidence, each test failed before its change:

- AUD-DS1/1: `packages/design_system/test/theme/font_weight_test.dart` measures the glyphs the
  engine lays out with the bundled font files: a weight set after `dsTextStyle`, a bold `Text`
  below the theme, the unread thread row, the unread sidebar rows, Markdown bold and a mention
  are as wide as the same text with the axis set by hand, and wider than at the regular weight.
  Before the change each of them was exactly as wide as the regular weight.
- AUD-DS1/2: `packages/design_system/test/theme/control_outline_contrast_test.dart` renders a
  switch that is off, a text field with the default decoration, an outlined text field,
  `DsDropdownField` and a segmented button with `buildDsTheme` in both themes and reads the
  pixels of the line through their middle: ring on canvas, thumb on track, underline and border
  on canvas reach 3:1.
- AUD-DS1/4: `packages/design_system/test/dependencies_test.dart` reads the package graph of the
  workspace (`.dart_tool/package_graph.json`, the file the Flutter tool decides the bundled
  assets from): no app reaches `alchemist` through regular dependencies. The font manifest of a
  bundle of the client built before the change lists the family `packages/alchemist/Roboto`,
  the one built after it does not.
