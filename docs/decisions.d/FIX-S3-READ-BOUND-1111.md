# FIX-S3-READ-BOUND-1111 In-memory reads of an object are bounded by the caller, ranged answers are checked

Follow-up to AUD-SF01/3 (docs/decisions.d/AUD-srv-files-01.md). An automated security review of
that change reported that the S3 driver no longer bounds the body of an object, so a caller that
reads an object into memory and relied on the old limit of the egress client reads as much as the
storage answers. The threat is an object storage that is hostile or broken, or an object that was
replaced behind the server.

The report was checked at the source and holds. Before AUD-SF01/3 the egress client of the driver
cut every answer at `file.max_upload_bytes`; since then the body of a successful `GetObject` is
as long as the answer announces. The consumers of `ObjectStore.Get`, read in the code:

| Consumer | Keeps in memory | Bound before this ticket | Bound now |
|---|---|---|---|
| image job, `Codec.Inspect` of a WebP that stays unchanged (`ImageProcessor.keepOriginal`) | the whole object | none (the old limit of the egress client was the only one) | the stored size of the row, FIX-SRB/2 |
| image job, PNG filter and header (`pngWalker.small`: the `iCCP` chunk as a whole) | one chunk of any declared length | none (same) | the stored size of the row, FIX-SRB/2 |
| image job, GIF and still WebP (`readAll` in `adapters/imaging`) | the whole object | the stored size of the row | unchanged, and the reader of FIX-SRB/2 in front |
| image job, JPEG filter | one segment and the parts of the colour profile, both bounded by the format | the format | unchanged, and the reader of FIX-SRB/2 in front |
| image job, MP4 and QuickTime boxes (`objectReaderAt`, ranged) | fixed buffers of the box reader | the buffers | unchanged; the driver now checks the range, FIX-SRB/3 |
| text extraction (`ExtractText.extract`) | the object up to the limit | `search.extract.max_input_bytes` | unchanged, now through the shared reader of FIX-SRB/1 |
| object journal (`journal.go`) | the whole object | `files.JournalObjectMaxBytes` | unchanged |
| storage probe (`storageprobe.go`) | the whole object | the length of the probe | unchanged |
| public logo (`readVariant` in `instance/adapters/httpapi`) | the whole variant | the stored size of the variant row | unchanged |
| S3 driver, every answer that is not an object (the SDK reads it) | the whole answer | `egress.max_response_bytes` (AUD-SF01/3) | unchanged |
| scan pass, download and its digest of a thumbnail, export package, personal data export, transcription | nothing: they stream | not bounded in memory terms | unchanged on purpose, FIX-SRB/1 |

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-SRB/1 | 2026-11-11 | The port and both drivers stay as AUD-SF01/3 left them for a whole object: `Get` yields as many bytes as the storage answers. A use case that keeps what it reads in memory bounds the read itself, with the stored size of its row or a named configuration value, through one reader: `limitedObject` in `internal/files/app` yields at most the limit, takes at most one byte more from the object and then fails for good with the error of its caller. The text extraction uses it with `search.extract.max_input_bytes` (its own `inputLimit` is gone), the image job with `files.size_bytes` (FIX-SRB/2). Streaming callers stay without a bound on purpose: the scan pass (which stops one byte after the declared size anyway), the download and the digest of a thumbnail, the export package, the personal data export and the transcription hold no part of the object. | Only the use case knows the length it expects: the port has no size for a whole object, and adding one would change every streaming caller that has no use for it. The bound has to hold for both drivers: on the driver `fs` a file replaced on disk is as long as it is, so a check of the announced length in the S3 driver alone would close half of the threat. A reader in front of the consumer also bounds an answer whose announced length is honest but far above the row. Tests: `TestLimitedObject`, `TestExtractTextRun` (case `bytes beyond the stored size`). |
| FIX-SRB/2 | 2026-11-11 | The image job opens every original through `ImageProcessor.opener(key, size)`, whose readers end at the stored size of the row of that key; an object that yields more is `errObjectLonger`, a read error of the store: the run returns it, River retries, and no row, event or object is written. `ImageCodec.Inspect` takes the stored size; the codec reads a WebP there through `readAll` like the conversion does, and an object of another length is `errOriginalSize`, never an image error. | `Codec.Inspect` read a WebP with `io.ReadAll`, and the PNG filter holds the `iCCP` chunk as a whole (a declared length up to the largest chunk of the format), so both held as much as the storage answered once the limit of the egress client was lifted. The opener is the one place where the job reaches the storage for an original, so the filters, the header readers and the decoders are all behind it; `Inspect` is bounded in the adapter as well, because its read is the one that needs the whole object and must not depend on what a caller passes. A wrong object is no property of the image, so the file is neither failed nor stored unchanged because of it. Tests: `TestProcessImageReadsAtMostTheStoredSize` (original, unchanged original, cleaned original of the thumbnails), `TestKeptOriginalInspectsWithTheStoredSize`, `TestInspectWebPReadsAtMostTheStoredSize`, `TestImages/ImageObjectLongerThanRow` (server, driver `fs`, a replaced object). |
| FIX-SRB/3 | 2026-11-11 | The S3 driver hands out the body of a `GET` with a range only for the range asked for (`checkObjectAnswer` in `answerBodies`): status 206 and a `Content-Range` in bytes that starts at the first byte asked for, ends at or before the last one and has the length the answer announces. Every other successful answer, such as the whole object with status 200, another offset, a longer range or a missing `Content-Range`, is a storage failure with the detail `not the range asked for`. No answer with status 200 is accepted for a range, not even one that would happen to hold the same bytes. Amends AUD-SF01/3. | A storage that ignores the range answers the object from its first byte: the box reader of the image job and a ranged download would take those bytes for the range, and the body would be as long as the object instead of the range. With the check a ranged read never yields other or more bytes than the caller asked for, which is the length a caller of a range expects. S3 answers every valid range with 206 and `Content-Range`, so the strict rule costs nothing there and needs no second case to reason about; the conformance suite reads the whole object as one range against SeaweedFS (`TestS3Conformance/GetRange`), as a download with `Range: bytes=0-` does. An S3-compatible storage or a proxy in front of it has to answer a range that way. Tests: `TestRangedGetNeedsTheRangeAskedFor`, `TestS3ReadsObjectAboveBodyLimit`. |
| FIX-SRB/4 | 2026-11-11 | An answer of the storage above `egress.max_response_bytes` is a storage failure whatever its status: `fail` checks `egress.ErrResponseTooLarge` before it maps a status to a port sentinel, and the detail reads `response too large (status <n>)`. Amends M3-02/5. | The error document was not read, so its status alone does not say what failed: a 404 may be `NoSuchBucket`, which is a storage failure, and was reported as a missing object. Carried over from the review of AUD-srv-files-01 as a recorded minor of the same driver. Test: `TestOversizedErrorDocumentIsNoSentinel`. |
| FIX-SRB/5 | 2026-11-11 | Not built: the thumbnails read the header of the cleaned original for the pixel guard and decode it in a second read of the same key, and nothing ties the two answers together; a successful `GET` without a range that is answered with status 206 is not refused; an object shorter than its row is no error of the reader of FIX-SRB/1 (the image filters report it as a broken structure, as before). The object mirror of the backup service stays as AUD-SF01/4 describes it. | The two reads of the thumbnails existed before AUD-SF01/3, and the old limit of the egress client never bounded a decode, so it is no part of the reported regression: a storage that answers the same key with two different images is a separate case without a known occurrence. The other two yield fewer bytes than expected, never more. |
