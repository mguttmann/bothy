| D-M7-04-3 | 2026-10-20 | Start lock: every role compares the stored identity with the current one once at start, after the instance row loaded (02 15.1 step 5); a mismatch logs one ERROR line with the runbook step and registers the readiness check `restore_not_finalized`, which fails for good like `schema_requires_newer_server` (the process keeps running, `/healthz` stays 200); unlike the version lock it also skips the steps that serve or process (log tail, River jobs, worker consumers, public listener), because the Compose stack publishes `api` without a proxy that follows `/readyz`, so readiness alone would not keep writes and deliveries of a mixed timeline out (red team finding). The documented command in the stack is `docker compose run --rm migrate restore finalize` (the entrypoint of the image is `bothy`), with the manifest of `--relocation` mounted into the read-only container. A read error of the identity ends the start. An empty stored identity never blocks. | D-M7-04-4 | 2026-10-20 | `database.restore_guard` (`on`, `off`; default `on`, chapter 16): `off` skips the comparison at start; `bothy restore finalize` behaves the same with either value. `--relocation <file>` reads `backup_manifest.v1` (checked by `status/domain.ParseManifest` as bothy-backupd writes it) before the database is touched and compares, in this order, `event_log.head_seq` with `event_seq` (equal to `max(seq)` because the partition of the head is never dropped), `audit.last_seq` and `audit.last_hash` (lowercase hex) with the last row of `audit_events` and `sync_epoch` with the instance row; the first difference is exit `1` naming the field, and nothing changes.
