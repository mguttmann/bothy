# FIX-windows-dictation Text from dictation tools in the Windows composer

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-WD/1 | 2026-10-31 | The Windows runner fills the scan code of a key message that arrives without one before `TranslateMessage` and the engine see it (`apps/client/windows/runner/key_scan_code.h`, called in the message loop of `main.cpp`): for `WM_KEYDOWN`, `WM_KEYUP`, `WM_SYSKEYDOWN` and `WM_SYSKEYUP` whose lParam bits 16-23 are 0 and whose virtual key is not `VK_PACKET`, the scan code is `MapVirtualKeyW(vk, MAPVK_VK_TO_VSC_EX)`, and a result with the prefix `0xE0` sets the extended bit 24. Every other message, a real scan code and a key without a scan code in the layout stay unchanged. | A dictation tool that pastes with Ctrl+V through `SendInput` with virtual keys only delivers scan code 0. The Flutter embedder derives the physical key from the scan code, so Ctrl and V became the same unknown physical key (`0x01600000000`): V down on a "held" key made the engine send a synthesized Ctrl up first, the framework saw a plain V and `PasteTextIntent` never fired, while typed text still arrived through `WM_CHAR`. The fix lives in the runner because the cause is the embedder's handling of any VK-only sender, not one tool, and the runner is ours. Filling the code before `TranslateMessage` gives the generated `WM_CHAR` the same scan code. |
| FIX-WD/2 | 2026-10-31 | The other ways of inserting text keep working and need no change: `SendInput` with `KEYEVENTF_UNICODE` (`VK_PACKET`) is left alone, the engine passes it on and the text arrives as `WM_CHAR` through text input; typed keys from a keyboard already carry a scan code. The macOS app is not touched: dictation there (system dictation and tools that insert through the text input client or Cmd+V) never passes through the Windows runner, and no Dart code changed. Writing text through the UI Automation value pattern of the field is not part of this fix: the Flutter Windows embedder exposes the composer as a pane without an editable element, so such tools fall back to the window and their keyboard paste, which FIX-WD/1 covers. | Scope of the reproduced failure; the accessibility tree of the embedder is not ours. |
| FIX-WD/3 | 2026-10-31 | The header has no Windows dependency and is tested with the host C++ compiler: `apps/client/windows/runner/test/run_tests.sh` builds every `*_test.cpp` there with `CXX` (default `c++`, `-std=c++17 -Wall -Wextra -Werror`) and runs it; the root target `make runner-test` runs every such script and `make test` runs it when the apps are selected, so the CI job `test (apps)` runs it on Linux. A widget test (`apps/client/test/composer/external_paste_test.dart`) feeds the composer the key data and raw messages the embedder sends for both cases and documents the effect: with scan codes Ctrl+V pastes, without them nothing is pasted. | The fix is native and `apps (Windows)` only builds the runner; a host compiler test runs on every change of the apps without a Windows runner. That Windows delivers scan code 0 for the tool's input was derived from the tool's source and the documented behaviour of `SendInput`, not observed on a Windows desktop; one dictation into the installed build confirms it. |
