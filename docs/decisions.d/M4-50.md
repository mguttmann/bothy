# M4-50 Free text selection in the history

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-M4-50-1 | 2026-10-31 | Cause: no widget above the messages of the history provided a selection registrar (`SelectionArea`), so no `Text` of a message ever registered as selectable; no gesture detector, list item wrapper or custom painting blocked it, and the `SelectionContainer.disabled` of M4-48 and M4-49 covers only the copy button, the toggle and "Show all". The fix gives each message on the desktop its own `SelectionArea` around the rendered content (`DsMessage.onSelectionChanged`), not around the header, the reply line, "Show more", reactions, files or the hover bar. Without the callback (the phone, the outbox rows, the web console) `DsMessage` adds no selection area, so the web build gets none (the style element of D-M6-04-6). | Owner report 2026-10-31 (macOS app, 01 6.15). Only the content is text a person wants to copy; the chrome would end up in every copy. |
| D-M4-50-2 | 2026-10-31 | One selection per message: a drag does not continue into the next message. | The history is a reversed `ListView.builder`; a message off screen is not built, so a selection across messages would silently lose the text of messages that scroll out of the cache, and the copy would not be what the person selected. A per message selection keeps virtualization and exactness; "Copy text" still copies a whole message. |
| D-M4-50-3 | 2026-10-31 | Plain text of a selection: Flutter joins the selected text of neighboring paragraphs with nothing, so the renderer wraps its containers in `DsSelectionJoin` (only under a selection): blocks apart by an empty line, list items and the blocks of an item by a line break, a list marker copies "- " or its number when it is selected (`DsSelectionJoin.replace`), table cells by a tab and rows by a line break (rows by the tops of their cells), code lines by a line break and the hanging indent and the rest of one line by nothing. An empty code line is a space that copies as nothing, so its line break stays; parts the selection only touches at its edge add no separator. The language label of a code block is out of the selection. | 01 6.15 item 3; the copy of a quote (D-M4-48-3) uses the same markers, so a pasted selection and a pasted quote read alike. The display wrap of M4-49 is a soft wrap of one paragraph per line and never part of the selected text. |
| D-M4-50-4 | 2026-10-31 | Right click: the selection draws no context menu of its own (an empty `contextMenuBuilder`); the message menu opens on the release of the right button, after the selection handled the press (on macOS it selects the word under the pointer), and starts with "Copy" (`MessageAction.copySelection`) while text is selected. The menu takes the focus, which ends the selection, so the tile keeps the selected text from the moment the menu opens and copies that. Cmd+C (Ctrl+C) is the selection's own copy. | Two menus on one right click would compete; the message menu is the established one (M4-20). The release is the first moment at which the selection's word select has run, because the gesture recognizers see the release after the tile's pointer listener. |
| D-M4-50-5 | 2026-10-31 | Phone: no selection in the history, so a long press stays the message menu's and a tap stays the block copy's (01 6.12 item 2); the menu has "Select text" (`MessageAction.selectText`) after "Copy text" for every message with content, which opens a modal sheet (`SelectTextView`) with the rendered content under a `SelectionArea`: system handles, the system menu with Copy and Select all, the same plain text as on the desktop. A link in the sheet closes it and opens. Both new actions are run by the message tile, never by the history's action handler. | The owner wants the long press menu kept on the phone; a selection in the history would take the long press. A sheet is the pattern of the phone app for secondary views (session sheet, 01 5.3). |
| D-M4-50-6 | 2026-10-31 | Out of this ticket: the agent text inside a card's components and the messages still in the outbox are not selectable ("Copy text" copies them). Tests: widget tests of the renderer and of the history under macOS and Windows and under iOS and Android, headless; no GUI test runs on a maintainer's machine, so the feel of a selection with a real trackpad is not proven by them. | The report names the history's messages; cards carry buttons whose labels would join a selection, and an outbox row is the person's own text. |
