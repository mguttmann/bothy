# FIX-ios-floating-cursor The trackpad of the space bar in the composer

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-IFC/1 | 2026-11-02 | Not reproduced in the app's code: no app code takes part in the iOS floating cursor. The thread composer is a plain `TextField` (`packages/design_system/lib/src/components/ds_composer.dart`) with interactive selection on, no input formatter, no own `TextInputClient` and a key handler that only sees hardware keys; no native code of the runner touches the text input outside the debug-only test probe. Widget tests (`apps/client/test/composer/floating_cursor_test.dart`) drive `TextInputClient.updateFloatingCursor` start, update and end through the text input channel into the phone composer, as the engine does, and the selection moves, also to the line above; selection-only editing values (the Gboard slide on Android) move the cursor and it stays. They pass on main, so the defect is not in the framework path. No fix is made without a reproduced cause. | The owner's report says the keyboard does not turn into a trackpad at all. That mode is drawn by the iOS keyboard before any message reaches Flutter, so it needs a real device: the iOS version, the keyboard in use in Bothy (iOS remembers the last keyboard per app, and a third-party keyboard such as a dictation keyboard has no space bar trackpad) and a screen recording. Open, needs the device. |
| FIX-IFC/2 | 2026-11-02 | The floating cursor of a multi-line composer that scrolls does not scroll the text: `RenderEditable.calculateBoundedFloatingCursorOffset` bounds the cursor to the visible lines (Flutter 3.47.7), so lines above the visible part are not reached with the trackpad. Not changed in this ticket. | Kept as the widget test "moving up in a scrolling composer stops at the first visible line" in `apps/client/test/composer/floating_cursor_test.dart` (30 lines, the trackpad moved up 800 points leaves the last line but does not reach the first); it fails once Flutter scrolls there. Scrolling would need the floating cursor's position, which `EditableText` and `RenderEditable` keep private; a work-around would mean an own copy of the text field. That a native `UITextView` scrolls there is not checked on a device. Whether the limit is accepted is an open product decision. |
