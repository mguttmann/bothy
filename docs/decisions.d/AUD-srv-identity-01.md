# AUD-srv-identity-01 Step-up for the first sign-in data, auth_time, password hashing in parallel, retention indexes

Work package of the audit of 2026-11-11 for the identity module, findings srv-identity-app-1,
srv-identity-core-1, srv-identity-core-2, data-layer-3, fn-sign-in-devices-4 and
fn-sign-in-devices-11.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-SI01/1 | 2026-11-11 | The `conditional` step-up of `passkey.register` and `local_credential.set` is waived only for a session that has nothing to confirm a step-up with: a session outside the console on a device that is not `cli` and has no active `step_up` key, of a person without an active passkey and without an established password path. Every other session needs a step-up, also for the first sign-in data of a kind: a device with a `step_up` key, a console session, a person with a passkey or a password (either one counts for both actions), and a `cli` device, which gets `401 step_up_required` and so sets up none. The rule stays in `authz` (`stepUpWaived`); the facts of the device (`DeviceCLI`, `DeviceStepUpKey`) come with `authz.CredentialFacts` from the device row identity already reads, the two facts of the person from `PrincipalSource` as before. Stored sign-in data counts whether or not its method is switched on in the configuration. Amends the brief notes "Conditional step-up" of M1-39 and M1-40, INT-W18/2 and 05 section 2.4, 07 section 4.2 step 8, 08 sections 2.5 and 6.4 (R-ID-19). | Finding srv-identity-app-1: the old rule asked only whether sign-in data of the same kind existed, so a session without any step-up set up the first passkey or the first password with TOTP, confirmed its own step-up with it (a passkey also the fresh step-up of the terminal) or logged in to the console, where the new web device is active without an approval. The reason the old rule gave, that a stolen session only gains a login whose new devices stay `pending`, did not hold for these two ways. |
| AUD-SI01/2 | 2026-11-11 | Not built for srv-identity-app-1, and why: (a) a person without any sign-in data on a device without a `step_up` key still sets up the first passkey or password with the session alone (threat T-ID-07, residual). Binding that case to an enrollment code of the owner needs a rule for the first owner after `bothy setup bootstrap-owner` on such a device and for people who log in with OIDC or the proxy header there and have no local identity; that is a product decision and a new flow, not a fix of this rule. (b) Marking a factor "set up in this session" and refusing it for step-up and console until a new login adds nothing: a login from a device the server knows, with the same key, keeps the device `active` (`loginDevice`, `TestLocalAccounts/TestPasswordLoginKnownDeviceStaysActive`), so the same session holder logs in again and confirms. (c) An event to the other devices of the person when sign-in data is added is a new event type of the sync protocol with a view in the apps. | The first sign-in data must come from somewhere; on a device that cannot confirm anything, the session is the only proof the server has. (b) and (c) are the second half of the audit's recommendation: (b) was checked against the login completion and gives no protection, (c) is a feature of its own. |
| AUD-SI01/3 | 2026-11-11 | `oidcflow.ExternalFromClaims` no longer puts `iat` in place of a missing `auth_time`; `external_identity.v1` leaves `auth_time` out when the provider sent none, and a stored document without the member reads as "none". A console step-up by OIDC re-login whose ID token has no `auth_time` is a wrong confirmation: `401 step_up_required`, the challenge fails and counts toward `auth.step_up_fail_limit`, audit cause `auth_time_missing` (new, next to `auth_time_before_challenge`). The login itself never read `auth_time` and is unchanged. Amends the brief M1-41 (fallback to `iat`) and M1-41/5 (08 sections 2.2 step 6 and 6.2, R-ID-20). The step-up method `oidc_reauth` is still offered for every OIDC identity: whether a provider sends `auth_time` is only known after a login. | Finding srv-identity-core-1: `iat` lies after the start of the flow by construction, so with the fallback the check "auth_time not before the challenge" always passed and a provider that ignores `prompt=login` and `max_age=0` confirmed a step-up with a silent session. The case "no auth_time" of the unit test described a state the real path never produced. |
| AUD-SI01/4 | 2026-11-11 | New configuration key `auth.argon2id_max_concurrent` (Argon2id computations at the same time, each with `auth.argon2id_memory_kib` of memory). The hasher (`adapters/passwordhash`) holds one slot per running computation; `Hash`, `Verify` and `VerifyDummy` of the port `app.PasswordHasher` take a context, wait for a free slot and return the error of the context when it ends first, without computing. The wait is not part of the timing average or the padding of ID-T21, and it is the same for a known and an unknown name. There is no queue limit and no own `429`: a waiting login ends at `http.request_timeout` with `503 unavailable` (cause `deadline_exceeded`), the answer the HTTP layer already gives a request that ran out of time (08 section 2.5). | Finding srv-identity-core-2: every password login computes one Argon2id hash, also for an unknown name and during a lockout, and nothing bounded how many ran at once; `rl.public_auth` counts per address, so a few addresses could hold more memory than the process has. A named limit is how the other expensive paths are bounded (`file.scan.max_concurrent`, `file.image.max_concurrent`). |
| AUD-SI01/5 | 2026-11-11 | Migration `00104_retention_indexes.sql` adds, each built `CONCURRENTLY`: for the candidate queries of the retention jobs `refresh_tokens (expires_at, id)`, `auth_sessions (LEAST(expires_at, revoked_at), id)`, `devices (revoked_at, id) WHERE revoked_at IS NOT NULL`, `terminal_sessions (closed_at, id) WHERE closed_at IS NOT NULL` and `messages (created_at, id) WHERE deleted_at IS NULL AND kind <> 'system'`; for the foreign keys to `devices` the column `updated_by_device_id` of `read_states`, `drafts`, `user_settings`, `user_space_states` and `user_channel_states` (each `WHERE updated_by_device_id IS NOT NULL`) and `push_registrations (device_id)`. The queries stay as they are: the expression index serves `LEAST(expires_at, revoked_at)` of `auth_sessions` in condition and order. `TestRetentionIndexes` reads the statements from the query files of the modules and holds that each candidate query reads its index in order without a sequential scan or a sort, and that the check of each named foreign key can use its index in a generic plan. Not indexed: `LEAST(...)` of `api_tokens` and `enrollment_codes` (one valid code per person, tokens per agent, app and person: tables that stay small), and foreign keys to other tables the jobs delete from, which the finding does not name. | Finding data-layer-3: without an index on the end time every hourly batch read its whole table, and `refresh_tokens` gains a row with every token refresh; deleting a device read every child table whole for each foreign key. The plans are checked with the sequential and the bitmap scan switched off, because on the empty tables of a test the planner prefers a sequential scan whatever index exists; the test therefore shows that the index can serve the query, not a measured time on a large instance. |
| AUD-SI01/6 | 2026-11-11 | The step-up screen of the console says under the field of the one-time code that a code works once and to wait for the next one (`consoleStepUpCodeHint`). Unchanged: a code is accepted once (08 section 2.5), the console asks for a step-up directly after the login (08 section 7.5), and the code of the login sent again is a wrong confirmation that counts. | Finding fn-sign-in-devices-4: both rules are deliberate, but nothing told the person that the code still shown by the authenticator app was used up by the login, so the first step-up after a password login failed and counted. A reused code as an own reason that does not count would change the counting of the login rules and the API; the hint removes the cause. |
| AUD-SI01/7 | 2026-11-11 | Every accepted request of a console session counts as activity for `auth.console_session_idle_timeout`, also the periodic requests of the live page and of TV mode (`viz.live_poll_interval`, only while the tab is visible). A console left open on such a page stays logged in until `auth.console_session_max_age`; the idle end applies once no request arrives any more, for example while the tab is hidden. No code change; written into 08 section 7.5. | Finding fn-sign-in-devices-11: the behaviour is what TV mode needs, a screen nobody touches in the session of a person (25 section 6.6, R-VZ-09), and its risk is the threat T-VZ-04 with its recommendation of a person with few rights for the screen; administration needs a fresh step-up whatever the session's age. Taking the polls out of the idle rule would end TV mode after the idle time. The rule was only implied by D-M6-01-3 ("an accepted request writes last_seen_at"). |
