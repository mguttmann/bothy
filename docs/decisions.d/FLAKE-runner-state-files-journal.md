| FRSJ/1 | 2026-11-02 | The scenario conftest of the Claude Code runner has one walk over a live state directory: `live_entries` takes the `lstat` of each listed entry and skips one that is gone by then, `live_files` reads the regular files that still exist and `assert_private` asserts `0700` for every directory and `0600` for every file that exists. `test_state_files_private_and_retention` uses `assert_private` and also asserts that `inbox.sqlite3` was among the checked entries; the two secret scans (`test_br_13_no_secret_values_leak`, `test_no_secret_or_content_in_runner_output`), which had each caught the same `FileNotFoundError` inline, use `live_files`. `test_state_walk.py` covers the helpers with an entry removed after the listing. No product change, no retry, no rerun. | Run 41492154233 (PR #533, job `test (SDKs and plugins)`, attempt 1) failed at the old `test_heartbeat_and_secrets.py:118` (`path.lstat()` of each `rglob` entry) with `FileNotFoundError` on `state/inbox.sqlite3-journal`. The runner still polls (every 20ms in the scenarios) while the test walks the state, and the SDK store opens its database with `journal_mode = DELETE` (`sdk/python/src/bothy_sdk/_store.py:79`), so SQLite creates and deletes the journal around each transaction. Reproduced locally: 2 of 50 runs failed with the same error under 16 busy CPU workers; with the fix 50 of 50 passed under the same load. The product walks only `sessions/`, `files/`, `outgoing/` and `tmp/` (`statedir.py` `sweep`), never the inbox, and already treats a vanished entry as not old (`_old_file`, `_mtime`), so a live runner cannot hit this. |
