# CU-03 Host service: computer sessions and frames

Rulings of the ticket that builds the session kind `computer` of `bothy-host`
([27-computer-use.md](../spec/27-computer-use.md) sections 4 to 9, 12.3; brief
[CU-03](../briefs/CU-03-host-computer-sessions.md)).

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-CU-03-1 | 2026-11-26 | Package names: `services/host/internal/computer` (manager, session, helper channel, peer rule, scale map, chunking, token check), the frame types in `internal/frame/computer.go`, the control ops in `internal/control/computers.go`, the shared data connection as `session.Stream` (`session.DialStream`) and the shared JWS step as `session.ParseJWS`. `frame.Decode` takes the session kind (`frame.KindTerminal`, `frame.KindComputer`); the Noise configs take a `Label` (`noise.ComputerPrologueLabel`). | Reuse, not fork (brief design note 2): the terminal path keeps its code and its recordings byte for byte. |
| D-CU-03-2 | 2026-11-26 | Every action with `coordinate` or `region` carries `scale_id` in `args`; `cu_result.cursor` and the pointer are `{"x", "y"}` in pixels of the screenshot; `cu_result.app` is `{"id", "name"}`; `seq` of `cu_action` starts at 1. Chapter 27 6.2 and 6.3 name these now. | 27 6.2 binds coordinates to a `scale_id` without naming its place; C1 (CU-05) and C3 need one shape. |
| D-CU-03-3 | 2026-11-26 | Scale IDs: a counter from 1 per session, one ID per distinct geometry (screen origin, size, scale and image size); the session keeps every geometry it saw, without a limit and therefore without a key. An ID whose screen is no longer the screen of the helper's last `done` is `stale_screenshot`; an unknown ID or a point outside the image is `invalid_action`. A `zoom` keeps the ID of its screenshot. Mapping: `origin + x * width / image_width`, rounded to the nearest pixel of the screen (`1 / scale` of a unit), then to two decimals, kept inside the screen. | A session sees few geometries (one per display change); keeping them all tells an outdated ID from an unknown one, which a bounded list could not. |
| D-CU-03-4 | 2026-11-26 | `cursor_position` without a known geometry takes one capture to learn it and drops the image; a pointer outside the screen maps to the nearest pixel of the image. `wait` sleeps up to `computer.wait_max`, then captures. A helper request that fails (no helper, broken channel) answers `os_refused`; the helper's crash itself ends the session with `error` `helper_crashed`. | The host service answers both actions itself (27 6.4); `cursor` must be in screenshot pixels. |
| D-CU-03-5 | 2026-11-26 | `computer.close` ends the session on the host (release, hide, `cu_state` `stopped` with the server's reason, data connection closed) without a `computer.ended`, like `session.close` of the terminal; every other end path the host sees sends exactly one `computer.ended`. A failure of step 0 of 5.3 closes with `4104` `handshake_failed` and sends no `computer.ended` (27 5.3: "a failure after step 0 also ends ..."). A `computer.ended` that the control connection cannot take is kept, named in `live_sessions`, and sent after the next `ready`. | The brief lists `computer.close` among the ends with a `computer.ended`, but 12.3 allows the host only `done`, `stopped_by_user`, `device_disabled`, `connection_lost`, `open_failed` and `error`, while `computer.close` carries the server's reasons (`run_ended`, `access_revoked`, ...); the specification wins (brief rule 10). |
| D-CU-03-6 | 2026-11-26 | The `report` object `computer` is always sent; without `host_service.computer_use`, without pairing or without a helper it is `{helper: "absent", enabled: false, generation: 0, os_account: "", permissions: unknown, helper_version: "", signature, locked: false}`, after a refused peer `helper: "refused"`. `signature` is the state of the host build (`verified` with `buildinfo.ComputerHelperRequirement`, else `development`), not the helper's own claim. | The acceptance criterion asks for `helper: absent` without the key; a claim of the peer proves nothing, the requirement the peer rule enforces does. |
| D-CU-03-7 | 2026-11-26 | Installed helper paths: macOS `/Library/Application Support/bothy-host/bin/Bothy Computer Helper.app/Contents/MacOS/Bothy Computer Helper`, Windows `%ProgramFiles%\bothy-host\bothy-computer-helper.exe`; the signing requirement comes from `-ldflags -X .../buildinfo.ComputerHelperRequirement=<value>` (empty: development build). CU-02 installs the helper there and sets the value in its release targets. | Chapter 27 names no path; the peer rule needs a fixed one under the trusted program folder. |
| D-CU-03-8 | 2026-11-26 | The doctor section `computer` is printed after the summary of HD1 to HD11 through `startup.Deps.ComputerDoctor` (no HD entry, nothing in `report.doctor`): `computer: off`, or one line each for installed, path trusted, build signed or development, helper, switched on with the generation, the two permissions, and `computer test peer: set (test setting)`. | 27 9.3; the doctor output is assembled in `internal/startup`, so the hook lives there (one field, no other change of that package). |
| D-CU-03-9 | 2026-11-26 | The install plan creates the endpoint folder only with `host_service.computer_use`: macOS `/Library/Application Support/bothy-host/computer` (service user, `0755`), Linux `RuntimeDirectory=bothy-host-confirm bothy-host-computer` in the unit. Without the key the plans and the packaged unit stay byte for byte as before. | Brief rule 11 (additive only). |
| D-CU-03-10 | 2026-11-26 | Linux test backend `services/host/test/computer_backend/`: Python 3 with `python-xlib` (XTEST) and Pillow for the image encoding and Tk for the fixture app; text is typed through keycodes of the layout or through empty keycodes remapped in batches with a short pause (`MAPPING_PAUSE`) for the clients to read the mapping; SIGUSR1 and SIGUSR2 simulate lock and unlock, SIGHUP the stop button. The tests use `unittest` (no new project in `PY_PROJECTS`), the Xvfb test skips with the missing part named outside an image that has Xvfb, `python3-xlib`, `python3-pil` and `python3-tk`. | Smallest set that drives an X display and encodes JPEG and PNG; CU-06 runs it in its Compose image. |
| D-CU-03-11 | 2026-11-26 | The required members of `computer.open`, `computer.close` and `computer.disable` are kept apart from the terminal ops in `control/frames.go` (`requiredComputer`), so the recording check of `server_frames.json` still demands every terminal op, and a hand-written strict decode test covers the computer ops until CU-04 records them. The host recording `host_frames.json` keeps its frames; CU-04 adds the computer ops to `docs/api/asyncapi.yaml` and both recordings. | `server_frames.json` and the asyncapi rows belong to the server side (27 12: "with CU-04"); lowering the recording check was not an option. |
| D-CU-03-12 | 2026-11-26 | Security finding of the coordinator (PID reuse between the peer credentials and the path and signature checks): the helper peer is identified by its process ID together with the process start time (macOS `kern.proc.pid` `p_starttime`, Windows `GetProcessTimes`), read before and after the checks of the executable; it must lie before the accept of the connection and must stay the same after `hello` and before every session (`PeerRule.Identify`, `PeerRule.Same`); otherwise the channel closes with `computer_peer_refused`. Linux uses only the uid of `SO_PEERCRED`. Chapter 27 9.4 states the rule for both directions. Not built: the macOS audit token with `SecCodeCopyGuestWithAttributes` and a held Windows process handle, because the brief demands the signer check without cgo (design note 3); the start-time binding closes the PID reuse the same way, the dynamic signature check of the running process stays a follow-up for CU-02, which owns the signing. | A PID alone can be reused after the peer exits while its socket lives on in a child; a reused PID belongs to a process that started after the connection. |
