| M1-58/1 | 2026-10-15 | No-op rule: an edit whose resulting content equals the stored content byte for byte and whose resolved mention set equals the stored one (order ignored), an empty body included, answers `200` with the current message and its `ETag` and writes nothing: no revision, no event, no new version. Mentions that resolve differently than before (a person left or joined) make an edit with the same content a change, which stores the unchanged content as a revision. | Brief design note 2 point 5; the resulting state is what the edit compares. |
| M1-58/2 | 2026-10-15 | Error precedence of `updateMessage`: `428` (the precondition stage of the chain, before any lookup) > `404` (missing and invisible share the path: the message is read in the visible channels of `Scope(message.read)`, and `authorize` gets an unknown thread hint when none is found) > `403` (author, `write`, `channel_read_only`) > `410` > `412` > `413` > `400`. An `If-Match` that is not a version (`"x"`, a weak tag) is `412` like a stale one, because version 0 never exists. A system line names a person in its author column but is the server's: editing it is `403 forbidden` (the contract lists no `409` for `updateMessage`, and the content CHECK of a system line would otherwise fail with `500`). | Brief design note 2; 06 "Concurrency" item 2; the response list of `updateMessage` in `openapi.yaml`. |
| M1-58/3 | 2026-10-15 | The visible channels of an edit, a deletion and a revision list come from `Authorizer.Scope` for `message.read`, the list action of reading messages; `message.update` and `message.delete` are not read-level actions, which `Scope` refuses. An app needs `messages:read` for them to find its messages, so an app with only `messages:write` gets `404` on its own message. | 07 section 7.4 rule 1; the predicate is the read scope, the decision is `authorize` with the action itself. |
