# AUD-srv-cmd-01 Import tool findings of the audit of 2026-11-11

Work package of the audit of 2026-11-11 for the import tool (`services/server/cmd/bothy/importtool`),
findings `fn-import-migration-1`, `fn-import-migration-2`, `fn-import-migration-3`,
`fn-import-migration-4` and `fn-import-migration-7`.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-SC1/1 | 2026-11-12 | The tool fits a channel topic, a thread name and a forum tag name to the display text rule of the server before it sends them (`displayText` in `fit.go`): every control character becomes a space (line breaks and tabs included), bidi control characters and invalid bytes are dropped, and the white space this leaves at the ends is trimmed. A value that already fits is sent exactly as before. A topic is also cut to `TopicMaxChars`, the default of `channel.topic_max_chars`; `TestTopicLimitEqualsServerDefault` holds the constant equal to the default of a started server. The row of the channel notes a fitted value, in the dry run too. The set of bidi controls comes from `kernel/textcheck`, the package the server checks with. | `fn-import-migration-1`: the server checks an imported value like any other input (22 5.1, SEC-IN-4) and a batch is one transaction, so a Discord topic with a line break or above the limit, a thread name or a tag name with a bidi control lost its batch; the cursor stayed and every later run ended with exit `1` at the same place (reproduced on a started server, `TestApplyFitsTopicToServerRules`, `TestApplyFitsThreadNamesToServerRules`, `TestApplyFitsTagNameToServerRules`). The tag name is the same rule on a third member and has the same fix. Names of spaces and channels come from the mapping and are checked when the source is created; names of people are fitted by the server (`PlaceholderDisplayName`). The topic limit is not part of `getInstance`, so the tool cannot read the effective value: a server that allows less than its default refuses the channel, and the run names the topic (AUD-SC1/5). |
| AUD-SC1/2 | 2026-11-12 | A message of a taken type whose parts convert to no visible text and that has no attachment, its own or one of a forwarded message, is skipped with the existing reason `empty` (`hollow` in `fit.go`, 22 6.1). The rule reads the message alone: the dry run, the import, the read mirror and the lookup of a reply target of an earlier run decide the same. A reply to such a message gets the quote line of 22 6.2. A reply that itself converts to nothing is skipped too, also where a quote line would have been its only content. | `fn-import-migration-1`: an embed that holds only an image, or a forward of such a message, converted to an empty `content_md`, which the server refuses for a message without a file (`TestApplySkipsMessagesWithoutContent` on a started server). A rule that looked at the final content of one run (with the quote line) could not be repeated by a later run that has to know whether a reply target was taken over; a wrong "taken over" there names a target that does not exist and loses the batch again. |
| AUD-SC1/3 | 2026-11-12 | Pins above `pin.max_per_thread` follow the answer of the server. When `applyImportBatch` refuses a pin item with `limit_reached` at its `message_origin_key`, the tool removes that pin item and every pin item after it from the batch, sends the batch again, sends no further pin item for that thread in the run (a mirror round starts without that memory) and counts the pins as `pins_not_taken` with a note. The messages are taken over. A dry run counts every pin as "would take over". | `fn-import-migration-1`: the batch of the pin above the limit was refused for good (`TestApplyCountsPinsAboveTheLimit` on a started server). The tool can know neither the limit (not in `getInstance`) nor the pins a thread already holds (from earlier runs, or set here in a channel that an existing target or the lead `bothy` made writable), so a count of its own would be wrong in exactly the cases that matter; the refusal of the server is exact and costs one more request per full thread. |
| AUD-SC1/4 | 2026-11-12 | Not built for `fn-import-migration-1`: the limits in `InstanceLimits`, and a rule that drops any refused item and goes on. Open minors for a later run: a message with more attachments than a lowered `message.max_attachments`, a tag name above a lowered `forum_tag.name_max_chars` and a topic above a lowered `channel.topic_max_chars` still end the run, now with a message that names the member, the rule and the item. | New members of `InstanceLimits` change the API contract and every generated client for values only the import tool reads. Going on after any refused item is the question ruling AUD-SIM1/6 left with the owner (whether single failed items are recorded and the import goes on). The three cases need a value above a limit of the server: with the defaults the tool cuts the topic itself, and the other two were not reproduced; they are a question of a lowered limit. |
| AUD-SC1/5 | 2026-11-12 | The error of a refused call carries the field errors of the answer (`APIError.Fields`): for each its JSON pointer and its code, and for a batch the `thread_origin_key` and the origin key of the item a pointer names. The tool repeats a code only in the form of a problem token and a pointer only as lower-case member names and indexes; a detail text and every other member are dropped. In the read mirror the note of the channel and a line on standard error name the thread and that error. `switch` tells messages left behind by a thread that failed in its round from messages written after the round; only the second text says that the Discord channel is not locked. No option for the debug log is added. | `fn-import-migration-2`: the owner read `applyImportBatch: status 400 validation_failed` without thread, item or rule (`TestRefusedBatchNamesRuleAndItem` on a started server); the mirror wrote the reason to a debug log the binary never opens and the report repeated "a thread failed" round after round; `switch` concluded a missing Discord lock for a thread the server refuses for good. The pointer names members of the request the tool built itself and the origin keys hold Discord IDs only, so the text stays inside 22 10.2 rule 4. The reason now reaches standard error and the report, which is where the owner looks; a debug switch would be a new option for the same information. |
| AUD-SC1/6 | 2026-11-12 | A report reads the notes of its channels when it is written (`report.currentRows`), not when it is built. | A full run builds its report before the walk, because the cursor writes carry its counters; it kept the notes of that moment, so the notes of the walk never reached the report of a full run (a channel that became unreadable, a message above `message.max_content_bytes`). The notes of AUD-SC1/1 and AUD-SC1/3 would have been lost the same way; the tests of those rulings read them from the report of a full run. |
| AUD-SC1/7 | 2026-11-12 | No change for `fn-import-migration-3`. A full run still reads a channel with the lead `bothy` and takes over the messages it finds new there. | Decided on main since the audit by ruling AUD-SIM1/5 and written down in 22 7.2 and 12.1: the mirror rules no longer apply to a posted thread of such a channel (the part of the finding that was a fault, held by `TestPostedThreadWhereThisServerLeads`), while importing a channel with the lead `bothy` from the start and taking over late messages are intended and held by `TestImportedMessagesNeverTrigger`. Skipping such channels in a full run, as the audit proposed, would contradict that decision. |
| AUD-SC1/8 | 2026-11-12 | The texts that advised a change of the stored mapping are corrected: the refusal of `switch` for threads with another operator names `--force` as the way on and no longer a change of `planned_operator`; 22 13.3.1, the guide and the README say the same, 22 5.2 states that the mapping of a source is fixed, and the troubleshooting row for a differing mapping no longer advises a new source after the first import. Not built: an operation that changes the stored mapping. | `fn-import-migration-4`: the mapping of a source is fixed by decision (D-M8-04-3), `--apply`, the mirror and `switch` end with exit `2` when the file differs in anything but `lead` (`TestSwitchChangedPlannedOperatorExit2`), and a second source knows none of the items of the first, so each advised way ended in a dead end. An operation to change the mapping would be a new owner action with step-up, a route in the API contract, a check against the posted items and a console step: a new feature surface, larger than this package. |
| AUD-SC1/9 | 2026-11-12 | An embed converts to a quote block with the name of its author, the title, the link, the description, one line `<name>: <value>` per field (the value converted like content) and the footer text; an embed without any of them stays empty. The attachments of a forwarded message are not loaded: the message gets the line of 22 6.5 item 6 for each, with the reason "of a forwarded message", and the report counts them as `attachments_forwarded`. `content_sha256` is unchanged in its form (the converted content and the IDs of the message's own attachments). Supersedes the sentence of D-M8-04-6 on the embed. | `fn-import-migration-7`: the fields, the author and the footer of an embed were dropped although 22 6.3 says that what cannot be mapped stays as readable text, and the attachments of a forward vanished without a count. Loading them was not built: the origin key of a file is `file:<attachment_id>` (22 7.1), a forward carries the attachment objects of the message it copies, nothing the tool reads tells them from the attachments of the original (not measured against the real Discord), and a file hangs on exactly one message of its uploader in its channel (R-FI-08). With the same ID the original message and its forward would name one file, and the batch of whichever comes second would be refused, which can stop the import of an original message; a key per forwarding message changes the import interface. A message with an embed that has fields gets another `content_sha256` than before; a batch replayed across the update of the tool counts such a message as changed at the source and changes nothing. |
| AUD-SC1/10 | 2026-11-12 | The fake server of the tool's unit tests (`bothyapi/bothytest`) applies the rules of AUD-SC1/1 to AUD-SC1/3 (display texts and the topic length, content without a file, and a pin limit when a test sets one with `SetPinLimit`) and can refuse a batch with a field error (`RefuseBatch`). A unit test holds the topic length of the fake equal to `TopicMaxChars`. | The audit named the cause that let the fault through: the fake and the fixture did not know the cases, so no unit test could fail. With the rules in the fake, a tool that sends such a value fails its unit tests; the proof against the real server stays in `test/importtool`. |
