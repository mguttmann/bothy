# M7-21 Status page in apps and console

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-M7-21-1 | 2026-10-26 | One view, three surfaces: `StatusScreen` of `admin_ui` reads its page and its changes through the port `StatusSource` (`load`, `changes`, `unreachable`). The apps implement it with `LiveStatusSource` over `getStatus`, the sync engine's `status.updated` (a new hub `StatusEventsHub` announced after the commit of the event's page; nothing is stored) and the engine's connection state; the console, which uses neither `sync_engine` nor `local_store`, with `PollingStatusSource` over `getStatus` every `client.status_poll_interval`, a new key of place `App` (default `30s`) in the configuration reference and `AppConfig`, the rule of D-W-115 for a named client value. A read requested while one runs runs once after it, so the last change always reaches the page. | Brief Design note 1 and requirement 12; 15 3.1. |
| D-M7-21-2 | 2026-10-26 | Unreachable rule: the page shows "Server unreachable" and hides every state (components, overall state, incidents) while the source reports the server unreachable or the last read got no answer at all; once the connection is back the page is read again before it shows, so a page from before the outage never reappears as current. In the apps `offline` and `backoff` of the connection state are unreachable, `live`, `catchingUp` and `resyncing` reachable; `connecting`, `identifying`, `suspended`, `signedOut` and `updateRequired` keep the last answer. A read the server answers with a problem is no outage: it shows the server's reason (`ProblemBanner`). | Brief requirement 14; 16 12 "Limit". |
| D-M7-21-3 | 2026-10-26 | Owner texts (`body_md` of incidents and updates) render with `DsMarkdown`, the renderer of messages: its safe subset (no HTML, images as text, links only by its link policy), no mentions and no attachments; an active link opens through the host (system browser in the apps, a new tab in the console) and stays inactive where the host gives none. | Brief requirement 15; SEC-OUT-1, SEC-OUT-2. |
| D-M7-21-4 | 2026-10-26 | Maintenance: the read model has no separate flag for the maintenance mode (16 12 item 8 derives it into the states), and `overall_state` is also `maintenance` when the owner sets one component to `maintenance` in normal operation, so the page shows a neutral maintenance banner ("Maintenance is in progress", no claim that changes wait) whenever `overall_state` is `maintenance`, and lists open incidents of kind `maintenance` as "Maintenance windows" apart from "Open incidents"; maintenance uses the state role `info` and its own icon, outages `warning`, `attention` and `danger`. | Brief requirement 16; ADR 0065 item 6. |
| D-M7-21-5 | 2026-10-26 | Forms: they show only when `getMe` says the caller is an owner, because `status.manage` is an owner action (05); the server still decides each change. Each form builds the generated body of its operation; a change of a component sends the name (required by `StatusComponentInput`) and only the members that changed, because the server keeps every member the body leaves out; `health_source` is offered for components without an agent (the server creates the components of agents); an incident starts now (`started_at` is the clock at "Publish"), with the server's default state of its kind preselected. The administration lists "Status page" for owners; every person has the page itself at `/status` in the apps. | Brief requirement 15; D-M7-09-8. |
| D-M7-21-6 | 2026-10-26 | Public page: the console serves `/console/public-status` (not an administration page, so no login and no step-up), linked from the login; it reads `getPublicStatus` on the same interval and says "This instance shows its status only after login" for the server's `404`. | Brief Goal; 05 `status.public.read`. |
| D-M7-21-7 | 2026-10-26 | Differences to the brief's names (D-W-100, the merged code wins): the console page `/console/status` and its navigation entry existed as a placeholder and now host the page; the place in the administration is `AdminSection.status`; the apps' path is `/status` (a `SectionLocation` with area `status`, on the phone in the Me tab); the owner operations are part of `AdminRepository` through `StatusRepository`, as the statistics are (D-M6-06-5); the client tests live in `apps/client/test/status/`. | D-W-100, D-W-125. |
