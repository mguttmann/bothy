# FEAT-RUNNER-BG-SESSIONS Claude Code runner on background sessions

Owner order of 2026-11-16: the Claude Code runner shall be able to run its turns as Claude Code
background sessions (`claude --bg`), as an opt-in mode beside print mode, and the path shall be
tested. The design with its evidence, the alternatives and the risks is
[runner-background-sessions.md](../design/runner-background-sessions.md); its decisions D-BG-1
to D-BG-13 are the rulings 1 to 13 below, as built. Normative text: 09 18.1, 18.2 "Background
mode", 18.3 to 18.7, 18.9 and 21.

Everything about the CLI below was run with the pinned Claude Code 2.1.325 against the local
stand-in for the API (`plugins/claude-code-runner/tests/real_cli/stand_in.py`) with a `HOME`
and a configuration folder of its own, a key helper that prints a dummy key and a trust entry
for the working folder: no login and no model call. The recordings are in
`plugins/claude-code-runner/tests/fixtures/recording/background_2.1.325/`, and level one of the
real-CLI suite (`tests/real_cli/test_background.py`) runs the same mechanics with the runner's
own functions. What rests on a login (that a request of a session on a stored login carries a
beta whose name starts with `oauth-`) comes from the runs of the design and is held by a
level-two test that was not run in this ticket.

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-FEAT-RUNNER-BG-SESSIONS-1 | 2026-11-16 | `runner.launch_mode` is `print` (the default) or `background`; `runner.background_channels` is a list of channel ids, empty by default, and with entries only runs in these channels use background mode. `runner.background_status_interval` (default `2s`, above zero) is the interval of the session list. All three are read at start. Without `runner.launch_mode` the runner builds no part of the mode and calls no command of background sessions (`tests/unit/test_byte_equal_baseline.py`, `test_without_the_key_no_command_of_background_sessions_runs`). | Nothing changes until an operator opts in, the opt-in can be one forum, and the way back is one key. A member of the binding would need the server, the API and the apps (D-BG-1). |
| D-FEAT-RUNNER-BG-SESSIONS-2 | 2026-11-16 | Background mode runs only the turns of the runner's own agent in billing mode `personal`. Every `organization` turn, every turn of a hosted agent, every turn that loads a channel skill folder (26 5.9, `test_a_turn_that_loads_channel_skills_stays_in_print_mode`), the compaction of a full context and the one-shot calls (search assistant, builder of the interview) stay in print mode; the retry after a compaction runs as a session again. | A background session takes no API key from the environment; a hosted turn below `host` runs `--restricted`, for which the CLI binds no inbox socket, and is never adopted; the launch command of a background session has no `--plugin-dir`, and such a folder was not run with a session, so a background turn would lose the skills of its channel without a note; `/compact` is an input line of print mode, and both modes share the session store (D-BG-2). |
| D-FEAT-RUNNER-BG-SESSIONS-3 | 2026-11-16 | The launch is one command `<claude> [--resume <id>] --bg --name bothy-<run id> --model <model> <class flags> [--add-dir <folder>] --append-system-prompt-file <file> --messaging-socket-path <socket> --settings <file>` in the project folder, the prompt on its stdin, with the allow-list environment plus `DISABLE_AUTOUPDATER`. The class flags are those of 18.2 without `--permission-prompts none` and with `--disallowedTools AskUserQuestion` under `scoped` and `host`. The settings file holds exactly `crossSessionInbound` `accept`, `worktree.bgIsolation` `none` and an `env` block (later rulings changed this list; since D-FIX-RUNNER-BG-NO-PROMPT-1 every file also holds `permissions.denyInsteadOfPrompting` `true`). The CLI makes the id of a new session: the runner reads it from the session list, moves the session lock and the session's state folder to it and reports it. Before a resume an entry of the session under the name prefix `bothy-` is stopped and removed; an entry under another name is never touched (`session_busy` with a process, print mode without one). A copy at a resume ends the run with the cause `background_session_copied`. | The CLI ignores `--session-id` for a background session; of the launching command's environment only `PATH` reaches the session; without `bgIsolation` `none` the session moves into a worktree of its own and its transcript with it; a resume of a session that still has an entry starts a copy (D-BG-3). |
| D-FEAT-RUNNER-BG-SESSIONS-4 | 2026-11-16 | The files of a launch (settings file, system prompt file, stdout and stderr of the launch command) and the inbox socket lie in `<runner.state_dir>/bg/`, named after the run; the socket's name is the first 16 hexadecimal digits of the SHA-256 of the run id. They go when the run left the runner. With `runner.launch_mode` `background` the start is refused, naming `runner.state_dir`, when the socket path is longer than a socket address of the system allows. | The session's own folder is renamed when the CLI's id is known, and a live process keeps the paths it was started with; the system bounds a socket path, and a run id is longer than the digest. |
| D-FEAT-RUNNER-BG-SESSIONS-5 | 2026-11-16 | A follow-up, the retry line after an account error and every other input of a running turn is one JSON line on the session's inbox socket, with the `uuid` and the text the line has on stdin in print mode. `delivered` follows the write, `absorbed` the echo in the transcript (`queue-operation` `remove` with `absorbed_mid_turn`, or a `user` record with `origin.kind` `peer`). `capabilities.followups` stays `steer`. The runner prompt of a session started in background mode gains one paragraph: a relayed message with the runner's lead-in, or the runner's retry line, is followed like the person's own. The prompt of a print turn keeps its bytes. | The channel the runs proved, with the timing of the stdin line and an exact echo. The CLI introduces such a line as a message of another Claude session, so the model is told who relays it (D-BG-4). |
| D-FEAT-RUNNER-BG-SESSIONS-6 | 2026-11-16 | The live source is the session transcript and the session list `claude agents --json --all` (one reader for all turns of the runner process; `status`, `pid`, `waitingFor`, `sessionId`, `id`, `kind` and `name` of own entries, never `state`). Each transcript record is mapped to the stream message of 18.4 that means the same (`bgtranscript.py`), so the live box, the turn record, `ProcessState` and the rules of 18.5 and 18.9 run one code path in both modes. A turn ends at `system` `turn_duration`; its answer is the text of the turn's last assistant message. After a turn end the runner waits for a reading of the list taken after it: `busy` without a turn the transcript already shows is background work. A session that waits for a person is stopped (cause `background_session_waiting`). | The session list is the only surface the documentation calls supported, and `state` did not follow the turn in the runs. One mapping keeps every rule of print mode instead of a second copy of them; the class test `test_a_recorded_transcript_gives_the_decisions_of_its_print_stream` holds both against the recordings (D-BG-5, D-BG-6). |
| D-FEAT-RUNNER-BG-SESSIONS-7 | 2026-11-16 | Not available in background mode: steps inside subagents and workflows (each is the one `tool_call` step of its tool), the list of background tasks (`/metrics/background_jobs` is 1 while the list says `busy` between turns, and a summary names lost work without a count; superseded for background shell commands by D-FIX-RUNNER-BG-VISIBILITY-2, which lists them), `system/status` and `system/api_retry`, `rate_limit_event`, and the context window of a model the session's store does not know. While the list says `busy` during a turn, each reading counts as one progress event. | The transcript of the main conversation and the session list carry none of these; the progress events keep a long tool call from being reported stalled (D-BG-6). |
| D-FEAT-RUNNER-BG-SESSIONS-8 | 2026-11-16 | A stop is `claude stop`, then SIGTERM and SIGKILL to the session's process group while a process of the recorded identity lives, then `claude rm`. The end of a run is the same stop (the release), then the costs, then `claude rm`, then `run.finish`. An orderly stop of the runner stops its background turns with `adapter_stopped`, also with `runner.turn_handover`. A cancellation while a launch is under way stops and removes that session and ends the run `cancelled`; right after a launch the entry names no process yet, and level one holds that `claude stop` and `claude rm` at that moment leave no session that takes the prompt. A session whose entry names another process than the launched one is stopped (cause `background_process_replaced`). | A background session does not end by itself, and its totals are written only when its process ends. The keeper and the named pipe are parts of print mode. A session that may have taken the prompt must not be started a second time from the inbox (D-BG-7). |
| D-FEAT-RUNNER-BG-SESSIONS-9 | 2026-11-16 | The costs of a run are the difference between the session's totals in the last `cost-state` record after the release and the stored values, by the rules of 18.7. While the run works `/cost` is priced from `message.usage`. Without any totals (a process killed hard) the run books the priced values of its `assistant` messages and logs `costs_priced_without_totals`. The CLI's own requests for a background session are not booked. | `cost-state` is the line the runner already reads before a resume, cumulative across the processes of a session. The CLI's own requests are in no transcript and follow the small-model alias of the host user's settings (D-BG-8). |
| D-FEAT-RUNNER-BG-SESSIONS-10 | 2026-11-16 | Account errors, the wait, the schedule, the give-up and the summaries of FIX-RUNNER-LIMIT-KEEPS-RUN are unchanged: the API error record and the `turn_duration` after it give the same events, and the retry line goes to the inbox socket. | `ProcessState` decides from the same events in both modes; level one runs a refused request, the retry line and a background command that lives through refused turns (D-BG-9). |
| D-FEAT-RUNNER-BG-SESSIONS-11 | 2026-11-16 | The runner installs, starts and stops no supervisor. Before every launch it reads `claude daemon status`: without a supervisor the launch starts one, and the runner records it (process id and start time, `<runner.state_dir>/bg/supervisor.json`) when the launch printed that it started the service; it launches under a running supervisor only when that is the recorded one in the pinned version. Any other supervisor makes the run use print mode (`background_supervisor_foreign`, `background_supervisor_version`). The runs of one runner process check, launch and record one after the other, so runs that start together launch under the same supervisor. `run_slots` counts a background turn until its release; `degraded_reasons` gains `background_unavailable` for a cause of the host. | Sessions inherit the supervisor's environment, so only a supervisor a launch of the runner started carries the allow list of 18.2 and nothing else. `claude daemon stop` would end sessions of the host user. A run that read the supervisor between the launch of another run and its record would take the runner's own supervisor for another program's. The heartbeat lists are closed, so no new member (D-BG-10). |
| D-FEAT-RUNNER-BG-SESSIONS-12 | 2026-11-16 | A new runner process adopts a background turn with every right: it finds the session by the short id of the turn record or by its name `bothy-<run id>`, takes the thread and session locks itself, maps the transcript from the launch offset to the stored offset again and drives the turn on with follow-ups, retry lines and a stop, with or without `runner.turn_handover`. A live process of an ended run is stopped and removed; a process that is not the recorded one is stopped and counts as gone; without a process the run is finished from the transcript when a turn end follows the stored offset or the record holds a decided end, else it is left to the server. The end of an adopted turn has no recovery. A record of a background turn is settled the same way after the key went back to `print`. | No channel of a background session belonged to the old runner process, and a session process cannot inherit lock descriptors. No process is ever started for an adopted run (R-AG-17) (D-BG-11). |
| D-FEAT-RUNNER-BG-SESSIONS-13 | 2026-11-16 | A run that should use background mode and cannot uses print mode for all its processes. The live box says once "Background sessions are not available (`<code>`); this run uses print mode.", the log has `background_fallback`, and the codes are `background_version_untested`, `background_supervisor_foreign`, `background_supervisor_version`, `background_bypass_not_accepted`, `background_workspace_untrusted`, `background_session_foreign` and `background_launch_failed`. The fallback happens only while it is certain that no session took the prompt (the launch exited with an error, or, watched for `runner.cli_probe_timeout`, no session of the run is listed or its entry got no process and its transcript no prompt); in every other doubt the session is stopped and removed and the run ends `runtime_error` with the code as its cause. The runner never writes the CLI's trust entry or its acceptance of bypass mode (the trust entry of a bound project folder: superseded on 2026-11-22 by D-FIX-RUNNER-NEW-PROJECT-TRUST-1). The mode runs only on the pinned version. | The mode is an optimisation and both modes continue the same session, so a refused launch must not fail a run; a prompt must never run twice; trust and bypass acceptance are decisions of the host user (D-BG-12, D-BG-13). |
| D-FEAT-RUNNER-BG-SESSIONS-14 | 2026-11-16 | The interface is held on three levels. Recordings of the pinned CLI (`tests/fixtures/recording/background_<v>/`, written by `tests/real_cli/record.py`, `--only background` for this folder alone): the launch output per case, the session list per state, the outputs of the control commands, the transcripts of five scenarios with the print streams of four as twins, and the member table. Fake-Claude gains a background side (`tests/fake_claude/fake_bg.py`) that every unit and scenario test uses; a test holds every member it writes against the member table. Level one of the real-CLI suite runs the mechanics with the runner's own functions and compares the member table with a fresh run. The recorder keeps only the record types the runner reads; `test_no_account_identifier_leaves_the_transcript` holds that no value of a record with account identifiers reaches a file of the runner, a log line or a request. | The transcript format, the socket line and the output texts are internal to Claude Code and can change with any release, so a change of the pin must find every difference (D-BG-12). |
| D-FEAT-RUNNER-BG-SESSIONS-15 | 2026-11-16 | The end-to-end test of the mode (`tests/realserver/test_background.py`: a post, a follow-up, a stop) starts a server of its own, on which the owner revokes the grants of persons on the space Support and switches Lotse to `personal` with themselves as the credential holder. | I1 allows `personal` only while the credential holder alone can trigger; on the server the other end-to-end files share, the switch would refuse every flow Alex triggers. |
| D-FEAT-RUNNER-BG-SESSIONS-16 | 2026-11-16 | Level two of the real-CLI suite has one background turn on the stored login (`test_real_background_turn_runs_on_the_stored_login`, behind `CLAUDE_CODE_RUNNER_REAL_TURN=1` and `CLAUDE_CODE_RUNNER_REAL_BG_FOLDER`). It refuses to start while a supervisor runs and stops and removes only its own session. It was not run in this ticket; the function that reads the path of a turn and the login beta from a transcript is held by level one. | A real turn on a login is the owner's decision, and the ticket forbade one. Whether a background turn draws a subscription like an interactive session is not proven by any test: it is a measurement of the operator on their own account. |
| D-FEAT-RUNNER-BG-SESSIONS-17 | 2026-11-16 | One finding of SonarQube Cloud is suppressed on its line with `NOSONAR`: `bgsession.launch` opens the files of the launch command's stdout and stderr with `Path.open` inside an asynchronous function (rule `python:S7493`, counted once per file). | Both are small files of the run on the local disk, opened once right before the command that writes them starts. The runner writes its other private files of a run without an asynchronous file API as well, and a thread for the two opens would add a failure path to every launch for no gain. The other findings of that analysis (cognitive complexity, the `timeout` parameters) do not fail the quality gate and are left for a change of their own. |

Left for later, as the design lists in its section 7.5: background mode for hosted agents and
for `organization` turns, channel skills in background mode (`--plugin-dir` on the launch
command, proven on the pinned CLI), a member of the binding for the mode, leaving background
turns for the next runner at an orderly stop, steps inside subagents and workflows, following a
process the supervisor started again, a second source of the answer, and a key that accepts a
supervisor the host user started.

Deploy note: none. The default is `print`; nothing here enables the mode anywhere. Before an
operator sets `runner.launch_mode = "background"`, the README section "Background sessions"
names the one-time steps on the host (the pinned CLI version, workspace trust per bound folder,
the acceptance of bypass mode for tool class `host`).
