# demo-compose-api-restart Demo survives a restart of api

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-demo-compose-api-restart-1 | 2026-10-27 | The network namespace of the demo is held by `demo-net` (the pinned image of `demo-exchange-init` running `sleep infinity` under `init`), which publishes `DEMO_PORT` on `127.0.0.1` and carries the name `api` on both networks; `api`, `demo-tls`, `demo-agent` and `demo-host` join it with `network_mode: service:demo-net`, and all of them restart unless stopped. The TLS front keeps forwarding to `127.0.0.1:8080`, so the server still sees a loopback peer (SEC-TLS-1). | A restart of `api` gave it a new namespace and left the front, the agent and the host in the old one, where the port led nowhere (demo test R2); a holder that runs nothing never restarts on its own, and the engine starts it before the containers in its namespace when Docker restarts. Moving the front onto the Compose network instead would make the server trust a non-loopback peer. |
| D-demo-compose-api-restart-2 | 2026-10-27 | `demo.sh` takes `DEMO_PORT` (1 to 65535, free on `127.0.0.1`, else exit `2`) in place of the free port, and `DEMO_CHECK_RESTART=1` restarts `api` once the demo is ready and ends with `0` only when discovery answers again through the published port and in the demo agent and the server listens on `127.0.0.1:8080` inside the demo host. The check is a manual run like `make demo`, not a CI gate; the tools tests hold the overlay layout. | A long-running demo keeps its address across runs; the check needs the server image and minutes of warm-up, which the CI does not build for the demo. |
