# FIX-host-open-gate-slow The gate before a PTY ends with the opening window

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-HOGS/1 | 2026-11-07 | One run of the service-side checks (`doctor.RunService`, also the `Light` run of the gate, D-M2-45-12) reads each answer of the user database once: every account lookup, the account list, the groups of an account and the ID of a group are cached for the run (`hostos.Scope`); on macOS a lookup is the search of the name in the one `dscacheutil -q user` of the run. The next run reads fresh answers. | Each lookup started `dscacheutil` and read the whole user database, so one gate run started dozens of programs one after the other and on a loaded host could outlast `terminal.open_timeout`; every opening there then ended `open_failed` with `open_timeout`. The peer check of the helper channel looks its session user up in the same cache (`doctor.UsersHelpers`). A run takes a snapshot of the host anyway; an account that changes during one run is seen by the next. |
| FIX-HOGS/2 | 2026-11-07 | The gate run of an opening ends with the opening window (`HostSessionOpen.expires_at`): its context carries that deadline down to every program the checks start. A run cut short by it refuses the opening with `open_timeout` and applies nothing: no `report`, no end of running sessions, the last result stays, and the helper answers it got are not kept for later runs. | Without local confirmation the server has ended the opening at that point anyway (24 6.1 step 6); with `require_local_confirm` the pairing stops that deadline, but the host does not wait longer for its own checks than the window, and a run that went on overlapped the next try of the person and slowed it too. A partial run proves nothing, so it must neither report a finding nor end a session. |
| FIX-HOGS/3 | 2026-11-07 | The LaunchAgent of the owner account mode (`owner.plist.tmpl`) sets `ProcessType` to `Adaptive` instead of `Background`. The system service plists and the units of Linux and Windows set no such class and stay. | launchd applies the resource limits of `Background` (CPU and I/O throttling) to the job at all times, which stretched every gate run on a loaded host; `Adaptive` lets launchd move the job between the background and the interactive class. The effect is not covered by a test. |
