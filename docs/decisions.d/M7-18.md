# M7-18 Capacity load test

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-M7-18-1 | 2026-10-26 | Scenario (Design note 1, `tests/load/README.md`): a seeded world (seed `20261026`) of Sam, Robin and `person-<n>@example.com` with local accounts and own devices, one space with one text channel per 20 people (the fan-out of a message), the first member of each group an observer of commit to dispatch; open-loop sends at the rate of a step from as many senders as keep each within half of `ratelimit.rl.message.per_minute`, every sender connected to the gateway; steps of 50, 100, 200, 300, 400, 600, 800 and 1000 messages per second, each 15 s warm-up, 60 s measured, up to 10 s drain; texts of 20 to 400 characters from a fixed vocabulary. A step misses on `perf.message_create_p99`, `perf.fanout_local_p99`, a failed send, a missing dispatch or a failed connection; the ramp stops there, and the sustained throughput is the goodput (sends answered `201` within `perf.message_create_p99`, per second) of the last step that held. Every value is a constant of `services/server/test/load/params.go` and is repeated in the result file. | The rows of 16 13 need connections, fan-out and the counter under one load that grows; groups bound the fan-out so the gateway, not one huge space, is measured. |
| D-M7-18-2 | 2026-10-26 | Installation and profile: `make load-capacity` takes the interface of `make portability` and its installation path (signature check, `install.sh` with `--storage fs` and the options of `tests/portability/install-options`); the overlay `local` runs with Prometheus and the collector only (Loki and Tempo filled the disk of the Docker host in the first run). The profile mode follows ADR 0063 from the vCPUs and memory of the Docker runtime; a Compose override gives `api` and `worker` `GOMAXPROCS` and `cpus` of `perf.reference_profile`, PostgreSQL `cpus` and `mem_limit`, and lets `api` trust the forwarding headers of the network of its published port, so every simulated person is its own client as behind a reverse proxy. The seeding runs with raised rate limits (`admin`, `public_auth`, `write`, `read`, `gateway_connect`), the ramp after a restart with the defaults. The layout stays the installation's (`api` and `worker`, not one process with role `all`); the report records it. The driver runs in a container in the network of the Docker host, so its CPU is sampled with the stack. | The brief asks for the stack from the images on the documented path; the profile limits make the measurement comparable to the other load tests; the restart keeps the measured server at its defaults. |
| D-M7-18-3 | 2026-10-26 | Gate value and margin (Design note 2): `perf.capacity_steady_messages_per_s` is the highest ramp rate that held in most runs of the measurement (300: the runs on the build host held up to 200, 300, 300 and 400 messages per second, and the run that missed at 300 still answered 276 per second within the target), `perf.capacity_min_messages_per_s` is 80 % of it (240). Margin rule: the minimum is 0.8 times the steady rate, the steady rate a rate that held in most runs on the reference profile; a later measurement may raise both by this rule, never lower them (ADR 0063 point 5). The gate is `TestPerf_CapacitySteadyThroughput` in `make perf` (`perf/capacity`), the scenario as one steady step of 15 s plus 45 s; a dropped connection fails it whatever the goodput. | One named value per rule (02 section 22); a run on a busy host varies by a step, the margin keeps one noisy step from failing a healthy change while a collapse (the missed steps answered 190 to 380 per second) still fails. |
| D-M7-18-4 | 2026-10-26 | The harness of `make perf` on the build host runs the server process on the host and PostgreSQL in the Docker VM, so every statement crosses the port forward of the VM: there the steady run at 300 answered 69 per second within the target and the M1 target `perf.message_create_p99` at 200 per second measured 272 ms. Both are recorded as not proven on this host; the gate value comes from the stack in the VM, where server and database share the network as in an installation. | The harness of this host is no evidence for the capacity (mode `emulated`, but a topology no installation has); a host where the harness meets the M1 targets is the place of the gate. |
| D-M7-18-5 | 2026-10-26 | Names that differ from the brief (D-W-100): the Go code of the scenario is `services/server/test/load` with the command `bothy-load` (it uses the generated client `api/rest`), the runner `tools/load/capacity_run.py` behind `make load-capacity` (the Python tooling of the repository runs in `tools/`, as D-M7-14-6), `tests/load/` holds the README; the gate lives in `services/server/perf/capacity`. Server metrics come from Prometheus (export every 5 s), memory and CPU from `docker stats`, sizes from PostgreSQL; the p99 of `bothy.db.event_seq.lock_wait` has the resolution of its histogram buckets (first bound 5 ms). | Merged names win; the requirements stay the same. |
