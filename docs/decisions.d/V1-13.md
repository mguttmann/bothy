# V1-13 Platform runs of the host service: causes read from run 46103059338

Plan row V1-13 (`docs/PLAN.md`), issue 622. The three jobs `platform suite` of
`.github/workflows/host-platform.yml` failed in run 46103059338 of 2026-11-28 on `main`. Each
cause below was read from the log of that run and reproduced off the runner where a machine
could; what stays open is listed in the "Open" part of
[AUD-misc-misc-01.md](AUD-misc-misc-01.md).

| No | Date | Ruling | Reason |
|---|---|---|---|
| V1-13/1 | 2026-11-28 | Before the suite the Linux job also removes every ACL entry of `/opt` itself (`setfacl -b /opt`), next to the owner and mode of AUD-MISC-MISC-01/1; the folder alone, not its content. `tools/ci/tests/test_host_platform_workflow.py` asks for all three. | The failure step of run 46103059338 printed `/opt` as `drwxr-xr-x+` with the default ACL `default:user:runner:rwx`, `default:other::rwx` and `/opt/bothy-platform` and `/opt/bothy-platform/bin` as `drwxrwxrwx+`. A new folder takes a default ACL of its parent in place of the umask, so every folder the suite created below `/opt` was writable by every user, and `bothy-host` refused its start with `claude_bin_untrusted`, `program_location_untrusted` and `shared_location` for both session users. Reproduced in an `ubuntu:24.04` container: with that ACL on `/opt` and umask `022`, `mkdir -p /opt/bothy-platform/bin` gives `0777`; after `setfacl -b /opt` it gives `0755`. A stock system has no ACL on `/opt`, so the product stays as it is. |
| V1-13/2 | 2026-11-28 | The suite reads the exit code of a stopped launchd job with `launchdExitCode` (`test/platform/launchd.go`, untagged): the number before a `:` of the line `last exit code = `, and no code while the job runs or never exited. `TestLaunchdExitCode` holds it in `make check`. | `launchctl` prints a code with a name in `sysexits.h` as `last exit code = %d: %s` (format strings of `/bin/launchctl`), so the refused start reads `78: EX_CONFIG`. The suite parsed the first word `78:` as a number, got 0, and every test that expects a refused start on macOS failed with `start not refused with 78` while `doctor` named the expected code (TM-T13, TM-T22, TM-T24, TM-T27, the exit policy). |
| V1-13/3 | 2026-11-28 | HD3 runs `sudo -n -- <true>` with `true` by absolute path, the first of `/usr/bin/true` and `/bin/true` that exists, still with an empty environment (`hostos.UnixProbe.SudoWithoutPassword`). `TestSudoProbeMatchesSudo` compares the probe with `sudo -n true` run in the environment of the test. | The probe ran `sudo -n true` without `PATH`. sudo then finds a bare command only through `secure_path`, which Ubuntu sets and macOS does not, so on macOS sudo ended with `true: command not found` and HD3 never reported a passwordless sudo rule, for the service user or in a helper (TM-T13 `passwordless sudo` in run 46103059338: `doctor 0, want 1`). The check failed open; this is a fix of the product. Reproduced on a macOS build host whose account has a passwordless sudo rule: `env -i /usr/bin/sudo -n true` exits 1 with that message, `env -i /usr/bin/sudo -n /usr/bin/true` exits 0, and the new test failed before the change. |
| V1-13/4 | 2026-11-28 | The command that starts the nohup child prints its process ID with `echo BG=$!` at the end of the line, without quotes. The commands the suite types on Linux and macOS (except the size, which needs a terminal) live in the untagged `test/platform/typed_unix.go`, and `TestTypedCommandsInInteractiveShells` runs each through an interactive `zsh` and `bash` and expects its expression. | Interactive zsh expands history: `!` followed by a double quote turns that off for the rest of the line and is removed, so `echo "BG=$!"` left an open quote, the login shell of a macOS session user waited for more input, and the PTY tests that start background processes failed with `output never matched` (`TestPlatform_PTYRunsAsSessionUser`, `TestPlatform_HelperChannelBreak`, `TestPlatform_TMT21_Sessions`). Reproduced with zsh in a PTY and with zsh reading standard input (`dquote>`, `unmatched "`); the bash 3.2 of macOS refuses the old line as well. |
| V1-13/5 | 2026-11-28 | TM-T26 stages its fake helper on macOS as on Linux (`stageUnixImpostor`): after the unprivileged attempt it boots the launchd job of the helper out, moves a socket the session user bound onto the endpoint and bootstraps the job again in the cleanup. The attach check on macOS counts only what lldb shows: exit 1 with `attach failed` is a refused attach, exit 0 with `Process <pid> stopped` an attach, anything else (no helper running, no answer) fails the test. | launchd owns the endpoint of the helper (the `Sockets` entry of the job `bothy-host install` writes) and starts the real helper on the next connection, so on macOS the host service always reached the real helper and `doctor` passed HD10: the test never put an impostor in place there. The attach check read the exit code alone; it now cannot pass when lldb did not run. Whether a process of the session user can attach to its helper on the hosted macOS runner (`a process of the session user attached to its helper` in run 46103059338) is read from the next run with this output. |
| V1-13/6 | 2026-11-28 | On Windows the cleanup of a test removes each service of the suite completely: stop, end its process when it does not stop within the bound of the suite, delete, and wait until the service control manager no longer knows it. On macOS and Windows a failed test prints the last 30 lines of `bothy-host.log` before the cleanup removes the state directory. | In run 46103059338 every `install` after the first test failed with `win.service bothy-host-helper-<user>: The specified service has been marked for deletion`: `sc.exe delete` of a service whose process still runs only marks it, and the next test created the service again a few seconds later, so one failure turned into 21. The log of the host service lies in the state directory on both platforms (AUD-host-01), which the cleanup deletes; Linux keeps its journal. |
