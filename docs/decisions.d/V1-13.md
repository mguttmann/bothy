# V1-13 Platform runs of the host service: causes read from run 46103059338

Plan row V1-13 (`docs/PLAN.md`), issue 622. The three jobs `platform suite` of
`.github/workflows/host-platform.yml` failed in run 46103059338 of 2026-11-28 on `main`. Each
cause below was read from the log of that run and reproduced off the runner where a machine
could; what stays open is listed in the "Open" part of
[AUD-misc-misc-01.md](AUD-misc-misc-01.md).

| No | Date | Ruling | Reason |
|---|---|---|---|
| V1-13/1 | 2026-11-28 | Before the suite the Linux job also removes every ACL entry of `/opt` itself (`setfacl -b /opt`), next to the owner and mode of AUD-MISC-MISC-01/1; the folder alone, not its content. `tools/ci/tests/test_host_platform_workflow.py` asks for all three. | The failure step of run 46103059338 printed `/opt` as `drwxr-xr-x+` with the default ACL `default:user:runner:rwx`, `default:other::rwx` and `/opt/bothy-platform` and `/opt/bothy-platform/bin` as `drwxrwxrwx+`. A new folder takes a default ACL of its parent in place of the umask, so every folder the suite created below `/opt` was writable by every user, and `bothy-host` refused its start with `claude_bin_untrusted`, `program_location_untrusted` and `shared_location` for both session users. A stock system has no ACL on `/opt`, so the product stays as it is. |
| V1-13/2 | 2026-11-28 | The suite reads the exit code of a stopped launchd job with `launchdExitCode` (`test/platform/launchd.go`, untagged): the number before a `:` of the line `last exit code = `, and no code while the job runs or never exited. `TestLaunchdExitCode` holds it in `make check`. | `launchctl` prints a code with a name in `sysexits.h` as `last exit code = %d: %s` (format strings of `/bin/launchctl`), so the refused start reads `78: EX_CONFIG`. | V1-13/3 | 2026-11-28 | HD3 runs `sudo -n -- <true>` with `true` by absolute path, the first of `/usr/bin/true` and `/bin/true` that exists, still with an empty environment (`hostos.UnixProbe.SudoWithoutPassword`). `TestSudoProbeMatchesSudo` compares the probe with `sudo -n true` run in the environment of the test. | The probe ran `sudo -n true` without `PATH`. sudo then finds a bare command only through `secure_path`, which Ubuntu sets and macOS does not, so on macOS sudo ended with `true: command not found` and HD3 never reported a passwordless sudo rule, for the service user or in a helper (TM-T13 `passwordless sudo` in run 46103059338: `doctor 0, want 1`). | V1-13/4 | 2026-11-28 | The command that starts the nohup child prints its process ID with `echo BG=$!` at the end of the line, without quotes. | V1-13/5 | 2026-11-28 | TM-T26 stages its fake helper on macOS as on Linux (`stageUnixImpostor`): after the unprivileged attempt it boots the launchd job of the helper out, moves a socket the session user bound onto the endpoint and bootstraps the job again in the cleanup. The attach check on macOS counts only what lldb shows: a nonzero exit with `attach failed` (and not `no such process`) is a refused attach, exit 0 with `Process <pid> stopped` an attach, anything else (no helper running, a helper that ended meanwhile, no answer) fails the test. | launchd owns the endpoint of the helper (the `Sockets` entry of the job `bothy-host install` writes) and starts the real helper on the next connection, so on macOS the host service always reached the real helper and `doctor` passed HD10: the test never put an impostor in place there. | V1-13/7 | 2026-11-28 | On macOS the attach part of TM-T26 runs only when `csrutil status` does not report System Integrity Protection as disabled; on a machine without it the test logs that this part is not provable there. | V1-13/9 | 2026-11-28 | Both ends of the pipes of the local channel (helper pipes and the admin pipe) use overlapped handles: `ListenPipe` creates every instance with `FILE_FLAG_OVERLAPPED` and waits in `ConnectNamedPipe` with an event that `Close` can end, `dialPipe` opens with the same flag, and the Go runtime runs reads, writes and deadlines of both ends on its completion port, as the pipe of the confirmation endpoint already did. `TestPipeWritesWhileAReadIsPending` and `TestPipeCloseEndsAccept` hold it; the Windows unit test step of the workflow now runs `internal/localchan`. | In run 46122005337 the host service refused each start with `HD10 helper_unreachable` exactly at the bound of one helper check (about three minutes after its start), while V1-13/8 showed every helper service `RUNNING` with exit code 0. The session channel of a helper (`helper.ServeSessions`) answers `hello` from a goroutine while its loop already waits in the next read; on a handle opened without `FILE_FLAG_OVERLAPPED` Windows runs the I/O of one file object one after the other, so the answer waited behind that read, and the host service, which sends nothing before the answer, waited until its bound. Linux and macOS use sockets, where a read and a write run at the same time. The change also settles the first two findings of D-M2-42-29 (an `Accept` that `Close` could not end, reads that did not end when `Conn.Call` closed the channel at its deadline). Proven by run 46128962469 on b7f0bb8e8: `TestPlatform_TMT29g_Token` passed, `doctor` reached every helper and sessions started on Windows; the new tests were not run against the old code on Windows. |
