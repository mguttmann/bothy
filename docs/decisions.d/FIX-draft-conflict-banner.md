# FIX-draft-conflict-banner The draft conflict notice and the phone thread header

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-DCB/1 | 2026-10-29 | Cause: the server reported `overwrote_newer` for every write whose `base_version` was absent or older than the stored version, without looking at who wrote that version. The composer writes the draft through the outbox, coalesced, one write in flight and one waiting; the waiting write carries the base the composer knew when the person typed, and the composer learns its own new version only when the answer of the write in flight is stored. So the second write of a freshly opened draft had no base, and every later write while typing had the base before the device's own last write: nearly every typed draft reported a conflict on the device that typed alone. The other device, its clock and the per-thread or per-channel key play no part; the clearing after a send deletes the row, so the next write starts at version 1 without a conflict. | Reproduced against the real server with two devices of one person (`TestDraftsOwnWritesNeverOverwrite`, `TestChannelDraftsOwnWritesNeverOverwrite`): the phone's second write without base answered `overwrote_newer: true` while the laptop wrote nothing. |
| FIX-DCB/2 | 2026-10-29 | The rule moves to the server (`domain.OverwroteNewer`): a stored row the client had not seen (base absent or older), written by another device (`updated_by_device_id` differs, or none is known), with different `content_md` or `file_ids` than the write; an empty write, which deletes the draft, never reports it. The upsert returns the replaced row from its statement snapshot (a `WITH prev` read in the same statement, no `RETURNING old`, which sqlc 1.31 does not analyse); the row is the replaced one only when its version is the stored version - 1, otherwise a concurrent write came in between and the conflict is reported as before. The client keeps its base handling and its notice. | One rule for all clients (iOS, Android, macOS, Windows) and for clients already installed; the client cannot tell who wrote the replaced version. A race of two first writes keeps exactly one notice (`TestDraftsConcurrentFirstWrite`). |
| FIX-DCB/3 | 2026-10-29 | The fake server of `sync_engine` applies the same rule. Before, it reported a conflict only with a base present, unlike the server, which is why no client test showed the false notice. | The fake must not drift from the server (brief M4-17 Design note 5). |
| FIX-DCB/4 | 2026-10-29 | The description of `base_version` in `docs/api/openapi.yaml` ("older than current sets `overwrote_newer`") stays: an older base is still a condition, and changing the text would regenerate the Go and Dart API clients for a comment; 04 14 holds the full rule. | No change of the contract shape. |
| FIX-DCB/5 | 2026-10-29 | The phone thread header has one overflow button `thread.more` (an icon with the tooltip "More actions"): its menu lists Edit title, Done or Reopen, Move and Session, then the entries of the thread or channel menu of M4-33 (notifications, mute until). The labelled "More" button stays in the wide header. | The screenshot of the report showed "... More" and "..." beside each other on the phone. |
| FIX-DCB/6 | 2026-10-29 | Restoring or syncing a draft changes no navigation: the composer and the new chat view only set the text of their field (`applyStored`, `restoreUnsent`); the routes change only on actions of the person on the same device (send, leave, open). The sidebar's draft row "New chat" is selected only by the route of the new chat view, not by an arriving draft. No link to the cross-device navigation report was found in the draft path. | Checked in `composer_controller.dart`, `thread_composer.dart`, `new_chat_view.dart` and the sidebar's new chat rows. |
