# FIX-macos-legacy-keychain-prompt No keychain dialog holds the start

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-MLKP/1 | 2026-11-01 | On macOS the old items of the login keychain (service `flutter_secure_storage_service`) are read and deleted only through the runner channel `bothy/legacy_keychain` (`apps/client/macos/Runner/LegacyKeychain.swift`, `LegacyKeychain` in `lib/platform/secure_store.dart`), never through `flutter_secure_storage`. The channel turns the user interaction of the keychain off for the call (`SecKeychainSetUserInteractionAllowed(false)`, restored afterwards) and runs on its own serial queue. Every other read of the old place (iOS, the Data Protection keychain) passes `kSecUseAuthenticationUI` = `kSecUseAuthenticationUISkip` (`u_AuthUIS`) through the plugin options. | Live report of 2026-11-01: a release build without keychain entitlements (secrets in the login keychain) stopped 0.3 s after launch on a keychain access dialog for an old item whose access list trusts only the code signing identifier of the old bundle identifier; nobody could click, the app stayed at 0 % CPU and never reached the server. Measured on macOS with a real keychain: a `SecItemCopyMatching` of such an item waits for the dialog also with `kSecUseAuthenticationUISkip` or `kSecUseAuthenticationUIFail` (those only cover items with an access control); with the user interaction off it answers `errSecAuthFailed` (-25293) at once, a delete `errSecInvalidOwnerEdit` (-25244). The plugin offers no way to turn the interaction off, and its calls run on one serial queue, so one waiting call holds every later one. |
| FIX-MLKP/2 | 2026-11-01 | Superseded by FIX-MMD/2 (docs/decisions.d/FIX-macos-migration-denied.md): a refusal is never final, no marker, the next start tries again; the move reads only what the build before the scope read (FIX-MMD/1). Original ruling: An old item that the keychain refuses without a dialog (`errSecAuthFailed`, `errSecInteractionNotAllowed`, `errSecNoAccessForItem`, `errSecUserCanceled`, `errSecInvalidOwnerEdit`) makes the old secrets not migratable: the copy takes nothing, not even the items it could read, logs it once (`secure_store`), records the marker `app/secret_scope`, and the app starts with enrollment. The refused items stay where they are. There is no fallback to the read path of the build before the scope: it reads the same items under the same access list, so it cannot get them without a dialog either. | The old items of one installation were written by one app, so one refused item means the others belong to that app as well; a partial copy (a device ID without its refresh token, a database key without the session) would start a half session. The marker keeps later starts from asking again and logging again; the items cannot be deleted without a dialog (-25244), and leaving them is harmless because no build of this identity reads them again. |
| FIX-MLKP/3 | 2026-11-01 | The start never waits for the keychain without an end: the copy of the old secrets has a deadline of 5 s (`FlutterSecureBackend.legacyDeadline`); a copy that does not finish in time is abandoned, writes nothing more and writes no marker, so the next start tries again, and the app starts without it. Every call of the backend (`read`, `write`, `delete`, `keys`) has a deadline of 15 s (`callDeadline`) and fails with a `TimeoutException` after it, which the start handles like any other failed read (the connect screen). | A dialog or a hanging platform call must end in a state the person can see, and an abandoned copy must not write old secrets over a session the app enrolled in the meantime. 15 s covers the 5 s of the copy plus the call itself. |
| FIX-MLKP/4 | 2026-11-01 | Evidence against a real keychain instead of fakes: `apps/client/macos/LegacyKeychainTests/run_tests.sh` creates a keychain file of its own (never in the user's search list) with an old item whose access list trusts only `/usr/bin/true` and one that trusts the checks binary, proves that a plain read of the first gets no value (on a Mac with a logged-in session it waits for the dialog), and runs `LegacyKeychain.swift` against both: refused at once, read, delete refused, delete, the interaction setting restored, `kSecUseAuthenticationUISkip` is `u_AuthUIS`. `apps/client/tool/run_legacy_keychain_test.sh` puts such a foreign item into the login keychain and runs `integration_test/legacy_keychain_test.dart` in the app: the move through the real channel finishes within 5 s with the refusal logged and no marker (FIX-MMD/2), the owner's case of FIX-MMD/4 moves, and an old item the app wrote itself moves. Both run in the macOS job of `platform-tests.json`. Not covered: an item with an access control that requires the person (user presence) needs a Data Protection keychain and a signed app, which the checks binary is not; such an item is covered by `kSecUseAuthenticationUIFail` in the channel's query and skip in the plugin's. | The Dart tests of FIX-secure-store-migration used storage fakes that answer every read at once; they passed while the real app waited for a dialog. Whether a read shows the dialog is decided by securityd from the item's access list and the caller's code signature, which no fake has. This is the second failure of this class after the update into the app scope (the first was the `readAll` -50 of FIX-secure-store-migration), so the class is fixed at the one place every old read goes through and tested against the real artifact. The Dart fakes now model the dialog as a plugin call that never answers, so a return to the plugin path fails the unit tests as well. |
| FIX-MLKP/5 | 2026-11-01 | Superseded by FIX-MMD/2: every refused status now writes no marker. Original ruling: `errSecInteractionNotAllowed` (-25308) stays a refusal of FIX-MLKP/2 for the copy (nothing is copied) but writes no marker: the move is left to the next start, which logs it again. Every other refused status writes the marker as FIX-MLKP/2 rules. An abandoned copy (FIX-MLKP/3) also writes no scope item and no pending list after its last copied item. | A locked login keychain or an iOS item read while the device is locked answers the same status with the user interaction off; a marker would lose the old session for good although it moves once the keychain is unlocked. A retry copies nothing before every read succeeded, so it cannot leave a half session. |
