# AUD-sdk-typescript-01 Runs of model commands, a lost end of a run, adapter state and the FakeServer against the contract

Six findings of the audit of 2026-11-11 against the TypeScript SDK (`sdk-typescript-1` to
`sdk-typescript-4`, `sdk-typescript-10` and `comments-3`). The first is a fault a person runs
into: a run started with a model command of an agent on the TypeScript SDK never started. It was
reproduced against the server of this tree before the change
(`sdk/typescript/test/live/model-command.live.test.ts`): the run ended `failed` with
`invalid_invocation_token` and no start. Normative text: 09 sections 4.5, 4.8, 4.9, 5.3, 5.5 and
10.4, 04 section 13.2, `docs/api/openapi.yaml`.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-ST1/1 | 2026-11-12 | `expectationFor` compares the `command_id` of the payload for an `agent.invocation` with `trigger_kind = command` (`sdk/typescript/src/invocation/verifier.ts`), in the canonical lower-case form like every other ID. A payload without `command_id` still has no counterpart and its token is `invalid`; `command_invocation_id` is never compared, because no token carries it. | Audit finding `sdk-typescript-1`: the contract (`AgentInvocationPayload.command_id`) and the server send the command since M2-16, and the token names it (09 10.4). The TypeScript SDK still returned no counterpart, so the adapter refused every such run and ended it `failed`. The Python SDK compares it since D-M2-37-15. |
| AUD-ST1/2 | 2026-11-12 | The proof of AUD-ST1/1 runs on three levels: the verifier with a signed token (`test/invocation.test.ts`), the adapter against the FakeServer (`test/loop.test.ts`) and the adapter against the real server (`test/live/model-command.live.test.ts`: the adapter declares a command, Alex invokes it through `invokeCommand`, the run starts once and ends `completed`). For it the FakeServer takes `trigger(text, { command })`, the port of `trigger(command=...)` of the Python FakeServer: the payload names command and invocation, every token of the run names the command, `getRun` answers `trigger_kind = command`, and `getRunContext` answers `500 internal_error` as the server does for a run without a triggering message (D-M2-37-16). The live driver gets the op `call` of `sdkserver` and the channel of the world. No scenario is added to the shared list of `sdk/testdata/scenarios/README.md`. | The finding went unnoticed because the FakeServer could only trigger message runs. A shared scenario has to exist in both SDKs (`sdk/python/tests/test_scenario_list.py` holds the list equal), and the Python SDK belongs to other work packages of the same program; the live test covers the real server for the TypeScript SDK. |
| AUD-ST1/3 | 2026-11-12 | `RunHandle.finish` distinguishes an end the server decided from an end it did not store. Not stored: no answer (`TransportError`, a timeout included), `5xx`, `401` and `429`, the classes the adapter already treats as "not stored" for a refusal (`NOT_STORED` in `adapter.ts`). After such a failure the call throws as before, but `finished` is `false` again and `finishPending` is `true`. The first end asked for (state, reason, summary, metrics, costs) is the run's end: a later `finish` sends it again and ignores its own arguments, and `retryFinish` sends it without arguments. Every other outcome is unchanged: `2xx`, `run_inactive` and `run_not_active` finish the handle, another refusal throws and leaves it finished. While a call is on its way `finished` is `true`, as before, so a second call still does nothing. | Audit finding `sdk-typescript-2`: `finished` was set before the request, so after the retries of the client every further call was a no-op and the end was lost. The first end has to win, because the adapter's own reaction to a throwing handler is `finish("failed")`: without it a run whose work was done would be recorded as failed once the server is back. |
| AUD-ST1/4 | 2026-11-12 | The adapter keeps a run whose end is pending: the inbox entry stays `started`, the run stays in `active_runs` of the heartbeat, and `resendEnd` sends the end again after waits that double from `sync.reconnect_backoff_base` up to `sync.reconnect_backoff_cap`, until the server stores or refuses it or the adapter stops. A pending end is no failure of the handler: the adapter logs it as a warning and does not replace it by `failed`. A follow-up of such a run is not handed to the handler. The wait is a timer of the adapter, not the next `ready`. The pending end is kept in memory only. The end of an idle run that `run.cancel_requested` triggers (`onCancel`) is not sent again. | 09 5.5: the server ends a run `interrupted` only when it is missing from `active_runs` for `agent.presence_timeout`, so the listed run stays open until the end arrives. `PollingSource` announces `ready` once, so a wait for `ready` would never end over polling. Not written to disk: after a restart the adapter closes its started entries and the server ends those runs `interrupted` (09 4.9), a rule a stored end would change for every adapter; the case of the finding, a server outage longer than the retries while the adapter lives, is covered. The cancel path is the finding `sdk-typescript-5` of the next work package, which also decides which errors may end the delivery loop. |
| AUD-ST1/5 | 2026-11-12 | `PollingSource` takes `HeartbeatAck.interval_ms` only when it is a finite number above zero and keeps its current interval otherwise, the rule of `HeartbeatSender.beatOnce`. The loop of `PollingSource` is not replaced by `HeartbeatSender`. | Audit finding `sdk-typescript-10`, verified: with `0` or a negative value the loop sent `sendHeartbeat` without a pause (`test/sources.test.ts` failed before the change). The finding offers either the check or the move; the move also changes what happens when the heartbeat cannot be built, which is the finding `sdk-typescript-7` of the next work package. |
| AUD-ST1/6 | 2026-11-12 | The FakeServer keeps a row per follow-up (`queued` at `deliverFollowup`, in `Run.followups`), and a patch of `/followups/<message_id>/state` moves it forward only: `patch_target_missing` without a row, `invalid_transition` for a step back (port of `_move_followup` of the Python FakeServer, `followupState` like `followup_state`). The comments that named the state before M2-11 and M2-22 say the current one: `src/testing/fake/patch.ts`, and in the Python SDK the module text of `testing/_fake_patch.py` and the two texts on `costs` in `testing/fakeserver.py` (comments only, no behaviour). `costs` stays off by default in both FakeServers. | Audit finding `comments-3`, verified at the source: the server keeps follow-up rows since M2-11 (migration `00060_runs_run_followups.sql`), the Python FakeServer moves them, and the TypeScript FakeServer refused every patch `RunPatcher.followupDelivered` sends. The default of `costs` is no leftover: off plays a server without cost booking, which the Python SDK answers by ending the run without costs (D-M2-33-7) and tests that way. |
| AUD-ST1/7 | 2026-11-12 | The FakeServer accepts `costs` in `finishRun` behind a switch (`FakeServerOptions.costs`, `enableCosts()`, the names of the Python FakeServer) and keeps them per run (`costs(runId)`). It serves the six operations the hand layer calls and it lacked: `reportAgentSession` (compare-and-swap over the session row, `sessionReports`), `getInstance` with `InstanceLimits`, and the upload session of mode `direct` (`createUpload`, `uploadPart`, `completeUpload`, `abortUpload`); `createMessage` refuses a content above `message_max_content_bytes` and attaches completed uploads (ports of `_fake_uploads.py` and `report_session`). `test/fake-contract.test.ts` is the gate: every entry of `ROUTES` is an operation of `docs/api/openapi.yaml` with that method, path and `operationId`, one run over all routes must answer every route with `2xx`, and every answer, refusals included, is checked against the schema of its operation and status (types, required and unknown members, enums, patterns, bounds, the formats `uuid` and `date-time`). The checker is part of the test file; no schema library is added. The other operations of the Python FakeServer are not ported. | Audit finding `sdk-typescript-3`: `RunHandle.finish` with costs, `RunHandle.reportSession` and `sendLongMessage` could not run against the kit, and nothing held the FakeServer to the contract. A route that is not exercised fails the gate, so a new operation cannot be added without its form being checked. Which further parts of the Python SDK the TypeScript SDK takes over is the parity list of the finding `sdk-typescript-8` of the next work package. |
| AUD-ST1/8 | 2026-11-12 | Retention of the adapter state. `InboxStore.prune` drops, besides expired `jti` rows, every entry that stayed closed for the retention of the store (`CLOSED_ENTRY_RETENTION_MS`, one day; `InboxStoreOptions.closedRetentionMs`). The first prune that finds an entry closed starts its time, a redelivery of the event starts it again, and an entry in another state never leaves. The stores keep that time in memory, so a new process counts from its first prune. The adapter prunes at its start and every hour (`INBOX_PRUNE_INTERVAL_MS`); a failed prune in the loop is logged and tried again. The adapter drops the token of a run from `runTokens` when it forgets the run; a late outbox entry of the run is bound with the token of the inbox as before, and fails with `run_token_unavailable` once that entry has left. Not built: the `jti` store as an append log, and a limit for failed outbox entries. | Audit finding `sdk-typescript-4`: no entry, `jti` row or run token ever left. A day is far above the time in which the server delivers an event again (`agent.ack_timeout`) and above the life of a token (`agent.invocation_token_ttl`); a dropped entry whose event still arrived would be handled as new, where the server guards a second start with `409 already_started` (09 4.5). No time stamp in the entry files: the record format stays as it is, and the cost is at most one more retention after a restart. With the prune the `jti` file holds only tokens that can still pass, so the full rewrite per token stays small. Failed outbox entries stay on purpose (04 13.2 point 5) and are the finding `sdk-typescript-9` of the next work package. The Python SDK has the same gap (`sdk-python-3`) in its own work package; the rule is local to the TypeScript SDK until then. |

## Open minors

- A model command is no shared scenario of both SDKs yet (AUD-ST1/2). When the Python SDK gets
  one, the heading in `sdk/testdata/scenarios/README.md` and both functions come together.
- A pending end of a run is lost when the adapter itself restarts before the server is back
  (AUD-ST1/4); the server then ends the run `interrupted`.
- The contract gate checks answers, not the requests the FakeServer accepts, and of the formats
  only `uuid` and `date-time`.
- The FakeServer answers `renewInvocationToken` for a token of a model command with
  `500 internal_error`, as the Python FakeServer does; the answer of the real server for that
  case is not checked by a test of this SDK.
- `HeartbeatSender` is still used by no source of the SDK (AUD-ST1/5).
