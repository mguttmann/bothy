# AUD-client-notifications-01 Hints on a phone in front, the permission moment on macOS, read threads and the log of swallowed failures

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-CN1/1 | 2026-11-12 | Nothing more is built here for a phone in front that drops `notification.created` (audit finding client-phone-background-1). It is the defect of audit finding fn-push-notifications-4, and work package AUD-client-app-01 fixed it before this package: the in-app banner (`InAppBanners` and `InAppBannerHost` in `apps/client/lib/notifications/in_app_banner.dart`, docs/decisions.d/AUD-client-app-01.md AUD-CA1/1 and AUD-CA1/2) with the title and the text of 01 10.2, a tap that opens the target, one haptic tap unless the hint is quiet and nothing for the thread on screen. AUD-CA1/2 also rules that the banner has no sound. This package only adds that the banner of a thread goes when the thread is read (AUD-CN1/3). | One cause gets one fix: a second presenter for the phone would show every hint twice. The recommendation of this finding (a banner with a tap on the target, a signal by `quiet`, a test that a connected phone shows the banner unless the thread is open) is what that package built. Checked for this package: `apps/client/test/notifications/in_app_banner_flow_test.dart` runs the phone app of an iOS and an Android build over the real services against the fake server and passes; with the presenter of the ports in place of the banner, as before that fix, the same tests fail ("the banner did not happen"). |
| AUD-CN1/2 | 2026-11-12 | The macOS app asks for the permission of local notifications (alert and sound) once per run when its first local notification is about to show (`LocalNotificationPresenter.show`), not when the plugin initializes. The request stays not awaited (D-M4-30-2), so the first notification of a Mac that was never asked may not show. | Audit finding client-phone-background-15, verified at the source: the app widget reads `desktopNotificationsProvider` when it starts, `NotificationRouter.listen` reads the click that started the app, and that initialized the plugin, which asked at once, so the dialog of the system came at the first start before any login, against the class's own description ("asked once at the first notification") and against the rule of push (D-M5-04-5: never before the login). `apps/client/test/notifications/local_presenter_test.dart` ("macOS: the click that started the app is read without asking for the permission") failed against the old order. |
| AUD-CN1/3 | 2026-11-12 | A connected desktop app removes the local notification of a thread as soon as the person has nothing unread in it: `desktopNotificationsProvider` listens to the count changes of the engine (a read on this device, `read_state.updated` of another one) and calls `NotificationRouter.onRead`, which removes the slot it filled for that thread through `NotificationPresenter.cancelThread`, once. The router remembers only the slots it filled since the app started. A phone in front has the same router, so the banner of a read thread leaves the screen the same way; a banner of another thread stays. 01 10.3, 13 8 and 15 10.3 say what is built. Not built: removing the pushes that iOS or macOS already show when the app becomes active, a badge the apps of Apple set themselves, and the removal of a local notification that an earlier run of the app showed. | Audit finding fn-push-notifications-9, verified at the source: no code called `cancelThread`, and the runners of iOS and macOS neither remove a delivered notification nor set a badge; only Android removes read threads, with the sync push. 01 10.3 promised the removal "as soon as that app is active the next time". For the local notifications the read is known in the app, so they are removed (`apps/client/test/notifications/flow_test.dart`, "read on another device", and `in_app_banner_flow_test.dart`, "the banner of a thread goes", both with the real engine against the fake server, and `router_test.dart`). For the pushes of Apple the recommendation leaves the choice to build the removal or to take 01 10.3 back to what is built; the removal needs a new call of both runners for the delivered notifications, the read state from the encrypted database and a check on devices, and the badge of 13 8 is a count only the server has. Open for the next change of the Apple runners: that removal, and whether the Mac app, which gets no sync (13 8), keeps a badge that a push set (derived from the source, not checked on a device). |
| AUD-CN1/4 | 2026-11-12 | Every failure that push (`NativePush`) and the sharing glue of iOS and macOS (`AppleShare`) swallow writes one line: the step and the type of the error, never the text of the error, a token or an ID of the instance. The router and the presenter of the local notifications and the sender of the app metrics (`MetricsSender`) had such lines already but no sink in a build; all five now write to the developer log (`dart:developer`, names `notifications`, `push`, `share`, `telemetry`) unless a sink is given, as discovery and the secure store do. Deferred, with a question for the owner: the diagnostic channel that a release build keeps and shows (a ring buffer with a status page or an export) and the state of push in D9 (permission, registered, last error). Until then the finding is not solved for a release build. | Audit finding client-phone-background-3: the guards swallowed without a trace and the `log` parameters were never set in a build, although the descriptions promise lines without content. `apps/client/test/platform/push_apple_test.dart`, `apps/client/test/share/share_apple_test.dart` and `apps/client/test/telemetry/metrics_sender_test.dart` hold the lines and that they carry no content; what the developer log receives cannot be observed in a unit test, so the tests of the default sink only hold that nothing fails without a sink. A release build keeps the developer log nowhere, so "push does not arrive" still cannot be diagnosed on a device of a person: that needs the local diagnostic log, which is a feature of its own, a new store with its own retention and content rules, a page or an export on four platforms with texts and tests. Question for the owner: shall release builds keep such a log on the device, with which retention, and may a person export and send it (a product and privacy decision; the same question as for audit finding client-shell-3, docs/decisions.d/AUD-client-app-01.md AUD-CA1/6)? And shall D9 show the state of push, which 01 does not ask for today? What is built here is the part that needs no decision: every sink the recommendation names is connected, so the log, once it exists, only replaces the default sink. |
