| D-M2-06-3 | 2026-10-20 | The header has exactly `alg`, `kid` and `typ`; `iat` is the issuing time truncated to seconds and `exp` is `iat` plus `agent.invocation_token_ttl` truncated to seconds; `aud` is one string; absent claims are omitted, never `null`. | D-M2-06-4 | 2026-10-20 | `Verify` looks the key up by purpose `invocation` and accepts `next`, `active` and `retiring`; it also compares the purpose, the algorithm and the state of the returned key. | D-M2-06-5 | 2026-10-20 | `typ` is compared byte for byte after the case-insensitive profile check of `kernel/jose`; a header `jwk` is never used. | 09 4.5 item 2 says "exactly". |
| D-M2-06-6 | 2026-10-20 | Every cause of `invalid` is checked before the expiry: `expired` only when the token is otherwise valid; `IgnoreExpiry` skips only the expiry. | 09 4.5 reason table: "`exp` passed, otherwise valid and current"; 09 4.5.1 step 1. |
| D-M2-06-7 | 2026-10-20 | Unknown payload members are ignored; member names are matched exactly (no case folding) and the issuer writes exactly the set of 05 section 5. | RFC 7519 section 4: a token of a newer server version stays verifiable during an upgrade. |
| D-M2-06-8 | 2026-10-20 | The server applies `auth.clock_leeway` to `iat` and `exp` of its own invocation tokens: valid while now is before `exp` plus the leeway. | 08 7.2 defines the leeway for `exp`, `nbf` and `iat`; the retiring window of 09 4.5 "Keys and rotation" point 2 already contains this margin, so an accepted token always has a published key. |
| D-M2-06-9 | 2026-10-20 | The reference verifier is test support in `runs/adapters/runstest`, written with the standard library only and independent of `kernel/jose`; it reports in this precedence: points 1 to 4 and 6 (`ErrRefInvalid`, `ErrRefUnknownKey` for a `kid` missing after one forced reload), then 8 and 10 (the mismatches), then 5 (`ErrRefExpired`, `ErrRefInvalid` for an `iat` in the future), then 7 (`ErrRefReplay`). | D-M2-06-10 | 2026-10-20 | This ticket proves AG-22 at token level: scheduled, no token fails at three adapters or a second process inside its validity through two rotations and no adapter needs a forced reload; emergency, the old key fails at once in the same process and within `signing_key.cache_ttl` in another, and a new token verifies after at most one reload. The run level of both halves is M2-31's. The late check of an adapter that saw the token before expects `ErrRefReplay`, which proves every other point held. | PLAN row M2-06 and M2-31; the replay check is the last point of the adapter check. |
