# FEAT-topology-agent-tree The agent tree of a run in the live topology

Design: [topology-agent-tree.md](../design/topology-agent-tree.md).

| No | Date | Ruling | Reason |
|---|---|---|---|
| FEAT-TAT/1 | 2026-11-01 | The live frame carries the agent tree per run as a flat list `tasks` (parent before child, `parent_id` to the task node above) built by the server from `run_steps`; the client builds the tree. The server sends no separate tree event and no new op. | The steps already hold every fact (D-RV-3); the frame is the one stream the topology reads, and a flat list keeps the payload size predictable for the size rule. |
| FEAT-TAT/2 | 2026-11-01 | The Claude Code runner reads the agents of a workflow from `task_progress.workflow_progress` of the stream, not from the workflow journal files under the session folder. | The stream carries the full agent list live on every progress message (measured in 50 recorded turns of the pinned CLI); reading files of the CLI would add a second, slower source and file access outside the runner's own state. |
| FEAT-TAT/3 | 2026-11-01 | A task with `owned_by_subagent = true` whose tool call is unknown to the stream and that is not backgrounded gets no step. | It is a foreground command of a workflow agent; its step would land at the root of the run as noise (one per command), and the agent's node already shows the command's tool as its current tool. A backgrounded one keeps its step, since it outlives the call. |
| FEAT-TAT/4 | 2026-11-01 | The parent of a node is its task ancestor through the tool calls (the merge rule of 09 5.6 applied on the server); a parent that is not an earlier node puts the node under the run. | The same structure as the run graph, and no cycle can reach a client. |
| FEAT-TAT/5 | 2026-11-01 | The label of a node is the first line of the step title, at most 80 characters, sent only to a receiver with `run.read` on the run's channel (a second `Scope` per receiver, only when a node of the frame has a label). Without it the client names the node by kind and position. | Chapter 25 rule 3 keeps content out of the statistics; a receiver who may read the run sees the same title in the run graph, so the label shows nothing new to that person and nothing to anyone else. The owner asked for the role of each child. |
| FEAT-TAT/6 | 2026-11-01 | Limits: `stats.live_max_tasks` (25) nodes per run, running first, then the newest finished, each with its ancestors; `stats.live_task_max_depth` (4); `stats.live_task_keep` (2m) for finished nodes. Under the payload bound the trees of the oldest runs go before any run. | A long session with many workflows must not push other runs out of the frame; the finished children fade on the client and disappear after a short time, as the owner asked. |
| FEAT-TAT/7 | 2026-11-01 | No "waiting" state for a child node. | The stream has no signal that a subagent waits; a guessed state would be wrong. The run itself keeps `waiting_input`. |
| FEAT-TAT/8 | 2026-11-01 | One drawing in `bothy_viz` for every client: under each run card an indented tree with elbow lines, node cards with state, runtime and tool, collapsible branches, finished nodes faded; the same vertical tree on the phone. The run card and its tree are one cached widget per run, so an unchanged run does not rebuild. | A vertical tree does not move when nodes arrive, fits a phone and a lane, and reuses the card and color roles of the topology. |
| FEAT-TAT/9 | 2026-11-01 | The run graph (D14) shows `detail.last_tool` as the current tool of an open node without a running tool call. | Workflow agents have no tool call steps of their own; without it their node would show no current tool in the run graph while the topology shows one. |
