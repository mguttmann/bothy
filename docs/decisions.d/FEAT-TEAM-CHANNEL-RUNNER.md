# FEAT-TEAM-CHANNEL-RUNNER Runner slice of the team channels

Contract: [09-agents.md](../spec/09-agents.md) 3.9.9, built in 18.5 "Team runs and team
inputs"; server rulings in [FEAT-TEAM-CHANNEL-SERVER.md](FEAT-TEAM-CHANNEL-SERVER.md).

Threat model of every ruling below: a member's agent controls the text of its final reply, which
reaches this runner's session as an input, and it may run as another program of the same host
user (it can read every file of that user, also the session transcripts of this runner). It
cannot read the runner process's memory or forge the server's data of a message.

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-TEAM-RUNNER-1 | 2026-11-21 | Who wrote an input is decided from the message alone: origin `agent` or an author of kind `agent` makes it a team member's input (`team.is_member_input`), labelled "team member @handle", a colleague's request that is not the owner's word and never an approval; never from the member `team`, `triggered_by` or the token's `sub`. Either mark is enough, so a disagreement labels the member's. Evidence: `test_the_message_decides_who_wrote_never_the_facts`, `test_a_member_s_input_is_never_a_person_s`. | 3.9.9 "Owner authority" and D-TEAM-3: the authority of a member's input is the sponsor, so every field that names the authority names an owner; only the message says that an agent wrote the text. |
| D-TEAM-RUNNER-2 | 2026-11-21 | The team facts reach the session in a third text item of the run's first input line, between the context and the trigger part, never in the system prompt; the runner instructions get one general paragraph on the lead-in `Input from team member`. | The CLI keeps the system prompt of a conversation's first request for a session a later run continues (design 2.2 item 16, as for the owner check), and the work thread's session lives across runs of several kinds. |
| D-TEAM-RUNNER-3 | 2026-11-21 | Owner codes keep the rule of D-FIX-RUNNER-TRUSTED-OWNER-FOLLOWUPS-1 unchanged in team runs: a run has an owner only when its triggering message is a person's, and only that person's follow-ups get codes. A run a member's input started therefore has no owner check, and an owner's message that reaches it is a relayed request. Rejected: codes for every person's follow-up in a team run. | The runner cannot tell an active owner from any other person (a `PrincipalRef` names no role), and a person with a grant added later could write in the work thread while a team run works; the narrower rule never gives such a person the owner's word. The cost: an owner who must approve a step in a run a member started writes again after the turn, which starts the owner's own run. |
| D-TEAM-RUNNER-4 | 2026-11-21 | A follow-up whose text, file texts or transcripts hold a code the runner wrote (any spelling of its hex, `OwnerLines.carries_code`) is not written: warning `followup_carries_owner_code`, the follow-up stays `queued` and the server defers it. Evidence: `test_a_member_s_input_that_names_a_written_code_is_not_passed_on`. | A written code is readable by every program of the host user, also by a member's agent. The watch of D-FIX-RUNNER-TRUSTED-OWNER-FOLLOWUPS-3 judges inputs of other senders; a line the runner writes is its own, so the code would reach the model unjudged inside it. |
| D-TEAM-RUNNER-5 | 2026-11-21 | The follow-up check compares the message's author with the token's `sub` only for a person's message; for an agent's message (a member's input, whose `sub` is its authority) it checks the thread, the run, the kind and the rest as before. | The server sets `sub` to the authority of a team input (3.9.9), so the old comparison refused every member's input. `sub` grants nothing in the runner: owner codes come from the message's author and origin alone. |
| D-TEAM-RUNNER-6 | 2026-11-21 | The SDK's token check of `agent.invocation` gets the row `team` (`message_id`), and the FakeServer of the SDK learns team runs (`trigger_kind = team` with `authority` and `team`, an input of the agent Texter, its run context) and follow-ups of Texter. | Without the row the SDK refused every team token as having no counterpart; the Hermes adapter slice needs the same row, so it lives in the shared SDK. |
| D-TEAM-RUNNER-7 | 2026-11-21 | Answers, the live box and every request of a run keep the invocation token of exactly that run through the SDK (`RunHandle.bound`, `Outbox` `token_for`); no runner change was needed, and `test_a_member_s_team_run_shows_the_team_and_hands_over_with_its_own_token` holds it for a team run whose answer mentions another member. | The server links an answer to its run only with that run's token (07 SR9, D-TEAM-12), and only a linked answer hands on. |
| D-TEAM-RUNNER-9 | 2026-11-21 | A `team` run without an owner check ends its first input line with the runner note `team.NO_OWNER_CHECK` after the trigger part. Evidence: `test_a_run_a_member_started_has_no_owner_check`. | Red team round 1 (minor 1): otherwise the member's text was the last part, and a steered member could append a forged owner check with its own digests where the runner instructions say a first message may end with one. |
| D-TEAM-RUNNER-8 | 2026-11-21 | Not covered: the member list of a turn this runner adopted after a restart (the adopter has no team facts; a member's input then names the agent's own handle and no "mentions you" note), and a hosted agent's team run has the same team part but no further hosting-specific check. | Labels only; whose word an input is never depends on the facts (D-TEAM-RUNNER-1). |

Open minors (red team, round 1; for the next run in this area): no scenario for a team run of a
hosted agent (same code path as the runner's own agent); the agent's display name stands
unquoted in the team part and the member's lead-in (a label only, as for a person's lead-in);
`docs/spec/09-agents.md` 17 (Hermes mirror, item 5) still says the server opens runs only for a
person's message, a command or an interaction, which `wake` and `team` runs no longer match.
