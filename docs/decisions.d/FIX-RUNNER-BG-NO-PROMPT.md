# FIX-RUNNER-BG-NO-PROMPT Background sessions: a tool call that would wait for a person is refused

Reproduction condition: a run in background mode (`runner.launch_mode` `background`) of class
`host` (bypass mode) whose session has background agents. One agent sends a Bash command that
edits a Makefile through a quoted Python heredoc whose text holds a recipe with
`rm -f "$$f" "$$f.tmp"`. The removal is text and never runs, but the CLI's check of removals
cannot parse the whole command with certainty ("This command could not be checked for dangerous
rm operations: the shell may read it differently than it was parsed. This requires explicit
approval."), and bypass mode cannot skip that check. In print mode the call is refused; in a
background session it becomes a pending approval: the session list shows `status` `waiting`,
`waitingFor` `permission prompt`. The runner's reader turns that into an error `result` with the
cause `background_session_waiting`, the runner stops the session with `claude stop`, and every
background agent, monitor and command of the session ends with it. The run ends `failed`,
`runtime_error`. The runner's log showed only `run_finished failed runtime_error`, so the stop
read like a crash. A continued agent sent the same command again, so the stop repeated.

| D-FIX-RUNNER-BG-NO-PROMPT-1 | 2026-11-25 | Every settings file of a background session holds `permissions.denyInsteadOfPrompting` `true` (`NO_PROMPT_SETTING` in `bgsession.py`); a hosted turn keeps the members of its own `permissions` beside it, and a `false` there does not switch it off. Always on, no configuration key. Print mode is unchanged. Evidence: read in the file of the pinned CLI (2.1.326 and 2.1.332 hold the setting and its description "Never wait for a person to answer a tool permission prompt: a call that would prompt is denied at once, the model is told, and the turn carries on ...
