# CU-07 Clients: status, stop and desktops

Rulings of the client side of computer use ([27-computer-use.md](../spec/27-computer-use.md)
section 11, 15 R-CL-18, 07 2.15). Owner ruling OR-1 of 2026-11-26 applies (D-CU-01-1).

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-CU-07-1 | 2026-11-26 | Strings in `packages/l10n` with the prefix `computer` (chip, desktop entry, close reasons) and `trayComputerStop`; the helper's switch keeps its name "Allow computer control" (German "Computer-Steuerung erlauben") in the note that switching on is only local. The chip shows the frontmost app by its identity (`front_app`, a bundle ID or executable name), because `ComputerSession` carries no display name (D-CU-04-18). | 27 11 item 1 names "frontmost app"; the server stores the identity only. |
| D-CU-07-2 | 2026-11-26 | The chip sits under the live box of the thread (`ComputerChipSlot` after `LiveBoxSlot` in the history column), the same on desktop and phone; it shows the session of every run of the thread whose session is not closed. | The live box is the run's place in the thread (01 6.2); one slot serves both form factors. |
| D-CU-07-3 | 2026-11-26 | "Names the close reason once": a session this device knew live shows its end with the reason until the owner dismisses it; a session the list or an event names closed without the device having seen it live shows nothing, and a dismissed end never returns. No timer, so no new configuration key. | Brief requirement 13 without a limit that rule 9 would have to name. |
| D-CU-07-4 | 2026-11-26 | Tray: on Windows the existing icon gains the entry "Stop computer control (`desktops`)" while a session of the owner is live; on macOS the app shows a menu bar icon with the same menu only while such a session is live (this narrows D-M4-30-5, which gave macOS no tray). The entry stops every live session of the owner. | Brief requirement 15 names macOS and Windows; one entry keeps the menu short, and one controller per host keeps the list small. |
| D-CU-07-5 | 2026-11-26 | Desktops: the console and the desktop app show computer control on the host page of the administration (`HostComputerSection` of `admin_ui`, which both apps use); the phone shows it under each host of screen M9 (`ComputerDesktopEntry`). Both appear only for a host that carries the reported `computer` object, which the server sends to active owners alone. The Stop of the host page reaches the owner's own session on that host (`listComputerSessions` lists one's own sessions only). | 27 11 item 3 and 01 3.9 (switch-off on D, M, W); owner-only by the server's answer (07 2.15 item 5), without permission logic in the client (15 1 principle 1). |
| D-CU-07-6 | 2026-11-26 | The sessions live in memory in the provider `computerSessionsProvider`; the engine announces `computer_session.changed` on the host event hub (`ComputerSessionChanged`) and writes no table; `toString` of the event and the status leaves out the desktop's name and the app. A person who is no owner (`getMe.is_owner` false) sends no computer request. | R-CL-18: no cache beyond the engine's rows, app identities out of crash reports and logs. |
| D-CU-07-7 | 2026-11-26 | The Dart fake server serves `listComputerSessions`, `stopComputerSession` and `disableComputerDevice` (owners only, `403 owner_only` otherwise) and returns `computer`, `computer_listed` and `computer_disabled_generation` of a host to owners in `getHost` and `listHosts`; the agent's operations are not served, tests open a session with `FakeWorld.openComputerSession` as the runner would. | The apps call only these three; the agent side is tested on the server. |
