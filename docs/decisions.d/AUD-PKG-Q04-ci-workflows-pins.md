# AUD-PKG-Q04-ci-workflows-pins CI workflows, pins and the release chain

Work package of the audit of 2026-11-11 for the workflows, the tool pins, `tools/distribution`
and the locks of the Android and Apple builds. Each finding was read again on the current
`main` first; findings already fixed or decided since the audit are closed with their evidence
and have no row here.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-Q04/1 | 2026-11-28 | Semgrep runs from a locked project of its own, `tools/semgrep` (`pyproject.toml` with `requires-python ==3.12.*`, `uv.lock`), through `uv run --project tools/semgrep --locked`; the Makefile variable `SEMGREP_VERSION` and `uvx` are gone, Renovate raises it with the tools (pep621). `make osv` reads the new lock like every tracked `uv.lock`; `tools/semgrep/osv-scanner.toml` accepts the eight advisories of the packages Semgrep 1.180.0 pins exactly or in a narrow range (mcp, opentelemetry-api, wcmatch), each with the reason the gate does not reach the code and the expiry 2027-02-28. The license gate is unchanged: it judges shipped components only. | Issue #755: only Semgrep's own version was pinned, its dependencies resolved anew on every fresh cache without hashes. The lock made eight advisories visible that the `uvx` run had hidden; none can be fixed inside Semgrep's requirements, and none is reached by `semgrep scan` and `semgrep --test` over the repository's own files. |
| AUD-Q04/2 | 2026-11-28 | A new scheduled workflow `images.yml` builds bothy-server and bothy-postgres from `main` for the runner's platform and runs `make trivy-image` over them and over the third-party images of `compose.yaml` and `compose.multi-node.yaml` at their default versions (`tools/ci/compose_images.py`, which fails for a third-party image without a version default). Every image is scanned before the job fails. Same visibility guard as the lock scan of `advisories.yml`, but a workflow of its own: a third-party finding can stay red until upstream publishes a fixed image, and in `advisories.yml` it would hide a new red lock scan behind the same open issue. | Issue #908: between two releases nothing reported a new vulnerability in the operating system packages of a shipped image. A red scheduled run reaches an issue since the owner switched on `BOTHY_RED_RUN_ISSUES` (AUD-R2O/12), the blocker the earlier deferral named. Published images do not exist before the first release, so the job builds them. |
| AUD-Q04/3 | 2026-11-28 | `docs/quality/toolchain.md` names three review dates, each `Next review: <date>`: the pin review of section "Updates" (Go, Flutter and the release binaries against upstream, first on 2026-12-31) and the holds of Trivy and WiX (new section "WiX: keep the version"), each 2027-02-28. `test_every_review_date_of_the_page_lies_ahead` fails once a date has passed; the review moves the date at most three months on. No pin is raised in this change. | Issue #757: until Renovate is active (an owner step of the publishing checklist) nothing proposes updates, and the two holds had conditions but no date on which anyone checks them. An expiring date is the mechanism the OSV exceptions already use. Raising each lagging pin is the review's work, each with its own tests. |
| AUD-Q04/4 | 2026-11-28 | The store clients wrap their network seam in `storeapi.retrying`: a refusal for the rate (429) is sent again for every method, a 5xx or a lost connection (`NetworkError`) only for a read, three more tries after 5, 20 and 60 seconds. `ios.py promote --group beta` adds a processed build to the group beta, the catch-up of a release whose upload reached App Store Connect but whose job ended before the group step. `build-apple` gets 240 minutes, room for the processing wait after the builds. release.md section 4 describes the correction forward. Not built: store uploads only after all build jobs. | Issue #1478: one 5xx or 429 ended a release half way, a rerun would upload the same build number again, and the job limit equalled the processing wait alone. A write is not retried after a 5xx because it may have taken effect. With the catch-up command and the documented order (R-RL-07, correct forward) a partial state no longer needs a rerun, so moving the uploads behind every build job is not needed for the finding. |
| AUD-Q04/5 | 2026-11-28 | The release downloads of `tools/distribution` (Sparkle in `apple.py`, bundletool in `android.py`, WiX in `hostdist.py`) carry a `# renovate:` comment and one regex manager of `renovate.json` reads them; a package rule keeps WiX below 6. toolchain.md lists Sparkle and bundletool, held by `test_toolchain_doc.py` like the other pins, so the pin review of AUD-Q04/3 covers them. The pins stay in their modules with their SHA-256 and download functions. | Issue #1599: these pins had no update source and no review. `tools/bin/tools.lock.json` describes one binary per platform from a GitHub release; a framework archive, a jar and a NuGet package with one hash each do not fit it, and each module already checks its hash before use. OSV knows advisories of Sparkle (ecosystem SwiftURL), but OSV-Scanner reads them only from a lock file such as `Package.resolved`, and a release archive pinned in Python code is none; until then the dated pin review checks them by hand. The Visual C++ runtime part was #869 (AUD-R2O/5). |
