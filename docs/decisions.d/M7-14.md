| D-M7-14-8 | 2026-10-25 | The next trial run with `--storage s3` found the second gap M3-02 named as a plan gap: `secrets-init` reported `s3_access_key` and `s3_secret_key` as `pending`, so the server of every `s3` installation stopped at its start (`secret not found`). In the catalog of `internal/platform/secrets/stack` both stay supplied entries but carry a generator (`s3_access_key` `key`, 32 bytes as hex, `s3_secret_key` `token`, 32 bytes as base64url; neither holds `/`, which would break a SigV4 credential scope): absent from `_store` and the source, `init` generates them, and SeaweedFS of the profile `s3` takes them as its admin identity; for an external S3 service the owner supplies both, `init` adopts them, and a changed source replaces them like any supplied entry (16 5.3 rule 3; a generated origin would have turned that rotation into a conflict, found by the delta red team). They are generated with every profile; unused without the profile `s3`. | The brief of M3-02 assigned the end-to-end profile `s3` to the installation and this test; one generator in the one catalog keeps every installation path working. |
