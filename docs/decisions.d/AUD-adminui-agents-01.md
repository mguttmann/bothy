# AUD-adminui-agents-01 Interview limit, adapter agents and loads of the agent administration

Four findings of the audit of 2026-11-11 against the agent screens of `packages/admin_ui`
(`fn-runner-builtin-agents-5`, `fn-agents-runs-2`, `admin-ui-agents-apps-hosts-1` and
`admin-ui-agents-apps-hosts-4`). Two are faults a person meets: the interview of "New agent"
ended in an error nobody could leave once the builder had asked past the server's turn limit, and
the administration had no way to create, disable, enable or configure the agent of an adapter,
although chapter 11 section 13 and the guide "Connect your own agent" said it had. Two concern how
the screens read and report: the agent page read lists it never showed, one after the other, and
the screens read the errors of the login layer in two different ways. Normative text: 01 sections
3.7, 5.2 A5 and 6.20; 07 section 2.11; 09 sections 2.1 and 2.2; 11 section 13; 26 section 6.1; the
package README.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-AA1/1 | 2026-11-12 | An interview the server finds too long ends with the draft. `AgentInterview` sends the request that got `400 validation_failed` with `too_many_items` on `/turns` once more, with `want_draft` and at most as many turns as the server took in an earlier request of the same interview (at least one). `fittingTurns` chooses them: the builder's questions at the end that nobody answered are left out first, then its questions from the oldest on, the person's answers from the oldest on last. The dialog keeps showing the whole interview. Any other refusal shows as before and gives the answer back. | The client keeps every question and every answer as a turn of its own and sent them all, the server refuses more than `agents.interview.max_turns` before it asks the builder, and the failure removed only the person's last answer, so every further request failed the same way, "Use what we have" included. The client cannot read the limit, but every answered request proves a count that fits, so the rule holds for any configured value without a constant in the app. The person's own words are what a draft needs; a question of the builder is the cheapest turn to lose. |
| AUD-AA1/2 | 2026-11-12 | Not built here: the limit in the payload of `agent.interview_requested` and a builder prompt that drafts before the limit is reached. | With AUD-AA1/1 no interview ends in an error; what remains is that the last request leaves out the oldest questions of the builder. Telling the builder the limit changes the event contract, both SDKs and the runner's prompt, which belong to the server and the runner; it is noted here for the next change of the interview in those components. |
| AUD-AA1/3 | 2026-11-12 | The agent page reads the agent, its operated targets and the people side by side, and nothing else. The names of an I1 explanation are the people the page has plus the agents, read when a `409 i1_violation` arrives. Every load counts itself, and an answer of an older load (another agent, or a load that a change replaced) is dropped. Not built: a load controller per area and directories shared by a whole administration shell. | The page waited for each read before it started the next, read the people twice and the spaces and channels twice, and read groups, targets and hosts only to hand them to an explanation that uses people and agents; a slow answer for a former agent could replace the shown one. A shared data layer for all screens is a redesign of the package without a fault behind it: the host keys the page per agent, and the performance targets of 15 section 19 name none for the administration. |
| AUD-AA1/4 | 2026-11-12 | The three mappings of the package read an error of the login layer the same way: a cancelled step-up says nothing after an action and is a cancel in "New agent"; a session without a step-up method is `403 forbidden` with `step_up_not_possible` (SEC-SL/3); a refresh that got no answer (`RefreshUnavailable`) is the offline text; a session that is gone (`SessionEnded`, `NotSignedIn`) is `session_revoked`. `newAgentFailureOf` switches over the sealed type, so a new kind of error does not compile until it has a reading; a test holds the table. Not changed: `NewAgentPort` stays next to `AgentsRepository`, and its agent state keeps reading a billing mode it does not know as `organization`. | "New agent" called an ended session and a failed refresh a cancelled confirmation and asked to try again, and the other screens called a refresh that could not reach the server a revoked session. Putting the port on the repository is a redesign of two data layers without a fault of its own. The billing mode is a closed enum of the contract with two values; the flow only asks whether it is `personal`, and a third reading would need a third state in the billing step for a value no server sends. The new project dialog of the app (`newProjectFailureOf`) reads a login error like "New agent" did; it belongs to the app and is noted here for its next change. |
| AUD-AA1/5 | 2026-11-12 | The agent list has "Add adapter agent": a dialog with name, handle (the pattern of `AgentCreate`), an adapter kind and an optional description, then `createAgent` with step-up. The kinds offered are `code_runner`, `hermes` and `custom`; `claude_agent` is not offered, because a built-in agent needs a hosting runner and has "New agent". After the creation the list loads again and opens the new agent, whose page creates the token. A taken handle (`409 conflict`, `taken` on `/handle`) is said in words; a `403` hides the button. | The administration could create only built-in agents, and those need a runner that is itself an adapter agent, so the first agent of an installation existed only through a hand-made request with DPoP and step-up. 11 section 13 step 1 names the administration as the way to create the agent, and brief M4-28 moved it to the console administration, where it was never built. The server takes any identifier as adapter kind (03 `agents`); the three kinds are the ones the project ships or documents, and a mistyped kind would make an agent no adapter serves. |
| AUD-AA1/6 | 2026-11-12 | The agent page has "Disable" and "Enable" for an adapter agent, each with one confirmation that says what ends (tokens, connections, runs) or what does not come back (the tokens) and with the reason for the audit log; without a typed reason the default reason is sent. A built-in agent keeps "Disable" in its own section and gains "Enable" once it is disabled; without that section (a host that passes none) the page offers both. A `409 i1_violation` of "Enable" shows the I1 explanation. | `disableAgent` was reachable only for built-in agents and `enableAgent` nowhere, so the only stop for an adapter agent was to revoke its token, and nothing could lift a disabling. Enabling counts the agent for I1 again (10 section 5.1), so the refusal needs the same explanation as a switch to Personal. |
| AUD-AA1/7 | 2026-11-12 | The page of an adapter agent shows its tool class with one sentence on what the runtime may do (07 section 2.11; for `host` who may start it, SR2) and "Change tool class": the three classes, a required reason, `setAgentToolClass` with `If-Match`. The class the agent has cannot be confirmed. A built-in agent shows no such control. | The class decides what a runtime may do on its host and who may trigger the agent; no screen showed or set it for an adapter agent. A built-in agent's class follows its definition and is set in the right order by "Edit" (26 section 8.4). |
| AUD-AA1/8 | 2026-11-12 | The page of an adapter agent shows which features are switched off and the default model, and "Edit features": one switch per member of `agent_operator_config.v1` (on allows, off stores `false`) and the default model with its pattern. The dialog saves the stored object with these members replaced, through `updateAgent` with `If-Match`: an allowed feature and an empty model drop their key, and a member this build does not know stays. | A missing key allows (09 section 2.2), so an explicit `true` and a missing key mean the same, and the smallest object says what the owner switched off. `updateAgent` replaces the whole object, so a member of a newer server must travel back unchanged. Built-in agents are left out: their model and tools are their definition, and a second place for a model would contradict it. |
| AUD-AA1/9 | 2026-11-12 | The owner actions of the page share one refusal: a `403` of the backend switch, the tool class, the features or the status hides them all. The header of the agent list wraps: the actions move below the title when both no longer fit. | They are all owner actions with step-up (05), so one refusal answers for the others (15 section 1 principle 1). With a third button the header overflowed at text scale 2 and in German. |
| AUD-AA1/10 | 2026-11-12 | The guide "Connect your own agent" and 11 section 13 step 1 say which owner steps the administration has: the agent (step 1), its token (step 2) and the grants. The space, the channel, its operator and its switches have no screen of their own and are sent as the guide shows. | The guide said the admin screens call the same operations for every owner step. No screen creates a space or sets the channel switches of step 3, and a channel's operator is set only by the project flows, "New agent" and the import. |
