# FIX-CU-HELPER-NO-ICON The computer helper shows nothing outside a session

Owner rulings of 2026-11-28. The owner, asked whether host service and helper should be one
program, kept the split of 27 9.1 and 9.2 and said (translated): "On the Mac the helper runs up in
the menu bar and on the Windows computer down in the tray. I do not need to see them." He added
(translated): "The border is great too ... if possible, the pointer could be orange as well, so you
know where it is and where it clicks ... an extra, not a must. If so, it would be cool, because
Claude Desktop does it too."

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-CU-NOICON/1 | 2026-11-28 | Outside a session the helper shows nothing on either platform: no menu bar item, no tray icon, no window. The menu bar item (macOS) and the tray icon (Windows) exist only while a session is shown, with the text "Agent <name> controls this computer, Esc to stop" and the item "Stop the agent". This supersedes the idle menu bar title "Computer Helper" of D-CU-02-14 and the idle tray text "Computer helper" of D-CU-02-19. | The owner ruling. 27 9.1 and 9.2 already list the menu bar item and the tray icon as parts of the indicator, which shows during a session; only the switch kept them up all the time. The session parts stay, because they are the protection of 27 section 1 item 3 (visible indicator, stop at the machine) and R-CU-09. |
| FIX-CU-NOICON/2 | 2026-11-28 | The switch "Allow computer control" moves into a settings window of the helper (the switch, the permission links of 27 9.1 on macOS, the version and build). It opens when the person opens the helper app at the machine: on macOS the app from Finder or Spotlight (Spotlight indexes the installed bundle; the system hands the running helper a reopen event, `applicationShouldHandleReopen`; should it start a second process instead, because the running helper came from launchd, that process sees the running one by its bundle ID, asks it over a distributed notification to open the window and ends, so two helpers never compete for the channel, and a second start by the LaunchAgent itself ends without asking); on Windows the new Start menu entry "Computer Helper" of the host MSI, which starts the helper with `--settings`, so the running helper of that session opens the window (a second start without the option stays silent, as the installer's and the login's starts do). The window also opens by itself at the helper's start while the switch was never switched on (generation 0), so the person finds it right after installing. Closing it hides it. | Rejected places: the Bothy apps and the console reach a desktop from anywhere, and a command of `bothy-host` (CLI or doctor) runs over ssh as well; any of them would switch a desktop on from a distance and break R-CU-03 and D-CU-01-4 (switching on only at the machine, by the owner in person). The helper is the process 27 names for the switch (27 section 3, C4), so the window keeps it there and changes only how it is reached. The window can be clicked by the agent of a running session like any window; a click whose input carries the helper's own injection marker (`GetMessageExtraInfo()` on Windows, `eventSourceUserData` of the current event on macOS) may switch off, as 27 section 1 item 1 allows, but never on, so a double click of the agent on the switch ends switched off (CodeRabbit finding on the pull request). A process of the console user could click it as it could click the old menu; that trust boundary is unchanged. |
| FIX-CU-NOICON/3 | 2026-11-28 | `bothy-host doctor` names the place while the switch is off: `computer switched on: no (switch it on at this computer: open Computer Helper)`. It switches nothing. | The brief named the doctor as a place; the doctor runs remotely too, so it may only point the person to the machine. |
| FIX-CU-NOICON/4 | 2026-11-28 | The pointer mark joins the indicator on both platforms, only while a session is shown: a ring in the indicator color `#FF6A00` with a soft glow that follows the pointer (polled every 16 ms on the helper's own UI or indicator thread, so it also follows the person's own moves) and a pulse at the point of every click the helper sends for the agent (one per press of a double or triple click; none for a move, a scroll, a key, text, or a click a stop interrupted), growing and fading over 400 ms. Ring and pulse are click-through, topmost and excluded from capture like the border (macOS: every window of the helper is left out by the content filter and has `sharingType = .none`; Windows: `WDA_EXCLUDEFROMCAPTURE`), so they are in no screenshot and do not confuse the agent. The real pointer is not recolored. | The owner's wish. The helper moves the real pointer (`CGEvent`, `SendInput`); recoloring the system cursor would change it for every app and outlive a crash, an overlay goes with the session. The native CI check `indicator_not_in_image` shows the exclusion (no pixel of the color in a capture while ring and border show); click-through holds by construction (`ignoresMouseEvents`; `WS_EX_TRANSPARENT` with `HTTRANSPARENT`), and the `click` check shows that a click near the pointer still reaches the fixture (the ring catches up with a move within one 16 ms tick, so the check does not prove a click through the ring's center). |
| FIX-CU-NOICON/5 | 2026-11-28 | The native CI probe checks the windows of the helper process: none before `show` and after `hide`, some while a session shows, and the settings window after the helper is opened again (`idle_shows_nothing`, `session_shows_indicator`, `hide_shows_nothing`, `reopen_opens_settings` in `tools/ci/computer_probe.py`). macOS counts the on-screen windows of the process with CoreGraphics, menu bar items included; Windows counts its visible top-level windows. Windows tray icons cannot be listed by a public API, so on Windows the tray rests on the code and the review. | The GUI proof runs in CI, never on a maintainer's desktop (services/host/desktop/README.md). |
