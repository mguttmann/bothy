# FIX-app-logout The secrets belong to one app identity

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-AL/1 | 2026-10-31 | The app secrets (`FlutterSecureBackend`) belong to one app identity: the bundle identifier, on Android the application ID. On iOS and macOS they sit under the keychain service `<identity>.secrets`, on Windows and Android under the key prefix `<identity>/`. A build with another identity never reads, lists or deletes them. | Live report of 2026-10-31: a macOS profile build under a new bundle identifier found the refresh token of the earlier bundle in the login keychain (service `flutter_secure_storage_service`, the same for every app), showed five keychain access prompts, sent the token, got 401 `session_revoked` (the earlier device had been revoked), wiped its data and showed the enrollment screen. The login keychain has no access group, and the Windows file of the package lies in a support folder that every branding of the runner shares, so only the app can keep the identities apart. |
| FIX-AL/2 | 2026-10-31 | The secrets of a build before the scope (service `flutter_secure_storage_service`, keys `app/...` and `instance/...` without prefix) move into the scope once, before the first call, and are deleted at the old place; a value already in the scope wins. Where only this app reaches the old store (the iOS keychain with the app's own access group, the private Android store, the macOS Data Protection keychain) they always move, also without local data, so a reinstall on iOS keeps its session. In a shared store (the macOS login keychain of a debug, profile or ad-hoc build, the Windows file) they move only when the app has the folder of an instance under its data root (`InstanceServices.hasLocalData`), the sign that they are its own; otherwise the old store is not touched at all, so a new identity shows no access prompt and starts with enrollment instead of a foreign session. The item `app/secret_scope` in the scope records the step, so later starts never read the old store. | An update must not sign anyone out, and a copy left behind would be a stale refresh token that another build could send (a reuse). A macOS app is sandboxed, so its data root is its own container; on Windows every branding of the runner shares the data root (`CompanyName` and `ProductName` of `Runner.rc`), so there the move of a pre-scope store can still pick up the store of another branding once; it shares the database folder anyway. |
| FIX-AL/3 | 2026-10-31 | No change to the reaction on 401 `session_revoked`: a revoked device still ends the account on the device (E7, then enrollment). | The server revoked the device on purpose (an operator action); the client did what 08 and 15 specify. The defect was that a new app identity picked up that session at all. |
