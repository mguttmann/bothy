# FIX-windows-keystore The Windows app without a step-up key

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-WK/1 | 2026-10-31 | `PlatformDeviceKeyStore.ensure` treats `not_available` from `ensure` of the step-up key as "this device has no step-up key": `DeviceKeys.stepUp` is `null` (the field of `auth` is nullable and optional), and every other failure of either key still throws. The rule is not limited to Windows: any key store that cannot hold a key with user presence answers `not_available` (Windows by design, D-M4-11-2; a Mac without a Secure Enclave in the login keychain, FIX-KC/2), and such a device can still sign in with its DPoP key. | The Windows plugin refuses the step-up key on purpose (08 6.1, 15 9, D-M4-11-2), but the app required it, so `InstanceServices.open` failed on every connect and E1 showed the keychain text although the DPoP key had been created. The API allows a device without `step_up_key` (06, `DeviceRegistration`). |
| FIX-WK/2 | 2026-10-31 | Without a step-up key the registration of the device leaves `step_up_key` out, and `StepUpService.confirm` throws the new `AuthException` `StepUpUnavailable` before the challenge request (login reason `step_up_unavailable`). The other step-up methods of 08 6 for such a device are not part of this fix. | A defined error instead of a null error; no challenge is spent that no key can answer. |
| FIX-WK/3 | 2026-10-31 | The E1 texts `onboardingKeychainUnavailable` and `onboardingOpenFailed` no longer say that the app log has the details; the cause still goes to the developer log (`onboarding`). A persistent app log for release builds is not part of this fix. | `developer.log` reaches no file in a release build on any platform, so the text pointed to nothing; a log file would be a new store with its own retention and content rules. |
