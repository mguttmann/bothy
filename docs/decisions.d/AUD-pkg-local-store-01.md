# AUD-pkg-local-store-01 Cache cleanup, search index writes and the mirror replaced by a snapshot

Seven findings of the audit of 2026-11-11 against `packages/local_store` (`fn-sync-offline-1`,
`sync-engine-store-4`, `sync-engine-store-5`, `sync-engine-store-13`, `sync-engine-store-14`,
`sync-engine-store-16` and `performance-11`). One is a fault a person sees: the cleanup at every
start of the app removed each thread a fixed time after the device first stored it, used or not,
because nothing recorded that a thread was opened. The others concern cost and leftovers: every
stored message read the whole offline search index, lookups by five columns read whole tables,
a snapshot that replaced the mirror left the cached files of a channel the person had lost in
the meantime, every write to any thread rebuilt every open history, and five methods had no
caller. Normative text: 04 sections 7.3 and 13.1, 15 sections 6.1, 6.3 and 7.3, the package
README.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-LS1/1 | 2026-11-12 | The access of a thread is "the person has it on screen". The app records it in `VisibleThreads` (`apps/client/lib/thread/providers.dart`), the notifier every history column of the desktop and the phone registers with: when a thread comes on screen, and for every thread still on screen each time the app window gets the focus back. `ThreadsDao.touch` writes the time and wakes no watcher of the threads. A thread the device does not hold yet has no row and gets its time when it is stored. | `ThreadsDao.touch` had no caller outside a test, so `last_accessed_at` stayed the time the row first reached the device and the cleanup removed daily used threads with their messages, read states and search rows once that time was older than `client.cache_max_age`; with a stored cursor nothing brought them back until a new message, the post list or a resync (04 13.1 promises removal only without access). Recording only the opening would still lose the one thread a person keeps open: a desktop app runs for weeks without a new history column, and the cleanup of the next start would find the access of weeks ago. The focus of the window is the signal the notifier already tracks for the gateway. The write wakes no watcher because no value the store hands out carries the access time; a normal table update would run every thread list of the sidebar again on each opening. |
| AUD-LS1/2 | 2026-11-12 | The cleanup by age keeps an open thread in the sidebar. Without access for `client.cache_max_age` a done thread goes with everything below it, as before. An open thread loses its content: the messages with what hangs on them (reactions, mentions, components, attachments, the files no other message attaches and their cached bytes), the wake-ups, the loaded ranges and the search rows of its messages and transcripts. Its row stays with everything the sidebar reads of a thread: tags, read state, seen mark, notification preference, runs and the title in the search index; drafts stay as before. Its age then starts again. The byte limit (`client.cache_max_bytes`) still removes whole threads, open ones included. Not chosen: leaving open threads out of the cleanup with their content, keeping the row alone, and loading the threads again after the cleanup. | The sidebar lists the open threads the device holds (01 6.8 item 2; the owner ruled on 2026-10-29 that a forum lists every open post, R-PR-23), and a connection that continues from a cursor delivers none of them again (R-SY-28 applies the active threads only with a whole snapshot). With the access recorded, an open post nobody opened for the period would still vanish from the sidebar of this device at its next start, while another device and the same device after a resync list it. A thread without messages and loaded ranges is the state a snapshot delivers (04 6.3 item 4), so its history loads when it opens. The row alone is not enough: nothing delivers the notification preference of a thread again on a connection from a cursor, so a muted thread would come back unmuted, and the counters, the status mark and the run icon of the row would change with the cleanup. The age restarts because a row without the restart would be emptied again at every start, also of the message that arrived the day before; a row that just reached the device starts the same way. Keeping the content of open threads would end the rule that unused content leaves the device (04 13.1, 20 4.7); loading after the cleanup needs the network and a new step in the engine, and an offline start would still show the gap. |
| AUD-LS1/3 | 2026-11-12 | The search index gets the companion table `search_rows` (schema version 16): one row per row of `search_index` with the same `rowid` and the locating columns `kind`, `target_id`, `thread_id`, `channel_id`, `space_id`, with indexes on target, thread, channel and space. Every write of the index goes through `lib/src/search_rows.dart`: a delete selects its rows in `search_rows` and reaches `search_index` by `rowid`; an insert takes the `rowid` from `search_rows`. `watchTranscriptsToIndex` and `pruneTranscripts` read `search_rows` instead of the index. `search_index` itself is unchanged, and so is `search`. The gate is `test/query_plans_test.dart`, not a timed load test. Not chosen: an FTS5 table with external content. | FTS5 reaches a row without a scan only through a match or its `rowid`; the locating columns are `UNINDEXED`, so `DELETE ... WHERE kind = ? AND target_id = ?` read the whole index table once per stored message, inside the page transaction, and so did the tombstone, the deletion of a thread, the removal of a channel or space, the pruning of transcripts and the watched query of the transcripts to index (`SCAN search_index VIRTUAL TABLE INDEX 0:` in the plan; with the companion `INDEX 0:=`). An external content table would rebuild the index in the migration and change how `snippet` and every delete work; the companion leaves the index and the search as they are and the migration only reads the index once. A plan is the same on every machine, a duration is not: the test records the statements the real calls send and fails when one of them reads the index table as a whole. The insert into the index is `INSERT OR REPLACE`, because the `rowid` now comes from `search_rows` and a stale row under it must not fail the storing of a message. |
| AUD-LS1/4 | 2026-11-12 | Schema version 16 adds the indexes `messages(client_msg_id)`, `messages(channel_id)`, `message_attachments(thread_id)`, `message_attachments(channel_id)`, `runs(channel_id)` and `files(scope_channel_id)`. `test/query_plans_test.dart` holds the plans of the statements they serve: the message an outbox entry sent, the attachments of a thread at its deletion, the files of a thread, the threads of a removed channel, the files of its scope and the runs of a post list. | Each of these statements read its whole table: once per thread the cleanup deletes, once per write to `runs` while a post list is open, once per created post. The finding names five indexes; `message_attachments(channel_id)` is the sixth because the removal of a channel reads threads, messages, attachments, runs and read states by channel in one statement, and four indexed arms beside one that scans would leave that statement as it was. |
| AUD-LS1/5 | 2026-11-12 | The step to schema version 16 creates `search_rows`, fills it from the rows `search_index` holds and creates the indexes. It does not clear the cursor. | Nothing of the mirror changes, so no snapshot has to fill anything (15 6.2 allows a step to discard the cache, it does not ask for it). The fill reads the index once; a device without it would have index rows no delete could find. |
| AUD-LS1/6 | 2026-11-12 | `SyncStateDao.clearMirror` takes the channels of the snapshot that replaces the mirror, deletes in the same transaction the file cache rows of the files of every other stored channel (a file whose scope is such a channel, or that a stored message of such a channel attaches) and returns their paths; the engine (`CatchUpListener._replaceMirror`, used by `resync_required` and by a `ready` without a stored cursor) deletes the bytes with the steps after the commit. Files of no channel (avatars) and the files of the listed channels stay. Drafts stay. No `TargetsRemoved` notice is sent, and `recent_targets` and the view states of such a channel are not touched. | A snapshot names what the person sees now and brings no `access.changed`; after the mirror is emptied nothing names the channel of a cached file any more, so the bytes of a channel the person lost stayed in the cache folder until the cleanup by age (04 8.3 item 3 asks for their deletion). The rule needs the mirror, so it runs before the mirror goes, and the bytes go after the commit like every other erased path. Drafts stay because 04 7.3 and 15 7.3 item 2 keep them on a resync: a channel can be missing from a snapshot for a reason other than lost access, and a draft is unsent work. The notice and the rows that hold only IDs are outside what the audit verified (the cached content); a view on a channel the snapshot dropped is handled by the route check as before. |
| AUD-LS1/7 | 2026-11-12 | `MessagesDao.watchContiguous` emits a window only when it differs from the last one; `ContiguousWindow` has value equality over its messages and gaps. The window is still read again on every write to messages, loaded ranges or threads. The other observations of `performance-11` are not changed here (see "Open"). | drift knows the tables a query reads, not its rows, so a write to any thread ran the three reads of every open window and emitted a new object without equality, and each open history column rebuilt and parsed its Markdown again. The reads are three indexed queries; the rebuild was the cost. Equality of the window is the equality of the domain `Message`, which compares every field, so an edit, a pin and a tombstone still arrive. |
| AUD-LS1/8 | 2026-11-12 | Removed, each without a caller outside the tests of this package: `OutboxDao.nextForThread` and `OutboxDao.replaceWithServer`, `MessagesDao.watchThread`, `SearchDao.removeForTargets` and `SyncStateDao.resetCursor`. Kept: `OutboxDao.pendingThreads`, `MessagesDao.pageBefore` and `MessagesDao.tombstone`, the value `OutboxState.confirmed`, and the columns `sync_state.permission_version` and `head_seq`. | `nextForThread` decided by one `depends_on` ID, while the column holds a list since D-M4-15-6, so it offered a rule the outbox no longer follows; the others duplicated `delete`, `watchContiguous`, `removeTargets` and `MigrationRules.resetCursor`. The three kept methods are read by tests of `sync_engine` and of the client; removing them is a change of those packages' tests for no behavior. `OutboxState.confirmed` is the end state of 15 7.5 that six places of the client and the engine compare with, and 15 6.1 names the two columns of `sync_state`. |
| AUD-LS1/9 | 2026-11-12 | `sync-engine-store-14` changes nothing: the steps to versions 6, 12, 14 and 15 keep clearing the cursor. | 15 6.2 and D-M4-12-6 allow a step to discard the cache and load it again, and each of the four steps says why it does (a mirror column only a snapshot fills). They have run on every installed device, so changing them now changes nothing there, and filling a single column through a targeted read is a new mechanism of the engine, not a fix of this package. The step of this ticket follows the advice where it applies (AUD-LS1/5). |

Evidence, each test failed before its change:

- AUD-LS1/1: `apps/client/test/app/cache_cleanup_start_test.dart` runs the whole app against the
  fake server: Alex reads two threads, their access times are moved back beyond
  `client.cache_max_age`, Alex opens one of them again, quits, and the next start (the real
  bootstrap with its cleanup) keeps the messages of that thread and removes those of the other.
  Without the record the start removed the messages of the thread opened the day before.
  `apps/client/test/thread/cache_access_test.dart` holds the same with the clock in the hand of
  the test, and the record at the return of the window focus for a thread that stays on screen.
- AUD-LS1/2: `packages/local_store/test/cleanup_test.dart` (an open thread loses its content
  and keeps its row with what the sidebar reads of it; its age starts again; a thread done
  meanwhile goes; recording an access wakes no watcher).
- AUD-LS1/3 to AUD-LS1/5: `packages/local_store/test/query_plans_test.dart`,
  `test/search_test.dart` (both tables hold the same rows through every kind of write),
  `test/drift/local_store/migration_test.dart` (the step 15 to 16) and `test/schema_test.dart`.
- AUD-LS1/6: `packages/sync_engine/test/catch_up/resync_file_cache_test.dart` (both ways to a
  whole snapshot) and `packages/local_store/test/commit_page_test.dart`.
- AUD-LS1/7: `packages/local_store/test/contiguous_test.dart`.

## Open

Collected, not built in this ticket:

- `performance-11`, the parts outside this package: `DsMarkdown` parses in `build`; the history
  limit of a thread only grows; the message list keeps one key per row it ever showed; the
  counters of a channel walk every read state. None has a measured effect once a foreign write
  no longer rebuilds the history, and each belongs to the client or the design system. A
  performance test for the event load of a long open thread is not added.
- `deleteOrphanFiles` reads the attachment index as a whole
  (`NOT IN (SELECT file_id FROM message_attachments)`) once per deleted thread that had files;
  the finding names the lookups by thread, which are indexed now.
- The cleanup walks `threads`: rows below a done thread that an event stored after the cleanup
  removed its row (the case `removeTargets` already expects) are removed with their channel, a
  resync or the wipe, not by age.
- The kept methods and the value `OutboxState.confirmed` of AUD-LS1/8.
- After a resync that dropped a channel, its rows in `recent_targets` and in the view states
  stay (IDs only), and an open view of it gets no "No access anymore" notice from the engine.
