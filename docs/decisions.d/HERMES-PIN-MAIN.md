# HERMES-PIN-MAIN Hermes adapter pin follows upstream main

Owner decision of 2026-11-07: the Hermes adapter follows the newest commit of upstream Hermes
Agent `main` instead of release tags, without a minimum age for this pin. Hermes installations
that follow upstream main run a commit before any release tag contains it, so the recording and
the tests must run against that commit. A scheduled workflow proposes the newest main commit
once a day as one pull request (spec 09 sections 17.1 and 17.10).

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-HERMES-PIN-1 | 2026-11-08 | The pin (`plugins/hermes-adapter/tests/hermes_pin.toml`) is the newest commit of `refs/heads/main` of `https://github.com/NousResearch/hermes-agent`, resolved with `git ls-remote`, with no `tag` line and no minimum age: `deps.min_release_age` does not apply to this pin. This supersedes the parts of D-M2-32-3 that require a release tag and an age older than `deps.min_release_age`, the exception D-HERMES-MAIN-1 (a tag-less pin only by a ruling that names its commit, and its return to the release rule) and the release-tag form of D-HERMES-COMPAT-3. Release tags are still never the pin; canaries never count (D-HERMES-COMPAT-1), and `--hermes-version=latest` still resolves the newest release tag, which is older than the pin. The pin file names this ruling, and 17.10 carries one line `Current pin: upstream main commit <commit[:12]>, recorded on <recorded_on> (D-HERMES-PIN-1).`; `tests/pin_rules.py` and the fixture tests require both and a pin without a tag. Place: `tests/hermes_pin.toml`, `tests/pin_rules.py`, `tests/follow_main.py`, `tests/unit/test_pin.py`, `tests/unit/test_follow_main.py`, 09 17.1 and 17.10. | The owner's ruling. A daily new pin cannot carry a ruling that names each commit (D-HERMES-MAIN-3 required that); one standing ruling and a sentence the workflow rewrites keep 17.10 and the pin equal by test. The supply chain rule of SEC-SC-1 (full SHA, Hermes' own lock) still holds; only the cooldown is dropped for this pin. |
| D-HERMES-PIN-2 | 2026-11-08 | The scheduled workflow `.github/workflows/hermes-pin.yml` runs once a day (and by hand) on `ubuntu-24.04`, a free GitHub-hosted runner. `follow_main.py bump` reads the upstream main head; when it differs from the pin on `main`, it rewrites `commit`, `recorded_on` (the UTC day) and the 17.10 sentence. The job `record` then runs the existing recording and tests of the component, `make -C plugins/hermes-adapter record` and `make -C plugins/hermes-adapter test`. It runs unreviewed upstream code, so it holds only `contents: read`, gets no token or secret, saves no cache, and hands over only the fixture JSON files as an artifact. The job `propose` holds the write permissions and runs no upstream code: it rewrites pin and sentence again with `follow_main.py bump --commit`, takes from the artifact only regular files named `[a-z0-9_]+.json` into `tests/fixtures/recording/`, commits as `github-actions[bot]` with a DCO sign-off and without the repository's hooks (`core.hooksPath=/dev/null`), force-pushes the branch `bot/hermes-main-pin` (`--force-with-lease`) and opens or updates its one pull request with the outcome of both steps. A failed recording or test still proposes the commit and fails the job, so the red pull request names what to adapt (fixtures, 17.10 verdicts, stubs). Bundled: one branch and one pull request carry the newest commit; a newer commit replaces the older proposal, but never a branch with a commit of anyone else (a maintainer adapting the proposal), and nothing happens while the proposal already names the head. | The owner's default: daily and bundled. The split keeps the write token out of reach of upstream code, which the dropped cooldown no longer buffers (T-SC-01); `tests/unit/test_follow_main.py` holds it. The proposing job needs `contents: write` and `pull-requests: write` only; `actions: write` stays forbidden (D-W-111, `tools/ci/check_runners.py`). Running the recording in the job turns the proposal into evidence: an unchanged mapping arrives green with the new fixtures, a changed one red with the diff. |
| D-HERMES-PIN-3 | 2026-11-08 | Renovate no longer tracks the pin: the two regex managers of `hermes_pin.toml` (D-M2-32-3, D-HERMES-MAIN-2) and the package rule "Hermes Agent recording pin" are removed from `renovate.json`, and a test keeps the pin out of it. | They proposed release tags, which the pin no longer follows, and a tag older than the pinned main commit would move the pin backwards (the open minor of D-HERMES-MAIN-2 about digest updates). |
| D-HERMES-PIN-4 | 2026-11-08 | GitHub starts no workflow for a pull request that the workflow token opens or pushes. The pull request of the workflow therefore runs `ci.yml` (and its ci-ok) only when a maintainer closes and reopens it or edits its title or body (`ci.yml` triggers `reopened` and `edited`); its body says so. The workflow's own record and test steps are the evidence until then. Opening the pull request needs the repository setting "Allow GitHub Actions to create and approve pull requests"; without it the step fails with a pointer to the setting, after the branch is pushed. | No token beyond `GITHUB_TOKEN` and no `actions: write`; both would be owner decisions (a secret, or a policy change of D-W-111). |
