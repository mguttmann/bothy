# AR-01 Specification of autonomous runs

Owner request of 2026-11-06: every session, chat or development, keeps working on its own as long
as it has work, without stopping after some time, so that a steering session can in principle work
on indefinitely when enough tasks exist; with cost safety. Design note:
[autonomous-runs.md](../design/autonomous-runs.md). Decision:
[ADR 0077](../adr/0077-autonomous-runs-wake-ups-and-turn-handover.md). Normative:
[09-agents.md](../spec/09-agents.md) 5.8 and 18.19, 07 2.14, 03 `run_wakes`, `run_autonomy`,
`runs.trigger_kind` and `channels.allow_autonomous_runs`, 01 6.21, 04 15.9, 10 10.4, 13 section 2,
16 10.1, 17 section 3; plan: [PLAN](../PLAN.md) section 22.

Rulings 1 to 5 are the owner rulings of the design note section 11, which the owner delegated and
which are decided as follows.

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-AR-01-1 | 2026-11-06 | Cap on autonomous inputs: `run.autonomous_chain_max` defaults to 25, an operator may raise it, and `0` (no chain cap) is an allowed value. | The default keeps a fresh installation cheap and visible; a higher value lets a steering session work through a long day and still stops visibly if it loops; `0` is allowed because the idle cap (which cannot be switched off), the minimum delay and the pending cap still stop a loop that does nothing. |
| D-AR-01-2 | 2026-11-06 | Who may run on alone: owners always; other persons only in channels with `allow_autonomous_runs`, which is off by default and changed with `manage`. This covers every autonomous input: wake runs, wake inputs, recovery and usage-window wake-ups. | Owners already carry the cost and SR2 decisions; for anyone else the opt-in must be explicit and visible per channel. |
| D-AR-01-3 | 2026-11-06 | GitHub access for `pr_checks` uses the host user's existing `gh` login, read only (`gh pr view` for the head commit and `gh pr checks`), and only for runs of owners. | No new token, account, GitHub app or public webhook; the owner restriction keeps the owner's login away from other persons' runs. |
| D-AR-01-4 | 2026-11-06 | Restart only while no turn runs, until the handover is on: the restart that installs AR-02, the one that installs AR-03 and the one that switches `runner.turn_handover` on happen only while no turn runs (16 10.1). | Until the handover is on, a restart while turns run ends their background work; after it, restarts need no wait, which is the point of the handover. |
| D-AR-01-5 | 2026-11-06 | Recovery runs are allowed within the autonomy rule of D-AR-01-2; a recovery run lists the lost work and runs nothing again; the agent decides what to do again. | The owner wants work to go on after a loss, and R-AG-17 forbids only repeating side effects blindly, which this does not. |
| D-AR-01-6 | 2026-11-06 | R-AG-17 is amended in its row of 09 section 19 (dated): the recovery run is a new run that only informs, and the next attempt of an adopted run by the adoption rule is no retry of an `interrupted` or `stale` run and repeats no answered input. The last clause of D-M2-35-3 ("an adopted turn takes no follow-up") is replaced by a dated "Current state" in its row and in 09 18.5: it holds only for a turn without a named pipe or with stdin closed. | ID rule 1 of DECISIONS.md: rows stay in place and name their current state. |
| D-AR-01-7 | 2026-11-06 | The normative text goes into the chapters of the design note section 7: the server side into a new 09 5.8, the runner side into a new 09 18.19 (the note's "18.18" was taken by hosted agents), the actions into 07 2.14, the tables into 03; no new chapter. Rules R-AG-45 to R-AG-56, tests AR-T01 to AR-T16 in 09 18.19.13 (not in 09 16.2, whose IDs the conformance suite of the server holds one to one). | The design note names the chapters; the stage changes behaviour of the existing runner and run model and has no topic of its own like 26. |
| D-AR-01-8 | 2026-11-06 | Catalogue entries, API operations, events, the reason `usage_limited`, the notification kind `wake_ended` and the metrics enter their machine-read places (`actions.yaml`, `openapi.yaml`, `asyncapi.yaml`, 09 5.2, 13 section 2, `signals.md`) with the AR ticket that builds them; the chapters fix them in prose until then. | Code generation and contract tests hold those tables equal to the code (ADR 0049, the reason and notification contract tests); an entry without its code fails them. |
| D-AR-01-9 | 2026-11-06 | `run_wakes` and `run_autonomy` are part of 03 now, with the module register, 02, the runs README, ERD part 5 and the retention coverage (both go with their parent row: `runs` and `threads`). | 03 is normative for migrations; the register, ERD and retention gates hold the tables in every place at once (the pattern of D-A1-01-3). |
| D-AR-01-10 | 2026-11-06 | `runner.wakes` needs `runner.turn_handover`; the runner refuses to start with only `runner.wakes` on. | A wake input or recovery run written into a turn that the next restart kills would be lost again; the rollout switches the handover on first anyway. |
| D-AR-01-11 | 2026-11-06 | A refused `run.wake.check` and a refused fire end the wake-up the same way: `refused` with the reason, an audit entry, the note in the thread and a notification; `run.wake.check` also checks that the channel is neither archived nor read-only (design note backlog item 24). | One end state per cause, whether a check or the fire found it; an archived channel must stop host executions as it stops a fire. |
| D-AR-01-12 | 2026-11-06 | The deadline of a `usage_limit` wake-up counts from its `not_before` (design note backlog item 21). | A weekly window that resets close to `run.wake_max_wait` would otherwise expire before it fires. |
| D-AR-01-13 | 2026-11-06 | `command` checks: `/bin/sh -c` in the turn's working folder, own process group, the environment of 18.2, stdin `/dev/null`, `runner.wake_check_timeout`, `runner.wake_check_interval` with backoff up to ten times, `runner.wake_checks_max_parallel`, result cut to `runner.wake_result_max_bytes`, stopped at a handover and run again by the next runner (design note backlog item 10). | Agent-supplied code runs outside any run; every bound is a named key and nothing outlives the runner unrecorded. |
| D-AR-01-14 | 2026-11-06 | `pr_checks` fires only when the pull request's current head has at least one check and none is pending; the result names the head and whether it moved since creation (design note backlog item 11). | Right after a push no check may be registered yet; a later push is the state the agent wants to know. |
| D-AR-01-15 | 2026-11-06 | `bothy-wake` requests go through `<runner.state_dir>/wake-requests/<run_id>/` with a per-run nonce in `BOTHY_WAKE_NONCE`; the runner accepts a request only with the nonce of that run (design note backlog item 13). | One turn cannot file wake-ups for another run's folder, also not under `scoped`. |
| D-AR-01-16 | 2026-11-06 | In-flight input lines at a handover: every line is recorded before it is written and marked written after its last byte; an orderly handover waits up to `runner.kill_grace` and records the bytes written of an unfinished line, which the next runner completes first; after a crash in the middle of a write the next runner writes nothing and closes stdin (design note backlog item 6). | A half line followed by another line would be one broken JSON line for the CLI. |
| D-AR-01-17 | 2026-11-06 | systemd: the handover holds only with `KillMode=process`; 16 10.1 says so, and the default `control-group` behaves like a killed keeper (design note backlog item 19). | A new session leaves the process group but not the cgroup. |
| D-AR-01-18 | 2026-11-06 | Hosted agents: the runner adds `Bash(bothy-wake:*)` after the intersection of 26 4.4 and calls `run.wake.list_pending` per hosted agent connection; a hosted agent's `--max-budget-usd` and `disableWorkflows` are listed in the inventory of 09 18.19.12 (design note backlog item 20). | The command is the runner's, not the definition's; each hosted agent has its own connection and token. |
| D-AR-01-19 | 2026-11-06 | Issue 556, items 1 to 4 and the comment: the AR-03 brief names the corrected line numbers as hints only and follows the code; the record carries `stdin_closed`, and an adopter takes stdin only for a turn with a named pipe and `stdin_closed = false` that is no compaction (09 18.19.7); the class test of AR-03 compares the sequence of stdin and stop decisions per recorded stream and checkpoint position (AR-T02); the fallback to today's adoption hangs on the record's named pipe, not on `process_start`; the `launching` record of each attempt carries the highest outage number reached before it, and live read and replay start from it, with a variant of AR-T04 (an outage in attempt 2, a handover, no new number). | The issue's minors belong to AR-03 and the specification; folding them here keeps one place for each rule. |
| D-AR-01-20 | 2026-11-06 | CLI facts read from the pinned CLI 2.1.288 (strings and `--help`, no session) are recorded in 09 18.19.12; what the strings cannot show (named-pipe stdin, the usage-limit frame order and `result` text, `--disallowedTools` in `system/init`) is captured by AR-03, AR-05 and AR-06 against a local stand-in for the API, which needs no login and costs nothing. | The design note marked them unverified; a free capture replaces a paid real turn. |
| D-AR-01-21 | 2026-11-06 | The brief and configuration tools accept the stage `AR` (ticket IDs `AR-<nn>`, status line `Milestone: AR`, planned keys `planned (AR)`), and a ticket ID never follows a letter, digit or dash, so `D-AR-12` and `D-M2-35-3` name no ticket. | PLAN P-29; the tools held only `M` and `A1`. |
