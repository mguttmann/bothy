## Open minors

Found by the red team of FEAT-TEAM-CHANNEL-ADAPTER (round 1) without a shown harm; the next run
in this area takes them along:

1. The member label has no end marker: a member's text can add lines after it that look like
   another speaker's. No right comes with them (a text approves nothing, Hermes commands are
   off), but a data block with a random boundary, as the run context uses, would be clearer.
2. With the same agent twice in a team, or in a run without the member list, the label of a
   follow-up names the agent's own principal handle, which may differ from its team handle (a
   handle with a dot prints as `unknown`).
3. `HermesHandler._teams` keeps its entry when `execute` stops with `PrepareRefused("context")` or
   `startRun` fails, as `_prepared` and `_anchors` do (memory only).
4. `docs/design/cross-project-handoff.md` 7 still says the Hermes adapter follows; the line is
   shared with the runner slice and is updated when both land.
5. With Hermes' `fresh_final` (a final answer sent as a new message, the old preview deleted
   through `delete_message`, which the adapter does not implement), an unfinalized preview could
   be posted at the end as a second answer; against the pinned Hermes only one answer came
   (red team round 2, not reproduced).
6. `_without_cursor` knows only Hermes' default cursor; previews live in process memory only (a
   gateway restart mid-stream loses them); the equal-text check of `_flush_edits` compares the
   cut text, so an answer above `max_message_bytes` may still be updated with the same text.
7. The line "Empty response after tool calls" Hermes sends before such an answer is posted as an
   answer of its own (as before this slice; red team round 3).
