| D-M7-06-1 | 2026-10-25 | Deadline (design note 1): `due_at` is the receipt in UTC plus one calendar month, the same day of the month at the same time; a day that does not exist in the target month moves to the last day of that month (31 January plus one month is 28 or 29 February). The extension of Art. 12(3) GDPR is the additive optional member `extend_months` (1 or 2) of `GdprDecision` (openapi.yaml, 06 section 10): accepted once and only before the original `due_at`, else `409 conflict` with reason `extension_not_allowed`; it moves `due_at`, is kept in `progress.extended_months` and is in the audit entry of the decision with the new `due_at`; the `reason` of the decision is its justification. | Regulation (EEC, Euratom) No 1182/71, Art. 3(2)(c), computes periods of EU law in months that way; `time.AddDate` would roll over into the next month. R-DP-05: the deadline is no configuration value. |
| D-M7-06-2 | 2026-10-25 | Package (design note 2): the job `privacy.export` calls every participant with a writer over a temporary directory; a JSON object file holds one member per section (each written by the module that owns its table), a JSON Lines file one record per line, own uploads go to `files/<file_id>`. Every file of 20 5.2 is in every package (an object without data is `{}`, a lines file is empty). `README.txt` is German for a person whose `users.locale` is German (`de` or `de-*`) and English otherwise; `manifest.json` (schema version, instance, person, request, creation time, size and SHA-256 of every other file) is written last and is the last entry of the ZIP. The ZIP is stored through the new port `files.ExportPackages` as a complete file with purpose `gdpr_export`, `uploaded_by` the person, scan status `skipped` (the server wrote it) and no event; `result_expires_at = now + privacy.export_ttl`. A retry builds the package again; a stored package that the request does not take is deleted at once. The format is described by JSON Schema 2020-12 in `docs/api/gdpr-export/v1/` (one file schema per JSON file referencing one schema per section, one line schema per JSON Lines file), checked by `make api-checks` (rule `gdpr-export`) and against a real package by DP-T03. | The modules own their data (03 principle 12), so the package is assembled from sections; files of fixed presence keep consumers simple. The server writes the package, so a virus scan of its own bytes adds nothing. |
| D-M7-06-3 | 2026-10-25 | Erasure (design note 3): the job `privacy.erase` runs steps 1 to 6 of 20 4.4, each step a call of every participant in registration order (each in its own transactions), and records the last finished step in `progress.last_step`; a crashed job resumes at the next step, and every step is idempotent. Order: notify (push registrations) before identity, the content modules before identity, identity last. `privacy.account_deletion_content` is read when the job starts and kept in `progress.content`. Step 7 is the audit entry `privacy.erase` (system, resource the person, request ID and content mode) in the unit that completes the request; the journal entry is M7-07. The last active owner is refused at creation, at the approval and in step 1 (`409 last_owner`); the job then ends the request `failed` with error `last_owner` without a retry. After `MaxAttempts` failed attempts (10) of `privacy.export` or `privacy.erase` the request is `failed` with error `job_failed`. Both jobs have River's job timeout `RequestTimeout` (6 hours, far above one run): River's rescuer never rescues a job with no timeout, so a worker that died mid-job would leave the request `running` for ever; with it the job is retried and resumes. Step 1 disables the person as the system through the revocation paths of `user.disable`, including the owner role; step 2 deletes identities, local credentials, passkeys, keys, tokens, enrollment codes, login flows, pairings, challenges, devices and sessions (a device or session a terminal session still holds stays without name and IP until `retention.security` removes it) and push registrations; step 3 sidebar, read states, drafts, settings, idempotency keys, notification levels, quiet hours and personal templates; step 4 removes memberships and revokes grants (rows stay); step 5 with `delete` deletes own messages through the deletion path of 20 4.2, own reactions, and own files through 4.3; step 6 pseudonymizes `principals` and `users` (`Deleted person <id>`, `deleted-<id>`, no avatar, no email, default language and time zone, status `deleted`). | 20 4.4 and the brief's resume rule; one transaction per participant lets each module reuse its own use cases (the message deletion, the revocations), which a shared transaction would forbid (nested rights changes). |
