| AUD-SW1/1 | 2026-11-12 | While the start lock of R-DM-50 holds (`restore_not_finalized`), the start step `routes` does not mount the incoming webhooks on the internal listener (`server.finalized` before `mountInternalHooks`): both post paths answer `404` there, in every role, until the start after `bothy restore finalize`. `TestInternalListener_NoIncomingWebhookBeforeRestoreFinalize` (test/integrations) posts with a valid token to a node of each role on a database whose stored identity differs; the harness option `NotReady` starts such a node. The signing keys step stays as it is: it runs before the lock skips anything (02 15.1 step 6), and it writes only when a purpose has no active key with its file. | The internal listener stays open under the lock, and a post of a sender inside the stack (Alertmanager) wrote a message, its events and audit entries on the restored timeline; the test answered `201` and stored the message in every role before the change. That is a further case of the class of D-M7-04-7 and D-M7-04-10 (docs/decisions.d/M7-04.md), and it moves the heads that `restore finalize --relocation` compares. Units of work that begin `READ ONLY` under the lock, the other way to close the class, would end the start in the signing keys step whenever that step has to write, for example after a restore without the key store (`signing_key.accept_lost_keys`). `404` is the answer of a path the listener does not serve; a sender that retries (Alertmanager at its next group interval) delivers after the finalize. |
| AUD-SW1/2 | 2026-11-12 | New key `privacy.export_work_dir` (string, default empty: the temporary directory of the system; cross-check `export_work_dir_absolute`): the directory below which the job `privacy.export` builds a package. `wire.PrivacyDeps.TempDir`, which nothing set, is gone. In the Compose stack `worker` sets it to `/var/lib/bothy/export-work` on the new volume `export-work`; the server image carries that directory with owner 65532 and mode 0700, so the volume takes both. `TestExportBuildsInWorkDir` (test/privacy), `TestConfigCheckExportWorkDir` and `TestComposeExportWorkDirOnVolume` (internal/wire) hold it. Not built: a check of the free space before the export, an archive that streams into the object storage, a load test with a large account. | `/tmp` of the hardened containers is a tmpfs, so the package of a large account, a copy of every own upload plus the archive, was built in memory. A named directory on a volume moves that to the disk. A failed attempt already ends cleanly (the package directory is removed, the job retries and the request ends `failed`), so the free space check adds no safety that the failure path lacks; streaming needs another archive format, because `manifest.json` carries the checksums of all other files and is written last; a load test is a suite of its own. These three stay open as minors of the privacy module. |
| AUD-SW1/3 | 2026-11-12 | `backup.pg.local_retention_full` keeps its default. 16 section 8.2 and section 14, `docs/operations/backup-restore.md` 5.1 and the description of the key now say what follows from it: a point-in-time restore from repo1 reaches back to the oldest kept full backup, so without an off-site target the window starts anew with every full backup, also one run by hand before an upgrade. No new warning in `bothy config check`. | The behaviour is the documented and tested one (`test/postgresimage` holds one full backup in repo1); what was missing is the consequence for the operator. With an off-site target repo2 holds the longer window, and a second full backup in repo1 would double the space of every installation to protect the mode that `bothy config check` and the start log of `bothy-backupd` already call "local backup only". The operator who wants the window sets the key. |
| AUD-SW1/4 | 2026-11-12 | 20 section 2 lists `agent_definitions` (content), `audit_ip_keys` (no), `deletion_journal_state` (no) and `gateway_presence` (indirect), and section 9 says that the live connections of people serve only the routing of notifications. `TestEveryPersonalTableHasAParticipant` now requires every table of `architecture/modules.yaml` in that section. The participant of agents names `agent_definitions`; the gateway gets a participant for `gateway_presence` (`adapters/postgres.PersonalData`). Both export and erase nothing for these tables. The export package gets no section for the definitions a person wrote. | The test read the list of tables from the very document it checks, so a table nobody entered there needed no participant; four tables were missing. Definitions are configuration of the instance and are never changed (R-DM-59), like the spaces and channels a person created, whose rows the export does not hold either; `created_by` becomes pseudonymous with the principal. A presence row is no stored record: it ends with the connection, which the revocation of the login sessions closes. A new section would change the export contract `docs/api/gdpr-export/v1` and is a product question of its own. |
| AUD-SW1/5 | 2026-11-12 | `backup.max_age`, `backup.restore_test.max_age` and `dr.rpo_target` stay planned keys (D-M7-03-9, R-OP-04): only the alert rules read them. Goal 3 of 16 section 1 and RK-51 now say what is measured: the duration of a restore from the local repository against `dr.rto_target`; no test measures the data loss, and the way back from the off-site target is not measured. | A key enters the schema with its first consumer in the server, and the alert tests hold the thresholds of the rule file against the defaults of the chapter. The two sentences claimed a measurement of both targets that the restore test of 8.3 does not make. A measurement of the WAL archive lag as data loss, or of a restore from the off-site target, would be a new check of the restore test. |
| AUD-SW1/6 | 2026-11-12 | No cross-check compares the sum of `jobs.queue.<queue>.max_workers` with `database.max_conns`. 16 section 13 and the README of `platform/jobs` state the rule instead: the queues share the pool, a job holds a connection only inside its units of work, an exhausted pool shows in `bothy.db.pool.connections`, and role `all` shares the pool with the API. | A handler holds no connection while it works outside a unit of work (a webhook delivery sends between two units of work), so a sum above the pool is a working configuration, the default one included; an error would refuse it, and a warning would show on every installation. `database.max_conns` is a start value that the load test confirms or changes (16 section 13). No failure was reproduced. |
| AUD-SW1/7 | 2026-11-12 | The size of `internal/wire` is not changed here (deferred). | The facts hold on `main`: the package has 120 files without tests, among them 37 `configkeys_*.go`, 26 Bind, Set and Enable methods and three lazy proxies. Its layout follows PL/28 (one wiring file per module) and L4 (the schema of the keys in the code of the server). The recommended cut, one sub-package per module as a component of the module register, the key declarations in an adapter of the owning module and a start order derived from `depends_on`, is a redesign of the composition root, of `tools/archgen` and of the config schema export, with every module file touched. It needs a design of its own. |
| AUD-SW1/8 | 2026-11-12 | `bothy-backupd` keeps `migrate.bootstrap_user` for `pg_dump`, the manifest queries and the restore test (deferred). | The use is the one D-M7-02-3 and 16 section 8.2 describe, and the finding is right that a read role would do for the dump and the counts. The change is one of database rights and of the distribution of secrets: a grant of `pg_read_all_data` to `bothy_backup` in `migrate up --bootstrap` (also for existing installations), the pools and the tool environment of `bothy-backupd`, the secret files that `secrets-init` hands to `backup`, the role table of 16 section 7.1 and the image tests of backup and restore. It spans four components and needs its own review of the rights, so it is a ticket of its own. |
