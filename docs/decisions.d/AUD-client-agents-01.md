# AUD-client-agents-01 Lines of ended runs, retry layers and one-time actions of the agent interface

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-CA01/1 | 2026-11-12 | The anchor of a run whose summary the local `runs` table lacks loads the runs of its thread: `RunLine` watches `threadRunsBackfill`, whose `ThreadRunsLoader` reads every page of `listThreadRuns` and stores each summary by the version rule, like `run.state_changed`. The load is asked for by such an anchor only, once per thread while one shows; a thread whose anchors all have their run asks for nothing. A page is stored only while the thread and its channel are stored on the device, checked in the transaction of the write. A failed read keeps what the table holds. The loader lives in the app (`apps/client/lib/agents/thread_runs_loader.dart`), next to the refresh of "Running now", which writes the same table from `listActiveRuns`. | The table is filled only by the active runs of the snapshot and by `run.state_changed` since then, and a resync empties it, so a new device and a device after a resync drew nothing at the anchor of a run that ended before: no line, no "Retry", no "Send again" (01 3.2 lists the collapsed line as core). Every page, because the list is paged newest first, an older anchor needs an older page, and "Retry" is offered only for the newest run of the thread, which the first page settles. On demand, because a device that followed the events holds every run and must not pay a read per opened thread. The check in the transaction keeps an answer that arrives after a removal from storing the summary of a thread the device no longer holds. |
| AUD-CA01/2 | 2026-11-12 | A refused read is repeated in one place, the read retry of the API client (D-M4-02-5). `endedRunDocument`, the one provider of the agent interface that passes the failure of a read on, carries `retry: noProviderRetry`, so Riverpod never runs it again; the line loads the document again when it is expanded or built again. The root `ProviderScope` keeps the default of Riverpod. | Riverpod runs a provider that threw an exception again several times, and each run went through every attempt of the read retry, so one refused `getRun` became a multiple of both limits. The read retry already waits `Retry-After` plus jitter and has its limits from the configuration; the second layer had none of that and was never chosen. A rule at the root scope would change how every view of the app recovers from a failed read and belongs to a ticket of the app scope; the other providers of the agent interface answer null or an empty list on a failure and never reach that retry. |
| AUD-CA01/3 | 2026-11-12 | `/status` and `/resume` read the sessions of the thread with `AgentReads.sessionsNow`: one attempt without the read retry (`noReadRetryExtra`), and a failure is an exception. Their dialogs then say "The sessions could not be loaded. Try again." (`commandSessionsFailed`): `/resume` in place of "No earlier sessions", `/status` under the run this device knows. An `Error` is not caught there. `AgentReads.sessions`, the read of the session column, keeps the read retry and still answers an empty list on a failure. The other catch blocks of the agent, file and terminal folders stay as they are. | A person who types a command waits for its dialog: with the read retry it opened only after every attempt had failed, and then `/resume` said that the thread has no earlier sessions, which was not known. The session column makes no statement about absence and fills in when it is built again. The audit's own check found that most of the other catch blocks set an error state or throw again; changing them all is not a fix of this finding. |
| AUD-CA01/4 | 2026-11-12 | A one-time action without a thread waits for its outcome with `outboxOutcome` (`apps/client/lib/sync/outbox_outcome.dart`): null once the entry left the outbox, else the code and reason of the refusal, after the failed entry was discarded. "Retry" on a run line, the cancel of a wake-up and the channel switch of autonomous runs use it instead of their own subscriptions. The wait belongs to the entry and ends with its outcome also when the view is gone. `Outbox` of the sync engine is unchanged; Stop stays a plain entry without a wait (changed by AUD-CM01/3: Stop waits for its outcome the same way); `outboxRetrigger` of the thread view, which already had this form, stays. | Each of the three views listened to the entries without a thread itself and stopped listening when it was disposed, so a refusal that arrived afterwards left a failed entry that no view shows and nothing removes. One function removes the three copies and that leak. Stop has no place to show a refusal; adding one is a new part of the interface and not this finding. |
| AUD-CA01/5 | 2026-11-12 | The name of a built-in command is matched without letter case (`BuiltinCommand.byName`). | Registered commands and the suggestions were matched that way already, so `/Stop` was neither a built-in nor a registered command and went out as a message, which reaches the model or a running turn; 09 10.1 reserves the names and keeps control commands away from a model. |
| AUD-CA01/6 | 2026-11-12 | The collapsed line of an ended run keeps loading its document when it is built (D-AR-08-3); nothing changes for the audit's proposal to carry the end state in the run summary. | That load is a recorded decision: the end state lives in `runs.metrics`, which the summary does not have, and moving it there changes the API, the event, the sync engine and the local table. What made the load expensive, the second retry layer, is gone with AUD-CA01/2. |
| AUD-CA01/7 | 2026-11-12 | The bookkeeping that `LiveBoxSlot`, the control room and the live page do while they build (start and stop of the second timer, the run shown last, the announcement of an end after the frame, the source per engine) stays, and so do the decode of the run document per build of a control room card and the reads per row of "Running now". | Each of these steps is guarded so that a repeated build changes nothing, and the announcement runs after the frame; no wrong behaviour follows from them. The decode was measured for this ticket and is small against the second between two builds of a card; the rows are built again only when the set of active runs changes. Moving them would restructure working code of three folders without a change a person or a measurement could see. |
