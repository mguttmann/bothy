| AUD-CM01/1 | 2026-11-12 | The app reports its build name. `BuildBranding.fromEnvironment.appVersion` is Flutter's `appBuildName` (`package:flutter/services.dart`): the `--build-name` of the build, else `version:` of the pubspec, and `0.0.0` without either. The build branding carries no version any more: `tool/branding_defines.dart` writes no `BRANDING_APP_VERSION` and reads no pubspec. The release steps hold the two sides together at the artifact: `check_dart_version` and `dart_code_reports` of `tools/distribution/common.py` look for the version as a whole dotted number in the compiled Dart code of the build (`App.framework/App` on macOS and iOS, `data/app.so` on Windows, `libapp.so` of every ABI in the App Bundle) in `apple.release_step`, `windows.release_step`, `ios.check_archive` and `android.verify_bundle`, which the releases and the trials share, and stop the step otherwise. The trials build `TRIAL_VERSIONS`, versions that no other text of the app holds. | The version came from a define of the branding tool, which read `version:` of the pubspec, and that is `0.0.0` in every member; the release steps set only `--build-name`. So the package of a release said `X.Y.Z` and the app `0.0.0`: with a minimum version set (R-RL-08) every app, the newest included, was refused as too old, and the device entry, telemetry and crash reports named `0.0.0`. The audit proposed to hand the version to the tool as an argument; Flutter already compiles the build name into every build from the same option that names the package, so a second hand-over would be a second place to fall out of step. A version as short as `1.0.0` can pass the check of a real release by chance, which is why the trials do not build one. Proof at the artifact: `make -C apps/client trial-android` on the build machine failed before the change of the app with "the Dart code of the build does not report the version" for `libapp.so` after the manifest check had passed, and passes with it; the trials of macOS, Windows and iOS need their own hosts and run in CI. |

| AUD-CM01/3 | 2026-11-12 | Stop of a run is an action with an outcome. `RunStops` (`apps/client/lib/running/providers.dart`) holds the runs whose Stop is on its way, from the activation until the server refused it; a Stop the server accepted stays, because that run ends. `stopRun` (`lib/running/stop_run.dart`) is the one Stop of the live box, the rows and cards of "Running now", the run graph and `/stop`: one activation puts one `cancelRun` into the outbox, a second one while the run is held does nothing, and the wait for the outcome (`outboxOutcome`) discards an entry the server refused for good, frees the run and shows "The run was not stopped" with the reason on the app's messenger. While a run is held the Stop of a row and of the run graph is busy, and the live box and a card offer none. Without a connection the entry waits in the outbox. This replaces the sentence of AUD-CA01/4 that Stop stays a plain entry without a wait. Not built: a labelled state "Stopping" in the live box and on the card, whose components (`DsLiveBox` of the design system, `RunControlCard` of `bothy_viz`) have no busy state. The held runs last as long as the session: a Stop that still waits when the app ends is not shown as on its way after the next start, and a refusal of it then stays in the outbox, as for every one-time action of AUD-CA01/4. | The Stop was put into the outbox without a thread and nobody looked at it again: the button stayed active, a refusal (the run had ended, `409`, or the right was gone, `403`) showed nowhere although the comment at `mayStop` promised a failed write, and the failed entry stayed in the table for good, because only a thread shows its failed entries. The busy button and the notice need no new component; a state inside the live box and the card does, with their goldens, and belongs to a ticket of those packages. |
