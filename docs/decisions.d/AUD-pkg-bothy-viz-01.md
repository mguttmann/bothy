# AUD-pkg-bothy-viz-01 Executive page: rates, period, active people; run history paging; fixture content

Six findings of the audit of 2026-11-11 against `packages/bothy_viz` (`viz-grafana-1`,
`fn-console-stats-viz-3`, `viz-grafana-2`, `viz-grafana-3`, `viz-grafana-4` and `viz-grafana-10`).
One is a fault a person sees on the executive page of "Live": failure rates were shown a hundred
times too small. Three concern what the page says and asks: it named no period and the server
answered two calendar days for the last 24 hours, the tile of the active people never appeared,
and costs in several currencies replaced the whole page by an error. One concerns the run
history, one the fixtures that hid the first fault, and one the cost of the timeline at the
limits of the server, which is recorded and not built here. Normative text: 25 sections 6.4 and
7.2, the package README, the fixtures README and the README of `tools/api-checks`.

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-VZ1/1 | 2026-11-11 | A rate of a query answer is a share from 0 to 1. `ExecutiveModel` turns it into percent once, when it builds the tile; `TileUnit.percent` keeps its range of 0 to 100 and no unit for shares is added. A rate is a metric named `<what>_rate` or the push rate of a provider, `push_failure_rate_<provider>` (`vizIsRate`); a count is never one, also when its code reads like a rate (`failed_reason_rate_limited`); the statistics page of the administration tells rates from counts with the same function. | The server divides failed by finished (`run_failure_rate`, `webhook_failure_rate`, `push_failure_rate_<provider>`), and the test of the started server pins shares. The tile passed the share to a formatter that expects percent, so 0.14 read "0 %", and the push rate, whose name does not end in `_rate`, read as a rounded count. One conversion at the place that knows the metric keeps the tile, its comparison text and the mark as they are; a second unit would have to be told apart in each of them. |
| AUD-VZ1/2 | 2026-11-11 | The executive page asks `getUsageStats`, `getRunStats`, `getErrorStats` and `getCostStats` in hours on whole UTC hours: the hour that holds the end of the host's range and as many hours before it as that range is long (`executiveRange`). It names this period under its title. This replaces "reads the five queries once" for the host's range of D-M6-12-3; the host and its range are unchanged. Not built: a period in days of `stats.time_zone`. | Asked without a bucket size, the server takes days of its own time zone and widens the range to every day it touches: two calendar days for the last 24 hours, which the tiles summed without saying so. Hours are counted in UTC, so the page can form bounds the server does not widen and name them without knowing the server's time zone; this is the rule the 24 hour preset of the statistics page follows. A period in days needs the time zone of the instance from the host and would make the page show a calendar day instead of the range the host chose. |
| AUD-VZ1/3 | 2026-11-11 | Every count of the three answers is its sum over the period: the list of D-M6-11-1 gains `threads_done`, `scan_errors`, `scan_infected`, the messages by origin (`messages_<origin>`) and the failed runs by reason (`failed_reason_<code>`). A level stays the value of the latest bucket of a single group (D-M6-11-1) and now carries the start of that bucket, shown as "Since: ..." in the tile, its screen reader label and the table; the current storage, which the server puts into the last bucket only, carries none. No rate over the whole period is computed. | With hour buckets the latest bucket is one hour, so a count that was not summed would have shown one hour under a page that names 24, and a level without a note would have read as a value of the whole period. "Since" is exact for a level: a later bucket is absent only when it has nothing to measure. A rate over the period cannot be computed from the answer, which carries the rate of each bucket without its denominator. |
| AUD-VZ1/4 | 2026-11-11 | The active people come from a second `getUsageStats` query in weeks over the same range. The tile shows the latest week of a single group and reads "fewer than the minimum group" where the server withheld the number (`below_min_group`). With several groups there is no tile, as D-M6-11-1 rules for every level, and 25 section 6.4 says so. Not built: one tile per space, and a number for the whole instance. | The server counts people per week or month only, so the tile could never appear from the query in days. The answer is grouped by space, and the people of two spaces are no sum: a number for the instance needs a metric the server does not have, and a tile per space would repeat the table of the statistics page on a page meant as an overview. |
| AUD-VZ1/5 | 2026-11-11 | `StatsQuerySource.costs` takes a `currency`. When `getCostStats` answers `currency_required`, the page asks again with the first currency the server names and shows a note; it has no currency selector. The statistics page reads the currencies of the refusal with the same function (`vizRequiredCurrencies`). | Only `forbidden` was handled, so costs in two currencies ended the whole page, the traffic lights included, in an error. The server answers one currency at a time; the amounts name their currency, and the statistics page offers the choice. A selector would be a control on a page that TV mode shows without controls. |
| AUD-VZ1/6 | 2026-11-11 | A further page of the run history that fails keeps the loaded runs, the filter and the table form; its problem text stands above "Load more runs", and the next press asks for the same page again. The first page, the detail of a run and every other view keep D-M6-12-1: the problem text, no automatic retry, a new view from the host. No retry with backoff and no error callback to the host are added. | The view showed only the problem and hid the runs a person had already loaded, together with the filter. A press is a request of the person and no retry of the view. The remaining points of the finding are the ruling D-M6-12-1, and the host builds a view again on a change of tab, scope or TV mode. |
| AUD-VZ1/7 | 2026-11-11 | The series fixtures carry what the server sends: rates as shares, the push rate per provider, no `active_people` in day buckets, and a new answer in weeks (`StatsSeries.usage.week.json`) with the number withheld in one space. The check `viz-fixtures` gains the sub-check `content` for the series of a query: metric names as the description of the operation lists them, rates from 0 to 1, people only in weeks or months. Not built: fixtures recorded from a running server, and load fixtures at the limits of the server. | The schema leaves `metrics` open, so a fixture with rates of 1 to 16 passed the gate and the goldens showed plausible percent values over the fault of AUD-VZ1/1. The names and scales stand in the descriptions of the operations, which the check now reads, so they have one home. A recording would tie the fixtures to one test world of the server and its random identifiers; the check states what it does not cover (a value the server would not compute from real rows). The load fixtures belong to the measurement of AUD-VZ1/8. |
| AUD-VZ1/8 | 2026-11-11 | Not built in this package: drawing the state icons of the bar mark in its painter, rebuilding only what depends on the playhead, lists as slivers, and a measurement of the timeline at `stats.timeline_max_runs` with a budget. | The finding is real: every tick of the playback rebuilds the whole chart, and the cost grows with runs and rows. Measured on 2026-11-11 in a widget test (debug build, shared host, so only the proportion counts): one rebuild took about half a second with the runs of the load fixture, about two seconds with the limit of the server in 50 rows and several seconds with one row per run. The fix changes the bar mark, the timeline view and the contract of the views (columns without their own scrolling), and a budget needs a measurement in profile mode on the reference hardware (D-M6-12-6, D-M6-12-10). That is a redesign with its own ticket, not a fix inside this package. |

Evidence. The tests of AUD-VZ1/1 and AUD-VZ1/6 failed before their change.

- AUD-VZ1/1: `packages/bothy_viz/test/executive_rates_test.dart` decodes the answer of
  `getErrorStats` with the generated serializers, with the values the test of the started server
  pins for the instance and for one space (`TestStats`, subtest `ErrorRates`), and reads the tiles
  on the screen: 0.2 is "20%", 0.25 "25%", the push rates per provider are percent. A third test
  goes through `ExecutiveView` and the fixture answer. Before the change each of them read "0%".
- AUD-VZ1/2 to AUD-VZ1/5: `packages/bothy_viz/test/executive_period_test.dart`: the bounds the
  page sends are the ones the alignment of the server leaves unchanged, the page names them, a
  count is its sum, a level names its bucket, the people tile with one space, below the minimum
  group and with two spaces, and costs in several currencies.
  `packages/admin_ui/test/live/live_query_source_test.dart` sends the currency through the
  generated client and reads the currencies of a refusal.
- AUD-VZ1/6: `packages/bothy_viz/test/run_history_view_test.dart`, test 'a failed "Load more
  runs" keeps the loaded runs'.
- AUD-VZ1/7: `tools/api-checks/tests/test_viz_fixtures.py`: a rate of 16, a push rate without
  provider and people in a day bucket each fail the check. Against the fixtures before this
  change the sub-check reports each of the three.
