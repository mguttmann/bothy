# FIX-macos-migration-denied A refused old item never loses the session

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-MMD/1 | 2026-11-01 | In the macOS login keychain the move reads by name only what the build before the app scope read at every start: `app/server_address`, `app/update_notice_dismissed` (`FlutterSecureBackend.legacyReadAppKeys`), the instance keys, and the session keys under the origin of the remembered server address. It never reads `app/instance`, and so never moves or deletes it. Where `app/instance` is not read, the remembered server belongs to the instance of this app that has an old session under its origin; only then do the app keys move with that instance. The Data Protection keychain, iOS, Android and Windows keep `readAll`. Replaces the app key list and the "origins of the remembered server address and instance" of FIX-SSM/1. | Live report of 2026-11-01: the build of the move did not take over the owner's macOS session; securityd refused one old item whose access list trusts only the app of an older bundle identifier. Cause, proved from the source and the unified logs of the launches: the build before the scope reads `app/server_address` at its start, connects, and on a successful discovery only writes `app/instance` (`OnboardingController.connect`); it reads `app/instance` only when discovery fails. The move read `app/server_address` (answered without a refusal) and then `app/instance` (the refusal, the only one of the launch), the second old read of the launch. The three items from the time of the older bundle identifier were created in the same second; that the first is readable by the current identity and the second is not means their access lists differ now: the items the build before the scope reads at every start were granted to the current identity once, when an earlier update showed keychain access dialogs for them (inferred: the access lists cannot be read without a dialog), `app/instance` never was, because that build never needed its value. Reading only what that build read gets no refusal it did not get. |
| FIX-MMD/2 | 2026-11-01 | A refusal is never final. An item the old store does not give out (any status other than success and not found from `LegacyKeychain`, a refused `readAll`) stays at the old place; the instance it belongs to is not copied (no half session), the other instances and the readable app keys are copied, the refusal is logged with the keys and statuses, and no marker is written, so the next start tries again. There is no "not migratable" any more. Replaces FIX-MLKP/2 and FIX-MLKP/5. | One refused item made the whole move "not migratable" and wrote the final marker, so the owner's session was lost for good although every item of the session was readable. A refusal can end (an unlocked keychain, an access granted later); a retry costs a few reads without user interaction, no dialog. |
| FIX-MMD/3 | 2026-11-01 | An instance counts as moved only when the scope holds its session (a refresh token under `instance/<id>/auth/`); until then its old secrets are copied again and replace what an earlier move left in the scope (the database key of the old local database, `device_key_scope` = `instance_id`). The marker `app/secret_scope` ends the move only while the scope holds a session; a marker without one (written by the build of the failed move) does not stop a retry. The pending list of old items (`app/legacy_pending`) of an earlier move is kept and extended. Replaces "only for an instance without any secret in the scope yet; a value already in the scope wins" of FIX-SSM/2. | The owner's Mac after the failed move holds the final marker and, in the scope, a new database key, a device key scope, the server address and the instance, but no session; under the old rules every later build skipped the move (marker) and every instance (secrets in the scope). The old local database is encrypted with the old database key, so the old key must replace the new one. A session in the scope is the only state that proves the app no longer needs the old one. |
| FIX-MMD/4 | 2026-11-01 | The old items are deleted only after the first write of their instance's refresh token into the scope (unchanged, FIX-SSM/3), and only the items the move copied. Evidence against the real login keychain: `apps/client/tool/run_legacy_keychain_test.sh` writes the owner's state on a keychain without `app/instance` and `app/server_address` (a CI runner): the old session written by the plugin the way the build before the scope wrote it, a foreign `app/instance` that trusts only `/usr/bin/true`, and the final marker of a failed move with its leftovers in the scope; `integration_test/legacy_keychain_test.dart` proves the session moves, the old database key and device key scope win, nothing is refused and the old items stay. On a keychain that already has those two items the case is skipped and nothing of them is touched. Not covered: an old item that the build before the scope read but that the keychain still refuses to the current identity (for example after a change of signing certificate) leaves its instance at enrollment until it is readable. | The class "the fake answers what the real keychain refuses" came a third time; the fix is held at the one place every old read goes through and tested against the real artifact. The fixed names of the two app keys are shared by every build on a machine, so the real-keychain case must not run where a person's own items could be overwritten. |
