| D-M5-08-1 | 2026-10-25 | Policy in `getInstance`: `InstanceInfo.app_lock` (`AppLockPolicy {required, after_ms}`, required in the response) for every authenticated caller, from `security.app_lock_required` (bool, default `false`) and `client.app_lock_after` (duration, default `5m`, at least `1s`), both process configuration registered in the instance key file. | D-M5-08-2 | 2026-10-25 | Lock triggers: a cold start that resumed a stored session locks before the first frame with content (the privacy cover stays while the switch and the cached policy are read); a fresh login does not. Afterwards the lock closes when the time since the last pointer or key event reaches `after_ms`, in front (a timer) or since the move to the background (checked on the return). An incoming message, an upload or a policy change is no activity. Without a known policy the time is zero, which locks on every return from the background but never while the person uses the app. The clock is injected; the rules are pure functions. | 01 5.6 E6; 08 9; brief Design note 2. |

| D-M5-08-8 | 2026-10-25 | The time without use is counted on two clocks (red team round 1): the wall clock, which keeps counting while the device sleeps, and the monotonic clock of the app process (`Stopwatch`), which nobody can set; the lock uses the larger of both, and a wall clock set back before the last activity counts as reached. So setting the device's date back in the system settings (possible without the device code) never keeps the lock open, and the time a sleeping device spends still counts. The order of the last activity and the move to the background is taken from the monotonic clock. E6 replaces the content without a page transition, because a transition would keep the replaced content painted while it runs; while the lock decides at a cold start the app rebuilds at once, so the privacy cover is in the same frame as the signed-in route. | T-DV-01; 08 9; brief Design note 2. |
