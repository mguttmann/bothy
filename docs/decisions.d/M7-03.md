| D-M7-03-1 | 2026-10-20 | Order and skipping (design note 1): check `pgbackrest` reads the newest succeeded `pg_full` or `pg_diff` from `backup_runs`, restores its label, runs `pgbackrest verify` on repo1 and starts the copy. | D-M7-03-3 | 2026-10-20 | Manifest check: the manifest of a physical run is read after the backup step (D-M7-02-6), the copy ends at the consistency point of the backup (recovery target `immediate`), so writes in between may differ. The check fails when schema version, `instance_id` or `sync_epoch` differ, when the copy is newer than its manifest (event head or audit head above it, `copy_newer_than_manifest`), when the audit heads are equal but the hashes differ, or when a table of the manifest is missing or the copy has another one. When the event head and the audit head of the copy equal those of the manifest, the row counts of `event_log` and `audit_events` must be equal (`row_counts_differ`); otherwise no count is compared. The counts of the other tables are never compared: sessions, tokens, cleanup jobs and `backup_runs` itself change rows without an event or audit row while a backup runs (found by the code review). | Exact counts on a busy instance would fail tests of undamaged backups and page the owner; every row of the two logs carries the number of its log, so at equal heads an undamaged copy holds exactly the rows of its manifest. |
| D-M7-03-4 | 2026-10-20 | Sampling (rule 15): per test `ORDER BY random() LIMIT n` over `threads` and over `files` with `deleted_at IS NULL AND upload_state = 'complete' AND scan_status IN ('clean', 'skipped')`; with fewer rows every row is checked. A pending upload has no object at its key yet, and the scan pass deletes the object of an infected or unscannable file while its row stays (found by the red team), so both are left out. Thread rule: `count(*) = max(thread_seq) - min(thread_seq) + 1`, `min >= 1` and `max = threads.last_message_seq`, or no messages and `last_message_seq = 0`. Objects: `restic restore latest --tag objects --path <file.fs.root>` with one `--include` per key into `<scratch>/objects` (the path picks the object backup, because the manifest snapshot of an objects run carries the tag `objects` too), read through an `os.Root`; a key the backup lacks is `object_missing`, other bytes `object_hash_mismatch`. With the driver `s3` the objects lie in the mirror of the off-site bucket, which this build does not fetch: check 6 is `skipped` with `objects_driver_s3`. | The brief names the restic fetch; a fetch from the mirror needs an S3 client in the restore path, left for the ticket that needs it (follow-up in the report). |
