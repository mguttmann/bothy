| D-M5-01-1 | 2026-10-15 | Key parameters (brief note 2): alias `<prefix>.<sha256(scope)>.<purpose>` (lowercase hex, prefix `device_key`, tests `test.device_key.<uuid>`), `KeyPairGenerator` `EC` in `AndroidKeyStore` with `secp256r1`, purpose `SIGN`, digest `SHA256`. `dpop` without user authentication. `step_up` with `setUserAuthenticationRequired(true)`, from API 30 `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`, before it `setUserAuthenticationValidityDurationSeconds(-1)`, and `setInvalidatedByBiometricEnrollment(true)`. From API 28 StrongBox is tried first and the key is generated again without it on `StrongBoxUnavailableException`; below API 28 an `SDK_INT` check skips it. A missing step-up key is created only when `BiometricManager.canAuthenticate` accepts the authenticators of the API level, otherwise `not_available`. | 08 6.1, 15 9; the alias keeps server addresses out of the Keystore, as on Apple (D-M4-10-3). |
| D-M5-01-2 | 2026-10-15 | The attestation is the key's certificate chain from `setAttestationChallenge`: the DER certificates, leaf first, concatenated (the channel member is bytes and the DER framing separates them). Android binds the challenge when it creates the key, so `attestation` creates a missing key with the challenge and returns its chain, and returns null for an existing key and where the device does not attest (a chain of one certificate); the app asks for the attestation before `ensure` when it registers. | M4-10 defined the member as bytes without an encoding; returning a chain with an old challenge would look like a fresh attestation. |
| D-M5-01-3 | 2026-10-15 | Device credential rule: from API 30 the step-up accepts strong biometrics or the device credential (the prompt then has no negative button); on API 26 to 29 strong biometrics only (the prompt shows the negative button from Dart), and a device without enrolled biometrics on those levels gets `not_available` for `step_up`. Written into 15 9 and the Android row of 08 6.1. | A per-operation key cannot be unlocked with the device credential before API 30 (brief note 3); the app explains that step-up needs biometrics there. |
| D-M5-01-4 | 2026-10-15 | Signatures: `SHA256withECDSA`, DER converted to `R \|\| S` with strict DER parsing (minimal integers, at most 33 bytes, left padding to 32). `hardwareBound`: from API 31 `KeyInfo.securityLevel` StrongBox or trusted environment, before it `isInsideSecureHardware`. Errors leave with a fixed text and never with a cause: `KeyPermanentlyInvalidatedException` is `key_invalidated`; `UserNotAuthenticatedException` and, from API 33, `android.security.KeyStoreException` with `ERROR_USER_AUTHENTICATION_REQUIRED` (what the Keystore throws at `sign` for a step-up signature without the prompt) are `not_available`; below API 33 that case is `internal`, because the class is hidden there. Prompt errors: cancel, negative button and system cancel are `user_cancelled`; no hardware, nothing enrolled, no device credential and lockout are `not_available`; others `internal`. A step-up signature without prompt texts is `internal`. | Brief note 4; the emulator at API 36 showed the `KeyStoreException` path, not `UserNotAuthenticatedException`. |
| D-M5-01-5 | 2026-10-15 | `apps_platform.py` knows the system `android`, which is no host: its commands run on any host when `adb devices` lists exactly one device in state `device`, print `SKIP ... android: no device` without one (or without `adb`) and fail with two or more; `--system android` runs only them. The CI job `apps-android` (public phase, `ubuntu-24.04`, kvm enabled, Temurin 17, `reactivecircus/android-emulator-runner` pinned by SHA, API 26 and 36, `x86_64`, `google_apis`) runs `apps_platform.py --system android` and feeds `ci-ok` like `apps-macos`. `make test` runs `./gradlew -p <module> testDebugUnitTest` for every Gradle module with a tracked `src/test/` under `packages/*/android/`; the jobs `gates` and `sonar` install Temurin 17 and the Android SDK (`android-actions/setup-android`) when such a wrapper is tracked. The run script sets a temporary PIN on an emulator without one (and clears it at the end), because the step-up key needs a secure lock screen; it never touches a physical device's lock screen. | Brief note 5 and its requirement that the JVM tests run in `make test`; an emulator can run on Linux and macOS, so a host check alone cannot select it. |
| D-M5-01-6 | 2026-10-15 | The Kotlin core is the Gradle library module `android/devicekeycore` with its own build file and tests. The plugin library compiles the module's main sources into itself (`sourceSets`), and its standalone `settings.gradle.kts` includes the module for the tests. An app (the push service of M5-05, the share activity of M5-06) uses `DeviceKeyCore.forContext` through its dependency on the plugin project `:device_key` and does not include `devicekeycore` as a second project, which would duplicate the classes. Both build files list the same dependencies (`androidx.biometric` 1.1.0); the plugin adds `kotlinx-coroutines-android` for Pigeon's `suspend` handler. | Flutter includes a plugin as one Gradle project and ignores its settings file, so a project dependency on the module would break every app build that does not include it by hand. |
