# AUD-client-search-01 Search view: file hits that open, reasons of a failed search, one request, agent and tag filters

| No | Date | Ruling | Reason |
|---|---|---|---|
| AUD-CS1/1 | 2026-11-12 | `SearchHit` of `docs/api/openapi.yaml` gets two optional members for hits of `kind = file`: `thread_id` and `message_id`, the message the file is attached to and its thread. The handler of `search` sets them from the hit of `files.SearchFiles`, which the coordinator already carried (`search.ResultHit.ThreadID` and `MessageID`); a message hit and a thread hit do not carry them, their object names the place. The apps map both to the hit and open `/t/<thread>?m=<message>`, as for a message hit. This replaces the last sentence of D-M4-23-3 ("a server file hit opens the channel of its `scope_channel_id`"): the `File` of a hit is the attached form, which never has `scope_channel_id` (D-M3-07-5), so against the real server a file hit had no target and its tile no action. The apps no longer read `scope_channel_id` of a hit. The fake server of `sync_engine` answers a file hit as the server does (the attached form without `scope_channel_id`, `thread_id`, `message_id`). The change is additive: an app against a server without the members shows the file hit without an action, as before. | Audit finding fn-search-1: a document found by its name or its extracted text could neither be opened nor traced to its message. The tests were green because the fake server and the fixture sent `scope_channel_id`. Proof on the real path: `TestSearch_FileHitNamesItsThreadAndMessage` (`services/server/test/attachments`, the server of `internal/wire` over HTTP, also after `moveThread`) failed before the change with a file hit that named neither thread nor message; `test/search/search_port_test.dart` in the app sends the body that test server answered through the client of `createApiClient` and the generated decoder to the target of the tile, and fails with the mapping the app had before (`scope_channel_id`, no target). The widget test "selecting a file hit opens the message it is attached to" shows that the tile acts on such a hit. The desktop E2E suite (`make e2e-desktop`) gets the flow "search finds a file and opens the message it is attached to"; that suite runs in no CI job, and the flow is no part of the proof named here. |
| AUD-CS1/2 | 2026-11-12 | The search port tells two more failures apart: `503 unavailable` with the reason `search_timeout` (`SearchFailureKind.timeout`) and `429 rate_limited` with the wait of `Retry-After` (`SearchFailureKind.rateLimited`). The view shows "The search took too long. Narrow it, ..." for the first and "Too many searches in a short time. Search again in n seconds." for the second (without a named wait: "Wait a moment, then search again"), each above the local hits, which stay with their note: the server said nothing about the query. The same holds for a further page ("Load more") and for the search in the thread, which share the function `searchErrorText`. The popup of the search assistant maps the same two answers of `assistSearch` and shows the same two texts. Every other failure keeps "The search did not work. Try again." and replaces the hits as before. | Audit finding fn-search-11; 14 7 and the row `unavailable` of 06 5 ask for the hint to narrow a search that timed out instead of repeating it. "Try again" on the same request led into a loop, and the local hits disappeared although nothing was wrong with them. |
| AUD-CS1/3 | 2026-11-12 | The request of the search (`search`, first page and further pages) goes out once: it carries `noReadRetryExtra`, so the read retry of the session (the backoff of the outbox from `client.outbox_retry_base` to `client.outbox_retry_cap`, D-M4-02-5) stays out of it. A connection error therefore shows the local hits as offline hits at once, and the search runs again when the connection is live again (D-M4-23-1) or when the person searches again. Every submit cancels the request of the submit before it (`SearchCancel`, a Dio cancel token in the API port), and so does closing the view. While the first page is pending the view shows the line "Searching" (text, no animation, as the popup of the assistant does), also in the search in the thread. Limit: only the search changes. `listMyMentions`, the template lists, the revisions of a message and the preview of the delete dialog keep the retry of the session; they live in other parts of the app, each with its own states, and a rule for every interactive read changes how every view recovers from a failed read, which is a ticket of its own. `searchThreadTitles` of the quick switcher keeps it too: it shows the local rows at once and merges the server titles when they come. | Audit finding client-chat-9: with nine attempts over minutes a refused or failed search showed an empty area without a sign of progress, a query the server had timed out was sent again and again (06 5: narrow it instead of repeating it), the note for offline came only after the last attempt, and the request of an older submit ran on behind the newer one. The person is in front of the view and has the button; a hidden retry helps a background read, not this one. No new configuration key: the app defines no number of its own (D-M4-02-5). |
| AUD-CS1/4 | 2026-11-12 | The filter column of D7 offers the two filters of 14 4.4 it lacked: "Agent" (`agent_id`, the stored agents, every type) and "Tag" (`tag_id`, the tags of the forum chosen under "Channel", for threads and messages; without a chosen forum and for the type files the menu is disabled, and a tag goes with its channel). The offline search applies both to the stored thread as the server does (the thread's own operator; at least one of the tags). The type stays a single choice (D-M4-23-2: the API takes one `type`), and the count line stays the number of loaded hits (14 4.3: no totals). The picture and the text of 01 D7 now show the column as built (one type, the tag and agent filters, the sort and "With files only"). | Audit finding fn-search-10: brief M4-23 requirement 11 asks for the filters of 14 4.4 as parameters, and the server checks and tests both; the app could send neither. Asking every type in turn and grouping the hits would be a new result view with three cursors and three rate-limited requests per search; the picture followed the decision instead. |
