# FIX-client-db-key The database key of an existing database is never replaced

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-DBK/1 | 2026-11-21 | `SecureDatabaseKeySource` creates a database key only while the database file of the instance (`<dataRoot>/instances/<instance_id>/local.db`, passed as `database`) does not exist. When the secret store has no key but the file exists, it stores nothing and throws `LocalStoreKeyError` with the reason `keyMissing`; `InstanceServices.open` treats that like a key that does not open the file (AUD-CO1/4): without a session the folder is created anew, with one E1 shows `ServerStatus.localDataUnreadable` and the person decides about the reset. A read the secret store refuses is thrown unchanged and is never read as "not found": a `PlatformException` of the keychain (for example `errSecInteractionNotAllowed` (-25308) of the iOS keychain of a locked device) shows `ServerStatus.keychainUnavailable`, a timeout of the store `ServerStatus.openFailed`, and in both cases "Connect" tries again. This holds on every platform, because the source is shared Dart code. | On 2026-11-21 the iPhone app of the owner showed "The app cannot read its local data" for a signed-in instance. The key source created and stored a new key whenever the read returned nothing, so any "not found" for an existing file (a keychain item not found at that moment, an Android store that deleted an item it could not decrypt) replaced the key of the file for good, and the file could never be opened again. A new key never opens an existing file, so creating one then has no use. The device trigger of that start was not read from the device (no device access in this ticket; a release build keeps no developer log), so which of the paths below hit the owner's phone is [unverified]. |
| FIX-DBK/2 | 2026-11-21 | `openLocalStore` classifies the SQLite error of the open and of the key check by its primary result code (`openErrorOf`): `SQLITE_NOTADB` (26) and `SQLITE_CORRUPT` (11), the answers to a key that does not decrypt the file, are `LocalStoreKeyError` (`wrongKey`); every other code (`SQLITE_PERM` 3, `BUSY` 5, `LOCKED` 6, `IOERR` 10, `CANTOPEN` 14, `AUTH` 23, an unknown code) is the new `LocalStoreUnavailableError`, which E1 shows as `ServerStatus.openFailed` ("Try again"), which "Connect" retries, and for which nothing is ever deleted. | Before, every SQLite error of the key check was a `LocalStoreKeyError`. AUD-CO1/4 named that the error also covered a file the device cannot read at that moment (the iOS file protection `NSFileProtectionComplete` of a locked device): with a stored session that showed "Reset local data", without one `InstanceServices.open` deleted the folder of the instance by itself. A probe on 2026-11-21 with the `-wal` and `-shm` files of a stored database made unreadable showed it: the file opens, the key check fails with `SQLITE_CANTOPEN`, and the code before this ticket reported `LocalStoreKeyError`; the same setup stands in for the file protection in the tests (`packages/local_store/test/encryption_test.dart`, `apps/client/test/onboarding/local_data_test.dart`). An unknown code counts as transient, because the cost of a wrong guess there is a retry, not lost data. |
| FIX-DBK/3 | 2026-11-21 | The protection classes stay as 15 6.3 and 9 and D-M5-08-6 set them: on iOS the database key `WhenUnlockedThisDeviceOnly`, the database files `NSFileProtectionComplete`, the tokens `AfterFirstUnlockThisDeviceOnly`. The mismatch between the tokens and the database is handled by deferring instead of aligning: a start while the device is locked finds the session but cannot read the key or the file, and that start now ends on E1 with `keychainUnavailable` or `openFailed` and opens the database at the next "Connect" after the unlock, instead of creating a key or offering the reset. | Aligning the classes (the key `AfterFirstUnlockThisDeviceOnly`, the files `CompleteUntilFirstUserAuthentication`) would weaken R-CL-08 ("a lost device reveals nothing"; the key is the residual protection of a lost device, 15 9) for a case the app does not need: the iOS app has no background mode, so its Dart code runs with a locked device only in the moments around a lock, and the extensions do not use the database. Migrating the existing key item to another class would also need a delete and add in the keychain, during which a crash loses the key. |
| FIX-DBK/4 | 2026-11-21 | Each path logs a fixed reason code without the key: `db_key.created`, `db_key.missing_with_database`, `db_key.read_failed: <type> <status>` (log name `database_key`), `local_db.key_error: wrong_key` or `key_missing` with what follows (log name `bootstrap`); `LocalStoreUnavailableError` names its SQLite code (for example `sqlite 14 (cantopen)`) in the open failure the onboarding logs. | Today's failure could not be traced because the release build logged no cause. The log stays the developer log; a release build still does not keep it, which this ticket does not change. |
| FIX-DBK/5 | 2026-11-21 | Android keeps the store option `resetOnError: true` of `flutter_secure_storage`. | With it the store deletes an item it cannot decrypt and answers "not found"; before this ticket the key source then created a new key for the existing file, the same dead end as on iOS. FIX-DBK/1 ends that: the read now leads to `localDataUnreadable` with the reset the person chooses (the old key is gone in that case, so the file can never be read again), never to a silent new key. Turning the option off would keep an item the store can never decrypt again and make every start fail on it with no way out on the device. Limits of the plugin (flutter_secure_storage 11.2.0, read from its source, not reproduced on a device): it deletes the item on every exception of a read, not only a failed decryption, so a passing Keystore failure also costs the key and leads to `localDataUnreadable`; and after an error it throws synchronously it deletes every item and answers the text "Data has been reset" as the value, which the key source fails to decode (`FormatException`, no reason code of its own) and which leaves no session. In neither case is a new key written for an existing file. |
| FIX-DBK/6 | 2026-11-21 | Not covered, kept for the next change in this area: the test of an unreadable database with a session checks that nothing is deleted but not that "Connect" opens it after the file is readable again; and the check "no key and no file" of the key source is not atomic, so two opens of one instance at its first start could write two keys. | Minors of the review of this ticket. No path to the second one is known: `_openServices` closes the services before it opens new ones. |
