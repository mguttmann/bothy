| D-M2-27-2 | 2026-10-20 | The token check is the chain stage `httpserver.StageWebhookToken`, directly after `StageRateLimit` and before `StageMaintenance` and the body stages, so it runs after `rl.webhook_in` and before any body is read or validated; it acts only on operations with action `webhook_in.post`, and every failure (malformed token, unknown ID, wrong hash, revoked webhook, installation not `active`) gives the same `404 not_found`; 02 9.1 gets the step. | D-M2-27-3 | 2026-10-20 | The actor of a verified post (`apps/app.WebhookActor`) is the app principal (`ID` = `incoming_webhooks.app_id`, `Kind` app) with the `InstallationID` of its active installation, `GrantedScopes` = the installation's granted scopes intersected with `messages:write`, and no `TokenID`, `SessionID` or `DeviceID`. | A stolen URL may only post into its channel (T-TK-03); `message.create` and `thread.create` need exactly `messages:write` (05 2.6). |
| D-M2-27-4 | 2026-10-20 | The requirement of `webhook_in.post` is `All(AppKind, AtLeast(LevelWrite))` on the channel of the webhook, without scope, and no longer deferred; an anonymous principal gets `unauthenticated`. The use case authorizes `webhook_in.post` on every post, replays included, and the messaging use case then authorizes `message.create` (and `thread.create`) for the same actor; every outcome other than `allow` (`not_found`, `forbidden` with any reason, `unauthenticated`, `step_up_required`) becomes the `404 not_found` of an unknown webhook, internal errors stay `500 internal_error`. Place: `authz/domain/requirements_table.go`, `apps/app/incoming.go` (`asNotFound`). | 07 4.2 allows anonymous only for the right `public`, and this right is "public with token; the app needs write"; 11 8.4 sends the branch "authorize app: message.create on the channel" with "no" to `404`, so a denial reveals nothing. |
| D-M2-27-5 | 2026-10-20 | The format is decided per request from the body (`incoming.Classify`), not stored per webhook; the request body is one closed schema `IncomingWebhookPost` with the native members (`content_md`, `title`, `thread_id`, `client_msg_id`) and the Alertmanager members (`version`, `groupKey`, `truncatedAlerts`, `status`, `receiver`, `groupLabels`, `commonLabels`, `commonAnnotations`, `externalURL`, `alerts`) and no `required` list, plus the schema `AlertmanagerAlert`. A body with an Alertmanager member is `alertmanager` and must hold no native member, else `400 validation_failed` with the pointer of the first native member and `format_mixed`; every other body is `native`; a format not in `webhook_in.formats_enabled` gives `400 validation_failed` with an empty pointer and `format_disabled`. | 03 `incoming_webhooks` has no format column (core contract), openapi has no format member, and `rule/oneof-needs-discriminator` forbids a `oneOf` without discriminator while the Alertmanager payload has none. |
| D-M2-27-6 | 2026-10-20 | A fixed thread is used only while it belongs to the webhook's channel (then `thread_id` and `title` of the body are ignored); when it was moved to another channel, the post gives `404 not_found`. Place: `apps/domain/incoming/target.go` (`ChooseTarget`). | A webhook writes only into its own channel (11 8.1 "for a channel", T-TK-03). |
| D-M2-27-7 | 2026-10-20 | A native post with `title` into a text channel writes the message into the main thread (`chat.TriggerChannel.MainThreadID`) and starts a new thread from it (`parent_message_id` = the message), like `auto_thread` of 09 3.7; the answer names the new thread in `thread_id`, and a replay answers the thread of the first answer (`chat.ThreadsByParent`) and creates none. In a forum a title creates a forum post with the message as first message. | In a text channel a thread grows from a message (01 4, M1-55 D1 requires the parent), and 11 8.2 says one message per call. |
| D-M2-27-8 | 2026-10-20 | The request hash of a native post uses `messaging.CreateMessageCmd.HashContext` = `"webhook:" + webhook_id + "\|thread:" + <thread_id of the body or empty> + "\|title:" + <title or empty>` (`incoming.HashContext`); the message is written with `SkipMentions`. A replay (same author, `client_msg_id` and hash) answers `200` with `Idempotent-Replay: true` and publishes nothing. | The hash covers the request as sent (04 5.1 point 3), and a `client_msg_id` repeated through another webhook of the same app gives `422 idempotency_key_reuse` instead of a replay of another webhook's message. |
| D-M2-27-9 | 2026-10-20 | After the commit `TouchIncomingLastUsed` sets `last_used_at` only when it is empty or older than `identity.last_active_granularity`, outside the unit of work; a failure is logged without the token and never fails the request. | The same rule as `api_tokens.last_used_at` (03); concurrent posts never upgrade their share lock. |
| D-M2-27-10 | 2026-10-20 | `incoming.RenderAlertmanager` writes a fixed layout, held by golden tests (`apps/domain/incoming/testdata`): a header `**FIRING**` or `**RESOLVED**` with the title (`commonLabels.alertname`, else `groupLabels.alertname`, else `Alerts`) and the alert count; one list item per alert with status, alert name, severity when labelled and summary (annotation `summary`, else `description`, else the other labels as sorted `name=value`, else `no summary`), with `Runbook:` and `Source:` lines; a last item `- and <k> more alerts` for `truncatedAlerts` and dropped items; the footer `Alertmanager:` with `externalURL`. Payload values have control characters replaced by a space and every ASCII punctuation character escaped; a URL is written only as an autolink of an absolute `http` or `https` URL with a host made only of printable ASCII without `<` and `>` (a character such as U+FEFF would end the autolink in a client and let the rest render as Markdown), else its line is left out; above `message.max_content_bytes` items are dropped from the end, then the footer, then the text is cut at a UTF-8 boundary with `...`. | 11 8.2 lists the contents, not the layout, and `docs/observability/alerting.md` 2 adds severity and runbook link; the escaping keeps a label from adding formatting, links or images (SEC-OUT-1), and the server never fetches these URLs (SEC-OUT-2). |
| D-M2-27-11 | 2026-10-20 | `createIncomingWebhook` answers `400 validation_failed` with `/app_id` and `app_not_installed` when the app has no active installation, with `/app_id` and `app_cannot_write` when the webhook actor of the app may not `message.create` in the channel (checked in filter mode, no audit), and with `/thread_id` and `not_in_channel` when `thread_id` is unknown or a thread of another channel. | 11 8.1: the webhook always writes as an app with `write` on the channel, and a manager sees the same through "Who has access?"; an unknown thread and a foreign one give the same answer. |
