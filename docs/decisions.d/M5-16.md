# M5-16 Several photos from the library at once on the phone

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-M5-16-1 | 2026-10-29 | `MediaPickerPort` has two calls instead of `pick(source)`: `camera()` returns one photo or null, `library(limit:)` returns the picked photos in the picker's order (empty for a cancel). `ImagePickerPort.library` calls `ImagePicker.pickMultiImage` with `photoJpegQuality`, no full metadata and the limit, so iOS uses `PHPickerViewController` with a selection limit and Android the photo picker with `EXTRA_PICK_IMAGES_MAX`; `image_picker` opens the single picker itself for a limit of 1. `PhotoPicked` carries a list of files and `attachPhoto` passes them to `AttachController.add` in one call. | Two calls state the two shapes (one photo, a list) in the types, so no caller can ask the camera for a list. One `add` call gives the all-or-nothing count and size checks of D-M4-22 for the whole pick, as a desktop multi-select has. |
| D-M5-16-2 | 2026-10-29 | All or nothing: `MediaPicker` converts the photos in picker order into the scratch folder (file name `<stamp>-<index>-<name>.jpg`, so two photos named alike stay apart); one photo it cannot decode refuses the set with `PhotoUnsupported` naming it, one it cannot read or write fails the set with `PhotoFailed`; then the JPEGs already written are deleted. The picker's own files are deleted in every case (D-M5-07-5). | Matches the rule of `AttachController.add` (refuse the whole set with the reason naming the file), so a pick never sends a partial set the person did not choose. |
| D-M5-16-3 | 2026-10-29 | The limit is the free slots: `AttachController.freeSlots` is `message_max_attachments` minus the attachments of the composer, null while the instance limits are unknown (no limit is passed then; the server checks). With no free slot `AttachController.hasRoom` sets the existing `TooManyFiles` refusal without writing anything and `attachPhoto` returns `PhotoNoRoom` without opening the camera or the picker. A platform that ignores the limit is caught by `AttachController.add`, which refuses the set and deletes the photos. | The ticket asked for the refusal at the library entry; the camera follows the same rule because a photo taken then would be refused anyway. |
| D-M5-16-4 | 2026-10-29 | The attachment chips of the composer scroll within a quarter of the screen height (`ConstrainedBox` and `SingleChildScrollView` around the `Wrap`), on the phone and the desktop alike. | The widget test with ten photos showed the phone composer overflowing by 49 pixels on a 390 by 844 screen: ten chips with previews no longer fit beside the field. Before M5-16 ten attachments on the phone needed ten openings, now one pick reaches the limit. |
| D-M5-16-5 | 2026-10-29 | The device test of three photos (`integration_test/phone/voice_test.dart`, run by `phone_suite_test.dart` on the iOS simulator and the Android emulator in the CI) uses the fake picker port, like the single photo test of M5-07; no test drives the real system picker. The ticket text asked for a `patrol` run that selects three photos in the system picker; `patrol` is not a dependency of the app (D-M5-07-0), and no GUI test runs on a maintainer's own machine. | The fake port proves everything from the picked files to the stored message on a real simulator and emulator; the call of `pickMultiImage` with its limit stays unproven on a device. |
