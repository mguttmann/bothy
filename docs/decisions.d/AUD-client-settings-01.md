| AUD-CST1/5 | 2026-11-12 | A write of a personal setting that the instance refuses for good (`putMySetting` or `deleteMySetting` ending as failed in the outbox, 04 13.2 item 5) shows in the settings, above every section on the desktop and on the phone: one notice per refused write with the label of the setting (its key for a setting without a row in D8), the translated reason, "Send again" and "Discard". Until the person decides, the local row keeps what the person chose, as a failed message keeps its text. "Send again" first puts the local row of the key to what the entry sends, as a new choice of the person does (the value of the entry one version above the stored row, or no row for a refused reset), and then replaces the entry with a new one under a new ID; an entry that is gone or no longer failed changes nothing. "Discard" first reads `listMySettings`, then puts the local row of the key back to the stored value and version, or removes the row when the instance stores none, so the default applies, and removes the entry last; without an answer nothing changes and the notice says so. While another write of the same key still waits in the outbox, a discard leaves the local row to that write. Limit: only the two operations of the personal settings. The writes of notification levels, quiet hours and the sidebar order are the finding client-phone-background-7 of another work package; one-time actions already watch their own entry (AUD-CA01/4). | Audit finding fn-sync-offline-5, verified at the source: these entries have no thread, only the thread history and single dialogs showed failed entries, and nothing reset the local row, so after a final refusal (an unknown key of a newer app on an older server, a refused value) the device showed a setting the instance never stored, with no way to send it again or to drop it. The settings are the one place every such write belongs to, whichever screen wrote it (the column widths, the notification settings). The stored value is read from the instance because the local row was overwritten by the write; its version would be older than the local one, so the row is removed and written anew in one transaction.
