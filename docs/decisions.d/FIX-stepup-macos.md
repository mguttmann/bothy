# FIX-stepup-macos Step-up with password and TOTP on a device without a step-up key

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-SU/1 | 2026-10-31 | `stepUpWithPassword` is allowed for a console session and for an `app` session whose device is not `cli` and has no active `step_up` key (08 6.2). An `app` session on a device with an active `step_up` key gets `403 forbidden` with reason `step_up_not_possible` and audit cause `step_up_key_present`; a `share_ext` session keeps cause `not_console`; a `cli` device is refused by the existing check (cause `cli_device`). The OIDC re-login stays console-only, because its redirect is the console callback. Only a console session gets a new cookie after the step-up. Supersedes FIX-WK/2 for the step-up of such a device. | Windows has no `step_up` key by design (D-M4-11-2), and 08 6.2 said that native apps always have one, so such a device had no step-up method at all: every step-up action on Windows ended with "The confirmation was cancelled". Password and TOTP are the strength the console already accepts; refusing it for a device with a key keeps the stronger method where it exists (no downgrade). |
| FIX-SU/2 | 2026-10-31 | The terminal rule of 08 6.3 does not change: a fresh step-up still needs `passkey` or `device_key`, so the terminal stays unavailable on Windows. The app's terminal uses the new `StepUpService.confirmFresh`, which throws `StepUpUnavailable` before any request on a device without a step-up key, so Windows never asks for a password that cannot open the terminal. The fake server of `sync_engine` follows the same rule (a `fresh` action refuses a `password_totp` step-up with `terminal_step_up_not_fresh`). | The owner requires a passkey or device key confirmation for remote access (R-ID-16); this fix only opens the administrative step-up. |
| FIX-SU/3 | 2026-10-31 | `StepUpService.confirm` of `packages/auth` runs the password step-up when the device has no step-up key: `createStepUpChallenge`, `StepUpPrompt.askPassword`, then `stepUpWithPassword` with the trimmed code, without `X-Console-Request`. A `401 step_up_required` answer (a wrong password or code, or an expired challenge, counted by the server) asks again with a new challenge and `rejected: true`, until the person cancels or the server revokes the session at `auth.step_up_fail_limit`; `403 forbidden` with reason `step_up_not_possible` (no local account) and `404 not_found` (`auth.local_password_enabled` off) throw `StepUpUnavailable`, a cancel throws `StepUpCancelled`. A device with a step-up key never sees the password variant. | One challenge per attempt, because the server ends a challenge with every answer; the limit lives on the server, so the client needs no counter of its own. |
| FIX-SU/4 | 2026-10-31 | `StepUpPrompt` gets `askPassword(purposeText, {rejected})` returning `StepUpCredentials?` (password and code, null for cancel); the app's `StepUpDialogPrompt` shows `StepUpPasswordDialog`: the purpose, a line that this device has no key for confirmations, the error line after a rejection, an obscured password field with the password autofill hint, a code field for six digits with the one-time code hint, Cancel and Confirm (disabled until a password and six digits are typed). Every test fake of `StepUpPrompt` implements it. | The interface is the port the brief names; an optional second interface would let a new prompt forget the password variant and fail on Windows again without a compile error. |
| FIX-SU/5 | 2026-10-31 | The fake server of `sync_engine` follows the server: a challenge no longer needs a step-up key, a step-up action without a step-up answers `401 step_up_required` instead of `403 forbidden` with reason `step_up_not_possible` for a device without a key, and `stepUpWithPassword` confirms an app session on such a device. | The fake answered `403 forbidden` where the server answers `401`, so no client test could reproduce the live failure on Windows. |
