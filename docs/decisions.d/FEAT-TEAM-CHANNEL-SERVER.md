# FEAT-TEAM-CHANNEL-SERVER Server slice of the team channels

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-TEAM-1 | 2026-11-21 | The owner's answers to the four open questions of the design ([cross-project-handoff.md](../design/cross-project-handoff.md) 9) are decisions: an owner message reaches every member, idle ones as a new run; mentions in it mark the addressed members and never narrow the recipients; the brake defaults are high named keys held by a test (`team.turn_budget` `200`, `team.pingpong_max` `40`, `internal/wire/config_test.go`); one work thread per member and team channel. | Owner answers of 2026-11-21; cost is no concern, finishing projects is. |
| D-TEAM-2 | 2026-11-21 | What a member must see is copied into its work thread as a message (an input, `team_inputs`) instead of running the member inside the team channel or pointing the run at the team channel's message. | The run context (09 4.6) only reads a triggering message in the run's thread, the follow-ups (09 7) are messages of the run's thread, and the runner reads its inputs there; a copy keeps all three and every adapter unchanged. |
| D-TEAM-3 | 2026-11-21 | An owner's message is copied as that owner's message (`origin = human`); a member's reply is copied as a message of the source member's agent (`origin = agent`). The authority (sponsor or writing owner) is stored in `team_inputs.authority_id`, is the run's `triggered_by` and the check principal of every check, and is never written into the message. | The runner attaches owner codes only to a message of origin `human` by an owner (09 18.5); a member's text therefore can never become the owner's word, even for a runner that does not know team channels yet (fail closed). The design's idea to take the owner code from `triggered_by` is dropped for this reason. |
| D-TEAM-4 | 2026-11-21 | The copying runs in the job `runs.team_input`, scheduled by the acceptance in the unit of work of the message, never inside that unit. | The reply's unit holds its thread row and a share lock on its run; copying into the team channel and other work threads there would take their locks in the opposite order of an owner's broadcast and could deadlock. The job is idempotent through `team_mirrors` and the unique key of `team_inputs`. |
| D-TEAM-5 | 2026-11-21 | The run of a member input has `trigger_kind = 'team'` and its token the claim `trigger_kind = team` with `message_id`; follow-ups stay `agent.followup`. Every delivery is checked with `agent.invoke` for the authority (`actor.Recheck`, origin human, the agent counted as addressed) like a wake run; the resolver of `agent.followup` and the follow-on run of 09 7 read the authority of an input from `team_inputs`. | The brief asks for the new trigger kind; an adapter that does not know it refuses the run, which is the safe failure until the runner and adapter slices land. A follow-up of an agent's message would otherwise be checked for the agent and refused by SR4. |
| D-TEAM-6 | 2026-11-21 | `messaging.SetTriggerState` is a no-op for a message of origin `agent` instead of an internal error. | The follow-up path sets trigger states on every follow-up message; an input of origin `agent` cannot carry one (03 `messages` check), and one central rule is safer than special cases in every follow-up step. A message of origin `app`, `import` or `system` stays an internal error. |
| D-TEAM-7 | 2026-11-21 | Readers rule of the first slice: every person `authz.Recipients.Readers` names for the team channel and for each home channel must be an active owner; checked at `enableChannelTeam`, `addTeamMember` and before every copy in either direction (reason `team_readers_not_owners`). An earlier version compared the two reader sets for equality; the red team showed that a person with a grant on both channels could then steer a member's agent into mentioning another member, whose run acted for the sponsor. | Design 5 and the owner's first slice: only owners read team channels and the home channels of their members. `Readers` is a superset without guards, so the rule errs on the side of refusing; rechecking every copy covers grants added later. |
| D-TEAM-11 | 2026-11-21 | A member's reply is mirrored and handed on only when the run it answers was started and fed only by active owners (`runs.triggered_by`, the authority of a team input, the person of every follow-up of the run and the principal of every interaction with the run's components; the interactions were added after the red team's round 3), checked in the job (since red team round 4 against the record of D-TEAM-12, not against the input rows); the acceptance passes the run of the reply (`run_id` of the answer, never stored on the message) as an argument of `runs.team_input`. The readers rule alone left a gap the red team reproduced in round 2: a person whose grant was revoked after starting a member's run could still steer its reply into triggering another member for the sponsor. | One check on the provenance of the run closes the whole class (grant revoked, person disabled, follow-ups by non-owners) at the one place where agent text becomes another member's trigger. Not covered: context a non-owner left in the member's session in an earlier run of the work thread; the readers rule keeps non-owners out of work threads, and an owner who revokes a grant can reset the session (`/new`). |
| D-TEAM-12 | 2026-11-21 | Who fed a run is recorded when an input is stored or given to the run, in the append-only table `run_feeders` (R-DM-63), and the check of D-TEAM-11 reads only that record: database triggers on `runs`, `run_followups` (insert and move to the follow-on run) and `interactions` record the stored inputs, `runs.Delivery.Prepare` records the person of every allowed delivery into a run (`domain.FeedSourceOf` for every invocation-bearing event type, so also a control command and a wake input), and the run context records the writers of the messages it gives the run. `bothy_app` may only read and insert the table; a run without its trigger row (older than the record) and a recorded input that speaks for no person fail. Tests: the round 2 to 4 reproductions, a test per source of `run_feeders` that fails for a source without a case, a test that every invocation-bearing event type has a source, and a schema test that every column referencing `runs` is classified as an input with its trigger or as no input. | The red team reproduced the same class three times, each time through a row the check derived the persons from: a revoked grant (round 2), an interaction (round 3), an interaction whose card was deleted (round 4). Recording at the moment of the input and never deriving from deletable rows closes the class at one place; the triggers make it impossible to store an input without recording it. Not covered, as in D-TEAM-11: what the agent reads on its own through the API during a run (a message of a person with a grant that is no input of the run), messages of other agents in the context, and what an earlier run left in the work thread or the session; the readers rule keeps non-owners out of work threads, and an owner who revokes a grant can reset the session (`/new`). |
| D-TEAM-8 | 2026-11-21 | The brake counts member inputs that were delivered; a refused input (sponsor, readers, `agent.invoke`) does not count. A pause posts one note when it starts; later refusals while paused are audited only. Ping-pong pauses the whole channel, not only the pair. | A refused input started nothing that could loop; one note per pause keeps the team channel readable; a paused pair could pull a third member into the loop. |
| D-TEAM-9 | 2026-11-21 | A home channel must be operated by the member's agent (its effective operator) and must not be a team channel; the work thread is a forum post in a forum, else a thread on a system note of the home channel's main thread. | The work thread then has the agent as its operator, so runs resume the member's session (09 9) and 3.4 keeps working for a person who writes there; a team channel as home channel would mirror into itself. |
| D-TEAM-10 | 2026-11-21 | Not in this slice: talk rules (`team_talk_rules`), a sync event for team changes and the `Channel` member that marks a team channel, push notifications for brake notes, attachments in copies, `bothy-team say` mid-run, the client side of `/team`. | The brief limits the slice to the server items 1 to 6 of the design; the app slice adds the sync side when it builds the header. The tables `team_inputs` and `team_mirrors` hold only IDs and are not listed as content tables of `tools/lint/sql_visibility.yaml`; their reads name one message, member or thread that the job or a delivery check reads without a principal. |
