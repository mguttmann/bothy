| M1-38/4 | 2026-10-14 | Pairing codes: 8 Crockford characters from one `crypto/rand` byte each (low five bits); the insert uses `ON CONFLICT (pairing_code_hash) WHERE status = 'requested' DO NOTHING`, and a collision draws a new code, at most 5 times (`pairingCodeAttempts`), then `500`. | 40 bits against few open pairings make a collision rare; several in a row mean a broken random source, which must not loop. | M1-38/5 | 2026-10-14 | `completePairing` with a proof of another key rejects a `requested` pairing (committed, then `401 invalid_dpop_proof`); an `approved` pairing answers the same `401` and stays approved. | The state machine of the brief has no `approved -> rejected`; the device exists for the approving person, only its own key can collect it, and the collection window ends it otherwise (`pairing_expired`). |
| M1-38/6 | 2026-10-14 | `approveDevice` and `approvePairing` write in a unit of work declared as the rights change `device.approve` of the device's person (the caller for a pairing), the expiries as `device.expire`; like `addOwner`, a first read and `authorize` run before that unit, and the unit locks and checks the row again. An unknown pairing code ends the step-up and writes its deny entry in a committed unit without rights change. | 05 marks both actions as rights changes; the rights hook must lock `permission_version` before any domain row, and a refused or unknown request must not raise the rights version. The deny entry belongs to the committed effect (the ended step-up), so it is recorded in the unit, not aggregated after a rollback. |
| M1-38/7 | 2026-10-14 | An expiry found on access (an expired pending device at `approveDevice`, an expired pairing at `completePairing`) is written in its own unit of work with the anonymous principal, so it is audited and evented like the job: the system action `device.expire` without actor, `revoked_by` NULL. The request still answers `409 invalid_state_transition` or `410 gone`. | The brief applies the expiry "lazily on access and by the cleanup job" and audits it as a system action with actor NULL; the caller did not decide the revocation. |
| M1-38/8 | 2026-10-14 | `devices.created_at` (and `approved_at` of an active device) takes the clock of the login or pairing request; `Devices.Register` keeps the database time. | M1-38/9 | 2026-10-14 | Cleanup job case: `identity.auth_cleanup` existed (M1-35); `AuthCleanup.Run` now also calls `ExpirePendingDevices` and `ExpirePairings` of the login service, each device or pairing in its own unit of work, read in batches of 200.
