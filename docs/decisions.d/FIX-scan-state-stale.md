# FIX-scan-state-stale Honest file states, small pasted screenshots, files of follow-ups

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-SSS/1 | 2026-10-31 | Cause of the live report (pasted screenshots stay "being checked" in the composer and in the waiting message although the server has them `clean`): the chips of the composer and of a message waiting in the outbox derived "being checked" from the absence of the upload entry and never read the file. Once the upload was confirmed the entry left the outbox, and the chip said "being checked" for as long as it existed, whatever `file.updated` reported. Fix: a chip of a confirmed upload shows the stored file (`fileMetaProvider` of the file ID from `UploadProgress` or the message's slot), which `file.updated` keeps current. Place: `apps/client/lib/composer/attachment_chips.dart`, `apps/client/lib/thread/outbox_rows.dart`. | The sync engine applies the real event: `packages/sync_engine/test/catch_up/scan_event_test.dart` feeds the envelopes the server's scan pass writes (unattached, to the uploader; attached, to the thread) from a golden file that `TestScanEventGolden` of the server compares with its own output, so a change of the shape fails on both sides. |
| FIX-SSS/2 | 2026-10-31 | "Being checked" only while `scan_status` is `pending`. A file whose scan passed and that the server still prepares (`upload_state` `pending`: an image before its cleaned original, MP4 audio before its duration) is "Preparing"; `scan_status` `error` is "Check failed", apart from `infected` ("blocked"); both are shown in the danger style, and only a failed or canceled upload offers "Upload again". | 12 2 named a cleaned image "being checked", which reads as a hanging scan while the server reports `clean`. A failed check is no finding of malware and should not look like one. |
| FIX-SSS/3 | 2026-10-31 | The fake server of `sync_engine` follows the server: a clean image gets one `file.updated` with `pending` after the scan and a second with `complete` and thumbnails, and the event of an attached file carries the thread in its scope. | The fake made an image `complete` in one step, which hid the state between the two events from every app test. |
| FIX-SSS/4 | 2026-10-31 | A bitmap pasted from the clipboard on the desktop (the PNG the app writes itself) goes as a JPEG of `photoJpegQuality` when that is at most `pastedJpegMaxShare` (0.7) of the PNG; the new personal setting `composer.paste_originals` (default `false`, Appearance on the desktop) keeps it. Files the person copied, dropped or picked are never re-encoded; a drop always carries files (`desktop_drop` delivers paths), so it is never changed. JPEG, not WebP: the server stores a still WebP as JPEG anyway (12 7.1) and JPEG is in its inline list. | Eight screenshots of about 7.6 MB each upload, scan and load slowly; a JPEG of a screenshot is a fraction of that, as other chat apps do. A flat image stays a PNG because its JPEG would not be smaller. |
| FIX-SSS/5 | 2026-10-31 | The Claude Code runner writes the attachments of a follow-up: before the write it reads the message again every `runner.poll_interval` until every file is final, a stop or the end of the turn, at most the new key `runner.followup_file_wait` (`2m`), without holding the write lock; the line lists each file as `local file: <path>` (downloaded like a trigger's attachment), `unavailable: file_blocked` or `unavailable: file_not_ready`. A follow-up of attachments only is written. No server change: the server delivers `agent.followup` at once (12 10 rule 1) and holds only invocations; FIX-voice-send changes nothing here. | The runner passed on only the text of a follow-up, and dropped a follow-up of files alone as `followup_no_text`, so a screenshot sent as an addendum never reached the turn. A follow-up that comes too late for the turn stays `queued` and goes into the follow-on run, whose invocation the server holds until its files are final. |
| FIX-SSS/6 | 2026-10-31 | Not verified: the live rows' `upload_state` (only `scan_status` was read). If the images stayed `pending` there, the image job did not finish them, and the apps now say "Preparing" instead of "being checked"; the server's image job is not changed by this ticket. | No access to the live database from this work; the client fix holds for both cases. |
