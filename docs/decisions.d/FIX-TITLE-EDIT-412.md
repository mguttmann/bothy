# FIX-TITLE-EDIT-412 A title edit in an active chat is saved on the first try

| No | Date | Ruling | Reason |
|---|---|---|---|
| FIX-TE412/1 | 2026-11-10 | Cause, read from an instance in operation and reproduced on the real server (`TestSetThreadTitle_AfterAgentActivity`, red before the fix with `412` and `current` carrying the unchanged title): every message raises `threads.version` (`AppendToThread`, 03 section 6.2) and is announced only by `message.created`, which does not carry the thread. The app sends the version of the thread it holds as `If-Match` of `setThreadTitle`, which is the version of the last thread object it received, and the server compared it with the stored version for equality. In a chat with a message since that object the first edit was always `412 version_conflict`; "Send again" took the version of `current` and went through. | The report: editing the title of an agent chat failed on the first try with "Not saved: somebody else changed this in the meantime" and succeeded when sent again. The server log of that instance, read by its operator, showed `412` answers of `PUT /threads/{thread_id}/title` from the app between `200` answers of the same route. |
| FIX-TE412/2 | 2026-11-10 | The fix is in the server: `threads.title_version` (migration 00103) holds the value of `version` at the last change of `title` or `title_source`, and the precondition of `setThreadTitle` holds for an `If-Match` from `title_version` up to `version` (`domain.Thread.TitleBasedOn`). A version from before the last title change, a version the thread never had and a malformed header stay `412 version_conflict` with the current thread (`TestSetThreadTitle_StaleTitleStillConflicts`, and the concurrent test of M2-18 unchanged). Every statement that writes `title` writes `title_version` (`SaveThread`, the mirror change of an import, both purge statements); `TestTitleWritesSetTitleVersion` reads the query files and holds that. 03 R-DM-61 and 06 R-API-32 state the rule. | What the precondition protects is the title a person saw when they started the edit. A version from `title_version` on names a thread with the current title, whatever else happened to it; an older one names a replaced title. The client cannot hold the newest version: the stream gives it no thread object for a message, and counting messages on the device would drift with every page it does not hold and would then block real thread events through the version rule of the local store. Reading the thread before each edit (as the agent adapters do) costs a round trip, leaves a window between the read and the write in which the next message brings the `412` back, and moves the comparison of titles into every client. |
| FIX-TE412/3 | 2026-11-10 | Every thread from before the migration gets `title_version = 1` (the column default, no backfill): until its next title change its precondition accepts every version it ever had. | The version of an earlier title change is not stored anywhere, so an exact backfill is not possible. The other possible value, the current `version`, would keep the fault for every existing chat until a thread event reaches each client: the first edit of each would fail once more. With 1 the only edit that passes wrongly is one a client queued before a title change of another person that happened before the upgrade and sends after it. Rules M3 and M7 of upgrade.md ask for a constant default and no backfill inside a migration. |
| FIX-TE412/4 | 2026-11-10 | No app change: `setThreadTitle` keeps sending the version of the thread the edit started from, and a failed edit is still sent again with the version of `current`. The fake server of `sync_engine` follows the server: every message raises the version of its thread (it did not, which is why no app test met the fault), and `setTitle` applies the rule of FIX-TE412/2. `title_edit_live_test.dart` runs the app against it: one request, `200`; a title another person replaced while the dialog was open: `412`, then `200` after "Send again". | The app already sends the right witness of what the person saw. The gap between the fake and the server on the thread version hid the fault from every test of the app, so it is closed where it was. |
| FIX-TE412/5 | 2026-11-10 | The other writes of the app with `If-Match` do not share the cause and are unchanged. `markThreadUnread` names the version of the person's read state, which only `putReadState` and `markThreadUnread` of that person raise (the two statements of `read_states.sql`); each answer and each `read_state.updated` carries the new version, and the executor reads the stored one when it sends. `TestMarkThreadUnread_AfterAgentActivity` shows that messages of the agent leave it alone and the write succeeds with the held version. `updateMessage` names the message version, and each statement that raises it (edit, deletion, trigger state, components) is followed by `message.updated` or `message.deleted` with the message. The app never sends `If-Match` with `setThreadTags`, whose optional precondition keeps the exact match (06 section 8 item 3). | Core goal 3 of the brief: check the class, fix what shares the cause, state with evidence what does not. Only the thread carries a version that moves without an event. |
| FIX-TE412/6 | 2026-11-10 | `docs/api/openapi.yaml` is unchanged, and so are the generated clients and the FakeServer of the Python SDK. | The wire format does not change, and the description of the header ("ETag of the version the change is based on. Mismatch gives 412") holds for the title rule as it stands; 06 section 8 item 2 states the rule. The agent adapters read the thread right before they set a title, so the exact match of the SDK's fake, whose messages do not raise the thread version, never refuses them. |
