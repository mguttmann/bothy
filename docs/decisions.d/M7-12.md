| D-M7-12-0 | 2026-10-26 | Built on `main` after M4-34 and M7-10 landed; the changelog entry and these rulings are fragments. Names that differ from the brief, following the merged code: the client has no `CHANGELOG.md` and no `VERSION` yet, so the change log entry is the root fragment only, and a tag `client/vX.Y.Z` resolves once the component gets both (a follow-up of its first release); `apps/client/Makefile` is new and also holds a `release-build` without output, because `release.yml` calls that target for every component; the release steps are `tools/distribution/appdist.py` (the module next to the folder of the same name would shadow it), `apple.py` and `windows.py`; the template uses `com.example.chat` and `example-chat`, the identity of `branding.example.yaml`, because `tools/ci/tests/test_product_name_places.py` allows the working name only at its listed places; the job `build-windows` calls `windows.py` directly, because Git Bash on the Windows runner has no `make`; the CI trials are the new jobs `desktop trial (macOS)` and `desktop trial (Windows)` (ids `desktop-trial-macos`, `desktop-trial-windows`) in `ci.yml` and `build-verify.yml`. | One PR per ticket on `main`; merged names win (D-W-100). |
| D-M7-12-1 | 2026-10-26 | Test publisher and the limit of `spctl` (Design note 1): macOS gets a self-signed RSA certificate with the code signing usage, made by `cryptography` and imported into a keychain of the run (created, unlocked, put in front of the search list, and removed with the search list restored at the end); codesign uses an identity only when its certificate is trusted for code signing, so the trial trusts it in the admin trust settings with `sudo -n security add-trusted-cert -d -p codeSign` and removes that trust at the end. The app, its nested code and the extension are signed with the hardened runtime and without a timestamp; `codesign --verify --deep --strict` must pass. `spctl --assess` runs and its rejection is recorded in `trial-apple.json`, because Gatekeeper accepts only an Apple-issued Developer ID with notarization; the release job runs it as a required check. Windows gets a self-signed certificate (`New-SelfSignedCertificate`, code signing usage) whose subject is the template's `windows.publisher`, exported as PFX for `signtool` and trusted in `LocalMachine\TrustedPeople` and `LocalMachine\Root` for the run; `signtool verify /pa` must pass; all three stores lose it at the end. | D-W-127; no account and no cost (D-W-125); nothing enters a person's login keychain. |
| D-M7-12-2 | 2026-10-26 | Update mechanisms (Design note 2): macOS uses Sparkle's own updater, `SPUUpdater` of the pinned framework, in `tools/distribution/macos/update_harness.swift` (a user driver without windows modelled on Sparkle's `sparkle-cli`, which the release archive does not ship), compiled with `swiftc` against that framework; it updates the installed bundle, and the trial waits for the new `CFBundleVersion` on disk. Windows uses App Installer's documented package manager call `Add-AppxPackage -AppInstallerFile <url>`: once to install `0.1.0` from `beta.appinstaller`, once more after the file points at `0.1.1`, which updates the installed package. Both serve the files from `127.0.0.1` with a port the system picks. Negative probes: on macOS the default channel offers no beta build and a changed archive is refused; on Windows a changed MSIX is refused; the older build stays in each case. | The brief allows Sparkle's tool or a harness that calls `SPUUpdater`; a probe that must fail shows that a pass means something. |
| D-M7-12-3 | 2026-10-26 | The updater inside the macOS app: `AppUpdater` (in `AppDelegate.swift`, started from `MainFlutterWindow`) loads `Sparkle.framework` at run time and creates `SPUStandardUpdaterController` when the bundle carries the framework and `SUFeedURL`, which only `release-apple` puts in; the project links no Sparkle, so debug, test and CI builds stay as they were. The Developer ID edition keeps the sandbox of `Release.entitlements`; `release-apple` adds Sparkle's installer service (`SUEnableInstallerLauncherService`) and its two Mach lookup exceptions (`<bundle id>-spks`, `-spki`). The installation follows the default channel and the channels of the user default `UpdateChannels`; a settings switch for the beta channel is not part of this ticket. | Chapter 18 8 says the Developer ID edition does not need the sandbox, not that it drops it; keeping it changes nothing for the other builds. |
| D-M7-12-4 | 2026-10-26 | Feed signature and promotion (Design note 3): the app requires a signed appcast (`SURequireSignedFeed`) and checks an archive before it extracts it (`SUVerifyUpdateBeforeExtraction`); the archive's EdDSA signature comes from Sparkle's `sign_update` (key on its standard input), the appcast is signed as a whole in Sparkle's format (the content, then the block `sparkle-signatures` with `edSignature` and `length`) by `appdist.py` with the same key, so promotion (`promote-appcast`: remove `sparkle:channel` of a build, sign again) and merging a release into the published appcast (`appcast-merge`) work on any system. `promote-appinstaller` writes `stable.appinstaller` for the MSIX of `beta.appinstaller`. | 18 5 rule 1; a tool that changes the feed has to sign it again, and Sparkle's own reader accepts the block (the trial proves it). |
| D-M7-12-5 | 2026-10-26 | Schema of `distribution.yaml` (`apps/distribution/distribution.schema.json`, draft 2020-12, no other keys): `schema_version` 1, `publisher.name`, `bundle_id`, `apple.team_id`, `apple.apns_topic`, `apple.sparkle` (`feed_url`, `download_url`, `public_ed_key`, `phased_rollout_interval`), `windows` (`package_name`, `publisher`, `update_url`, `hours_between_update_checks`, optional `timestamp_url`), `android.package_name`, `firebase.project_id`, optional `crash_reports.target`. Update addresses are `https`, or `http://127.0.0.1:<port>/` for the trial. A release refuses every value of the template (`PLACEHOLDERS`) and names the keys. The release build writes `bundle_id` and `android.package_name` into the build branding (`branding_defines.dart` with a derived file, the tree restored afterwards). App versions are `X.Y.Z` without a pre-release; build number `X * 1000000 + Y * 1000 + Z`, MSIX version `X.Y.Z.0`. | R-RL-05: the publisher owns the identity; 18 5 rule 1: no channel in the version. |
| D-M7-12-6 | 2026-10-26 | Signing of the release build on macOS: `flutter build macos` gets `DEVELOPMENT_TEAM` from `apple.team_id` with manual signing to run locally (`FLUTTER_XCODE_*`), so App Group and keychain groups carry the team prefix; `apple.py` then signs every nested code item from the inside out (bundles whole, other Mach-O files alone, symbolic links skipped) with their own entitlements, the extension with its build entitlements plus the team's application identifier, and the app with its build entitlements, Sparkle's exceptions, `aps-environment` production and the application identifier; the provisioning profiles of app and extension come from secrets. The release job checks the signing team and requires notarization, stapling and `spctl`. | D-M5-04-10: a Developer ID profile is a distribution profile; Apple's order for nested code. |
| D-M7-12-7 | 2026-10-26 | Windows signing in the release takes a PFX from the secrets (`signtool sign /fd SHA256 /f`, with `/tr` when `windows.timestamp_url` is set). Certificates of public authorities keep their key in hardware, so an OV certificate or Azure Artifact Signing needs the signing call of that service in `windows.py`; that change follows the owner's choice of the path (OQ-08). The package carries the Visual C++ runtime next to the app instead of a framework dependency, and its logos come from the PNG image of `app_icon.ico`. | No account to test against (D-W-125); a package that installs without a store dependency. |
| D-M7-12-8 | 2026-10-26 | CI: the trials run in their own jobs only when a change touches the release steps or what they package (`DISTRIBUTION_PREFIXES` and `DISTRIBUTION_FILES` in `tools/ci/components.py`), never for a shared input alone and never on `main`; `ci-ok` and `build-verify-ok` accept them as skipped only when the plan left them out. | Each builds the app twice on a macOS or Windows runner; on every merge that would hold a macOS runner for no change of the chain. |
