# M7-07 Deletion journal and restore

| No | Date | Ruling | Reason |
|---|---|---|---|
| D-M7-07-1 | 2026-10-26 | Event sources (design note 1): the worker consumer `privacy.journal` journals `message.deleted` (kind `message`, reason `deleted`, `deleted_at` of the payload) and `user.updated` whose person has the status `deleted` (kind `account`, reason the content mode of the deletion, `deleted_at` the time of the event). The mode is read in the round from the newest deletion request of the person that began (`running`, `completed`, `failed`), locked; without one it is `privacy.account_deletion_content`. Files: deleting a file writes no durable event (05 4.8 `file.delete`, 12 section 12 "No event announces the deletion"), so the consumer has no source for a file entry; the brief's "`file.updated` whose state is deleted" does not exist in the core contract. A file deleted with its message is deleted again with that message (the message deletion takes its attachments), and the own files of an account deleted in the mode `delete` with the account. A file deleted on its own (an unattached upload through `file.delete`, a replaced avatar or logo) has no entry; after a restore such an upload comes back and the cleanup of never attached files removes it after `file.unattached_ttl`. `ApplyJournal` still handles the kind `file` (deletion through `files.JournalFiles`, only an unattached attachment), so an event added to 05 later needs only its mapping in the consumer. Spec gap reported: 05 needs a durable event for a deleted file for 20 4.6 to hold for every file. | The core contract may not be edited by this ticket (fixed requirement 10); the attached and the account files, the cases with personal content, are covered through their message and account, and the uncovered case is bounded by the cleanup of never attached files. |
| D-M7-07-2 | 2026-10-26 | Storage (design note 2): one object per entry, key `deletion-journal/<number>` with the number zero-padded to 19 digits (the digits of the largest `bigint`, so keys sort like numbers), through the new inbound ports `files.JournalObjects` (`Put`, `Get`, `Delete`, only keys with the prefix `files.JournalKeyPrefix`, at most `files.JournalObjectMaxBytes`) and `files.JournalFiles`. The consumer takes the number with `UPDATE deletion_journal_state SET next_number = next_number + 1 RETURNING` inside its round, reads the object with `Get` (the port's `Get` reports a missing object, so no separate `Head` call is needed), writes it with `Put` when missing, accepts an object with the same bytes (a redone round after a crash between storing and commit) and stops with `ErrJournalConflict` on other bytes; the cursor and `next_number` commit together after the object is stored. The object is written inside the transaction of the round: the documented exception to R-AR-07 (02 11.5, the contract of `sync.ConsumerHandler`), because the row lock of the cursor is what keeps one writer of the dense numbers. An entry holds exactly `resource_kind`, `resource_id`, `deleted_at` (UTC), `reason` and `seq`, marshaled the same way every time. | 03 4.12 and R-DM-52 fix that `next_number` moves in the transaction that moves the cursor; the storage port has neither listing nor conditional write. |
| D-M7-07-3 | 2026-10-26 | Keeping the mode (design note 1): the consumer marks the request `progress.journaled = true` in its round (no event, a round appends none). `retention.privacy_job` keeps a finished deletion request whose `progress.last_step` is at least 5 (step 6, which writes `user.updated`, may have run) until it is journaled. | A lagging consumer still finds the content mode; the condition is exact without reading the cursor of another module. |
| D-M7-07-4 | 2026-10-26 | Apply on restore (design note 3): `bothy restore finalize` builds the modules of the server in the internal role `restore` (the start parts from the secrets to the privacy step, without the telemetry, the internal listener, routes, log tail, River work, consumers, measurement and the start lock; a job runtime of the role api only inserts), checks that no `bothy_app` session is connected, then `ApplyJournal` reads the objects from the restored `next_number` up to the first missing number and, in number order, deletes again what the restored database holds: a message through `messaging.JournalMessages` (the path of `retention.content`: no actor, no audit, `message.deleted` without `deleted_by`), a file through `files.JournalFiles`, an account that is not `deleted` through `Service.EraseForJournal` (steps 1 to 6 of 20 4.4 with the recorded mode, no request and no audit entry: the object is the record). Each deletion runs its own units of work, because the account deletion changes rights in several units and a unit takes only one rights change; an error stops the command before the epoch step, and a rerun skips what is deleted already. A person who is the last active owner of the restored database is not deleted (counted as `Refused`; runbook: make another owner, file the deletion again). The unit of the epoch reads `head_seq` after the deletions, so no consumer replays them, and stores the number after the last object found. A relocation applies the journal too (it finds nothing after a relocation without loss). The Compose stack runs the command in the new service `restore` (profile `restore`) with the volumes and the secrets of the worker plus the owner password of `migrate`. | SEC-BAK-3 requires the normal use cases (tombstones, redaction, purges follow) before the instance accepts requests; only the module graph of the server offers them, and the service `migrate` holds neither the object storage nor the secrets of the modules. |
| D-M7-07-5 | 2026-10-26 | Permission version: the unit of the epoch raises `permission_version` once with `RestoreRepository.AdvanceCounter` of instance, after the journal; the result and the audit entry `instance.restore.finalize` name it, with the counts `journal_entries`, `journal_messages`, `journal_files`, `journal_accounts`. | instance owns `sequence_counters`; the rights begin hook of authz raises the version only for a catalogue action that changes rights, and `restore finalize` is no catalogue action (D-M7-04-2). No other session runs, so the lock order of 03 6.3 cannot deadlock. |
| D-M7-07-6 | 2026-10-26 | Period conversion (design note 4, DP-T08): the cross-check `deletion_journal_retention` compares `privacy.deletion_journal_retention` with the longest of `backup.logical.retention`, `backup.objects.retention` and the pgBackRest period, the larger of `backup.pg.retention_full` and `backup.pg.local_retention_full` times the longest interval between two runs of `backup.pg.full_schedule` (`status/domain.Schedule.LongestGap`, read from a fixed start over four years and a day or 2000 runs), rounded up to whole days. A schedule that does not parse is left to the cross-check `backup_schedules`. As a cross-check of the configuration it stops every process that loads it, so `api`, `worker` and `bothy config check` alike. | The longest gap covers schedules with uneven intervals (a monthly full backup); equal values pass, as "at least as long" says. |
| D-M7-07-7 | 2026-10-26 | Manifest reference: `backup_manifest.v1` gets the optional member `deletion_journal.next_number` (at least 1), which `bothy-backupd` writes for every kind from `deletion_journal_state.next_number` in the snapshot of the manifest; `ParseManifest` accepts manifests of earlier runs without it. 03 is unchanged. | backup-restore.md 3 lists the references of a run; a restore of any kind of backup needs its journal position. |
| D-M7-07-8 | 2026-10-26 | Journal retention (requirement 16): `Journal.Retention()` is a participant of the class `privacy_job` registered with the period `privacy.deletion_journal_retention`. From `low_number` it deletes an object whose `deleted_at` lies before the cutoff (a missing object counts as deleted), then moves `low_number`, and stops at a younger object, at `next_number` and at the floor of `status.KeptBackups`: the smallest `deletion_journal.next_number` of the succeeded runs still kept (logical and object runs within their retention, the newest full runs by the larger pgBackRest count with the differential runs after the oldest of them), 1 for a kept run without the member. `Tables()` is empty: it removes objects, not rows. | 03 4.12; a kept backup can be older than the configured periods when backups failed, so the floor comes from the runs themselves. |
| D-M7-07-9 | 2026-10-26 | Differences to the names of the brief (D-W-100): the use case is `instance.Restore.Finalize` with the new port `instanceapp.DeletionJournal` (the brief's `FinalizeRestore` is its input type); the permission version rises through instance, not through a port of authz (D-M7-07-5); `ApplyJournal` is `privacyapp.Journal.ApplyJournal`, adapted by `wire.RestoreJournal`; the object storage port is reached through the new port `files.JournalObjects`, and its `Get` replaces the `Head` of design note 2; the consumer name constant is `sync.ConsumerPrivacyJournal`. | D-M7-07-10 | 2026-10-26 | Lost objects (red team findings): `ApplyJournal` first scans down from the restored `next_number - 1` to the first object that exists or to `low_number` and writes a placeholder `{"lost": true, "written_at": ...}` (`domain.Placeholder`, `ParseObject`) for every missing number, then reads as before; placeholders count as `Lost`, are skipped by the application and age by `written_at` in the retention. Only when no object below `next_number` exists and object `next_number` does, nothing is written: the database is an older backup whose restored `low_number` is stale, and the range below was removed by the retention. In the remaining rare case (an older backup, every object below it removed, nothing deleted since) the placeholders lie below `next_number` and the retention ages them out. | After a host loss the database comes back newer than the object backup; without placeholders the numbers keep a hole, a later restore to an older kept backup stops at it and brings back deletions made after the recovery, and the consumer meets an object of another entry and stalls. The retention removes only from `low_number` upward and never at or above the `next_number` of a kept backup, so the objects written after an older backup lie at or above its `next_number`. |
