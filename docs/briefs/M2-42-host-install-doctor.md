# M2-42: bothy-host: installation, state, doctor and pair

Status: ready | Depends on: M2-38, M2-41 | Milestone: M2

## Goal

After this ticket the host service `bothy-host` can be installed on macOS, Linux and Windows without leaving administrator rights behind, checks itself before every start and on command, and pairs itself with a server. `bothy-host install` creates the service user `bothy-host` with the state directory `host_service.state_dir`, one session user per person with a home only for that user, one PTY helper per session user as a system service of the operating system (launchd LaunchDaemon, systemd system service with socket activation, Windows service under the session user's account) and the host service itself, and on Windows, after the operator's confirmation, removes only the entry `Authenticated Users:(AD)` from the root of each drive with a location. `bothy-host session-user add` and `session-user remove`, `restart`, `pair`, `doctor`, `run` and `pty-helper` work as 24 "Host service `bothy-host`" and 16 "Terminal: forwarding and host service" describe. The private keys lie in the state directory as files with mode `0600` (on Windows encrypted with DPAPI in the context of the service user) and never leave it. `bothy-host doctor` runs HD1 to HD11 with the per-platform terms of 24 2.2 point 6 (trusted owners, "writable" including creating entries, appending and attributes, full path resolution, places of a session user resolved by its own helper, directory identity, the Windows drive root), reports codes and, by the rule for names, the names of session users, never paths, contents or values, and refuses the start of the host service with its own exit code after which no service manager restarts it. The local channel between the service user and each helper checks its peer by user and by the process ID the service manager reports. A fake `claude` in `testdata` proves HD6 without a real model or account. Why: a person with a terminal must never reach the keys of the host, another person's account, a subscription login of someone else or a place another person can write (Rulings T2, T12, T13; threats T-TM-04, T-TM-05, T-TM-08, T-TM-12, T-TM-13, T-TM-14), and a host that cannot prove this for its platform gets no terminal (RK-23). This is the host side of TM-T13, TM-T22, TM-T24, TM-T26, TM-T27 and of the parts of TM-T21 and TM-T29 that need no session; the control connection (M2-43) and the sessions with PTY (M2-45) build on it.

Product requirements implemented here:

11. Users without administrator rights (24 2.2, 16 4.4 point 1, Ruling T12): the service user `bothy-host` owns the state directory (mode `0700`, on Windows a protected DACL); each person gets an own session user from `host_service.session_users` with a home only for that user (mode `0700`, on Windows an ACL only for the user and the trusted owners); no session user can read the state directory; on macOS no session user is in `staff`.
12. Each PTY helper is a system service under its session user, never setuid; binary, service definition and the folder of the channel endpoint belong to a trusted owner and are writable by no session user; on Linux and macOS the service manager creates the endpoint (socket activation); the session user cannot stop or reconfigure the service (24 2.2 PTY helper points 1 and 2, HD10).
13. The local channel carries only control messages, check results and (later, M2-45) decrypted frames, never keys; `bothy-host` checks the peer by user and by the process ID the service manager reports, sends no frame on a mismatch and reports HD10 failed with the name of that session user (24 2.2 PTY helper point 3, D-W-109).
14. Private keys: an X25519 key pair (Noise) and an Ed25519 key pair (login) generated locally by `pair`, stored only in the state directory as a file with mode `0600` (Windows: DPAPI in the context of the service user); a key chain only where the service user has an unlocked session, which no installation of this ticket has (24 4.2, Ruling T10).
15. `pair --server <url> --code <code>` redeems the code through `pairHost` with both public keys, platform, host version, the profiles after HD7 and the session users with the display names of their working directories after HD7, shows the fingerprint of 24 4.3 in groups of four characters, and stores the keys only after the server accepted them (24 3.2, D-W-63, D-W-69).
16. `doctor` runs HD1 to HD11 before every start of the host service and on command (full run with the entry scan of HD11); it outputs per check result and code, with the names of the rule for names, with each listable home under HD9 and with the drive under `drive_root_writable`, never contents or values, and exits non-zero as soon as one check fails; warnings alone do not change the exit code (24 2.2, D-W-91).
17. The report to the server carries codes and, by the rule for names, one entry per account a person with a terminal can cause the finding in (HD6, HD10 with a wrong peer, HD11 at a place of a session user, HD9 for each former session user with a listable home); names of other users never leave the host; never paths, contents or values (24 2.2, D-W-70, D-W-109, `HostDoctorCheck`).
18. A refused start starts no PTY and accepts no session; a paired host reports first (login, one `report`, close) and then ends with its own exit code, after which the service definition of each platform does not restart it; only `bothy-host restart` starts it again (24 2.2, D-W-91, 16 4.4 points 2 and 6).
19. HD6 asks the coding agent only through the resolved `host_service.claude_bin` with the fixed search list (the configured folder of `host_service.claude_bin`, then `/usr/bin` and `/bin`, on Windows `%SystemRoot%\System32`) and the environment of 7.4, in every session user, plus the known login locations; at `none` or `organization` a detected subscription login (`authMethod` `claude.ai` or `oauth_token`, or a login file) refuses the start, one entry per affected session user; an empty value or one that counts as empty gives the warning `auth_status_unchecked`; an output that cannot be read fails closed (24 7.4, RK-14, D-W-45, D-W-85).
20. HD7, HD10 and HD11 use the per-platform terms of 24 2.2 point 6, resolve every path fully before the check (places of a session user by its helper, places for all by the service user), check each folder of the resolved chain, each configured component and each link with its folder, treat a path that cannot be resolved as absent, and compare working directories by file system identity (device and inode; on Windows volume serial number and the 128-bit file ID of `FILE_ID_INFO`) (D-W-80, D-W-83, D-W-84, D-W-86).
21. HD11 checks one rule for every configured path and every place of a session user, including the chain files `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.mcp.json`, `.claude` and `.git` in every folder on the way; the entry scan runs per session user in its helper, only that session user waits for it (`entry_scan_running`), `host_service.entry_scan_timeout` bounds it (`entry_scan_timeout`), and only a later full run lifts its finding (D-W-68, D-W-89).
22. `host_service.session_users` and `host_service.claude_workdirs` are read only at start; a folder listed under two session users drops out of both lists; the `CLAUDE_CONFIG_DIR` of the profile `claude` at `organization` is the fixed folder `.config/bothy-host/claude` in the session user's home (D-W-69, 24 7.4).
23. `session-user add` creates the user with a home only for that user and its helper service, refuses a name the state directory already binds to a person, and restarts the host service; `session-user remove` removes the name from `host_service.session_users` and its entry from `host_service.claude_workdirs`, removes the helper service, closes the home and restarts the host service, keeping the binding; `restart` restarts the host service so that a changed configuration takes effect (D-W-67, D-W-88, D-W-90).
24. On Windows `install` (also with `--drive-root <drive>`) removes, after the operator's confirmation, only the entry `Authenticated Users:(AD)` at the root of the system drive and of each drive with a location, by rewriting exactly that folder's DACL with `SetFileSecurityW`, keeping every other entry in order and with its control bits; without confirmation nothing changes and HD11 reports `drive_root_writable` (D-W-87).
25. The host service opens no network listener; its only network connection in this ticket is the outgoing HTTPS request of `pair` (R-TM-01).

## Design notes

1. **Who runs what.** Three identities: the administrator (root, or an elevated member of `Administrators`) runs `install`, `session-user`, `restart`, and `pair` and `doctor` when the service user cannot run them itself; the service user runs `run` and the service-side checks; each session user runs its `pty-helper` and the helper-side checks. Every command that needs administrator rights and lacks them exits `2` with `bothy-host <command>: administrator rights required`. Ruling for docs/DECISIONS.md: `pair` and `doctor` run with the identity of the service user: directly when the caller is the owner of the state directory (the service user itself, and the tests); through the admin endpoint of the running host service when an administrator calls them; with the service stopped, on Linux and macOS in a child process with the service user's credentials (`SysProcAttr.Credential`), and on Windows `doctor` starts the service once with the start argument `doctor-once` (it runs the full run, hands the result to the waiting command over the admin endpoint and stops with exit code `0`, connecting to no server and accepting no session), while `pair` on Windows requires the running service and otherwise exits `2` naming `bothy-host restart`. Reason: keys under DPAPI and files owned by the service user can only be written in its context, and places for all must be resolved by the service user (24 2.2 point 6).

2. **Commands and exit codes.** `install [--session-user <name>] [--drive-root <drive>] [--drive-root-confirm yes|no] [--config <path>]`; `session-user add <name>`; `session-user remove <name>`; `restart`; `pair --server <url> --code <code> [--ca-file <pem>]`; `doctor`; `run`; `pty-helper --session-user <name>`. Exit codes: `0` success; `1` a check failed (`doctor`) or a runtime failure; `2` usage or environment error (unknown flag, missing rights, unreadable configuration in a command); `78` refused start of `run` (constant `ExitStartRefused`, the value `EX_CONFIG` of sysexits). Ruling for docs/DECISIONS.md. `--drive-root` alone makes `install` do only the drive root step (24 2.2 point 6). The confirmation is a prompt on the terminal; `--drive-root-confirm` answers it for unattended installs; without a terminal and without the flag the answer is no. Ruling for docs/DECISIONS.md, the local output of `doctor` (24 2.2 "Output on the host"): one line per check in the order HD1 to HD11, `HD<n> ok`, `HD<n> WARN <code>` or `HD<n> FAIL <code>`, followed by `session_user=<name>` for a named entry, `user=<name>` for each user whose home HD9 could list and `drive=<letter>:` for `drive_root_writable`, one line per entry; then the summary `doctor: <failed> failed, <warnings> warnings`; the declaration in use on its own line (`declaration: none|personal|organization|unknown`); never a path, a content or a value.

3. **Configuration file.** 24 and 16 name the keys `host_service.*` but no file. Ruling for docs/DECISIONS.md (update 24 17 and 16 4.4): one YAML file nested like the names (`host_service: {session_users: [...], ...}`), decoded with `go.yaml.in/yaml/v3` like the server (M1-07): unknown keys, duplicate keys and wrong types are errors naming the key; durations in the duration grammar of M1-07. Paths: Linux `/etc/bothy-host/config.yaml`, macOS `/Library/Application Support/bothy-host/config.yaml`, Windows `%ProgramFiles%\bothy-host\config.yaml`; `--config` overrides it for tests. The file and every folder on the way belong to a trusted owner and are writable by no session user; HD10 checks them (Design note 8), because the file chooses every program of every session user.
    a. `host_service.profiles`: a list whose items are `shell`, `claude` or a mapping `{name, display_name, kind: command, program, args}` with an absolute `program`; names match the pattern of `HostProfile.name`; `shell` and `claude` get the display names `Shell` and `Claude Code`.
    b. `host_service.claude_workdirs`: a mapping from a session user name to a list of `{display_name, path}`; display names are not empty and unique within one list, else HD7 drops that entry with a warning.
    c. New key `host_service.auth_status_timeout` (Host service, default `30s`): the bound of one call of `claude auth status` and of the login-shell probe of HD6. Add the row to 24 17. Ruling for docs/DECISIONS.md.
    d. An invalid file makes `run` log `config_invalid` with the key and exit `78`, so no service manager loops on it; `doctor` and the other commands exit `2`.

4. **State directory (`internal/state`).** Files, each written atomically (temp file in the directory, `fsync`, rename, `fsync` of the directory), mode `0600` on Linux and macOS, on Windows inheriting the protected DACL of the directory (service account, `SYSTEM`, `Administrators`): `keys` (both private keys; on Windows the content is a DPAPI blob from `CryptProtectData` without `CRYPTPROTECT_LOCAL_MACHINE`), `pairing.json` (server URL, `host_id`, `instance_id`, the fingerprint; no private member), `bindings.json` (session user name to person ID, written by M2-45 at the first session, read here), `declaration.json` (the last `llm_credentials` learned from `ready`, a code), `admin.sock` on Linux and macOS (Design note 15). The name `claude_api_key` is reserved for the API key of `organization` (16 4.4 point 5), which M2-45 reads. Ruling for docs/DECISIONS.md: 24 4.2 and 7.4 say the state directory holds only the keys, the bindings and the API key; the pairing record and the last declaration are added there and in 24 17 (row `host_service.state_dir`), both without secrets and without a subscription login.

5. **Port to the operating system (`internal/hostos`).** All platform behaviour sits behind small interfaces so that every rule is unit-tested on any build host with `hostostest`: `Users` (look up by name and ID, home, enumeration of local users with their IDs, `UID_MIN` and `UID_MAX` of `/etc/login.defs` on Linux and the profiles of `ProfileList` on Windows for HD9, membership by `id -G <name>` on Linux and macOS, because the pure Go user database misses directory services, and local plus global groups on Windows), `Security` (owner, mode, POSIX ACL from `system.posix_acl_access` on Linux, the macOS ACL read with `getattrlist` and `ATTR_CMN_EXTENDED_SECURITY` where `golang.org/x/sys/unix` offers it, else parsed from `/bin/ls -led`, the Windows security descriptor), `Resolver` (Design note 7), `Services` (install, remove, start, stop, restart, main PID, exit policy per platform), `Runner` (absolute path, argument vector, environment, timeout), `Probe` (`sudo -n true` as a user, the Docker socket, `kernel.yama.ptrace_scope`). Ruling for docs/DECISIONS.md: no cgo on any platform; an ACL entry that cannot be read, parsed or mapped to a user or group counts as granting every right to every session user (fail closed), because one right too many only blocks, one too few opens a place (24 2.2 point 6).

6. **Checks HD1 to HD5 and HD8, HD9.** The check names of the report are the `check` values of `HostDoctorCheck` (`hd1_user` to `hd11_shared_locations`). Codes, Ruling for docs/DECISIONS.md and a new table "Codes of `doctor`" in 24 2.2 (the core contract only says "code"):

    - HD1: `session_users_empty`, `session_user_duplicate` (names compared without case on every platform, like `host_session_users`), `session_user_is_service_user`, `privileged_user` (`root`, `Administrator`, `SYSTEM`, or uid 0), `user_missing`, `session_user_name_invalid` (not the pattern of `HostReportedSessionUser.os_user`; the length is the server's `host.os_user_max_chars` and fails at `pairHost`).
    - HD2: `forbidden_group` (the fixed list of 24 HD2, compared without case on Windows, plus `host_service.extra_forbidden_groups`; the operator cannot shorten the fixed list), `docker_socket_writable` (Linux: `/var/run/docker.sock` writable by the user, one of its groups or others, by mode or ACL).
    - HD3: `passwordless_sudo` (`sudo -n true` succeeds for the service user or, in its helper, for a session user). On Windows HD3 has no probe and passes without code, because elevation needs the credentials of an administrator and HD2 covers `Administrators`. Ruling for docs/DECISIONS.md.
    - HD4: `state_dir_owner`, `state_dir_mode`, `key_file_unprotected` (mode not `0600`, or on Windows not a DPAPI blob or a DACL with more than the three principals).
    - HD5: warning `server_host_detected`: the host part of the paired server URL resolves to an address of an own interface or to loopback; reported as `is_server_host`.
    - HD8: `state_access_for_session_user` (owner, mode, ACL or group give a session user or one of its groups an entry), `helper_reads_state` (a helper could open the state directory or the key file).
    - HD9: `foreign_home_listable`. Each helper lists the home of each of these accounts that is not a session user, and every listing must fail: `root`, the service user, every former session user (bound in `bindings.json`, not in `host_service.session_users`), and every person account of the platform. Person accounts are: on Linux an account with a UID from `UID_MIN` to `UID_MAX` of `/etc/login.defs` (the file's documented defaults when a key is missing); on macOS an account with a `UniqueID` of at least 501, the first ID macOS gives a regular user; on Windows every account with a profile under `ProfileList` (the `ProfileImagePath` of its SID subkey; the values `Default` and `Public` name no account). HD9 skips all other system accounts (Linux below `UID_MIN`, `nobody`; macOS below 501, `nobody`), because their homes are system folders that every user may list by design (macOS `nobody` `/var/empty`, `_www` `/Library/WebServer`, `_networkd` `/var/networkd` with mode `0755` and owned by itself; Debian `daemon` `/usr/sbin`, `systemd-network` `/`), and they hold no files of a person. Ruling for docs/DECISIONS.md; update 24 2.2 (the HD9 row, point 4, "Reason for HD9") and R-TM-17 with this rule and reason. Report: one entry with the name for each former session user (bound in `bindings.json`, not in `host_service.session_users`) whose home can be listed, one entry without a name for all others; the local output names every such user.

7. **Path resolution and identity.** `Resolver.Resolve(path) (Resolved, error)` returns the final path (`realpath` semantics on Linux and macOS, `GetFinalPathNameByHandle` on Windows), each folder of the resolved chain, each component of the configured path, and each link followed (symbolic link, on Windows also a junction) with the folder it lies in; `Resolver.Identity(path)` returns device and inode, or on Windows the volume serial number and the 128-bit file ID of `GetFileInformationByHandleEx` with `FileIdInfo`. A missing path, a dangling link or a folder on the way the resolving user cannot open gives `ErrUnresolvable`: a working directory drops out of its session user's list, a `command` profile drops out, `host_service.claude_bin` counts as empty, and an unresolvable home fails HD11 for its session user (`home_unresolvable`). A link counts as an entry of its folder and as its target.

8. **HD10 helper integrity.** The service user checks, after resolution, that each of these belongs to a trusted owner and is writable by no session user (the per-platform lists of 24 2.2 point 6 and D-W-86, unit-tested right by right): the helper binary, every service definition, every folder of a channel endpoint, the configuration file (Design note 3), and, when set, `host_service.claude_bin` with every folder on the way, every folder of the search list of HD6 and, for a file starting with `#!`, the interpreter the search list finds (for `#!/usr/bin/env node`: `env` and the `node` in the search list). Codes: `helper_untrusted` (binary, definition, endpoint folder, configuration file, or a setuid or setgid bit on the binary), `claude_bin_untrusted` (also a Windows value that is not an `.exe`), `peer_mismatch` (named with the session user of the channel), `peer_check_unavailable` (the platform has no proven peer check, Design note 11), `ptrace_scope_low` (Linux, `kernel.yama.ptrace_scope` below `1`), `helper_unprotected` (macOS: the binary lacks the hardened runtime flag or carries `get-task-allow`). A missing interpreter in the search list leaves `host_service.claude_bin` checked but counting as empty for HD6 and the profile (D-W-85).

Read only the JSON member `authMethod`; a value outside `none`, `claude.ai`, `oauth_token`, `api_key`, `api_key_helper`, `third_party`, an unreadable output, a timeout or an exit code other than `0` and `1` gives `auth_status_unknown` (fail closed, RK-14). Login locations: `.claude/.credentials.json` in the home, `.credentials.json` in each checked `CLAUDE_CONFIG_DIR`, and a probe of the session user's login shell (Windows: the user's environment in its registry hive) that prints only whether `CLAUDE_CODE_OAUTH_TOKEN` is set and the value of `CLAUDE_CONFIG_DIR`, never a token. 11. **Local channel and peer check (`internal/localchan`).** Endpoints: Linux `/run/bothy-host/helper-<name>.sock` (systemd socket unit, `SocketUser=root`, `SocketGroup=bothy-host`, `SocketMode=0660`, `DirectoryMode=0755`, `Accept=no`), macOS `/Library/Application Support/bothy-host/run/helper-<name>.sock` (LaunchDaemon `Sockets` with `inetdCompatibility` `Wait = true`, so the listening socket arrives on standard input without cgo; owner and mode as on Linux), Windows `\\.\pipe\bothy-host-helper-<name>` created by the helper with `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS` and a DACL for the service account only. Ruling for docs/DECISIONS.md (update 24 2.2 PTY helper point 3): with socket activation the operating system reports the service manager as the peer of a connecting client, so on Linux and macOS the helper creates a `socketpair`, passes one end with `SCM_RIGHTS` over the accepted connection, and all further messages run over that pair; `bothy-host` reads the peer of its end (`SO_PEERCRED` on Linux, `LOCAL_PEERCRED` and `LOCAL_PEERPID` on macOS) and compares user ID and process ID with the session user and the main PID the service manager reports (`systemctl show --property=MainPID --value`, `launchctl print system/<label>`); on Windows it compares `GetNamedPipeServerProcessId` and the process token's user SID with the session user and the process ID of `QueryServiceStatusEx`. The helper accepts only the service user as client (`SO_PEERCRED`, `LOCAL_PEERCRED`, `GetNamedPipeClientProcessId`). Before both checks pass, no message flows. If the platform run of TM-T26 cannot prove the mechanism for a platform, HD10 fails there with `peer_check_unavailable` (RK-23: no terminal without proof) and the report says so. Codec: a 4-byte big-endian length, one kind byte and the body; kind `0x00` is a JSON control message `{"op", "id", "d"}`, kind `0x01` is reserved for the session frames of M2-45, any other kind closes the channel; the limit is `frame.MaxLen` of M2-38 plus the header (protocol constant, rule 9). Ops of this ticket: `hello` (helper, protocol version `1`), `check.run` (mode, the other session users, resolved `host_service.claude_bin` and search list, declaration, working directories), `check.result`.

12. **The helper (`internal/helper`).** At start: Linux `prctl(PR_SET_DUMPABLE, 0)`; Windows a process DACL without rights for its own user, with an `OWNER RIGHTS` entry that removes the owner's implicit rights; macOS relies on the hardened runtime that `install` signs in (Design note 13) and HD10 checks. It serves one channel to `bothy-host`, runs HD3, HD6, the helper part of HD8, HD9 and HD11 and reports the working directory identities for HD7, all as its session user; results carry codes, names and identities, never paths or contents. It closes the channel on any malformed message.

13. **Installation (`internal/install`).** `install` computes a plan of steps per platform from the configuration and the running system and executes it through `hostos`; every step is idempotent, nothing existing is removed or overwritten except by `session-user remove`. Places of the product name (update 02 "Places that carry the product name"): program folder Linux `/opt/bothy-host/bin/`, macOS `/Library/Application Support/bothy-host/bin/`, Windows `%ProgramFiles%\bothy-host\`, into which `install` copies the running binary owned by a trusted owner, mode `0755`, no setuid; systemd units `bothy-host.service`, `bothy-host-helper-<name>.socket` and `.service`; launchd labels `bothy-host` and `bothy-host.helper.<name>`; Windows services `bothy-host` and `bothy-host-helper-<name>`; pipes `bothy-host-admin` and `bothy-host-helper-<name>`. macOS: after copying, `install` signs the program binary ad hoc with the hardened runtime: `/usr/bin/codesign --force --sign - --options runtime <program folder>/bothy-host`, with no entitlements and so no `get-task-allow`. It skips this step when the binary already carries a signature with the `runtime` flag, so the Developer ID signature of M7-23 stays intact. HD10 reads the flags with `/usr/bin/codesign --display --verbose=4 <binary>` and the entitlements with `/usr/bin/codesign --display --entitlements - --xml <binary>`. Ruling for docs/DECISIONS.md. Users: Linux `useradd --system` for the service user with the state directory as home and no login shell, `useradd --create-home --user-group` per session user, home mode `0700`; macOS hidden users created with `dscl`, the service user with the state directory as `NFSHomeDirectory` (HD9 lists it), each session user with an own primary group and not in `staff`, home created with `createhomedir` and mode `0700`; Windows the virtual account `NT SERVICE\bothy-host` for the host service, and per session user a local account with a random password handed only to the service control manager, `SeServiceLogonRight`, the profile created with `CreateProfile` and its folder ACL only for the user and the trusted owners.     a. `session-user add <name>`: refuses a name in `bindings.json` (`bothy-host session-user add: <name> is bound to a person on this host; create a new name`), refuses a name already configured, creates user, home and helper service, adds the name to `host_service.session_users`, restarts the host service.

15. **Start sequence and the declaration (`internal/startup`).** `run`: load the configuration (Design note 3 d), open the state, open the admin endpoint (Linux and macOS `<state_dir>/admin.sock`, clients only with user ID `0`; Windows `\\.\pipe\bothy-host-admin` with `PIPE_REJECT_REMOTE_CLIENTS`, a DACL for `SYSTEM` and `Administrators`, clients only elevated members of `Administrators`), run `Full`. At start HD6 uses the declaration stored in `declaration.json`; it is unknown only if no `ready` was ever stored. If the host is paired, `run` calls `Control.Login` before deciding. The declaration of the `ready` replaces the stored one in `declaration.json`, and HD6 is evaluated again with it. A remaining finding with the consequence "Start refused" (HD1 to HD4, HD8, HD9, HD10, HD11 at a place for all, HD6 at a known `none` or `organization`) refuses the start: exactly one `Control.Report` with all checks, `Control.Close`, exit `78`. Without such a finding, `Control.Report` follows and the host waits for M2-43 to M2-45. If the host is not paired or `Login` fails, the stored declaration decides: log the codes and, on such a finding, exit `78`. A later change of a result (an entry scan ends, a `ready` with another declaration) sends a new report. The `doctor` command against a running service makes it run `Full`, return the result (op `doctor.run` of the admin endpoint, answering with the local result and the report entries as `HostDoctorCheck` items, which the platform suite reads directly), report it, and on a "Start refused" finding other than HD6, HD10 and HD11 end like a refused start. `Readiness(sessionUser)` tells M2-45 whether a session user may get sessions (HD11 per session user, `entry_scan_running`) and whether the host may (every other finding). `Control` is `Login(ctx) (Ready, error)`, `Report(ctx, Report) error`, `Close() error`; this ticket wires `NoControl`, which answers every `Login` with `ErrUnreachable`, exactly the case 24 2.2 names, and M2-43 replaces the wiring. Ruling for docs/DECISIONS.md (update 24 2.2 and 7.4, openapi `HostReady`, asyncapi `hostControl`): the host service learns `hosts.llm_credentials` only from `ready`, the server sends `ready` again on every change of the declaration (M2-43 builds it), and the host treats each `ready` as the current declaration; until a `ready` was ever stored the declaration is unknown, and no session is possible then.

16. **`pair` (`internal/pairing`).** Refuse any URL that is not `https://` (`pair: the server URL must use https`); trust the system roots plus `--ca-file`. Generate the X25519 key pair with M2-38's `noise.GenerateKeyPair(crypto/rand.Reader)` and an Ed25519 key pair with `crypto/ed25519`; compute the fingerprint with `fingerprint.Compute`; POST `<server>/api/v1/hosts/pair` with `HostPairRequest` (`noise_public_key` base64url without padding, `auth_public_jwk` with `kty`, `crv`, `x` only, `platform`, `os_version`, `host_version`, `profiles` after HD7, `session_users` after HD7). The lists come from the last `Full` run of the running service; in the direct path without a running service the helpers are asked over their endpoints, and an unreachable helper gives its session user an empty list with the warning `pair: working directories follow with the first report`. On `201`: if `key_fingerprint` differs from the own computation, store nothing and exit `1` (`pair: fingerprint mismatch`); else write `keys` and `pairing.json` atomically (a new pair replaces the old keys only now), print `fingerprint: XXXX-XXXX-...` and `host: <host_id>`, and, when an administrator called it, restart the host service. On a problem answer print `pair: server refused: <code>` with `reason` when present and, for `400 validation_failed`, each `errors[].code` with its pointer, then exit `1`; on `401 unauthenticated` (M2-41 answers every redemption failure so, also a retry after a lost answer, because the code is used) add the hint `ask an owner for a new pairing code`. After a `400` the same code stays valid, so the operator fixes the configuration and runs `pair` again. The code, the private keys and the request body appear in no output or log. Ruling for docs/DECISIONS.md: `pair` needs the identity of the service user (Design note 1) and restarts the service so that M2-43 logs in with the new keys.
