# M2-21: Switching and guided flow (I4)

Status: ready | Depends on: M1-54, M2-20 | Milestone: M2

## Goal

After this ticket an owner turns a change that invariant I1 would reject into an admissible one in a single request, without any moment in which I1 is broken (R-AZ-17). The five actions `grant.create`, `group.member.add`, `owner.add`, `space.operator.set` and `channel.operator.set` accept the optional request member `resolve_i1 = {switch_to_organization: [agent_ids], reason}`: the server authorizes `agent.billing_mode.set` for every listed agent, switches those agents to `organization` first and then applies the change, all in one transaction, checks I1 before the commit and writes one audit entry per action with the same `correlation_id`. Either every part commits or none does (BR-07). The grant preview (`previewGrant`, whose body is `GrantCreate`) runs the same request as a dry run. Switching per agent and for all agents with a reason (`setAgentBillingMode`, `setAllAgentsBillingMode`, built in M1-51) and the guided flow share one apply step, so all three paths write the same rows and events, and the whole I4 path is proven against all real sources and the heartbeat of M2-20: `set_all` to `personal` with one violating agent changes nothing (BR-08), a switch reaches every client and the agent's own consumer as `agent.updated`, and the adapter's actual mode shows as a difference until its heartbeat reports `organization`. This is the server side of 10 "Switching (I4)" and "Guided flow 'Grant a person access in a personal space'", the mitigation of RK-11 and the way out that OQ-01 relies on: I1 keeps no owner exception (L22), and a second owner or a further person with `trigger` becomes possible by switching first.

15. 16. Desired and actual mode stay apart: the actual mode from the heartbeat is evidence for display, warning and audit, never a permission; the agent card shows the difference until the adapter reports the new mode, and the warning ends with that heartbeat (10 8, 9.2 point 5, 11 point 5; 09 4.8).

18. ## Design notes

1. Module boundaries (02 4.1 rule 4, 4.3, 4.4). `authz`, `identity` and `chat` may not import `agents`, so the switch crosses through a source port that `authz` declares and `agents` implements, as `AgentPolicySource` does. `authz` owns the orchestration (validation, `authorize` of every listed agent, `AddAffected`, the call of the switch) because the rights logic of every action lives only in `authz` (05 rule 1); `agents` owns the write of its table, the event and the audit entry of `agent.billing_mode.set` because it executes that action (02 4.1 rule 6). `identity` and `chat` get `authz.I1Resolver` through their constructors; `make arch` stays green without a new edge. Port packages import only `kernel`, and domain packages import only `kernel-core` (02 5 and rule 1, R-AR-03). In `.go-arch-lint.yml`, generated by `tools/archgen`, the root components are `identity: [identity, kernel-ports]` and `chat: [chat, kernel-ports]`, and `authz-domain` may depend only on itself. So only `app` and `adapters` of `identity` and `chat` import `authz`, and they convert the module's own `ResolveI1` DTO into `authz.ResolveI1`. Until `internal/wire` binds the agents implementation, `EmptyAgentPolicySwitch` fails closed (02 4.4, last paragraph). Ruling for docs/DECISIONS.md.

2. Request member and validation.
    - Schema `ResolveI1` in `docs/api/openapi.yaml`: `type: object`, `required: [switch_to_organization, reason]`, `switch_to_organization`: array of `Uuid` with `minItems: 1` and `uniqueItems: true`, `reason`: string with `minLength: 1`; description "Guided flow (05 rule 1.6, 10 section 11): switch these agents to `organization` first, in the same transaction as the change." Close the schema the way the merged write schemas are closed: 06 2 "Unknown values" and SEC-IN-1 ask for `additionalProperties: false`, while `docs/api/openapi.yaml` today carries it on no schema and the request decoder of M1-18 rejects unknown members; follow the merged convention and name it in the report.
    - Rules beyond the schema (`internal/authz/domain`, used by all five paths and by the preview): `reason` is trimmed and not blank, passes `kernel/textcheck` (SEC-IN-4) and has at most `audit.reason_max_chars` characters (SEC-AUD-5); otherwise `400 validation_failed` with pointer `/resolve_i1/reason` and `errors[].code` `required`, the code M1-26 uses for a text check, or `too_long`. An empty list or a repeated ID gives `400 validation_failed` with pointer `/resolve_i1/switch_to_organization` (or `/resolve_i1/switch_to_organization/<index>` of the repeated entry) and the code the merged request validator uses for that keyword.
    - Field errors of the outer body and of `resolve_i1` come together in one answer with all `errors[]` (06 5 point 3).
    - Apply the same reason rules to `reason` of `BillingModeSet`, `BillingModeSetAll` and `CredentialHolderSet` where M1-51 does not already (10 9.1 "`reason` is required and appears in the audit").

3. Order of checks, the same skeleton for all five actions (05 rule 1.6; 10 11 point 4: "checks both actions individually with `authorize` ... first the switch, then the grant"):
    a. Decode and validate the whole body (note 2).
    b. Load the outer target and run the outer `authorize` exactly as M1-31, M1-48 and M1-54 do: `404 not_found`, `403 forbidden` (`owner_only`, `step_up_not_possible`, delegation reasons) and `401 step_up_required` come first, so a caller without read right on the outer target learns nothing about the listed agents.
    c. The outer checks that write nothing, unchanged: subject or person exists, `409 conflict` (already an owner, person not active, already a member, `reason` `claim_managed_group`, archived target), `If-Match` of the operator actions (`428 precondition_required`, `412 version_conflict`), operator validation (M1-54 D1).
    d. Operator no-op: when `setSpaceOperator` or `setChannelOperator` would change nothing, answer as M1-54 D2 (`200`, no event, no version, no rights version; audit with `no_change: true` for the operator action) and switch no agent. Reason: the guided flow exists to make a change admissible (05 rule 1.6), a request without change cannot violate I1, and a switch alone goes through `setAgentBillingMode`. Ruling for docs/DECISIONS.md.
    e. Inside the unit of work of the outer action (its `RightsChange` locked `permission_version` in phase 1, 02 8.1) and before its first write, `I1Resolver.ResolveI1`:
    - for each listed agent in ascending ID: `authorize(by, agent.billing_mode.set, {kind: agent, id})`. `not_found` (unknown ID, a principal that is not an agent, an agent the caller may not read) is answered as `404 not_found`, with exactly the status, body and headers of an unknown agent ID, identical in all three cases (05 rule 1.2 and 2.5, R-AZ-01, ADR 0017, 07 4.2 "second target"); every other denial is returned as `authorize` returns it (`403 forbidden` with `reason` `owner_only` for a visible agent and a non-owner, `401 step_up_required`, `403 forbidden` with `reason` `step_up_not_possible` for a personal token). The first failing agent decides; `authz` audits the denial as for every action with Audit `yes` (R-AZ-04).
    - `AddAffected(ctx, agentIDs...)` (M1-29), then `AgentPolicySwitch.SwitchToOrganization` (note 4).
    f. The outer write, its events and its allow audit entry, unchanged.
    g. Phase hooks: I1, SR8 and `access.changed` (M1-29), then `sync` and `audit`.
    An error before step e switches nothing; an error in e, f or g rolls back everything (BR-07).

4. The switch (`internal/agents`):
    - `SwitchToOrganization` runs in the ambient transaction and calls no `authorize`; its doc comment says that only `authz` calls it, after authorizing every agent. It locks the `agents` rows `FOR UPDATE` in ascending `principal_id` (lock order of M1-51 for `set_all`; 03 6.3 point 2).
    - Per agent on `personal`: `billing_mode = organization`, `credential_holder_id` NULL, `billing_mode_changed_at` now (`kernel/clock`), `billing_mode_changed_by` the actor, `version + 1`; append `agent.updated` (resource `{kind: agent, id, version}`, empty scope, payload `AgentPayload` with the agent after the change, receive action `agent.read`); record one allow entry `agent.billing_mode.set` with resource the agent and the detail keys M1-51 writes for this action (old and new mode, old holder, `reason`; 10 14), never names (SEC-AUD-5).
    - Per agent already on `organization`: no row change, no event, an allow entry with `no_change: true` (06 2 "No effect"). Reason: another owner may have switched it since the console's preview, and the aim of the request still holds. Ruling for docs/DECISIONS.md.
    - A disabled agent is switched like an active one, as `set_all` does in M1-51 (a disabled personal agent becomes relevant for I1 again at `agent.enable`, 10 5.1).
    - No `If-Match` for the listed agents, as for `set_all` (06 8). Ruling for docs/DECISIONS.md.
    - Shared apply step: the row change and the event of a switch to `organization` move into one function in `internal/agents/app` that `SetBillingMode`, `SetBillingModeAll` and `SwitchToOrganization` call; each caller keeps its own audit entry: one per agent for the single switch and the guided flow, one with the list of agents for `set_all` (10 14). M1-51's tests stay green unchanged. Ruling for docs/DECISIONS.md.

5. I1 after the switch: `AgentPolicySource` reads inside the ambient transaction (M1-29), so the hook sees the switched agents as `organization` and does not check them any more; every other active personal agent is checked as always (M1-29 ruling: all personal agents on every rights change). A list that misses a violating agent fails with `409 i1_violation` whose `conflicts` name only the remaining agents (10 5.4, `InvariantViolation`), and nothing of the switch remains.

6. Audit and correlation:
    - Success: one allow entry `agent.billing_mode.set` per listed agent, then the allow entry of the outer action with its unchanged details, all with the request's `correlation_id` from `kernel/reqmeta`, equal to the response header `Correlation-Id`. With one listed agent these are the two entries of BR-07 (10 11 point 4); with more agents there is one entry per action (05 rule 1.6 "one audit entry per action"). Ruling for docs/DECISIONS.md.
    - I1 or SR8 violation: only the deny entry of the outer action, written by the path of M1-29 in its own transaction (`deny_reason = i1_violation` with `details.violations`, or `last_owner`), with the same `correlation_id`.
    - A denied switch: the deny entry of `agent.billing_mode.set` written by `authz`; the outer action has no allow entry.

7. Events: in the one transaction first `agent.updated` per changed agent, then the outer action's events (`grant.changed`, `group.changed`, `user.updated`, `space.updated` or `channel.updated` with the inheriting channels of M1-54 D4), then `access.changed` from the hook. One request raises the rights version once (one `RightsChange`); every envelope carries the same `correlation_id`. The agent receives its own `agent.updated` through its consumer (04 15.1 point 4, M2-07), which tells its adapter that the desired mode changed (10 9.2 point 5).

8. Presence (M2-20). The tracker learns a desired mode changed by `resolve_i1` with the agent's next heartbeat, which re-reads the desired values under the row lock (M2-20 notes 2 c and 13), the same rule as for a change made in another process. This matches 10 11, where the warning follows the next heartbeat, and needs no after-commit mechanism: `kernel/txn` has none (its phases end with the commit, 02 8.1), and under `Idempotency-Key` the HTTP chain owns the outermost unit of work (02 8.4), so a use case cannot act after the commit. Do not add one. `Agent.presence.billing_mode_matches` in `getAgent` and in the payload of `agent.updated` compares the last reported mode with the desired `billing_mode` read in that request (the rule of M1-51 that M2-20 note 8 keeps); if the merged code takes it from tracker memory, change only that comparison in the representation, with a test. Warnings and the mismatch age follow the tracker. Ruling for docs/DECISIONS.md.

9. Preview (`previewGrant`, body `GrantCreate`):
    - With `resolve_i1` the preview is a dry run of the whole request (R-RE-10). Authorization: `access.preview` for the grant target exactly as M1-49; then for every listed agent in ascending ID `access.preview` with target action `agent.billing_mode.set` (05 4.2: right and owner rule of the target action, without step-up; `docs/spec/actions.yaml` `owner: as_target`): an owner passes without fresh step-up, a visible non-owner gets `403 forbidden` with `reason` `owner_only`, an unknown or invisible agent `404 not_found` as in note 3 e. `access.preview` never audits, so no deny entry is written.
    - In the dry-run transaction of M1-49: `AddAffected` and the switch, then the grant apply step, then the evaluator; the sentinel rollback of M1-49 leaves no row, event, audit entry or counter change.
    - Result: `allowed`, `effects`, `invariant_violations` and `hints` as after both parts. `text` gets one line per agent that the request would switch from `personal`, from two new catalogue entries per language in the style of the existing keys, worded after 10 11 point 2: the switch line ("First ... is switched to Organization; the organization key then bears the costs.") and, when `organization` is not in the agent's `billing_modes_supported`, the not-ready line ("The adapter of ... does not report an organization key yet. Invocations fail until it is switched."), with a German counterpart each; golden files for `de` and `en`. Ruling for docs/DECISIONS.md.
    - Without `resolve_i1` the preview is unchanged; `invariant_violations[].organization_ready` comes from `billing_modes_supported` that M2-20 now fills (10 11 point 1).

10. Idempotency and concurrency:
    - `createGrant`, `addGroupMember` and `addOwner` keep `Idempotency-Key` (M1-20; 02 8.4): `resolve_i1` is part of the stored body, so the same key with another list gives `422 idempotency_key_reuse`, and a replay returns the stored answer with `Idempotent-Replay: true` and switches nothing again. The operator actions keep `If-Match`.
    - Rights changes serialize on `permission_version` (03 6.3), so a guided flow and a parallel `setAgentBillingMode` back to `personal` for the same agent end in an order that keeps I1 (BR-03 shape); deadlocks and lock timeouts are retried by the unit of work (`database.tx_retry_max`). A heartbeat locks only its `agents` row (M2-20) and waits for the switch to commit.

11. Answers per step (codes only from `x-problem-codes`, 06 5 point 7):

| Step | Condition | Answer |

12. Discovery: no new key in `features` (06 13 point 1: `features` names capabilities beyond the base contract of the spec version; `resolve_i1` belongs to the spec version that declares it). Ruling for docs/DECISIONS.md.

13. Switching per agent and for all agents (M1-51 operations): the API stays; the shared apply step of note 4 and the reason rules of note 2; BR-08 and the end-to-end tests of I4 run against all real sources (world builder of M1-54) and the heartbeat of M2-20. `agent.updated` after a switch reaches every principal with `agent.read` and the agent itself; `access.changed` appears only for principals whose visible targets change (M1-29 ruling), the rights version rises in any case.

14. The reverse way (10 11 last paragraph): no new operation. The `409 i1_violation` of a switch back to `personal` names the extra principals in `conflicts`, and `explainChannelAccess` on a served channel names their sources (grant, group, owner); the test `TestReverseSwitchNamesBlockingSources` proves the console can show both.

15. Rulings for `docs/DECISIONS.md` section 10, one row each with date, decision, reason and place: `D-M2-21-1` resolver port in `authz` and source port `AgentPolicySwitch` implemented by `agents` (note 1); `D-M2-21-2` check order and the place of the switch before the first write (note 3); `D-M2-21-3` operator no-op switches nothing (note 3 d); `D-M2-21-4` agents already on `organization` and disabled agents, no `If-Match` (note 4); `D-M2-21-5` shared apply step with audit per caller (note 4); `D-M2-21-6` one audit entry per action, N plus one entries (note 6); `D-M2-21-7` presence follows at the next heartbeat, `billing_mode_matches` at read time (note 8); `D-M2-21-8` preview with `resolve_i1` as a dry run of the whole request with switch lines in the text (note 9); `D-M2-21-9` no discovery feature key (note 12). The rest is in 05, 07 and 10 and needs no ruling, including the `404 not_found` for unknown and invisible agents (note 3 e, 05 rule 1.2).
