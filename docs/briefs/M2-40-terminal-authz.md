# M2-40: Terminal rights, SR10, I6, SR12 and fresh step-up

Status: ready | Depends on: M1-49, M2-39 | Milestone: M2

## Goal

After this ticket `authorize` decides the five terminal actions of 05 "Hosts and terminal" (`terminal.open`, `terminal.attach`, `terminal.stream`, `terminal.read_own`, `terminal.close`) instead of treating them as deferred entries. Only a human in a session reaches them; effective `terminal` comes from the owner rule or a grant on the host (07 "Hosts and the `terminal` capability"); SR10 keeps people who are not owners on the host assigned to them and leaves a server host to owners alone; SR11 lets only the holder of a personal LLM login open or attach (I6, also against other owners); SR12 demands an own session user whose name the host reports, also from owners; and step-up `fresh` demands a passkey or step-up device key confirmation not older than `terminal.step_up_max_age` that no other opening has consumed. The module `identity` records the consumption in `auth_sessions.step_up_consumed_at` under a lock on the session row inside the transaction of the action, so one confirmation opens exactly one session. I6 holds transactionally: a grant on a personal host to anybody but the holder, any group grant there, and any rights change that would leave such a grant valid roll back with `409 i6_violation`; switching a host to `personal` or changing the holder of its LLM login ends every other person's session there in the same transaction, and so does a change of the assignee for the old assignee (SR10). The owner declares the LLM login with the new operation `setHostLlmCredentials`, the session users a host reports become part of the rights state (a change raises the rights version), and the preview of a grant on a host says when it would not take effect (hint `terminal_not_effective`). The routes that open and attach sessions come with M2-44; this ticket proves AZ-M54 to AZ-M61 (AZ-M60 with `terminal.open` itself), TM-T08, TM-T09, TM-T28 (a) and ID-T28 without the console part as decisions of `authorize` and through the `identity` and `terminal` use cases, which is the server side of T-TM-03, T-TM-08 and T-TM-09 (threat model 6.7), R-TM-05 to R-TM-07, R-TM-21 and R-TM-23.

3. **Resolution and visibility** (07 4.3, M1-28 resolution). A `host` resource resolves through `HostSource.Host`, fresh per call (`reported_is_server_host` changes without a new rights version, 03 `grants` paragraph). A `terminal_session` resource comes from `terminal` as `Resource{Kind: terminal_session, ID, HostID: terminal_sessions.host_id, OwnerID: terminal_sessions.user_id, Terminal: &TerminalFacts{...}}`; `authz` resolves the host through `HostID` (zero `HostID` is an internal error, an unknown host `not_found` with `no_grant`) and treats the session as visible when `OwnerID` is the principal or the principal is an effective owner, else `not_found` with `not_self` (the principal-owned kinds of M1-28). Replace the internal error of the visibility row `terminal_session`.

4. **Step-up `fresh`** (05 2.4, 07 4.2 step 8, 08 6.3). When `ActionSpec.StepUpFresh` is set, step 8 evaluates only this branch, not the `auth.step_up_max_age` branch:

    - `QuickReattach` first: action `terminal.attach`, `ClientComponent` not `console`, `Session.SessionState = detached`, `Session.SessionDeviceID` equal to the principal's `DeviceID`, `Session.SessionAuthSessionID` equal to the principal's `SessionID`, and `now - DetachedAt` not greater than `terminal.quick_reattach_window` (equal is allowed, one nanosecond more is not). When it holds, step 8 passes without step-up and the decision carries `QuickReattach = true`; the use case then consumes nothing.
    - `FreshStepUp` otherwise: `StepUpAt` set and `now - StepUpAt` not greater than `terminal.step_up_max_age` (equal allowed), `StepUpMethod` `passkey` or `device_key`, `StepUpConsumedAt` zero or before `StepUpAt`, and `ClientComponent` not `console`. Failing any of them gives decision `step_up_required` with reason `terminal_step_up_not_fresh`. Ruling for docs/DECISIONS.md: a console session fails closed until M6-18 adds the passkey rule with `userVerification = required` (08 6.3 point 3); console sessions do not exist before M6-01.
    - `identity.StepUp.ConsumeFresh(ctx, p)` joins the ambient unit of work (none is an internal error), locks the session row with `SELECT ... FOR UPDATE` (`id` and `user_id` of the principal), answers `401 session_revoked` for a revoked or expired session, re-evaluates freshness on the locked row's values through `authz.FreshStepUpCheck` (the same `domain.FreshStepUp` that step 8 uses) with the clock of the call, and on success sets `step_up_consumed_at = now`. On failure it returns the same error that `Decision.Err` gives for decision `step_up_required` with reason `terminal_step_up_not_fresh` (`401 step_up_required` without `reason` in the problem body), and the audit reason stays available to the caller. It writes no event and no audit entry; the use case of the action (M2-44) records the opening and the denial. Ruling for docs/DECISIONS.md: the check runs again on the locked row, not on the actor of the request, because two requests with one confirmation both pass `authorize` and only the lock orders them; `ConsumeFresh` is the first domain row lock of the action's transaction, so 03 6.3 holds and the second opening sees the consumption. Update 08 6.3 point 4.
    - Other step-up actions keep the `auth.step_up_max_age` branch and never read `step_up_consumed_at` (08 6.3 last paragraph).
