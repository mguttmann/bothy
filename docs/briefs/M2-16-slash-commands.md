# M2-16: Slash commands

Status: ready | Depends on: M2-08 | Milestone: M2

## Goal

After this ticket agents keep their slash commands in a server register and people run them in a channel or thread. The module `agents` owns the register (table `commands`, 09 "Slash commands"): `registerCommand`, `updateCommand`, `removeCommand` and `getCommand` refuse the reserved built-in names with `409 conflict` and `reason: command_name_reserved` (AG-24), allow a scope only on targets the owner serves or may write, keep at most `command.max_per_principal` live commands per owner, and write one audit entry and one `command.changed` event per change; `listChannelCommands` shows exactly the commands that 09 "Visibility and name conflicts" offers in a channel, the operator's first. The module `runs` executes them with `invokeCommand`: a control command (`commands.control = true`) goes at once to its owner as the personal event `command.invoked`, also during a run, and never creates a run, a follow-up or a model turn; a model command is triggered like a message (a run `queued` with `trigger_kind = 'command'` and `triggering_command_id`, the live-box anchor and `agent.invocation` with the parsed options) and is refused with `403 agent_invocation_denied` and `reason: run_active` while the thread has an active run. Every invocation passes `command.invoke` and, for agent commands, `agent.invoke` with I2, SR2 and SR4; every delivery of a command to an agent re-checks `agent.invoke` with current rights and carries a fresh invocation token. This closes the command path of the M2 red-team item "another person triggering a personal subscription through every path" (T-AI-08), keeps control commands away from the model (R-AG-13, D-AG-12), and gives M2-17 (autocomplete) and M2-25 (app commands) the register they build on.

Product requirements implemented here:

11. The names of the built-in commands (`stop`, `status`, `new`, `resume`, `title`, `close`) are reserved: `command.register` refuses them with `409 conflict` and `reason: command_name_reserved`; built-in and other control commands never reach a model as a prompt (09 10.1, R-AG-13, D-AG-11, AG-24).
12. Registration: fields after 03 `commands` (`name`, `description` up to `command.description_max_chars`, `options` schema `command_options.v1`, `scope_kind` and target, `required_level`, `control`); a scope only on targets the owner serves or on which it has `write`; at most `command.max_per_principal` commands per agent or app; every change is `command.register` or `command.remove` with an audit entry and `command.changed` (09 10.2, 05 4.10 Audit `yes`, 11 3.2 point 5).
13. Visibility: `command.read` gives for a channel the commands of the operator, of guest agents only with `allow_mentioned_agents`, and of apps with `write` on the channel; with equal names the operator's come first, the others are qualified with the owner's handle on display (09 10.3, 03 `commands`, 05 4.10, 07 7.4 point 4).
14. Control commands (`commands.control = true`): `command.invoked` with an invocation token at once to the owner, also during a run; no run, never to the model, never a follow-up; an answer is optional and comes as a message of the agent (09 10.4, 04 15.4 point 6, 05 5 point 8, D-AG-12).
15. Model commands (`commands.control = false`): like a triggering message, a run `queued` and `agent.invocation` with trigger kind `command` and the parsed options; the run carries `trigger_kind = 'command'` and `triggering_command_id`; during an active run the invocation is refused with `run_active`, not turned into a follow-up (09 10.4, 03 `runs`, 05 5 point 8, 07 4.1, D-K-D20, E-AG-08).
16. Agent commands check `required_level` and `agent.invoke` (active human, `trigger`, operator or permitted guest, I2, SR2, project readiness); a refusal answers `403 agent_invocation_denied` with `reason`; refusals are audited (05 4.10 `command.invoke` Audit `denials`, 05 5, 06 4 points 6 and 7, 07 SR1, SR2, SR4).
17. Every delivery of `command.invoked` and of the `agent.invocation` of a command run re-checks `agent.invoke` for the invoking human with the rights of that moment and carries a fresh invocation token with `trigger_kind = command` and `command_id` (04 15.3 step 2, 05 5 claims, 05 6 row `command.invoked`, 07 8.1, R-SY-07).
18. A read-only or archived channel refuses every command for everyone, owners included (05 rule 1.8, R-AZ-12, 07 4.5).
19. Events: `command.changed` (resource `command` with its new version, receive action `command.read`, change `registered`, `updated` or `removed`) and `command.invoked` (resource `command` without version, audience the owner, receive action `agent.events.consume`); payloads without JSON `null` and below `sync.event_payload_max_bytes` (05 6, 04 2.2, 04 9 point 3, ADR 0053).
20. Rate-limit classes `rl.admin` (register, update, remove), `rl.read` (get, list) and `rl.trigger` (invoke); `Idempotency-Key` on `registerCommand` and `invokeCommand`; `If-Match` on `updateCommand`; `removeCommand` is idempotent (05 4.10, 06 7, 06 8).

1. **Ports and placement** (02 4.3, 4.6). `agents` owns the register; `runs` owns execution; `authz` owns every rights rule (05 rule 1.1).

    ```go
    // package agents
    // Commands is the register of slash commands (09 10, 03 commands).
    type Commands interface {
        Register(ctx context.Context, cmd RegisterCommand) (Command, error)     // command.register
        Update(ctx context.Context, cmd UpdateCommand) (Command, error)         // command.register, If-Match
        Remove(ctx context.Context, commandID ids.ID) error                     // command.remove
        Get(ctx context.Context, commandID ids.ID) (Command, error)             // command.read
        ListForChannel(ctx context.Context, channelID ids.ID) ([]Command, error) // command.read on the channel
        // Resolve returns the live command that is usable in the channel (scope covers it and no
        // more specific command of the same owner and name shadows it, note 9). It does not
        // authorize: the caller authorizes command.invoke. Unknown, removed, not covered or
        // shadowed gives the same not_found error.
        Resolve(ctx context.Context, commandID, channelID ids.ID) (Command, error)
    }
    type Command struct {
        ID, OwnerPrincipalID ids.ID
        OwnerKind            string // "agent" or "app" (principals.kind)
        Name, Description    string
        ScopeKind            string // "instance", "space", "channel"
        ScopeID              ids.ID // zero for instance
        Options              []CommandOption
        RequiredLevel        string // "write" or "trigger"
        Control              bool
        Version              int64
    }
    type CommandOption struct { Name, Description, Type string; Required bool; Choices []CommandChoice; Autocomplete bool }
    type CommandChoice struct { Name, Value string }
    type RegisterCommand struct { Name, Description, ScopeKind string; ScopeID ids.ID; Options []CommandOption; RequiredLevel string; Control bool }
    type UpdateCommand struct { CommandID ids.ID; ExpectedVersion int64; Definition RegisterCommand }

    // package runs
    // CommandExec executes slash commands (09 10.4).
    type CommandExec interface {
        Invoke(ctx context.Context, cmd InvokeCommand) (CommandInvocation, error)
    }
    type InvokeCommand struct { ChannelID, CommandID, ThreadID ids.ID /* zero: absent */; Options []OptionValue }
    type OptionValue struct { Name, Value string }
    type CommandInvocation struct { InvocationID, CommandID, ChannelID, ThreadID, RunID ids.ID /* RunID zero for control */ }
    ```

    The actor comes from the context, as in the other use cases. Port DTOs mirror the openapi schemas; domain types stay inside the modules.

2. **Migration.** Follow 03 `commands` literally, with one point the text leaves implicit: the unique partial index is `(owner_principal_id, lower(name), scope_kind, coalesce(scope_space_id, scope_channel_id)) NULLS NOT DISTINCT WHERE removed_at IS NULL`. Without `NULLS NOT DISTINCT` two live instance-scoped commands with the same name and owner would pass, because the `coalesce` is NULL for `instance` and PostgreSQL treats NULLs as distinct; 03 uses the clause for `stats_minutes` for the same reason. Ruling for docs/DECISIONS.md; the report lists it as a spec gap for 03. The FK of `runs.triggering_command_id` joins the same migration. Rows are never deleted by the product: removal sets `removed_at` (03 1 point 7 by analogy, FK from `runs`).

3. **Definition rules** (`agents/domain`, pure; codes of `errors[]` from M1-18's list plus `limit_reached` and `not_enabled` of 06 5; `detail` never repeats a submitted value):
   a. Name: the pattern of 03 and `CommandRegister` (`StageValidate` already rejects others). Reserved names: `stop`, `status`, `new`, `resume`, `title`, `close`, compared exactly (names are lower case by the pattern): `409 conflict` with `reason: command_name_reserved`. A unit test reads the first column of the table in 09 10.1 and compares it with the constant, so a new built-in fails the test until the list follows.
   b. Description: a plain string (Design note 17, ruling on the translation map), at least one rune that is not white space (`400`, `/description`, `too_short`), `kernel/textcheck.DisplayText` (control and bidi characters: `400`, `/description`, `invalid`, SEC-IN-4), at most `command.description_max_chars` Unicode characters (`400`, `/description`, `too_long`).
   c. Scope: `scope_kind` one of `instance`, `space`, `channel` (`TargetKind` also has `host`: `400`, `/scope_kind`, `invalid_enum`); `scope_id` absent for `instance` (`400`, `/scope_id`, `invalid`) and required for the others (`400`, `/scope_id`, `required`). Defaults when absent: `scope_kind = instance`, `options = []`, `required_level = trigger`, `control = false` (03 defaults).
   d. Options (`command_options.v1` is exactly the array of openapi `CommandOption`; Ruling for docs/DECISIONS.md): option names follow the command name pattern and are unique within the command (`/options/<i>/name`, `pattern_mismatch` or `invalid`); option descriptions follow rule b; `choices` only for `string`, `integer` and `choice` (`/options/<i>/choices`, `invalid`); a `choice` option needs non-empty `choices` or `autocomplete = true`; `autocomplete` only for `string`, `integer` and `choice`; each choice name follows rule b, each choice value is valid for the type (note 10 i) and unique; at most `command.autocomplete_max_choices` static choices per option (`too_many_items`), because the client shows them in the same list as the suggestions of the owner (09 10.5 point 4).
   e. Size: the encoded `CommandChangedPayload` of the command must fit `sync.event_payload_max_bytes`, else `400`, pointer empty, `too_large`. Reason: 04 2.2 rule 2, the appender rejects a too large payload, and a command whose change cannot be announced must not be stored. No key limits the number of options otherwise; `http.max_json_body_bytes` bounds the body.

4. **`Register`**, one unit of work (`txn.UnitOfWork.Do`; deadlocks retried by `database.tx_retry_max`):
   a. Definition rules of note 3 including the defaults of 3 c (`400`). They are pure and read no stored state, so they run before authorization without revealing anything; the scope facts of b come from the validated definition, because the guard of note 8 c knows only `instance`, `space` and `channel` with a scope ID.
   b. `authorize(actor, command.register, Resource{Kind: command, OwnerID: actor, Command: &CommandFacts{OwnerKind, ScopeKind, ScopeSpaceID or ScopeChannelID}})` with the facts of a (note 8). Humans get `403 forbidden` (`subject_kind_not_allowed`); an invisible or unknown scope target gives `404`; a visible target without the right of note 8 c gives `403 forbidden` (`level_insufficient`). Denials are audited by the authz layer (05 Audit `yes`, R-AZ-04). Then reserved names (`409`).
   c. Lock the owner's `principals` row through the identity port (`LockPrincipal`), then count the owner's live commands; at `command.max_per_principal` answer `400 validation_failed` with pointer empty and `errors[].code = limit_reached`. Reason: without the lock two parallel registrations at the limit both pass (READ COMMITTED, 03 1 point 11); the owner row serializes them for agents and apps alike (03 6.3 point 2).
   d. Insert with a new UUIDv7 and `version = 1`. A violation of the unique index answers `409 conflict` without `reason` (06 5 point 7: a reason only where one is defined; Ruling for docs/DECISIONS.md).
   e. Append `command.changed` (note 15) with change `registered`; audit through `auditing.Recorder.Record`: action `command.register`, decision `allow`, resource `command` and its ID, attributes `change` (`registered`), `scope_kind`, `scope_space_id` or `scope_channel_id`, `control`, `required_level`, `version`; never name, description, options or choices (SEC-AUD-5 allows no names and no free text; Ruling for docs/DECISIONS.md).
   f. Answer `201` with `Command`. A replay with the same `Idempotency-Key` is answered by the M1-20 middleware.

5. **`Update`** (`updateCommand`, PUT, `IfMatchRequired`): first the rules of note 3 on the new definition including the defaults of 3 c (`400`), before the command is loaded, so an invisible command and an unknown ID answer alike; then load the live command (missing or removed: `404`); first `authorize(actor, command.read, Resource{Kind: command, ID, OwnerID: stored owner, Command: facts of the stored command})` (visibility of note 8 b on what exists; `not_found` gives the same `404` as an unknown ID); then `authorize(actor, command.register, Resource{Kind: command, ID, OwnerID: stored owner, Command: facts of the validated new definition})` (another principal that sees the command gets `403 forbidden` with `not_self` or `subject_kind_not_allowed`; for the owner the target guard of note 8 c checks the new scope only, so an owner that lost the stored target can still move its command); `ParseIfMatch`: not equal to `version` gives `412 version_conflict` with `current` (`errs.VersionConflict`); reserved names (`409`); a definition identical to the stored one is a no-op (`200`, no write, no event, no audit; Ruling for docs/DECISIONS.md); otherwise compare-and-swap on `version`, `version + 1`, the unique index as in note 4 d, `command.changed` with change `updated`, audit as note 4 e with `change = updated`; `200` with `Command` and `ETag` (`FormatETag`). The owner and the ID never change.

6. **`Remove`** (`removeCommand`, DELETE): load including removed rows (unknown: `404`); `authorize(actor, command.remove, Resource{Kind: command, ID, OwnerID, Command: facts of the stored command})` (also for removed rows; not visible gives the same `404` as an unknown ID); a command already removed answers `204` without write, event or audit (06 7: DELETE of a deleted resource with a deletion mark); otherwise `removed_at = now()`, `version + 1`, `command.changed` with change `removed` and the command as it was with the new version, audit action `command.remove` with `change = removed`; `204`. Runs keep `triggering_command_id` (soft removal).

7. **`Get`** (`getCommand`): load the live command (removed or unknown: `404`), `authorize(actor, command.read, Resource{Kind: command, ID, OwnerID, Command: scope facts})`; `not_found` returns the same error value as an unknown ID (02 9.2); `200` with `Command` and `ETag`.

8. **Authorization in `authz`** (05 rule 1.1; M1-28 owns the function; this ticket extends it):
   a. `kernel/authorize`:

      type CommandFacts struct {
          OwnerKind          string // "agent" or "app"

   b. Visibility of the resource kind `command` (replaces the row of M1-28 ruling D4; add the bullet to 07 4.3; Ruling for docs/DECISIONS.md):

    - Without `OfferedInChannelID` (`getCommand`, `updateCommand`, `removeCommand`, `registerCommand`, and the receive check of `command.changed`, whose resource `ResourceFromEvent` builds from the event scope): visible when the principal is `OwnerID`, or is an effective owner, or sees the scope target: `read` on the channel for a channel scope, the space visible after 07 4.3 for a space scope, and any authenticated principal for the instance scope. The path comes from the scope facts, or from the event scope when there are no facts; the event scope of `command.changed` is therefore exactly the scope target (note 15). Reason: 05 2.6 calls command data metadata, and 04 7.2 already delivers events without scope to everyone before the per-event check. In request mode a missing `Resource.Command` on kind `command` is an internal error; only the filter-mode receive check takes the path from the event scope (same rule as M3-03 for `file`).
    - With `OfferedInChannelID` = C (per item of `listChannelCommands`): visible when the principal has `read` on C and the command is offered in C after 09 10.3: C is not a DM channel, the owner principal is active, and either the owner is C's effective operator; or the owner is an agent, C has `allow_mentioned_agents`, the owner's own effective level on C is at least `write` (operator rule included, 07 2.9) and its billing mode is `organization` (05 5 point 3, R-AZ-19); or the owner is an app with effective level at least `write` on C (07 2.10). The owner's level comes from the owner's snapshot without session, the same mechanism the `agent.invoke` guard of M1-28 uses for guests. The scope coverage is filtered by the caller's query (note 9) and checked here again.
   c. `command.register` guard (09 10.2 "Scope only on targets that the agent operates or on which it has `write`"; Ruling for docs/DECISIONS.md): `instance`: no further condition, because the list rule of b decides where an instance-scoped command appears; `space` S: S exists and is visible to the principal (else `not_found`), and the principal is S's default operator or has effective `write` on the space path (else `forbidden`, `level_insufficient`); `channel` C: C exists, is not a DM channel and is readable (else `not_found`), and the principal's effective level on C is at least `write` (operator rule included; else `forbidden`, `level_insufficient`). The requirement itself stays `Any(AgentSelf, AppSelf)` (M1-28 text mapping); the app scope `commands:write` is checked by M1-28's scope table.
   d. `command.read` requirement by kind: `ByKind{channel: Level(read), command: Auth}`; on `command` the visibility of b decides.
   e. `command.invoke`: replace `Deferred` with `CommandLevel` (new atom: `Level(r.Command.RequiredLevel)`; a missing `r.Command` or an unknown level is an internal error) and the guard: `OwnerKind == app` is an internal error until M2-25 replaces it (fail closed; no app owner can exist before M2-24); a model command (`Control == false`) with `ActiveRun` gives `forbidden` with `run_active` (07 4.1). The read-only rule of 05 1.8 applies through M1-28's generic step (`channel_read_only`, `channel_archived`). Remove `command.invoke` from the golden list of deferred actions; `command.autocomplete` stays deferred (M2-17).
   f. Tests in `internal/authz` with the M1-28 fakes, including the app Tracker of its test world for the app branch of b.

9. **List** (`ListForChannel`, 09 10.3, 07 7.4 points 3 and 4):
   a. Built-in commands are not part of the list (Ruling for docs/DECISIONS.md; update 09 10.3 and the description of `listChannelCommands`): `Command` requires `id`, `owner_principal_id` and `version`, which a built-in does not have (03 `commands` stores commands "by agents or apps"); each built-in maps to an action with its own operation (09 10.1 column "Action"), `/status` explicitly needs no server call, and their names and descriptions are translated in the client. The client shows the fixed list of 09 10.1 to everyone with `command.read` (M4-21). With this reading the clause "The control command `stop` additionally checks `run.cancel`" of 05 `command.invoke` holds by construction: `/stop` is `cancelRun`.
   b. `authorize(actor, command.read, Resource{Kind: channel, ID: C})` in request mode (route proof, 02 9.3); `not_found` gives the same `404` as an unknown channel.
   c. Query the live commands whose scope covers C (`instance`; `space` with C's space; `channel` with C; a DM channel is covered by no command, because agents never act in DMs, 05 5 point 2) and, per owner and lower-case name, keep only the most specific one (`channel` before `space` before `instance`; Ruling for docs/DECISIONS.md: two entries with the same owner handle could not be told apart, and the narrower registration states the owner's intent for that channel). `Resolve` applies the same rule.
   d. Per remaining command `authorize(actor, command.read, Resource{Kind: command, ID, OwnerID, Command: &CommandFacts{OwnerKind, ScopeKind, ScopeSpaceID, ScopeChannelID, OfferedInChannelID: C}})` in filter mode (`authorize.Filter(ctx)`); the result depends only on owner and C, so memoize it per owner within the request. A `not_found` here is the normal outcome of the list rule and not a `filter_mismatch`, because the query filters only by scope.
   e. Order (Ruling for docs/DECISIONS.md): the commands of C's effective operator first, then the others; within each group by lower-case name, then owner principal ID, then command ID. The client qualifies equal names of other owners with the handle (`/handle:name`, 03 `commands`). 09 10.3 speaks of the list "for a thread", but `listChannelCommands` has no thread parameter; "operator" here is C's effective operator as in the last paragraph of 03 `commands`.    f. `200` with `CommandList`; no paging and no totals (06 4 point 2); a DM channel gives an empty list.

10. **`Invoke`** (`invokeCommand`), one unit of work, in this order:
    a. `agents.Commands.Resolve(CommandID, ChannelID)`; not usable gives `404` with the same body as an unknown ID.
    b. Target thread: with `thread_id`, `chat.Threads.Info`; missing, or its channel is not `channel_id`, gives the same `404`. Without `thread_id`: in a forum channel, or in a text channel for a model command while the channel's `auto_thread` is set, first check `channel.read` on C in filter mode (an invisible channel gives the same `404`, 05 rule 2). Then answer `400 validation_failed` with pointer `/thread_id` and code `required`. Otherwise the target is the main thread of the text channel. Read `auto_thread` in this unit of work from the same channel switches the message acceptance of M2-05/M2-08 reads (`Switches.AutoThread`, `chat` port). Reason (Ruling for docs/DECISIONS.md; change the description of `CommandInvoke.thread_id` and 09 10.4 accordingly): 03 `channels.auto_thread` requires that a triggering in the main thread creates a thread, and 05 rule 6 counts a command as a triggering. 09 3.7 starts that thread from the triggering message (`parent_message_id = M`), and 01 and M1-55 let a text-channel thread grow only from a message. A command has no message, so a model command needs an explicit thread there. A control command creates no run, anchor or session (09 10.4), which is the only thing `auto_thread` places (09 3.7; same reason as M2-25). Its event therefore keeps the main thread.
    c. For a model command, lock the target thread row (`chat` port) before reading the active run, so the order of locks equals message acceptance (thread, then `runs`; 03 6.3) and the active-run fact cannot change before the run is opened.
    d. Facts: the active run of the target thread (any agent; this module's repository); the owner's agent facts (`agents` port); then `DecideCommand` of M2-04 with `CommandTrigger{CommandID, ThreadID, Owner, Control, ActiveRun}`.
    e. `authorize(actor, command.invoke, Resource{Kind: thread, ID: T, ChannelID: C, Command: &CommandFacts{OwnerKind, RequiredLevel, Control, ActiveRun}})` in request mode (route action, proof).
    f. For agent commands `authorize(actor, agent.invoke, Resource{Kind: thread, ID: T, Invoke: &InvokeFacts{AgentID: owner, TriggerOrigin: "human" for a principal of kind user (else its kind), MentionsAgent: true, ActiveRunAgentID: zero, NewThread: false}})` in request mode (06 4 point 7). Ruling for docs/DECISIONS.md: a command addresses its owner explicitly, like a mention, so the operator's commands work regardless of `require_mention` and a guest's only under the guest rule (`allow_mentioned_agents`, `write`, `organization`), which matches the list of 09 10.3; the active-run rule of 05 5 point 8 is applied by e, so guard 7 of M1-28 is not used for commands, and a control command reaches its owner during the run of any agent.
    g. Outcome mapping (06 4 point 6; Ruling for docs/DECISIONS.md): `not_found` of e or f gives `404`; `forbidden` with `channel_read_only` or `channel_archived` gives `403 channel_read_only` (M1-28 mapping); every other `forbidden` of e or f (`level_insufficient`, `run_active`, `agent_not_reachable`, `origin_not_human`, `billing_mode_personal_not_holder`, `tool_class_owner_only`, `project_not_ready`, ...) gives `403 agent_invocation_denied` with `reason` equal to the decision's reason. Reuse the mapping M2-09 added for `renewInvocationToken` if it exists. When `DecideCommand` rejects with `run_active` but e allows, fail closed with `403 agent_invocation_denied` and `reason: run_active` and log `command_decision_mismatch` without IDs (same rule as M2-05 ruling 14). The audit of every denial is written by the authz layer (05 Audit `denials`).
    h. Option values (note 10 i), then execution (notes 11 and 12), then `202` with `CommandInvocation{invocation_id, command_id, channel_id, thread_id, run_id (model only), accepted: true}`. `invocation_id` is a new UUIDv7 per accepted invocation; it is not stored in a table (03 has none) and appears as `invocation_id` in `CommandInvokedPayload` and as `command_invocation_id` in `AgentInvocationPayload`. `accepted` is always `true`; a refusal is an error response (Ruling for docs/DECISIONS.md). A replay with the same `Idempotency-Key` returns the stored `202` and writes nothing (M1-20).
    i. `ValidateOptionValues` (`runs/domain`, pure; Ruling for docs/DECISIONS.md): every required option present (`/options`, `required`, `detail` names the option, never a value); unknown option name (`/options/<i>/name`, `unknown_member`); an option twice (`/options/<i>/name`, `invalid`); per type: `string` after `kernel/textcheck.DisplayText` (`invalid`); `integer` the canonical decimal form of a signed 64-bit integer (`invalid_format`); `boolean` exactly `true` or `false` (`invalid_enum`); `choice` one of the static values unless `autocomplete` is set, then any `string` value (the owner validates; `invalid_enum`); `user` a UUID in canonical form, existence not checked because the check would reveal accounts and the owner resolves the ID with its own rights (`invalid_format`); `file` gives `not_enabled` until files arrive (06 5 point 3). The values keep the order of the definition. The encoded event payload of note 11 or 12 must fit `sync.event_payload_max_bytes`, else `/options`, `too_large`.

11. **Control command** (09 10.4 row `true`): append `command.invoked`: `scope {space_id, channel_id, thread_id}` of T, `resource {kind: command, id}` without `version` (04 9 point 3), `audience` the owner, `receive_action` `agent.events.consume` (catalogue), `actor` the invoker, `correlation_id` of the request; payload `CommandInvokedPayload{invocation_id, command_id, command_name, control: true, channel_id, thread_id, run_id, invoked_by, options}` where `run_id` is the owner's active run in T when there is one and absent otherwise (05 section 5 row `run_id`, R-AZ-25: the adapter learns which run the command concerns; token and payload carry the same value, 09 4.5 check point 6). Nothing else is written: no run, no anchor, no `run_followups` row, no `trigger_state`. An answer comes from the agent as a message (M2-19).

12. **Model command** (09 10.4 row `false`), in the locked unit of note 10 c:
    a. `Open(OpenCmd{ThreadID: T, AgentID: owner, TriggeredBy: actor, TriggerKind: "command", TriggeringCommandID: command ID, BillingModeExpected: the owner's current billing mode})` of M2-05, extended by `TriggeringCommandID`. No `trigger_state` changes, because the run has no triggering message (M2-05 note 4).
