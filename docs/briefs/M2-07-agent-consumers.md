# M2-07: Agent consumers over the gateway and REST

Status: ready | Depends on: M1-65 | Milestone: M2

## Goal

After this ticket an agent adapter reads the event log as a named consumer with a durable cursor, over the gateway WebSocket and over REST, exactly as 04 "Agent adapters" ("Connection and cursor", "Ack and redelivery") and 09 "Connection and cursor" require. Each pair of agent and consumer name owns one row in `agent_consumer_cursors`. The first connection of a consumer starts at `head_seq`, every later one at `acked_seq + 1`; at most `agent.max_inflight_events` unacknowledged events are on the way, then the server waits; an event that is not acknowledged within `agent.ack_timeout` comes again with the delivery field `redelivered: true`; `acked_seq` is saved at the latest after `agent.ack_persist_interval` and at shutdown. The newest consumer wins (R-SY-09): a second `identify` with the same consumer takes it over and closes the older connection with `4015`, and the fenced save of 03 keeps that rule true when the takeover happens in another server instance. The REST operations `getConsumerState`, `pollAgentEvents` and `ackAgentEvents` give adapters without a WebSocket the same stream with the same rules. Without this an adapter either misses events or works twice, and the invocation tokens of M2-08 have no reliable stream to travel on.

## Design notes

1. Placement (02 4.4, 4.6, 7.3). `agent_consumer_cursors`, `agent.events.consume` and the op `ack` belong to `agents`, so the cursor use cases, the three REST handlers and the registration of `ack` live there. Delivery belongs to the gateway (02 10: agent connections are consumers; invocation events go through `runs.Delivery` before sending), and `agents` may not use `sync` or `gateway`. Therefore one delivery engine in `gateway` serves both transports: the WebSocket directly and REST through the source port `agents.ConsumerFeed`, which `agents` declares and `gateway` implements (02 4.1 rule 4). The gateway reaches the table only through `agents.Consumers`. Ruling for `docs/DECISIONS.md`: one engine for both transports, so the window rules and the later hook of M2-08 exist once.
2. Table and fencing. The table is built exactly as 03, with `holder_session_id`. Every takeover writes the holder and every save of `acked_seq` is `UPDATE ... SET acked_seq = GREATEST(acked_seq, $acked), updated_at = now() WHERE agent_id = $1 AND consumer_name = $2 AND holder_session_id = $holder`; no row means another holder took over: `ErrConsumerReplaced`. This holds in both values of `cluster.mode`, because 03 states the conditional save without restriction and OQ-07 keeps the code node-neutral. Ruling for `docs/DECISIONS.md`: fencing is always on; M7-17 adds only the faster signal between nodes. These statements take no lock beyond their row and append no events, so they take neither `event_seq` nor `NOTIFY` (02 11.7, 03 6.3).
3. Consumer name. An agent's `identify` carries `consumer`, default `default` (04 6.3); a `resume` keeps the consumer of the resumed session (`GatewayResume` has no such member). A value that does not match the pattern of `ConsumerPath` closes the connection with `4002` (M1-64 note 3, frame does not match its schema; this ticket adds the pattern to `GatewayIdentify.consumer`). In REST the path parameter is checked by the chain: `400 validation_failed` with pointer `#path/consumer`. Consumers exist only for principals of kind `agent` (04 6.2 row `ack`, 6.4 row `4015`: "agents only"); for people and apps the member `consumer` is accepted and ignored, and their delivery stays as M1-65 built it. Ruling for `docs/DECISIONS.md`.
4. Agent sessions on the gateway. For an agent the durable cursor decides where delivery starts (04 15.1 point 4), so the gateway ignores `cursor` and `sync_epoch` of `identify` and `resume` and skips the client cursor check of M1-64 note 12 for agent sessions. Order after `ready` (the hub registration before reading `head_seq` stays as M1-64 note 11 and M1-65 built it), in `Delivery.Attach`, under a per-process lock per `ConsumerKey`:
    a. If this process holds the key in another gateway session, save that session's acknowledgement with `Save` (it still holds the row).
    b. `Take(consumer, holder = this gateway_session_id, head = ready.head_seq)`: authorizes `agent.events.consume`; creates the row with `acked_seq = head_seq` if absent (the first connection starts at `head_seq`, 04 15.1 point 2); otherwise writes the holder and keeps `acked_seq`. `forbidden` closes with `4018`, `unauthenticated` with `4012`, a database failure with `4000` (04 6.4 table).
    c. Close the older connection of step a with `4015`, reason `consumer_replaced`, and remove its gateway session from the store, so a later `resume` of it gets `4006`. Drop a REST window of the key in this process. Log one INFO record with agent id, consumer and both session ids; no audit entry (05: Audit `no`).
    d. Start the runner with `acked = acked_seq` (note 5).
   A `resume` keeps the gateway session id and therefore the holder; it restarts the runner from the session's in-memory acknowledgement. If the resumed session's old connection is still open, it closes with `4015` (another process took over the same consumer), not `4017`, because agent connections have no device (M1-64 note 15). Ruling for `docs/DECISIONS.md`: steps a to d, the session end after `4015`, and the ignored client cursor.
5. Delivery window (`gateway/domain`, pure). State: `acked` (highest acknowledged), `read` (highest `seq` checked by this window), `inflight` (dispatched durable events with `seq > acked`, each with the time it was queued), `redeliverUpTo`, `highestSent`, the phase (backlog or live) and the count of skipped numbers since the last frame that carried a `seq`.
    - Budget: `agent.max_inflight_events` minus the number of inflight entries; at zero the runner reads nothing and waits (04 15.2 point 2).
    - Reading: a page after `read` up to the bound of note 6. Of the admitted events at most the budget is dispatched; if the page was cut, `read` becomes the `seq` of the last dispatched event, otherwise the last checked `seq` of the page.
    - Ack: `seq > acked` sets `acked`, drops inflight entries up to `seq` and raises `read` to `acked` if it was lower; acknowledging is cumulative (04 15.2 point 1).
    - Timeout: the deadline is the queue time of the oldest inflight entry plus `agent.ack_timeout`. When it passes, `redeliverUpTo = max(redeliverUpTo, highestSent)`, `read = acked`, inflight is emptied, and reading restarts from `acked + 1` (04 15.2 point 3). An event dispatched again with `seq <= redeliverUpTo` carries `redelivered: true`; an event never dispatched before in this window does not. A new `identify` or `resume` starts a fresh window without the flag. Ruling for `docs/DECISIONS.md`: the flag marks exactly the ack-timeout redeliveries, as `EventEnvelope.redelivered` describes; the deadline runs from the oldest unacknowledged dispatch.
    - Frames: while the window is in the backlog phase it sends `cursor {seq: read}` after every page whose `read` is above the last `seq` it sent, so an adapter can acknowledge past events it may not see (R-SY-03); when `read` first reaches `head_seq` of `ready` it sends `catchup.complete {head_seq}` once and enters the live phase; live it sends `cursor` whenever the skipped numbers reach `sync.cursor_advance_every` (04 7.1, 7.2 point 4, as M1-65 does for people). Ruling for `docs/DECISIONS.md`: a consumer connection always catches up from `acked_seq + 1` and ends that catch-up with `catchup.complete`.
    - Resync: at start the runner calls `CatchUp.Check` with `after = acked`. `retention` (events after `acked` were removed) and `cursor_ahead` (only after a restore without reset) send `resync_required {reason, head_seq, sync_epoch}`, set the cursor to that `head_seq` with `Restart`, and continue live from there without `catchup.complete`, as M1-65 does after `resync_required`. `too_far_behind` does not apply to consumers: the backlog is delivered through the window, because agent events are commands and the window already bounds the load; `epoch_changed` cannot occur, because the client epoch is ignored and the restore resets agent cursors (04 7.5 point 4, M7-04). Ruling for `docs/DECISIONS.md`.
    - Purge: when the queue purge of M1-65 drops dispatch frames of a removed target, the window drops their numbers from inflight so they hold no budget; the next `cursor` frame lets the adapter acknowledge past them.
6. Runner (`gateway/app`). One goroutine per consumer connection. The hub does not queue durable `dispatch` frames for agent sessions; after each event it wakes their runners with a non-blocking, coalescing signal. The runner reads pages with the sync port in `authorize.Delivery(ctx)` mode (M1-65), page size `sync.catchup_page_size`, upper bound the hub position: the highest `seq` the process's log tail has passed through `Authorizer.Observe` and `Hub.Dispatch`. Reason: every admission then happens with a permission cache that has seen every `access.changed` up to that event (04 8.1, R-SY-02), and a full window makes the runner wait instead of filling a buffer that would close the connection with `4014`. Envelopes carry `DeliveryFields{IncludeTraceContext: true, Redelivered: ...}` (M1-16, M1-63). The runner waits for queue space like the catch-up runner of M1-65 and retries a failing page read with backoff capped at `database.listen_reconnect_backoff_cap` while the connection is open (02 14.4). The `access.changed` handling of M1-65 (revalidation with `4012`, index update, purge) applies to agent sessions unchanged. Ruling for `docs/DECISIONS.md`: consumer connections pull from the log up to the hub position.
7. `DeliveryHook` (outgoing port of `gateway/app`): `Prepare(ctx context.Context, agentID ids.ID, ev sync.Envelope) (sync.Envelope, bool, error)`. Every dispatch to a consumer, on both transports, passes it; `false` means "do not deliver, treat as checked". This ticket binds `passdelivery`; M2-08 binds `runs.Delivery` there (02 10).
8. Acknowledgement rules (both transports; `agents/domain.CheckAck`): `seq` below 0 or above the head of note 9 is `validation_failed` (pointer `/seq`); `seq` at or below the stored or held acknowledgement changes nothing and is no error (06 2 "No effect"; monotone, 06 7); otherwise the acknowledgement advances. Acknowledging beyond what was dispatched is allowed and skips those events, because an acknowledgement covers every number up to `seq` (04 15.2 point 1). Gateway op `ack {seq}`: the dispatcher handler calls `agents.Consumers.AcceptAck` (authorize `agent.events.consume`, then `CheckAck`), then applies the acknowledgement to the session's window and marks it dirty; nothing is written yet; no reply frame (asyncapi `receive.ack` has none). Errors answer `error {op: "ack", code}` and keep the connection (04 6.2): `validation_failed`, `forbidden` (people and apps, `subject_kind_not_allowed`), `rate_limited` for class `rl.agent_runtime` (06 9 point 3; if the merged dispatcher has no per-op rate limit yet, apply the class to `ack` with `platform/ratelimit`, keyed by the agent). Ruling for `docs/DECISIONS.md`: the upper bound and the "no change" rule.
9. Head and saving. The head that consumer operations report and check acknowledgements against is the hub position of the serving process (note 6); only a gateway connection creates a missing cursor at the `head_seq` of its own `ready` (note 4 b), because that is the head the client was told. Ruling for `docs/DECISIONS.md`: a consumer never acknowledges or is told about a `seq` this process cannot yet deliver. Saving: a process-wide ticker with interval `agent.ack_persist_interval` calls `Save` for every consumer session whose held acknowledgement is above its last saved value. `ErrConsumerReplaced` closes that connection with `4015` and ends the session (the takeover happened elsewhere, 04 15.1 point 3); other errors keep the session dirty for the next tick (log WARN). Flush with `Save` also before a takeover in this process (note 4 a), when a connection detaches or closes for any reason (including `4012` and `4014`), and in step 3 of the shutdown before `CloseAll(4013)` within the remaining `shutdown.total_timeout` budget (02 15.3). Acknowledgements made after the last successful save of a connection that loses the row are lost; those events come again (at least once, 04 9; the adapter deduplicates by event ID, 04 15.2 point 4).
10. REST operations (`agents/app`, each first `authorize(actor, agent.events.consume, {kind: agent, id: actor, owner: actor})`, class `rl.agent_runtime`):
    - `getConsumerState`: the stored row; `404 not_found` if this consumer never connected (reading does not create a cursor; 04 15.1 point 2 creates it at the first connection). Answer `ConsumerState {consumer, acked_seq, head_seq}` with `head_seq` from `ConsumerFeed.Head`.
    - `pollAgentEvents`: delegates to `ConsumerFeed.Poll`. The engine keeps one REST window per `ConsumerKey` in the process with its own holder id (a UUIDv7 created with the window). Per call, under the per-key lock: flush and close a gateway session of the key in this process with `4015` (note 4 a and c); `Take(consumer, holder = REST holder, head)` (the first poll creates the cursor at `head_seq` and returns an empty page); reconcile the window with the stored `acked_seq` (drop inflight entries up to it); apply the timeout rule of note 5; resync check as note 5, where `retention` and `cursor_ahead` move the cursor to `head_seq` with `Restart` and answer `410 resync_required` with `reason`; otherwise read up to the budget, where `limit` defaults to `agent.max_inflight_events` and larger values are capped to it (06 6 point 3). Answer `EventPage {events, next_cursor, head_seq, sync_epoch}` with `next_cursor` = the window's `read` (the adapter acknowledges it after processing, also when `events` is empty). Within `agent.ack_timeout` a poll never repeats inflight events; it only continues after them while the budget allows. A REST window idle for `sync.resume_window` is dropped by the sweeper; the next poll starts a fresh window from `acked_seq + 1`. Ruling for `docs/DECISIONS.md`: a REST poll is a consumer like an `identify` (the newest wins, R-SY-09), the per-process window, the idle rule, and `410` for `retention` and `cursor_ahead`.
    - `ackAgentEvents`: head from `ConsumerFeed.Head`, `CheckAck`, then `AckConsumer` (`acked_seq = GREATEST(acked_seq, $seq)` immediately, without holder condition, `404 not_found` for an unknown consumer), then `ConsumerFeed.Acked` so a window of the key in this process sees it; answer `ConsumerState`. Neither `getConsumerState` nor `ackAgentEvents` takes the consumer over. Ruling for `docs/DECISIONS.md`.
11. Permissions. The descriptor of note 10 makes `AgentSelf` decide (M1-28): an agent passes for itself; a person or app token gets `403 forbidden` with `reason: subject_kind_not_allowed` and no row is created. `Take` and `AcceptAck` use the same descriptor. Denials are audited by `authz` (R-AZ-04); admission of events in the runner and the REST poll runs in delivery mode and writes no audit entry (07 4.2, AZ-P13). No permission version, no `access.changed`, no event of any kind is written by this ticket (05: Permissions `no`).
12. Errors (06 5; codes only from `x-problem-codes`):

| Situation | REST | Gateway |
|---|---|---|
| `consumer` does not match the pattern | `400 validation_failed`, pointer `#path/consumer` | `identify` closes with `4002` |
| caller is not an agent | `403 forbidden`, `reason: subject_kind_not_allowed` | `ack` answers `error` with `forbidden`; `consumer` ignored at `identify` |
| consumer never connected | `getConsumerState`, `ackAgentEvents`: `404 not_found` | not applicable (`identify` creates) |
| `seq` below 0 or above the head | `400 validation_failed`, pointer `/seq` | `error` with `validation_failed` |
| `seq` at or below the acknowledgement | `200` with the current state | nothing |
| `limit` below 1 | `400 validation_failed`, pointer `#query/limit` | not applicable |
| `retention`, `cursor_ahead` | `410 resync_required` with `reason`; cursor moved to `head_seq` | `resync_required {reason, head_seq, sync_epoch}`; cursor moved |
| class `rl.agent_runtime` exhausted | `429 rate_limited` with `Retry-After` | `error` with `rate_limited` |
| another consumer took over | not applicable | older connection closes with `4015` |

13. Concurrency. One runner goroutine per consumer connection owns the window; the reader goroutine passes acknowledgements to it (channel or the window's mutex), and the save ticker reads the held value under the same lock. A per-process lock per `ConsumerKey` serializes takeovers by `identify`, `resume` and REST polls. Across processes the last `Take` wins and the loser learns it at its next save (fencing); an acknowledgement through `ackAgentEvents` in another process is monotone and cannot lower `acked_seq`. Two consumer names of the same agent never affect each other.

Configuration keys used: `agent.ack_timeout`, `agent.ack_persist_interval`, `agent.max_inflight_events` (registered by this ticket), `sync.catchup_page_size`, `sync.cursor_advance_every`, `sync.resume_window`, `sync.outbound_queue_max`, `gateway.write_timeout`, `database.listen_reconnect_backoff_cap`, `shutdown.total_timeout`, `ratelimit.rl.agent_runtime.per_minute`, `ratelimit.rl.agent_runtime.burst`.
15. Rulings for `docs/DECISIONS.md` (one row each with reason and place): note 1 (one engine, `ConsumerFeed`); note 2 (fencing always on); note 3 (pattern, agents only); note 4 (takeover order, session end after `4015`, client cursor ignored, `4015` on resume); note 5 (flag and deadline, catch-up with `catchup.complete`, resync reasons for consumers); note 6 (pull up to the hub position); note 8 (upper bound, no change at or below); note 9 (head of the serving process); note 10 (REST takeover, window, idle rule, `410`, no takeover by state and ack).
