# M2-31: Conformance suite with the Fake-Agent

Status: ready | Depends on: M2-13, M2-15, M2-17, M2-18, M2-19, M2-20, M2-27, M2-29 | Milestone: M2

## Goal

After this ticket the mandatory agent scenarios of 09 "Required scenarios" run data driven against the real server in every `make check`. Each test ID AG-01 to AG-32 has one scenario file under `services/server/test/agents/scenarios/`; a Go conductor in `services/server/test/agents` starts the real server in the process (shared harness of M1-71, own PostgreSQL 18 through `pgtest`, fake clock), acts for the people through the public API, checks the stored state, and drives one or more Fake-Agent processes. The Fake-Agent is the scriptable adapter of 09 "Test doubles": built on the Python SDK of M2-29 (module `bothy_sdk.testing.fake_agent`, the plan's `sdk/python/testing`), it connects as a named consumer of its agent, verifies invocation tokens with the SDK, keeps an inbox, acknowledges, reads the context, starts, patches, waits, resumes, renews and finishes runs, sends heartbeats, posts answers and cards, registers commands and reports sessions, and on command plays the faults the scenarios need: a wrong `base_version`, an expired or forged token, a wrong actual mode or tool class, a crash after accepting, a slow start. Only the public API lies between the two sides (ADR 0022 "Confirmation"). Why: M2-04 to M2-20 proved the adapter contract module by module with Go test clients; this suite proves it end to end with a real SDK on the other side, it is M2 exit criterion 1, and it is the conformance check that RK-09 promises for every adapter. Parts of a scenario that need a ticket of a later milestone (a message of origin `import` in AG-01, attachments and transcripts in AG-20, voice messages in AG-25) are held in a golden list of deferred parts with the ticket that brings them; nothing is skipped.

- This brief was written before milestone M1 closed (D-W-100). Where the merged code of an M1 ticket names a package, type, function, file or make target differently from this brief, follow the code and list each difference in the report; where it behaves differently from the specification, stop with `Verdict: BLOCKED <reason>`.

- Tokens are passed only in memory (control pipe, conductor variables); the conductor's failure messages, the captured stderr of the Fake-Agent and the scenario files never contain a token, a signature, an API token or a DPoP key (print the first hex characters of the SHA-256 of the `jti` when a token must be named).

## Design notes

1. **Start check.** Run `make check` on the fresh worktree; if it is red, stop with `Verdict: BLOCKED base branch red` and the failing gate. Then confirm on the base branch: `services/server/test/harness` with `Start` and `BuildMatrixWorld` (M1-71); the operations `startRun`, `resumeRun`, `renewInvocationToken`, `awaitRunInput`, `finishRun`, `cancelRun`, `patchRun`, `getRunContext`, `createInteraction`, `bindAgentSession`, `reportAgentSession`, `autocompleteCommand`, `answerAutocomplete`, `registerCommand`, `setThreadTitle`, `sendHeartbeat`, `installApp` and `postIncomingWebhook` under `enabled` in `services/server/api/operations.yaml`; `sdk/python/src/bothy_sdk` with the hand-layer modules of 11 11.2 and the FakeServer in `bothy_sdk.testing` (M2-29). A missing one ends with `Verdict: BLOCKED dependency <ticket> missing`.

2. **Architecture.** Ruling for docs/DECISIONS.md: the conductor is Go and the Fake-Agent is Python. The Go side owns what only it can own: the real server in the process with its fake clock, `pgtest`, the matrix world of M1-71, the jobs, the database checks and the response validator of M1-31. The Python side is what 09 16.1 demands: an adapter on the SDK. One Fake-Agent process per agent and consumer of a scenario, started with `uv run --project <repository root>/sdk/python --locked --quiet python -m bothy_sdk.testing.fake_agent`; the repository root is found by walking up from the test directory to the directory that holds `sdk/python/pyproject.toml`. If M2-29 already built a Go-side runner that starts the real server for its own real-server tests, extend it instead of building a second one and list it in the report. If a linter flags the start of the subprocess (the program is `uv` from `PATH`, the arguments are constants and repository paths), add a suppression at that line with this reason, never a global exclusion.

3. **Scenario files** (`scenarios/ag-NN.yaml`; parsed with the YAML library already in `services/server/go.mod`, strict decoding with known fields only; if the module has no YAML library, the files are JSON with the same structure and the extension `.json`, and no dependency is added). The format is defined by the Go types in `scenario_test.go` and their `Validate` method and documented in the README; there is no separate schema file. Top-level keys:
    - `id` (exactly the file's ID), `title` (the English row text of 09 16.2), `sources` (chapter references such as `09 16.2`, `04 15.5`), `world` (`matrix`), `config` (dotted keys of `docs/operations/configuration.md` with test values; every key the scenario advances the clock by must be set here), `setup` (steps run before the first case), `agents` (name to `{agent, consumer, transport, runtime, launch}`; `transport` is `rest` or `gateway`; `launch` is `start` (default) or `later`; `runtime` gives the actual billing mode, billing evidence, loaded tool class, reported capabilities and the adapter options `adapter.invocation_token_leeway` and `adapter.jwks_refresh_min_interval`), `cases` (named lists of steps; each case runs on its own server and world unless the scenario sets `shared_world: true`), `matrix` (only AG-02 and AG-12: rows of values substituted into the steps, each row with its literal expected outcome), `deferred` (parts with ticket and reason, Design note 13).
    - Step kinds, exactly one per step: `as: <person>` (or the subjects `tracker` and `webhook` of Design note 10) with `call: <operationId>` and `with` (a call through that subject's client); `agent: <name>` with `do: <op>` and `with` (a Fake-Agent op, Design note 5); `server:` one of `advance_clock` (`by: <key>`, moves by that key's configured value plus one smallest tick of the fake clock), `run_jobs` (`kind: <job kind>`), `snapshot_cursors` (`keep: <name>`, the stored rows of `agent_consumer_cursors`), `restart` (optional `restore_cursors: <name>`), `proxy` (`drop_next: <operationId>`); `check:` one of `run`, `runs`, `message`, `followup`, `component`, `interaction`, `session`, `thread`, `events`, `audit`, `consumer` (Design note 4); `parallel:` a list of steps released together behind a barrier; `repeat: {times, steps}`; `await: <name>` with an `expect`, which waits for a human call that an earlier step started with `async: <name>` (a call that blocks inside the server, such as `autocompleteCommand`).
    - `expect` on every call and op: `status`, `code`, `reason`, `errors` (list of `{code, pointer}`), `none` (no event of a type arrived), `one_of` (alternatives), and op-specific fields (`event`, `verdict`, `redelivered`, `trigger_kind`, `session_mode`); `keep` binds names to IDs from answers (`run: r1`, `message: m1`, `token: t2`) for later steps (`$r1`). Names of people, agents, spaces, channels and threads are the world's names.
    - Expectations are literal data. AG-02 lists all its rows with the expected outcome written out from 09 3.4; nothing in the suite calls `Decide` of M2-04 or any other server function to compute an expectation.

    Example (illustrative, AG-14):

    ```yaml
    id: AG-14
    title: Stop without an adapter answer
    sources: ["09 16.2", "09 8", "04 15.5"]
    world: matrix
    config: {agent.cancel_grace: <test value>}
    agents:
      lotse: {agent: Lotse, consumer: default, transport: rest}
    cases:
      main:
        - as: alex
          call: createMessage
          with: {thread: support-allgemein-1, content: "@lotse please check the export"}
          expect: {status: 201}
          keep: {message: m1}
        - agent: lotse
          do: receive
          expect: {event: agent.invocation, verdict: valid}
          keep: {run: r1}
        - agent: lotse
          do: start
          with: {run: $r1}
          expect: {status: 200}
        - as: alex
          call: cancelRun
          with: {run: $r1}
          expect: {status: 202}
        - server: advance_clock
          by: agent.cancel_grace
        - server: run_jobs
          kind: runs.cancel_timeout
        - check: run
          run: $r1
          expect: {state: cancelled, state_reason: cancel_timeout}
        - agent: lotse
          do: patch
          with: {run: $r1, ops: [{op: replace, path: /status_line, value: "still here"}]}
          expect: {status: 409, code: conflict, reason: run_not_active}
    ```

4. **Conductor.** Executes the steps of a case in order on a fresh `harness.Start` with `Options{Config: scenario config, Clock: a fake clock, ManualJobs: true, PublicOrigin: the origin of the case's fault proxy}` (Design note 9) and the world of Design note 10.
    - At the start of each case it starts the Fake-Agent process of every entry in `agents` and runs `hello` and `connect`, so every consumer's cursor exists before the first trigger (04 15.1: the cursor starts at `head_seq` on the first connection). An entry with `launch: later` (a restarted adapter in AG-10, a second process) is started by a step `agent: <name>` with `do: launch`, which runs `hello` and `connect`.
    - Human calls go through the harness client of that person (DPoP, `Idempotency-Key`, step-up for the Owner where the operation needs it); every response is validated with the response validator of `services/server/test/apitest` (M1-31) and must contain no JSON `null`.
    - Checks read the stored state through `AdminDB()` with read-only SQL: `runs` (`state`, `state_reason`, `version`, `trigger_kind`, `triggered_by`, `agent_session_id`, `billing_mode_used`, and `started_jti`, `invocation_jti`, `renewed_from_jti` compared only by their hash prefix), `messages` (`origin`, `kind`, `system_code`, `trigger_state`, `trigger_state_reason`), `run_followups`, `message_components`, `interactions`, `agent_sessions`, `threads` (`title`, `title_source`, `parent_message_id`, `operator_agent_id`), `event_log` (`type`, `audience_principal_id`, `resource_kind`, `resource_id`, order by `seq`, count), `audit_events` (`action`, `decision`, `deny_reason`, keys of `details`), `agent_consumer_cursors`. Reads go through `AdminDB`, also for history and audit rows, although the history and audit reads (M1-57, M1-50) are in this ticket's closure; every read names its table and column as 03 does.
    - Asynchronous effects (a delivery over the gateway, a reconnect after a restart) are awaited by polling the condition until it holds or the test's deadline (`t.Deadline()`) is reached; no other wait exists, and no step waits for a window of the specification in real time.
    - A failed expectation names the scenario, case, step index, the expected and the observed value (codes, states, counts), never a token or a body that could contain one.
    - Cases run with `t.Parallel()`; `pgtest` starts one container per test binary and clones a database per case. The package must finish within the default timeout of `go test`, because the `Makefile` line stays as it is; if it does not, first let the cases of one file share their world (`shared_world: true`) where they touch different threads, and report the wall time either way.

5. **Fake-Agent** (`bothy_sdk.testing.fake_agent`; public API of the module documented with google-style docstrings, rendered by M2-29's MkDocs reference).
    a. Control protocol: JSON lines on stdin (requests `{id, op, args, now}`) and stdout (replies `{id, ok, result}` or `{id, ok: false, error: {kind, detail}}`); the first request is `hello` with `base_url`, `gateway_url`, `agent_id`, `consumer`, `transport`, `runtime`, the adapter options and the credentials (Design note 6). Every request carries `now`, the harness clock as RFC 3339 UTC with milliseconds; the Fake-Agent sets its SDK clock to it before it acts. Logs go to stderr at level `WARNING` and never contain a token, a credential or message content; stdout carries only replies.
    b. Ops (each through the SDK hand layer; a request the hand layer would never send, such as a forged, empty or absent token, a stale `base_version` or a start past the adapter's own checks, goes through the generated core `bothy_sdk.generated` directly):

    | Op | Effect | Result fields |
    |---|---|---|
    | `connect` | register the consumer before the first trigger of a case (REST: a first `pollAgentEvents`, which creates the cursor and returns an empty page; gateway: `identify`), so its cursor starts at `head_seq` (04 15.1) | `head_seq` |
    | `receive` | consume until an event of the requested type arrives or the consumer reached `head_seq` (REST: `pollAgentEvents` pages; gateway: dispatch frames); verify its token with the SDK (`invocation`), store event and token in the inbox (newest token wins for the same event, 09 4.3) and acknowledge, unless `accept: false` or the verdict forbids it (09 4.5: unknown `kid` after one reload is neither accepted nor acknowledged); `hold: true` keeps the event unverified and unacknowledged until a later `verify` of it | `event`, `seq`, `redelivered`, `run_id`, `thread_id`, `message_id`, `interaction_id`, `command_id`, `trigger_kind`, `session_mode`, `verdict`, `jti_hash`, or `none` |
    | `start`, `resume` | `startRun` or `resumeRun` with the newest inbox token of the run, or the token named in `token` (`inbox`, a kept name, `empty`, `absent`, `forged:<variant>`), with `billing_mode_used`, `tool_class_used`, `billing_evidence` and `model` from the runtime or overridden | `status`, `code`, `reason`, `run_state`, `replay` |
    | `renew` | `renewInvocationToken` with the named token; on success the new token goes into the inbox; option `retry: false` sends this one call through a client whose `SdkSettings.retry_max_attempts` is 1, so a dropped answer is reported as `error {kind: transport}` | `status`, `code`, `reason`, `jti_hash` |
    | `context` | `getRunContext`; per element `message_id`, `role`, `trust`, `truncated`, byte length; the SDK helper composes the prompt with marked blocks (ADR 0054), and the Fake-Agent reports for every element with `trust` other than `trigger` and `self` whether its text occurs only inside a marked block | `trigger_complete`, `elements`, `truncated_before_seq` |
    | `patch` | `patchRun` (REST) or op `run.update` (gateway) with `ops`; `base_version: stale` sends the version before the last stored change; the SDK's rebase after `409 base_version_conflict` runs unless `rebase: false` | `status`, `code`, `errors`, `current_version` |
    | `await_input`, `finish` | `awaitRunInput`; `finishRun` with `state`, `reason`, `summary` | `status`, `code`, `reason` |
    | `heartbeat` | `sendHeartbeat` with `active_runs` (default: the runs it holds), `capabilities`, reported mode, evidence and tool class from the runtime | `status` |
    | `post` | `createMessage` or `createThread`, plain or as a card (the SDK `components` builders, the approval card of 09 11.5) | `status`, `code`, `reason`, `message_id`, `component_ids` |
    | `respond`, `update_component`, `set_title`, `report_session`, `register_commands` | `respondToInteraction`, `updateComponent`, `setThreadTitle` (with the `ETag` of `getThread`), `reportAgentSession` (with `If-Match`), `registerCommand` through the SDK's declarative command list | `status`, `code`, `reason` |
    | `autocomplete_mode` | `answer` with given choices, or `ignore` (receive `command.autocomplete_requested`, report it, never answer) | `requested` |
    | `verify` | SDK verification of a named token without any request; for a held event, acceptance and acknowledgement then follow the verdict as in `receive` | `verdict` |
    | `export_token`, `import_token` | hand a token of this agent's inbox to the conductor, or take one into the inbox (AG-08 foreign `aud`, AG-32 lost answer) | `jti_hash` (and `token` only in `export_token`) |
    | `crash` | exit at once with a non-zero status, no `finishRun`, no flush | none |

    c. Verdicts of `verify` and `receive`, mirroring M2-06's reference verifier: `valid`, `expired`, `invalid`, `unknown_key`, `billing_mode_mismatch`, `tool_class_mismatch`, `replay`.
    d. Well-behaved default (09 4.9): after `receive` with verdict `invalid`, `billing_mode_mismatch` or `tool_class_mismatch` the Fake-Agent starts nothing and calls `finishRun` with `failed` and the matching reason (`invalid_invocation_token`, `billing_mode_mismatch`, `tool_class_mismatch`); a step with `skip_own_checks: true` sends the start anyway through the generated core (AG-11, AG-30 server parts).
    e. Token variants of `forged:<variant>` (`token_faults.py`): `bad_signature` (one byte of the signature changed), `alg_hs256`, `alg_none` (header re-encoded), `typ_access` (header `typ` of an access token), built from the run's current token; `empty` is an empty string; `absent` leaves the member out.
    f. SDK hook (Scope, Change): if the merged SDK has none, add a keyword argument `clock` (a callable returning an aware `datetime`, default the system clock) to the invocation verifier and its JWKS cache, used for expiry, `iat` and `max-age`, documented as a test hook; the default keeps M2-29's behaviour.

6. **Credentials.** The conductor reads the agent's API token, and its DPoP private key when the harness bound the token to one, through `(*Client).AgentCredentials()` and sends them only in `hello` on stdin; never in `argv` or the environment of the process. Ruling for docs/DECISIONS.md: credentials of a test double travel only over its stdin.

7. **Time and jobs.** One fake clock per case (the harness clock). The conductor advances it only between steps, after the previous step's effects were observed; the Fake-Agent follows through `now`. Jobs never run by themselves: `Options.ManualJobs` keeps the job runtime from working jobs, and `run_jobs` calls `(*Server).RunDueJobs(kind)`, which runs every due job of that kind (scheduled at or before the harness clock) through its registered handler in `id` order, or a periodic kind (`runs.stall_check`, `instance.key_rotation`) once. Ruling for docs/DECISIONS.md: jobs in the suite run only on request, because River's own scheduling follows the wall clock while the server follows the fake clock. Kinds used: `runs.cancel_timeout`, `runs.stall_check` (M2-09), `runs.queued_expiry` (M2-08), `instance.key_rotation` (M1-32).

9. **Fault proxy** (`proxy_test.go`). Every Fake-Agent talks to the server through one reverse proxy per case on `127.0.0.1` port 0 (REST and the WebSocket upgrade of the gateway), whose upstream transport is the loopback client of M1-22 (`egress.NewLoopback`) with the case's value of `http.request_timeout`. It keeps the Fake-Agent's base URL stable across `restart` (it switches its upstream and closes open WebSockets, so the SDK reconnects) and serves `proxy: {drop_next: <operationId>}`: the next matching request is forwarded, the server's response is read completely and kept in memory for the conductor (`keep: {token: t2}` takes the token of an `InvocationTokenGrant`), and the client connection is closed without an answer. This is the "fake proxy" of AG-32. Before `harness.Start` the conductor opens the proxy listener on `127.0.0.1:0` and starts the server with `Options.PublicOrigin` set to the proxy origin, which the harness also sets as `server.public_url`, because the server builds the DPoP `htu` from `server.public_url` (08 7.3, M1-18) and every client signs the URL it calls. Every client of the case (the people through the harness, `tracker`, `webhook` and every Fake-Agent, REST and gateway) goes through the proxy; its upstream is `(*Server).ListenURL()`. `restart` keeps `server.public_url`; the proxy switches only its upstream.
