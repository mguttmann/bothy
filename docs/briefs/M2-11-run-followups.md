# M2-11: Follow-ups with steer and queue

Status: ready | Depends on: M2-10 | Milestone: M2

## Goal

After this ticket a human message that would trigger the agent of the thread's active run becomes a follow-up of that run (`run.followup.create` through `createMessage`) instead of a second run: a row in `run_followups` with state `queued` and `trigger_state = received` on the message. When the agent's effective capability `followups` is `steer`, the server writes the personal event `agent.followup`, which M2-08 delivers with a fresh invocation token after re-checking `agent.invoke` for the follow-up's author; the adapter acknowledges `delivered` (the message shows `followup_delivered`) and then `absorbed` through a run patch, forward only. With `queue` or without the capability the server sends nothing, except to a run in `waiting_input`, where the follow-up is the answer to the open question and resumes the run with the token of its delivery. When the run ends, every follow-up still `queued` or `delivered` without `absorbed` becomes `deferred`, and the first of them, in thread order, triggers a new run whose follow-ups are the rest; after a stop by a person (`cancelled` with `user_cancelled`) they become `discarded` and nothing runs. This is 09 "Follow-ups during a run" and AG-13: people can add to a running turn without losing what they wrote, a stop really stops, and no follow-up of another person ever reaches an agent on a personal subscription.

11. Only a message that would trigger the agent of the thread's active run becomes a follow-up; a message without a trigger (no `trigger`, mention rule not met) stays a normal message and reaches the agent only as context of the next run; a message for another agent is rejected with `run_active_other_agent`; control commands are never follow-ups (09 7, 09 3.4 point 6; 04 15.4 points 1 and 6; 05 5 point 8; R-SY-22, D-K-D34).
12. `run.followup.create`: resource `thread`, right "write and `agent.invoke`" (so I2, SR2 and SR4 hold for every follow-up), Audit `denials`, class `rl.message` through `createMessage`, no route of its own (05 4.10; 06 4 point 7). It replaces the deferred entry of M1-28.
13. A follow-up is one row in `run_followups` (`state = queued`, unique per message) and `trigger_state = received` on its message (03 `run_followups`; 09 6; 04 15.4 point 1).
14. The effective capability `followups` is the owner's permission `supports_followups` (absent means allowed) and the adapter's report `steer` or `queue` (09 2.2, R-AG-01). With `steer` the server writes the personal event `agent.followup` (payload `run_id`, `thread_id`, `message_id`, never content); with `queue` or none it sends nothing and the follow-up stays `queued` until the run ends (09 7; 04 2.2 rule 4, 15.4 point 1).
15. A follow-up to a run in `waiting_input` is the answer to the open question: the adapter hands it over and resumes the run with the token of its delivery (`resumeRun`, action `run.start`) (09 7 last paragraph, 5.1; 04 15.3 point 5, 15.4 point 5; R-AG-08).
16. The adapter acknowledges `delivered` (handed to the runtime) and `absorbed` (taken up by the runtime) through `run.update` on `/followups/<message_id>/state`, forward only; at `delivered` the message gets `trigger_state = followup_delivered` (09 4.7, 5.3; 04 15.4 point 3; 01 6.2).
17. At the end of a run every follow-up in `queued` or `delivered` without `absorbed` becomes `deferred` after `completed`, `failed`, and `cancelled` with any reason other than `user_cancelled`; the first becomes the triggering message of a new run and the rest its follow-ups; after `cancelled` with `user_cancelled` they become `discarded`, and the message shows "not processed, run stopped" (09 7, 8 point 5, 15; 04 15.4 point 4; 03 `runs.triggering_message_id`; R-AG-10, D-AG-09).
18. Every delivery of `agent.followup` re-checks `agent.invoke` for the follow-up's author with the rights of that moment and carries a fresh token with `trigger_kind = followup` and the follow-up message as `message_id`; a denial delivers nothing and never ends the run of another person (04 15.4 point 2, 15.3 point 2; R-SY-07; 05 5 claims; 07 8.1).
19. The run document lists the follow-ups keyed by message id with their state (09 5.3 and 5.4; 04 11.1; openapi `Run.followups`, `RunFollowup`).
20. No follow-up of another person reaches an agent on a personal subscription: I1 keeps `trigger` with the holder and I2 is part of every check of this ticket (05 5 point 4; 07 SR1; T-AI-08; OQ-01; M2 Red Team).

## Design notes

1. **Placement.** Follow-ups belong to `runs` (02 4.2 and 4.3; `modules.yaml` lists `run_followups`, `run.followup.create` and `agent.followup` there). Pure rules live in `internal/runs/domain`; the service `Followups` in `internal/runs/app` uses the unit of work of its caller (`txn`, never its own `Do` when called from a subscriber, the end-of-run function or `Prepare`). Other modules are reached only through their ports: `messaging` (`SetTriggerState`, message facts), `chat` (`Threads.Info` for scope), `agents` (capability, status), `authz` through `kernel/authorize`. No other module changes a follow-up state (Ruling for docs/DECISIONS.md, `D-M2-11-1`).

2. **Domain rules** (table tests in Tests):
    - `EffectiveFollowupMode(permitted, reported)`: `none` when `permitted` is false; otherwise `steer` or `queue` when `reported` is exactly that value; `none` for an absent or unknown report (fail closed, 09 1 point 4). `permitted` nil means the key is absent in `operator_config`, which allows (09 2.2).
    - `FollowupEventNeeded(mode, runState)`: true for `steer` in `queued`, `running` and `waiting_input`; true for `queue` and `none` only in `waiting_input` (requirement 15); false for every end state.
    - `AdvanceFollowup(from, to)` for adapter patches: `queued -> delivered`, `queued -> absorbed`, `delivered -> absorbed` change; `to == from` for `delivered` or `absorbed` is no change (06 2 "No effect"); every other pair (backward, or out of `deferred` or `discarded`) is `ErrFollowupTransition`, which wraps `errs.CodeInvalidStateTransition`. `to` other than `delivered` or `absorbed` never reaches here (M2-10's value check).

3. **Acceptance of a follow-up** (in `OnMessagePosted`, inside the unit of work of `createMessage`):
   a. The active run of the target thread is read with `SELECT ... FOR UPDATE` before M2-04's `Decide` is called, so the fact stays true until the commit (the thread row lock of `createMessage` already serializes messages of one thread, M1-55; the run row lock serializes against the end of the run). If the merged acceptance reads it without a lock, add the lock.
   b. `Decide` returns `followup` with `RunID` and `Check = CheckFollowUp` (M2-04). Where M2-05 and M2-08 return without writing (M2-05 note 6 step 3, M2-08 note 10 e), continue here. `ErrActiveRunExists` from `Open` (a concurrent acceptance created the run, M2-05 note 6 step 7) leads here as well when the active run belongs to the candidate.
   c. Check `authorize(P, run.followup.create, Resource{Kind: thread, ID: thread of M, Invoke: &InvokeFacts{AgentID: run.agent_id, TriggerOrigin: human, MentionsAgent: the decision's Mentioned, ActiveRunAgentID: run.agent_id}})` in the same mode and with the same audit pattern the merged acceptance uses for `agent.invoke` (M2-08 notes 8 and 10 d: one deny entry with `stage = acceptance`), with action `run.followup.create` in the entry.
   d. Denial: map the reason with the acceptance mapping of M2-08 note 10 d (for example `level_insufficient` without mention writes nothing, with mention `no_trigger_right`; `billing_mode_personal_not_holder` stays) and call `Messages.SetTriggerState(M, failed, reason)`; no row, no event.
   e. Allow, in this order: `INSERT INTO run_followups (run_id, message_id)` (state `queued`); `UPDATE runs SET version = version + 1` (note 10); `Messages.SetTriggerState(M, received)`; read the effective mode (note 15); when `FollowupEventNeeded(mode, run.state)`, append `agent.followup` (note 4). Nothing else happens to the run: its state, `invocation_jti` and `billing_mode_expected` change only at a delivery (M2-08).
   f. A replay of `createMessage` publishes no `MessagePosted` (M1-56), so it creates no second row; the unique `(message_id)` is the last line.
   Ruling for docs/DECISIONS.md (`D-M2-11-2`): the mode is evaluated once at acceptance under the run lock; a follow-up to a `waiting_input` run gets its event also with `queue` or without the capability, because 09 7 makes it the answer and only a delivery's token can resume the run (R-AG-08); a follow-up written while the run was `queued` or `running` with `queue` is not delivered later, even if the run then waits for input (it was not an answer).

4. **Event `agent.followup`** through the payload builder of M2-08 (note 14): `eventlog.Event` with type `agent.followup`, `schema_version` from the event register, actor P, scope `{space_id, channel_id, thread_id}` of the run's thread now (`chat.Threads.Info`), resource `{kind: run, id: run_id}` without version (04 9 point 3; actions.yaml `resource_version: false`), `AudiencePrincipalID = run.agent_id`, receive action from the catalogue (`agent.events.consume`), the request's `correlation_id`, payload `AgentFollowupPayload {run_id, thread_id, message_id}`: no content, no prompt, no JSON `null` (04 2.2 rules 1 and 4, ADR 0053). The token is never in the log row (R-SY-17); M2-08 adds it per delivery.

5. **Acknowledgement by the adapter** (implementation of M2-10's port `FollowupStates`, called inside M2-10's patch unit of work with the run row locked):
    - `States(runID, messageIDs)`: the stored states; ids that are not follow-ups of this run are absent, so M2-10 answers `patch_target_missing`.
    - `Set(runID, messageID, to)`: lock the row (`FOR UPDATE`), `AdvanceFollowup`; on change `UPDATE run_followups SET state = $to, updated_at = now()`; when the row leaves `queued` (to `delivered`, or straight to `absorbed`), `Messages.SetTriggerState(message, followup_delivered)`, which writes `message.updated` (02 4.7). `absorbed` after `delivered` changes no `trigger_state`.
    - `ErrFollowupTransition` reaches the client as `409 invalid_state_transition` (06 2 "No effect"); if the merged patch use case turns every port error into `400 validation_failed`, add this exception and its test. The patch is all or nothing.
    - The `message.updated` of `followup_delivered` is a durable event inside a patch: its count is bounded by the number of follow-ups, not by the patch rate, so R-SY-05 and M2-10's load test still hold.
   Ruling for docs/DECISIONS.md (`D-M2-11-3`): the forward-only transitions including `queued -> absorbed`, no change on the same state, `409 invalid_state_transition` for every other pair, and `followup_delivered` when a follow-up first leaves `queued`.

6. **Delivery of `agent.followup`** (the row `agent.followup` of M2-08's matrix; M2-08 note 3 f leaves "the state of the `run_followups` row" to this ticket):
    - `ForDelivery(runID, messageID)` gives the facts for M2-08's resolver: author (the trigger, `sub` of the token), origin, mention of the run's agent, and whether the follow-up is deliverable. Deliverable means the row exists for this run in `queued` or `delivered` and the message is not deleted; otherwise `Prepare` returns `Send = false` without check, token or audit (the event counts as checked, M2-07 `DeliveryHook`), like a terminal run in M2-08's matrix. Ruling for docs/DECISIONS.md (`D-M2-11-4`).
    - Denial (M2-08 note 3 f: the message gets `failed` with the mapped reason of M2-08 note 6, audit, counter, run unchanged): `RefuseDelivery(runID, messageID)` sets the row to `discarded`, `updated_at = now()`, and raises `runs.version` by one (note 10), in the same unit of work. Reason: the follow-up will never be processed, and `run_followups` has no `failed` state; `trigger_state = failed` shows the reason. Ruling for docs/DECISIONS.md (part of `D-M2-11-4`).
    - Allow: nothing changes here; M2-08 issues the token with `trigger_kind = followup`, `message_id` = the follow-up and `sub` = its author, and records the `jti` only while the run waits in `waiting_input` (M2-08 note 2, 09 5.1). A delivery of `agent.followup` never sets `trigger_state = queued`: 09 6 sets `queued` only for `agent.invocation` (M2-08 note 12). If the merged resolver takes `sub` from `runs.triggered_by` or sets `queued` for follow-ups, correct it and list it.

7. **End of a run** (`OnRunEnded`, called at the extension point of M2-09's end-of-run function, in the same unit of work, after the transition with `version + 1` and `run.state_changed`; every path to `completed`, `failed` or `cancelled` passes there: `finishRun`, `cancelRun` on a `queued` run, the job `runs.cancel_timeout`, `runs.stall_check` with `interrupted` and `stale`, `OnAgentDisabled`, M2-08's denial of a queued invocation and its expiry `runs.queued_expiry`; route any path that bypasses it through it):
   a. Lock the open follow-ups: `SELECT ... FROM run_followups WHERE run_id = $1 AND state IN ('queued','delivered') ORDER BY message_id FOR UPDATE` (03 6.3). None: return.
   b. Load their facts through `messaging` (author, `thread_seq`, deleted). `PlanRunEnd`: a follow-up whose message is deleted goes to `Deleted`. End `cancelled` with reason `user_cancelled`: every other open follow-up goes to `Stopped`. Every other end: all others go to `Candidates` ordered by ascending `thread_seq` (04 4; Ruling for docs/DECISIONS.md, `D-M2-11-5`). `absorbed`, `deferred` and `discarded` rows are never touched.
   c. `Deleted`: `state = discarded`, no `trigger_state` change (note 9). `Stopped`: `state = discarded`; `Messages.SetTriggerState(message, cancelled, user_cancelled)`. Reason: the message must show "not processed, run stopped" (09 7), 09 6 defines `cancelled` as "Run stopped" with the reason in `trigger_state_reason`, and 03 lists `user_cancelled` as such a reason. Ruling for docs/DECISIONS.md (part of `D-M2-11-5`).
   d. Defer: `state = deferred` for all candidates; then the follow-on run of note 8.
   e. No extra `runs.version` step and no `run.updated` for the ended run: the follow-up changes are part of the stored change of the final transition, and clients load the ended run per REST (04 11.3 point 6).
   This is literal 09 7: `cancelled` with `cancel_timeout`, `access_revoked`, `agent_disabled`, `channel_read_only` or `user_disabled` defers; `failed` with `interrupted` or `stale` defers (09 15). Deferred follow-ups are new, unprocessed requests (09 7 "Reason"), so a follow-on run is no retry of the failed run's own trigger (R-AG-17 holds). The surprise after a stop that ends with `cancel_timeout` is a spec gap (reported), not changed here.

8. **Follow-on run** (04 15.4 point 4; 03 `runs.triggering_message_id`), in the same unit of work, for the candidates in order:
   a. For candidate M with author P: `authorize` with the re-check principal of M2-08 note 4 for P (P is not the actor of this unit), action `agent.invoke`, `Resource{Kind: thread, ID: run.thread_id, Invoke: &InvokeFacts{AgentID: run.agent_id, TriggerOrigin: origin of M, MentionsAgent: M mentions the agent, ActiveRunAgentID: zero}}` (the ended run is no longer active), in the mode and with the audit pattern of M2-08's delivery check (note 8, attribute `stage = run_end`). Reason: the follow-on run is an acceptance of M as a trigger (09 3.4 point 7); without the check a run would be created for a disabled agent or in a read-only channel.
   b. Denial: `state = discarded`; `Messages.SetTriggerState(M, failed, reason)` with the reason mapping of M2-08 note 6; continue with the next candidate.
   c. Allow: M is the trigger. Create the run through the invoke step of the acceptance (M2-05 `Open` with `TriggerKind = message`, `TriggeringMessageID = M`, `TriggeredBy = P`, `AgentID = run.agent_id`, `ThreadID = run.thread_id`; the anchor; `SetTriggerState(M, received)`; job `runs.queued_expiry`; `agent.invocation` last, M2-08 note 10 f). M's row stays `deferred` on the ended run.
   d. The remaining candidates after M become follow-ups of the new run: `UPDATE run_followups SET run_id = <new>, state = 'queued', updated_at = now()` (one row per message; 03 unique `(message_id)` allows no second row), `Messages.SetTriggerState(message, received)` (a no-op when already `received`, M2-05 ruling 17); when `FollowupEventNeeded(mode, queued)` (mode read now), append `agent.followup` for each, in `thread_seq` order, after the new run's `agent.invocation`. Ruling for docs/DECISIONS.md (`D-M2-11-6`): the first stays `deferred` on the ended run, the rest move.
   e. No candidate allowed: no run; all candidates are `discarded` with `failed` on their messages.
   f. The new run is an ordinary run: its own end runs this note again, so the process ends after at most one run per open follow-up. `ErrActiveRunExists` cannot occur, because the ended run is no longer active and the thread's acceptances wait at the run row lock (note 12); treat it as an internal error.

9. **Deleted follow-up message** (`OnMessageDeleted(messaging.MessageDeleted)`, in the deleting unit of work; M1-58 is not in this ticket's closure: if `MessageDeleted` is not on the base branch, leave this subscriber out and name it as a follow-up in the report; notes 6 and 7 treat a deleted message as not deliverable and discard it at the end in any case): if the message has a row in `queued` or `delivered`, lock the run row, set the row `discarded`, raise `runs.version` (note 10); no `trigger_state` change (the tombstone keeps its representation, 03 `messages`). Reason: deleted content must never become the trigger of a new run, and redaction (03 6.5) would leave the adapter an empty text. Ruling for docs/DECISIONS.md (`D-M2-11-7`; spec gap reported). A deleted triggering message of an active run is not handled here.

10. **Run document and versions.** The projection of M2-05 fills `followups` with every row of the run (`{message_id, state}` keyed by message id; rows moved to another run belong to that run). `runs.version` "rises with every stored change" (03) and the document contains the follow-ups (09 5.3, 04 11.1), so every server-side change of a follow-up of an active run raises `runs.version` by one: acceptance (note 3 e), refused delivery (note 6), deletion (note 9). The adapter's next patch then meets `409 base_version_conflict` and rebases on `current` (04 11.2; the SDK handles it, M2-29). These server-side changes publish no `run.updated`: they happen inside the unit of work of another use case, and `run.updated` may only leave after a commit (M2-10 note 1h). Focused clients see the follow-up at once through `message.created` and `message.updated` (`trigger_state`), and the box catches up with the next frame of the run, which M2-10's coalescer sends as a snapshot after a version step without patch (M2-10 note 9), or with `getRun`. Ruling for docs/DECISIONS.md (`D-M2-11-8`). The adapter's own acknowledgement goes out as `run.updated` through M2-10.

11. **Rights** (05 4.10, 07 2.3, M1-28):
    - Requirement of `run.followup.create`: `All(Level(write), Level(trigger))` plus the `agent.invoke` guard of M1-28 with the descriptor's `Invoke` (required, else internal error); mapping row "write and `agent.invoke`" in the requirement source table. `Level(trigger)` is what "`agent.invoke`" requires (05 4.10 row `agent.invoke`); `Level(write)` is kept so the requirement reads like the catalogue.
    - Guard step 7 passes because `ActiveRunAgentID` equals the agent; another agent's active run gives `run_active_other_agent` (05 5 point 8). I2 (`billing_mode_personal_not_holder`), SR2 (`tool_class_owner_only`), SR4 (`origin_not_human`), `channel_read_only` and the project checks apply unchanged.
    - Remove `run.followup.create` from the deferred entries and from the golden list of `TestDeferredActionsGolden`. The action has no route (06 4 point 7), so AZ-P1 is unaffected; no rights version, no `access.changed` (05: Permissions `no`).
    Ruling for docs/DECISIONS.md (`D-M2-11-9`): the expression and the mapping row.

12. **Locks and concurrency** (03 6.3, 02 8.2): acceptance holds the thread row (M1-55), then the run row (note 3 a), then inserts the follow-up, then updates `messages`. The end of a run holds the run row (M2-05 `Transition`), then the follow-up rows in ascending `message_id`, then `messages`, and for a follow-on run the thread row through the anchor. An acceptance and the end of the same run can therefore deadlock; PostgreSQL detects it and the unit of work retries the whole unit up to `database.tx_retry_max` (02 8.2). Every interleaving ends in one of two consistent outcomes: the follow-up exists before the end (it is settled by note 7) or the message comes after the end (it triggers a new run or becomes a follow-up of the follow-on run). Never a `queued` follow-up on an ended run. `Set` (note 5) runs under M2-10's run row lock; `Prepare` (note 6) under M2-08's.

13. **Trigger state of a follow-up message** (09 6; every change through `Messages.SetTriggerState`):

    | Moment | `trigger_state` | `trigger_state_reason` |

    | accepted as follow-up | `received` | |
    | refused at acceptance | `failed` | acceptance mapping (M2-08 note 10 d) |

    | moved to the follow-on run | `received` | |
    | refused as trigger of the follow-on run | `failed` | delivery mapping (M2-08 note 6) |

    Update the diagram and table of 09 6 with the edges `followup_delivered -> received`, `followup_delivered -> failed`, `received -> cancelled` and `followup_delivered -> cancelled` for follow-ups.

14. **Queries, audit, telemetry.** Reads of `run_followups` have no visible-channel predicate by design (03 gives the table no `channel_id`): each reads the rows of one run (or one message) whose run was authorized in the same use case or is being changed by it (07 7.4 rule 1, exception "loading a resource that has already been checked"; the rule M2-05 note 10 wrote into 07 7.4). Name them in the runs README and, if the lint file exists, under `after_authorize` (Scope). Audit: only denials (`denials`), written as described in notes 3 c, 6 and 8; allowed follow-ups and state changes write none. No new metric (signals.md has none for follow-ups); M2-08 counts delivery denials. No log line, span, audit detail or problem body contains message content or a token.

15. **Effective capability source** (09 2.2): the owner's `operator_config.supports_followups` (M1-51) and the adapter's reported `capabilities.followups` from the heartbeat (`reported_details`, schema `agent_heartbeat.v1`, 09 4.8; written by `sendHeartbeat` of M2-20, which may hold newer state in memory between persists, 03 `agents`). ## Acceptance criteria

- [ ] Migration `run_followups` matches 03 (columns, CHECK, PK, unique `(message_id)`, cascading FKs, index) and has its line in `migrations.sha256`.
- [ ] AG-13 with `steer`: a follow-up during a run is a `queued` row with `received`, `agent.followup` is written and delivered with a fresh token (`trigger_kind = followup`, `sub` the author), the adapter's `delivered` and `absorbed` change the row forward only.
- [ ] `followup_delivered` in the trigger state: the patch to `delivered` sets `trigger_state = followup_delivered` with one `message.updated`.
- [ ] AG-13 with `queue` (and without the capability): nothing is sent; at the end of the run the open follow-ups become `deferred`, the first in thread order triggers a new run, the rest are its follow-ups.
