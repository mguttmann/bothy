# M2-27: Incoming webhooks native and alertmanager

Status: ready | Depends on: M2-05, M2-24 | Milestone: M2
## Goal

After this ticket an external system writes into exactly one channel of the instance through an incoming webhook, without a session or an API token of its own. A person with `manage` on the channel creates the webhook for an installed app that has `write` there (step-up, audit) and receives its URL with a `bothy_whi_` token exactly once; the server keeps only the HMAC. The sender posts either with `Authorization: Bearer <token>` or with the token as the last path segment, in the format `native` (Markdown with optional `thread_id`, `title` and `client_msg_id`) or with the unchanged webhook payload of Prometheus Alertmanager, which the server turns into one message per notification. The checks run in the order of 11 8.4 (`rl.webhook_in`, token, body size, format, `authorize` of the app), and every refusal of the token or of the app's rights looks like an unknown webhook (`404`). The message lands in the thread chosen by the rules of 11 8.3, carries `origin = app` with the app as author, resolves no mentions and never triggers an agent (AZ-M53, SR4). The path token appears in access logs, traces and `Problem.instance` only as the route pattern. A cron job that sends `native` with one `client_msg_id` per run gets exactly one message per run however often it retries (11 10.4), and the instance's own Alertmanager reaches the same routes on the internal listener (16 4.2), which M7-20 then configures. This builds the two built-in inbound formats of R-EX-08 and the cron and alarm paths of requirement 19 (11 section 10, PLAN block "reference integrations").

Product requirements implemented here:

11. `createIncomingWebhook` (`webhook_in.create`: `manage` on the channel, step-up, Audit `yes`, `rl.admin`, `Idempotency-Key`) creates a webhook for one channel that always writes as its app (`incoming_webhooks.app_id`) with `write` on the channel, optionally with a fixed thread. The answer carries the URL with the token exactly once; only `token_hash` (HMAC-SHA-256 with the server pepper) is stored; a replay of the same `Idempotency-Key` answers `409 conflict` with `reason: one_time_secret` (11 8.1, 05 4.11, 03 `incoming_webhooks`, 08 12, ADR 0061, 06 7).
12. A call is a `POST` with `Authorization: Bearer <token>` or with the token as the last path segment. An unknown webhook, a wrong token and a revoked webhook give the same `404` (11 8.1, R-EX-09, 06 1 and 3).
13. Order of checks (11 8.4): `rl.webhook_in` (`429 rate_limited`), token (`404 not_found`), body up to `webhook_in.max_body_bytes` (`413 payload_too_large`), format switched on and valid (`400 validation_failed`), `authorize` of the app (`404 not_found`), then the message and `201` with `message_id`.
14. Formats `native` and `alertmanager` only, switched by `webhook_in.formats_enabled` (11 8.2, R-EX-08). `native` with `client_msg_id` is idempotent: a repeat answers `200` with the original and `Idempotent-Replay: true`, other content `422 idempotency_key_reuse` (06 7, 04 5.1). `alertmanager` gives one message per notification with state, count, `alertname`, a summary per alert from labels and annotations, and `generatorURL` and `externalURL` as text (11 8.2).
15. Target thread: the fixed thread of the webhook, else `thread_id` of the body when the thread belongs to the channel, else a new thread with `title` (required in forums), else the main thread of the text channel (11 8.3).
16. The message has `origin = app` and the app as author, resolves no mentions and never triggers an agent; content up to `message.max_content_bytes`; no attachments on this path (11 8.4, 03 `incoming_webhooks`, 07 2.10 and SR4, 05 5 point 1, R-EX-09; AZ-M53).
17. Rate-limit class `rl.webhook_in` per webhook. The path token appears in access logs, traces and `Problem.instance` only as the route pattern `/api/v1/hooks/{webhook_id}/{token}` (05 3, 06 5 point 1, 19 SEC-LOG-3, 08 12).
18. `listIncomingWebhooks` (`webhook_in.read`, `manage`, never a token) and `revokeIncomingWebhook` (`webhook_in.revoke`, `manage`, step-up, Audit `yes`; a second revoke has no effect, 06 2 "No effect") (05 4.11).
19. Uninstalling the app revokes its incoming webhooks; suspending keeps them (11 4.3), and a post is refused while the installation is not `active` (07 4.1 `app_not_installed`).
20. Senders inside the stack (Alertmanager) reach the same routes on the internal listener, in every role (16 4.2, 02 3.2).
21. No JSON `null` in answers; every answer validates against `openapi.yaml` (ADR 0053).

- No real Alertmanager, Prometheus or other third-party service in tests: the Alertmanager payloads are fixtures built from the structure documented in 11 8.2 (evidence retrieved 2026-10-10) with white-label values. No model call of any kind.
- Tokens never appear in logs, problem bodies, audit details, event payloads or test failure messages; tests build tokens at runtime, and every committed token-shaped value (openapi examples, fixtures) carries the marker `EXAMPLE` in its random part (CONTRIBUTING.md, M1-44).
- Time only through `kernel/clock`; tests move a fake clock and never sleep for a window.
- A mutation used to prove a red run is never committed.

## Design notes

0. **Start check.** `make check` is green on the fresh worktree, else `Verdict: BLOCKED base branch red`. Check before writing code that the base has (all are in the dependency closure; the check guards against a capability the merged code lacks, while a differing name follows Boundaries): `internal/platform/ratelimit` with `rl.webhook_in` keyed by the path value `webhook_id` and the failed-credential hook (M1-19); the tables `channels` and `threads` (M1-53, M1-55); `createMessage`, `createThread` and `MessagePosted` (M1-56); `apps` and `app_installations` with an uninstall use case (M2-24); the acceptance subscriber `runs.OnMessagePosted` (M2-05). A missing one ends the ticket with `Verdict: BLOCKED dependency <id> missing`.

1. **Routes and order of checks.** Two operations serve posts, with the same action `webhook_in.post`, class `rl.webhook_in`, exemption `client_id` and request body: `postIncomingWebhook` on `POST /api/v1/hooks/{webhook_id}/{token}` (`security: []`) and `postIncomingWebhookWithBearer` on `POST /api/v1/hooks/{webhook_id}` (`security: bearerAuth`). Ruling for docs/DECISIONS.md: the Bearer variant of 11 8.1 and 10.3 is its own operation, because one operation cannot have two paths and the plan row asks for both. A request passes, in this order, which is the order of 11 8.4 placed into the chain of 02 9.1:
   a. Stages 1 to 6 as for every route (M1-18). `StageRoute` sets the body limit of these two operations to `webhook_in.max_body_bytes` instead of `http.max_json_body_bytes`.
   b. `StageAuthenticate`: for every operation whose action is `webhook_in.post` the identity authenticator is not called and the actor stays anonymous, whatever `Authorization` holds (the token of these routes is not an API token; M1-44 would reject kind `whi` with `401`).
   c. `StageRateLimit`: `rl.webhook_in` keyed by the path value `webhook_id` (M1-19); exhausted gives `429 rate_limited` with `Retry-After`, before any database access and for unknown IDs too.
   d. `StageWebhookToken` (new, Design note 2): token check; failure gives `404 not_found`.
   e. `StageMaintenance`, `StageIdempotency` (the exemption `client_id` skips it), `StageBody` (`413 payload_too_large` naming `webhook_in.max_body_bytes`, `400 malformed_request`), `StagePreconditions`, `StageValidate` (`400 validation_failed`, unknown members included), `StageProof`.
   f. Handler: classification and format switch (`400 validation_failed`, Design note 4), body rules per format, target thread (Design note 5), `authorize` (Design note 3, every denial gives `404 not_found`), write (Design note 6), `201` with `IncomingWebhookResult`, or `200` with `Idempotent-Replay: true` on a replay.
   Ruling for docs/DECISIONS.md: the token check is a chain stage between the rate limit and the body stages, so it runs after `rl.webhook_in` and before any body is read or validated, exactly as 11 8.4 orders it; 02 9.1 gets the new step.

2. **Token check** (`StageWebhookToken`, middleware in `internal/apps/adapters/httpapi`, installed by `internal/wire`). It acts only on operations with action `webhook_in.post`; others pass through.
   a. Token source: `postIncomingWebhook` takes the path value `token` and ignores `Authorization`; `postIncomingWebhookWithBearer` takes `Authorization` and accepts exactly the scheme `Bearer` with one token. A missing or other scheme counts as a wrong token.
   b. `identity.Tokens.HashIncomingWebhookToken`: a malformed value fails without a database call. Otherwise `AuthenticateIncoming` loads the webhook by the path value `webhook_id` with its app's installation that is not `uninstalled` (`GetIncomingForAuth`) and compares `token_hash` with `hmac.Equal`. Unknown ID, wrong hash, `revoked_at` set, no installation or an installation in state `suspended` all give the same `404 not_found` (11 8.1, 4.3; 07 4.1 `app_not_installed`). A known and an unknown ID take the same path (one HMAC, one indexed lookup), so AZ-P4 timing holds.
   c. A failed check is a failed credential (02 9.1, 05 3): it takes one token from `rl.public_auth` of the client IP through the hook M1-19 gave `StageAuthenticate`. At the start of the stage, while that bucket of the client IP is empty, the stage answers `429 rate_limited` without checking the token, as `StageAuthenticate` does for other credentials. A failed check writes no audit entry (it is authentication, not an `authorize` decision).
   d. Success replaces the anonymous actor with the webhook actor (Design note 3) and stores the verified webhook ID for the handler. The handler uses the path value only after checking it equals the stored ID.

3. **Webhook actor and rights.** Ruling for docs/DECISIONS.md: the actor of a verified post is the app principal (`ID` = `incoming_webhooks.app_id`, `Kind` app) with `InstallationID` of its active installation, `GrantedScopes` = the installation's `granted_scopes` intersected with `messages:write`, and no `TokenID`, `SessionID` or `DeviceID` (the fields of M1-28; M2-24 fills the same fields for app tokens). Reason: a stolen URL may only post into its channel (T-TK-03); `message.create` and `thread.create` need exactly `messages:write` (05 2.6).
   a. Ruling for docs/DECISIONS.md: the requirement of `webhook_in.post` is `All(AppKind, Level(write))` on the resource `{kind: channel, id: incoming_webhooks.channel_id}`; it needs no scope (05 2.6, already in M1-28's scope table). An anonymous principal gets `unauthenticated` (fail closed; 07 4.2 step 1 allows anonymous only for the right `public`, and this right is "public with token; the app needs write").
   b. The use case calls `authorize(webhookActor, webhook_in.post, channel)` on every post, also on a replay (02 9.3 proof). Then the messaging use case authorizes `message.create` (and `thread.create` for a new thread) for the same actor, which brings the scope check, the read-only check (05 rule 1.8) and the archive rule (07 4.5).
   c. Every outcome other than `allow` of these three checks (`not_found`, `forbidden` with any reason including `scope_missing`, `channel_read_only` and `channel_archived`, `unauthenticated`) becomes `404 not_found` with exactly the body and headers of an unknown webhook (11 8.4: decision "authorize app: message.create on the channel", branch "no" to `404`). Internal errors stay `500 internal_error`.
   d. Audit: denials of `webhook_in.post` are written by the authz layer (Audit `denials`, aggregated per `audit.deny_aggregate_window`, R-AZ-04); `message.create` has Audit `no`; an allowed post writes no audit entry.

4. **Formats and body rules.** Ruling for docs/DECISIONS.md: the format is decided per request from the body, not stored per webhook. Reason: 03 `incoming_webhooks` has no format column (core contract), openapi has no format member, and one closed request schema must cover both shapes because `rule/oneof-needs-discriminator` forbids a `oneOf` without discriminator and the Alertmanager payload has no discriminator member. The request body stays one schema, `IncomingWebhookPost`, with the native members (`content_md`, `title`, `thread_id`, `client_msg_id`) and the Alertmanager members (`version`, `groupKey`, `truncatedAlerts`, `status`, `receiver`, `groupLabels`, `commonLabels`, `commonAnnotations`, `externalURL`, `alerts`) and no `required` list.
   a. `Classify`: a body with at least one Alertmanager member is `alertmanager`; it must contain no native member, else `400 validation_failed` with the pointer of the first native member and `errors[].code` `format_mixed`. Every other body is `native` (8.2: `native` is the standard).
   b. A format not in `webhook_in.formats_enabled` gives `400 validation_failed` with an empty pointer and `errors[].code` `format_disabled`.
   c. `native` (M1-56 D2 rules, pointers into this body): `content_md` required (`/content_md`, `required`) with at least one non-white-space character (`empty`); more than `message.max_content_bytes` UTF-8 bytes gives `413 payload_too_large` with `detail` naming `message.max_content_bytes`; `client_msg_id`, when present, a UUIDv7 (`/client_msg_id`, `not_uuid_v7`), when absent a new server UUIDv7 (03 `messages.client_msg_id`); `title` follows the title rules of M1-55 (`/title`); `thread_id` is a UUID (schema). Content is stored byte for byte.
   d. `alertmanager` (`ParseAlertmanager`): `version` must be `4` (schema enum), `status` and each `alerts[].status` `firing` or `resolved` (schema enum), `alerts` at least one item (schema), each alert needs `status` and `labels` (`/alerts/<i>/labels`, `required`); every value inside `groupLabels`, `commonLabels`, `commonAnnotations`, `labels` and `annotations` must be a string (pointer to the member, `invalid_type`). The client message ID is always a new server UUIDv7: retries of Alertmanager are not deduplicated (8.2 makes only `client_msg_id` of `native` idempotent).
   e. Unknown members give `400 validation_failed` with `unknown_member` in `StageValidate` (SEC-IN-1, W7); the label maps use `JsonObject`, which M1-18 exempts from the closed-schema check.

5. **Target thread** (`ChooseTarget`, 11 8.3). Facts: the webhook (`channel_id`, `thread_id`), the channel kind and its main thread, and `chat.Threads.Info` of a fixed or named thread. In this order:
    1. Fixed thread: used while it belongs to the webhook's channel; `thread_id` and `title` of the body are ignored. Ruling for docs/DECISIONS.md: when the fixed thread was moved to another channel (M1-62), the post gives `404 not_found`, because a webhook writes only into its own channel (11 8.1 "for a channel", T-TK-03).
    2. `thread_id` of the body (native only) when that thread belongs to the webhook's channel; an unknown thread or one of another channel falls through to the next rule, so nothing about other channels is revealed.
    3. `title` (native only) creates a new thread. Forum: a forum post through the `createThread` use case with the message as its first message (M1-56 D8). Text channel: ruling for docs/DECISIONS.md: the message is written into the main thread and the new thread starts from it (`parent_message_id` = the message), like `auto_thread` of 09 3.7; reason: in a text channel a thread grows from a message (01 4, M1-55 D1 requires the parent), and 8.2 says one message per call. The answer names the new thread in `thread_id`.
    4. Main thread of a text channel. In a forum without rule 1 to 3: `400 validation_failed`, pointer `/title`, `errors[].code` `required_for_forum_post`; for `alertmanager` the pointer is empty (10.3: Alertmanager posts into a text channel or a fixed thread).

6. **Writing** (`PostIncoming`, one unit of work).
   a. Lock the webhook row with `FOR SHARE` (`LockIncomingForPost`) and check again `revoked_at IS NULL` and that the actor is its app; else `404 not_found`. A revoke, an uninstall and an archive update the row and therefore wait for posts in flight; after their commit no post writes (Design note 10). Deadlocks are retried by the unit of work (`database.tx_retry_max`).
   b. Choose the target (Design note 5), call `authorize` (Design note 3), then the messaging port with the webhook actor in the context, `SkipMentions = true`, `Silent = false` (notifications follow the channel settings, 11 8.4), no reply, no attachments, `kind = text`: `createMessage` for rules 1, 2 and 4; `createThread` with first message for rule 3 in a forum; `createMessage` into the main thread followed by `createThread` with `parent_message_id` of that message for rule 3 in a text channel.
   c. Ruling for docs/DECISIONS.md: `HashContext` = `"webhook:" + webhook_id + "|thread:" + <thread_id of the body or empty> + "|title:" + <title or empty>`, so the hash covers the request as sent (04 5.1 point 3) and a `client_msg_id` repeated through another webhook of the same app gives `422 idempotency_key_reuse` instead of a replay of a message of another webhook. A replay (same author, `client_msg_id` and hash) answers `200` with `Idempotent-Replay: true`, the original `message_id` and the thread of the first answer (the thread whose `parent_message_id` is the message in the text-channel case), and publishes nothing. The messaging port tells the caller that its answer is a replay (M1-56 D1 step 5); on a replay the use case creates no thread.
   d. Post-condition: the `channel_id` of the written message equals the webhook's `channel_id`, else roll back and answer `404 not_found` (a thread moved concurrently).
   e. `MessagePosted` carries `Origin = app` and `AuthorKind = app`; `runs.OnMessagePosted` returns at its first step (M2-05), so no run, no anchor, no `trigger_state` (SR4). Events are those of M1-56 D7 (`message.created` with `actor {id, kind: app}`; `thread.created` when a thread is created), in its order.
   f. After the commit, `TouchIncomingLastUsed` sets `last_used_at` only when it is empty or older than `identity.last_active_granularity` (ruling for docs/DECISIONS.md: the same rule as `api_tokens.last_used_at`, 03); outside the unit of work so concurrent posts never upgrade their share lock; a failure is logged without the token and never fails the request.

7. **Rendering of an Alertmanager notification** (`RenderAlertmanager`, golden tests). Ruling for docs/DECISIONS.md: the layout below, so the expected message of a payload is fixed by test (11 8.2 lists the contents, not the layout; `docs/observability/alerting.md` 2 adds severity and runbook link).
   a. Header line `**FIRING** <title> (<n> alerts)` or `**RESOLVED** ...` from the top-level `status`; `<title>` is `commonLabels.alertname`, else `groupLabels.alertname`, else `Alerts`; `<n>` is the number of items in `alerts` plus `truncatedAlerts`, written `1 alert` for one.
   b. A blank line, then one list item per alert in payload order: `- **<firing|resolved>** <alertname>, severity <severity>: <summary>`, where `<alertname>` is the alert's label `alertname` (else the title), `, severity <severity>` appears only with the label `severity`, and `<summary>` is the annotation `summary`, else `description`, else the remaining labels except `alertname` and `severity` as `name=value` sorted by name and joined by `, `, else `no summary`. Continuation lines indented by two spaces: `Runbook: <URL>` from the annotation `runbook_url` and `Source: <URL>` from `generatorURL`.
   c. When `truncatedAlerts` is above zero or items were dropped (d), a last item `- and <k> more alerts`.
   d. A blank line and `Alertmanager: <URL>` from `externalURL`.
   e. Values from the payload: line breaks and other control characters become one space, then every ASCII punctuation character is escaped with a backslash (CommonMark), so a label cannot add formatting, links or images. A URL is written only when it is an absolute `http` or `https` URL with a host and without white space, `<` or `>`, as an autolink `<URL>` whose visible text is the target itself (SEC-OUT-1); otherwise its line is left out. The server never fetches any of these URLs (11 1 point 4, SEC-OUT-2).
   f. When the text exceeds `message.max_content_bytes`: drop alert items from the end (counting them into the last item of c), then the footer, then cut the rest at a UTF-8 boundary so that `...` still fits. The result is never larger than `message.max_content_bytes` and always valid UTF-8.

8. **`createIncomingWebhook`** (`POST /channels/{channel_id}/incoming-webhooks`).
   a. Load the channel (unknown gives `404`); `authorize(actor, webhook_in.create, channel)`: invisible gives `404 not_found` identical to an unknown channel, read without `manage` gives `403 forbidden`, no fresh step-up gives `401 step_up_required`; tokens of agents and apps cannot do step-up (R-AZ-03).
   b. Body (`IncomingWebhookCreate`): `name` non-empty after trimming, without control or bidi characters (`kernel/textcheck`, SEC-IN-4; `/name`); `app_id` an app principal with an installation in state `active`, else `400 validation_failed` with `/app_id` and `errors[].code` `app_not_installed`; the app must be allowed `message.create` on the channel, checked with the webhook actor of Design note 3 in filter mode (`authorize.Filter`, no audit), else `/app_id` with `app_cannot_write` (11 8.1: it always writes as an app with `write` on the channel; a manager sees the same through "Who has access?"); `thread_id`, when present, a thread of this channel (`chat.Threads.Info`), else `/thread_id` with `not_in_channel`, the same for an unknown ID. Ruling for docs/DECISIONS.md: these three codes.
   c. Unit of work: `identity.Tokens.NewIncomingWebhookToken`; insert the row with `created_by` = the actor; audit allow `webhook_in.create` on the channel with details `{webhook_id, app_id, thread_id}` (no name, never token or hash); `idempotency.MarkOneTimeSecret(ctx)` (M1-20).
   d. `201` with `IncomingWebhookCreated`: `webhook` and `url` = `server.public_url` joined with `/api/v1/hooks/{webhook_id}/{token}` (ruling for docs/DECISIONS.md: absolute, as the schema says "Full URL"; Bearer senders drop the last segment and send the token in the header). No event (05 section 6 has none for incoming webhooks), no rights change.

9. **`listIncomingWebhooks`**: load the channel; `authorize(actor, webhook_in.read, channel)` (`404` without read right, `403 forbidden` without `manage`); the active webhooks of the channel ordered by `created_at`, then `id`, as `IncomingWebhook` without token or hash. Ruling for docs/DECISIONS.md: revoked webhooks are not listed (the partial index of 03 serves exactly this list; their history is in the audit log).

10. **`revokeIncomingWebhook`**: load the webhook (unknown gives `404`); resource `{kind: incoming_webhook, id, ChannelID}` (M1-28 visibility row); `authorize(actor, webhook_in.revoke, ...)`; already revoked: `204` and an audit allow entry with `no_change: true` (06 2 "No effect"); otherwise `UPDATE ... SET revoked_at = now() WHERE id = $1 AND revoked_at IS NULL`, audit allow with `{webhook_id, app_id}`, `204`. The next post with its token gives `404 not_found`.

11. **Lifecycle of the app and the channel.**
    a. Uninstall (M2-24 use case, 11 4.3): in the same unit of work `RevokeIncomingByApp` sets `revoked_at` on every active webhook of the app; the audit entry of `app.uninstall` stays the record.
    b. Suspend (11 4.3: "remain"): the rows stay; posts give `404 not_found` while the installation is not `active` (Design note 2b); after `app.resume` the same URL works again. Ruling for docs/DECISIONS.md: suspend is an emergency stop for everything the app writes (11 4.3, R-EX-05, 07 4.1 `app_not_installed`).
    c. Ruling for docs/DECISIONS.md: `apps.OnChannelArchived` (the subscription that 02 4.3 lists for `apps`) sets `revoked_at` on the active webhooks of the archived channel in the archive transaction, because archiving is irreversible (05 has no unarchive) and such a webhook could never post again. - [ ] `incoming_webhooks` exists exactly as in 03; `listIncomingWebhooks`, `createIncomingWebhook`, `revokeIncomingWebhook`, `postIncomingWebhook` and `postIncomingWebhookWithBearer` are enabled and registered; AZ-P1 passes.

- [ ] The Alertmanager example payload gives the expected message byte for byte (golden), resolved notifications too; rendering stays within `message.max_content_bytes`.
- [ ] Cron path of 11 10.4: a test job sends `native` with one `client_msg_id` per run; a repeat of the same run creates no second message, a new run creates a new one.
- [ ] The path token appears in the access log, in traces and in `Problem.instance` only as the pattern of 06 "Errors"; the Bearer token never appears.
- [ ] `rl.webhook_in` limits per webhook and runs before the token check; failed token checks count against `rl.public_auth`.
- [ ] The order of 11 8.4 holds: `429`, then `404` for the token, then `413` for `webhook_in.max_body_bytes`, then `400` for the format, then `404` for `authorize`, then `201`.

- [ ] The token is shown once, only its HMAC is stored, and a replay of the creation gives `409 conflict` with `reason: one_time_secret`.
- [ ] The target thread follows 11 8.3 with the rulings of Design note 5; mentions are never resolved.
- [ ] Revoke, uninstall and channel archive end posting; no post writes after their commit.
- [ ] Both post operations work on the internal listener in every role.
- [ ] The spec and API changes of Design note 15 and the rulings of Design note 16 are in the same change.
- [ ] `make check` is green.
