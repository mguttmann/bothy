# M2-41: Host pairing and fingerprint

Status: ready | Depends on: M2-40 | Milestone: M2

## Goal

After this ticket an owner registers a host with a one-time pairing code of the token format of ADR 0061 with kind `hpc` (`bothy_hpc_<random>_<checksum>`), shown exactly once and stored only as HMAC, valid once and only until `terminal.pairing_code_ttl` ends. The host service redeems it with `pairHost` (public, the code is the credential): it registers its static X25519 key (Noise) and its Ed25519 key (login), its platform, versions and profiles and the names of its session users, which the server stores in `hosts.reported_session_users`; the server computes the fingerprint of 24 "Fingerprint", raises `key_generation` and the host waits in `confirming`. The owner then confirms with step-up by typing the first `terminal.fingerprint_confirm_chars` characters of the fingerprint (`confirmHost`), declares the LLM login of the host (I6 checked in the same transaction) and whether the server runs there, and assigns each person their own session user, only from the reported names and never a taken one (T12); a wrong prefix gives `409 fingerprint_mismatch`, and after `terminal.fingerprint_max_attempts` failures the host falls back to `pairing` with its keys dropped. A new code for an existing host (`issueHostPairingCode`, re-pairing) drops its keys at once, ends its sessions with `host_rekeyed`, audits the old fingerprint and, at the next redemption, the old and the new one, and tells every owner through `host.updated` with `key_changed`. The token generator of M1-44 knows the kind `hpc`, the API token authenticator never accepts it, and the secret scanner rule detects a generated code. Why: a host that anybody with an intercepted code could pair, or that the owner confirms blindly, would receive every later terminal session (24 3.2, R-ID-08 by analogy, T-TM-06); a re-pairing must leave no path for copied keys (T-TM-05) and must be visible to every owner, because pinning on the devices only warns about a change the server announces (T-TM-01, SEC-TERM-8). This is the server side of 24 "Pairing" and "Re-pairing" with TM-T19 and TM-T20 and of TM-T28 (b) and (e) at confirmation; M2-42 builds `bothy-host pair` against it, and M4-37 the screen A8.

Product requirements implemented here:

11. The pairing code has the form `bothy_hpc_<random>_<checksum>`: 256 bits from `crypto/rand` in Base62 as exactly 43 characters, CRC-32 (IEEE) over the random part as exactly 6 Base62 characters, generated by `domain/apitoken` of M1-44 extended by the kind `hpc` (ADR 0061 point 1, 24 3.2, D-T32).
12. Only the HMAC-SHA-256 of the code with the pepper of `auth.token_pepper_ref` is stored (`hosts.pairing_code_hash`); the code is shown exactly once in `HostPairingCode` and appears in no log, audit entry, event, job, idempotency row or problem body (03 point 9, 24 3.2, SEC-LOG-1).
13. A code works once and only before `terminal.pairing_code_ttl` ends; a used, replaced, expired or unknown code and a code with a wrong checksum give `401 unauthenticated` with the same body; a wrong form or checksum is rejected without any database access (TM-T20, ADR 0061 point 2).
14. `pairHost` (`host.pair`: public with a valid code, Audit `yes`, `rl.public_auth`) stores both public keys, platform, versions, profiles and the reported session users in `hosts.reported_session_users`, computes `key_fingerprint` (24 4.3), raises `key_generation` and moves the host `pairing -> confirming` (24 3.1 and 3.2, D-W-63).
15. `confirmHost` (`host.manage`: owner, step-up, Audit, Permissions `yes`, `Idempotency-Key`, `If-Match`) compares the typed prefix of the fingerprint; a mismatch gives `409 fingerprint_mismatch` and the host stays `confirming`; after `terminal.fingerprint_max_attempts` failures it falls back to `pairing` and its keys are dropped (TM-T19, 24 3.2, D-T31).
16. With the right prefix `confirmHost` declares `llm_credentials` and the credential holder with I6 in the same transaction (`409 i6_violation`, 03 6.8, 24 7.3), records `declared_server_host` (24 2.3), assigns session users only from the reported names (`400 validation_failed` with `errors[].code` `session_user_not_on_host`) and never a name that belongs or belonged to another person or a second valid assignment of one person (`409 conflict` with `reason: session_user_taken`), stores nothing on any of these failures (TM-T28 (b) and (e), T12, D-W-63), and moves the host `confirming -> active`.
17. `issueHostPairingCode` (re-pairing) from `pairing`, `confirming`, `active` or `disabled` issues a new code, drops the stored keys at once, ends the sessions of the host with `host_rekeyed` in the same transaction, audits the old fingerprint and writes `host.updated` with `key_changed = true`, which every owner receives through `host.read`; the next `pairHost` raises `key_generation` and audits old and new fingerprint (24 3.3, SEC-TERM-8).
18. Every transaction of this ticket that changes a host's state, its declaration, `declared_server_host`, `reported_session_users` or rows of `host_session_users` raises the rights version first (03 4.3 and 6.3, 05 rule 1.7).
19. The kind `hpc` is never accepted as an API token and never issued by `createToken`; the gitleaks rule `bothy-api-token` detects a generated code (SEC-SEC-4, D-T32, PLAN row).
20. No JSON `null`; no private key member is ever accepted or stored; events, logs, audit details, problem bodies and test failure messages never contain a pairing code, its HMAC or key material other than what the `Host` representation shows (ADR 0053, 05 6 row `host.updated`, SEC-AUD-5).

## Design notes

1. **Code and hash (identity).** `NewHostPairingCode` generates a token of kind `hpc` with `domain/apitoken` (the constant `bothy` stays exactly once, M1-44) and returns it in the redacting secret type of M1-44 together with `Hash = HMAC-SHA-256(pepper of auth.token_pepper_ref, full code string)`, the same derivation as `api_tokens.token_hash`. `HashHostPairingCode` parses (form, kind `hpc`, checksum) and returns `ErrTokenMalformed` before computing any HMAC for a wrong value. Ruling for docs/DECISIONS.md: one derivation for every token of ADR 0061; the prefix `bothy_hpc_` already separates the kinds, so no extra label is hashed. The authenticator of M1-44 treats `hpc` like `whi`: `401 unauthenticated` without a database call.

2. **Shared issuer.** `IssuePairingCode`'s inner function `issueCode(ctx, hostRow)` runs inside the caller's unit of work: `PairingCodes.New`, `pairing_code_hash = Hash`, `pairing_expires_at = now + terminal.pairing_code_ttl`, `fingerprint_failures = 0`; it returns the code. `createHost` (M2-39) and `issueHostPairingCode` both use it. Check the merged code first:
   a. M2-39 already mints `hpc` codes through `domain/apitoken` and the identity port: keep its names, add only what is missing and route `issueHostPairingCode` through the same function.
   b. M2-39 mints codes another way (its own generator or another HMAC input): replace that path with the identity port, so the format exists once and the hash derivation is one; `createHost` keeps its behaviour and its tests.
   c. `createHost` is still `later` on the base branch: enable it here with the shared issuer, with `TestCreateHost_IssuesCode`, because it is the only way to create a host in `pairing`.
   Name the case in the report. Ruling for docs/DECISIONS.md: one issuer for both operations.

3. **`pairHost`** (`POST /api/v1/hosts/pair`, `host.pair`, `security: []`, `rl.public_auth`, `x-idempotency-exempt: auth_flow`), in this order:
   a. The schema validator of M1-18 rejects a missing member or a `pairing_code` outside its pattern with `400 validation_failed`.
   b. `PairingCodes.Hash`: `ErrTokenMalformed` (wrong checksum, kind not `hpc`) gives `401 unauthenticated`; no unit of work is opened and no query runs; the denial goes to `auditing.Recorder.RecordDenial` (action `host.pair`, reason `unauthenticated`, no resource), which aggregates it per IP pseudonym and `audit.deny_aggregate_window` (R-AZ-04) and writes outside the request.
   c. `ParseHostKeys` and `ValidatePairReport` (pure, no database): every finding is `400 validation_failed` with a pointer into the body and leaves the code valid (Design note 4).
   d. Read the host by `pairing_code_hash` without lock (unique partial index). No row, or `pairing_expires_at <= now`: `401 unauthenticated` with the same body as in b and a denial through `RecordDenial` (resource `host` with its ID when a row matched).
   e. One unit of work with `txn.RightsChange{Action: host.pair, Resource: the host, Targets: [the host]}` as M2-39 and M2-40 use it for a host (03 4.3 lists `reported_session_users`, so the rights version rises first, although 05 gives `host.pair` Permissions `no`; ruling for docs/DECISIONS.md). Lock the host `FOR UPDATE` and check again that `pairing_code_hash` equals the hash, `state = 'pairing'` and `pairing_expires_at > now`; otherwise roll back and answer as in d (a parallel redemption won).
   f. `authorize(principal, host.pair, Resource{Kind: host, ID})` gives `allow` through `Public` (Design note 10).
   g. `ComputeFingerprint`; equal to the retained `key_fingerprint` of this host: `409 conflict` with `reason: host_key_reused` (Design note 9), roll back, the code stays valid.
   h. Write `noise_public_key`, `auth_public_jwk` (exactly `{"kty":"OKP","crv":"Ed25519","x":...}` as built by the server), `auth_jkt`, `key_fingerprint`, `key_generation + 1`, `fingerprint_failures = 0`, `paired_at = now`, `platform`, `reported_os_version`, `reported_host_version`, `reported_profiles`, `reported_session_users` (exactly as reported, order kept; through the M2-40 helper for a change of the report if it exists, so M2-43's `report` writes the column the same way), `pairing_code_hash = NULL`, `pairing_expires_at = NULL` (ruling: the index on `pairing_expires_at` serves only `pairing`), state `confirming` through the M2-39 transition, `version + 1`. A unique violation on `auth_jkt` (the key belongs to another host, also a retired one) rolls back with `409 conflict` and `reason: host_key_in_use`.
   i. `host.updated` through the M2-39 writer without `key_changed`; audit allow `host.pair` (Design note 11). Answer `201 HostPairResult{host_id, key_fingerprint, instance_id}` with `instance_id` from the `instance` port (M1-15).
   A retry after a lost answer gets `401 unauthenticated`, because the code is used (D-T37); the operator asks the owner for a new code (M2-42 prints that hint).

4. **Key and report rules** (`ParseHostKeys`, `ValidatePairReport`; pointers relative to the body; ruling for docs/DECISIONS.md: these rules and their `errors[].code` values):
   a. `noise_public_key`: strict unpadded base64url (`base64.RawURLEncoding.Strict()`), exactly 32 bytes, else `invalid_key`; a low-order point is `invalid_key` too: `crypto/ecdh` `X25519().NewPublicKey`, then an ECDH with a fresh private key; an error there means the key can never complete a Noise handshake (M2-38 rejects a zero result).
   b. `auth_public_jwk`: exactly the members `kty` (`OKP`), `crv` (`Ed25519`) and `x`; any other member, the private member `d` above all, is `unknown_member` at `/auth_public_jwk/<name>`; `x` must decode strictly to 32 bytes, else `invalid_key`; parse it with `kernel/jose.ParseJWK` and take `auth_jkt` from `JWK.Thumbprint()` (RFC 7638); `auth_public_key_raw` of the fingerprint is the decoded `x`.
   c. `session_users`: at least one entry (`empty`; a host service without session users fails HD1 and can never give a terminal); each `os_user` matches `^[A-Za-z0-9_][A-Za-z0-9_.-]*$` and has at most `host.os_user_max_chars` characters (`too_long`); names are distinct without regard to case (`duplicate`); each `workdirs` entry is a non-empty display text (`kernel/textcheck.DisplayText`) of at most `terminal.report_label_max_chars` characters.
   d. `profiles`: names match the schema pattern, are distinct (`duplicate`) and at most `terminal.report_label_max_chars` characters long; `display_name` is a display text of at most that length; an empty list is allowed (HD7 may drop every profile).
   e. `profiles`, `session_users` and the `workdirs` of one session user each have at most `terminal.report_max_entries` entries (`limit_reached`).
   f. `host_version` is a SemVer 2.0.0 version without a leading `v` (`invalid_format`); `os_version`, when present, a display text of at most `terminal.report_label_max_chars` characters.

5. **Fingerprint** (24 4.3, the same function as M2-38 note 7): `SHA-256("bothy-host-fp/1" || noise_public_key || auth_public_key_raw)` (32 raw bytes each), Crockford base32 with the alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, 5-bit groups from the most significant bit, the last group padded with zero bits on the right, upper case, no padding character, no check symbol, 52 characters shown as 13 groups of four joined by `-`. Known vector, computed independently for this brief: noise key bytes `0x00` to `0x1f` and auth key bytes `0x20` to `0x3f` give `F0CC-6QS6-RF5D-3BSH-CAZQ-PXMR-J8RA-AHK5-1HF0-9S02-1GW6-BW3J-HK90`. If `services/host/testdata/noise/fingerprint.json` exists on the base branch (M2-38 merged), add `TestFingerprint_HostVectors`, which reads that file and checks every entry; otherwise do not add it and say so in the report (M2-42 compares both sides end to end). Ruling for docs/DECISIONS.md if M2-38 has not written 24 4.3 yet: the encoding details above go into 24 4.3.

6. **Prefix rules** (`HostConfirm.fingerprint_prefix`, "without separators, case-insensitive"): upper-case it; it must have exactly `terminal.fingerprint_confirm_chars` characters, all from the Crockford alphabet, else `400 validation_failed` with pointer `/fingerprint_prefix` and `errors[].code` `invalid_format`, and the attempt does not count. A well-formed prefix is compared with the first characters of `CompactFingerprint(key_fingerprint)` by `crypto/subtle.ConstantTimeCompare`. Ruling for docs/DECISIONS.md: only a well-formed prefix counts as an attempt; letters outside the alphabet (`I`, `L`, `O`, `U`) are not mapped, the client may normalise before sending.

7. **`confirmHost`** (`POST /api/v1/hosts/{host_id}/confirm`, `host.manage`, step-up, `rl.admin`, `Idempotency-Key`, `If-Match`), in this order:
   a. `428 precondition_required` without `If-Match` comes from the precondition stage of M1-18; the schema validator rejects missing members.
   b. Load the host; unknown gives `404 not_found`. `authorize(actor, host.manage, host)`: invisible gives the same `404`, a visible host without owner rights `403 forbidden` with `reason: owner_only`, no fresh enough step-up `401 step_up_required` (M1-28, M1-35).
   c. Body rules without the database: `reason` (`kernel/textcheck`, at most `audit.reason_max_chars`, else `400 validation_failed` with `errors[].code` `too_long`), the prefix of Design note 6, the declaration's own validation of M2-40 (`credential_holder_id` exactly with `personal`, as the 03 check demands).
   d. One unit of work with `txn.RightsChange{Action: host.manage, Resource: the host, Targets: [the host]}`; lock the host `FOR UPDATE`; `version` different from `If-Match`: `412 version_conflict` with `current`; `state <> 'confirming'`: `409 invalid_state_transition`.
   e. Prefix mismatch: `NextAttempt` raises `fingerprint_failures` without changing `version` (the counter is not part of `Host`, so the owner's next attempt keeps its `If-Match`); when it reaches `terminal.fingerprint_max_attempts`, the fallback of Design note 8 runs in the same unit. Audit allow `host.manage` (Design note 11). `confirmHost` declares `Idempotency-Key`. With a key, the M1-20 stage owns the unit of work, the use case's `Do` joins it and never commits (M1-13), and the stage rolls back every final error (02 8.4). Without a key, the use case's unit is the outermost: return the outcome from the `Do` function so it commits, then return the error. With a key, the handler calls the new `idempotency.KeepEffectOnFinal(ctx)` (in `internal/kernel/idempotency` next to `MarkOneTimeSecret`; the stage in `internal/platform/httpserver`, M1-20) before it writes `409 fingerprint_mismatch`. For a marked final answer the stage stores it with `Store.Complete` in the same unit and commits, so the counter, the fallback of Design note 8, the audit entry, `host.updated` and the stored answer commit together. Only this answer is ever marked. Add this exception to 02 8.4 in the same change. Ruling for docs/DECISIONS.md: the kept effect of `fingerprint_mismatch`, because every failed attempt must count also under a key (TM-T19). Ruling for docs/DECISIONS.md: `attempts_remaining` is a new problem member, because screen A8 (M4-37) shows the remaining attempts and no other field carries them.
   f. Prefix match: assign `session_users` through the assignment function of M2-39 (pointer `/session_users/<i>/os_user`; a name not in `reported_session_users` gives `400 validation_failed` with `errors[].code` `session_user_not_on_host`; a name that belongs or belonged to another person on this host, two entries for one person or one for a person who already has a valid assignment gives `409 conflict` with `reason: session_user_taken`); then declare `llm_credentials` and `credential_holder_id` through the declaration function of M2-40, which checks I6 before the commit (`409 i6_violation` with its deny entry in an own transaction, 03 6.8). Any of these failures rolls the whole unit back: no assignment, no declaration, no state change, `fingerprint_failures` unchanged.
   g. Then `declared_server_host`, `confirmed_by`, `confirmed_at`, `fingerprint_failures = 0`, state `active` through the M2-39 transition, `version + 1`; `host.updated`; audit allow; commit; `200 Host` with `ETag`.

One `confirm` audit entry, plus the entries the reused M2-39 and M2-40 functions write (`session_user`, `llm_credentials`), all with the same `correlation_id`. A replay with the same `Idempotency-Key` gets the stored answer (06 7 point 2 stores `400`, `409` and `412`), so a network retry never burns a second attempt; a new attempt needs a new key.

Honest limit for the report: the server keeps no dropped key, so a host service that keeps one of its two keys is not detected; M2-42 generates both keys anew at every `pair`. Ruling for docs/DECISIONS.md; update 24 3.3.

## Acceptance criteria

- [ ] `issueHostPairingCode`, `pairHost` and `confirmHost` are enabled and registered; AZ-P1 passes; `host.pair` is a real requirement and no longer in the deferred golden list.
- [ ] Pairing codes have the form of ADR 0061 with kind `hpc`; only their HMAC is stored; they are shown exactly once; the authenticator never accepts one; the gitleaks rule detects a code generated in the test run.
- [ ] TM-T20: a code used twice, an expired code and a code with a wrong checksum are rejected with `401 unauthenticated`, the wrong checksum without database access.
- [ ] `pairHost` stores both public keys, the fingerprint, the raised `key_generation`, platform, versions, profiles and the reported names of the session users in `hosts.reported_session_users`, and the host is `confirming`.
- [ ] TM-T19: a wrong fingerprint gives `409 fingerprint_mismatch` with `attempts_remaining`; after `terminal.fingerprint_max_attempts` failures the host is `pairing` and its keys are dropped, with and without `Idempotency-Key`.
- [ ] TM-T28 (b) and (e) over `confirmHost`: a taken name or a second valid assignment gives `409 conflict` with `reason: session_user_taken`, a name the host did not report `400 validation_failed` with `errors[].code` `session_user_not_on_host`, and nothing is stored; I6 is checked in the same transaction.
- [ ] Re-pairing drops the keys at once, ends the sessions with `host_rekeyed`, audits old and new fingerprint, refuses a re-sent key pair, and writes `host.updated` with `key_changed` that every owner receives.
- [ ] No pairing code, HMAC or key material in events, logs, audit details or problem bodies; no JSON `null`; the spec, `openapi.yaml`, ADR 0061, the threat model and DECISIONS are updated as in Scope.
- [ ] `make check` is green.
