# M2-46: Terminal revocation, limits, audit and metrics

Status: ready | Depends on: M1-30, M1-69, M2-45 | Milestone: M2

## Goal

After this ticket every kind of revocation of 24 "Revocation" ends the affected terminal sessions in the transaction that causes it, and every limit of 24 "Limits" takes effect without the help of the host service: the relay ends a session after `terminal.idle_timeout` plus `terminal.idle_grace` without bytes from the device, at `terminal.max_session_duration` after `opened_at` (across reattaching) and after `terminal.detach_grace` in `detached`; the job `terminal.sweep` repeats these checks in the database for the sessions of a failed node and ends sessions whose login session expired; `terminal.open` is refused with `403 terminal_denied` and `reason` `session_limit` once `terminal.max_sessions_per_person` or `terminal.max_sessions_per_host` is reached; and `rl.terminal` and `rl.host` bound openings, attachments and connections. The module `terminal` subscribes to `authorize.AccessChanged` (a removed `host` entry or a lost owner status ends sessions), `identity.DeviceRevoked` and `identity.SessionEnded` (they end the sessions bound to the device or login session with the exact reason). Every end of a session goes through the one end function of M2-39 (`EndSessions`), which this ticket completes: `close_reason` and `close_detail` only from the closed lists of 24 "Reasons for ending", one audit entry `terminal.terminate` with codes and numbers only, the personal event `terminal_session.changed`, the metric `bothy.terminal.sessions.closed`; after the commit every api process that holds a connection of the session closes it with `4100`, and the process holding the host's control connection sends `session.close`, after which the PTY helper ends the whole process tree. A run with canary values in terminal input and output finds them in no relay capture, log, trace, metric, audit row, event or database row (TM-T06, SEC-T10). This is the server side of TM-T06, TM-T10 and TM-T11 (24 "Tests"), of 07 8.2 point 7 and of the session ends that SR10 demands on a change of the owner status, of R-TM-10 and R-TM-11, and of the threats T-TM-01 and T-TM-11; M2-48 runs the same scenarios later against a real host service in a container. Why: a terminal is remote access to a machine, so a revocation must end it at once (fail closed, D-L23), a manipulated host service must not keep a session open (R-TM-11), and nothing a person types or sees may leave the end-to-end stream (SEC-TERM-1).

Product requirements implemented here:

11. Every kind of revocation of 24 8.3 ends the affected sessions at once, fail closed, in the transaction that causes it: revocation or expiry of a grant, leaving a group, losing the owner role, disabling the person, revoking the device, revoking or ending the login session, logout, disabling, re-pairing or retiring the host, ending the session user assignment or a `report` without its name (SR12), and a change that violates SR10 or I6. The connections close with `4100`, the host service is told to end the session, and its PTY helper ends the whole process tree (24 8.3, 6.5; 04 8.2; 07 8.2 point 7, SR10, SR12; D-L23).
12. `close_reason` only from the closed list of 24 10.3 (equal to the check of 03 `terminal_sessions` and to `TerminalCloseReason`); `close_detail` only from the closed list of 24 10.3 (equal to `TerminalCloseDetail`), never free text (24 10.3, 03 `terminal_sessions`).
13. The limits of 24 6.3 work without the host service: the relay ends a session after `terminal.idle_timeout` plus `terminal.idle_grace` without bytes from the device, at `terminal.max_session_duration` after `opened_at` also across reattaching, and after `terminal.detach_grace` in `detached`; the job `terminal.sweep` checks the same every `terminal.sweep_interval` in the database for sessions of a failed node (24 6.2, 6.3; 02 12.3; R-TM-11; D-T23; D-T39).
14. `terminal.max_sessions_per_person` and `terminal.max_sessions_per_host` count sessions that are not `closed`; reaching one denies `terminal.open` with the decision `terminal_session_limit`, answered as `403 terminal_denied` with `reason` `session_limit` (24 6.1 step 2, 6.3, 13; 07 4.1).
15. `rl.terminal` per human for opening, attaching and connecting a stream; `rl.host` per host, counted after the check of the host's key, for control and data connections; a failed check of presented credentials on these channels consumes one token of `rl.public_auth` of the client address (05 3; 02 9.1; 24 6.3; D-T34).
16. Every end by the server or by the host writes one audit entry `terminal.terminate` (system action, Audit `yes`) with `session_id`, `close_reason`, `close_detail`, `bytes_in`, `bytes_out` and the duration; never terminal content, commands, environment variables, paths or profile command lines (24 10.1; 19 SEC-AUD-5; R-TM-10).
17. Telemetry carries only counters and durations without IDs of people and without host names, no span per frame, and only the instruments of signals.md 4.3a with closed attribute sets (24 10.4; signals.md 2 and 4.3a; D-T41).
18. No terminal content in relay, proxy, logs, audit, telemetry, event log or database (TM-T06; SEC-TERM-1; T-TM-01); the canary scenario SEC-T10 contains a terminal input and a terminal output (19 SEC-T10, SEC-T18).
19. `terminal_sessions` holds metadata only, with retention class `security` (`retention.security_after_end` after `closed_at`); there is no content recording (24 10.4; 20 R-DP-07; OQ-04 default).
20. The stream is never an event; the event log carries only the personal event `terminal_session.changed` per state change; no JSON `null` (24 10.2; ADR 0053).

## Design notes

1. **One end function.** M2-39's `EndSessions` stays the only writer of an end (M2-39 Design note 7; M2-43 and M2-44 extended it with detail, exit code, event and close path). This ticket completes it: it locks the selected rows with `state <> 'closed'` `FOR UPDATE` in ascending `id`, validates the pair of note 2, sets `state = 'closed'`, `detached_at = NULL` (03 check `(state = 'detached') = (detached_at IS NOT NULL)`), `closed_at`, `close_reason`, `close_detail`, `exit_code` (only `process_exited` from the host), `closed_by` (only `client_closed` and `closed_by_owner` from `closeTerminalSession`), takes `bytes_in`, `bytes_out` and `last_input_at` from `end.Progress` (and from `RelayControl.Counters`, M2-44 Design note 11) when they are higher than the stored values, never as a sum, because both carry session totals (note 7 d), raises `version`, writes `terminal_session.changed` and, unless `end.Source` is `close_request`, one `terminal.terminate` entry (note 11); `bothy.terminal.sessions.closed` is recorded after the commit (note 12). A row that is already `closed` is skipped. Ruling for docs/DECISIONS.md: the first committed end wins for every path (server, host, job, subscriber); a later report or job for a closed session changes nothing and writes no audit entry.

2. **Closed lists and pairs** (24 10.3). M2-43 accepts from the host only `client_closed`, `process_exited`, `idle_timeout`, `detach_expired`, `open_failed` and `host_policy_violation`, with `close_detail` required exactly for `open_failed` (any of the 14 codes) and `host_policy_violation` (`subscription_login_detected`, `helper_untrusted`, `shared_location`) (`ValidateHostSessionEnd`, M2-43 Design note 10). `ValidateEnd` applies the same pair rule to every end inside `EndSessions`, server ends included: a detail with any other reason, a missing detail with those two, or an unknown code is an internal error, never stored. Ruling for docs/DECISIONS.md: the pair rule holds for every writer, not only for host reports; update 24 10.3.

3. **Close path after the commit.** No connection is touched inside a transaction. Ends are committed by request handlers of any module (subscribers), by the worker (`terminal.sweep`, `authz.expiry_sweep`) and by relays; every api process that holds a device stream or a host data connection of the session must close it with `4100` and the close text `close_reason`, and the process that holds the host's control connection must call `ControlLinks.CloseSession` (M2-43), which sends `session.close {session_id, close_reason}`. M2-44 built this path and this ticket builds no other (M2-44 Design note 11): every end writes `terminal_session.changed` in its transaction, and the event-log tail of every api process hands each committed one with `state = closed` to the relay observer, which closes the connections of the session held in that process and calls `ControlLinks.CloseSession` (a no-op without the link). The tail reads the committed rows of `event_log` from the database, woken by `NOTIFY event_log`, which is on in every mode (03 6.6), and polls every `sync.log_poll_interval` (02 11.2). So an end committed in a worker process while api and worker run as separate processes with `cluster.mode = single` (02 16 level 1), and an end committed on another node with `cluster.mode = multi` (02 16: every node has its log tail), reach the process that holds the connections at once, without `NOTIFY ephemeral` and without M2-47. A host service that was offline gets `session.close` at its next login through `live_sessions` (M2-43 Design note 6 b). Ruling for docs/DECISIONS.md: an established stream always ends with `4100` and the reason, also after an identity revocation (24 8.3), while `4012` stays the answer at stream `identify` when the credential is already revoked (04 6.4 "Mapping during connection setup"); the client learns the identity revocation from its gateway connection (`4012`, M1-65).

4. **Rights changes from outside `terminal`** (`OnAccessChanged(ctx, authorize.AccessChanged)`, phase 3.1 of the revoking transaction, 02 8.1 and 8.3). It never calls `authorize`, because the snapshot cache does not see uncommitted rights (M1-29).

    a. For every principal in `Changes`: each target of kind `host` in `Removed` ends that person's sessions on that host (`SessionSelector{HostID, UserID}`). `authz` computes the host set with `TerminalEffective` of M2-40 (effective `terminal` of 07 2.12 point 3, I6 aware), so a revoked or expired grant, a group left or expired, an owner role lost on a host without own grant, and an I6 switch for other owners all arrive here (04 8.2: "Whoever loses it, their terminal sessions on the host end in the same transaction").

    b. Then, for every principal in `Changes` that still has open sessions, read `People.IsActiveOwner` (M2-40) in the transaction; when it is false, end each remaining session for which `SR10Lost` holds: the host's `AssignedUserID` is not the person, or the host has `DeclaredServerHost` or `ReportedIsServerHost` (`HostFacts` of M2-39, read fresh). This is 07 SR10 "on every change of ... the owner status", the case M2-40 Design note 11 leaves to this ticket; it uses the same predicate as M2-40's assignee change and M2-43's report (`SessionsEndedByReport`). A person who was never an owner cannot hold such a session (SR10 at opening), so the check only ends sessions after `owner.remove`.

    c. Reasons by `ReasonForLostHost`: `AccessChanged.Action` `user.disable` gives `user_disabled`; a host with `LLMCredentials = personal` whose `CredentialHolderID` is not the person gives `i6_violation`; every other case `access_revoked`. Ruling for docs/DECISIONS.md: removed host entries and a lost owner status are the two signals of a rights change outside `terminal`, and both are consequences of the commit, not new rights decisions.

5. **Identity revocations** (method values of the `terminal` app type, synchronous in the transaction of the cause).

    a. `OnDeviceRevoked(ctx, identity.DeviceRevoked)`: the open sessions whose current `device_id` is the device; `ReasonForDeviceRevoke`: `user_disabled` gives `user_disabled`, every other device revoke reason of 03 `devices` gives `device_revoked`. Ruling for docs/DECISIONS.md: a device revocation ends the sessions whose last opening or attaching came from that device (`terminal_sessions.device_id`, the column the index of 03 serves), not those it once opened and another device took over.

    b. `OnSessionEnded(ctx, identity.SessionEnded)`: the open sessions whose `auth_session_id` is one of the ended sessions (one ID or a list, as the merged event carries it); `ReasonForSessionEnd`: `logout` gives `logout`, `user_disabled` gives `user_disabled`, `device_revoked` gives `device_revoked`, every other session revoke reason of 03 `auth_sessions` gives `session_revoked`.

    c. Ruling for docs/DECISIONS.md: device and login-session revocations end sessions through the identity events because they carry the exact reason (`logout` against `session_revoked`); the rights path of note 4 ends what else became unusable; both are idempotent through `EndSessions`, so the order of `DeviceRevoked`, `SessionEnded` and `AccessChanged` within `user.disable` does not matter.

6. **Ends already built inside `terminal`.** TM-T10 covers them as rows; the expected owners and reasons are: host disabled, retired (`host_disabled`, `host_retired`, M2-39) and re-paired (`host_rekeyed`, M2-41); assignment ended (`access_revoked`, M2-39); I6 switch or holder change (`i6_violation`, M2-40); assignee changed (`access_revoked`, M2-40); report without a name or with a new server host flag (`access_revoked`, M2-43); duplicate control connection (`host_disabled`, M2-43). A row that fails because the merged ticket did not end the session is fixed in that use case with the end function, and the fix is listed in the report.

7. **Deadlines in the relay** (api role; one set per session the process holds a side of).

    a. Idle: the reference is the latest of the last binary message from the device after `identify` seen by this process, `last_input_at`, `started_at` and `opened_at`; the session ends with `idle_timeout` when `clock.Now()` reaches reference plus `terminal.idle_timeout` plus `terminal.idle_grace`. Only device bytes count, as 24 6.3 says; the server cannot see frame types. When the deadline fires and input arrived meanwhile, the relay schedules the new deadline instead.

    b. Maximum duration: `opened_at` plus `terminal.max_session_duration`, unchanged by reattaching; reason `max_duration`. Detach: in `detached`, `detached_at` plus `terminal.detach_grace`; reason `detach_expired`.

    c. A deadline is reached at the instant itself (a check one clock tick before keeps the session). The relay ends through `EndSession` with `Source` `server` and its in-memory `Progress`.

    d. Progress persistence: `Progress` and `RelayControl.Counters` carry session totals: the row's `bytes_in` and `bytes_out` read when the relay began the pairing plus the live pairing's counts (M2-44 Design note 7 "Counting"). The relay writes these totals and `last_input_at` of a held session at most once per `terminal.idle_grace` (`PersistDue`) and when the pairing or the session is released, only `WHERE state <> 'closed'`, only increasing values (`GREATEST` with the stored value), without raising `version` and without an event. This write replaces M2-44's additive updates: the pairing-end update that adds the pairing's counts to the row (M2-44 Design note 7 "Counting") and the end value "row value plus the live pairing's counts" (M2-44 Design note 11) become this total write and the higher-value rule of note 1; M2-44's `TestRelay_ByteCountersAndLastInput` stays green unchanged as the regression test. Ruling for docs/DECISIONS.md: the stored value lags the true last input by less than `terminal.idle_grace`, so the sweep, which ends at stored value plus `terminal.idle_timeout` plus `terminal.idle_grace`, never ends a session before `terminal.idle_timeout` of real inactivity; counters do not change `version`, like reactions on messages (04 9 point 3); update 24 6.3.

8. **`terminal.sweep`** (worker; every `terminal.sweep_interval`; one unit of work per affected session, so no batch key is needed; no actor).

    a. It reads the open sessions with the state of their host and `SweepVerdict` ends a session with the first match in this order: host not `active` (`HostStateEnd`: `disabled` gives `host_disabled`, `retired` gives `host_retired`, `pairing` and `confirming` give `host_rekeyed`); login session ended (`session_revoked`); `opening` past the last grant plus `terminal.open_timeout` (`open_failed` with `open_timeout`), except on a host whose `hosts.reported_require_local_confirm` is true, where the pairing meets the open deadline and the host service bounds start and consent (M2-44 Design note 7, M2-45 Design note 15 d), so such an opening is bounded only by the rules after this one; `max_duration`; `detach_expired`; `idle_timeout` with the stored `last_input_at`. Each end goes through `EndSessions` with `Source` `server`. The last grant is not `opened_at`, because an attach to an `opening` session restarts the opening with a new deadline while `opened_at` never changes (M2-44 Design note 6 d and f); its time is the UUIDv7 timestamp of `terminal_sessions.token_jti`, which every grant renews (M2-44 Design notes 4 d and 6 e; if the merged attach writes a `jti` that is not a UUIDv7, make it one), so no column is needed.

    b. Ruling for docs/DECISIONS.md: the order (security reasons before limits); the end of a session whose login session passed `expires_at` as `session_revoked` (07 4.1 "session revoked or expired"; no event marks the expiry, the same pattern as `authz.expiry_sweep` for grants, 07 8.3); the `opening` fallback for a node that died before `terminal.open_timeout`, measured from the last grant and not applied on a host that reports `require_local_confirm`; update 02 12.3.

    c. "Login session ended" comes from the `identity` port: use the read M1-34 or M1-45 offers for the state of a list of sessions; if none exists, add `Auth.EndedSessions(ctx context.Context, sessionIDs []ids.ID, at time.Time) ([]ids.ID, error)` returning those revoked or with `expires_at` not after `at`, and bind it to an outgoing port of `terminal` in `internal/wire`.

    d. The pairing part of the 02 row ("discard expired pairing codes") cannot be built as written: 03 `hosts` requires `pairing_code_hash` while `state = 'pairing'`, and `pairHost` already rejects an expired code (M2-41, TM-T20). Change the 02 row to say that an expired code stays stored until the next code or the retirement and is rejected at redemption (spec gap in the report).

9. **Session limits.** In the unit of work of `openTerminalSession`, before `authorize`: take `pg_advisory_xact_lock(hashtextextended('terminal.open:' || <user_id>, 0))` for the person, then lock the host row `FOR UPDATE`, then count the sessions of the person and of the host with `state <> 'closed'` and pass them in `TerminalFacts`. The guard after SR12 denies with `terminal_session_limit` when the person's count is at least `terminal.max_sessions_per_person` or the host's count at least `terminal.max_sessions_per_host`; the answer is `403 terminal_denied` with `reason` `session_limit` (M2-40's mapping row), audited as every denial of `terminal.open` (07 4.2). A denial rolls back, so the step-up stays unconsumed. Attaching creates no session and is not counted. If M2-40's `ConsumeFresh` must stay the first row lock of the opening (M2-40 Design note 4), take the person lock before it and the host row after it; an advisory lock is no row lock. Ruling for docs/DECISIONS.md: the person lock (an advisory lock, because no table of `terminal` has one row per person; it is taken first, so 03 6.3 stays free of cycles) and "at least the key value" as the limit test.

10. **Rate limits** (05 3, the limiter of M1-19 before `authorize`).

    a. `openTerminalSession` and `attachTerminalSession` use `rl.terminal` keyed by the human principal and answer `429 rate_limited` with `Retry-After`; the device stream counts against the same bucket at `identify` after the credential check and closes with `4008` and the wait time in the close text.

    b. Host control and data connections use `rl.host` keyed by the host ID after the proof check (M2-43 Design note 3) and close with `4008` likewise.

    c. A failed check of presented credentials on the three channels (device stream `4004` or `4012`; host proof `4110` or `4113`) consumes one token of `rl.public_auth` of the client address; when that bucket is empty, a new connection from the address that presents credentials closes with `4008` before the check, as 02 9.1 rules for REST. Ruling for docs/DECISIONS.md: the rule of 02 9.1 applies to the WebSocket channels of the terminal (M2-43 left the counting of failed proofs to this ticket).

    d. Each rejection counts `bothy.ratelimit.rejected` with its class. If M2-43 or M2-44 already applied a class, only add the tests.
