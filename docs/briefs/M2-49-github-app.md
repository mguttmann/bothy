# M2-49: Reference app for code hosting (GitHub)

Status: ready | Depends on: M2-25, M2-30 | Milestone: M2

## Goal

After this ticket `plugins/github-app` is the reference app for code hosting of 11 10.1: a Node.js program in TypeScript on the SDK of M2-30 that receives GitHub webhooks at its own address, verifies `X-Hub-Signature-256` (HMAC-SHA256 over the raw body, value `sha256=` plus hex, compared in constant time) before it reads anything else, and posts issue and pull request events into a forum, one thread per issue or pull request, with the mapping kept in the app's own state: an event of a known issue or pull request lands in its thread, an event of a new one opens a forum post. A person with `trigger` on the forum runs `/issue` with a title; the app opens a forum post with a form, and when the form is submitted it creates the issue through the GitHub REST API and answers in that thread. With the optional scopes for mirroring, replies of people in a linked thread go to GitHub as comments, while the app's own messages are never mirrored back and its own GitHub objects never come back into the chat (loop protection). The manifest requests exactly the scopes of 11 10.1, `installApp` refuses an installation without one of its required scopes, and a scope missing at call time surfaces as `403 scope_missing` from the server, which the app logs once and never retries. The tests run against an in-process Fake-GitHub API with webhook payloads from GitHub's documented examples and the test values of the GitHub documentation, against an in-memory chat port, and inside `make check` against the real server through M2-29's `sdkserver`, driven as M2-30's live files drive it; no test reaches a real GitHub service, and the npm license gate stays green. Why: requirement 19 asks for working integrations (D-W-10), R-EX-11 asks for one real app per SDK as the proof that the SDK is enough for apps, and 11 10 makes this app the pattern that M2-50 (Jira) and owners' own apps copy, so its signature check, its duplicate and loop protection and its handling of foreign text must be right (RK-83, T-PL-01).

16. The app never mirrors its own messages (author = app) back (11 10.1 row "Loops"); apps never trigger agents and never hold `trigger` or `manage` (11 6 row "Never allowed", R-EX-03, SR4).
17. Commands and interactions reach the app as signed `POST` requests to `delivery.interactions_url`, answered within `app.interaction_timeout` with `202` and acted on through the API (11 9; webhooks.md section of M2-25); requests of the server are verified with the SDK's `webhooks` module: raw body, `webhook-timestamp` within `webhook.receiver_tolerance`, `v1a` keys from `getWebhookKeys` only (webhooks.md 3, 11 11.2 row `webhooks`).
18. Duplicates are recognised by `webhook-id`, at least for `webhook.retry_max_age` (webhooks.md 3 point 4), and by GitHub's delivery identifier.
19. Foreign text never resolves a mention or becomes a link (03 content format rules 2 and 3, SEC-OUT-1); titles carry no control or bidi characters (SEC-IN-4).
20. No test calls a real GitHub service; the counterpart is a Fake-GitHub API with webhook fixtures from the public GitHub documentation (PLAN 8 "Test strategy", D-W-10, 11 10).
21. Secrets (the app's API token, the GitHub token, the GitHub webhook secret) never appear in logs, error messages or test output, and their files have mode `0400` or `0600` (SEC-SEC-1 and SEC-SEC-3 applied to the app, SEC-LOG-2, SEC-LOG-4, `plugins/README.md`).
22. Dependencies locked with checksums; the license gate for npm and OSV pass without a change to `quality/licenses/allowed.txt` (SEC-SC-1, licenses.md, PLAN row).
23. The app's own names do not carry the product name; the product name appears only as the SDK package `bothy-sdk` (02 6, ADR 0044).
24. Own `VERSION` and `CHANGELOG.md` in the folder; the app is not a release component (11 10, D-W-38 for the English CHANGELOG).
25. No JSON `null` in requests to the server (ADR 0053); unknown members of server events are tolerated through the SDK (06 2).

3. **Configuration** (new rows in 11 16 with place "GitHub app"; Ruling for docs/DECISIONS.md). A JSON file named by `--config` holds one object `github_app` whose members are the keys without their prefix:

    - `github_app.listen`: no default, required; `host:port` of the HTTP listener.
    - `github_app.server_url`: no default, required; base URL of the instance, `https`, `http` only for a loopback host.
    - `github_app.token_file`: no default, required; file with the app's API token (M2-24 `createToken`).
    - `github_app.dpop_key_file`: empty; key file for a DPoP-bound app token (`auth.dpop_required_for`), loaded with the SDK's `loadDpopKey`.
    - `github_app.webhook_secret_file`: no default, required; file with the secret of the GitHub webhook.
    - `github_app.github_token_file`: no default, required; file with the token for the GitHub REST API.
    - `github_app.github_api_url`: `https://api.github.com`; base URL of the GitHub REST API.
    - `github_app.repositories`: no default, required, not empty; list of `{"repository": "<owner>/<name>", "channel_id": "<forum id>"}`; each repository once, compared without case; several repositories may share one forum.
    - `github_app.state_dir`: no default, required; state directory of Design note 8.
    - `github_app.max_body_bytes`: `1048576`; largest request body on each endpoint.
    - `github_app.dedupe_window`: `72h`; how long GitHub delivery identifiers, `webhook-id` values, the GitHub objects the app created and open drafts are kept. The default equals the default of `webhook.retry_max_age`; the README tells operators to keep it at least as long as that server key (webhooks.md 3 point 4).
    - `github_app.max_queued_jobs`: `10000`; open jobs, above which the endpoints answer `503`.

    Reused keys, never new numbers: `webhook.receiver_tolerance` (the SDK default of `verifyWebhook`), `sdk.http_timeout` (also the time limit of each GitHub request), `sdk.retry_max_attempts`, `sdk.retry_backoff_base` and `sdk.retry_backoff_cap` (the SDK client; `sdk.retry_backoff_cap` is also the worker's pause after a transient failure). Durations follow configuration.md 2. Unknown members, wrong types, bad durations and missing required keys abort the start with a message that names key and file and never a value. Secret files (`token_file`, `dpop_key_file`, `webhook_secret_file`, `github_token_file`) must have mode `0400` or `0600` and belong to the process user, otherwise the start aborts (the rule of SEC-SEC-1); the GitHub token and the webhook secret are read at each use with the same check, so rotation needs no restart (a failing check answers `503` or fails the job), the app token once at start. `state_dir` is created with mode `0700`; an existing one with group or other access is refused. `config.example.json` parses with the loader (test).

4. **HTTP surface** (Ruling for docs/DECISIONS.md). Routes `POST /github/webhook`, `POST /chat/interactions`, `POST /chat/events`; any other path gives `404`, another method `405`. Per request, in this order: `Content-Type` must be `application/json` (parameters allowed), else `415`; the body is read as bytes up to `github_app.max_body_bytes` (a larger `Content-Length` answers `413` before reading, a stream that grows beyond it is cut and answers `413`); signature check (Design notes 5 and 7), failure `401`; JSON parse with invalid UTF-8 or JSON answering `400`; duplicate check; classification and, in the same store write, the seen identifier and the new job; then `202` when a job was queued and `204` when there is nothing to do; `503` when the queue holds `github_app.max_queued_jobs` jobs, the store fails, a secret file fails its check or the app is stopping. Bodies are empty except for the autocomplete answer of Design note 7. The app speaks plain HTTP on `github_app.listen` and runs behind the TLS-terminating proxy of the instance; `delivery.interactions_url` and `delivery.events_url` are `https` addresses of that proxy (11 3.2 rule 3), and the README shows the route. Node.js keeps its default header and request time limits; the proxy bounds slow clients.

5. **GitHub signature** (11 10.1 row "Input"; RK-83). Ruling for docs/DECISIONS.md.

    - `X-Hub-Signature-256` must be present and match `^sha256=[0-9a-f]{64}$`; a missing, truncated, upper-case or otherwise malformed value is refused without computing anything. `X-Hub-Signature` (SHA-1) is never used.
    - The app computes HMAC-SHA256 with the secret over the raw body bytes and compares the 32-byte digest with the 32 bytes decoded from the header through `crypto.timingSafeEqual`; both have the same length, so it never throws. No string comparison of a signature anywhere.
    - Only after a valid signature: `X-GitHub-Event` and `X-GitHub-Delivery` must be present (else `400`), then the JSON is parsed.
    - Every signature failure answers `401` without body and logs only `reason` (`missing`, `malformed`, `mismatch`).
    - Test values of the GitHub documentation (the page cited in 11 10.1, section on testing the payload validation): secret `It's a Secret to Everybody`, payload `Hello, World!`, expected header value `sha256=757107ea0eb2509fc211221cce984b8a37570b6d7586c22c46f4379c8b043e17` (the HMAC was recomputed while this brief was written). The test names the URL and the access date of 11 10.1 in a comment.

6. **GitHub events** (closed list; Ruling for docs/DECISIONS.md). Supported: `ping` (answer `204`, no job); `issues` with action `opened`, `closed` or `reopened`; `issue_comment` with `created`, on issues and on pull requests (the member `issue.pull_request` marks a pull request); `pull_request` with `opened`, `closed` (merged when `pull_request.merged` is true) or `reopened`; `pull_request_review` with `submitted`. Every other event or action answers `204` with log reason `unsupported`. `repository.full_name` is compared without case with `github_app.repositories`; an unknown repository answers `204` with reason `repository_not_configured`. The parser keeps only the fields used: key (Design note 9), kind (issue or pull request), number, title, `html_url`, the actor login, the text (body of issue, pull request, comment or review), comment id, review state, merged flag; a missing required field answers `400` with reason `invalid_payload`. The job stores this parsed event, never the raw payload. Reason: the list covers the life of an issue or pull request; more events are a later change with their fixtures.

7. **Requests of the server** (11 9; webhooks.md 3 and the section of M2-25). Ruling for docs/DECISIONS.md.

    - Both `/chat/` endpoints verify with the SDK: `verifyWebhook` over the raw body with the keys of one `WebhookKeyCache` of the app's client and the default tolerance `webhook.receiver_tolerance`; never an own verifier and never keys from the request. A `WebhookVerificationError` answers `401` and logs its `code`. No `v1` secret: an interactions address has no HMAC (M2-25), and the app's subscription is created without `enable_hmac`.
    - Duplicates: `webhook-id` (the event `id`) is remembered for `github_app.dedupe_window`; a repeat answers as the first time (`202` on `/chat/interactions`, `202` or `204` on `/chat/events`) without a second job.
    - `/chat/interactions`: `command.invoked` with `command_name` `issue` queues the job `issue_command`; `interaction.created` queues `issue_form`; both answer `202`. `command.autocomplete_requested` answers `200` with `{"choices": []}` (`AutocompleteAnswer`; the app declares no option with autocomplete). Another type or command name answers `202` with Warn reason `unknown_request`. Reason: in a forum the server has no reply thread for a `200` (M2-25 `no_thread`), and GitHub calls do not fit into `app.interaction_timeout`; the person sees the result through the API answers of Design note 11.
    - `/chat/events`: only `message.created` is handled (Design note 12); any other type answers `204`. `sync_epoch` is ignored, because the app keeps no `seq` state.

8. **State, queue and worker** (Ruling for docs/DECISIONS.md).

    - Port `Store` with `FileStore` in `github_app.state_dir`: `state.json` (thread map in both directions, drafts, the GitHub objects the app created, seen identifiers with their time) and one file per job under `jobs/`. Every write goes to a temporary file, `fsync`, `rename`, `fsync` of the directory; files `0600`, directories `0700`; one writer at a time through an in-process mutex. `MemoryStore` serves unit tests; one contract test runs against both.
    - A lock file `lock`, created exclusively and holding the PID, keeps a second process away; a lock whose PID is not alive is taken over with a Warn line.
    - A job is written before its request is answered; the worker processes jobs strictly in creation order, one at a time, so events of one issue keep their order and a `/issue` job records its issue before GitHub's `opened` event of that issue is handled (Design note 12).
    - A job records its progress per step. Every write to the server gets its `client_msg_id` (SDK `uuidv7`) or `Idempotency-Key` stored in the job before the first attempt, so a rerun after a crash repeats the same request and the server answers the original (04 5.1 and 5.2; the description of `createThread`). The SDK client retries transient failures within `sdk.retry_max_attempts`; when they are exhausted, the job stays queued and the worker pauses `sdk.retry_backoff_cap`. Permanent answers end the job (Design note 13).
    - A write to GitHub is never repeated: the job marks the step `attempted` in the store before it sends; a rerun that finds `attempted` without a stored result treats the outcome as unknown (Design notes 11 and 12). Reason: GitHub's create calls are not idempotent, and a second issue is worse than a missing comment.
    - Finished jobs are deleted; seen identifiers, created objects and drafts older than `github_app.dedupe_window` are pruned at each write; the thread map stays.
    - SIGTERM and SIGINT: stop accepting (requests after the signal get `503`), let the running step finish, release the lock, exit 0.

9. **One thread per issue or pull request** (11 10.1 row "Output"; Ruling for docs/DECISIONS.md).

    - Key `<owner>/<name>#<number>` in lower case, built from the configured repository name; issues and pull requests share the numbers of a repository. The map holds key to `{thread_id, channel_id}` and thread to key.
    - Port `ChatPort` (`src/chat/port.ts`) with `me()`, `limits()`, `createForumThread(...)`, `postMessage(...)`, `getMessage(...)`, `respondInteraction(...)`, typed with the schema types the SDK exports from the generated core (no own type repeats a schema, ADR 0026 "Confirmation"); `src/chat/sdk-adapter.ts` implements it on `createApiClient` (`getMe`, `getInstance`, `createThread`, `createMessage`, `getMessage`, `respondToInteraction`).
    - Known key: `createMessage` into its thread. Unknown key: `createThread` in the repository's forum with `title` and `first_message` (the event's message) in one call, idempotent through `first_message.client_msg_id`; the map entry is stored with the answer.
    - Title `#<number> <title>` for an issue, `PR #<number> <title>` for a pull request (also when the first event is a comment on it), cleaned and cut as Design note 10 says.
    - `404 not_found` when posting into a mapped thread (it moved out of reach or the grant there is gone): drop the entry, open a new forum post for the key once, Warn reason `thread_unreachable`; a second `404 not_found` ends the job.
    - Messages (English templates; GitHub text rendered as Design note 10; "#12" stands for the number, linked to the event's `html_url` as Design note 10 allows): `issues` `opened` "**Issue #12 opened** by `login`" plus the body; `closed` and `reopened` one line each; `issue_comment` "`login` commented on #12:" plus the comment, linked to the comment's `html_url`; `pull_request` `opened` with the body, `closed` as "merged" or "closed", `reopened`; `pull_request_review` "`login` reviewed #7: `state`" plus the body when present, linked to the review's `html_url`.

10. **Foreign text** (03 content format, SEC-IN-4, SEC-OUT-1; Ruling for docs/DECISIONS.md).

    - GitHub text never resolves a mention or becomes a link in the chat: logins and titles inside messages go into a code span, bodies of issues, pull requests, comments and reviews into a fenced code block; the delimiter of each is one backtick longer than the longest backtick run of its text (CommonMark 0.31.2, the version of 03), so the text cannot close it (03 content format rule 2: no mentions in code).
    - A link is written only for the event's `html_url` when it parses as an absolute `https` URL without whitespace, angle brackets or parentheses; otherwise no link.
    - Messages are cut to `limits.message_max_content_bytes` of `getInstance` (UTF-8 bytes, at a code point boundary) by cutting the fenced text and adding the line "(cut, full text on GitHub)", with the fence always closed; titles to `limits.thread_title_max_chars` code points.
    - Titles: Unicode control characters (category `Cc`) and the bidi controls U+200E, U+200F, U+061C, U+202A to U+202E and U+2066 to U+2069 are removed, line breaks become spaces, the result is trimmed; an empty result leaves `#<number>` or `PR #<number>`. If the server still answers `400 validation_failed` on the title, the job retries once with `#<number>` or `PR #<number>` alone.
    - Limits come from `getInstance` at start and once more after a `400 validation_failed` with `errors[].code` `too_long`, followed by one retry.
    - Text the app writes itself (the confirmation of `/issue`, the form card) contains no mention.

11. **`/issue` with a form** (11 10.1 row "Commands"; Ruling for docs/DECISIONS.md).

    - The manifest command `issue`: description "Create a GitHub issue" within `command.description_max_chars`, option `title` (`string`, required, description "Issue title"), `required_level` `trigger`. Reason: the form is submitted with `interaction.create`, which needs `trigger` (05 4.10); with `write` a person could run the command but never submit its form, and agents and apps, which hold at most `write`, cannot run it.
    - Job `issue_command`: the payload's `channel_id` must be a configured forum, else Warn reason `channel_not_mapped` and end (the README tells operators to grant `write` only on configured forums, so the command is listed only there, 09 10.3). Then `createThread` in that forum with the option `title` cleaned and cut as the title (empty: "New issue") and the first message "New GitHub issue for `<owner>/<name>`. Fill in the form below.", then `createMessage` in the new thread with `kind` `card` and one component built with the SDK's `form` builder: `custom_id` `issue:<draft id>` (within `component.custom_id_max_chars`), `single_use` true, `restricted_to` `any`, fields `body` (`textarea`, label "Description", not required) and, only when more than one repository maps to the forum, `repository` (`choice` of the configured names, required), within `component.form_max_fields`. Store the draft `{draft id, thread id, card message id, title, repositories}`. Reason: a thread belongs to exactly one issue and an app cannot retitle a thread (05 2.6), so `/issue` always opens its own forum post, also when it was run inside a thread.
    - Job `issue_form`: the draft is found by `interaction.custom_id`, else by `interaction.message_id`; unknown or pruned: `respondToInteraction` with state `rejected` and text "This form expired. Run /issue again.". The repository is the only one or the chosen one, checked against the draft. Mark `attempted`, then POST the issue with `title` and `body` = the form text plus a last line "Created from chat.". Ruling: nothing about the person (name, handle, id) goes to GitHub from `/issue`, and the text is not neutralized, because the person wrote it for GitHub.
    - GitHub answers `201`: store number and URL, record the issue as created by the app (Design note 12), map the key to the draft's thread, `respondToInteraction` with state `acknowledged` and text "Created issue #<number>", `createMessage` into the thread "Created GitHub issue #<number>." with the number linked to the issue's `html_url`, delete the draft. This is the answer in the thread.
    - GitHub answers `3xx` or `4xx` (not followed, so the issue was not created): `respondToInteraction` with state `failed` and text "GitHub refused the issue (status <status>).", then a new form card in the same thread; the draft stays with the new card.
    - `5xx`, a time-out after `sdk.http_timeout`, a transport error, or `attempted` without result after a restart (outcome unknown): `respondToInteraction` with state `failed` and text "GitHub did not confirm the issue. Check the repository before you try again."; no new card, the draft is deleted.
    - A `409` answer to a repeated `respondToInteraction` (rerun after a crash) counts as done.

12. **Mirroring and loop protection** (11 10.1 rows "Scopes" and "Loops"; Ruling for docs/DECISIONS.md).

    - Mirroring exists only when the owner granted `messages:read` and `events:subscribe`, added `message.created` to the installation's `event_subscriptions` and created a subscription to `delivery.events_url` for `message.created` (webhooks.md 1); otherwise `/chat/events` receives nothing.
    - Decision at receipt, in this order, each answering `204` without a job and logging its reason: the author is the app itself (`message.author.id` equals the principal id from `getMe`; reason `own_message`, the loop protection of 10.1); `origin` is not `human` (`not_human`: agent, app, import and system messages are never mirrored, so two mirroring apps cannot feed each other and no agent output leaves the instance without a person); `kind` is not `text` (`not_text`); `deleted_at` is set (`deleted`); the thread is not mapped (`thread_not_mapped`). Otherwise the job `mirror`, answer `202`.
    - Job `mirror`: if `content_truncated` is set, load the message with `getMessage`; the comment body is "`<display name>` wrote in chat:" followed by the content in a fenced block (Design note 10 delimiter rule), because chat mentions name chat people and must not become GitHub mentions or links; mark `attempted`, POST `/repos/<owner>/<name>/issues/<number>/comments`; `201`: record the comment id as created by the app; any other outcome: log `status` or reason `github_outcome_unknown` and end without retry.
    - Echo protection in the other direction: GitHub's `issues` `opened` event of an issue the app created through `/issue` and the `issue_comment` `created` event of a comment the app created are not posted (answer `204`, reason `own_github_object`); later events of these objects are posted. Reason: the chat already shows the original, and without the rule every mirrored reply would come back as an app message.

13. **Answers of the server** (06 5, 07 2.10).

    - `403 scope_missing`: end the job, one Warn line with `operation`, `status` and reason `scope_missing`, no retry; the GitHub delivery was already answered `202`.
    - `404 not_found`: Design note 9 for threads; for `respondToInteraction` and `getMessage` end the job.
    - `403 forbidden` and `403 channel_read_only`: end the job and log the code and `reason`.
    - `400 validation_failed`: the retries of Design note 10, otherwise end the job and log the `errors[].code` values.
    - `401 unauthenticated` (token revoked, app suspended or uninstalled, M2-24): end the job with an Error line; the endpoints answer `503` until `getMe` succeeds again, tried once per `sdk.retry_backoff_cap`.
    - `422 idempotency_key_reuse`: Error line (the same identifier with another body is a programming fault), end the job.
    - `429 rate_limited` and `503 unavailable`: retried by the SDK, then Design note 8. Unknown codes are classified by status through the SDK's `ProblemError`.

14. **GitHub REST client** (Ruling for docs/DECISIONS.md). Two calls: `POST <github_api_url>/repos/<owner>/<name>/issues` with `{title, body}` and `POST <github_api_url>/repos/<owner>/<name>/issues/<number>/comments` with `{body}`, headers `Accept: application/vnd.github+json`, `Authorization: Bearer <token>`, `X-GitHub-Api-Version: 2022-11-28`, `User-Agent: github-app/<VERSION>` and `Content-Type: application/json`; time limit `sdk.http_timeout`; redirects are not followed (`redirect: "manual"`, a `3xx` is a failure); the response body is read only on `201` for `number`, `html_url` and `id`; errors carry the status only, never a body. The README names the GitHub REST pages for issues, issue comments and API versions and says that the token needs only the right to create issues and issue comments in the configured repositories.

15. **Logs** (SEC-LOG-2, SEC-LOG-4 and SEC-SEC-3 as the rule for this app). JSON lines on stdout with `time`, `level`, `msg` (a fixed code such as `github.delivery.accepted`) and only these attributes: `event`, `action`, `delivery_id`, `webhook_id`, `job_id`, `job_kind`, `step`, `operation`, `status`, `outcome`, `reason`, `code`, `number`, `thread_id`, `channel_id`. Never titles, bodies, comments, form values, display names, handles, GitHub logins, repository names, URLs, header values, tokens, secrets, signatures or file contents. The SDK client gets this logger. Start errors name key and file, never a value.

## Acceptance criteria

- [ ] `X-Hub-Signature-256` is verified with the test values of the GitHub documentation; wrong, missing and truncated signatures answer `401` and create nothing; the comparison goes only through `timingSafeEqual` on the digests.
- [ ] An event of a known issue or pull request lands in its thread; a new one creates exactly one forum post; the mapping survives a restart.
- [ ] `/issue` with the form creates exactly one issue through the Fake-GitHub API and answers in the thread; failures follow Design note 11, never with a second issue.
- [ ] The app's own messages are never mirrored back; mirrored human replies and the app's own issues do not come back; GitHub text never becomes a mention or link.
- [ ] The manifest requests exactly the scopes of 11 10.1; `installApp` refuses an installation without one of the required scopes; a missing scope at call time gives `403 scope_missing`, logged once and not retried.
- [ ] No test calls a real GitHub service.
- [ ] The app passes its live test against the real server inside `make check` (`test/live/github-app.live.test.ts` in the script `test`).
- [ ] The npm license gate and OSV pass without a change to the allowlist; the typedoc gate fails on an undocumented export of the app.
- [ ] 11 10.1 and 16, `configuration.md`, the threat model, `plugins/README.md`, the app's README and CHANGELOG, the root CHANGELOG and `docs/DECISIONS.md` describe what was built.
- [ ] `make check` is green.
