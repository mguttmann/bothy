# M2-32: Recording Hermes Agent before the build

Status: ready | Depends on: none | Milestone: M2

## Goal

Before the Hermes adapter is built (M2-33), this ticket measures the six open points of 09 17.10 "To check before building" against a pinned public version of Hermes Agent with a fake model, and keeps the evidence as fixtures in `plugins/hermes-adapter/tests`. The six points are: how the pinned version calls `format_tool_event`, `send_draft`, `set_status_text` and `edit_message`; whether `steer` is available to a platform adapter; whether a public surface tells a plugin which credential type (API key or OAuth) the next turn uses, and whether OAuth wins over an API key; whether `on_processing_complete` reports an interrupted turn as cancelled; how a new session and a bind to an existing session are triggered through public ways, and how a plugin learns the Hermes session ID; and how the Hermes gateway recognises a plugin's own access policy (`enforces_own_access_policy` with policy "allowlist"). After this ticket each point has recorded observations, a verdict computed from them and a row in 09 17.10 with answer, fixture and consequence; where a claim of chapter 09 did not hold, the mapping in 09 section 17 (and in 10 10.1 where it describes Hermes) is adapted in the same change. The recording is not a one-off: a test in the component's default test run provisions the pinned commit read-only in a temporary directory, installs it into a throwaway environment, starts its gateway with a probe platform plugin that Hermes finds through its real plugin discovery and a local fake model, replays the scenarios, compares the normalized call patterns with the checked-in fixtures and proves the checkout and the installed files unchanged afterwards. Nothing in a run can reach a real model, a real credential, another Hermes installation or a productive runtime (PLAN 1 point 2). Why: progress hooks, `steer` and credential detection of Hermes are no promised plugin API (RK-12), and the proof of the actual billing mode may depend on a surface that is not public (RK-13, T-AI-08); an adapter built on guesses could carry organization traffic over a personal subscription or show a broken live box. The harness built here (pin, provisioning, isolation, fake model, control channel, integrity check) is the base on which M2-33 builds its Fake-Hermes scenarios.

3. **The pin.** `tests/hermes_pin.toml` (TOML, SPDX comment line) holds `repository` (exactly `https://github.com/NousResearch/hermes-agent`, the URL in 09 17.1), `tag`, `commit` (40 lower-case hex digits), `python` (the CPython line for the throwaway environment, the newest line the pinned `requires-python` allows), `install` (`uv-lock` or `requirements`), `extras` (list, empty unless the probe platform or the providers need one), and `recorded_on` (date). Ruling for docs/DECISIONS.md: pin the newest release tag of the public repository that is older than `deps.min_release_age` on the build day (the Renovate cooldown, ADR 0041), resolved to its commit with `git ls-remote`; if the repository has no release tags, pin the newest commit of its default branch older than that window and leave `tag` out. `renovate.json` gets a regex custom manager for this file (datasource `github-tags`, package `NousResearch/hermes-agent`, `currentValue` from `tag`, `currentDigest` from `commit`; for a tag-less pin `git-refs`) and a package rule with `prBodyNotes`: record again with `make -C plugins/hermes-adapter record`, review the fixture diff, update 09 17.10 before merging; the update fails the test run until then, on purpose (the pattern of the rule "release binaries"). `pin.py` exposes `HermesPin` (frozen dataclass of these fields) and `load_pin(path) -> HermesPin`, which raises `PinError` for a missing field, a short or non-hex commit, a branch name in `tag` or an unknown `install`.

4. **Provisioning in a throwaway folder** (`provision.py`, `integrity.py`). `provision(pin, root) -> HermesInstall` works only inside `root`, a fresh temporary directory outside the repository:

    - Checkout: `git init`, `git fetch --depth 1 <repository> <commit>`, `git checkout --detach FETCH_HEAD`; `HEAD` must equal `commit`. Then the checkout becomes read-only (write bits removed recursively), so any write attempt fails loudly.
    - Install from an export, never from the checkout: `git archive <commit>` unpacked into `root/build`, because build backends write `build/` and metadata into the source tree. With `install = "uv-lock"`: `uv sync --locked --no-dev --no-editable` of the export with `UV_PROJECT_ENVIRONMENT=root/venv`; with `install = "requirements"`: `uv venv root/venv --python <python>` and `uv pip install --require-hashes -r plugins/hermes-adapter/tests/hermes_requirements.txt` plus the export without dependencies. Ruling for docs/DECISIONS.md: use Hermes' own `uv.lock` when the pinned commit has one; otherwise generate `plugins/hermes-adapter/tests/hermes_requirements.txt` with `uv pip compile --generate-hashes` from the export, check it in next to the pin, and let `record` regenerate it when the pin changes (name it in the Renovate note).
    - Provisioning runs with the allowlist environment of Design note 5 without proxy variables (it needs the network), with `UV_CACHE_DIR` and `UV_PYTHON_INSTALL_DIR` set to the caller's uv cache and Python directories (asked from `uv cache dir` and `uv python dir`), so repeated runs do not download again, and with a throwaway `HOME`, so no git or uv credential helper of the caller is used.

5. **Isolation** (`environment.py`, `sandbox.py`, `egress.py`, `gateway.py`). Ruling for docs/DECISIONS.md, the isolation set; each part closes one way to a real credential, a real model or another installation:

    - Throwaway homes: `ThrowawayHomes` creates under the temporary root a `home`, one Hermes home per configuration (`hermes/<profile>`), a working directory `work`, `tmp` and a shim directory `shims`; `assert_inside(root, path)` resolves symlinks and refuses any path outside the root.
    - Environment allowlist: `build_environment(homes, profile, proxy_url, extra) -> dict[str, str]` returns only `PATH` (shims first, then the venv's `bin`, then `/usr/bin` and `/bin`), `HOME`, `HERMES_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME`, `TMPDIR`, `LANG`, `TZ` (`UTC`), `PYTHONDONTWRITEBYTECODE`, `PYTHON_KEYRING_BACKEND` (the null backend of `keyring`), `NO_COLOR`, `TERM` (`dumb`), the proxy variables in upper and lower case pointing to the egress recorder, `NO_PROXY` with `127.0.0.1` and `localhost` only, and the scenario's own names (fake credentials, base URLs, as the pinned version reads them). Nothing of the caller's environment passes; in particular no API key, token, `SSH_AUTH_SOCK`, `DBUS_SESSION_BUS_ADDRESS` or cloud credential.
    - Credential stores: the shim directory holds executables named `security` and `secret-tool` that exit non-zero and record that they were called; the keyring backend is null; on Linux no D-Bus address exists in the environment, so the Secret Service is unreachable.
    - Network: the egress recorder (`EgressRecorder`, an HTTP proxy on `127.0.0.1` port 0) answers every request, `CONNECT` or absolute URI, with `403`, records only `host:port` and never forwards. On macOS the Hermes process tree runs under `sandbox-exec` with a profile that denies outbound network except to loopback (`sandbox.py`), because the macOS keychain is reachable through the system API whatever the environment says; on Linux the environment above already makes every stored credential unreachable, so a leaked request could carry only fake credentials. A fake credential reaching a real provider costs nothing; that is the guarantee, and the report states it.
    - No listener: every platform of the pinned version except the probe and every server component it offers (API server, webhook receivers, dashboards) is disabled in the throwaway configuration; after the probe connected, `HermesGateway.listening_sockets()` lists the listening TCP and UDP sockets of the process tree and the run fails on any.
    - Process: `HermesGateway` starts the foreground gateway command of the pinned CLI by absolute path with `start_new_session=True`, waits for the probe's `connect` within a named deadline, and `stop()` ends the process group (`SIGTERM`, then `SIGKILL` after the stop deadline) and fails if a member survives. Toolsets of the probe platform: exactly one built-in tool without effect outside the throwaway homes and without network (for example a todo tool or a file read inside `work`); never a terminal, code execution, web, browser, MCP, delegation or messaging tool. If the pinned version needs model metadata at start, the fake endpoint serves it; the real metadata service is never allowed.

6. **Fake model** (`fake_model.py`). `FakeModel` serves on `127.0.0.1` port 0 an OpenAI-compatible route (chat completions, streaming and non-streaming, and the model list) and an Anthropic route (messages, streaming events from message start to message stop, tool use blocks), plus any further route the pinned version needs for the configured providers, each replaying the scenario's `model_script`: per turn either tool calls or text in fixed chunks, with fixed usage numbers, optionally held on a named latch until the test calls `release(latch)`. A request that the script does not cover (titles, compression, memory) gets a fixed short answer and is recorded as `unscripted`. Each request is recorded as its shape: route, model name, sequence of roles, the texts the scenario injected (verbatim), tool names and call IDs, and for every other text only `sha256:<hex>` and its length. Credentials: `FakeCredentials` generates per run a fake API key and a fake OAuth token, in the format the pinned version uses to classify credentials if it does (random content, never written to a file outside the throwaway homes); the endpoint compares the presented header with them and records only `CredentialKind` (`api_key`, `oauth`, `none`, `unexpected`); any other value is `unexpected`, is discarded at once and fails the run. Point every provider base URL and every auxiliary model of the pinned version at this endpoint (configuration file in the Hermes home and the variables the pinned version reads).

7. **Probe plugin and control channel** (`probe_plugin/`, `control.py`). The probe is a platform plugin with `plugin.yaml` (`kind: platform`) and one module `probe.py`, the only file that imports Hermes; it uses the standard library only and registers through `ctx.register_platform(...)` in `register(ctx)`. Ruling for docs/DECISIONS.md: the probe's platform name is `recording_probe`, because the product name may appear only at the places of 02 6 and the adapter's `hermes_adapter.platform_key` belongs to M2-33. The harness copies the probe into the place of the throwaway Hermes home where the pinned version discovers plugins (record the place as a fact). The probe subclasses `BasePlatformAdapter`, reads its settings only from `PlatformConfig.extra` (or the pinned equivalent; never `os.getenv` or `os.environ`, 09 17.2): the control URL and its flags (`supports_draft_streaming`, `supports_status_text`, `enforces_own_access_policy` and the policy value). It overrides every method that 09 17.3 maps and the pinned base class offers, with the pinned signatures; each override posts `{"method", "args"}` to the control channel, returns what the base contract expects (sequential message IDs for sends, `None` from `format_tool_event`) and holds no other logic. On `connect()` it starts a loop that takes commands from the control channel and executes them: `inject` (a `MessageEvent` built with `build_source(chat_id = <channel id>, chat_type = "thread", thread_id = <thread id>, user_id = <user id>, user_name = <name>, message_id = <message id>)` as 09 17.4 prescribes, passed to `handle_message`), `interrupt` and `session` (the ways of the bullets `interrupt_outcome` and `session_switch` of Design note 9), `credential_type` (the surface of the bullet `credential_type`) and `describe` (the presence and signature of each surface of note 9, from `inspect`). `ControlServer` (on `127.0.0.1` port 0) keeps the calls in arrival order, serves each command once in order, and offers `wait_for(method, predicate)` with a named deadline.

8. **Recording, normalization and fixtures** (`calls.py`, `observations.py`, `conftest.py`, `test_recording.py`).

    - `normalize(calls, redactions)`: IDs (chat, thread, message, session, tool call) become `<id:n>` in order of first use; the temporary root and the real home become `<tmp>` and `<home>` as path prefixes, also where such a path stands inside a longer string; the host name and the user name become `<host>` and `<user>` only where they are the whole string or a whole segment of an absolute path outside `<tmp>` and `<home>`, never inside a longer token and never below `<tmp>` or `<home>`, so the normalized output does not depend on the machine or the OS user that runs it; timestamps and durations are dropped; a string is kept verbatim only if it is a scenario text, an identifier (`^[A-Za-z0-9_.:-]{1,64}$`) or a placeholder path, else it becomes `sha256:<hex>` with its length. Ruling for docs/DECISIONS.md: fixtures hold no third-party prose (system prompts, status texts and messages of Hermes are hashed), because it would copy foreign text into this repository and could carry machine details.
    - `derive_pattern(calls)`: the ordered list of calls with method, argument shape (names and types, enum-like values verbatim) and the final content of text arguments; runs of consecutive `send_draft` or `set_status_text` calls collapse into one entry with their last content. Ruling for docs/DECISIONS.md: the comparison ignores the repeat count of these two methods (it depends on chunk timing) and compares everything else exactly. `compare_patterns(expected, actual) -> list[str]` names the first difference and ends with the hint `make -C plugins/hermes-adapter record`.
    - Fixture `<scenario>.json`: `scenario`, `pin` (tag and commit), `inputs_sha256`, `calls` (normalized), `model_requests` (shapes and `CredentialKind`), `pattern`. `observations.json`: `pin`, `inputs_sha256`, `recorded_on`, `plugin_discovery`, `surface` (Design note 9 "Surface facts"), `egress` (sorted `host:port` with phase `start` or `turn`), `credential_store_calls`, and per point slug its `facts` and `holds`. All JSON with sorted keys, two-space indent and a final newline, each file below `repo.max_file_kb`; digests and commit IDs sit under names without `key`, `token`, `secret` or `password`, so gitleaks' generic rule does not read them as secrets, and no gitleaks allowlist entry is added.
    - `inputs_sha256` is the digest over `tests/hermes_pin.toml`, `tests/recording/probe_plugin/`, `tests/recording/scenarios/` and the modules of `tests/hermes_harness/`. Ruling for docs/DECISIONS.md: a change to any of them without recording again fails the offline tests, because the fixtures are evidence only while the inputs that wrote them hold.
    - Without `--record` the live test runs every scenario, derives patterns and observations and compares them with the fixtures. With `--record` (target `record` of the component Makefile: `uv run --locked pytest tests/recording --record`) it writes the fixtures, and only after every scenario passed and the integrity check held, through a temporary directory replaced at the end, so a failed run never leaves partial fixtures.
    - `limits.py` holds the named deadlines of the harness (provisioning, gateway start, a scenario step, stop grace). Ruling for docs/DECISIONS.md: these bound a test, not product behaviour, so they are named module constants and no configuration keys (the precedent of M1-73's probe); code and docs name the constant, never the number.
