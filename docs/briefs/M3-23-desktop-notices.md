# M3-23: Desktop hints over the gateway

Status: ready | Depends on: M3-19 | Milestone: M3

## Goal

After this ticket a person who sits at a connected desktop is not disturbed twice. The gateway implements the presence port `presence.View` that M3-19 declared in `internal/kernel/presence` and wired as `presence.None`: for the people the worker consumer `push` asks about, it returns one entry per device with a live gateway connection, with the focus set and the `idle` flag of the last `focus` op that M1-66 stores (04 6.2, 13 4.4, 13 12 point 4). The pure decision of M3-17 then sees the facts it was built for: a device that focuses the thread and is not `idle` stops the hint on every device ("Active in the thread"), a connected device gets the ephemeral event `notification.created` instead of a push (13 4.6 point 1, 6.3, R-PN-01), and while a `macos` or `windows` device is connected and not `idle`, pushes to `ios` and `android` devices wait `notify.mobile_delay_when_desktop_active` and are dropped when the person has read the message in the meantime (13 4.4 "Desktop active", `ReleaseDelayed` of M3-17). The outgoing port `LiveRoutes` of M3-19 gets its real implementation in `notify`: a gateway route becomes one job `notify.gateway_send` per hint and recipient, which after the commit of the round checks the rights of that moment and publishes `notification.created` through `kernel/eventlog.EphemeralPublisher` to the live connections of the recipient (audience `self`, receive action `push.deliver`, or the recipient rule of R-AZ-30 for hints without a thread); a delayed route becomes one `notify.push_send` per registration scheduled at the end of the delay, carrying the thread sequence of the message, so the send job drops it with the skip reason `read`. The two plan cases hold end to end: a thread in focus on the desktop gives no push to the phone, and a message read on the active desktop before the delay ends gives no push to the phone. With `server.role = all` (level 0 of 02 16) everything runs in one process; with separate roles or several api nodes the worker sees no live connection and every device is reached by push, as documented until M7-17 brings a shared presence state (RK-37).

12. 13. 17. Presence is an internal fact of the decision: it is never sent to another person and appears in no event, log or metric (OQ-06).
18. An ephemeral event is published only after the commit of the transaction that decided it (M2-10 Design note 8; M2-01 note 2), and the round of the consumer `push` stays the only place where hints arise (13 12 point 1, ADR 0051).

## Design notes

1. **Place, dependencies and roles** (02 3.2, 4.4, 4.5; 13 12 point 4; RK-37; Ruling for docs/DECISIONS.md). `notify` and `gateway` sit on the same top layer of 02 4.4, so neither imports the other: the gateway implements the kernel port `presence.View` (as it implements `eventlog.EphemeralPublisher`), and `notify` uses only kernel ports and its existing edges (`chat`, `sync`, `identity`). No module edge changes; `make arch` and `make register-check` stay green without a change to `architecture/modules.yaml`. The gateway lives in role `api`, the consumer `push` and job execution in role `worker` (02 3.2), so `internal/wire` wires by role:

    | `server.role` | `presence.View` | `LiveRoutes` | publisher for `notify.gateway_send` |
    |---|---|---|---|
    | `all` | `gateway/app.PresenceView` | `notify/app.liveRoutes` | the gateway's `EphemeralPublisher` |
    | `worker` | `presence.None` | M3-19's fail-closed default | none |
    | `api` | not wired (no consumer `push`) | not wired | not wired (no job execution) |

    With `None` the decision never yields `gateway` or `push_delayed` (M3-19 `TestLiveRoutes_DefaultFailsClosed`), so in role `worker` every device with a registration gets its push at once and a device without one gets nothing (13 4.6 point 3). Ruling: presence is memory of the process that holds the gateway (13 12 point 4), and only role `all` holds both; separate roles (level 1 of 02 16) and several api nodes (level 2) reach desktops only by push until M7-17 brings a shared presence state and the cross-process path of 02 11.6 (PLAN row M7-17, D-W-108 point 8). A worker without presence logs one Info line at start (`presence unavailable in this role: hints go by push only`, attribute `bothy.server.role`). With `cluster.mode = multi` and role `all` the view sees the connections of its own node only (RK-37). Write the role table into the `notify` README and 13 12 point 4.

2. **`PresenceView`** (13 4.4, 12 point 4; 04 6.1, 6.3, 7.2 point 6; Ruling for docs/DECISIONS.md). `Connections(ctx, userIDs)` returns, for each requested person that has at least one counted connection, one `presence.Connection{DeviceID, Focus, Idle}` per device; people without one are absent from the map (not an empty list). A connection counts exactly when its principal is a human (`kind = user`), it has a device (every human session is device-bound, 08), it is in phase `live` (after `catchup.complete`, 04 7.2 point 4) and it is not closing. Reason for `live`: `notification.created` is never delivered before `catchup.complete` (requirement 14), so a catching-up connection that counted as connected would get a gateway route whose frame is dropped, and the hint would be lost for that device; counted as not connected it gets its push, and the app replaces it by thread ID (13 6.1). `Focus` is a copy of the connection's `FocusSet` (the readable threads M1-66 kept after its checks and pruning), `Idle` the stored flag; a connection that never sent `focus` has an empty focus and `Idle = false`, so a connected desktop that never reported idle counts as active (13 4.4 "connected and not `idle`"). Because a device holds exactly one connection (04 6.1, `4017` closes the older one), there is at most one entry per device; if the hub briefly holds two during the replacement, keep the newer one. The read takes the hub's lock only to copy, never waits on a connection queue, allocates new slices, and returns an error only for a cancelled `ctx`. It reads no database. Agent and app connections are never returned.

3. **`LiveRoutes`** (M3-19 Design note 10; 13 4.6; Ruling for docs/DECISIONS.md). `notify/app.liveRoutes` implements both methods inside the round's unit of work (the consumer round and the flush job of M3-19); both insert jobs only, so the round keeps its rule "jobs and cursor commit together" (ADR 0051) and nothing leaves the process before the commit:

    a. `Gateway(ctx, h Hint, r domain.Route)`: insert `GatewaySend` for the hint with `jobs.Inserter.InsertUniqueTx` (M3-19 Design note 9 a), so the second and later gateway routes of the same hint (one per connected device) add nothing: one job per hint and recipient. The job publishes once with audience the recipient, which reaches every live connection of that person; at decision time those were exactly the devices with a gateway route, because `Decide` gives `gateway` to every device with a connection (M3-17 Design note 8).

    b. `Delayed(ctx, h Hint, r domain.Route)`: insert one `PushSend` per ID in `r.Registrations` with `InsertTx`, `ScheduledAt = r.NotBefore`, `DueAtUnixMicro = r.NotBefore` (13 9 row t0: "with ... desktop delay the end of the waiting time") and `ReleaseSeq = h.MessageSeq`; every other field as M3-19 fills it for an immediate push of the same hint (the same `NotificationID`, kind code, quiet flag and count; M3-17 Design note 6 keeps the quiet flag).

4. **Job `notify.gateway_send`** (02 12.1 to 12.4; 13 6.3, 9; 05 4.9 row `push.deliver`, R-AZ-29 to R-AZ-31; Ruling for docs/DECISIONS.md). Module `notify`, trigger the consumer `push` (and the flush job), queue `delivery` (it is part of push, so it keeps running in maintenance mode like `notify.push_send`, 02 12.2). Args, only IDs and `int64` (`jobs.ValidateArgsType`): `GatewaySend{NotificationID, RecipientID, ThreadID, MessageID, TargetID ids.ID; Kind, Quiet, Count, DueAtUnixMicro int64}` with the same meaning and kind codes as `PushSend` of M3-19 Design note 11 a. The handler:

    a. Step 1 in a unit of work: `now - DueAt > push.max_age`: skip `expired`. The recipient is no longer an active human: skip `no_access`. A kind with a thread: `authorize(r, push.deliver, thread)` with the principal of a human without a request, in filter mode, exactly as the send step of M3-19 Design note 11 b builds it (R-AZ-29, R-AZ-31; reuse that function, do not copy it): denied gives skip `no_access`. `security` or `admin`: the recipient rule of R-AZ-30 through the same function the send step of M3-19 uses for these kinds: false gives skip `no_access`. A kind with a thread also reads `chat.Threads.Info(ThreadID)` for the current `space_id` and `channel_id` of the scope (the thread may have moved since the decision). Commit.

    b. Step 2 outside any transaction: if this process has no publisher (role `worker`, Design note 1), skip `no_registration` and log one Warn line per process (`gateway hint without a gateway in this process`); this happens only in a deployment that mixes role `all` with separate workers, which 02 16 does not describe. Otherwise build the envelope of Design note 6 and call `PublishEphemeral` once; an error is a programming fault (M1-66) and is returned, so River retries and the alarm on failed jobs shows it.

    c. Exactly once is not promised: if the process dies after step 2 and before River marks the job complete, River runs it again and the same `nid` reaches the client twice; the client shows one hint per thread (13 6.1 replacement by thread ID). Reason: an in-memory publish cannot join a transaction, and an ephemeral event is pure acceleration (04 2.1).

    d. Every skip counts `bothy.push.skipped` with its reason (the values M3-19 defined); a publish counts nothing new (the gateway records `bothy.delivery.duration` with `bothy.event.durability = ephemeral` when it writes the frame, M1-68, which is t1 of 13 9 for this route). A connection that is not live or ended between decision and publish gets nothing and no fallback push (at most once, 04 9 point 4); its unread counters show the message on the next opening (13 4.6 point 3).

5. **Delayed push and its release** (13 4.4 "Desktop active"; M3-17 Design note 9; 03 `read_states`; Ruling for docs/DECISIONS.md).

    a. `Hint.MessageSeq` is the `thread_seq` of the message the hint points at: the `message.thread_seq` of the `message.created` payload, the `ThreadSeq` of the last agent message of a run (M3-19 Design note 5 b), the `ThreadSeq` of the newest message a flush hint points at (M3-19 Design note 9 d); zero for a hint without a message (`security`, `admin`, a run hint without an agent message).

    b. `PushSend.ReleaseSeq` is zero for every immediate push and `Hint.MessageSeq` for a delayed one. In the send use case of `notify.push_send`, after the registration and age checks and the `push.deliver` (or R-AZ-30) check of M3-19 Design note 11 b and before the provider lookup: if `ReleaseSeq > 0`, read the recipient's read position `readSeq = max(read_states.last_read_seq, threads.unread_floor_seq)` (`sync.ReadStates.PositionsFor` with an absent row read as 0, and `chat.Threads.InfoForShare` for `UnreadFloorSeq`, both of M3-19 Design note 9 d), and when `domain.ReleaseDelayed(ReleaseSeq, readSeq)` is false skip `read`. An immediate push reads nothing extra.

    c. Nothing else is re-evaluated at the end of the delay: not whether the desktop is still active, not the focus, not whether the phone connected meanwhile (13 4.4 names only "read"). A delayed push of a quiet hint stays quiet.

6. **Envelope and admission** (04 2.2; 05 section 6 row `notification.created`; R-AZ-30; M1-65 `sync.Admit`; Ruling for docs/DECISIONS.md). `EphemeralEvent` of M1-66: `Type` `notification.created`, `SchemaVersion` from the event register, no `Actor` (a job without principal), `Audience` the recipient. A kind with a thread: `Resource {kind: thread, id: ThreadID}`, `Scope {space_id, channel_id, thread_id}` from step 1. A kind without a thread: `Resource {kind: user, id: RecipientID}`, empty `Scope`. Envelope `id` a new UUIDv7, `occurred_at` the clock at publish. The hub's candidates are the connections of the audience (M1-65). `sync.Admit` stays the single admission rule: a `notification.created` with resource `thread` passes the generic path (audience equals the connection principal, then `push.deliver` on the thread in `authorize.Delivery(ctx)`), so a revocation that arrived in log order before the frame stops it (T-AZ-03); a `notification.created` with resource `user` is admitted exactly when the connection principal equals `Audience` and `resource.id`, without `push.deliver`, because 05 section 6 replaces it with the recipient rule of R-AZ-30, which step 1 evaluated with the rights of that moment, and the connection itself proves an active session of that person. The resource `user` of a hint without a thread is the core contract's (05 section 6 row `notification.created`: "for a hint without a thread the recipient (`user`)"; R-AZ-30; D-W-108 point 8).

7. **Payload** (13 6.3; R-AZ-30; ADR 0053; Ruling for docs/DECISIONS.md). `NotificationCreatedPayload`: `nid` (= `NotificationID`, the same ID as the pushes of the same hint), `kind` (from the kind code), `thread_id` and `message_id` when set, `quiet`, `count`, and the new optional `target_id` for `security` (the waiting device) and `admin` (the grant or group of the reminder), because R-AZ-30 says the payload of such a hint names the kind and the target ID and the schema had no member for it. Absent members are omitted, never `null`. Add to `docs/api/openapi.yaml`: `target_id` (`$ref: '#/components/schemas/Uuid'`, description "Target of a hint without a thread: the waiting device for `security`, the grant or group of the reminder for `admin` (R-AZ-30)."); the descriptions of `thread_id` and `message_id` ("absent for hints without a thread", "absent when the hint points at no message") and of `count` ("1, or the unread count of a bundled hint (13 4.5)"). The asyncapi message references the schema and needs no change; `make codegen-check` regenerates the server and client types.

8. **Rights and timing** (13 1 point 2, 4.2; 04 7.6; 05 4.9). A gateway hint is checked three times: at the decision (M3-19), in step 1 of the job with the principal of a human without a request, and in the hub with the connection's actor and the rights cache in log order. The second check catches a revocation committed after the round, the third one a revocation the tail has already applied. No check reads `idle` or focus: presence changes the route, never the right.

9. **No preview fields** (13 6.3, 6.4; Ruling for docs/DECISIONS.md). 13 6.3 lets the preview fields of 6.4 come with `notification.created`. Their builder (preview mode, names, excerpt, attachment count, image ticket) is part of the preview endpoint of M3-22, which needs M3-05, M3-06 and M3-07; none of them is in this ticket's closure, and M3-22 depends on M3-23 and fills these fields in `notification.created` with its preview builder (PLAN row M3-22, D-W-108 point 8). This ticket therefore sends the payload of Design note 7 without them; a live client already holds the message and its names through the synced events of the same connection and renders the hint from them. Add to 13 6.3 (English): the preview fields come from the builder of 6.4, which M3-22 adds to `notification.created`; until then they are absent and the client shows the hint from its synced data.

10. **Configuration and observability.** Keys used, all present after M3-19: `notify.mobile_delay_when_desktop_active`, `notify.coalesce_window` (through M3-19's routing), `push.max_age`, `server.role`, `cluster.mode`; read through the configuration loaded at start, never as literals. No new key, no new metric, no new `bothy.reason` value. Logs carry only `bothy.job.kind`, `bothy.reason`, `bothy.server.role` and `error.type`, never a person, device, thread, focus set or `nid`.

## Acceptance criteria
