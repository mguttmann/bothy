# M2-30: TypeScript SDK with webhook verifier

Status: ready | Depends on: M2-26, M2-29 | Milestone: M2

## Goal

After this ticket `sdk/typescript` is a complete SDK: on the generated core of M2-23 it has the same hand-layer modules as the Python SDK of M2-29 (`auth`, `gateway`, `invocation`, `runs`, `components`, `commands`, `outbox`, `retry`, `heartbeat`, `webhooks`, `testing`, 11 11.2), it runs the same shared scenarios as M2-29 (AG-08 adapter side, AG-09, AG-12, AG-28 and AZ-P6 for the SDK) against its own in-process FakeServer and against the real server in `make check`, and it verifies Standard Webhooks signatures for apps: `v1a` (Ed25519 with the keys of `getWebhookKeys`) and `v1` (HMAC-SHA256 with a `whsec_` secret) over the raw body, with the timestamp window `webhook.receiver_tolerance`, proven against every case of the test vectors that M2-26 committed. Every export carries a TSDoc comment, typedoc reports an undocumented export as an error and fails the script `lint` (gate of 23 "Documentation in code"), the typedoc reference is built in `make docs` and linked from the documentation site, and `npm run build` produces the ESM build output `dist/` that the GitHub reference app (M2-49) and later integrations use. Why: integrations in the webhook world are usually written in TypeScript (ADR 0026, option 4), R-EX-11 requires one real app per SDK, and a receiver that verifies by hand gets the raw-body rule, the time window or the constant-time comparison wrong (webhooks.md 3, RK-20); the security-critical adapter parts (token check, inbox, start only after the promise) must be built once per language and proven by the same scenarios (ADR 0026, RK-09).

Product requirements implemented here:

11. The hand layer has the modules of 11 11.2 (`auth`, `gateway`, `invocation`, `runs`, `components`, `commands`, `outbox`, `retry`, `heartbeat`, `webhooks`, `testing`) with the behaviour of the Python modules of M2-29; it sits on the generated core, which is never changed by hand (11 11.1, R-EX-10), and declares no own type for an object the core generates (ADR 0026 "Confirmation").
12. The same scenarios as M2-29 run against the TypeScript FakeServer and against the real server: AG-08 (adapter side), AG-09, AG-12 and AG-28 (acknowledgement after acceptance into the inbox, renewal of the token, a newer token of a redelivery replaces the stored one) (PLAN rows M2-29 and M2-30; 09 16.2; ADR 0026 "Confirmation").
13. AZ-P6 for the SDK: an adapter built on the SDK never starts the runtime with a missing token, a wrong signature, a foreign `aud`, an expired token, a repeated `jti`, a different `billing_mode` or a higher tool class (07 11.2; 09 4.5; T-TK-05).
14. One hand-layer function assembles the run context with trust marks as marked data blocks: `unverified` content only as marked data behind the fixed notice, file contents always as data, a transcript with the mark of its message (09 4.6, ADR 0054, SEC-AI-1), byte for byte like the Python function on shared golden files rendered with a fixed test boundary; outside tests the block boundary is random per call (M2-29 Design note 11).
15. Webhook verification after Standard Webhooks for apps, also for requests to `interactions_url`: signed content `{webhook-id}.{webhook-timestamp}.{body}` over the raw body bytes; `webhook-timestamp` within `webhook.receiver_tolerance` of the own clock; every entry of `webhook-signature` tried against the trusted keys and secrets, one valid entry suffices; `v1a` keys come from `getWebhookKeys` (`whpk_`) as a trust list and never from the request; `v1` secrets are `whsec_` values compared in constant time (webhooks.md 2, 2.1, 3; 11 7, 9, 11.2; ADR 0016; R-API-14); every case of `docs/api/webhook-test-vectors.json` verifies (PLAN row M2-30, D-M2-26-12).
16. The invocation token is checked in the adapter by points 1 to 10 of 09 4.5 with a JWKS cache that reloads once for an unknown `kid` and at most once per `adapter.jwks_refresh_min_interval`, the allow list `EdDSA`, `typ = agent-invocation+jwt`, `iss`, `aud`, time with `adapter.invocation_token_leeway`, a `jti` store and a callback for the actual mode (11 11.2 row `invocation`, 11 11.3).
17. An event with a token is acknowledged only after it passed the check (expiry excepted) and was stored with its token in the inbox; the start follows from the inbox; `403 invocation_token_invalid` is handled per `reason` (`expired`: renew, start once more; `superseded`: wait for the newer token; `invalid`: finish `failed` with `invalid_invocation_token`); `409 already_started` starts nothing; the runtime starts only after `200` (09 4.3, 4.5, 4.9; 04 15.2, 15.3; R-AG-07, R-AG-24, R-AG-25).
18. The gateway client follows 04: `hello`, `identify` with `api_token`, `consumer` and a DPoP proof when the token is bound, `resume`, heartbeat with random offset, `ack` window, reconnect with full jitter between 0 and `min(sync.reconnect_backoff_cap, sync.reconnect_backoff_base * 2^n)`, the reaction per close code of 04 6.4 (`4015` ends without reconnecting); unknown ops, fields, event types and close codes are tolerated and a received JSON `null` counts as absent (04 6.1 to 6.5, 15.1, 15.2; 06 2; ADR 0053).
19. Retries only for idempotent operations: network errors, timeouts, `5xx` and `429` with `Retry-After`; full jitter between `sdk.retry_backoff_base` and `sdk.retry_backoff_cap`; at most `sdk.retry_max_attempts` attempts; each request limited by `sdk.http_timeout` (11 11.2 row `retry`, 11 16).
20. The outbox stores `client_msg_id` before sending (replaceable store) and uses `Idempotency-Key` for other writes (11 11.2; 04 5; 06 7).
21. Errors are typed after the problem format; a `404` means "not there or not visible" and is never treated as "definitely missing"; unknown problem codes are handled by status (11 11.2; 06 5).
22. DPoP proofs with a key from a file or a key store, `DPoP-Nonce` kept and one retry on `401 use_dpop_nonce` (06 3.1; 08 7.3); the gateway proof uses the nonce of `hello` (04 6.3 point 3).
23. One warning per operation when the server sends `Deprecation` or `Sunset` (11 12; 06 13 point 4).
24. The heartbeat building block for `agent_heartbeat.v1` rejects fields that could carry secrets (11 11.2 row `heartbeat`; 09 4.8).
25. Components within the limits of 09 11.1 (approval card of 11.5, question of 11.6); commands as a declarative list reconciled on connect; autocomplete with a guard that never answers after the request expired (09 10.2, 10.5; 11 11.2).
26. ESM for the active LTS lines of Node.js; in a browser only the parts without secrets (11 11.3).
27. Documentation in code: typedoc reports an undocumented export as an error and fails the script `lint` (test with a deliberately undocumented export); the typedoc reference is produced in the build of the documentation site and linked there (23 "Documentation in code"; R-QA-14; D-W-33; PLAN row M2-30).
28. Dependencies locked with checksums; license and vulnerability gates green without a change to the allowlist (SEC-SC-1, T-SC-01).
29. Tokens, DPoP proofs, secrets and message content never appear in logs, error messages or test output (SEC-LOG-2; 04 2.2 rule 3).
30. Nothing is published to npm and no name is reserved (OQ-17).
31. During a run every REST request the SDK sends for that run carries the run's newest invocation token in the header named by `components.parameters.InvocationToken` (`Invocation-Token`), automatically; outside a run no request carries it (07 SR9; M2-29 requirement 19 and Design note 5 `bind_run`).

4. Client, auth, retry, errors and deprecation. Extend `createApiClient(options)` of M2-23 without breaking its tests; new optional members: `token`, `dpopKey` (`DpopKey` or `DpopSigner`), `timeoutMs` (default `sdk.http_timeout`), `retry` (`maxAttempts` default `sdk.retry_max_attempts`, `baseMs` default `sdk.retry_backoff_base`, `capMs` default `sdk.retry_backoff_cap`, `random`, `sleep`), `logger`, `fetch`, `userAgent` (`<app>/<version> (<platform>)`, 06 2 "Client identifier"). It passes openapi-fetch a wrapped `fetch` that per attempt:
    - sets `Authorization: DPoP <token>` and a fresh `DPoP` proof when a DPoP key is configured, else `Authorization: Bearer <token>` (06 3); a proof has header `typ = dpop+jwt`, `alg` `EdDSA` or `ES256` (signature as 64-byte `R || S`), public `jwk` only; claims `jti` (random), `htm`, `htu` (without query and fragment), `iat`, `ath` (base64url SHA-256 of the token), `nonce` when known (08 7.3). `loadDpopKey(path)` reads a PKCS#8 PEM or a private JWK file; `DpopSigner { alg; publicJwk; sign(data) }` serves key stores; `dpopThumbprint(jwk)` gives the RFC 7638 `jkt`;
    - sets the header named by `components.parameters.InvocationToken` (`Invocation-Token`) to the bound run's newest token while a run binding is set, and never outside it (07 SR9). `client.bindRun(runId, token, fn)` runs `fn` with the binding held in an `AsyncLocalStorage` (Node entry only, never `./core`); `AgentLoop` runs `handleRun`, `onFollowup`, `onInteraction` and the command handler of a `command.invoked` with `run_id` inside it and replaces the bound token after a renewal or a newer delivery (note 7). Ruling for docs/DECISIONS.md: `AsyncLocalStorage`, so two concurrent runs in one process never see each other's token; a test holds the header name equal to openapi.yaml;
    - limits the attempt with `AbortSignal.timeout(timeoutMs)`; keeps the newest `DPoP-Nonce` of any response; on `401 use_dpop_nonce` rebuilds the proof and repeats exactly once, outside the retry count (06 3.1 point 2);
    - retries only when the request is idempotent: method `GET`, `HEAD`, `PUT` or `DELETE`, or an `Idempotency-Key` header is present, or the operation is in `IDEMPOTENT_EXEMPT_OPERATIONS`, the table of every operation whose `x-idempotency-exempt` reason is `agent_runtime`, `client_id` or `read_only` (keyed `METHOD /path/template`; a test holds it equal to openapi.yaml, Ruling: these reasons promise an equal first answer per request or no state change, 06 7 point 3). Retried are network errors, timeouts, `5xx` and `429`; never another `4xx`. Attempt n (n at least 1) waits a uniform random time in [`sdk.retry_backoff_base`, min(`sdk.retry_backoff_cap`, `sdk.retry_backoff_base` times two to the power n-1)], the reading of "full jitter between base and cap" that D-M2-26-7 fixed; a valid `Retry-After` (delta-seconds or HTTP-date) raises the wait to at least its value; at most `sdk.retry_max_attempts` attempts in total.

    `ProblemError` carries `status`, `code` (the raw string), `reason`, `errors` (`FieldError`), `current`, `correlationId`, `instance`, `retryAfterMs`; `KNOWN_PROBLEM_CODES` is held equal to `x-problem-codes` by a test; an unknown code keeps its string and is classified by status (06 5; R-API-04); `isNotFound(err)` says in its TSDoc that `404` means "not there or not visible". Error messages contain status, code and operation, never a body, a token or a proof. A response with `Deprecation` or `Sunset` makes one warning per `METHOD schemaPath` and client through `logger.warn` (default `process.emitWarning` with type `DeprecationWarning`) naming the operation and both header values (11 12). `pages(fetchPage)` iterates `next_cursor` pages (06 14 point 2).

7. `AgentLoop` (`runs`), the flow of 09 4.9 for every event with a delivery field `invocation_token` (`agent.invocation`, `agent.followup`, `interaction.created`, `command.invoked`):
    - `unknown_kid`: neither stored nor acknowledged (it comes again after `agent.ack_timeout`); `replayed`: acknowledged without action; `reject`: `finishRun` with `state: failed` and the reason when the event has a `run_id` and is not a `command.invoked`, then acknowledged; `accept` or `expired`: stored with its token in the `Inbox`, then acknowledged. An inbox entry with the same event `id` whose run has not started gets the newer token instead of a second entry (09 4.3, 04 15.2 point 4). After the check, a `command.invoked` (a control command, 09 10.4) goes to the handler of `commands`, and the loop never starts, resumes or ends a run because of it; it carries `run_id` exactly when the agent has an active run in the thread (05 section 5, R-AZ-25). Any other event for a run this loop holds in `running` goes to the handle's callbacks (`onFollowup`, `onInteraction`) instead of a start, and one for a run the loop put into `waiting_input` resumes it.
    - Start from the inbox with the newest token: an expired token is renewed first with `renewInvocationToken` (its `Idempotency-Key` stored in the entry, at most one renewal per run in flight, 09 4.5.1); then `startRun` (or `resumeRun` for a run in `waiting_input`, 04 15.3 point 5) with `billing_mode_used`, `tool_class_used` and the optional members of `RunStart`. `200` (also with `Idempotent-Replay: true`) marks the entry started and calls `handleRun(run: RunHandle)` inside the run binding of note 4; `403 invocation_token_invalid` with `expired` renews and starts once more; with `superseded` the entry waits for a newer token; with `invalid` the loop finishes the run `failed` with `invalid_invocation_token`; `409 already_started`, `409 billing_mode_mismatch`, `409 tool_class_mismatch` and `403 agent_invocation_denied` drop the entry (the server already decided).
    - The runtime callback runs only after `200` (R-AG-07). After a restart the loop resumes entries that are not started (09 4.9 last paragraph). `run.cancel_requested` calls the cancel callbacks of the run's handle. `FileInboxStore` writes one JSON file per entry with mode `0600` in a directory of mode `0700` through write and rename; it never stores more than the event and its token.

8. `RunHandle` and `RunUpdater` (`runs`). `context()` calls `getRunContext`. `patch(ops)` checks every path and op locally against the table of 09 5.3 and throws `PatchPathError` without a request for anything else, including `/state`; the updater coalesces queued ops (a later `replace` of the same path replaces the earlier one, other ops keep their order) and sends at most once per `agent.run_update_min_interval` over REST `patchRun` with `base_version` (Ruling for docs/DECISIONS.md: REST, because `409 base_version_conflict` carries the document in `current`, while a gateway `error` frame has no document; `sendRunUpdate` stays available). `200` sets `base_version` to `version`; `409 base_version_conflict` sets it to `current.version` and resends the pending ops once, then surfaces the error ("start over on `409`", 11 11.2); any other problem stops the updater and surfaces. Helpers: `step(...)` adds `/steps/<uuidv7>` and replaces its `status`, `title`, `detail`, `finished_at`; `followupDelivered(messageId)` and `followupAbsorbed(messageId)`; `awaitInput(statusLine)`; `reportSession(...)` wraps `reportAgentSession` with its precondition header; `finish(...)` flushes pending ops, then sends the members of `RunFinish`, and a repeated equal end state is success. `renderContext(context, { fileTexts, boundary })` returns `{ system, trigger }` like M2-29's `RenderedContext` and produces the texts of note 2's golden files: one fixed system part separate from the trigger text, every element with author, role and trust, `unverified` content and every file content inside a marked data block behind the fixed notice, a transcript with the trust of its message (09 4.6, 17.6, ADR 0054). `boundary` defaults to 16 hex characters drawn per call with Web Crypto `crypto.getRandomValues` and is drawn again if the content contains it; it uses no `node:` import, so `./core` stays clean. It is injectable only for tests, and the golden files are rendered with a fixed test boundary. Reason: an author cannot forge the end of a block without knowing the boundary (M2-29 Design note 11, ADR 0054).

10. Webhooks (`webhooks`, Rulings for docs/DECISIONS.md). Public API, each with TSDoc and an example:
    - `parseWebhookPublicKey(value)`: `whpk_` plus standard base64 of the DER SubjectPublicKeyInfo of an Ed25519 key (D-M2-26-11); another prefix, bad base64 or another key type throws `WebhookConfigError`. `parseWebhookSecret(value)`: `whsec_` plus standard base64 (D-M2-26-10); empty or malformed throws.
    - `verifyWebhook({ body, headers, keys, secrets, toleranceMs, now })`: `body` is the raw request body as `Uint8Array` or string (a string counts as its UTF-8 bytes; never parsed and serialized again); `headers` is a `Headers` object or a plain record (case-insensitive). Steps: the three headers present, else `missing_header`; `webhook-timestamp` an integer of Unix seconds, else `invalid_timestamp`; its distance to `now()` at most `toleranceMs` (default `webhook.receiver_tolerance`) in both directions, else `timestamp_out_of_tolerance`; no key and no secret configured gives `no_trusted_key`; the header is split at spaces, each entry at the first comma, entries with an unknown scheme or bad base64 are ignored; a `v1a` entry is tried against every key with `crypto.verify`, a `v1` entry against every secret with HMAC-SHA256 and `timingSafeEqual` (length checked first); one valid entry returns `{ id, timestamp, scheme, event, syncEpoch }` with `event` decoded by M2-23's `decodeEvent`; none gives `signature_mismatch`. Errors are `WebhookVerificationError` with `code` from exactly this list; messages never contain the body, a signature or a secret.
    - `verifyWebhookRequest(request, options)`: the same for a Fetch API `Request`, reading the body once as bytes. It serves `interactions_url` requests as well (11 9).
    - `WebhookKeyCache`: fetches `getWebhookKeys` once, trusts every listed key (`next`, `active`, `retiring`), refreshes after the response's `Cache-Control` `max-age` (without the header: `agent.jwks_max_age`), and never refreshes because of an incoming request, so a forged request cannot make the app fetch. Update webhooks.md 3 point 3 with this rule ("reload the list after the `max-age` of the response; new keys appear in it beforehand as `next`").
    - Not in the SDK: storing seen `webhook-id` values (webhooks.md 3 point 4 needs the app's own storage for `webhook.retry_max_age`); the README says how an app does it. No Standard Webhooks library as dependency: the vectors were checked against the reference library and the standard library in G10 (M2-26).
