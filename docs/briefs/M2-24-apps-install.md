# M2-24: App manifest, installation and scopes

Status: ready | Depends on: M1-44 | Milestone: M2

## Goal

An owner installs an integration as an app from an uploaded manifest: the server checks the manifest against `app_manifest.v1` and the rules of 11 "Validation rules" (unknown members, scopes from the catalogue, subscribable events with their scope, `https` addresses on hosts from `webhook.allowed_hosts`, never `trigger` or `manage`, commands without reserved names), stores nothing before the owner consents, and then creates the app principal, the `apps` row and the `app_installations` row with the granted scopes and event subscriptions in one transaction with step-up, audit and a new rights version. A new manifest version is installed with a recorded difference: scopes and events it adds stay inactive until the owner consents with `setAppScopes`, while what it removes acts at once. Suspend is an emergency stop that keeps every grant, uninstall revokes tokens and grants and disables the principal. `createToken` for an app no longer answers `409 conflict` with `reason` `app_not_installed` when the app has an active installation: it issues a token shown exactly once whose scopes come from the installation (08 "API tokens for agents, apps and tools"). From then on `authz` lets an app act only with a grant on the target and a scope that both its token and its installation hold, which is AZ-M32 to AZ-M34 with a real app. This is the extension contract of ADR 0022: an app is a principal outside the server process whose reach is its token, its grants and its scopes, and the server module never loads plugin code in process.

Product requirements implemented here:

11. Extensions never run in the server process; an app is a principal of kind `app` with its own token, grants and scopes and uses only the public API (11 1 points 1 and 2, ADR 0022, D-B6).
12. A manifest is uploaded, never fetched from an address; it follows `app_manifest.v1`; unknown members are an error; it is at most `app.manifest_max_bytes`; the server stores it and its SHA-256 (11 3.1, R-EX-01, R-EX-02, 03 `apps`, 06 2 "Unknown values", SEC-IN-1).
13. Check rules: every scope is in the catalogue; every event is a durable type of 05 6 and not a personal event of another principal, and the scope of its receive action is requested; every address is `https` and its host is in `webhook.allowed_hosts`; `requested_grants` never carries `trigger` and as capability at most `upload`; commands follow 09 10 without reserved names and at most `command.max_per_principal` (11 3.2 rules 1 to 5, R-DM-08, R-DM-17, R-DM-20, R-EX-03).
14. `app.install`, `app.scopes.update`, `app.suspend`, `app.resume` and `app.uninstall` are owner only, need step-up, are audited on allow and deny, raise the rights version and use `rl.admin`; `app.read` is owner only without step-up and audit and uses `rl.read` (05 4.11, 2.4, rule 1.7).
15. Installation in one transaction: rights version first, then principal (kind `app`), `apps`, `app_installations` with `granted_scopes` and `event_subscriptions`, audit (11 4.1, 03 6.3).
16. A new manifest with the same `slug` is a difference; new scopes and events need a new consent with `app.scopes.update` and stay inactive until then; new delivery hosts are confirmed by the upgrade itself (Design note 7 g); an upgrade never adds grants (Design note 8); removed scopes, events and commands act at once (11 4.2; the command part with M2-25).
17. Suspend keeps every grant and blocks the tokens without revoking them; uninstall revokes tokens and grants and disables the principal while its messages keep their author (11 4.3, R-EX-05).
18. An app acts only with both an effective level from grants (at most `write`) and the scope of the action; no grant gives `404`, a missing scope on a visible target gives `403 scope_missing` (07 2.10, 05 2.3 point 5 and 2.6, 06 4 point 4; AZ-M32 to AZ-M34).
19. App tokens carry a subset of the granted scopes of the installation, are stored only as HMAC and shown exactly once; a replay with the same `Idempotency-Key` answers `409 conflict` with `reason` `one_time_secret` (08 12, 06 7, ID-T23).
20. An app whose installation is not `active` is unauthenticated with reason `app_not_installed` (07 4.1); a gateway connection of such an app ends with `4012` (04 6.4).
21. No JSON `null` in answers; every answer validates against `openapi.yaml` (06 2, ADR 0053).

## Design notes

1. **Where the rules live.** `apps` owns manifests, installations and their use cases. `authz` owns every rights rule: the scope table of 05 2.6 (M1-28 `domain/scopes.go`), which events an app may subscribe to (Design note 4), the scope check and the snapshot (Design notes 10 and 11), and grant revocation. `identity` owns principals and tokens and reads the installation through a port that `apps` implements, so `identity` never imports `apps` (02 4.4, edges point down). Ruling for docs/DECISIONS.md: the module `apps` may use `authz` (new edge in 02 4.4 and `modules.yaml`), because uninstall must revoke the app's grants (11 4.3) and the subscription rule needs the scope table that only `authz` holds (05 rule 1.1); `authz` is a lower layer, so the graph stays acyclic.

2. **`AppManifest` in `openapi.yaml` follows 11 3.1 field for field.** The current schema has `scopes` as a list, `event_subscriptions` and `webhooks` and lacks `min_api_version`, `delivery`, `components`, `requested_grants`, `incoming_webhooks` and `data_egress`; 03 `apps.manifest` names components and webhook URLs, and the plan's acceptance needs `requested_grants` to reject `manage`. Ruling for docs/DECISIONS.md: the YAML precedence for forms (06 header, SPEC 8) decides between two complete descriptions; here the YAML lacks members that 11 3.1, 3.2 and 03 `apps.manifest` require, so the change that finds the contradiction aligns the YAML with 11 (SPEC 13 point 5). `requested_grants` uses the shared enums on purpose, so `trigger`, `manage`, `export`, `approve_actions` and `host` reach the rule check and `validateManifest` can report them (Design note 3). Update every example that shows a manifest. Rewrite the schema with inline objects (no new component names) and `additionalProperties: false` on every object (06 2 "Unknown values", M1-18 W7):
    - required: `schema_version` (integer, enum `[1]`), `slug` (pattern `^[a-z0-9][a-z0-9-]*$`), `name`, `description`, `publisher` (strings, `minLength: 1`), `version` (string, SemVer), `min_api_version` (string, pattern `^[0-9]+\.[0-9]+$`), `scopes` (object with required `required` and `optional`, both arrays of `AppScope`);
    - optional: `homepage_url` (string), `events` (array of string), `delivery` (object, required `mode` with enum `[gateway, webhook]`, optional `events_url` and `interactions_url`), `commands` (array of `CommandRegister`), `components` (array of enum `[button, select, form]`), `requested_grants` (array of objects with required `target_kind` (`TargetKind`), `level` (`Level`), `purpose` (string) and optional `capabilities` (array of `Capability`)), `incoming_webhooks` (array of objects with required `name` and `purpose`), `data_egress` (string).

3. **Validation pipeline and answers.**
   a. Request validation (M1-18 `StageValidate`) checks the body against the schema first: unknown members, wrong types, unknown enum values give `400 validation_failed` with `errors[]` (`unknown_member`, `invalid_enum`, ...) for every operation, `validateManifest` included (SEC-IN-1).
   b. The handler reads the raw bytes of the manifest (the body for `validateManifest`, the member `manifest` otherwise) and calls the pure `domain.ValidateManifest` with an `Env` built by the app layer: catalogue facts (Design note 4), `webhook.allowed_hosts`, `app.manifest_max_bytes`, `command.max_per_principal`, `command.description_max_chars`, `principal.handle_max_chars`, `principal.display_name_max_chars` and the server's spec version (`routes.SpecVersion`).
   c. `validateManifest` answers `200 ManifestValidation` with `valid` true and `errors` empty, or `valid` false and every rule error, pointers relative to the manifest root; it stores nothing and writes no audit entry.
   d. `installApp` and `upgradeAppManifest` answer rule errors with `400 validation_failed` and the same errors with pointers under `/manifest`; when every error is a host error (Design note 5) the answer is `400 webhook_host_not_allowed` with those errors. Nothing is stored and no rights version is raised.
   e. `errors[].code` uses the M1-18 vocabulary (`required`, `invalid`, `too_large`, `too_long`, `too_many_items`); where 06 or 09 already name a reason, the item uses it as its code: `webhook_host_not_allowed` for a host, `command_name_reserved` for a reserved command name. `detail` is a short English text naming the rule (for example "R-EX-03"), never the submitted value. Ruling for docs/DECISIONS.md: points a to e.

4. **Rule set of `ValidateManifest`** (11 3.1 and 3.2), each failure one error item. Ruling for docs/DECISIONS.md: the subscribable set and the `events:subscribe` requirement, the conditional members of the delivery block, and the command rules for manifests.
    - Size: raw bytes above `app.manifest_max_bytes` give `too_large` on the root pointer and stop further checks.
    - `slug` at most `principal.handle_max_chars` characters (it becomes the handle, note 6); `name` a display name after M1-26 (not blank, at most `principal.display_name_max_chars`, `kernel/textcheck`); `description`, `publisher`, `data_egress`, every `purpose` and `incoming_webhooks[].name` pass `kernel/textcheck` (SEC-IN-4); `version` is SemVer 2.0.0; `min_api_version` is not above the major and minor of `routes.SpecVersion` (if the base lacks `routes.SpecVersion`, extend the M1-17 route generator with it exactly as M1-46 Scope item 10 describes).
    - Scopes: no duplicates; no scope in both `required` and `optional`.
    - Events: no duplicates; each event `t` must be subscribable: `authz.AppScopes.EventScope(t)` returns `subscribable` true only for a durable type of the catalogue that either has no `audience: self` and a receive action that the scope table of 05 2.6 lists (with a scope or "no scope"), or is `interaction.created` or `command.invoked` (`receivers: agent_or_app`, E-EX-05); every other type (`access.changed`, `draft.*`, `agent.invocation`, `grant.changed` with receive action `grant.read`, `host.updated`, ...) is refused (rule 1). The returned scope must be in `required` or `optional` (rule 2). `events:subscribe` must be requested when `events` is not empty (05 2.6 row "Event subscriptions"). If the generated `EventSpec` lacks `receivers`, keep the two personal types as a list in `authz/domain` with a test that compares it with `docs/spec/actions.yaml`.
    - Delivery: `delivery` is required when `events`, `commands` or `components` is not empty; `delivery.events_url` is required when `mode` is `webhook` and forbidden otherwise; `delivery.interactions_url` is required when `commands` or `components` is not empty and `mode` is not `gateway`; `data_egress` is required when `events` is not empty or `interactions_url` is set (11 3.1 column "Required").
    - Addresses: Design note 5.
    - `requested_grants`: `target_kind` not `host` (R-DM-35); `level` `read` or `write`, never `trigger` (R-DM-08); `capabilities` a subset of `[upload]` without duplicates, so `manage`, `export` and `approve_actions` are refused (R-DM-20, R-EX-03). The manifest never names a target (11 4.1).
    - Commands: at most `command.max_per_principal`; names unique (case-insensitive) and not reserved (`stop`, `status`, `new`, `resume`, `title`, `close`, 09 10.1); `description` at most `command.description_max_chars` and through `kernel/textcheck`; option names unique within a command; `scope_kind` absent or `instance` and `scope_id` absent, because a manifest never sets a target (11 4.1).
    - `components` and `incoming_webhooks[].name`: no duplicates.

5. **Addresses and `webhook.allowed_hosts`.** `delivery.events_url` and `delivery.interactions_url` are absolute URLs with scheme `https`, a host, no user information and no fragment; their host, lowercased and without port, must equal an entry of `webhook.allowed_hosts` (case-insensitive, no wildcard); otherwise the item has code `webhook_host_not_allowed` (R-DM-17, 11 3.2 rule 3, SEC-NET-2). `homepage_url` must be an absolute `https` URL; its host is not compared, because the server never loads it (11 3.1). Parse with `net/url`; patterns only with `regexp` (SEC-IN-6). 11 3.2 rule 3 offers to add a missing host "in the same confirmed action"; `webhook.allowed_hosts` is process configuration that changes only at start (configuration.md 1, 03 9), so this ticket refuses the manifest instead and changes the sentence in 11 (spec gap, Ruling for docs/DECISIONS.md).

6. **`installApp`** (`app.install`, resource `instance`, step-up, `rl.admin`, `Idempotency-Key`), in this order:
   a. `authorize(actor, app.install, instance)` before anything is loaded, so a non-owner learns nothing about existing apps: non-owners get `403 forbidden` with `reason` `owner_only`, app and agent tokens the same, an owner without fresh step-up `401 step_up_required` (07 4.2 order, SR5). Denials are audited by the authz layer, aggregated per `audit.deny_aggregate_window` (R-AZ-04).
   b. Validation of Design note 3; `reason` through `kernel/textcheck`, at most `audit.reason_max_chars` (`too_long`), required.
   c. Consent rules (`domain/consent.go`): `granted_scopes` without duplicates, every scope in `scopes.required` or `scopes.optional` and every scope of `scopes.required` present (11 4.1 "choose optional scopes"), else `400 validation_failed` with pointer `/granted_scopes` or `/granted_scopes/<i>`; `event_subscriptions` absent means none; each must be in the manifest's `events`, with `events:subscribe` and the event's scope in `granted_scopes`, else pointer `/event_subscriptions/<i>`.
   d. Generate the app principal id (UUIDv7) before the unit of work; open it with `txn.RightsChange{Action: app.install, Resource: {kind: app, id}, Principals: [id]}` (permission_version first, 03 6.3). On a reinstall (step e) declare the existing principal with `AddAffected` before its rows are written (M1-29).
   e. Lock `apps` by `lower(slug)` `FOR UPDATE`. An app with an installation that is not `uninstalled` gives `409 conflict` (use `upgradeAppManifest`). An app whose installations are all `uninstalled` is reinstalled: same principal, status back to `active` through identity, manifest columns replaced, display name updated, a new `app_installations` row; its revoked tokens and grants stay revoked. Otherwise create the principal (kind `app`, handle = `slug`, display name = `name`, status `active`); a handle already taken by a person or an agent gives `409 conflict`. A unique violation from a concurrent install maps to `409 conflict`.
   f. Insert or update `apps` (`manifest`, `manifest_version`, `manifest_sha256`, `publisher`, `homepage_url`, `updated_at`) and insert `app_installations` (`granted_scopes` and `event_subscriptions` sorted, `state = active`, `installed_by` = actor).
   g. Audit allow inside the transaction through `auditing.Recorder` (Design note 14).
   h. Commit; `201 App`. No token and no grant is created here (Design note 8). A replay with the same `Idempotency-Key` answers the stored `201` with `Idempotent-Replay: true` (M1-20).
   Ruling for docs/DECISIONS.md: handle = slug, display name = name, reinstall reuses the principal, all required scopes at install, absent subscriptions mean none.

7. **`upgradeAppManifest`** (`app.install`, resource `instance`, step-up, `rl.admin`; PUT without `Idempotency-Key`):
   a. Authorize as 6a, then load the app (unknown or not an app: `404`).
   b. Validation of Design note 3; `manifest.slug` must equal the stored slug (pointer `/manifest/slug`, `invalid`).
   c. After the no-change check of 9g, inside the unit of work (`RightsChange` with `app.install`): lock `apps` then `app_installations` `FOR UPDATE`; an `uninstalled` installation gives `409 conflict`; `suspended` stays `suspended`.
   d. No change: the stored manifest equals the new one (jsonb equality) and `granted_scopes` and `event_subscriptions` equal the request: answer `200` with the current `App`, no rights version, no event, audit with `no_change: true` (06 2 "No effect", the M1-29 pattern). A different manifest with the same SemVer precedence of `version` gives `400 validation_failed` at `/manifest/version`, because `manifest_version` names the content in the console and the audit; a lower version is allowed (rollback).
   e. Consent: `granted_scopes` of the request must be a subset of the current `granted_scopes` and of the new manifest's scopes; a scope that is not granted now gives `400 validation_failed` at `/granted_scopes/<i>` with detail "consent with setAppScopes" (11 4.2: new scopes need `app.scopes.update`). `event_subscriptions` absent means the current ones that the new manifest and the remaining scopes still allow; present, each must be current and still allowed. The result replaces the stored lists, so scopes and events the new manifest dropped act at once.
   f. Update `apps` and the display name; update the installation lists; audit allow with the difference of `DiffManifests` (Design note 14); commit; `200 App`.
   g. Hosts: the upgrade itself, run by the owner with step-up under `app.install`, is the consent for new delivery hosts (`delivery.events_url`, `delivery.interactions_url`). Every new host must already be in `webhook.allowed_hosts` (Design note 5), and the audit names it in `delivery_hosts_added`. `setAppScopes` has no host member. An existing webhook subscription keeps its URL (M2-26).
   Ruling for docs/DECISIONS.md: an upgrade never adds a grant; changed content needs a new version; identical upgrade is "No effect"; the upgrade is the consent for new delivery hosts (point g).

8. **Grants and tokens are separate steps.** 11 4.1 shows grants and an API token inside the installation transaction, but `AppInstall` has no member for the chosen targets and `App` has no secret. Grants for an app are created per target with `grant.create` (subject kind `app`, owner only per R-RE-08, M1-29 `Admin.CreateGrant`, HTTP `createGrant` of M1-48); tokens with `createToken` (Design note 10). The manifest's `requested_grants` only inform the consent. Change 11 4.1 accordingly. Ruling for docs/DECISIONS.md.

9. **Scope change, suspend, resume, uninstall.**
   a. `setAppScopes` (`app.scopes.update`, resource `app`, step-up, `rl.admin`): load (unknown `404`; a non-owner gets `404` because only owners see apps, M1-28 visibility of kind `app`); `authorize`; no-change check of 9g; `RightsChange`; lock `apps` and the installation; `uninstalled` gives `409 conflict` (add `409` to the operation in `openapi.yaml`); `granted_scopes` must be a subset of the manifest's scopes (required ones may be dropped after the install; the app then fails with `scope_missing`); scopes not granted before are the new consent; `event_subscriptions` absent means the current ones that the new scopes still allow, present it replaces them under the rules of 6c; equal lists are "No effect"; audit; `200 App`.
   b. `suspendApp` (`app.suspend`): `active` to `suspended`; on `suspended` "No effect" (`204`, audit `no_change: true`); on `uninstalled` `409 invalid_state_transition`. Tokens stay unrevoked; they stop working because the installation is not `active` (Design note 11). `204`.
   c. `resumeApp` (`app.resume`): `suspended` to `active`; on `active` "No effect"; on `uninstalled` `409 invalid_state_transition`. `204`.
   d. `uninstallApp` (`app.uninstall`, `ReasonBody`): `active` or `suspended` to `uninstalled` with `uninstalled_at` and `uninstalled_by`; in the same unit of work, in this order after the installation row: revoke every active token through `identity.Tokens.RevokeAllForPrincipal` (M1-44), revoke every active grant with subject the app through `authz.Admin.RevokeSubjectGrants` (no `authorize` per grant: it is a consequence of the authorized `app.uninstall`; rows in ascending `id`, `revoked_by` the actor, `revoke_reason` the reason; if the base writes `grant.changed` in `RevokeGrant` (M1-48), write it here too), set the principal `disabled` through identity; the app's messages keep their author (11 4.3). On `uninstalled` "No effect" (`204`). `204`.
   e. Every change of a to d runs in one unit of work with `txn.RightsChange{Action, Resource: {kind: app, id}, Principals: [app]}`; the no-change answers are decided before it (point g); the M1-29 hook writes `access.changed` for the app where its visible targets differ (Design note 11).
   f. Later tickets extend these use cases with their parts of 11 4.3 (M2-25 commands and components, M2-26 deliveries and subscriptions, M2-27 incoming webhooks); the README lists them.
   g. "No effect" comes before the rights change. Phase 1 of a `RightsChange` unit of work always raises `permission_version` (02 8.1, M1-13), and R-API-27 forbids a rights version for a no-op. So `upgradeAppManifest`, `setAppScopes`, `suspendApp`, `resumeApp` and `uninstallApp` first, after `authorize`, open a unit of work without `RightsChange`, load `apps` and the installation and check the no-change condition (7d, 9a to 9d). If it holds, they write the allow audit entry with `no_change: true` there and answer. Otherwise that unit of work ends without a write, the `RightsChange` unit of work of e opens, locks as described and checks the condition again. If a concurrent request made the same change first, it finishes as no-change (the one extra version step is rare and harmless; same pattern as M1-45 step 3 and M1-48 `revokeGrant`).
   Ruling for docs/DECISIONS.md: no-change answers, decided before the `RightsChange` unit of work (point g), and `409 invalid_state_transition` for the transitions above, `409 conflict` for scope changes and upgrades of an uninstalled app.

10. **App tokens and scope check** (decides the open points of 08 12).
    a. `createToken` for a principal of kind `app` (after the M1-44 steps up to `authorize`): `identity.AppInstallations.LockActiveInstallation(app)` inside the unit of work; no active installation (none, `suspended`, `uninstalled`) keeps `409 conflict` with `reason` `app_not_installed`. Body `scopes` absent or empty: the token stores the installation's `granted_scopes` at this moment; present: every scope must be in `granted_scopes`, without duplicates, else `400 validation_failed` at `/scopes/<i>`. Expiry, `dpop_jkt` (required only when `app` is in `auth.dpop_required_for`), one-time secret and audit as M1-44, with the stored `scopes` added to the audit details. The share lock serializes with an uninstall that holds the installation row `FOR UPDATE`, so no live token is created for an uninstalled app.
    b. Authentication of an app token (the API token path of M1-44): `ActiveInstallation(app)`; not active gives an actor with zero `InstallationID`, so `authorize` answers `unauthenticated` with reason `app_not_installed` (M1-28 liveness rule; HTTP `401 unauthenticated`); active gives `InstallationID`, `GrantedScopes` from the installation and `TokenScopes` from the token. Read on every request, no cache (AZ-P9 style).
    c. Scope check in `authz` (05 rule 1.1): an app request needs the action's scope in `GrantedScopes` and in `TokenScopes`; missing in either gives `forbidden` `scope_missing`. A check without a token (`TokenID` zero, for example a webhook delivery of M2-26) uses `GrantedScopes` alone. `Scope` filters lists for apps with the same rule. Agents stay unchanged (no scope check).
    d. Consequence: removing a scope from the installation acts on the next request of every token; a scope granted later needs a new token (rotation as 08 12: create the new token, switch, revoke the old one).
    Ruling for docs/DECISIONS.md: points a to d; it replaces the M1-28 ruling that token scopes are not evaluated.

11. **Installation state on long-lived connections.**
    a. The installation is part of the credential: `AuthenticateAPIToken` (used by REST and by the gateway `identify`, M1-64) applies 10b; put the installation check into the identity function that every API token check calls, so `Revalidate` (M1-65) inherits it; if `Revalidate` exists on the base, it also fails with `app_not_installed` when the installation is no longer active, or when the actor's `GrantedScopes` hold a scope the installation no longer grants.
    b. The rights snapshot of an app principal whose installation is not `active` is empty, like the snapshot of a principal that is not active: identity's `PrincipalSource` sets `PrincipalFacts.AppInstallationActive` from `AppInstallations.ActiveInstallation`, and the authz snapshot builder applies it. Then `app.suspend` and `app.uninstall` remove every visible target of the app, and `app.resume` adds them again, so the M1-29 hook writes `access.changed` for the app and the gateway runs `Revalidate` on it (M1-65 "Revocation" step a) and closes the connection with `4012` (04 6.4).
    c. Known gap, not built around: a change of `granted_scopes` alone changes no visible target (07 2.10), so 04 8.2 writes no `access.changed`, and an open gateway connection of the app learns a removed scope only at its next `identify`, `resume` or `Revalidate`. REST and webhook deliveries (checked per attempt, M2-26) see it at once. Record it in the report as a spec gap of the core contract (04 8.2).
    Ruling for docs/DECISIONS.md: points a and b as the answer to "how long-lived connections recheck the state of the installation" (08 12).

## Acceptance criteria

- [ ] The nine operations `listApps`, `installApp`, `validateManifest`, `getApp`, `upgradeAppManifest`, `setAppScopes`, `suspendApp`, `resumeApp` and `uninstallApp` are enabled and registered; AZ-P1 passes.
- [ ] `AppManifest` in `openapi.yaml` follows 11 3.1; invalid manifests are refused: an unknown member, `manage` in `requested_grants` and a host outside `webhook.allowed_hosts` (`webhook_host_not_allowed`); `validateManifest` reports rule errors with `valid` false and stores nothing.
- [ ] The installation runs in one transaction with step-up, audit and a new rights version, creates principal, `apps` and `app_installations` and no token; owners only.
- [ ] `createToken` for an app with an active installation issues a token with scopes from the installation, shown exactly once (replay `409 conflict` with `reason` `one_time_secret`); without an active installation it keeps `409 conflict` with `reason` `app_not_installed`.
- [ ] New scopes of an upgrade stay inactive until `setAppScopes`; removed scopes act on the next request; the upgrade's audit entry carries the difference.
- [ ] Suspend blocks the app without revoking tokens or grants; resume restores it; uninstall revokes tokens and grants and disables the principal; suspend and uninstall write `access.changed` for an app with grants.
- [ ] AZ-M32 to AZ-M34 pass with a real app (tier 1 always, tier 2 when M1-56 and M1-57 are on the base); app requests need the scope in token and installation.
- [ ] The server module cannot import `plugin` (`make lint` fails on it).
- [ ] 11, 08, 07, 02, the threat model, `modules.yaml`, the READMEs and `docs/DECISIONS.md` describe the behaviour; the report lists the gateway gap of Design note 11c as a spec gap.
- [ ] `make check` is green.

## Definition of done

- Code and tests as specified; doc comment on every public symbol (purpose, parameters, return value, errors, example where useful); comments explain why.
- READMEs of `apps`, `identity` and `authz` updated (ports `Apps`, `AppInstallations`, `AppScopes`, `Admin.RevokeSubjectGrants`, the token scope rule, the snapshot rule, the new edge, the parts of 11 4.3 that M2-25 to M2-27 add).
- Rulings of Design note 18 recorded in `docs/DECISIONS.md` (one row each with reason); the changes to `openapi.yaml`, 11, 08, 07, 02 and the threat model of the Scope made in the same change.
- `services/server/CHANGELOG.md` entry under 'Unreleased'.
- An ADR only if you take an architecture decision beyond this brief (MADR 4 as in `docs/adr/0000-template-madr-4.md`, headings and text in English, next free number, `make adr-index`).
- `make check` green.
- An independent code review over the diff, then the red team gate (`docs/quality/red-team-gate.md`, verdict `JA` or `NEIN`); on `NEIN` fix with a test per finding and have the delta checked again. Record both verdicts. Name the milestone's red team point "exceeding the scopes of an app" and T-PL-01 in the request.
- Land the change as `AGENTS.md` ("How work lands on `main`") describes: a pull request from this branch, squash-merged only when review, red team and `make check`, `ci-ok` and the review threads are green; then `git worktree remove`.
