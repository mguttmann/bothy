# M2-34: Claude Code runner core

Status: ready | Depends on: M2-03, M2-12, M2-29 | Milestone: M2
## Goal

After this ticket `plugins/claude-code-runner` is a working reference adapter: a Python process on the M2-29 SDK that serves dev forums with a project binding (M2-03). It resolves each binding's opaque `workspace_ref` under `runner.projects_root` (symbolic links resolved, nothing outside) and reports the readiness of every bound forum it serves in its heartbeat; it accepts an `agent.invocation` only with a valid invocation token and a configured tool class not above the token's `tool_class`; it proves the actual billing mode for every run with `claude auth status` in the run environment right before `startRun` and checks it again with `system/init.apiKeySource`, so a run in `organization` without a key never falls back to a subscription; it starts exactly one `claude -p` turn per run, in its own process group, with an environment built as an allow list and a command line that equals the table of 09 "Process contract" for `chat`, `scoped` and `host`, and reports the configured class as `tool_class_used`; it hands the server's context to the runtime with trust markers, `unverified` content only as marked data and files only as data (ADR 0054); it reads the stream into the live box, answers in the thread, proposes the title once per new session and reports the cost of each run as the difference of the cumulative session values. Why: the runner is the reference for dev forums (01 "Dev forum with project binding and runner agent"), and every guarantee of the adapter contract (I3, I5, SR2, ADR 0054) only holds if the adapter enforces it by construction instead of assuming it (D-R-RUNNER). Tests run against Fake-Claude, an executable that plays stream-json fixtures, and the SDK FakeServer; the installed CLI runs only behind an explicit switch because a real turn costs money. This is the runner side of AG-20, AG-30, AG-11, AG-08, BR-12, BR-05, BR-13 and AZ-P6; M2-35 adds follow-ups over stdin, the stop, compaction and the error paths of 09 "Error paths", M3-12 answer attachments.

Product requirements implemented here:

11. A turn is one `claude -p` process with the base command line of 09 18.2 and the flags of exactly one tool class from the table there: `chat` gives `--permission-mode dontAsk --tools "" --disallowedTools "mcp__*"`, `scoped` gives `--permission-mode dontAsk --allowedTools <named tools>`, `host` gives `--permission-mode bypassPermissions`; `--permission-prompts none` is always set (09 18.2, R-AG-21, R-AG-23, D-W-16).
12. The tool class is the configured one: it is reported as `reported_tool_class` in the heartbeat and as `tool_class_used` in `startRun`; a configured class above the token's `tool_class` (order `chat` < `scoped` < `host`) starts nothing and ends the run `failed` with `tool_class_mismatch` (09 4.5 point 10, 2.4, 07 2.11, AG-30, AZ-P6).
13. The environment of a turn is an allow list, never a deny list: `HOME`, `USER`, `LOGNAME`, `SHELL`, a cleaned `PATH`, `LANG`, `LC_*`, `TERM`, `TMPDIR`, optionally `SSH_AUTH_SOCK`, plus the variables of the mode (09 18.2, 18.3); the runner never reads, copies or writes login files of a runtime (09 18.3, 10 10.2, I5).
14. The actual mode is proven per run: the pre-check `claude auth status` in the run environment binds the start, `system/init.apiKeySource` is the counter-check; a mismatch or an undeterminable mode starts nothing or interrupts the turn with SIGINT and reports `billing_mode_mismatch`; `organization` without a key never falls back to a subscription and ends `runtime_not_authenticated` (09 18.3, 10 7, R-AG-20, AG-11, BR-05, BR-12).
15. The runtime starts only after `200` on `startRun`; the adapter check of the token (09 4.5 points 1 to 7) is the SDK's; an invalid token starts nothing and reports `invalid_invocation_token` (R-AG-07, 09 4.9, AG-08, AZ-P6, T-TK-05).
16. The context comes only from `getRunContext`; content with `trust = unverified` reaches the runtime only as marked data with a fixed notice before the block; the context is a fixed system part separate from the text of the triggering person; file contents are always data, also when the triggering person uploaded them; a transcript carries the trust of its message (09 4.6, ADR 0054, SEC-AI-1, AG-20, T-AI-01, T-AI-03).
17. A project is a forum with a binding the runner serves; `workspace_ref` resolves to a directory under `runner.projects_root`, never outside it, also not through symbolic links; readiness (directory present, Git working tree, rights fit) is reported per bound forum in every heartbeat (09 18.1, 4.8, M2-03).
18. A thread is one Claude Code session: `--session-id <uuid>` while the session is new or not started, `--resume <uuid>` once it is started; `started = true` is reported after `system/init` (09 18.1, 9.1, 18.4).
19. File locks per session and per thread with a wait of at most `runner.session_lock_wait`; at most `runner.max_parallel_runs` turns; an own process group per turn; stream and stderr kept per session in `runner.state_dir` for `runner.stream_log_retention` (09 18.2).
20. The live box follows the stream after 09 18.4 through `patchRun`, throttled by the SDK to `agent.run_update_min_interval`; the title is proposed once, after the first completed run of a new session (09 12 point 5, 18.4).
21. The cost of a run is the difference of the cumulative `result.modelUsage` of the session per model, reported as `RunFinish.costs` and labelled an estimate by the server (09 18.7, 4.10, 10 12.1).
22. The API key and the agent token appear in no log line, no request body, no file of `runner.state_dir`, no argument and no prompt of a turn; the key reaches the turn only as `ANTHROPIC_API_KEY` (BR-13, I5, SEC-LOG-2).
23. A failed or interrupted turn is never repeated automatically (09 1 point 5, R-AG-17).
24. Real model calls only behind an explicit switch (09 16.1, PLAN 3 point 5).

## Design notes

0. **Start check.** Run `make check` on the fresh worktree; red gives `Verdict: BLOCKED base branch red`. Confirm: M2-03 is merged (`docs/api/openapi.yaml` has `ProjectRunnerConfig` and `ChannelBehavior.project_binding`); M2-29 is merged (`sdk/python/src/bothy_sdk/` has the hand layer and the FakeServer). 1. **Process model.** One Python process per agent token, asyncio throughout (the SDK is asynchronous first, 11 11.3), POSIX only (Linux, macOS): process groups, `flock` and the signals of 18.6 have no equivalent the spec names for Windows, so `run` refuses other platforms with a start error. Names avoid the product name (02 6 lists the only places for it; the runner is listed nowhere), so the package is `claude_code_runner`, the heartbeat names `claude-code-runner` and `claude-code`, and the only product-name strings in the component are the SDK's distribution and import names, which M2-23 listed as a kind of 02 6. Ruling for docs/DECISIONS.md.

2. **Configuration.** One TOML file given by `--config`, read with `tomllib`; keys nested by their dots (`[runner]`, `[adapter]`, `[sdk]`). Unknown keys, wrong types, missing required keys and invalid durations (form of configuration.md 2: number plus `ms`, `s`, `m`, `h`, `d`) abort the start with a message that names key and file, never a value (configuration.md 3). `secret_ref` values follow 16 5.2 with the schemes `file` and `env`; values are read fresh for each use and never cached in an object that can be printed (a wrapper type whose `repr` and `str` write `[redacted]`).     The existing keys of 09 21 with Place Runner, `adapter.invocation_token_leeway`, `adapter.jwks_refresh_min_interval`, `agent.run_update_min_interval` (the adapter's own throttle) and the `sdk.*` keys are read from the same file and passed to the SDK. Ruling for docs/DECISIONS.md: the thirteen keys and TOML.

3. **Start.** Read the agent token, build the SDK client for `runner.server_url` (DPoP key if set); read `getMe` and require a principal of kind agent, whose id is the expected `aud`; build the SDK's adapter configuration with `runner.instance_id` as the expected `iss` (the SDK compares it with `getDiscovery` and stops on a difference, M2-29: 09 4.5 point 4 says "the configured instance"), the agent id, `runner.consumer`, `runner.state_dir` and the names and versions of note 15; probe `claude --version` (Design note 15); load all served channels with `listServedChannels` into the channel cache; compute readiness (Design note 6); connect the SDK gateway with `runner.consumer`; send the first heartbeat after the connection is ready. Existing turn records in `runner.state_dir/turns/` are logged with the code `orphan_turn_found` and left for M2-35; their locks are held by their processes (Design note 11), so no second turn of that session starts.

4. **Acceptance of `agent.invocation`** (09 4.3, 4.5, 4.9). The runner is a handler of the SDK's run loop (expected `bothy_sdk.adapter`: acceptance into the inbox, `ack`, a prepare step before the start, renewal and `startRun`, an execute step after `200`); it never rebuilds that loop. Acceptance, first failure wins; a refusal is `finishRun` with `state = failed` and the reason, then `ack` (09 4.3: a run refused with `run.finish` counts as accepted):

    a. The SDK verifier, points 1 to 7 of 09 4.5 with `adapter.invocation_token_leeway` and `adapter.jwks_refresh_min_interval`: invalid gives `invalid_invocation_token`; a missing `kid` after the reload is neither acknowledged nor answered (4.5); an expired but otherwise valid token is accepted (renewal before the start). A repeated `jti` is ignored (point 7). The optional allow list of point 9 stays off: I1 and I2 are decided by the server and carried by the token.
    b. Point 10: the actual tool class the runner gives the SDK is `runner.tool_class`; above the claim `tool_class` the SDK refuses with `tool_class_mismatch`. Nothing else runs, Fake-Claude is never called (AG-30).
    c. Point 8: the desired mode is the claim `billing_mode` (never the payload member). The actual mode the runner gives the SDK at acceptance is the desired one when it may run it (`organization` always, because the key is read and proven right before the start; `personal` only with `runner.allow_personal`), else `unknown`, which the SDK refuses with `billing_mode_mismatch` (the runner never uses a subscription it was not allowed to, RK-13). The binding evidence comes in prepare (note 8), right before the start, because it must describe the environment the turn will use (10 7: "binding for the start"); when the SDK asks again at the start, the runner answers the mode of that evidence, or `unknown`.
    d. Otherwise the SDK stores event and token in its durable inbox in `runner.state_dir` (expected `SqliteInboxStore`, mode `0600`) and acknowledges; a redelivery replaces the stored token (09 4.3).

    Ruling for docs/DECISIONS.md: b and c, and no allow list.

5. **Prepare, start and execute** (09 4.9, 18.11). Prepare runs, in this order:

    a. `trigger_kind` other than `message` gives `adapter_error`: the runner registers no commands and builds no components.
    b. The channel must be a forum the runner serves with a binding in the channel cache; when the payload's `settings_version` is newer than the cached one, reload it first with `getServedChannelConfig`. No binding gives `adapter_error` with the log code `project_not_bound`.
    c. While `degraded` with `runtime_unreachable` or `runtime_version_unsupported` (note 15): `runtime_error`.
    d. Resolve the project (note 6); failure gives `adapter_error`.
    e. Take the thread lock, then the session lock (note 11), waiting at most `runner.session_lock_wait`; a timeout gives `adapter_error` with the log code `session_busy`. Then a slot of `runner.max_parallel_runs`.
    f. Load the context (`getRunContext`; a `404`, or `403 invocation_token_invalid` with `reason` `run_inactive` because prepare runs inside the run binding (note 13, M2-14 note 4c), means the run is no longer active: end without a start and without `finishRun`).
    g. Download the attachments of the triggering message (note 10).
    h. Build the run environment (note 7) and run the pre-check (note 8); a non-start outcome ends the run with its reason.
    i. Return the start options: `model` and `external_session_ref` (note 9) and `billing_evidence` (note 8).

    The SDK then renews an expired token (4.5.1), calls `startRun` with `billing_mode_used`, `tool_class_used = runner.tool_class` and the start options, and handles every answer as the `reason` table of 09 4.5 says (`expired` renews once and starts once more; `superseded` keeps the entry; `invalid` finishes `invalid_invocation_token`; `409 already_started`, `409 billing_mode_mismatch`, `409 tool_class_mismatch` and `403 agent_invocation_denied` start nothing). Only after `200` does execute run: write the turn record and start the turn (notes 9 to 14). After a restart the SDK closes entries of started runs without a call, so such a run ends `interrupted` (4.9). An end without a start in prepare (a to h) must finish the run with exactly the reason named there; if the merged SDK has no way for a handler to end a run with a given reason without a start (M2-29 maps only exceptions of execute to `runtime_error` and `adapter_error`), add one to its run loop, for example an exception `RunRefused(reason)` that prepare raises and the loop answers with `finishRun` `failed` and that reason and a closed entry, with a test and a line in `sdk/python/CHANGELOG.md`, instead of calling `finishRun` beside the SDK. In execute the runner ends every run itself with the run handle's `finish` (state, reason, metrics, costs). Every path releases slot and locks (one per-run object opened in prepare and closed when execute ends or the SDK reports that the run did not start). Ruling for docs/DECISIONS.md: this order.

6. **Workspace and readiness** (09 18.1). `resolve(workspace_ref)`: refuse a value that is empty, absolute, starts with `~` or `-`, contains `\`, a drive letter with colon or a `..` segment (defence in depth after M2-03 note 4); join with the real path of `runner.projects_root`, take `os.path.realpath`, and require a strict descendant of the root (`os.path.commonpath`). The resolved real path is used as working directory, never the joined one. Ready means: resolved, a directory, `.git` exists in it (directory or file, so linked worktrees count), and the runner user has read, write and search rights (`os.access`). Not ready carries a log code: `outside_root`, `workspace_missing`, `not_a_git_worktree`, `not_writable`. Readiness is computed at start, after every channel cache change and before every heartbeat. Ruling for docs/DECISIONS.md.

7. **Run environment** (09 18.2, 18.3). Built from scratch, never by removing from `os.environ`:

    - `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `TERM`, `TMPDIR` and every `LC_*` from the runner's environment when present; `HOME` missing aborts the start.
    - `PATH` cleaned: entries kept in order only when absolute, existing directories, not writable by group or others, without duplicates; empty entries and `.` dropped. `runner.claude_bin` is looked up in this `PATH` and its absolute path is used. Reason: a writable directory on the path lets another account plant a program.
    - `SSH_AUTH_SOCK` only with `runner.forward_ssh_agent` (T-DEV-01: an agent socket gives the turn the runner user's keys).
    - `organization`: `ANTHROPIC_API_KEY` read from `runner.anthropic_api_key_ref` for this run (missing or empty gives `runtime_not_authenticated` without any CLI call, BR-12) and `CLAUDE_CONFIG_DIR = <runner.state_dir>/claude-config/organization`, created empty with mode `0700` and never written by the runner. `personal`: neither variable, and `HOME` stays the runner user's own, whose login is the person's (10 10.2); the README tells the operator to enable `runner.allow_personal` only when the runner runs as the account of the agent's `credential_holder`, because I1 and I2 then guarantee that only this person triggers (21 1). The variables `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_PROFILE`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` and `CLAUDE_CODE_USE_FOUNDRY` are never set, because they are not on the list.

    Consequence to document in the README: sessions of `organization` live in the runner's own configuration directory and sessions of `personal` under `HOME`, so after a switch of the mode (I4) `--resume` does not find the earlier session; M2-35 handles a missing session (fail open). Ruling for docs/DECISIONS.md.

8. **Pre-check and evidence** (09 18.3, 10 7). Run `<claude_bin> auth status` with the run environment, working directory the project, stdin closed, time limit `runner.cli_probe_timeout`. Parse stdout as one JSON object and read `authMethod`; anything else (no JSON, member missing, unknown value, start failure, time limit) is `unknown`. The exit code is ignored, because `none` may come with a non-zero exit. Outcome, first match wins:

    | Desired | `authMethod` | Outcome |
    |---|---|---|
    | `organization` | `api_key` | start |
    | `personal` | `claude.ai` or `oauth_token` | start |
    | any | `none` | `runtime_not_authenticated` |
    | any | every other value, and `unknown` | `billing_mode_mismatch` |

    `billing_evidence.key_type` follows `authMethod` alone: `api_key` and `api_key_helper` give `api_key`, `claude.ai` and `oauth_token` give `oauth`, `third_party` gives `cloud`, `none` gives `none`, everything else `unknown` (09 4.8, 10 7: an unknown mode counts as different from every desired mode). `billing_evidence` in `startRun` is `{provider: anthropic, key_type, method: claude_auth_status}`; never a value or prefix. A non-start ends the run with `finishRun` `failed` and the reason, without `startRun` and without a turn (AG-11, BR-05). Ruling for docs/DECISIONS.md: the table, including that `none` is `runtime_not_authenticated` (09 5.2) and that the CLI is never called for `organization` without a key.

9. **Command line** (09 18.2), an exact argv list, built by a pure function:

    ```text
    <claude_bin> -p --input-format stream-json --output-format stream-json --verbose
      --replay-user-messages --model <model> (--session-id <uuid> | --resume <uuid>)
      <class flags> --permission-prompts none [--add-dir <thread inbox>]
      --append-system-prompt-file <system prompt file>
    ```

    - Class flags are exactly the cell of the class in the table of 18.2, split like a shell would: `chat` gives `--permission-mode dontAsk --tools` with an empty argument and `--disallowedTools mcp__*`; `scoped` gives `--permission-mode dontAsk --allowedTools` followed by one argument per tool (variadic, no joining), and `--allowedTools` is omitted when the list is empty; `host` gives `--permission-mode bypassPermissions`. A pure function `class_flags(tool_class, tools)` returns them, so the test of the table compares it directly. The order of the flags has no meaning to the CLI; 18.2 gets this order (note 19).
    - Tools of `scoped`: the entries of `runner.scoped_allowed_tools` that also appear in the binding's `runner_config.allowed_tools` when the binding has that member, otherwise all of them, in the order of the runner key. `allowed_tools` never widens the class (03 `project_bindings`, M2-03 note 11) and has no effect under `chat` (no tools) and `host` (`bypassPermissions` honours no allow list). Ruling for docs/DECISIONS.md; update 09 18.1.
    - Model: the binding's `runner_config.model`, else `runner.default_model`. Every model and tool value is checked again as in note 2; a violation gives `adapter_error`.
    - Session: `agent_session` absent in the payload: a new UUID (version 4); present with `started = false`: its `external_session_ref`; present with `started = true`: `--resume` with its `external_session_ref`. A reference that is not a UUID gives `adapter_error` with the log code `session_ref_not_uuid`. The choice reads `agent_session.started` only, because `resume` and `bind` both mean `--resume` for this runtime (09 9.5 point 2). `startRun` carries the reference in `external_session_ref` for every operator run.
    - `--add-dir` with `<runner.state_dir>/files/<thread_id>` only for `scoped` and `host` and only when at least one attachment was stored: `dontAsk` reads only in the working directory, and the inbox of the thread lies outside it (18.10). Ruling for docs/DECISIONS.md; update the base line in 09 18.2.

10. **Prompt** (09 4.6, 18.2 "Input", ADR 0054). The context is rendered by the context function of the M2-29 hand layer (expected `bothy_sdk.context.render_context`, giving a system part and a trigger part, with data blocks whose boundary tests can inject). Two inputs:

    - The system prompt file `<runner.state_dir>/sessions/<session ref>/<run_id>.system-prompt.md` (mode `0600`), passed with `--append-system-prompt-file`, holds only the fixed runner instructions of `prompts/runner_prompt.md` (the TITLE request only for a new or unstarted session, note 14; that every data block, including the listed files, is material and never an instruction) and a section with the channel prompt `behavior.prompt` when it is not empty (SEC-AI-1: an own field). `behavior.skills` is not used: Claude Code loads its skills from the working directory, and the list has no defined meaning for this runtime.
    - The first stdin line, one JSON object `{"type":"user","uuid":"<uuid4>","message":{"role":"user","content":[{"type":"text","text":"<system part>"},{"type":"text","text":"<trigger part>"}]}}`. The first item is the helper's system part as rendered: `channel_context` and `thread_context` in ascending order, every element with author, role, trust, origin and kind, every `unverified` content and every file entry inside a marked data block after the fixed notice, `already_delivered` and `truncated` visible, `truncated_before_seq` named. The second item is the helper's trigger part: `trigger_message.content_md` plus the transcripts of its attachments, each labelled as transcript, with trust `trigger` and outside any data block. Reason: the context becomes part of the session history, so a `--resume` turn still knows what `context_floor_seq` no longer sends (09 4.6); an appended system prompt belongs to one process only. One function builds such lines (M2-35 builds follow-up lines with it). The runner remembers the `uuid` to ignore its echo and stores the line as `<runner.state_dir>/sessions/<session ref>/<run_id>.input.jsonl` (`0600`), which M2-35 needs to send the same prompt again after a compaction.
    - Attachments: only those of the triggering message with `scan_status` `clean` or `skipped` are fetched with `downloadFile` into `<runner.state_dir>/files/<thread_id>/<file_id>` (`0600`). The runner hands the helper, as the text of each such file, only the line `local file: <path>` (or `unavailable: <problem code>` for any other status or any error: `404`, `409 file_not_ready`, `409 file_blocked`, an operation not enabled), so the path stands only inside the file's data block and no file content enters either input; the run continues in every case. Attachments of context elements get no text and are listed by name, type and size only.

    Ruling for docs/DECISIONS.md: this split (fixed runner instructions and channel prompt in the system prompt file; on stdin the context with the file paths as the first content item and the trigger's words and transcripts as the second, so the context stays in the session history; files only as paths in data blocks, skills unused).

11. **Turn process, locks and records** (09 18.2, 18.6). Start with `subprocess.Popen(argv, cwd=<resolved project>, env=<note 7>, stdin=PIPE, stdout=<stream file>, stderr=<stderr file>, start_new_session=True, pass_fds=<lock fds>, close_fds=True)`; never a shell. Stream and stderr go to `<runner.state_dir>/sessions/<session ref>/<run_id>.stream.jsonl` and `.stderr.log` (`0600`), not to pipes, so a turn survives a restart of the runner (18.2 "Detachment") and the files are the transcript. Locks are `fcntl.flock` on `<runner.state_dir>/locks/thread-<thread_id>.lock` and `session-<ref>.lock`, taken in this order with non-blocking attempts every `runner.poll_interval` until `runner.session_lock_wait`; their descriptors are inherited by the turn, so a lock lives as long as the turn even when the runner dies (no second turn of the session, 18.2 "Locks"). The turn record `<runner.state_dir>/turns/<run_id>.json` holds run, thread, channel, session reference, pid, process group, start time and the file paths, never a token. The termination primitive `terminate(group)`: SIGINT to the group, wait `runner.stop_grace`, SIGTERM, wait `runner.kill_grace`, SIGKILL (18.6); M2-35 reuses it for the stop. The `# nosec` markers that bandit needs on the `subprocess` import and the `Popen` call carry a comment with the reason (argument list, no shell, program from the cleaned `PATH`). Files older than `runner.stream_log_retention` under `sessions/` and `files/` are deleted at start and after every turn. Ruling for docs/DECISIONS.md: files instead of pipes, polling the stream file every `runner.poll_interval`, locks inherited by the turn, retention of downloaded attachments.

12. **Stream reader and live box** (09 18.4). The reader tails the stream file line by line, keeps a partial last line until it is complete, ignores lines that are not JSON objects and messages of unknown type or without the fields below (counted per type in a debug log line without content), and stops after `result` or when the process has exited and the file is read to its end. Fields read, [derived] from the Agent SDK reference that 18.4 cites; write this table into 18.4:

    | Message | Fields | Live box |
    |---|---|---|
    | `system` `init` | `session_id`, `model`, `apiKeySource` | replace `/model`; counter-check (note 13); session report |
    | `assistant` | `message.content[]` with `text` items and `tool_use` items (`id`, `name`, `input`); `message.usage`; `parent_tool_use_id` | `/last_text_excerpt` from the text items of the newest message; `add` on `/steps/<id>` with kind `tool_call`, `name`, `title`, status `running`, `parent_step_id` of the step of `parent_tool_use_id` |
    | `user` | `message.content[]` with `tool_result` items (`tool_use_id`, `is_error`); `isReplay`, `uuid` | step `completed` or `failed` with `finished_at`; the echo of the own prompt is ignored |
    | `tool_progress` | none | no change |
    | `system` `task_started`, `task_progress`, `task_updated`, `task_notification` | `task_id`, `description`, `task_type`, `ambient`, `status` | step kind `subagent` with detail `{"type":"local_agent"}` when `task_type` is `local_agent`, else `background_job`; `ambient` tasks get no step; `status` `completed`, `failed`, `stopped` end the step as `completed`, `failed`, `cancelled` |

    | `system` `status` | `status` | `compacting` sets `/status_line` to `compacting`, its absence removes it |

    | `result` | `subtype`, `is_error`, `result`, `modelUsage` (`inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`, `costUSD`, `contextWindow` per model) | end of the turn (note 14) |

    Step title: the first non-empty line of the first string member of `input` in the order `command`, `file_path`, `path`, `pattern`, `url`, `query`, `description`, `prompt`, else of the first string member, else empty; no step `detail` (data economy). Step ids are UUIDv7 (09 4.7), one per `tool_use` and task, from one step-id helper (the SDK's if it has one), which M2-35 reuses. `/metrics/context_pct` after an `assistant` message with usage: input plus cache tokens divided by the `contextWindow` of the model stored from the last `result` of the session, omitted while unknown. `/metrics/subagents` counts subagent steps. A leading `TITLE:` line is removed from the excerpt when the TITLE request was given. All ops go through the SDK's patch helper (throttle, `base_version`, rebase after `409 base_version_conflict`).

13. **Counter-check and session** (09 18.3, 18.4, 9.1). At `system/init`: `apiKeySource` must be `ANTHROPIC_API_KEY` for `organization` and `none` for `personal`; anything else calls `terminate`, sends no reply and ends the run with `finishRun` `failed` `billing_mode_mismatch` (BR-05: change during the run). When `session_id` equals the reference of the turn and the payload's `agent_session` was absent or not started, report once with `reportAgentSession` (`external_session_ref`, `model`, `started: true`) and `If-Match` of `agent_session.version`, or `"1"` when `startRun` created the row (M2-12 note 10); on `412 version_conflict` whose `current` has the same reference, retry once with its version; other failures are logged with their code and change nothing. A different `session_id` is left to M2-35 (no report). Every request of the runner for a run, in prepare and in execute, goes through the SDK client inside the SDK's run binding (expected `Client.bind_run`; M2-29 wraps execute, and the run loop wraps prepare too, which this ticket adds when the merged SDK does not, Scope), so it carries the run's newest token in the header `Invocation-Token` (07 SR9, M2-14 notes 1 and 3d); the runner never calls the server beside that client.

14. **End of the turn** (09 18.4, 18.7, 12, 4.10).

    - After `result` the runner closes stdin and waits `runner.stop_grace` for the exit, then `terminate`. A turn that exits without `result`, or a `result` with `is_error` or a `subtype` other than `success`, ends `failed` with `runtime_error`: first one step of kind `status` with `name` `runtime_error`, an empty `title`, status `failed`, `finished_at` and `detail` `{"exit": "<exit code or signal name>"}` (no error text and no stderr, because both can echo content; M2-35 adds the recognised texts of 18.9), then `finishRun`; no reply and no title.
    - Success: the reply is `result.result` without a leading `TITLE: <title>` line when the TITLE request was given; an empty reply sends nothing. One `createMessage` in the thread with `client_msg_id` from the SDK outbox (stored before sending), `content_md` and `run_id`; a `400 validation_failed` on it ends the run `failed` with `adapter_error` (03 sizes `message.max_content_bytes` for long answers without splitting).
    - Title: only after a completed first run of a new or unstarted session and only when the line was present and not empty: `getThread`, and when `title_source` is `auto`, `setThreadTitle` with `If-Match`; `409 title_manual`, `412 version_conflict` and any other failure are logged by code and never retried; the run still completes (AG-19).
    - Cost (18.7): per model the difference of `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens` and `costUSD` against the last stored values of the session (zero for a new session); a negative difference of any value means the runtime started counting again, and the current values count as this run's. `CostReport{provider: anthropic, model, tokens_in, tokens_out, tokens_cache_read, tokens_cache_write, amount_micros, currency: USD}`, cache writes as 5 minutes (10 12.3), `amount_micros` from the decimal value of `costUSD` with half-even rounding. Before `finishRun` the runner writes `<runner.state_dir>/sessions/<ref>/usage.json` atomically with the new values and a pending record (`run_id`, the reports); a retried `finishRun` of the same run (a retry of the SDK, or M2-35's takeover after a restart) sends the stored reports (a repeated final state answers `200`, M2-09 note 6), so a delta is reported at most once and never twice. Ruling for docs/DECISIONS.md.
    - `finishRun` `completed` with `costs` and `metrics` (`tokens_in`, `tokens_out`, `tokens_cache_read`, `tokens_cache_write` as sums of the run, `context_pct`, `subagents`, `background_jobs`, `api_retries`). `409 invalid_state_transition` means the server ended the run already (for example `cancel_timeout`): log it, never retry. Then remove the turn record and release the locks.
    - Cancellation safety: if the SDK cancels execute (for example on `run.cancel_requested`, M2-29), the runner calls `terminate` on the turn's group and waits for it before the cancellation propagates, then releases the locks; a runtime never outlives the end of its run (09 1 point 4, 8). M2-35 builds the stop path, its reasons and its scenarios on this.

15. **Heartbeat** (09 4.8, M2-20 note 3), built with the SDK's heartbeat building block and sent on the SDK's heartbeat path (the member `agent` of the gateway heartbeat or `sendHeartbeat`, as M2-29 builds it). The members that change at run time (`state`, `degraded_reasons`, `runtime_version`, `project_readiness`) come from the runner at every send; if the merged SDK takes heartbeat members only once from its adapter configuration, add a handler hook to its heartbeat path (test, line in `sdk/python/CHANGELOG.md`). After a channel cache change that altered a readiness, the runner asks the SDK for an immediate heartbeat when it offers one, else the next regular one carries it. Body: `state` (`online`, or `degraded` with `degraded_reasons` `runtime_unreachable` when `claude --version` fails or exceeds `runner.cli_probe_timeout`, `runtime_version_unsupported` when its version is below `MIN_CLAUDE_CODE_VERSION` or unreadable, `runtime_version_untested` when it differs from `PINNED_CLAUDE_CODE_VERSION`); `runtime_version`; no `reported_billing_mode` (the runner follows the desired mode per run, D-L8); `billing_modes_supported` with `organization` when `runner.anthropic_api_key_ref` is set and `personal` when `runner.allow_personal` is true, omitted when both are off; no `billing_evidence` in the heartbeat; `reported_tool_class = runner.tool_class`; `details` with `capabilities {title: true, components: false, voice_input: false, files_out: false}` (no `followups` until M2-35), `active_runs` (runs with a live turn), `degraded_reasons`, `adapter {name: claude-code-runner, version}`, `runtime {name: claude-code}`, `protocol_version` from the SDK; `project_readiness` with `{channel_id, ready}` for every bound forum in the cache. `claude --version` is probed at start and before each heartbeat. 16. **Secrets and logs** (BR-13, SEC-LOG-2, I5). Logs are JSON lines on stderr with event code, run, thread and channel ids; never message content, prompt text, tool input, titles, file names, tokens, keys or the values of `secret_ref`. The API key exists only in the environment passed to `auth status` and to the turn. Every file under `runner.state_dir` is created with mode `0600` (directories `0700`); the inbox stores invocation tokens by design (4.3) and nothing else secret. `agent.config_changed` reloads the forum's configuration (`getServedChannelConfig`; `404` removes it from the cache) and never logs its content. `run.cancel_requested` is handled by the SDK's run loop as M2-29 builds it; the runner's part here is the cancellation safety of note 14, and M2-35 owns the stop. `agent.followup`, `interaction.created` and `command.invoked` reach the handler's other entry points, which acknowledge and log them by type only (the runner reports no capability that leads to them).

17. **Fake-Claude, FakeServer and the real CLI.**
