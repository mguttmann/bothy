# M2-37: Guide "connect your own agent" with a check run

Status: ready | Depends on: M2-22, M2-30, M2-31 | Milestone: M2

## Goal

After this ticket the documentation site has the developer guide "Connect your own agent" (`docs/guides/connect-agent.md`, English like the site) with the ten steps of 11 "Guide: connecting your own agent in ten steps", and the guide is executable: one Go test (`services/server/test/guide`) reads the page, starts a fresh server, sends every request block as the owner or as a person, runs every command block (key generation, the example adapter in `sdk/python/examples/guide/` on the Python SDK of M2-29, the example's FakeServer tests), compares every answer and every output line with the text and every shown file with the file in the repository, and fails at the first step that differs from the text. The example adapter connects through the gateway with a consumer, reports its capabilities in the heartbeat, registers a control command and a model command with autocomplete, accepts invocations only after the SDK's token check and its own actual-mode comparison, fetches the context with trust marks, starts runs, fills the live box, answers, finishes with usage, handles a follow-up, a stop, a question, an approval card and (when the base branch already accepts attachments) a file, and survives a restart between acceptance and start. This is exit criterion 7 of milestone M2 ("The guide check run is green") and the proof for the owner's requirements 8 and 21 (PLAN 18.1) that an outside developer connects a generic agent through the public API alone (09 1 point 2, 11 1 point 3, ADR 0022, P-18). Why: a guide that nobody runs drifts away from API, SDK and server unnoticed, and the first developer who follows it hits a broken step; executing the text itself is the only way the text stays true.

## Fixed requirements that apply

Owner's fixed build rules (apply verbatim):

1. No MVP. New from scratch and directly in the final state; stages are only the order.
2. Strictly modular: clear module and service boundaries, dependencies only through defined
   interfaces, no cross access.
3. Documentation in code: every public module, class, function and interface with a docstring/doc
   comment (purpose, parameters, return value, errors, example where useful); comments explain the
   why, not the what. API documentation is generated from code (OpenAPI from the routes, dartdoc,
   Python API docs in MkDocs).
4. Documentation in the repo: README per module/service, ADR for every architecture decision,
   CHANGELOG per release, keep the documentation site current. A change without matching
   documentation is not done.
5. Quality gates (SonarQube, linters, type checking, security scanners, test coverage) block the
   merge.

Rules for every brief:

6. Test first: write the failing test, run it and keep the red output for the report, then make it green, then clean up.
7. No en dash and no em dash in any file you write; the `text-rules` pre-commit hook rejects them. Use a hyphen or rephrase.
8. White label: examples and test data use `example.com` and the people Alex, Sam and Robin; no company, host or personal names, no paths under a home directory.
9. Limits, windows and thresholds only through named configuration keys listed in `docs/operations/configuration.md`; code comments and docs name the key, never the number.
10. Specification first: a change to behaviour, API, event, right or configuration updates `docs/spec/` or `docs/api/` in the same change. The core contract (`docs/spec/00-glossary.md`, `03-data-model.md`, `04-sync-protocol.md`, `05-actions.md`) is not edited by this ticket.

Product requirements implemented here:

11. The guide covers the ten steps of 11 13 in that order, each under a heading whose title is the bold title of the step in 11 13 (PLAN row M2-37).
12. One automated test runs every step against a fresh server and fails when a step differs from the text: a request or an answer, an output line, a shown file, a step title, the order of the steps or the SDK version pin (PLAN row M2-37, exit criterion 7).
13. The example adapter uses only the public API through the Python SDK, never a private channel and never the generated core where the hand layer offers the operation (09 1 point 2, 11 1 point 3, 11 11.2, ADR 0022, ADR 0026); it never calls a model (PLAN 3 point 5).
14. The agent token is bound to the adapter's key (DPoP) as `auth.dpop_required_for` requires by default, lives only in a file readable by the adapter, and never appears in any output (08 12, T-TK-02).
15. The adapter processes an event with a token only after the SDK's checks of 09 4.5 and its own actual-mode comparison (I3, 10 7), acknowledges after storing it in its inbox (09 4.3), starts its runtime only after `200` on `startRun` (R-AG-07), and hands context with trust `unverified` to the runtime only as marked data (09 4.6, ADR 0054, T-AI-01).
16. Output and logs of the example contain no message content, no prompt, no token and no secret (SEC-LOG-2, SEC-LOG-4).
17. The example passes the scenarios AG-08 (adapter side), AG-09, AG-11, AG-12 and AG-28 of 09 16.2 against the SDK's FakeServer (09 16.1, step 10 of 11 13).
18. A restart between acceptance and start resumes the run from the inbox and starts it exactly once (09 4.9, 09 15, RK-18).

3. **Block grammar** (the contract between text and test; Ruling for docs/DECISIONS.md). Every fenced block of the page starts at column 0 with three backticks, a language and a `title="..."` attribute; an untitled block, a block with an unknown title form and an indented titled block fail the check. Kinds:

    - Request: language `http`, title `<Actor>: <operationId>` with actor `Owner`, `Alex` or `Sam`. First line `<METHOD> /api/v1/<path> HTTP/1.1` (the HTTP lexer of the site needs the version); then header lines (only `Content-Type: application/json` and `If-Match`); then a blank line and an optional JSON body. The method and the path must equal the operation of that `operationId` in `docs/api/openapi.yaml`, with any placeholder matching any path parameter. There is no actor `Agent`: the agent acts only through the example program.
    - Response: language `json`, title `Response <status>`, directly after a request block. The status must be equal and the body is an expected subset (note 5). A request without a response block must answer with a `2xx` status.
    - Command: language `bash`, title `Shell: <text>`. Run with `bash -euo pipefail -c` in the repository root after substitution; it must exit 0. Its stdout is recorded for a following output block.
    - Adapter start: language `bash`, title `Adapter: start`, exactly one command line; starts the adapter as a background process in its own process group. A start while a previous adapter may still run fails the static check, unless that previous start carried `--stop-after accept` (it stops by itself, note 7 step 10) or an `Adapter: stop` block came after it; the runner then waits for the previous process to exit and requires exit code 0 and all of its stdout lines matched.
    - Adapter stop: language `bash`, title `Adapter: stop`, body exactly `# Ctrl+C in the adapter's terminal`. The runner sends `SIGINT` to the adapter's process group and requires exit code 0.
    - Output: language `text`, title `Output`. After a `Shell:` block: the complete stdout, line by line. Otherwise: the next stdout lines of the running adapter, consumed in order.
    - File: language `python`, title the repository path of a file under `sdk/python/examples/guide/`. The block content plus a final newline equals the file byte for byte; every file there (note 8) appears in exactly one block.
    - Pin: language `toml`, title `pyproject.toml (excerpt)`. It parses as TOML, and `project.dependencies` contains exactly one entry for the SDK, `bothy-sdk==<content of sdk/python/VERSION>`. The prose says that until the packages are published (OQ-17) the SDK comes from a checkout of the repository.

    Fenced blocks stand only in `## Prerequisites` and the ten step sections; a fence in any other section fails the check, so the maintainer section describes the grammar in prose.

4. **Placeholders, captures and secrets.** A placeholder is `{name}` with `name` matching `^[a-z][a-z0-9_]*$`, or `{secret:<file>}` with a file name matching `^[a-z0-9][a-z0-9._-]*$`. Bound by the runner before the first block, and listed in the table `## Placeholders` (the check requires that the table's first column holds exactly these names): `{server_url}` (address of the instance; in the guide's prose an example like `https://chat.example.com`, in the test the public URL of the fresh server), `{adapter_dir}` (a folder only the adapter may read; in the test a `t.TempDir()` with mode `0700`), `{alex_id}`, `{sam_id}` (the people of the preconditions), `{new_uuid}` (a fresh UUIDv7 at each occurrence, for `client_msg_id` and `client_interaction_id`), `{expires_at}` (RFC 3339 in UTC; in the test the start time plus half of the effective `auth.api_token_max_ttl` of the test server). Every other name is captured exactly once, from a response block or an output block, before its first use; a later occurrence compares with the bound value; a use before the capture and a second capture fail the check. In a JSON body or an expected body, a string that is exactly `"{name}"` stands for the bound JSON value with its type (so `"{history_backfill_limit}"` becomes a number); everywhere else substitution is textual, and a value substituted into a `bash` block must match `^[A-Za-z0-9._:/@+-]+$` and is single-quoted. `{secret:<file>}` may appear only as a string in a response block: the runner captures the string, writes it to `{adapter_dir}/<file>` with mode `0600`, never logs or compares it and redacts it from every error message.

5. **Matching.** JSON: an expected object matches when every expected member exists in the actual object and matches; an expected scalar matches an equal scalar of the same JSON type; an expected array matches when each expected element matches exactly one distinct actual element, order ignored, extra actual elements allowed; an element that matches more than one actual element fails as ambiguous (the guide then adds a distinguishing member). Output: each expected line must equal the next actual stdout line after substitution; an unbound placeholder in a line captures `\S+`; a differing line fails at once with step, expected line and actual line; a process that ends before all expected lines arrived fails; a process whose stdout has lines no output block expects fails when it ends. Every failure names the step (`Step <n>` or the section), the block title and, for JSON, the JSON Pointer of the first difference; nothing after the failing block runs.

6. **Actors and authentication.** `Owner` is the first owner of the fresh server (Robin); before every `Owner` request the runner performs a fresh step-up with the device key, as the admin screens do before an admin action (08 6.2, `auth.step_up_max_age`), so no owner block can fail with `401 step_up_required`. `Alex` has `trigger` and `approve_actions` on space Support, `Sam` only `write` (granted in "Prerequisites"). Each person's requests carry their session token with DPoP and the server nonce and an `Idempotency-Key` where 06 "Idempotency" asks for one, all added by the harness client; the guide says in prose that the client adds authentication, DPoP and `Idempotency-Key`.
