# M2-26: Outgoing webhooks after Standard Webhooks

Status: ready | Depends on: M1-56, M2-01, M2-24 | Milestone: M2

## Goal

After this ticket an owner subscribes an installed app to event types (`createWebhookSubscription`, `webhook_out.manage`, step-up), and the worker delivers every matching durable event from the event log to the app's HTTPS address as one Standard Webhooks `POST` (ADR 0016): the body is the event envelope of ADR 0052 with the delivery field `sync_epoch`, the headers are `webhook-id` (the event ID), `webhook-timestamp` and `webhook-signature` with `v1a` (Ed25519 with the server key of purpose `webhook_out`, public keys at `getWebhookKeys`) and, per subscription, `v1` (HMAC-SHA256 with a secret derived from a master key and never stored). Delivery runs as the first production consumer `webhooks` of the M2-01 frame and the job `apps.webhook_deliver`: strictly in `seq` order per subscription, with backoff and full jitter, `Retry-After` honoured for `429`, `502`, `503` and `504`, a subscription switched off by `410`, by `webhook.max_consecutive_failures` or by a delivery that stays undelivered for `webhook.retry_max_age`, and a check `webhook_out.deliver` with the app's current grants and scopes before every attempt, so that a revoked right ends the delivery as `dead` without any request (AZ-M49). Every connection goes through the egress client, so a target that resolves to a private address is never contacted. Gate G10 holds the signatures against committed test vectors, the Standard Webhooks reference library (`v1`) and Ed25519 of the Go standard library (`v1a`). This is the plan's "webhooks" part of M2 (P-18: apps and webhooks use the same public API) and the server half of threat T-PL-01 ("webhooks only to allowed targets").

Product requirements implemented here:

11. Tables `webhook_subscriptions` and `webhook_deliveries` exactly as 03 4.11, owned and accessed only by `apps` (02 4.2; 03 principle 12): every column, the check "exactly one of `app_installation_id` and `agent_id`", `hmac_enabled OR hmac_generation = 0`, the state and status checks, the foreign keys with their actions, unique `(subscription_id, event_seq)`, the indexes `(state)`, `(agent_id) WHERE agent_id IS NOT NULL` and `(next_attempt_at) WHERE status = 'pending'`; retention classes `config` and `transient` (20).
12. A subscription is created, changed, paused, resumed, rotated and deleted only by an owner in a session with step-up, audited (`webhook_out.manage`; 05 4.11, R-AZ-03); lists and delivery history need `webhook_out.read` (owner); `redeliverWebhook` needs `webhook_out.redeliver` (owner, audited, no step-up). An invisible resource answers `404` exactly like an unknown ID (05 rules 1 and 2, R-AZ-01).
13. The address is `https` and its host is in `webhook.allowed_hosts`, otherwise `400 webhook_host_not_allowed` (R-DM-17; webhooks.md 1 point 2; 06 5); `event_types` is a subset of the installation's `event_subscriptions` (03; 11 7 row "Subscription").
14. Delivery comes from the event log through the worker consumer `webhooks` and the job `apps.webhook_deliver` in queue `delivery` (02 11.5, 12.3; ADR 0051; 11 6 "Deliveries come from the event log, not from a copy"); no network call inside a transaction (02 8.5, R-AR-07).
15. Wire format after Standard Webhooks: one `POST` per event; body = the envelope of the event (04 2.2, ADR 0052) with the delivery field `sync_epoch` and no JSON `null` (ADR 0053); `webhook-id` = event ID, unchanged across retries and redeliveries; `webhook-timestamp` = Unix seconds of this attempt; `webhook-signature` = space-separated `v1a,<base64>` (Ed25519, server key of purpose `webhook_out`) and, when `hmac_enabled`, `v1,<base64>` (HMAC-SHA256); signed content `{webhook-id}.{webhook-timestamp}.{body}` over the body bytes as sent (webhooks.md 2; 11 7; ADR 0016).
16. Public keys of purpose `webhook_out` in the states `next`, `active` and `retiring` at `GET /api/v1/instance/webhook-keys` (`getWebhookKeys`, `instance.discovery.read`, public, `rl.public_auth`) in the format `whpk_<base64>` (webhooks.md 2.1 point 1; 11 7 last paragraph; SEC-CORS-2). The JWKS (`getJwks`) never lists `webhook_out` keys.
17. The `v1` secret is never stored: `HMAC-SHA256(master key, "webhook-v1:" || subscription_id || ":" || generation)` with the master key from the secret provider, shown once as `whsec_<base64>`; `rotate_hmac_secret` raises `hmac_generation` and the server signs with the old and the new generation for `webhook.secret_rotation_overlap` (webhooks.md 2.1 point 3; 03 `hmac_generation`, `hmac_rotated_at`; 03 principle 9). Responses with a secret are one-time secrets for idempotency (06 7, R-API-26).
18. Strict order per subscription: the next event goes out only after the previous one is finished; `last_delivered_seq` is the highest `seq` accepted with `2xx` (webhooks.md 5; 11 7 row "Order"; 03).
19. Outcomes: only `2xx` is success; `410` switches the subscription off (`disabled`); `429`, `502`, `503` and `504` throttle and honour `Retry-After`; `3xx` is a failure and redirects are never followed; other statuses, timeouts and connection errors are failures retried with exponential backoff and full jitter between `webhook.retry_backoff_base` and `webhook.retry_backoff_cap` until `webhook.retry_max_age`, then the delivery is `dead` and the subscription `disabled`; after `webhook.max_consecutive_failures` failures in a row the subscription is `disabled` and audited; response bodies are never stored (webhooks.md 4, 5 point 3; 11 7; openapi `webhooks:` responses).
20. Before every attempt `webhook_out.deliver` decides with the app's current grants and scopes (receive action of the event type for the app, filter mode, no denial in the audit); without access the delivery is `dead` with `last_error = not_authorized`, without a request and without counting as a failure (05 4.11, R-AZ-11; 07 4.2, 8.1; webhooks.md 4 point 3; 11 7 row "Check"; ADR 0051 "Confirmation").
21. SSRF protection: only `https`, only hosts of `webhook.allowed_hosts`, the egress client checks the address after name resolution at connection time and connects only to the checked address, loopback, link-local and private addresses are refused unless `egress.allowed_hosts` has a matching entry with `allow_private`, no redirects, time limit `webhook.delivery_timeout` per attempt (webhooks.md 6; 11 7 row "SSRF protection"; SEC-NET-1 to SEC-NET-5).
22. A paused subscription continues where it stood; an event that is no longer in the log when its turn comes switches the subscription to `disabled` with the hint "gap" instead of being skipped silently, and so do events the consumer `webhooks` itself lost to retention (11 6 last paragraph, R-EX-07; ADR 0051 Consequences). Above `webhook.max_pending_per_subscription` open deliveries a subscription is `paused` and the owner learns it (11 6 row "Delivery quota").
23. `app.suspend` pauses deliveries and keeps their state; `app.uninstall` sets the app's subscriptions `disabled` (11 4.3). Installing an app whose manifest has `delivery.mode = webhook` creates its subscription in the install transaction (11 4.1).
24. Logs, spans and audit carry no URL path or query, no body, no secret and no content (SEC-LOG-1 to SEC-LOG-4, SEC-SEC-3, SEC-AUD-5); the span `webhook.deliver` (CLIENT, worker) carries `server.address`, `http.response.status_code` and `bothy.outcome` (signals.md 5.2).
25. Gate G10: committed test vectors; a delivery in an integration test verified with the Standard Webhooks reference library (`v1`) and with Ed25519 of the standard library (`v1a`) (06 15; ADR 0016 "Confirmation").

2. Subscription use cases (`apps/app/webhooks.go`), one unit of work each, in this order: the generated layer has validated the request schema (unknown fields give `400 validation_failed`); `authorize(actor, action, Resource{Kind: app, ID: app_id})` with `webhook_out.manage` (create, update, delete) or `webhook_out.read` (lists); for operations by subscription or delivery ID, an unknown ID gives `404 not_found` before `authorize`, and `authorize` runs on the subscription's app, so a non-owner gets the same `404` as for an unknown ID (07 4.3: `app` is visible to owners only; AZ-P4). Then:
   a. Create (`createWebhookSubscription`): lock the app's current installation row `FOR SHARE`; no installation in `active` or `suspended` gives `409 conflict` with `reason: app_not_installed` (the reason M1-44 uses); validate `url` (Design note 9, `400 webhook_host_not_allowed` or `400 validation_failed` with pointer `/url`) and `event_types` (non-empty, no duplicates, each `AppSubscribable` and in `event_subscriptions` of the installation; otherwise `400 validation_failed` with pointer `/event_types/<index>` and `errors[].code` `not_subscribable` or `not_granted`); insert with `signing_key_kid` = `KeyID()` of the `active` `webhook_out` signer, `hmac_enabled = enable_hmac`, `hmac_generation = 0`, `state = active`, `created_by` = actor; with HMAC derive the secret (Design note 11), return it once as `hmac_secret` and call `idempotency.MarkOneTimeSecret(ctx)`, so a replay answers `409 conflict` with `reason: one_time_secret` (06 7, R-API-26). Answer `201 WebhookSubscriptionCreated`.
   b. Update (`updateWebhookSubscription`, PATCH): lock the subscription row `FOR UPDATE`; a new `url` or `event_types` is validated as in a; `state: paused` from `active` or `disabled`; `state: active` from `paused` or `disabled` (owner resume and re-enable, Design note 5): `consecutive_failures = 0`, `disabled_at = NULL`, the head pending delivery (lowest `event_seq` with `status = 'pending'`) gets `next_attempt_at = now`, and `Schedule(subscription, now)`; `rotate_hmac_secret: true` without HMAC gives `400 validation_failed` with pointer `/rotate_hmac_secret` and `errors[].code` `hmac_not_enabled`, with HMAC it sets `hmac_generation = hmac_generation + 1`, `hmac_rotated_at = now`, returns the new secret once and marks the one-time secret (replay `409 conflict`, `one_time_secret`; this ticket adds the `409` response to the operation). An empty body changes nothing. Answer `200 WebhookSubscriptionCreated`.
   c. Delete (`deleteWebhookSubscription`): delete the row (deliveries go by `ON DELETE CASCADE`); `204`; a second delete is `404` (no tombstone, 06 7 row "PUT and DELETE").
   d. Lists: `listWebhookSubscriptions` returns every subscription of every installation of the app, ordered by `created_at`, then `id`; `listWebhookDeliveries` pages by `(event_seq DESC, id DESC)` with the cursor codec of `platform/httpserver`, filter `status`, `400 cursor_invalid` for a foreign cursor (06 6). `app_id`, `signature_schemes` (`[v1a]` or `[v1a, v1]`) and `event_type` are derived (Design note 13).
   e. Audit: every allowed change writes one entry `webhook_out.manage` in its transaction through `auditing.Recorder.Record` (07 4.2: the use case writes allows) with `subscription_id`, `app_id`, `change` (`created`, `updated`, `paused`, `resumed`, `rotated`, `deleted`), `host`, `event_types` (list of codes), `hmac_enabled`, `hmac_generation`; never the URL path or query and never a secret (SEC-AUD-5). Denials are written by `authorize` (R-AZ-04).

3. The consumer `webhooks` (`apps/app/consumer.go`), the `sync.ConsumerHandler` of M2-01, runs in the round's transaction once per event in `seq` order, writes only `apps` rows, jobs and the audit entries of its system transitions (`webhook_out.transition`, R-AZ-27, through `auditing.Recorder.Record`), calls nothing outside the process and appends no durable event (M2-01 Design notes 2 and 6). For an event `ev`:
   a. Skip at once when `AppSubscribable(ev.Type)` is false.
   b. Candidates (loaded once per round and memoised under a `txn.Key`): app subscriptions (`app_installation_id IS NOT NULL`) in state `active` or `paused` whose installation is `active` or `suspended`, with `ev.Type` in `event_types` and in the installation's `event_subscriptions`. A `disabled` subscription gets no rows: events that arrive while it is disabled are not delivered (Ruling for docs/DECISIONS.md, `D-M2-26-1`; webhooks.md 5 states it). A personal event (`ev.AudiencePrincipalID` set) goes only to the subscriptions of the installation whose app principal is the audience. Rights are not checked here: they apply at delivery time (04 8.1, B7).
   c. Per candidate insert `webhook_deliveries (id, subscription_id, event_seq, event_id, status 'pending', attempt 0)` with `ON CONFLICT (subscription_id, event_seq) DO NOTHING`.
   d. Quota (11 6 "Delivery quota"; Ruling for docs/DECISIONS.md, `D-M2-26-2`): the open count of a subscription (rows with `status = 'pending'`, counted once per round with a bounded count and then tracked in the memo) is compared before and after each insert; when an insert brings an `active` subscription from below `webhook.max_pending_per_subscription` to it or above, the subscription becomes `paused` (row lock `FOR UPDATE`, system transition of Design note 5, audited). Rows keep being created while paused, so no event is lost; because the rule fires on the crossing, an owner who resumes a subscription with a large backlog is not paused again before it drained below the quota and filled up again.
   e. Jobs: one `Schedule(subscription, now)` per `active` subscription with an `active` installation that got at least one new row in this round (repeated wake-ups are harmless, Design note 4).
   f. Lost range (ADR 0051 Consequences, R-EX-07, M2-01 Design note 5): when the consumer `webhooks` itself fell behind `sync.event_retention`, the M2-01 round reports `LostFrom` and `LostTo`. Those events never became rows, so the head rule of note 5 e cannot see them. `internal/sync` gains `type ConsumerLossHandler interface { HandleLost(ctx context.Context, from, to int64) error }`. When `PlanRound` reports a loss and the registered handler implements this interface, the round calls it once, in the round's transaction, before the first `HandleEvent`. An error rolls back the round like a handler error. Consumers without the interface (for example `push`) are unaffected. The `webhooks` handler implements it as follows: every app subscription in state `active` or `paused` whose installation is `active` or `suspended` becomes `disabled` with cause `gap` (system transition of note 5 b, `disabled_at = now`), because any of them could have matched a lost event. Their `pending` rows all belong to events below `from`, which left the log as well, so they become `dead` with `last_error = event_expired` as in note 5 e; the audit entry names `from_seq` (the lowest `event_seq` of those rows, else `from`) and `to_seq` = `to`. A re-enable then continues with the events the consumer reads after it, so it never loops. The candidates of note 3 b are loaded after this step.

4. The attempt (`apps/app/deliver.go`, job `apps.webhook_deliver` with args `{SubscriptionID}`; Ruling for docs/DECISIONS.md, `D-M2-26-3`). One job kind serves every trigger: a round (note 3 e), the chain after a finished delivery, a scheduled retry, the lease wake-up (note 4 e), an owner resume or re-enable (note 2 b), `redeliverWebhook` (note 13) and `ResumeInstallation` (note 14). Several jobs for one subscription are harmless: all serialize on its row lock and only a due head is sent, so at most one attempt per subscription is in flight (strict order, requirement 18).
   a. Claim, one unit of work: `SELECT ... FROM webhook_subscriptions WHERE id = $1 FOR UPDATE`; missing or not `active`: done. Installation not `active` (for example `suspended`): done without change. Head = the `pending` row with the lowest `event_seq`; none: done. `next_attempt_at` after now: done (a scheduled retry, the lease wake-up or the attempt in flight owns it).
   b. Event: `sync.LogReader.EventBySeq(head.event_seq)`; not retained: gap (note 5 e), done.
   c. Routing: `ev.Type` no longer in the subscription's `event_types` or in the installation's `event_subscriptions` (11 4.2 "Removed ... events ... take effect immediately"): head `dead` with `last_error = not_subscribed`, chain, done.
   d. Rights: `authorize(authorize.Filter(ctx), appPrincipal, webhook_out.deliver, Resource{Kind: ev.ResourceKind, ID: ev.ResourceID, SpaceID, ChannelID, ThreadID from ev, DeliveryOf: ev.ReceiveAction, Audience: ev.AudiencePrincipalID})` with `appPrincipal = actor.Principal{ID: app principal, Kind: app, InstallationID, GrantedScopes}` read in this unit of work (current grants, scopes and installation). Any outcome other than `allow`: head `dead` with `last_error = not_authorized`, `attempt` unchanged, no request, `consecutive_failures` unchanged, chain, done (requirement 20, AZ-M49). An `error` (not a decision) returns the error, and River retries the job. If M1-63 merged a mapping from a stored event to the resource of its receive action, use it instead of building the descriptor here.
   e. Request: body = `json.Marshal(ev.Envelope(sync.DeliveryFields{SyncEpoch: instance.State.Load(ctx).SyncEpoch}))`; `ts` = `clock.Now()` in Unix seconds; signatures of note 11. Lease: `attempt = attempt + 1`, `next_attempt_at = now + webhook.delivery_timeout`, and in the same unit of work `Schedule(subscription, next_attempt_at)` as the lease wake-up, so an attempt whose send or record step ends with an error, a cancellation or a crash is sent again once the lease has run out; commit. Keep body and header in memory only.
   f. Send through `WebhookSender` outside any transaction (02 8.5).
   g. Record, one unit of work: lock the subscription row, reload the head; if it is no longer `pending` with the claimed `attempt` (deleted, redelivered, paused and changed), discard the result. Otherwise apply the outcome of note 6 with the timing of note 7, set `response_code` when a response arrived, and chain: `Schedule(subscription, now)` after a finished delivery while the subscription stays `active`; `Schedule(subscription, next_attempt_at)` after a retryable outcome; nothing when the subscription became `disabled` or is no longer `active`.
   h. On a 2xx: head `succeeded`, `delivered_at = now`, `next_attempt_at = NULL`, `last_error = NULL`; subscription `last_delivered_seq = GREATEST(last_delivered_seq, event_seq)`, `consecutive_failures = 0`, `signing_key_kid` = the kid of the active key that signed (Ruling for docs/DECISIONS.md, `D-M2-26-4`: the field names the key that signed the last accepted delivery, at creation the active key).
   Locks: the subscription row first, then its delivery rows; a round locks a subscription row only for the quota transition and never waits for the consumer cursor (M2-01), so no cycle exists. The job's own failures (database, context cancelled) return the error and River retries with its defaults (M1-14 rules 15 and 16); a retry that still finds the lease ahead ends, and the lease wake-up of e sends the head again; the attempt is idempotent through `attempt` and the lease. A crash after the receiver answered and before g leads to a second send with the same `webhook-id` (at least once, webhooks.md 5 point 1; the receiver deduplicates).

5. Subscription states (`domain/subscription.go`; 03 `state`; webhooks.md 4 and 5; 11 6):
   a. Owner: `active -> paused`, `paused -> active`, `disabled -> active` (re-enable), `disabled -> paused`; resume and re-enable reset `consecutive_failures` and make the head due now (note 2 b).
   b. System, each audited with the system action `webhook_out.transition` (05 4.11, R-AZ-27; actor none, resource `app`, details `subscription_id`, `from_state`, `to_state`, `cause`, and `from_seq`, `to_seq` for a gap), in the transaction of the change, and logged at warn level: `410` -> `disabled` (cause `gone`); `consecutive_failures` reaches `webhook.max_consecutive_failures` -> `disabled` (cause `max_consecutive_failures`; the head stays `pending` and goes first after a re-enable); a delivery `dead` after `webhook.retry_max_age` -> `disabled` (cause `retry_max_age`); a gap -> `disabled` (cause `gap`); the quota of note 3 d -> `paused` (cause `max_pending`). `disabled_at = now` on every change to `disabled`. "the owner is notified" (11 6) is this audit entry plus the state in `listWebhookSubscriptions`; the product sends no mail (webhooks.md 4 point 2) and 05 has no event type for subscriptions.
   c. `uninstallApp` sets every subscription of the installation `disabled` in its transaction (11 4.3; covered by the audit entry of `app.uninstall`).
   d. After a re-enable delivery continues with the remaining `pending` rows in `seq` order and then with events committed after it (webhooks.md 5 point 3 "next event").
   e. Gap (Ruling for docs/DECISIONS.md, `D-M2-26-5`; 11 6, R-EX-07): detected at the head when its event is no longer in the log (`EventBySeq` false). In one unit of work: subscription `disabled` (cause `gap`), every `pending` row of the subscription with `event_seq` below `MinRetainedSeq()` becomes `dead` with `last_error = event_expired`, the audit entry names the first and last lost `seq`. A re-enable then continues with the first retained pending row, so it never loops. Among the rows that exist, this detects exactly the deliveries that were due, without false positives for subscriptions that match rarely. A loss inside the consumer itself is detected by note 3 f.

6. Outcomes and statuses (`domain/delivery.go` `Classify`; Ruling for docs/DECISIONS.md, `D-M2-26-6`). Statuses of 03: `pending` (waiting for its first or next attempt, also after a failed attempt; `next_attempt_at` set), `succeeded` (2xx), `failed` (finished without success because the receiver answered `410`; terminal, the owner may redeliver), `dead` (finished: `webhook.retry_max_age` passed after a failure, `not_authorized`, `not_subscribed`, `event_expired`). `last_error` is a code from the closed list `timeout`, `connection_failed`, `tls_failed`, `address_blocked`, `host_not_allowed`, `http_status`, `throttled`, `gone`, `not_authorized`, `not_subscribed`, `event_expired` (never a response body, 03; webhooks.md 4 point 5). Mapping: 2xx -> success; `410` -> `failed`, `gone`, subscription `disabled`; `429`, `502`, `503`, `504` -> retry, `throttled`, not counted; any other status including `3xx` (the egress client returns it unchanged with `RedirectNever`) -> retry, `http_status`, counted; `egress.ErrBlocked` with reason `address_blocked` -> retry, `address_blocked`, counted; reasons `host_not_allowed`, `scheme_not_allowed`, `url_not_allowed` -> retry, `host_not_allowed`, counted; deadline -> `timeout`; TLS handshake or certificate error -> `tls_failed`; other transport errors -> `connection_failed`; all counted. "Counted" means `consecutive_failures + 1`, compared with `webhook.max_consecutive_failures` (webhooks.md 4 table separates "Throttle" from "Failure"; only "failures" count, point 2). Retention (M7-05) may delete only `succeeded`, `failed` and `dead` rows older than `retention.webhook_deliveries`, never `pending` ones: state this in the `apps` README and in webhooks.md 4.

7. Timing (Ruling for docs/DECISIONS.md, `D-M2-26-7`). After the n-th counted or throttled failure in a row of this delivery (n = `attempt`), the backoff is a uniform random duration in [`webhook.retry_backoff_base`, min(`webhook.retry_backoff_cap`, `webhook.retry_backoff_base` times two to the power n-1)]: exponential with full jitter between base and cap (webhooks.md 4 point 1), the random source injected for tests. For a throttle with a valid `Retry-After` (delta-seconds or HTTP-date of RFC 9110 10.2.3; a past date counts as zero; anything else is ignored) the delay is the larger of backoff and `Retry-After` (webhooks.md 4 table). The retry deadline is `created_at + webhook.retry_max_age`: a retry is never scheduled after it (a later time is cut to the deadline), and a counted or throttled failure at or after it makes the delivery `dead` and the subscription `disabled` (webhooks.md 5 point 3). The deadline is checked only after a failed attempt, never before sending, so a head that waited in a paused or disabled subscription still gets its attempt after the resume.

8. `webhook_out.deliver` in `authz` (07 4.2 "Requirements that need facts of a later milestone ... The ticket that delivers the facts replaces the entry"). Requirement atom `Delivery` in `domain/requirements.go`, evaluated in `decide.go`, in this order: principal kind `app` (an `agent` gives `forbidden subject_kind_not_allowed` until the agent transport, Out of scope; any other kind the same); the liveness check of M1-28 has run (`app_not_installed` for an installation that is not `active`); scope `events:subscribe` in `GrantedScopes`, else `forbidden scope_missing` (05 2.6 "Event subscriptions"); with `Audience` set: `Audience` equal to the principal, else `not_found not_self`, then `allow` (receive action `self`, and for apps `agent.events.consume` is replaced by `events:subscribe`, 03 `event_log.receive_action`); otherwise the full decision of `DeliveryOf` on the same resource (visibility, requirement, the app scope of `DeliveryOf` from `domain/scopes.go`, for example `messages:read` for `message.read`, none for `instance.read`, `status.read`, `command.read`, `agent.read`), whose outcome is the result. `DeliveryOf` empty or itself `webhook_out.deliver` is an internal error. Only in filter mode from the job: no denial is written and no decision is counted (07 4.2, AZ-P13). `writes(webhook_out.deliver)` stays false (M1-28). Owners have no special rule here: an app is never owner. The rights version does not change.

Targets (`domain/subscription.go` `ValidateTarget`; Ruling for docs/DECISIONS.md, `D-M2-26-8`): entries of `webhook.allowed_hosts` have the form `host[:port]` (host lower case, no scheme, no path; without port only the default port of `https`); a URL is accepted when it parses, its scheme is `https`, it has no user info and no fragment, and its canonical host (lower case, no trailing dot) and port match an entry; otherwise `400 webhook_host_not_allowed` for a host or port not in the list and `400 validation_failed` (pointer `/url`) for every other defect. 11. Signatures (Rulings for docs/DECISIONS.md, `D-M2-26-10` and `D-M2-26-11`):
   a. `v1a`: one signature per signer of `instance.Keys.Signers(ctx, webhook_out)` (active first, then every `retiring` key whose `not_after` lies ahead; webhooks.md 2.1 point 2: "the server signs with both until the old one reaches `not_after`"). With the promotion rule of M1-32 (`not_after` = time of promotion) this is the active key alone; the rule stays general so a later change of the window needs no change here.
   b. `v1` when `hmac_enabled`: key of `hmac_generation`, plus the key of `hmac_generation - 1` while `hmac_rotated_at + webhook.secret_rotation_overlap` lies ahead; never older generations.
   c. Header: entries separated by one space, all `v1a` entries first in signer order, then the `v1` entries newest generation first; each entry `<scheme>,<standard base64 with padding>` (webhooks.md 2).
   d. HMAC derivation: `HMAC-SHA256(master, "webhook-v1:" + subscription_id + ":" + generation)` with the subscription ID in canonical lower-case hyphenated form and the generation in decimal ASCII; the master key is the hex-decoded value of `webhook.hmac_master_key_ref` (M1-09 D5). The derived bytes are the HMAC key; `whsec_` + standard base64 of them is the secret shown once, the form the reference libraries decode.
   e. `whpk_` + standard base64 of the DER-encoded SubjectPublicKeyInfo (RFC 8410) of the Ed25519 key, the form of the example under `getWebhookKeys` (Ruling `D-M2-26-11`; the openapi description of `WebhookKey.public_key` names it).
   f. `getWebhookKeys` (`instance/adapters/httpapi`): `PublicKeys(ctx, webhook_out)` ordered by state (`active`, `next`, `retiring`) and `kid`; each item `{kid, public_key, state, not_after}` with `not_after` only when set (no `null`); `Cache-Control` and `Access-Control-Allow-Origin: *` exactly as `getJwks` sets them (M1-32: a `next` key is published `agent.jwks_max_age` before it signs; SEC-CORS-2).
   g. Secrets never leave memory except in the one response: no log, no audit, no error text, no row (including `idempotency_keys`), no span (SEC-SEC-3, R-API-26).

Test vectors (Ruling for docs/DECISIONS.md, `D-M2-26-12`): `docs/api/webhook-test-vectors.json`, the contract file for every verifier (M2-29, M2-30): `{"version": 1, "derivation": [...], "signatures": [...]}`; each derivation case `{master_hex, subscription_id, generation, derived_hex}`, with `derived_hex` the lowercase hex of the 32 derived bytes. The secret shown to the owner is `whsec_` + standard base64 of those bytes (note 11 d) and is not stored in the file, because a derived value cannot carry the `EXAMPLE` marker. `master_hex` values are low-entropy fixed byte sequences (for example the bytes 00 to 1f), so no gitleaks rule matches them. ## Acceptance criteria
