# M1-15: Sequence counters and instance record

Status: ready | Depends on: M1-11, M1-13 | Milestone: M1

## Goal

After this ticket the module `instance` owns the tables `instance` and `sequence_counters`, offers
the port `Counters` that only the phase hooks of `authz`, `sync` and `audit` may use, records the
instance identity, schema version and minimum server version during `bothy migrate up`, exposes
the setup state, and keeps a server whose version is below `instance.min_server_version` from
becoming ready. The counter rows are the serialization points that make event sequence, audit
chain and permission version gapless and commit-ordered (B8, ADR 0009, 03 R-DM-05).

## Scope

All Go paths are relative to `services/server/`.

1. Migration (goose, SQL, in `migrations/`): tables `instance` and `sequence_counters` per 03;
   `INSERT` of the three counter rows with value `0`; a `BEFORE UPDATE` trigger function
   `instance_counter_monotonic()` that raises when `NEW.value < OLD.value` or the name changes;
   grants for `bothy_app`: `SELECT, UPDATE (value)` on `sequence_counters`, `SELECT` on
   `instance`; no `INSERT` or `DELETE` for `bothy_app` on either table. Follow the grant pattern
   M1-12 set up. Name the file with the next free sequential number of the base branch (ADR 0007
   rule 4); renumber before the final `make check` if another ticket took it.
2. `internal/instance` (port):
    - `type CounterName string` with `CounterEventSeq = "event_seq"`,
      `CounterAuditSeq = "audit_seq"`, `CounterPermissionVersion = "permission_version"`.
    - `type Counters interface { Advance(ctx context.Context, name CounterName, n int64) (last int64, err error); Current(ctx context.Context, name CounterName) (int64, error) }`.
      `Advance` locks the row until commit (`UPDATE ... SET value = value + $n ... RETURNING value`)
      and returns the new value, so the numbers are `last - n + 1 .. last`. `Current` reads the
      value without a lock (inside the hook that already holds the lock, or the committed value).
    - `type Record struct { InstanceID ids.ID; SetupCompletedAt time.Time; SchemaVersion int64; MinServerVersion string; SyncEpoch ids.ID; CreatedAt time.Time }`
      with `func (r Record) SetupCompleted() bool` (zero time means not completed; no JSON `null`
      anywhere later, ADR 0053).
    - `type State interface { Load(ctx context.Context) (Record, error); RecordMigration(ctx context.Context, schemaVersion int64, minServerVersion string) (Record, error) }`.
      `Load` returns `not_found` kind when the row is missing. `RecordMigration` creates the row if
      missing (new UUIDv7 for `instance_id` and `sync_epoch`) and sets `schema_version` and
      `min_server_version`; it never changes `instance_id`, `sync_epoch` or `setup_completed_at`.
3. `internal/instance/domain`: counter name validation; phase rule (see Design notes);
   `CompareSemVer(a, b string) (int, error)` after SemVer 2.0.0 precedence including
   pre-release identifiers (https://semver.org/spec/v2.0.0.html, section 11), hand-written
   because the domain layer imports no third-party library; `CheckServerVersion(own, min string) error`.
4. `internal/instance/app`: services implementing `Counters` and `State` over an outgoing
   repository port.
5. `internal/instance/adapters/postgres`: sqlc queries under `queries/`, repository; entry in
   `sqlc.yaml`; generated code checked in.
6. Server version: `internal/platform/buildinfo.Version()` from M1-10 (18 "Components" rule 5).
7. Schema compatibility constant (18 "Components" rule 6, upgrade.md "Schema check at startup"):
   in the package that embeds `migrations/` (M1-12), add
   `const MinServerVersion = "<content of services/server/VERSION>"` with a doc comment: the oldest
   server version allowed to run against the schema these migrations produce; per upgrade.md rule
   M1 it is the previous release, a deliberate break sets the own version; before the first
   release it equals the current version.
8. `cmd/bothy migrate up`: after the migrations, if the database version equals the newest
   migration this binary knows, call `State.RecordMigration(goose version, MinServerVersion)`; if
   the database is newer than this binary, leave the row unchanged and exit 0 (upgrade.md
   "Rollback" item 1). The write runs in a unit of work on the migrate connection.
9. Start (`internal/wire`, `internal/platform/lifecycle`): after the schema check of M1-12, load
   the record (missing row: abort start with a message telling the instance operator to run
   `bothy migrate up`); keep it for later tickets (setup state, `instance_id`, `sync_epoch`); run
   `CheckServerVersion(buildinfo version, record.MinServerVersion)`; on failure register a failing
   readiness check named `schema_requires_newer_server` with the API of `platform/health`, keep
   running, never become ready. Applies to all roles.
10. Phase guard and injection: `Counters` is constructed only in `internal/wire` and passed only to
    phase hook constructors (none exist yet).
11. Static check `TestCountersOnlyUsedByPhaseHooks` in `internal/wire` (see Tests).
12. Docs: `internal/instance/README.md` (status, tables, `Counters` rule, `State`, start check);
    CHANGELOG. 02 "Lock order" and "Other checks in the gate" (phase guard, static check),
    03 `instance` (row created by `migrate up`), 18 (version constants) and upgrade.md already say
    what this ticket builds.

## Design notes

- Phase guard (02 "Lock order": enforce the lock order at run time instead of relying on
  review): the `Counters` service checks `txn.CurrentPhase(ctx)`:
  `Advance(permission_version)` only in `rights_begin`; `Advance(event_seq)` only in `sync`;
  `Advance(audit_seq)` only in `audit`; `Current(...)` only in one of the four hook phases. Any
  other call returns kind `internal` with a message naming counter and phase. `n < 1` is an
  internal error. Unknown names are rejected in the domain before SQL; the table `CHECK` is the
  second line.
- Static check: `TestCountersOnlyUsedByPhaseHooks` parses the Go packages under `internal/`
  (`golang.org/x/tools/go/packages` if already in `go.mod`, else `go/parser` plus `go/types`) and
  lists every package that references `instance.Counters` or its methods. Allowed: `internal/instance`
  and its subpackages, `internal/wire`, and the packages of the hook handlers in the real
  `txn.Registry` registrations (field `Handler` of the M1-13 registrations, package derived from
  the function name). Any other package fails the test. A fixture package under
  `internal/wire/testdata` that references `Counters` must be reported (negative test).
- Commit order: the row lock taken by `Advance` is held until commit; in `READ COMMITTED` a waiting
  transaction rereads the committed value (04 "Pattern with a counter row" items 1 to 4).
  Nothing in this module may run `SELECT ... FOR UPDATE` on the counters outside `Advance`.
- `instance` row: `id = 1` (`CHECK (id = 1)`), `instance_id` and `sync_epoch` UUIDv7 from
  `kernel/ids`, `schema_version` from goose, `created_at` default. Created by `migrate up` (03
  `instance`). Concurrent `migrate` runs are safe by `INSERT ... ON CONFLICT (id) DO NOTHING`
  followed by the update.
- Readiness message: `/readyz` names only the check (`schema_requires_newer_server`), no
  versions (16 "Two listeners"); the log line at start gives both versions.
- Start check runs once at start (02 "Start" step 5 and 16 "Upgrade" item 4: the process keeps
  running but never becomes ready).

## Tests (write them first)

Integration tests use `pgtest` and connect as `bothy_app` unless stated.

- `TestMigration_InstanceTablesMatchSpec`: columns, types, nullability, defaults, checks and keys of
  both tables read from `information_schema` and `pg_constraint` equal the 03 definition.
- `TestMigration_CounterRowsCreated`: three rows with value 0.
- `TestCounters_ConcurrentAdvanceGaplessInCommitOrder`: many goroutines run units whose test
  `sync` hook calls `Advance(event_seq, k)` with random k and writes the range into a scratch table;
  a random sleep after `Advance` and random rollbacks; a reader polls the scratch table and at every
  read the visible ranges form one contiguous block from 1; at the end the block ends at the
  committed counter value.
- `TestCounters_RollbackLeavesNoGap`.
- `TestCounters_PhaseGuard`: `Advance` in `work`, `Advance(event_seq)` in `audit`,
  `Advance(audit_seq)` in `sync`, `Advance(permission_version)` in `sync`, `Current` in `work`
  all fail with kind `internal`; the allowed combinations succeed.
- `TestCounters_RejectsUnknownNameAndNonPositiveN`.
- `TestCounters_ValueNeverDecreases`: a direct `UPDATE` lowering a value (as `bothy_owner`) raises;
  `bothy_app` cannot `INSERT` or `DELETE` counter rows.
- `TestCountersOnlyUsedByPhaseHooks` and its fixture case.
- `TestState_RecordMigrationCreatesAndKeepsIdentity`: first call creates the row with UUIDv7 IDs;
  second call keeps `instance_id`, `sync_epoch` and `created_at`, updates the versions.
- `TestState_LoadMissingRow`.
- `TestMigrateUp_RecordsSchemaAndMinServerVersion` (command level): after `migrate up` the row has
  the goose version and `MinServerVersion`; with a database newer than the binary (simulate by
  applying an extra test migration) the row stays unchanged and the exit code is 0.
- `TestStart_MinServerVersionAboveOwn_NotReady`: set `min_server_version` above the own version;
  start the server on port 0; `/readyz` returns 503 naming `schema_requires_newer_server`;
  `/healthz` returns 200.
- `TestStart_InstanceRowMissing_AbortsWithHint`.
- `TestCompareSemVer`: table including pre-release ordering from SemVer 2.0.0 section 11 examples

- `TestMinServerVersionNotAboveOwnVersion`: `MinServerVersion` is valid SemVer and not greater than

## Acceptance criteria

- [ ] Concurrent increments are gapless and follow commit order, also with rollbacks.
- [ ] Counters can only be advanced in their phase; the static check limits `Counters` to
      `instance`, `wire` and registered phase hooks (fixture proves it fails otherwise).
- [ ] Counter values cannot decrease; `bothy_app` cannot insert or delete counter rows.
- [ ] `migrate up` records `instance_id`, `sync_epoch`, `schema_version`, `min_server_version` and
      leaves a newer schema untouched.
- [ ] A start with `min_server_version` above the own version does not become ready and `/readyz`
      names `schema_requires_newer_server`.
- [ ] The setup state is available from `Record.SetupCompleted()` at start.
- [ ] README and CHANGELOG updated; 02, 03, 18 and upgrade.md still match the build; `make check` green.

## Definition of done

Code, tests and docs are complete: `internal/instance/README.md` current (status, ports, tables,
rules), doc comment on every public symbol (purpose, parameters, return value, errors, example
where useful), comments explain why. No new ADR (R-DM-05 and ADR 0009 cover the decision); rulings
go into `docs/DECISIONS.md`. CHANGELOG entry under "Unreleased" in `services/server/CHANGELOG.md`.
The migration has its final sequential number before the merge. `make check` green. Independent
review (`make review` plus a code review over the diff) and the red team gate
(`docs/quality/red-team-gate.md`) over the whole diff with verdict `Urteil: JA` recorded in the
report; findings fixed with a test each and the delta re-checked. Merge locally into the base
branch only if review and red team are green, then `git worktree remove`.
