# M2-28: Cost reconciliation as its own app

Status: ready | Depends on: M2-22, M2-24 | Milestone: M2

## Goal

After this ticket the estimated costs of agent runs can be replaced by the amounts of the provider's invoice data without the provider's admin key ever reaching the server. A separate app in `plugins/cost-reconciler` (its own process, default off, no inbound port) reads the admin key from its own secret provider, fetches daily cost buckets per provider workspace, distributes each day's amount over the estimates of the agents mapped to that workspace (in proportion to the estimates, the rounding remainder to the largest one, anything without a run reported as not assigned, BR-10) and submits the result with an app token that carries only the scope `costs:reconcile` (`submitCostReconciliation`, action `cost.reconcile.submit`, no step-up). An owner can do the same by hand with step-up (`reconcileCosts`, action `cost.reconcile`); app, agent and personal tokens are refused there (R-AZ-03). Both ways store new `reconciled` entries next to the estimates, never change or delete an existing entry, and apply them through the same job `billing.reconcile`, which brings `runs` and `agent_sessions` (amounts and the estimate flags) up to date. Why: the estimate from tokens and a price table misses surcharges, discounts and price tiers (10 12.1 to 12.3, RK-16), and an admin key of the provider organisation can manage members and keys, so a break-in into the chat server must not reach it (10 12.4, ADR 0055, RK-17, baseline B10 and I5).

Product requirements implemented here:

11. The reconciliation is an app outside the server, off by default, with its own process, its own configuration and its own secret provider; the provider's admin key exists only there; the app needs no inbound port and talks to the server only through the public API (10 12.4, ADR 0055 points 1 and 4, 11 1, PLAN P-18).
12. The server never receives, reads, stores or forwards a provider key: no server configuration key, table column, job argument or code path for it, and no environment read of provider credentials (`.semgrep/bothy-go-no-model-credentials.yaml`; ADR 0055 "Confirmation"; B10, I5; PLAN row "the server stores no vendor key (canary)").
13. `cost.reconcile` (`reconcileCosts`): instance, owner only, step-up `yes`, audit `yes`, `rl.admin`, effect `write`; agent, app and personal tokens are refused (05 4.12, 2.4, R-AZ-03; 07 4.2).
14. `cost.reconcile.submit` (`submitCostReconciliation`): instance, only an app with the granted scope `costs:reconcile`, no step-up, audit `yes`, `rl.admin`; it only adds `reconciled` entries to existing runs and never changes or deletes another entry (05 2.6 and 4.12, ADR 0055 point 3 and "Confirmation", 10 12.4 "Authorization").
15. A reconciled entry has `source = 'reconciled'`, `is_estimate = false`, `reconciled_at` and `supersedes_id` on the entry it replaces; every entry has at most one successor; the valid sum is the sum of the entries without a successor (03 `cost_entries`, 10 12.4 point 4).
16. Both ways apply their entries through the same job `billing.reconcile` in queue `default`, never periodic; job arguments carry only IDs; the job can run again without a second effect (02 12.1, 12.3, 12.4; PLAN row M2-28).
17. After the job, `runs.cost_micros`, `runs.cost_is_estimate`, `agent_sessions.cumulative_cost_micros` and `agent_sessions.cost_is_estimate` reflect the valid entries; amounts of different currencies are never converted (10 12.1 and 12.4 point 4).
18. The app distributes each day's amount of a workspace over the estimates of the mapped agents in proportion to the estimates; the sum equals the actual amount; the rounding remainder goes to the largest entry; amounts without a matching run are reported as not assigned (10 12.4 point 3, ADR 0055 point 2, BR-10).
19. The app asks the provider at most once per `reconciler.min_request_interval`, for the last `reconciler.lookback` days, and maps workspaces to agents through `reconciler.workspace_map` (10 12.4 points 1, 2 and 5; 10 17).
20. The audit entry of a reconciliation holds the period, the numbers of entries and the sums per currency, never a secret or free text (10 14; 19 SEC-AUD-5, SEC-SEC-3).
21. Errors follow 06 "Errors" with codes from `x-problem-codes`; both operations accept `Idempotency-Key` with the behaviour of 06 "Idempotency".
22. Amounts of runs in mode `personal` are information, never invoice (03 `cost_entries`, 10 12.2); they are never reconciled (Design note 4).
23. `cost.reconcile.read` (`listCostEstimates`): instance, an owner in a session or an app with the granted scope `costs:reconcile`, no step-up, audit `no`, effect `read`, `rl.read`; per run it returns only run, agent, provider, currency, the estimate and whether it is reconciled, of mode `organization`, never a channel, a thread or content, and it is not filtered by visible channels; agents, personal tokens and people who are not owners get `403 forbidden` (05 rule 1.2, 2.6, 2.7, 4.12 and R-AZ-28; 06 4 point 2).

4. **Matching** (Ruling for docs/DECISIONS.md, documented in 10 12.4). A request entry for run R is matched when R has at least one valid entry in the period and all of them have `billing_mode = 'organization'`, `provider` equal to the request's `provider` and `currency` equal to the entry's `currency`. Otherwise R is unmatched: no cost entry at all (also an unknown or still active run; `billing` cannot and need not tell them apart), no valid entry in the period, mode `personal` (amounts are information, never invoice, 03), another provider, another currency or mixed currencies (no conversion, 10 12.1). A matched run is a no-op when all its valid entries in the period are `reconciled` and their sum equals the amount: nothing is written and it counts as reconciled. Reason: the app submits the same days again on every pass within `reconciler.lookback`; the second pass must not grow the chain. A different amount supersedes the reconciled entries (a correction, "a correction entry replaces an earlier one", 03). Entries of R outside the period stay as they are (a run with turns on two days is reconciled per day).

5. **Split within a run** (Ruling for docs/DECISIONS.md). One request entry carries one amount per run, but a run has one entry per model and turn (10 12.1, 09 4.10). The amount A is split over the run's valid entries in the period in proportion to their current amounts: share = floor(A times amount_j divided by the sum); the remainder goes to the entry with the largest amount, ties to the smallest `id`; if all amounts are `0`, the whole of A goes to the entry with the smallest `id`. Every valid entry in the period gets exactly one successor, also with share `0`, so no estimate stays valid next to a reconciled amount. Compute without int64 overflow (`math/big` or `math/bits`). Reason: the same rule as BR-10 one level down; the per-model attribution is a proportion, as the ADR states for the day.

6. **Job `billing.reconcile`** (02 12.3, queue `default`, River defaults, never periodic): the handler in `internal/billing/adapters/jobs` calls `ApplyReconciliation(ctx, runIDs)` in one unit of work:
   a. For each run ID of the job in ascending order `SELECT pg_advisory_xact_lock_shared(hashtextextended('billing.reconcile:' || $1::text, 0))`. With the exclusive lock of note 3c this orders a job against a concurrent request: a request that commits new rows after the job read the totals had to wait for the job, and its own job runs afterwards.
   b. Per run: amount = sum of the valid entries (all periods), currency = their currency (one currency per run after note 4; if a run's valid entries mix currencies, leave that run unchanged, log the run ID without amounts and go on), is_estimate = any valid entry has `is_estimate = true`.
   c. Per `agent_session_id` of these runs: the same over all valid entries of the session (query by `thread_id` and `agent_session_id`, index `(thread_id)`).
   d. `txn.Publish(ctx, billing.CostsReconciled{Runs, Sessions})`, both lists in ascending ID order.
   e. Ruling for docs/DECISIONS.md, with 02 12.3 updated ("the request stores the `reconciled` entries; the job applies them to runs and sessions"): the request stores the entries because job arguments carry only IDs (02 12.1; `ValidateArgsType` of M1-14 allows only `ids.ID`, `[]ids.ID` and `int64`) and 03 has no other table that could hold a submission; the job applies them. ## Acceptance criteria

- [ ] Preconditions of Design note 1 checked and named in the report; the read operation is built exactly as 05 4.12 and 2.6 define `cost.reconcile.read` (R-AZ-28) and `docs/api/openapi.yaml` defines `listCostEstimates`.
- [ ] `reconcileCosts` and `submitCostReconciliation` (and the read operation) are enabled and registered with their actions and `rl.admin` (the read operation with the class of its catalogue entry); AZ-P1 passes.
- [ ] BR-10: the app's distribution sums to the actual amount, puts the remainder on the largest entry and reports unassigned amounts; the server replaces each estimate in the period by exactly one reconciled entry.
- [ ] The server stores no provider key: the canary admin key appears in no table, job, log, request or response of the server, the positive control holds, and the server's configuration has no `reconciler.` key.
- [ ] Both ways apply their entries through the same job `billing.reconcile`; the job is never periodic and can run again without effect.
- [ ] `reconcileCosts` needs an owner with a fresh step-up; app, agent and personal tokens get `403 forbidden` (`owner_only`) and are audited (R-AZ-03).
- [ ] `submitCostReconciliation` works only for an app with `costs:reconcile`; it only adds `reconciled` entries to existing runs and never changes or deletes an entry.
- [ ] After the job, `runs` and `agent_sessions` carry the valid sums and `cost_is_estimate = false` where everything is reconciled; `agent_sessions.version` rose by one exactly for the sessions whose totals changed.
- [ ] Audit entries carry period, counts and sums per currency only.
- [ ] `docs/api/openapi.yaml`, 10 12.4 and 17, 02 4.3 and 12.3, the configuration reference, ADR 0055 "Confirmation", the READMEs and `docs/DECISIONS.md` are updated.
- [ ] `make check` is green.

- `make check` green.
- An independent code review over the diff, then the red team gate (`docs/quality/red-team-gate.md`, verdict `JA` or `NEIN`), with attention to T-PL-01, T-TK-02 and RK-17: can any path put the admin key into the server or its logs, can an app token reach `cost.reconcile`, can a submission change or delete a non-reconciled entry or reconcile a `personal` run, can the app send the key to another host; on `NEIN` fix with a test per finding and have the delta checked again.
