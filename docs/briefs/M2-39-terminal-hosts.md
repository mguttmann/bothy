# M2-39: Host records and the target `host`

Status: ready | Depends on: M1-48 | Milestone: M2

## Goal

After this ticket the server module `terminal` exists with its three tables `hosts`, `host_session_users` and `terminal_sessions` and with the first five operations of the API group Hosts. An owner with step-up creates a host in state `pairing` and receives its pairing code `bothy_hpc_...` exactly once (`createHost`), renames it, sets or clears its holder, assigns people their own session user and ends assignments (`updateHost`, ruling T12), and disables, enables and retires it (`setHostState`). Everyone who may read a host (every owner, its holder, every person with a grant `terminal` on it in effect, also through a group) lists and reads it (`listHosts`, `getHost`); everyone else gets `404`, identical to an unknown id. Every change is a rights change with step-up, a mandatory reason, an audit entry and the event `host.updated`, which never carries a key. Every state change follows the life cycle of 24 "States"; a transition out of `active` ends all sessions of the host, and the end of an assignment ends the sessions of that person on the host, in the same transaction that raises `permission_version`. In `authz` the host becomes a real target outside the tree `instance` -> `space` -> `channel`: the source `authz.HostSource`, the rights snapshot per host, the atoms for the holder and for `+terminal`, visibility of `host`, real requirement entries for `host.read` and `host.manage` instead of deferred ones, host entries in `access.changed`, and grants on hosts that reference a real row (the foreign key `grants.target_host_id` deferred by M1-27). The signing-key purpose `terminal` gets its active key at start (`EnsureActive` of M1-32). On these records M2-40 builds the guards SR10, SR11 with I6 and SR12 and the actions `terminal.*`, M2-41 pairing, M2-43 the control connection, M2-44 sessions and the relay, M2-46 revocation and limits.

Product requirements implemented here:

11. Life cycle (24 "States", 3.2): the five states `pairing`, `confirming`, `active`, `disabled`, `retired`; a transition exists only as the diagram of 24 3.1 draws it, plus the fall back from `confirming` to `pairing` after `terminal.fingerprint_max_attempts` failures (24 3.2); every other request gives `409 invalid_state_transition`; a host disabled with `disabled_reason = duplicate_connection` cannot be enabled, only paired again; only `active` allows sessions. Every state change raises `permission_version` (03 4.3, paragraph after `grants`), and every transition out of `active` ends all sessions of the host (`host_disabled`, `host_retired`), in the same transaction.
12. `host.read` (05 4.14, 07 2.12 point 5): owners read every host, the holder (`hosts.assigned_user_id`) reads the own host, a person with a grant `terminal` in effect on the host (directly or through a group in effect, also when SR10 blocks it) reads that host; everyone else gets `404` with the same status, body and headers as for an unknown id (05 rule 1.2, AZ-P4). The host is a target outside the tree; a grant on the instance gives no host (07 2.12 point 1, R-AZ-24, AZ-M60).
13. `host.manage` (05 4.14): owner only, step-up `yes`, a mandatory reason, Audit `yes`, Permissions `yes`. Agents, apps and personal tokens reach neither `host.read` nor `host.manage`: `403 forbidden` with `reason` `subject_kind_not_allowed` (05 4.14, SR5, R-AZ-23).
14. Grants on hosts (07 2.12 points 1 to 3, 24 8.1, 03 `grants`, R-DM-35): only owners create them, only for people and groups, without level and with exactly the capability `terminal`; `grants.target_host_id` references `hosts(id)` with `ON DELETE RESTRICT`; a change of the effective `terminal` right appears in `access.changed` as an entry `{kind: host, id, capabilities: [terminal]}` without `level` (04 8.2).
15. Session users (ruling T12, 24 2.2 points 1, 2 and 5, 03 `host_session_users`, R-DM-39, R-DM-41): an owner assigns a person a session user only with a name the host reported in `hosts.reported_session_users`, otherwise `400 validation_failed` with `errors[].code` `session_user_not_on_host` and nothing stored (TM-T28 (e)); a name is unique per host over all rows, including ended ones, without regard to case, and a person has at most one valid assignment per host, otherwise `409 conflict` with `reason: session_user_taken` and nothing changed (TM-T28 (b)); an ended row stays and keeps its name taken; the end of an assignment ends the sessions of that person on the host in the same transaction (`access_revoked`, SR12, 24 8.3).
16. `terminal_sessions` holds metadata only, never content or commands (03, R-DM-36); its session user belongs to the same host and person through the composite foreign key `(host_session_user_id, host_id, user_id)` -> `host_session_users(id, host_id, user_id)` (R-DM-40, D-W-66).
17. `host.updated` (05 6, 24 10.2): durable, receive action `host.read`, written on every change including the creation, with the host's state, holder, LLM declaration, profiles, check results and session user assignments; never a key, never the pairing code or its hash.
18. Audit (24 10.1, 19 SEC-AUD-5): every `host.manage` write and every refusal is audited; details are codes, IDs, the mandatory reason and the session user name of an assignment, never the host name, a pairing code, a key, a path or terminal content. Every session the server ends is audited with the system action `terminal.terminate`.
19. Pairing code (24 3.2 point 1, ADR 0061, 03 principle 9, D-T32): `createHost` returns `bothy_hpc_<random>_<checksum>` exactly once with `Cache-Control: no-store`; only its HMAC-SHA-256 with the server pepper is stored (`hosts.pairing_code_hash`), valid until `pairing_expires_at` = creation plus `terminal.pairing_code_ttl`; the code never appears in a log, an event, an audit entry, the idempotency store or a test failure message.
20. Signing-key purpose `terminal` (03 `server_signing_keys`, 24 5.3, D-T33): `EnsureActive` creates an `active` key for it at every start; it rotates only on owner request, its retiring window is `terminal.session_token_ttl` plus `auth.clock_leeway`, and `getJwks` does not publish it (the host service gets the keys over its control connection, M2-43).
21. Display texts without control or bidi characters (SEC-IN-4): host names at most `host.name_max_chars` characters, session user names at most `host.os_user_max_chars` characters and never a path, reasons at most `audit.reason_max_chars` characters; no JSON `null` in any response or event (ADR 0053).

## Design notes

**1. Module layout and port.** `internal/terminal` follows the module layout of 02 (port in the root package, `domain` without dependencies outside `kernel`, `app` with outgoing ports, `adapters/postgres`, `adapters/httpapi`). The port `Hosts` (02 4.3 names it) is:

```go
type Hosts interface {
    List(ctx context.Context, p actor.Principal, page Page) (HostPage, error)
    Get(ctx context.Context, p actor.Principal, hostID ids.ID) (HostView, error)
    Create(ctx context.Context, p actor.Principal, cmd CreateHost) (PairingCodeIssued, error)
    Update(ctx context.Context, p actor.Principal, cmd UpdateHost) (HostView, error)
    SetState(ctx context.Context, p actor.Principal, cmd SetHostState) (HostView, error)
}
```

`actor.Principal` stands for the request principal type of `kernel/actor`. DTOs: `CreateHost{Name, Reason string; AssignedUserID ids.ID}`; `UpdateHost{HostID ids.ID; IfMatch int64; Name string; NameSet bool; AssignedUserID ids.ID; ClearAssignedUser bool; Add []SessionUserAssign; Revoke []ids.ID; Reason string}`; `SessionUserAssign{UserID ids.ID; OSUser string}`; `SetHostState{HostID ids.ID; IfMatch int64; State, Reason string}`; `PairingCodeIssued{HostID ids.ID; Code <the redacting secret type of M1-44>; ExpiresAt time.Time}`; `HostView` mirrors the schema `Host` field by field (zero values mean absent); `HostPage{Items []HostView; NextCursor string}`. No `Sessions` or `Relay` port yet; M2-44 adds them. Outgoing ports of `app`: `Store` (the repository), `PairingCodes { Issue(ctx context.Context) (PairingCode, error) }`, `People { User(ctx context.Context, id ids.ID) (UserFacts, error) }` with kind and status, `Presence { Connected(ctx context.Context, hostID ids.ID) bool }`. `internal/wire` binds them to `identity.Tokens`, `identity.Directory` and `NoConnections` (Design note 8).

**2. Life cycle as a pure function.** `domain.Transition(from State, disabledReason string, c Cause) (Result, error)` with `Result{To State; DisabledReason string; EndSessions bool; CloseReason CloseReason}` and `ErrInvalidTransition` (mapped to `409 invalid_state_transition`). It is the only place that knows the transitions; M2-41 and M2-43 call it for theirs. Every transition raises `permission_version` (03 4.3), so callers run it in a unit of work with a rights change. The table, first column the state before (none for a new host):

| From | Cause | To | Ends sessions with | Driven by |
|---|---|---|---|---|
| none | `create` | `pairing` | | `createHost` (this ticket) |
| `pairing` | `pair` | `confirming` | | `pairHost` (M2-41) |
| `pairing` | `new_pairing_code` | `pairing` | | `issueHostPairingCode` (M2-41) |
| `confirming` | `confirm` | `active` | | `confirmHost` (M2-41) |
| `confirming` | `new_pairing_code` | `pairing` | | M2-41 |
| `confirming` | `fingerprint_attempts_exhausted` | `pairing` | | M2-41 (24 3.2) |
| `active` | `new_pairing_code` | `pairing` | `host_rekeyed` | M2-41 (24 3.3) |
| `active` | `disable` | `disabled` with reason `owner` | `host_disabled` | `setHostState` (this ticket) |
| `active` | `duplicate_connection` | `disabled` with reason `duplicate_connection` | `host_disabled` | M2-43 (24 3.4) |
| `active` | `retire` | `retired` | `host_retired` | `setHostState` |
| `disabled` | `enable` | `active` (only with reason `owner`) | | `setHostState` |
| `disabled` | `new_pairing_code` | `pairing` | `host_rekeyed` | M2-41 |
| `disabled` | `retire` | `retired` | `host_retired` | `setHostState` |

Every other pair is `ErrInvalidTransition`, among them every cause from `retired`, `enable` with `duplicate_connection` (24 3.1), `disable` and `retire` from `pairing` and `confirming`, and every cause that would keep the state except `new_pairing_code` on `pairing`. A request for the state a host already has is not a transition; the use case answers it as "No effect" (Design note 4). Ruling for docs/DECISIONS.md: every transition into a state other than `active` sets `EndSessions` (when leaving `disabled` there are normally no open sessions; ending them anyway costs one indexed query and closes any row a crash left behind).

**3. The target `host` in `authz`.** Everything below lives in `internal/authz` (rights logic only there, 05 rule 1.1).

- Source (`sources.go`), read fresh per call inside the ambient transaction, like `StructureSource` (host facts are few and change rarely; a stale cache would decide on an old holder):

    ```go
    type HostFacts struct {
        ID                   ids.ID
        State                string // pairing, confirming, active, disabled, retired
        AssignedUserID       ids.ID // zero: owners only (SR10)
        LLMCredentials       string // none, personal, organization (consumed by M2-40)
        CredentialHolderID   ids.ID // set exactly with personal (consumed by M2-40)
        DeclaredServerHost   bool   // consumed by M2-40
        ReportedIsServerHost bool   // false while not reported; consumed by M2-40
    }
    type HostSource interface {
        Host(ctx context.Context, id ids.ID) (HostFacts, bool, error)
        HostIDs(ctx context.Context) ([]ids.ID, error)                    // every host, ascending
        AssignedTo(ctx context.Context, userID ids.ID) ([]ids.ID, error) // ascending
    }
    ```

    The fields follow 02 4.3 ("the host's state, assignee, LLM declaration, server host"). The implementation is `internal/terminal/app/hostsource.go` over the terminal store; `internal/wire` binds it.

- Snapshot (`domain/snapshot.go`): replace "host grants are skipped" by a map `Hosts map[ids.ID]Caps` built from the grants in effect with target `host` (the principal's own and, for people, those of their groups in effect; `Grant.InEffect` and `Membership.InEffect` of M1-27); their `expires_at` enter `ValidUntil`. Host grants never enter `Instance`, `Spaces` or `Channels`.
- Effective right: `TerminalOn(s Snapshot, hostID ids.ID) bool` is true for an effective owner, or when `s.Hosts[hostID]` contains `terminal` (07 2.12 point 3). Ruling for docs/DECISIONS.md: the exception of I6 for owners on a `personal` host (07 2.12 point 3, first bullet) is decided by the SR11 guard of M2-40 with reason `i6_holder_only` (AZ-M56), which comes after the requirement (07 4.2 step 9); before M2-40 no host can be `personal` (only `confirmHost` and `setHostLlmCredentials` set `llm_credentials`), so the atom does not repeat it.
- Atoms (requirement table of M1-28): `HumanSession` (kind `user`, acting in a session, not with an API token; reason `subject_kind_not_allowed`); `Assignee` (the resource is a host whose `AssignedUserID` is the principal; reason `not_self`); `Terminal` (`TerminalOn` for the resolved host; reason `capability_missing`).
- Mapping row for the 05 text `owner or assignee or +terminal`: `Any(Owner, Assignee, Terminal)`. Overrides by action id (they win over the text rule): `host.read`: `All(HumanSession, ByKind{instance: Auth, host: Any(Owner, Assignee, Terminal)})` (`instance` is the resource of `listHosts`, as `listGroups` does in M1-48); `host.manage`: `All(HumanSession, Owner)`. Remove both from the deferred entries and from the golden list of deferred actions in the same change; `host.pair`, `host.connect` and `terminal.*` except the system action stay deferred.
- Gate before resolution: when the requirement of an action is `All(HumanSession, ...)`, `authorize` evaluates `HumanSession` right after step 1 of 07 4.2 (after `check_active` and the pending checks, before snapshot, resolution and visibility) and answers `forbidden` with `subject_kind_not_allowed`. The answer depends only on the principal, never on the resource, so it reveals nothing (an agent gets the same `403` for an existing and for a random host id, AZ-P4). Ruling for docs/DECISIONS.md: 05 4.14 refuses agents, apps and personal tokens with `subject_kind_not_allowed` (TM-T17, AZ-M59), which visibility first would turn into `404`; update 07 4.2 with one paragraph. M2-40 uses the same gate for `terminal.*`.
- Resolution: a resource of kind `host` resolves through `HostSource.Host`; missing gives `not_found` with `no_grant`. A `grant` resource with target `host` keeps M1-28's rule (no path in the tree, only `Owner` passes) and resolves the host for existence.

Memoised per request (`WithRequestScope`), never stored in the cache entry.

The difference step drops everyone without a change.
- `Admin.CreateGrant` with target `host`: the host must exist (`404` otherwise, like an unknown space); a host in state `retired` gives `409 conflict` like an archived target. **4. The five operations.** Every operation calls `authorize` before it reads anything else, then validates, then writes in one unit of work. Answers in this order: `403 forbidden` with `reason` `subject_kind_not_allowed` (gate), `404` (unknown or invisible host), `403 forbidden` with `reason` `owner_only` (a visible host, not an owner), `401 step_up_required`, `400 validation_failed` for the checks of the body alone, `428 precondition_required` and `412 version_conflict` with `current`, then the checks against stored state (`400 validation_failed` for a name the host does not report before any `409`), success. Schema validation of the generated server and a presence check of `If-Match` in the merged chain may answer earlier; keep the chain's order where it does and name it in the report.

- `listHosts` (`host.read`, `rl.read`): `authorize(host.read, Resource{Kind: instance})`, then `Scope`; query `WHERE ($all OR id = ANY($ids))` ordered by `lower(name)` then `id`, keyset cursor over both (cursor helper of M1-31; a foreign or broken cursor `400 cursor_invalid`), `limit` default `api.page_size_default`, capped at `api.page_size_max`, no totals; then `authorize(host.read, host)` per element in filter mode, dropping a mismatch as 07 7.4 rule 3 and the list use cases of M1-48 do. Hosts in every state are listed, `retired` included. Ruling for docs/DECISIONS.md: retired hosts stay readable records (retention `security` after `retired_at`), and the contract has no filter parameter.
- `getHost` (`host.read`, `rl.read`): `authorize(host.read, host)`; `200` with `HostView` and `ETag: "<version>"`.
- `createHost` (`host.manage` on `instance`, `rl.admin`, `x-idempotency-exempt: auth_flow`, so no `Idempotency-Key` handling and no stored answer):
    1. `authorize`; then body: `name` trimmed, not empty (`required`), `textcheck.DisplayText` (its rule codes), at most `host.name_max_chars` characters (`too_long`); `assigned_user_id` absent or a principal of kind `user` whose status is not `deleted` (`People.User`), else `400 validation_failed` with `errors[].code` `unknown_user` and pointer `/assigned_user_id`; `reason` trimmed, not empty, `textcheck.DisplayText`, at most `audit.reason_max_chars` characters.
    2. Name taken by a host that is not `retired` (case-insensitive, also when the unique index fires in a race): `409 conflict` without a `reason`. Ruling for docs/DECISIONS.md, like group names in M1-29.
    3. `PairingCodes.Issue` before the unit of work (no slow work inside a transaction).
    4. Unit of work with a rights change (`Action: host.manage`, `Resource: host` with the new id, `Targets: [host]`, `Principals: [holder]` when set): insert the row (UUIDv7, `state = pairing` through `Transition(none, create)`, `pairing_code_hash`, `pairing_expires_at = t + terminal.pairing_code_ttl`, `created_by`, defaults of 03 for the rest), `host.updated`, audit allow. The hook writes `access.changed` for every active owner (`added` host entry).
    5. `201` with `HostPairingCode{host_id, pairing_code, expires_at}` and `Cache-Control: no-store`; the handler calls `idempotency.MarkOneTimeSecret(ctx)` as a second guard if the M1-20 middleware runs for exempt operations.
- `updateHost` (`host.manage` on `host`, `rl.admin`, `Idempotency-Key`, `If-Match` required):
    1. `authorize`; body: at least one of `name`, `assigned_user_id`, `clear_assigned_user = true`, a non-empty `add_session_users` or `revoke_session_users`, else `400 validation_failed` with an empty pointer and `errors[].code` `required`; `name` and `reason` as in `createHost`; `assigned_user_id` with `clear_assigned_user = true` gives `400 validation_failed` with `errors[].code` `mutually_exclusive` and pointer `/clear_assigned_user`; each `add_session_users` entry: `user_id` as `assigned_user_id` (pointer `/add_session_users/<i>/user_id`, `unknown_user`), `os_user` through `domain.NewOSUser` (pattern of 03, at most `host.os_user_max_chars`, `too_long`).
    2. Compare `If-Match` with the current `version` (`428 precondition_required` when absent, `412 version_conflict` with `current` when different), then decide "No effect" in a read before any rights change (phase 1 raises `permission_version` unconditionally): same name, same holder, nothing to add and only people without a valid assignment to revoke gives `200` with the current host, no new version, no event, no rights version, and one audit entry with `no_change: true`.
    3. Unit of work with a rights change (`Targets: [host]`, `Principals`: old and new holder, every person in both lists): lock the host row `FOR UPDATE`, compare `version` again (`412` on a race); a `retired` host gives `409 conflict` (ruling: retired is final, 24 3.1); revocations first, then additions (Design note 6); the name and holder change; `version + 1`; one `host.updated`; the audit entries of Design note 9.     4. `200` with the `HostView` and `ETag`.

**5. **6. Session users (T12).** `domain.PlanAssignments(reported []ReportedSessionUser, rows []SessionUserRow, revoke []ids.ID, add []SessionUserAssign) (Plan, error)` is pure; the use case feeds it the locked rows of the host (`FOR UPDATE`, ascending `id`).

- Revocations first: each listed person with a valid assignment gets `revoked_at = t`, `revoked_by` = the owner; a listed person without one has no effect for that entry. Then `EndSessions(host, that person, access_revoked)`.
- Additions after the revocations, so one request can move a person to a new session user: the name must equal a reported `os_user` exactly, including case (else `400 validation_failed` with `errors[].code` `session_user_not_on_host` and pointer `/add_session_users/<i>/os_user`); then a row of this host with the same `lower(os_user)`, valid or ended and of any person, or a remaining valid assignment of the same person, gives `409 conflict` with `reason: session_user_taken`. All `400` checks of all entries come before any `409` check, and both before any write. Duplicates inside one request fall under the same two rules.
- Ruling for docs/DECISIONS.md: a reported name matches only exactly, because the host service compares `osu` exactly with `host_service.session_users` (24 5.3) and a case variant would fail there with `4104`; uniqueness stays case-insensitive (03). Update 24 2.2 point 5 with one sentence.
- Rows are never deleted or updated except `revoked_at` and `revoked_by`; the database unique indexes are the last line (map `23505` on them to the same `409`).
- `HostView.session_users` lists the valid assignments ordered by `created_at` then `id`, absent when there is none.

**7.
