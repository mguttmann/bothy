# M2-35: Claude Code runner: follow-ups, stop and error paths

Status: ready | Depends on: M2-34 | Milestone: M2

## Goal

After this ticket the Claude Code runner of M2-34 handles everything that can happen to a turn after it started, in the final state of 09 18.5, 18.6 and 18.9. Follow-ups of people reach the running turn as further `user` lines on stdin and come back as `delivered` and `absorbed`; after the `result`, stdin stays open for `runner.followup_grace` while follow-ups are not yet absorbed. A stop sends SIGINT to the turn's process group, then SIGTERM after `runner.stop_grace` and SIGKILL after `runner.kill_grace`, and reports `cancelled` with the reason of the request only when no process of the group is left. A full context is compacted exactly once and the same prompt runs again, with a hint when the turn had already worked; a session that Claude Code no longer knows is replaced by a new one without blocking the run (fail open), and a session that already exists at the first turn is resumed; a missing login ends the run with `runtime_not_authenticated`, an error `result` with `runtime_error` and the error texts in the last step; a crash of the runner kills and repeats nothing, because a new runner takes the turn over or ends it. Every row of 09 18.9 "Error paths" has one green Fake-Claude scenario (plan row M2-35, exit criterion 5 of M2), the recognised error texts of the CLI live in one table in the runner, and a test behind the explicit switch checks them against the installed, pinned CLI (RK-14). Why: an unattended turn must never hang, run twice, outlive a stop or carry a follow-up that the server did not authorize into a runtime (09 1 points 4 and 5, R-AG-17, T-AI-08), and the CLI changes its messages without notice (RK-14).

## Design notes

1. **What exists and where this goes.** M2-34 built the runner: its configuration (09 21), the consumer through the SDK (`bothy_sdk` modules `gateway`, `invocation`, `runs`, `heartbeat`, `outbox`), the inbox in `runner.state_dir` (09 4.3), the token check of 4.5, the pre-check and the counter-check of 18.3, the start of `claude -p` with the flags of 18.2 per tool class in its own process group (`start_new_session`), the session and thread locks, the stream reader of 18.4, the answer, the cost difference of 18.7, the session report with `started = true` at `system/init`, Fake-Claude and its fixtures. This ticket adds what happens after a turn started. Every decision is a pure function without I/O (`classify_turn_end`, `next_action`, `followup_verdict`, `stdin_close_due`, `escalation_due`, `adoption_decision`), so it gets a table test; the I/O stays in M2-34's turn runner, which calls them. Where the merged code of M2-34 already does one of these things, extend it instead of building a second path, and list it.

2. **Follow-up intake** (`agent.followup`; 09 4.4, 7, 18.5; 04 15.4 points 2 and 3).
   a. Acceptance into the inbox is 4.3 unchanged (M2-34): the token passes the checks of 4.5 except point 5, event and token are stored, then the event is acknowledged. The same `message_id` of the same run again (a redelivery with a new token) replaces the stored token while the follow-up is not yet written and is never written twice ("Duplicate detection").
   b. At the moment of writing, the runner checks the stored token again with points 1 to 6 and 8 to 10 of 4.5 as M2-34 applies them before a start, point 5 included (expiry with `adapter.invocation_token_leeway`; point 7, the replay check, ran at acceptance), plus: `run_id` is the run of the turn, `trigger_kind` is `followup`, and the message read in note 3 belongs to the run's thread and has the author `sub`. Ruling for docs/DECISIONS.md: the expiry is checked when the text reaches the runtime, because that bounds how old the server's rights decision behind the follow-up can be (`agent.invocation_token_ttl`); a follow-up starts nothing here, so 4.5.1 does not apply (renewal takes only start tokens, 5.1).
   c. Outcomes of `followup_verdict`: all checks pass: `write` (note 4); the turn has not started yet: `hold`; any other failed check: `skip`, the follow-up is not written and not acknowledged in the run document, the turn goes on, the follow-up stays `queued` and the server defers it at the end of the run (09 7), so its next delivery is checked again. A follow-up token whose `billing_mode` differs from the mode of the running turn, or whose `tool_class` is below `runner.tool_class`, is refused by the SDK at acceptance (09 4.5 points 8 and 10; M2-29 Design note 9: not handed to the handler, the run is not ended). If it passes acceptance (for example `personal` with `runner.allow_personal`), the check at writing time gives `skip` (log code `followup_check_failed`). The follow-up stays `queued` and the server defers it to the next run, which uses the new target (10 10.2). Ruling for docs/DECISIONS.md: unlike at a start (4.5 "reports the reason"), a broken follow-up token never ends the run, because the run belongs to the person who started it and a follow-up must never end another person's run (M2-11 requirement 18).
   d. A follow-up for a run the runner does not hold, or for a turn whose stdin is closed (note 5), is acknowledged and dropped (log code `followup_not_deliverable`); the server defers it.

3. **Text of a follow-up.** `AgentFollowupPayload` carries no text (04 2.2 rule 4). The runner reads the message with `getMessage` (action `message.read`, `rl.read`; the agent reads a message of the thread it operates). A `404`, a message with `deleted_at` or an empty `content_md` is not written (log code `followup_no_text`); the follow-up stays `queued` (M2-11 discards a deleted one). The text reaches the runtime as an instruction, not as marked data: a valid follow-up token proves that the server checked `agent.invoke` for its author at the delivery (04 15.4 point 2), which requires effective `trigger`, and 09 4.6 rates such an author `trigger` or `authorized`, neither of which is marked (ADR 0054). Ruling for docs/DECISIONS.md, with the openapi change: `run.context.read` carries no follow-up of the running run (M2-13 "Out of scope"), so the description of `AgentFollowupPayload.message_id` becomes "Follow-up message; the adapter reads its content with `getMessage` (`message.read`); its author is `sub` of the invocation token of this delivery." The line is one `user` line from M2-34's builder of the prompt line, with a fresh `uuid` (UUIDv4) and the text `Follow-up from <display_name> (@<handle>):`, a blank line and `content_md`, the lead-in in the language of M2-34's runner prompt. Because the line never starts with the message text, a follow-up that starts with `/` (for example `/compact` or `/clear`) never becomes a command of the CLI.

4. **Writing, acknowledging, holding.**
   a. Turn running with open stdin: write the line and flush, then patch `replace /followups/<message_id>/state` with `delivered` through the SDK `runs` helper (`base_version`, throttled by `agent.run_update_min_interval`, rebase after `409 base_version_conflict`). A failed write (the process is gone) leaves the follow-up `queued`.
   b. Echo: a `user` message with `isReplay` on stdout whose `uuid` is that of a written follow-up patches `absorbed`. `absorbed` never goes out before `delivered` (same or a later patch); a second echo of the same `uuid` changes nothing; the echo of the prompt line and unknown `uuid`s are ignored.
   c. Turn not started yet (run in the inbox, waiting for `run.start`, a lock or a slot of `runner.max_parallel_runs`): keep the follow-up with the run and write it right after the prompt line when the turn starts, in event order, with the checks of note 2 b at that moment.
   d. Restart within a run (notes 8 and 9): every follow-up written to the failed process without echo is written again into the next process after the prompt line, with its original `uuid`, so its echo still maps; it stays `delivered`.
   e. An adopted turn (note 12) takes no follow-up: its stdin ended with the old runner. Its follow-ups stay `queued` and the server defers them.
   f. A patch that the server refuses with `400 validation_failed` because the run has no such follow-up (M2-10 note 4) is logged as a code; the turn goes on.
   g. The heartbeat reports `capabilities.followups = steer` (09 2.2, 4.8) from this ticket on.
   Ruling for docs/DECISIONS.md: c, d and e.

5. **End of a turn with follow-ups** (18.5). The runner closes stdin only by this rule (`stdin_close_due`); change M2-34 if it closes stdin after the prompt line. At a `result` without a written follow-up that has no echo: close stdin. At a `result` with such follow-ups: keep stdin open until their echoes or until `runner.followup_grace` after that `result`; a follow-up that passes note 2 within this window is written and joins the set; when the set is empty at a later `result`, close; when the window ends with follow-ups left, close, and they stay `delivered` for the server to defer (09 7). The process then ends, and the run finishes once, after the process exited. Every `result` without error posts one answer through M2-34's answer path, because each answers a different input; the cost difference of the run comes from its last `result` (18.7: the values are cumulative per session). Ruling for docs/DECISIONS.md.

6. **Stop** (`run.cancel_requested`; 09 8 point 3, 18.6, 04 15.5). The event carries no token; the SDK's run loop receives and acknowledges it (M2-29 Design note 9) and, with the run-loop changes of the Scope, calls the hook `on_cancel` for a started run.
   a. Live turn: `os.killpg(pgid, SIGINT)`, then close stdin. Ruling for docs/DECISIONS.md: with `--input-format stream-json` SIGINT ends the model turn, and the closed stdin makes the process end after its `result` instead of waiting for input. If a process of the group is still alive `runner.stop_grace` after SIGINT, send SIGTERM to the group; if one is still alive `runner.kill_grace` later, SIGKILL. Then wait until no process of the group is left (`os.killpg(pgid, 0)` raises `ProcessLookupError`).
   b. Only then: `finishRun` with `state` `cancelled` and `reason` the reason of the request exactly as received (also a value the SDK keeps raw, G5), costs from the last `result` if one came; no answer message; locks released; the run leaves `active_runs`. Ruling for docs/DECISIONS.md: no answer after a stop, because a stop means "nothing more" (R-AG-10) and the box keeps the last text.
   c. Run in the inbox, not started: drop it, never start it, `finishRun` `cancelled` with the reason of the request, both done by the SDK's run loop (Scope, change b) (M2-09 accepts `cancelled` from `queued`; a run the server already cancelled answers `200`). A request for a run the runner does not know: acknowledge and drop.
   d. A stop wins: after a stop request no restart, compaction or follow-up write starts; a second request for the same run changes nothing. A stop during the follow-up grace, a compaction or a restart applies a and b to the process that runs.
   e. Run ended by the server while its turn runs: `patchRun` answered with the `409 conflict` that M2-10 gives for an ended run, or any call of the run answered `401 unauthenticated` (agent disabled, 09 2.1): stop the turn with a, and do not finish. Ruling for docs/DECISIONS.md.
   f. A finish answered `200` without change or `409` after a stop is logged as a code; the SDK's retry rules apply, nothing more.
   g. Every SIGTERM and SIGKILL is logged with the code `stop_escalated` and the signal name.
   h. Documentation in 09 21 and the README: `runner.stop_grace` plus `runner.kill_grace` stays below `agent.cancel_grace` of the server, else the server ends the run with `cancel_timeout` first; the runner cannot read the server value, like `adapter.invocation_token_leeway` and `auth.clock_leeway` (09 4.5).

7. **Classification of a process end** (`failures.py`; 18.9 last paragraph).
   a. `ERROR_TEXTS` is a tuple of `ErrorText(kind, fragment, channel, source)`: `kind` from `ErrorKind`; `fragment` the stable part of a text of the pinned CLI (no ids, no numbers that vary); `channel` where the pinned CLI writes it (`result`, `assistant` or `stderr`); `source` the evidence (file of the installed pinned CLI, or documentation URL with retrieval date). Take the fragments from the files of the pinned CLI version (Design note 14) and the documentation cited in 09 18; record each source. At least one entry per kind.
   b. `classify_turn_end(evidence)`. Inputs: stop requested, `system/init` seen, the last `result`, the text of the last `assistant` message, the stderr file of the process, the exit status. Rules in this order: a stop was requested: `stopped`; the last `result` has `subtype` `success` and no error flag (`is_error`): `completed`; the first entry of `ERROR_TEXTS` in table order whose fragment occurs in its channel gives its kind, but `session_missing` and `session_exists` only while no `system/init` came (afterwards `runtime_error`); otherwise `runtime_error` with the error texts of the `result` (the members the SDK reference names for them, none without `result`) and the exit status. Check `subtype`, `is_error` and the member of the error texts against the Agent SDK reference of the pinned version (09 18.4 cites it); follow the reference and list a difference.
   c. stderr is read only to match fragments; its text never goes into a step, a log line or a finish body, because it can echo content.
   Ruling for docs/DECISIONS.md: the order and the `system/init` condition.

12. **Crash of the runner** (18.2 "Detachment", 18.9 row 6, 09 4.9, AG-10).
    a. Detachment: stdout and stderr of the turn are files in `runner.state_dir` (the "Recording" of 18.2) that the runner reads, never pipes owned by the runner, so the CLI never writes into a closed pipe; stdin is a pipe from the runner, so the CLI sees the end of its input when the runner dies and finishes its current work. Change M2-34 if it reads pipes (the crash scenario fails otherwise).
    b. Turn record (M2-34's, extended), written atomically (temporary file and rename, mode `0600`): run id, thread id, session reference and mode, `pid`, `pgid`, the process identity of note c taken at the spawn, the offset of the stream file processed, the map of step ids, the follow-up map (`message_id`, `uuid`, written, echoed), the recovery flags, a stop request. Persist before the action that depends on it: a reference before its process starts, an offset after the patches of its lines.
    c. Identity before every signal: a stored `pid` or `pgid` is signalled only when `os.getpgid(pid)` equals the stored `pgid` and the output of `ps -ww -o lstart= -o command= -p <pid>` equals the stored start time and contains the session reference; otherwise the process counts as gone. The runner never signals a process it did not start. Ruling for docs/DECISIONS.md.
    d. At start, before the first event from the inbox and before the first heartbeat, for each record: check the process by note c. A live process keeps its session and thread lock through its inherited descriptors (M2-34 Design note 11), so the runner takes no lock for it. For a process that is gone, the runner takes both locks with one non-blocking attempt; a busy lock is logged with the code `adoption_lock_busy` and the record stays for the next start. Then it reads the run with `getRun`, then by `adoption_decision`: process alive and run `running`: adopt, read the stream file from the stored offset (a line read twice reuses its step id; answers go through the outbox with their stored `client_msg_id`, 09 15), list the run in `active_runs` (adopted runs enter `active_runs` through the runner's heartbeat members, M2-34 Design note 15), end it by note 5 and finish once; alive and run ended: stop it by note 6 a without a finish; gone and the stream file has a `result` after the offset: finish by that `result`, `completed` when it has no error and otherwise as in note 10 (classification of note 7, no recovery); gone without such a `result`: no finish and not in `active_runs`, so the server ends the run `interrupted` (09 5.5, AG-10). Remove the record when done. Ruling for docs/DECISIONS.md: the last case is left to the server, because the outcome of the turn is unknown.
    e. Never `run.start` and never a new process for an adopted run (R-AG-17). A run `running` without a turn process (crash between `run.start` and the spawn) is left out of `active_runs` (09 4.9).
    f. Recovery invariants (added 2026-10-25 after three red team rounds found crash regressions; ruling D-M2-35-28). They hold for an own turn and an adopted turn alike, each at one place, the turn ledger (`ledger.TurnLedger`), whose state is part of the turn record. A runner may die after any write (record, usage file, server call), and a second runner may die the same way; the rules make every such crash safe.
       1. Offset. The stored offset moves only through the ledger's checkpoint, after the patches of the lines before it went out (a failed flush keeps the old offset), and never past the first line of the run's end evidence (the last `result` read, and an API error message before it) while the run is not finished. So the next runner always reads that `result` again, classifies the end by it and books its costs. A line read again is harmless: its step reuses its id (note b), its echo is known, its answer is known (rule 2).
       2. Booked once. Each `result` line posts at most one answer: its `client_msg_id` is stored in the record, under the line's offset, before the reply goes to the outbox; a line read again sends the same `client_msg_id` (the server answers a repeat with the original, 04 13.2) or nothing once the reply was stored as sent. The costs of a run are booked only by its finish, from its last `result` (the record keeps that result's usage, numbers only, across the processes of a recovery), through the session's usage file, which keeps the reports of a run once computed; the decided end (state and reason) goes into the record before the costs go into the usage file, and a runner that finds a decided end repeats the finish with the same costs; the run is finished once.
       3. Inputs by their own id. Every input line of a turn process (the prompt line and each follow-up) carries its own `uuid`. It counts as answered when a success `result` names it (`user_message_uuid`, `user_message_uuids`), or when its echo (`isReplay` with that `uuid`) came before a success `result`: the CLI echoes a line when a turn takes it, also when it folds the line into a running turn whose `result` names nothing (a background task's notification; 2.1.259 emits a folded `queued_command` as a `user` echo with the line's `uuid`). A line still queued has no echo, so a `result` of another turn never answers it. There is no positional rule. A process of a recovery gets exactly the inputs not answered. A follow-up enters the record before its line is written, so a runner that adopts the turn maps its echo and patches it `absorbed` (a follow-up left `delivered` would be deferred into a run of its own and answered twice).
       4. Kind. The kind of a process (`turn` or `compaction`) is fixed when the process starts and written with every record; an adopting runner takes it from the record and never changes it, so an adopted compaction is never posted and never completes the run.
       The crash-point test (`tests/unit/test_crash_points.py`) runs the scenarios turn, follow-ups queued and folded, compaction and import baseline, enumerates every first crash point and every second crash point of the adopting runner with a fake clock, and asserts one end per run, costs booked once, each follow-up answered once and no run left running.
