# M2-33: Reference adapter for Hermes Agent (L7, L8)

Status: ready | Depends on: M2-12, M2-29, M2-32 | Milestone: M2

## Goal

After this ticket an operator connects one Hermes Agent profile to the server as one agent principal with the reference adapter in `plugins/hermes-adapter`: a Hermes platform plugin (`plugin.yaml` with `kind: platform`, registered with `ctx.register_platform()` in `register(ctx)`) on the Python SDK of M2-29 that uses only the public plugin surfaces of the Hermes version pinned and recorded by M2-32 (09 17). The adapter accepts an invocation only after the SDK has checked the invocation token (09 4.5 points 1 to 10) with the adapter's actual billing mode, actual tool class and allow list; it stores the event with its token in its inbox before it acknowledges it, reads the run context, determines the actual billing mode again from the key type of the credential Hermes resolves (never from its value) and starts the Hermes turn only after `200` on `startRun`, so no Hermes turn ever runs without a matching token, and an undeterminable mode fails the run with `billing_mode_mismatch` (I3, I5, R-AG-07, AZ-P6, RK-13). During the turn `format_tool_event` creates run steps instead of Hermes's progress bubble and returns `None`, `set_status_text` and `send_draft` fill the live box, the answer is one message, and the run ends with `finishRun` and the run's costs (D-L7, R-AG-18). The server-built run context reaches Hermes as a fixed system part in which content marked `unverified` and every file content appear only inside marked data blocks (ADR 0054, AG-20); follow-ups follow `busy_input_mode` (`steer` or `queue`, AG-13); cards from `send_clarify`, the approval prompt, the slash confirmation and the pickers become components whose single interaction resolves the Hermes callback exactly once (AG-15); stop interrupts the turn; each thread has one Hermes session that the adapter reports; the heartbeat carries actual mode, evidence and provable modes (D-L8); an installer sets up the profile, sets `busy_input_mode`, switches the billing mode and writes Hermes's own allow list for `personal` (10 10.1, 17.7). The Fake-Hermes scenarios AG-08, AG-11, AG-13, AG-15 and AG-20 run green in `make check` against the pinned Hermes version in a subprocess with a fake model and the SDK's FakeServer, the pinned version is unchanged before and after (M2 exit criterion 5), and a leak test finds no key value in any request, log, output or state file of the adapter (BR-13).

Product requirements implemented here:

11. The adapter is a Hermes platform plugin that uses only public plugin surfaces and never changes Hermes; logic lives in modules without a Hermes import; configuration comes only from the platform configuration Hermes hands to the plugin, never from `os.getenv` or `os.environ` (09 17.1, 17.2; ADR 0022; B6).
12. No Hermes turn without a matching token: the SDK checks points 1 to 10 of 09 4.5, a failed point on an event that would start or resume a run ends the run with `finishRun` `failed` and the reason of 09 4.5 (M2-29 note 9), an unknown `kid` is neither accepted nor acknowledged, and the turn starts only after `200` on `startRun` or `resumeRun` (09 4.5, 4.9; R-AG-07; AZ-P6; AG-08).
13. The actual billing mode is determined before every `startRun` and `resumeRun` from the key type of the credential Hermes resolves for the turn, never from its value; an undeterminable mode counts as unequal to every target and fails the run with `billing_mode_mismatch`; the value is never logged, stored, sent or printed (09 17.8; 10 7, 10.1; I3; I5; AG-11; BR-05; T-AI-08; RK-13).
14. The actual tool class is reported in the heartbeat and in `tool_class_used`, and a run whose token carries a lower `tool_class` fails with `tool_class_mismatch` (09 2.4, 4.5 point 10; 07 2.11; D-W-16).
15. An event with a token is acknowledged after it is stored with its token in the adapter's inbox; a redelivery replaces the stored token of a run not yet started and is not processed twice; the start uses the newest token, renews an expired one with `renewInvocationToken` and resumes from the inbox after a restart (09 4.3, 4.5.1, 4.9, 15; R-AG-24; D-W-15).
16. Live box and answer: `format_tool_event` creates and closes run steps of kind `tool_call` and returns `None`; `set_status_text` sets `/status_line`; `send_draft` sets `/last_text_excerpt`; the answer is one message created with a `client_msg_id` stored before sending; `edit_message` is buffered until `finalize` or the end of the run; typing is ignored; the run ends with `finishRun` and its `costs` (09 4.7, 4.10, 5.3, 17.3; D-L7; R-AG-18).
17. The run context reaches Hermes as a fixed system part with author and trust per element, separate from the text of the triggering person; content with `trust = unverified` and every file content appear only as marked data behind a fixed note; the transcript of a voice message carries the trust of its message (09 4.6, 17.6; ADR 0054; SEC-AI-1; AG-20; T-AI-01; T-AI-03).
18. Follow-ups follow the configured `busy_input_mode`: `steer` passes the text into the running turn and reports `delivered`, then `absorbed`; `queue` passes nothing; `interrupt` makes the adapter `degraded` with `busy_mode_invalid` and without follow-up capability (09 7, 17.5; AG-13).
19. Cards and interactions: clarify, approval, slash confirmation and pickers are single-use components with the Hermes callback ids as `custom_id`; the run waits with `awaitRunInput`; an interaction resumes the run with its own token and resolves the Hermes callback exactly once; approval buttons follow 09 11.5 (09 11, 17.3; SEC-AI-4; AG-15).
20. Stop: `run.cancel_requested` interrupts the turn and ends the run `cancelled` with the reason of the event; no later patch or message of that run is sent (09 8; 04 15.5; AG-13 stop part).
21. Sessions: every source is built with `build_source` and the thread id, so Hermes keeps exactly one session per thread; the adapter follows `session_mode` (`new`, `resume`, `bind`), reports the Hermes session id with `reportAgentSession`, and falls back to a new session with `bind_failed: session_missing` when a bound session is missing (09 9.1, 9.5, 17.4; R-AG-04).
22. Allow list: the adapter enforces its own access policy with the principals of `getAgentTriggerers` and reloads it when a token carries a newer `permission_version`; at `personal` the installer writes Hermes's own allow list with exactly the credential holder (09 4.5 point 9, 17.7; R-AG-19).
23. Heartbeat after `agent_heartbeat.v1`: state, degraded reasons, runtime version, actual mode or its absence, provable modes, evidence without value, actual tool class, capabilities, active runs (09 4.8; D-L8; 10 8).
24. Every request inside a run carries the run's current invocation token in the header `Invocation-Token`; requests outside a run carry none (07 SR9; M2-14).
25. No key value, token or message content appears in a log line, error text, heartbeat, request field or state file of the adapter (BR-13; I5; SEC-LOG-2; SEC-LOG-4 applied to the adapter).
26. Tests use the pinned Hermes version in a subprocess with a throwaway `HERMES_HOME`, a fake model on `127.0.0.1` and the FakeServer; the pinned version is unchanged before and after; real model calls never happen (09 16.1; PLAN 1 point 2; M2 exit criterion 5).
27. No JSON `null` in any request body (ADR 0053).

## Design notes

1. **Layout and layering** (09 17.2, rule 2). Ruling for docs/DECISIONS.md: distribution `bothy-hermes-adapter`, import package `bothy_hermes_adapter`, the same naming as `bothy-sdk` (M2-23 note 1), listed in 02 6. Exactly two modules import Hermes: `platform.py` (runtime) and `hermes_config.py` (installer and credential resolution over Hermes's own reader, which 10 10.1 and 17.5 require); 17.2 is aligned to say so. Every other module depends on the protocol `Runtime` in `runtime.py`, which `platform.py` implements and unit tests fake: `start_turn(run, source, user_text, system_part)`, `steer(run_id, text)`, `interrupt(run_id)`, `resolve_callback(custom_id, values, operator)`, `switch_session(thread_id, mode, external_session_ref)`, `current_session(thread_id)`, `session_title(thread_id)`, `resolved_credential()` and `loaded_toolsets()`. The installer runs inside Hermes's interpreter (`python -m bothy_hermes_adapter ...` of the profile's venv), so no package module starts a subprocess. Two static tests hold this: `test_only_two_modules_import_hermes` (AST scan against the top-level module names of the pinned distribution) and `test_no_environment_access` (AST scan: no `os.getenv`, `os.environ`, `os.putenv` in the package).
2. **Hermes surfaces** (09 17.1, 17.10; RK-12). The pinned version and its record from M2-32 decide every Hermes name used here (method signatures, the event of `format_tool_event`, the MessageEvent fields, the session switch path, the credential resolution, the steer and interrupt paths, the plugin discovery). The adapter uses only the surfaces 09 17 names; a surface that M2-32 found missing and adjusted in 09 17 is built as adjusted. Stubs in `typings/` describe exactly the used symbols; `test_hermes_stubs_match_pinned_version` imports each from the pinned version and compares `inspect.signature`, so a pin update that changes a used surface fails at once. Hermes is not a dependency of this component (09 17.1: not part of the product): it runs only in the Fake-Hermes harness and in the operator's installation.
3. **Configuration** (09 17.2, 21; rule 9). Keys arrive in `PlatformConfig.extra` of the platform section of the profile configuration, flat with their full names, written by the installer; `config.py` validates them into a frozen dataclass and fails the connect with a message naming the key. Existing keys: `hermes_adapter.platform_key`, `hermes_adapter.consumer`, `adapter.invocation_token_leeway`, `adapter.jwks_refresh_min_interval`, `sdk.http_timeout`, `sdk.retry_max_attempts`, `sdk.retry_backoff_base`, `sdk.retry_backoff_cap`. New keys, rows in 09 21 with Place "Hermes adapter" (Ruling for docs/DECISIONS.md, spec gap: 09 names no way to reach the server):
    - `hermes_adapter.server_url` (no default, required): base address of the instance; discovery and JWKS come from `getDiscovery`.
    - `hermes_adapter.instance_id` (no default, required): instance ID of the server and the expected `iss` of every token (09 4.5 point 4); `connect()` passes it as `AdapterConfig.instance_id`, and the SDK compares it with `getDiscovery` and stops on a difference (M2-29 note 8). The adapter's own ID, the expected `aud`, comes from `getMe` (a principal of kind agent, otherwise stop) and becomes `AdapterConfig.agent_id`, as in M2-34.
    - `hermes_adapter.token_file` (no default, required): file with the agent's API token, readable only by the profile's user; read at connect, never logged; a file is the adapter's secret provider because `os.getenv` is forbidden (17.2) and the token must not stand in the configuration file.
    - `hermes_adapter.dpop_key_file` (no default; without it no DPoP): private key the SDK `auth` module signs DPoP proofs with; the installer creates it with user-only permissions when asked.
    - `hermes_adapter.max_message_bytes` (default equal to the default of `message.max_content_bytes`): `MAX_MESSAGE_LENGTH` of 17.3; the adapter cannot read the server's value, so the README says that both change together, and `test_max_message_bytes_default_matches_server` holds the two defaults equal in `docs/operations/configuration.md`.
    - `hermes_adapter.attachment_text_max_bytes` (default equal to the default of `agent.context_message_max_bytes`): largest attachment text the adapter inlines as a data block (Design note 9).
    - State lives in the directory named like the platform key below the profile's home directory, which the adapter learns from the function the pinned version offers plugins (M2-32 record), never from the environment; mode `0700`; it is the `state_dir` of the SDK (its inbox and outbox files, M2-29) and holds the adapter's own SQLite file of Design note 18.
4. **Connect and disconnect** (09 17.3). `connect()`: load the configuration, the token and the DPoP key; `getMe`; then start the SDK loop of Design note 5, which compares `getDiscovery` with `hermes_adapter.instance_id`, loads `getJwks` and the allow list, opens the gateway through the SDK `gateway` module with `identify` and `consumer` = `hermes_adapter.consumer` (one process per consumer; on `4015` the SDK stops and the adapter reports the platform as disconnected without reconnecting), starts the heartbeat (Design note 15) and resumes not-started inbox entries (M2-29 note 9). No command registration (Out of scope). `disconnect()`: stop the SDK loop (close with `1000`), stop the heartbeat; open runs are no longer listed in `active_runs` and the server ends them as `interrupted` (09 5.5). `get_chat_info(chat_id)` reads the thread with `getThread`.
5. **SDK run loop and handler** (`handler.py`; 09 4.3, 4.5, 4.9; M2-29 notes 7 to 9). `platform.py` runs the SDK loop of M2-29: `connect()` starts `Adapter(AdapterConfig(..., allowlist=True, state_dir=<state dir>), HermesHandler(runtime))` as a task and `disconnect()` stops it. `HermesHandler(AgentHandler)` (module `handler.py`, no Hermes import) implements `actual_billing` (Design note 6), `actual_tool_class` (Design note 7), `prepare` (Design note 8: context, channel config and actual mode; returns `StartOptions`), `execute` (the session handling of Design note 14, the turn and Design note 10), `on_followup` (Design note 11), `on_interaction` (Design note 12) and `on_event` (`agent.config_changed`, Design note 9). Inbox, `jti` store, ack rule, allow list (M2-29 note 8), token renewal, start answers, cancel and restart are the SDK's (M2-29 notes 7 to 9) and are not rebuilt. `prepare` raises, so the run ends `failed` `adapter_error` without a start, for an `agent.invocation` with `trigger_kind` `command` (the adapter registers no commands) or `interaction` that names no open card of this adapter. Behaviour the SDK lacks is added to `bothy_sdk` with an SDK test and listed in the report:

    - allow list unloadable with `404`: `finishRun` `failed` `adapter_error` and the event is settled (the operation is absent on this server; a visible reason instead of a run that waits until `run.queued_max_age`);
    - allow list unloadable with a network error, `429` or `5xx`: the event stays unsettled, no inbox, no `ack` (redelivery retries).

    Ruling for docs/DECISIONS.md: the two allow-list failure kinds as SDK additions and the refusals in `prepare`.

6. **Actual billing mode** (`actual_mode.py` and `hermes_config.py`; 09 17.8; 10 7). `Runtime.resolved_credential()` (implemented with the resolution function of `hermes_config.py`) asks Hermes which credential it will use for the next turn (surface of the M2-32 record) and returns only `provider` and `key_type`; the bridge drops every other attribute of Hermes's answer inside the call and never logs, formats, stores or returns the value. The table, Ruling for docs/DECISIONS.md: Anthropic with a console API key gives `organization`, `key_type: api_key`; Anthropic with OAuth gives `personal`, `key_type: oauth` (OAuth wins over an API key when both are set, 17.8); another provider with an API key gives `organization`, `key_type: api_key`; every other result (no credential, cloud credentials, an OAuth login of another provider, an exception, an unknown answer) gives no mode with `key_type: unknown`, because 17.8 lists the determinable rows exhaustively and 10 7 counts an undeterminable mode as unequal to every target. `billing_evidence` is `{provider, key_type, method: "resolved_credentials"}` (`provider` omitted when unknown). The mode is computed at intake (point 8), again immediately before every `startRun` and `resumeRun` (`billing_mode_used` and `billing_evidence` in `RunStart`), and at every heartbeat. A change during a running turn (heartbeat computation differs from the run's `billing_mode_used`) interrupts the turn and ends the run `failed` `billing_mode_mismatch` (BR-05 "change during the run"). Ruling for docs/DECISIONS.md.
7. **Tool class** (`tool_class.py`; 09 2.4, 4.5 point 10; 07 2.11). Spec gap: 09 17 does not say how the Hermes adapter knows its actual class. Ruling for docs/DECISIONS.md and new 09 17.11: the class follows the toolsets Hermes enables for this platform (`Runtime.loaded_toolsets()`, read at connect and at every heartbeat): none gives `chat`; only toolsets listed in the classification table of `tool_class.py` as `scoped` (named tools with their own minimal credentials whose effect outside the thread needs an approval card) give `scoped`; any other toolset, including an unknown name, gives `host` (fail closed: a too high report only blocks starts and raises the effective class, 09 2.4). The table names each toolset of the pinned version with its class and reason, taken from the M2-32 record; `test_tool_class_table_covers_pinned_toolsets` fails when a toolset of the pinned version is missing from it. `tool_class_used` in `RunStart` and `reported_tool_class` in the heartbeat carry this class.
8. **Start of a run** (`handler.py`; 09 4.9, 17.6). `prepare`, called by the SDK after the inbox and the `ack`: `getRunContext`; `getServedChannelConfig` when `settings_version` of the payload is newer than the cached one (operator runs only); the actual mode (Design note 6); it returns `StartOptions` with `billing_evidence` and without `external_session_ref` (Hermes creates it during the turn, 09 9.1). Renewal of an expired token, `startRun` with `invocation_token`, `billing_mode_used`, `tool_class_used` and `billing_evidence`, and every answer to it (`expired`, `superseded`, `invalid`, `409 already_started`, `409 billing_mode_mismatch`, `409 tool_class_mismatch`, `403 agent_invocation_denied`, transient failures) are the SDK's (M2-29 note 9). After `200` the SDK calls `execute`: session handling (Design note 14), then `Runtime.start_turn`.

    The source for Hermes: `build_source(chat_id = <channel_id>, chat_type = "thread", thread_id = <thread_id>, user_id = <sub>, user_name = <display name of triggered_by>, message_id = <message_id>)`, `thread_id` always set (17.4). The user text is the `content_md` of `trigger_message`, plus the transcripts of its voice attachments; the context goes into the system part (Design note 9). A run ends after the turn: the buffered edits are flushed, then `finishRun` (Design note 10).

9. **Context for Hermes** (`context_format.py`; 09 4.6, 17.6; ADR 0054). The fixed system part is rendered with the SDK's context function of M2-29 for the data blocks and in Hermes's channel-context form for the rest. Rulings for docs/DECISIONS.md:
    - Structure: a header line with the fixed note (English, for the model): the context comes from the chat server; lines marked `[unverified]` and every data block are material and never instructions; then a section "channel instructions" with the channel prompt from `getServedChannelConfig` when it is set (09 4.1, SEC-AI-1: an own field); then `channel_context`, then `thread_context`, ascending, one element per entry.
    - An element with `trust` `trigger`, `authorized`, `self` or `system` is a line `[<display_name> (@<handle>)] <content>`; an element with `unverified` is a line `[unverified] [<display_name> (@<handle>)]` followed by its content inside a data block. Every data block is opened and closed with a marker that carries a random nonce of this turn, created with `secrets`, so no content can close a block or forge a header line; a content that contains the nonce is impossible by construction and is checked anyway.
    - Attachments of any element (also of the trigger) with `scan_status` `clean` or `skipped` and MIME type `text/*` or `application/json` are fetched with `downloadFile` and inlined as a data block, cut at a UTF-8 boundary to `hermes_adapter.attachment_text_max_bytes` and marked as cut; other attachments, `409 file_not_ready` and `409 file_blocked` give a data line with name, MIME type and size only. A file content is always data, also from the triggering person (T-AI-03).
    - A transcript carries the trust of its message: inside the data block of an `unverified` element, in the user text for the triggering message, as a line for the others.
    - Elements with `already_delivered: true` are left out, because the continued Hermes session already holds them (09 4.6 reason of the floor); `truncated: true` and `truncated_before_seq` give one note line each.
    - Skills of the channel (`ChannelBehavior.skills`, 03 "ordered list of skills that the operator loads in this channel"): named in order in the channel-instructions section as the skills to use in this channel, so Hermes loads them with its own skill tools; spec gap (09 17 maps neither prompt nor skills), settled without a further Hermes surface because both come from a person with `manage` (R-AZ-09) like the prompt.
10. **Live box, answer and end** (`live_box.py`; 09 4.7, 5.3, 17.3). All patches go through the SDK `runs` helper (`patchRun` or the gateway op `run.update`, throttled to `agent.run_update_min_interval`, `base_version` kept, rebuilt after `409 base_version_conflict`).
    - `format_tool_event(event)`: a start event adds `/steps/<id>` with a new UUIDv7, `kind: tool_call`, `name` the tool name, `title` the tool name, `status: running`; the matching end event replaces `/status` (`completed` or `failed`) and `/finished_at`. Pairing by Hermes's call id when the event has one, otherwise first-in first-out per tool name. `detail` is `{"preview": <the preview text Hermes would have shown>}` and nothing else (never tool results). The method returns `None` so Hermes sends no progress bubble. Ruling for docs/DECISIONS.md (03 `run_step_detail.v1` names no fields; spec gap).
    - `supports_status_text` is true; `set_status_text` replaces `/status_line`. `supports_draft_streaming` is true; `send_draft` replaces `/last_text_excerpt` with the draft text. `render_message_event` keeps Hermes's default and also sets `/last_text_excerpt` from text parts. `send_typing` and `stop_typing` do nothing. `on_processing_start` does nothing.
    - `send(chat_id, content, reply_to, metadata)`: `createMessage` in the thread of the run with `run_id`, `reply_to_message_id` when `reply_to` is a message id, and a `client_msg_id` written to the outbox before the first attempt (SDK `outbox` with its store in the state directory, M2-29 note 13). `splits_long_messages = False`; `MAX_MESSAGE_LENGTH` from `hermes_adapter.max_message_bytes`; a longer answer is cut at a UTF-8 boundary and the cut is logged with the run id only. A `send` for a thread without an active run of this adapter returns a failure result and sends nothing.
    - `edit_message(..., finalize)` on an own answer: buffer; `updateMessage` once at `finalize=True` or at the end of the run.
    - `on_processing_complete(event, outcome)`: `completed`, `failed` with `runtime_error` (Hermes reported an error) or `adapter_error` (the adapter failed), or `cancelled` after Design note 13; `finishRun` after every `createMessage` and `updateMessage` of the run, with `metrics` (token counts) and `costs` per model from Hermes's usage report (`provider`, `model`, token counts, `amount_micros` when Hermes estimates one, `currency`). Ruling for docs/DECISIONS.md: `currency` is the code Hermes's usage report states; when it states none, `USD`, the currency of the prices the pinned version ships (verify in the M2-32 record). No live `/metrics` or `/cost` patches: 17.3 names no Hermes surface for per-call usage.
    - Title: after the first `completed` run of a session with `session_mode = new` of an operator run, `getThread` and `setThreadTitle` with `If-Match` and the Hermes session title (`Runtime.session_title`) when Hermes has one; `409 title_manual`, `412 version_conflict` and `403` end the attempt without retry; guest runs never set titles (09 12 points 3 to 5).
11. **Follow-ups** (09 7, 17.5). Capability `followups` is `steer` or `queue` from the configured `display.platforms.<platform_key>.busy_input_mode`, absent at `interrupt` (then `degraded` with `busy_mode_invalid`). An `agent.followup` reaches `on_followup` (Design note 5). For a `running` run at `steer`: read its content from `getRunContext` (`message_id` of the payload), `Runtime.steer`, patch `/followups/<message_id>/state` to `delivered`, and to `absorbed` when Hermes reports the text taken into the turn (surface of the M2-32 record; without one, at the end of the turn that received it). For a run in `waiting_input` it is the answer to the open card: the SDK resumes the run with the follow-up's token (`resumeRun`, M2-29 note 9), then `on_followup` disables the active components of the open card with `updateComponent` (`state: disabled`) and passes the text as the answer (09 11.6). At `queue` the server sends `agent.followup` only for a run in `waiting_input` (04 15.4 point 5; M2-11 D-M2-11-2). In both modes that event is the answer to the open card as described above. A follow-up for a `running` run at `queue` is acknowledged and not passed to Hermes. Ruling for docs/DECISIONS.md: the absorbed signal, the queue case and the answer to a waiting card in both modes.
12. **Cards and interactions** (`cards.py`; 09 11, 17.3). Ruling for docs/DECISIONS.md: every card of the adapter is a `createMessage` with `kind = card`, `run_id` and `single_use` components, followed by `awaitRunInput` with the question's first line as `status_line`:
    - `send_clarify`: buttons or a select with `custom_id` `cl:<id>:<idx>`, `restricted_to: run_starter`.
    - `_send_exec_approval_prompt`: the four buttons of 09 11.5 with `custom_id` `appr:<id>:<choice>`, values `once`, `session`, `always`, `deny`, `required_capability: approve_actions` except `deny`, `restricted_to` `run_starter` (`owner` for `always`).
    - `send_slash_confirm`: buttons "Once", "Always", "Cancel" with `custom_id` `sc:<choice>:<id>`, the "Always" button restricted to `owner` like `always` (R-AG-12), the others to `run_starter`.
    - `send_model_picker` and `send_choice_picker`: one select.
    - An `interaction.created` for an open card: the SDK resumes the run with the interaction's token (`resumeRun`, M2-29 note 9), then `on_interaction` calls `Runtime.resolve_callback(custom_id, values, principal_id)` exactly once per callback id (the store records resolved ids, so a redelivery resolves nothing), then `respondToInteraction` with `state: acknowledged` and `response.text` the chosen label. No `updateComponent` after an interaction: the server disables the other single-use components in the same transaction (09 11.3); 17.3 "update the card" is aligned to this. A `custom_id` longer than `component.custom_id_max_chars` is a server `400 validation_failed`, which ends the run `failed` `adapter_error`.
13. **Stop** (09 8). `run.cancel_requested` is the SDK's (M2-29 note 9): it cancels the run's `execute` and then sends `finishRun` `cancelled` with the event's `reason`. The handler's part: on that cancellation `execute` calls `Runtime.interrupt` and drops every later Hermes callback of that run (no patch, message or card); follow-ups not absorbed are never reported `absorbed`. If Hermes reports no interruption (17.10 point on `on_processing_complete`), the run still ends through the SDK. A cancel for a run that is still in the inbox (not started) only closes the entry (M2-29 note 9; the server cancels a queued run itself), and no turn starts; a `409 invalid_state_transition` answer (the server already ended it) ends the matter.
14. **Sessions** (09 9.1, 9.5, 17.4; M2-12). Before `start_turn`: operator runs follow `session_mode`. `new`: `Runtime.switch_session(thread, new)` when Hermes already holds a session for the thread, after the turn created it `reportAgentSession` with `external_session_ref` (Hermes session id), `started: true`, and `If-Match` only when the payload carried `agent_session`. `resume`: continue; if Hermes's session id differs from `agent_session.external_session_ref`, switch to the server's reference like `bind`; after a switch, and after any turn in which Hermes's session id for the thread changed (compression), report the id in use with `If-Match` (17.4; M2-12 note 11). `bind`: switch to `agent_session.external_session_ref`; after Hermes took the session over, `reportAgentSession` with `If-Match` = `agent_session.version` and `external_session_ref` = the Hermes session id actually in use (the living end of a compression chain), without `bind_failed` (09 9.1, 9.5 point 3). If Hermes does not know it, start a new session and report it with `If-Match` and `bind_failed: session_missing` (fail open). Guest runs (no `session_mode`): a fresh Hermes session for the run and no report, because a guest run has no session (R-AG-04) and its context already holds the own earlier messages (09 4.6). `412 version_conflict` and `409 conflict` on a report are logged with run id and reason only; the run continues.
15. **Heartbeat** (`heartbeat.py`; 09 4.8; D-L8; M2-20 note 3). Built with the SDK `heartbeat` module, sent at the interval the server announces. Ruling for docs/DECISIONS.md, inside the closed key set and forms of M2-20 note 3: `state` `online`, or `degraded` with `details.degraded_reasons` from `busy_mode_invalid` and `billing_evidence_unknown`; `runtime_version` the Hermes version; `reported_billing_mode` the actual mode and `billing_modes_supported` exactly that mode, both absent when unknown (Hermes proves one mode per profile process; D-L8 is for runtimes with both); `billing_evidence` of Design note 6; `reported_tool_class`; `details.capabilities` `components: true`, `title: true` and `followups` per Design note 11; `details.active_runs` (runs in `running` or `waiting_input`); `details.adapter` `{name: "hermes-adapter", version}`; `details.runtime` `{name: "hermes-agent"}`; `details.protocol_version`. Never `rate_limit` (M6-14), never `project_readiness` (runner only), never a value, path or content.
16. **SR9 header** (07 SR9; M2-14 note 1). Every request the adapter makes for a run (`getRunContext`, `downloadFile`, `patchRun`, `createMessage`, `updateMessage`, `respondToInteraction`, `updateComponent`, `reportAgentSession`, `getThread`, `setThreadTitle`, `getServedChannelConfig`) carries `Invocation-Token` with the run's current token; `startRun`, `resumeRun` and `renewInvocationToken` carry the token in the body; heartbeat, discovery, JWKS, allow list and `ack` carry none. Through the SDK's run helper; Scope says when the SDK gets it.
17. **Installer** (`installer.py`, `hermes_config.py`; 09 17.2, 17.5, 17.7; 10 10.1). Commands, each reading the configuration with Hermes's own reader before and after the change and printing a summary without values:
    - `install --profile-home <dir> --server-url <url> --instance-id <id> --token-file <file> [--dpop-key-file <file>] --busy-input-mode steer|queue`: places the plugin where the pinned version discovers it, writes the platform section with the keys of Design note 3 and `display.platforms.<platform_key>.busy_input_mode` explicitly; refuses `interrupt`; refuses to change an existing `hermes_adapter.platform_key` (D-AG-19).
    - `switch-mode organization|personal [--credential-holder <principal id>]`: `organization` requires the API-key variable of the profile environment to be set (checked by name, never read) and empties the OAuth variables; `personal` empties the API-key variable and writes Hermes's platform allow list (`allowed_users_env`) with exactly the credential holder; `organization` empties that list (17.7 layer 3). Variable names come from the M2-32 record. Afterwards it prints the actual mode Design note 6 now predicts and whether the gateway process serves several profiles; it never restarts a process and names the restart the operator must do (17.8). Ruling for docs/DECISIONS.md: no restart by the installer; values never read.
    - `check`: the same reads and prediction without changes.
18. **Persistence and restart** (`store.py`; 09 4.3, 4.9, 15). Inbox, `jti` store and outbox are the SDK's files in the state directory (M2-29 notes 8, 9 and 13), and the restart rules are the SDK's: not-started runs are resumed (renewing expired tokens), runs that were `running` are not (the server ends them as `interrupted`, R-AG-17). `store.py` keeps only the resolved callback ids and the open card per run, in one SQLite file through the standard library; a write is durable before the Hermes callback or the send it guards.
19. **Logs** (SEC-LOG-2, SEC-LOG-4 applied; BR-13). Logger `bothy_hermes_adapter` through Python `logging`; records carry run, thread and event ids, reasons and codes only: never a token, a key value, a DPoP proof, a message or context content, a display name, a file name or a transcript. Exceptions from the SDK are logged by type and problem code, never by their text.

## Acceptance criteria

- [ ] The plugin is found by the real discovery of the pinned Hermes version, connects as the agent with `hermes_adapter.consumer`, uses only public surfaces, and only `platform.py` and `hermes_config.py` import Hermes; no module reads the environment.
- [ ] AG-08 and AZ-P6: no token, a bad token, a repeated `jti`, a wrong mode or a too low tool class never start a Hermes turn; the run fails with the reason of 09 4.5.
- [ ] AG-11 and BR-05 (adapter side): an actual mode unequal to the target, an `unknown` mode and a change during the run end the run with `billing_mode_mismatch`; the predicted mode equals the credential Hermes really uses.
- [ ] Events are acknowledged after the inbox, redeliveries replace the token, expired tokens are renewed, and a restart resumes not-started runs exactly once.
- [ ] D-L7: tool events become run steps and `format_tool_event` returns `None`; status and drafts fill the live box; the answer is one message; the run ends with `finishRun` and `costs`.
- [ ] AG-20: unverified content and every file content reach Hermes only inside nonce-marked data blocks after the fixed note; transcripts carry the trust of their message.
- [ ] AG-13 and AG-15: follow-ups follow `busy_input_mode`, a stop interrupts and ends `cancelled`, and concurrent clicks resolve the Hermes callback exactly once.
- [ ] Sessions follow `session_mode` and are reported; the heartbeat carries the fields of Design note 15; every run request carries `Invocation-Token`.
- [ ] BR-13: no key value appears in any request, log, output or state file of the adapter.
- [ ] The installer sets `busy_input_mode`, switches the mode and writes Hermes's allow list for `personal`, without reading a value and without restarting a process.
- [ ] The pinned Hermes version is unchanged before and after the tests (exit criterion 5).
- [ ] 09 17 and 21, 02 6, `configuration.md`, the threat model, RISKS.md, the READMEs and `docs/DECISIONS.md` describe what was built.
- [ ] `make check` is green.
