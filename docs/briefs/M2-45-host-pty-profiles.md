# M2-45: bothy-host: sessions, PTY and profiles

Status: ready | Depends on: M2-44 | Milestone: M2

## Goal

After this ticket the host service `bothy-host` runs terminal sessions end to end on macOS, Linux and Windows. For every `session.open` of the server it opens one data connection `/api/v1/hosts/sessions/{session_id}/stream`, answers Noise message 1 as responder (M2-38), checks the session token in the fixed order of 24 "Terminal session token" and refuses at the first failing step without a PTY, with exactly that step's `close_detail`; only then it sends message 2, and only after the first transport message `start` (Ruling T9), a passed HD6 and HD11 run and, with `host_service.require_local_confirm`, the consent of the person at the machine it starts a PTY, and only in the PTY helper of the session user named by `osu`. It serves the profiles `shell`, `claude` and `command` of 24 "Profiles" with allow-list environments plus `TERM`: the `claude` profile starts with `organization` exactly the resolved path of `host_service.claude_bin` with the fixed search list of HD6 first in `PATH`, its own `CLAUDE_CONFIG_DIR` in the session user's home and the organization key, with `personal` the holder's own `claude` through the login shell with a `CLAUDE_CONFIG_DIR` that resolves inside the home, and with `none` it does not exist. HD6 and HD11 run before every PTY and every `host_service.credential_check_interval` with the consequences of 24 "Enforcement on the host" and of HD11 in operation; every session runs in its own process group, cgroup or Job Object, and every end kills the whole process tree; every helper ends its PTYs when its channel to the host service breaks; the scrollback lives only in memory and is replayed between `replay_begin` and `replay_end` on attach. Why: the server only decides and relays (24 "Protection goal"); on the machine the token is the only proof of a decision, so a replayed or swapped first message, a foreign session user, a foreign working directory or a foreign login must never reach a PTY (T-TM-02, T-TM-08, T-TM-13, Rulings T9, T12, T13, I6), and a session that ends must leave no process behind (T-TM-11, R-TM-15). This is the host side of TM-T03, TM-T04, TM-T05, TM-T21, TM-T25, TM-T28 (c) and (d), TM-T29 (a), (c), (f), (g), (k) and (l); before building, the owner's own login path of OQ-03 is checked against the current provider documentation. M2-46 adds revocation, the server-side limits, audit and metrics; M2-48 runs the whole terminal suite against the real server and a host service in a Linux container.

Product requirements implemented here:

11. The host service checks the session token in the fixed order of 24 5.3 and stops at the first failing step without a PTY; the order of Design note 5 is the order of the spec with the two steps it adds; a failure carries exactly one `close_detail` from 24 10.3 (`token_invalid`, `token_expired`, `token_replayed`, `profile_unknown`, `session_user_unknown`, `session_user_mismatch`, `server_host_owner_only`); a failed Noise message 1 is `handshake_failed` (24 5.3, R-TM-16, SEC-TERM-2).
12. A token is valid once: every `jti` is remembered until its `exp` plus `auth.clock_leeway`; a replayed message 1 gives `token_replayed` and never a second PTY (TM-T03, Ruling T9, T-TM-02).
13. The PTY starts only after message 2 and the first transport message `start`; message 1 and 2 without `start` start nothing (TM-T05, Ruling T9, 24 5.2).
14. A refused handshake reaches the device with exactly one close code: `4101` for `token_expired` and `token_replayed`, `4104` for every other failure of the token or the handshake (24 5.3 table, R-TM-16, D-T18; TM-T04, TM-T05); the host service signals it by closing its data connection with that code and the `close_detail` as close reason (M2-44 Design note 9).
15. The PTY starts only in the helper of the session user named by `osu`, only when `osu` is in `host_service.session_users`, and only for the person (`sub`) the host service first gave that session user; the binding `osu` to `sub` lives in the state directory (`bindings.json`; 24 2.2 point 3, Ruling T12, TM-T28 (c)).
16. The `claude` profile starts only in a working directory from the list of `osu` after HD7 that the host service reported, chosen by `wdi`; an index outside it gives `profile_unknown` (24 5.3 and 11.1, Ruling T13, D-W-69, TM-T29 (c) and (g)).
17. Profiles come only from `host_service.profiles`; the client sends a name and an index, never a command line or a path; the environment of every profile is an allow list plus `TERM` (24 11.1, R-TM-08, SEC-TERM-9).
18. `claude` with `organization`: exactly the resolved path of `host_service.claude_bin` that HD10 checked, the fixed search list of HD6 first in `PATH`, `ANTHROPIC_API_KEY` from the state directory, `CLAUDE_CONFIG_DIR` set to `.config/bothy-host/claude` in the home of the session user, none of the OAuth or provider variables of 09 18.3; with an empty `host_service.claude_bin`, or one that counts as empty (not resolvable, interpreter not in the search list), the profile is not offered (HD7 warning `claude_profile_unavailable`) (24 7.4 and 11.1, D-W-81, D-W-85, TM-T29 (l)).
19. `claude` with `personal`: the holder's own `claude` through the login shell of the session user, with the `CLAUDE_CONFIG_DIR` that the helper read from a separate login shell and that resolves inside the home (unset: the default folder of the coding agent in the home); outside the home or not resolvable: the profile does not start (`open_failed` with `shared_location`) and `shell` stays (24 7.4, D-W-82, D-W-84, TM-T29 (k)). The service user never opens, reads, copies or passes a login of `personal` (TM-T25, D-W-17, R-TM-19, I5). With `none` there is no `claude` profile.
20. HD6 and HD11 run before every PTY and every `host_service.credential_check_interval`, with the consequences of 24 7.4 and HD11: a subscription login under `none` or `organization` refuses new sessions with `subscription_login_detected` and ends all running sessions with `host_policy_violation`; a violation at a location of a session user blocks only that session user (`shared_location`); a violation at a location for all ends all sessions with `host_policy_violation` and `shared_location` and admits none until HD11 passes (D-W-89, TM-T21, TM-T29 (a) and (f)); a finding of the entry scan is lifted only by a full run.
21. On macOS and Linux every session runs in its own process group and session (`setsid`), on Linux additionally in its own cgroup; on Windows every session runs in a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; every end, for whatever reason, ends the whole tree (24 6.5, R-TM-15, SEC-TERM-11).
22. Every PTY helper ends its PTYs with their trees as soon as its channel to the host service breaks (D-W-90, R-TM-27).
23. The scrollback buffer of `host_service.scrollback_bytes` per session lives only in the memory of the host service, never on disk or in the server; an attach replays it between `replay_begin` and `replay_end` (24 6.2).
24. With `host_service.require_local_confirm = true` no PTY starts and no attach is replayed without the consent of the person at the machine within `host_service.local_confirm_timeout`; otherwise `local_confirm_denied` (24 6.4, Ruling T3).
25. No terminal content, session token, key, environment value, path or command line in any log line, `report`, `session.ended`, close reason, error text or test failure message of the host service (24 10.1, R-TM-10, SEC-TERM-1, SEC-LOG-2).
26. PTY tests run on macOS, Linux and Windows (PLAN 8 exit criterion 8, RK-23).

3. **Data connection per grant** (M2-44 Design note 7). The host service opens exactly one data connection for each `session.open` and never one on its own; each carries exactly one Noise handshake. A `session.open` for a session ID without a live PTY is an opening (also a repeated opening of an `opening` session, whose token says `att = open`); one for a session ID with a live PTY is an attach (`att = attach`). A newer `session.open` for the same session replaces any older data connection of it, which the host service closes with `1000` if the server has not already. `session.close {session_id, close_reason}` and a close of the data connection by the server with `4100` (`hostData` `x-close-codes`: the session ended) end the PTY with its tree at once (Design note 12), or abandon an opening that has no PTY yet; the host service stops the timers of that session, drops its scrollback, removes it from `live_sessions` and sends no `session.ended`, because the server closed the session already (M2-43 Design note 10 changes nothing for a closed session); a `session.close` for a session the host service does not know changes nothing. Every other close of the data connection by the server (`1000`, `4002`, `4013`, `4014`, a code of the login) or its loss, while the PTY lives, makes the session detached on the host (Design note 14); the host waits for the next `session.open` and never redials a data connection on its own. Ruling for docs/DECISIONS.md: these reactions, because M2-44 Design note 11 closes the host side with `4100` and sends `session.close` for every end, and one data connection per grant leaves no other reconnect. 24 6.2 changes as M2-44 states.

4. **Session token verification** (24 5.3, ADR 0067 rules 1 to 3, D-T33). The host module cannot import the server's `internal/kernel/jose`, so `internal/session/token.go` implements the needed subset with the standard library: compact JWS only, exactly two dots, base64url without padding; header with `alg` exactly `EdDSA`, a `kid`, `typ`; any `crit`, `jku`, `x5u`, `x5c`, `zip` or `jwk` member rejected; the key is the Ed25519 key (`kty` `OKP`, `crv` `Ed25519`) with that `kid` in the `jwks` of the `hello` of this data connection; `crypto/ed25519` verifies. Claims: `iss`, `aud`, `sub`, `sid`, `jti`, `iat`, `exp`, `dev`, `prf`, `cek`, `own`, `osu`, `att` are required with their JSON types (strings, integer NumericDates, boolean `own`), `wdi` an integer of at least 0 when present, `att` `open` or `attach`; a JSON `null` anywhere, a missing or mistyped claim or trailing data is a parse failure; unknown claims are ignored. `iss` and `iat` are not compared: the key from this server's JWKS binds the issuer, and 24 5.3 fixes the checks. Ruling for docs/DECISIONS.md (a second, smaller implementation of the ADR 0067 profile in the host module, tested with the RFC 8037 A.4 vector and the negative cases of ADR 0067 "Confirmation"); add a sentence on it to ADR 0068 "Confirmation".

5. **Check order and close details.** In the service user, for every message 1 on a data connection; first failure wins, nothing after it runs:

    ```text
     0  ReadMessage1 with prologue (sid of session.open, own host ID) and the static Noise key
                                                                        -> handshake_failed
     1  JWS parse and signature (Design note 4)                          -> token_invalid
     2  typ = terminal-session+jwt                                       -> token_invalid
     3  aud = own host ID                                                -> token_invalid
     4  sid = session ID of the prologue                                 -> token_invalid
     5  now <= exp + clock leeway (Design note 2a)                       -> token_expired
     6  jti not seen; remember it now until exp + clock leeway           -> token_replayed
     7  cek = EphemeralKeyHash(e of message 1)                           -> token_invalid
     8  att: open needs a sid without live PTY; attach needs a sid with
        a live PTY whose sub, osu and prf equal the claims               -> token_invalid
     9  prf names a profile in profiles.Offered now                      -> profile_unknown
    10  osu in host_service.session_users                                -> session_user_unknown
    11  osu unbound (bind it to sub now) or bound to sub                 -> session_user_mismatch
    12  wdi: present exactly for a profile of kind claude with att open,
        and an index into the reported list of osu after HD7             -> profile_unknown
    13  own = true when this host detected that it is the server host   -> server_host_owner_only
    ```

    Steps 8 and 12 add what 24 5.3 leaves open: which session an `attach` may name, and when `wdi` may be present (M2-44 issues `wdi` exactly so). Ruling for docs/DECISIONS.md (an `att` mismatch can only come from a server fault or manipulation, R-TM-16); update 24 5.3. An `attach` for a session whose end the host service already reported is no refusal: it closes that data connection with `1000` and reports nothing new (the server closed the session). Step 6 records the `jti` before later steps run, so a replay of a token that failed later is still `token_replayed`. The `jti` memory lives only in memory: after a restart of the host service every earlier session is ended (`host_restarted`, D-W-90), so only a server that sends `session.open` for an ended session could replay, which 24 5.1 excludes from the protection goal. Step 13 uses M2-42's HD5 result or-ed with M2-43's `PeerIsLocal` (the `is_server_host` of `report`). Step 11 writes `bindings.json` through `internal/state` (atomic write, M2-42 Design note 4) under a lock before step 12, so two first opens of one session user with two people never both bind; a binding stays when a later step fails, because the server never reassigns a session user (T12). Ruling for docs/DECISIONS.md.

6. **Reporting a failure** (M2-44 Design notes 8 and 9). A refusal at steps 0 to 13, for an opening and for an attach, closes the data connection with `4101` (`token_expired`, `token_replayed`) or `4104` (every other detail) and the `close_detail` as close reason; the host service sends no `session.ended` for it, and the server ends an opening with `open_failed` and that detail, leaves a started session `detached` on `4101` and ends it on `4104`; on a `4104` refusal of an attach to a live PTY the host service also ends that PTY with its tree at once (M2-44 Design note 9), and the following `session.close` finds nothing left to do. A failure after message 2 and before the PTY runs (Design notes 7, 11, 15, the PTY start) and every fault of the stream send `session.ended` with `close_reason` `open_failed` and the `close_detail` and keep the data connection open: the server ends the session and closes both sides through M2-44's end path (host side `4100`, device `StreamCodeForEnd`, M2-44 Design note 11), so the device gets `4104` for `handshake_failed` and `4100` for `open_timeout`, `subscription_login_detected`, `shared_location`, `helper_untrusted`, `local_confirm_denied` and `pty_failed`. A close by the host service right after the report would reach the relay before the end and give the device `4102` (M2-44 Design note 7, row "host side closes otherwise"). This holds for every `session.ended` the host service sends while it holds the data connection (Design notes 7, 11 and 14). Only when the server has not closed the data connection within the length of the opening window (`HostSessionOpen.expires_at` minus the arrival of that `session.open`) after the report does the host service close it with `1000`. Ruling for docs/DECISIONS.md: the close order after `session.ended`. M2-43 accepts from a host exactly `client_closed`, `process_exited`, `idle_timeout`, `detach_expired`, `open_failed` and `host_policy_violation` (M2-43 Design note 10); the host service sends no other reason.

7. **Message 2, `start` and the stream.** After step 13 the host service sends message 2 with the payload `{"v":1,"host_version":"<internal/buildinfo.Version>","profile":"<prf>"}` and waits for the first transport message until `HostSessionOpen.expires_at`; `expires_at` bounds only this wait, the gate and the local confirmation after `start` are bounded by their own values (Design note 15 d). It must be `start`; anything else, a failed decryption, an unknown, malformed or wrong-direction frame (M2-38 `frame.Decode` errors), a second `start` or any such fault later in the session ends the session: PTY and tree end, `session.ended` with `open_failed` and `handshake_failed`, and the device gets `4104` (24 5.4) through the server's close (Design note 6). Ruling for docs/DECISIONS.md: 03 `terminal_sessions.close_reason` has no value for a fault of the encrypted stream after the opening, and M2-43 accepts no other host reason; `open_failed` ("rejection by the host service") with `handshake_failed` keeps the manipulation signal of `4104` without a core change (spec gap in the report). Without `start` until `expires_at`: no PTY, `session.ended` with `open_failed` and `open_timeout` (the server's own deadline may have ended the session already; then the report changes nothing, TM-T05). Until the PTY runs the host service reads no further frame (backpressure through the relay). `start` sets the size of a new PTY or resizes the PTY of an attach; `data` goes to the PTY; `resize` resizes; `close` ends the session with `client_closed`. PTY output goes out in `data` frames within the body limit of M2-38. When the process exits, the host service sends `exit` with the exit code (Unix: the status, or 128 plus the signal number after a signal; Windows: the process exit code), ends the tree and sends `session.ended` with `process_exited` and `exit_code`. After a PTY started the host service sends `session.started` once; an attach sends none (the server sets the state when the relay pairs, M2-44).

    - `command`: the resolved path of `program` (the path HD11 checked) with `args`, working directory the home, the allow list.
    - `claude` with `organization`: program the resolved `host_service.claude_bin`; working directory the working directory of `wdi` (Design note 10); `PATH` the search list of HD6 followed by the cleaned `PATH`; `ANTHROPIC_API_KEY` from `claude_api_key` (Design note 10); `CLAUDE_CONFIG_DIR` = `<home>/.config/bothy-host/claude` (Windows `%USERPROFILE%\.config\bothy-host\claude`), which M2-42's helper creates with mode `0700` (Windows: an ACL only for the session user), refused with `shared_location` when it does not resolve to exactly that folder inside the home; never `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_PROFILE`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY` (09 18.3), because they are not on the list.
    - `claude` with `personal`: the login shell started with a command that sets `CLAUDE_CONFIG_DIR` to the checked value (or removes it when it was unset) and then runs `claude` from the shell's own `PATH` (Unix: `export CLAUDE_CONFIG_DIR=<quoted value>; exec claude` or `unset CLAUDE_CONFIG_DIR; exec claude`, quoted for the shell kind; Windows: `powershell.exe -NoLogo -Command` with `$env:CLAUDE_CONFIG_DIR = '<value>'` or `Remove-Item Env:\CLAUDE_CONFIG_DIR -ErrorAction SilentlyContinue`, then `& claude`); working directory the working directory of `wdi`; no API key.

    Ruling for docs/DECISIONS.md: `TERM`, the Windows environment block, the resolved program of `command`; update 24 11.1 and 7.4.

9. **Login shell and the query of `CLAUDE_CONFIG_DIR`** (24 7.4, D-W-82, D-W-84). The login shell and the home come from `hostos.Users` (M2-42, which reads the user database without cgo). Unix: a login shell starts with `argv[0]` = `-` plus the base name of the shell (login(1) convention, valid for every POSIX shell, `fish` and `tcsh`); a shell that is not an absolute existing path listed in `/etc/shells` gives `pty_failed`. Windows: `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoLogo` (present on every Windows 10 and 11) is the login shell, with the environment block of Design note 8. Before every start of `claude` with `personal`, the helper runs M2-42's login-shell probe of HD6 (it prints only whether `CLAUDE_CODE_OAUTH_TOKEN` is set and the value of `CLAUDE_CONFIG_DIR`, never a token; on Windows from the user's registry hive), bounded by `host_service.auth_status_timeout`; unset means the default folder `<home>/.claude`; the value is resolved by the helper as the session user with M2-42's `Resolver` and must be the home or below it; a value outside, a link leading outside, a dangling link or a missing folder give `shared_location` (TM-T29 (k)); a timeout or a failed shell gives `pty_failed`. Only that probe is ever run, so no other variable and never a token is read (24 7.4). Ruling for docs/DECISIONS.md: the login shell convention and PowerShell on Windows; update 24 7.4 and 11.1.

10. **Session ops on the local channel** (24 2.2; M2-42 codec). Kind `0x00` JSON ops `{"op","id","d"}`: from the service `pty.start {session_id, profile, kind, program and args for command, workdir_index, cols, rows, api_key only for claude with organization}`, `pty.resize {session_id, cols, rows}`, `pty.stop {session_id}`; from the helper `pty.started {session_id}`, `pty.exited {session_id, exit_code}`, `pty.failed {session_id, close_detail}`. Kind `0x01` body: the 16-byte session ID (M2-38 `ParseID` order) followed by the bytes of one M2-38 `data` frame, in both directions; the helper reads PTY output in chunks small enough that the body stays within the codec limit of M2-42. The service user reads the key file `claude_api_key` in `host_service.state_dir` (reserved by M2-42, placed by the operator, 16 4.4 point 5) for each such start and sends the value only in that `pty.start`; the helper puts it only into that child's environment and clears its copy after the start; it never reaches a log, a file or another start. The helper maps `workdir_index` to the entry of its own list after HD7, resolves it as the session user and requires the identity it reported at start (M2-42, D-W-84), else `shared_location`. With `personal` no key, token or login ever crosses the channel (TM-T25). Ruling for docs/DECISIONS.md: the op set, the kind `0x01` body and the per-start handover; update 24 7.4 and 16 4.4 point 5 with the file name.

11. **Gate: HD6, HD10 and HD11 in operation** (24 2.2 HD10, HD11, 7.4, D-W-89). `gate.go` keeps the latest result per check and session user, builds on M2-42's `Readiness` and decides admission:

    - Before every PTY start (after `start` and before the local confirmation): the `Light` run of the helper of `osu` (HD6 and HD11 without the entry scan) and the service user's HD11 for the locations for all; the latest periodic results of the other helpers still apply. Ruling for docs/DECISIONS.md: other helpers are not run per opening, because the open time would grow with the number of session users and the periodic run bounds their age to `host_service.credential_check_interval`.
    - Every `host_service.credential_check_interval`: the `Light` run in every helper and HD11 for the locations for all.
    - HD6 not passed in any session user while the declaration is `none` or `organization`: no new session (`open_failed` with `subscription_login_detected`), every running session ends with `host_policy_violation` and `subscription_login_detected`, `report` with one HD6 entry per affected session user; sessions again only when HD6 passes in every session user.
    - HD11 not passed at a location of session user X (also `entry_scan_running`, `entry_scan_timeout`, `foreign_entry`, `home_unresolvable`): X gets no session (`open_failed` with `shared_location`), X's running sessions end with `host_policy_violation` and `shared_location`, the others continue; a finding of the entry scan is lifted only by a `Full` run (start or `bothy-host doctor`), never by `Light`.
    - HD11 not passed at a location for all: no new session, all running sessions end with `host_policy_violation` and `shared_location`, `report` without a session user name; lifted by the next passing run.
    - A failed peer check of the local channel in operation (HD10, `peer_mismatch`): no new session, all running sessions end with `host_policy_violation` and `helper_untrusted` (24 HD10 "as with HD6").
    - Every change of a result sends `report` (24 7.4, `HostReport` "on every change").

12. **Process trees** (24 6.5, R-TM-15). Every end, whatever its reason, kills the whole tree at once with SIGKILL or `TerminateJobObject`, without a grace period, because every end is either the person's `close` or an enforcement that 24 8.3 wants "immediately". Ruling for docs/DECISIONS.md.

    - Linux: the helper unit gets `Delegate=yes`; at start the helper moves itself into the leaf `<its cgroup>/helper` and creates one cgroup `<its cgroup>/s-<session id>` per session, places the child there before it runs user code (clone into the cgroup, or write the PID before releasing the child), ends it with `cgroup.kill`, falling back to SIGKILL of every PID in `cgroup.procs` until it is empty, then removes the cgroup. If the cgroup cannot be created the PTY does not start (`pty_failed`). Ruling for docs/DECISIONS.md: 24 6.5 names a systemd scope of the session user, but a session user without a login session has no user manager; a delegated subtree of the helper's system unit gives the same per-session cgroup (verify against the systemd documentation of `Delegate=` and record it [verified] with URL and date in 24 6.5); systemd also kills the whole subtree when the helper unit stops or restarts.
    - macOS: the child starts with `Setsid`; at the end the helper takes a process table snapshot (`golang.org/x/sys/unix` `SysctlKinfoProcSlice("kern.proc.all")`) and kills every process of the session user whose parent chain in the snapshot leads to the session leader, or whose POSIX session ID or process group equals the session's, repeating snapshots until one finds none. The helper keeps a run file of its live sessions (leader PID, its start time, process group, session ID) with mode `0600` in `<home>/.config/bothy-host/run`, because launchd does not kill process groups created with `setsid` when the helper exits; at start it kills the recorded trees whose leader start time still matches. Limit, honestly, in 24 6.5 and RK-23: a process that left the session with `setsid` after its parent ended before the end of the session is not found; it runs in the person's own session user like a long-running process (6.5 "Limit", T12).
    - Windows: the child is created suspended with the pseudo console attribute, assigned to a new Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and without `JOB_OBJECT_LIMIT_BREAKAWAY_OK`, then resumed; the end calls `TerminateJobObject` and `ClosePseudoConsole`; the job handle belongs to the helper, so the tree also ends when the helper dies.
    - Unix PTY with `github.com/creack/pty` and `Setctty`; ConPTY with `golang.org/x/sys/windows` (`CreatePseudoConsole`, `ResizePseudoConsole`, `ClosePseudoConsole`, `NewProcThreadAttributeList`); where the pinned `x/sys` lacks one of them, declare it through `windows.NewLazySystemDLL("kernel32.dll")`. The release build stays without cgo (M2-38 note 4).
    - The helper ends every PTY with its tree when its channel to the host service breaks, then waits for the next connection (D-W-90).

13. **Scrollback and attach** (24 6.2). The service user keeps per session a ring buffer of `host_service.scrollback_bytes` with the newest PTY output, in memory only (no file, never logged), and keeps draining the helper's output into it while no device is attached, so the program never blocks on a full PTY. After a successful attach (steps 0 to 13, `start`, local confirmation) it resizes the PTY to the `start` size, sends `replay_begin`, the buffer as it was when `start` arrived in `data` frames, `replay_end`, then the live output that arrived since; when the buffer has wrapped, the replay starts after its first line feed, so no half line, half UTF-8 sequence or half escape sequence opens it. Ruling for docs/DECISIONS.md; update 24 6.2.

14. **Idle and detach on the machine** (24 6.2, 6.3, R-TM-11). Idle is the time since the last input frame of the device (`frame.IsInput`: `data` and `resize`), also across a detach; after the idle value of Design note 2a the host service ends the session with `idle_timeout`. When the data connection of a session with a live PTY closes or is lost, the host service starts the detach value; an attach stops it; when it runs out, the session ends with `detach_expired`. The server keeps its own checks (M2-44, M2-46). The clock is injectable for tests.

15. **Local confirmation** (24 6.4, Ruling T3, ADR 0070). The host service cannot show anything in another user's desktop session, so the person at the machine runs a confirmation agent `bothy-host confirm-agent` in their desktop session, started at their login by an autostart entry the operator creates (LaunchAgent, XDG autostart file, a value under the `Run` key of that user; 16 4.4).

    a. Endpoint, created by the host service itself: Linux `/run/bothy-host-confirm/confirm.sock` (folder from `RuntimeDirectory=bothy-host-confirm` of the host service unit, mode `0755`, owned by the service user), macOS `/Library/Application Support/bothy-host/confirm/confirm.sock` (folder created by `install`, owned by the service user, mode `0755`), Windows the named pipe `\\.\pipe\bothy-host-confirm` with `PIPE_REJECT_REMOTE_CLIENTS`; the socket has mode `0666` and the pipe a DACL for the service account and interactive users. Access is decided by the peer check, not the mode: the peer's user (Linux `SO_PEERCRED`, macOS `LOCAL_PEERCRED`, Windows `GetNamedPipeClientProcessId` and the token user SID) must be neither the service user nor in `host_service.session_users` nor a former session user in `bindings.json`, and must own the active console session (Linux: the user of the active session on `seat0` from `loginctl`; macOS: the owner of `/dev/console`; Windows: the peer process's session equals `WTSGetActiveConsoleSessionId`); otherwise the connection is closed and logged with the code `confirm_peer_refused`. Reason: a long-running process of a session user must not approve PTYs, and the option means the person sitting at the machine (24 6.4). Ruling for docs/DECISIONS.md: the console owner instead of a configured user, because 24 6.4 names "the person logged in on the host" and a key could contradict who sits there.

    b. Protocol: JSON lines. Service to agent `{"op":"confirm","id":"<uuid>","kind":"open"|"attach","profile":"<name>","session_user":"<osu>","timeout_ms":<n>}` and `{"op":"cancel","id":"<uuid>"}`; agent to service `{"op":"answer","id":"<uuid>","allow":true|false}`. The request goes to every accepted agent; the first answer wins, the others get `cancel`.

    c. Dialog in the agent, default "deny": macOS `/usr/bin/osascript` with `display dialog` and `giving up after`; Linux `/usr/bin/zenity --question --timeout` or else `/usr/bin/kdialog --yesno`; Windows `MessageBoxW` (`golang.org/x/sys/windows`) with `MB_YESNO`, `MB_DEFBUTTON2`, `MB_SYSTEMMODAL`. No dialog program: the agent answers `allow: false` and logs `no_dialog_tool`. The text names open or attach, the profile and the session user; nothing else.

    d. With `host_service.require_local_confirm = true`, before every PTY start and before every replay of an attach (after `start` and the gate): no accepted agent, no answer within `host_service.local_confirm_timeout` or a denial give `open_failed` with `local_confirm_denied`; a denied attach ends the session (the person at the machine refused access to it). Ruling for docs/DECISIONS.md, stated identically in M2-44 Design note 7: on a host whose last `report` says `require_local_confirm = true` (`hosts.reported_require_local_confirm`), the server deadline of an opening (grant time plus `terminal.open_timeout`) is met by the pairing of both sides, not by `session.started`, because the consent window `host_service.local_confirm_timeout` (24 6.4) may be longer than `terminal.open_timeout`; the host service bounds the rest itself: `start` until `HostSessionOpen.expires_at`, the consent within `host_service.local_confirm_timeout`, and it ends a refused or unanswered opening with `session.ended` `open_failed` (`open_timeout` or `local_confirm_denied`). Ruling for docs/DECISIONS.md: the agent, the endpoint, the peer rule, and the attach, because an attach hands the scrollback and the live stream to the attaching device, exactly what the option guards against a malicious server; update 24 6.4 and 16 4.4.

16. **Logs and errors.** Log lines of the host service are JSON with an event code, the session ID, the profile name, the session user name, `close_reason`, `close_detail` and the exit code; never content, a token or its `jti` in clear (a SHA-256 prefix if needed), a key, an environment value, a path or a command line. Errors of these packages wrap sentinel values whose text names an operation and a code. Test failure messages print lengths and hash prefixes only.

- [ ] TM-T25: with `personal` the service user opens no login file (Linux trace), and no subscription login lies in the state directory, in the local channel or in a report; `auth status` in the session reports `oauth_token`.
- [ ] TM-T28 (c) and (d): an `osu` outside `host_service.session_users` and an `osu` bound to another person start no PTY (`4104` with `session_user_unknown` and `session_user_mismatch`); on macOS with an empty `host_service.claude_bin` the host warns `auth_status_unchecked`, offers no `claude` profile, and another person's session sees no foreign login.

- [ ] The `claude` profile starts with `organization` exactly the resolved `host_service.claude_bin` and is not offered without it or without the script's interpreter in the search list; with `personal` only with a `CLAUDE_CONFIG_DIR` that resolves inside the home; with `none` it does not exist; the environment of every profile is an allow list plus `TERM`, tested per declaration without a model call.
- [ ] Every PTY starts only in the helper of `osu`, `claude` only in the working directory `wdi` of the reported list of `osu`, and the binding `osu` to `sub` is stored in the state directory.

## Definition of done

- Code and tests as specified; doc comment on every public symbol (purpose, parameters, return value, errors, example where useful); comments explain why.
- `services/host/README.md` (English) updated: packages, the process split, the session ops of the local channel, the profiles and their environments, the confirmation agent, the platform specifics and limits; the README of `services/server/internal/terminal` if the server changed.

- An ADR only if you take an architecture decision beyond this brief (MADR 4 as in `docs/adr/0000-template-madr-4.md`, headings and text in English, next free number, `make adr-index`).
- `make check` green.
- An independent code review over the diff, then the red team gate (`docs/quality/red-team-gate.md`, verdict `JA` or `NEIN`); on `NEIN` fix with a test per finding and have the delta checked again. Record both verdicts.
- Land the change as `AGENTS.md` ("How work lands on `main`") describes: a pull request from this branch, squash-merged only when review, red team and `make check`, `ci-ok` and the review threads are green; then `git worktree remove`.
