# M2-47: Terminal relay across several nodes (T6)

Status: ready | Depends on: M2-44 | Milestone: M2

## Goal

With `cluster.mode = multi` several api nodes serve the terminal as one. The node that processes `openTerminalSession` sends the instruction `session.open` over `NOTIFY ephemeral`, only with IDs and only after its transaction committed, to whichever node holds the control connection of the host service; the edge routes both stream paths of a session (`/api/v1/terminal/sessions/{session_id}/stream` of the device and `/api/v1/hosts/sessions/{session_id}/stream` of the host service) by consistent hashing over the `{session_id}` segment to the same api node, where the relay of M2-44 pairs them in memory. A side that lands on another node because the edge lacks the hash rule finds no counterpart within `terminal.open_timeout`, closes with `4102`, is counted in `bothy.terminal.relay.unpaired` and leaves `/readyz` ready: a misconfigured edge fails visibly instead of passing bytes through a broker (24 "Multiple nodes", Ruling T6, R-TM-09, R-OP-19, RK-29). The same signal path carries what else the specification asks of several nodes for the terminal: a host transition decided on any node closes the host's connections on every node at once (24 3.1, 3.3), the probe of an older control connection reaches the node that holds it (24 "Second control connection"), and every node knows whether a host is connected anywhere, so `409 host_unavailable` behaves as with one node (24 6.1 point 2, 13). The end of a session needs no signal: M2-44's relay learns every committed end from the event-log tail of its own process on every node (24 "Revocation", 02 11.2), and this ticket proves that with two nodes. With `cluster.mode = single` nothing changes and no `NOTIFY` is sent. The ticket also ships the example edge with hash routing as a Compose overlay with two api nodes in `infra/compose` and updates 16 "Terminal: forwarding and host service" (4.4). This is TM-T15 at the server level with the fake host of M2-44; M2-48 runs it again end to end with the real host service in a container. The multi-node relay comes in M2, independent of the rest of the multi-node operation in M7-17 (P-25, OQ-07).

Product requirements implemented here:

11. With `cluster.mode = multi` the node that processes `terminal.open` sends the instruction `session.open` over `NOTIFY ephemeral`, only with IDs, to the node of the control connection; the receiving node reads everything else from the database (24 9 point 1, 03 6.6, 02 11.6, R-AR-10, R-SY-25, D-T6).
12. The host service opens one data connection per session on `/api/v1/hosts/sessions/{session_id}/stream`, the device connects to `/api/v1/terminal/sessions/{session_id}/stream`, and the edge routes both by consistent hashing over the `{session_id}` segment to the same api node, where the relay connects the two sides in memory; no broker, and no byte of a stream ever goes through the database, the event log or `NOTIFY` (24 9 points 2 and 3, 16 4.4 "Edge and proxy" point 2, R-TM-09, R-OP-19, 24 10.2).
13. A side that lands on another node finds no counterpart within `terminal.open_timeout` and closes with `4102`; the node counts this in `bothy.terminal.relay.unpaired` (M2-44's counter, D-W-105) and keeps `/readyz` ready (24 9 point 4, signals.md 4.3a, TM-T15, PLAN row M2-47).
14. The channel `ephemeral` is active only with `cluster.mode = multi`; with one node nothing of this ticket runs (03 6.6, 02 11.6, R-AR-10).
15. With `cluster.mode = multi` the probe of an older control connection reaches the node of that connection over `NOTIFY ephemeral` (24 3.4), and a transition of a host decided on any node ends the affected connections on every node at once, fail closed (24 3.1, 3.3, D-L23); the end of a session reaches every node through the event-log tail of M2-44 (its Design note 11; 24 8.3, 02 11.2), which this ticket proves with two nodes and does not duplicate with a signal.
16. The edge forwards WebSocket upgrades for `/api/v1/terminal/sessions/{session_id}/stream`, `/api/v1/hosts/connect` and `/api/v1/hosts/sessions/{session_id}/stream` with an idle timeout that never cuts a quiet terminal, does not buffer these connections and writes no content to logs (16 4.4 "Edge and proxy" points 1 to 3); published ports bind `127.0.0.1` of the host only (16 4.1 rule 1).
17. Telemetry only as the catalogue allows: this ticket registers no instrument and no attribute; it asserts M2-44's `bothy.terminal.relay.unpaired` (D-W-105) with the closed attribute set `bothy.terminal.side` (`client`, `host`) and uses that attribute, which M2-44 registers, in its log records; no IDs of people, no host names, no content (signals.md 2 and 4.3a, 24 10.4, SEC-TERM-1, SEC-LOG-3, SEC-LOG-5).
18. Every signal carries only a kind and IDs: never a session token, `jti`, profile, name, path, address or byte of a stream (03 6.6, 02 11.6, SEC-TERM-1).

## Design notes

1. **Scope of the ticket** (Ruling for docs/DECISIONS.md, `D-M2-47-1`). The plan row names `session.open` over `NOTIFY ephemeral` and the hash rule of the edge. With several nodes the specification needs the same path in three more places, and no other ticket builds them (M7-17 covers gateway, `runs` and `agents` only): the probe of an older control connection "through `NOTIFY ephemeral` to the node of the older connection" (24 3.4); the closing of a host's connections at a transition or re-pairing (24 3.1, 3.3); and the check "host connected" behind `409 host_unavailable` (24 6.1 point 2, 13). They belong here, because without them `cluster.mode = multi` would keep the control connection of a disabled or re-paired host open on another node, hide a copied key and answer `409 host_unavailable` by chance of the node. The immediate end of sessions with `4100` and the instruction to the host service (24 8.3) needs no signal: every end writes `terminal_session.changed` in its transaction, and the event-log tail of every api node hands it to M2-44's relay observer (M2-44 Design note 11; 02 11.2, 16), so this ticket only proves it with two nodes. The code stays node-neutral (OQ-07); with `cluster.mode = single` none of it runs.

2. **Mode and roles** (Ruling for docs/DECISIONS.md, `D-M2-47-2`). `cluster.mode` is the enum `single` or `multi` of 02 22 (default from that table, place Server). Register it in `internal/wire/configkeys_cluster.go` with `chapter02` if the base branch lacks it (keys enter with their first consumer, M1-07); then `make config-doc-check`.

    - `single`: `LocalSignals`, no listener, no `NOTIFY`, no presence view, no probation; the behaviour and the tests of M2-43 and M2-44 stay unchanged.
    - `multi`, roles `api` and `all`: `NotifySignals` and one `EphemeralListener` per process.
    - `multi`, role `worker`: `NotifySignals` for a unit of the Scope it commits, no listener, because it holds no connection; the ends it commits (`terminal.sweep`, expiries) need no signal (design note 3).

3. **Signals and payload** (Ruling for docs/DECISIONS.md, `D-M2-47-3`). Channel `ephemeral` (03 6.6). The payload is compact JSON with exactly the fields of its kind: `kind`, `host_id`, and per kind `session_id` or `conn_id`, each a UUID string. No other field, never `null`. Kinds, who sends them and what the receivers do:

    - `terminal.session_open` (`host_id`, `session_id`): staged by every unit after which M2-44 sends `session.open` (the open; the attach too, if M2-44 sends one there). Receivers: every api node loads the session through the app and, for a session of that host that is not `closed`, registers the expectation locally through M2-44's `RelayControl.Expect` (M2-44 Design note 7, with the expected `device_id` of the row and the node's receipt time of the signal as the grant time of its deadline), which closes an older device side of the session held on that node with `4103` and an older unpaired host side with `1000`; so the node the edge hashes the session to holds the expectation, whichever node served the REST call (M2-44 Design note 9 closes a host data connection without an expectation with `1000`). The deadline of such an expectation decides by the session state read from the database (design note 8), not by a local `started` mark, because `session.started` arrives only on the node of the control connection; an expectation without sides therefore ends only a session still in `opening`, through the compare-and-swap of design note 10. Ruling for docs/DECISIONS.md: on a host whose last `report` says `require_local_confirm = true` (`hosts.reported_require_local_confirm`), an expectation without sides that received `terminal.session_paired` for the session after its grant time only removes itself at its deadline; without that signal it ends the opening at its deadline like every other expectation (`open_failed` with `open_timeout`, compare-and-swap of design note 10). Reason: a pairing on another node meets the opening deadline there, and the host service then bounds start and consent itself and ends a refused or unanswered opening with `session.ended` (M2-44 Design note 7, M2-45 Design note 15 d); the server does not know the host's `host_service.local_confirm_timeout`, so only the fact of the pairing may spare the opening, and an opening that no node ever paired still ends after `terminal.open_timeout` (24 6.1 step 6). A node that holds a side keeps M2-44's rule. Only a node that holds an eligible control connection of the host (one that sent its first `report`, design note 6) additionally sends `session.open`, only for a session in `opening` of an `active` host, with M2-44's builder of `HostSessionOpen` (`session_id`, `data_path`, `profile`, `expires_at`); it drops everything else. A connection in probation waits with the `session.open`, not with the expectation (design note 7). With `cluster.mode = single`, `LocalSignals.Committed` hands the signal to the same handler on the one node, which does both, so M2-44's order (`RelayControl.Expect`, then `ControlLinks.OpenSession`) stays.
    - `terminal.host_close` (`host_id`): staged by every transition out of `active` (`setHostState`), by a re-pairing (`issueHostPairingCode` on a paired host) and by the duplicate verdict of design note 7. Receivers: every node closes the host's control and data connections with the code M2-43's single-node path uses for the host's state read after the signal (expected: `4110` after a re-pairing, `4112` for `disabled_reason = duplicate_connection`, `4111` for `disabled` by an owner and for `retired`).
    - `terminal.host_present` (`host_id`, `conn_id`) and `terminal.host_gone` (`host_id`, `conn_id`): sent outside any unit by the node of a control connection (design notes 6 and 7).
    - `terminal.session_paired` (`host_id`, `session_id`): sent outside any unit by the node whose relay pairs both sides of a session in `opening` on a host with `require_local_confirm = true`; every other node marks its side-less expectation of that session as paired (only IDs, R-SY-25).

    The end of a session has no kind. Every end, from any module, process or node (close by the person or an owner, the unpaired end, host transitions, re-pairing, `host_restarted`, a stored `session.ended`, the ends of M2-46 and `terminal.sweep`), writes `terminal_session.changed` in its transaction; the event-log tail of every api process reads the committed rows of `event_log` (woken by `NOTIFY event_log`, which is on in every mode, 03 6.6) and hands each closed session to M2-44's relay observer, which closes the device stream and the host data connection held there and calls `ControlLinks.CloseSession` on the node of the control connection (M2-44 Design note 11, 02 11.2). Reason: that path already reaches every api process in both modes, also for an end committed in a worker; a second path through `NOTIFY ephemeral` would act twice and would not reach the api process from a worker with `cluster.mode = single`.

    Decoding is strict: unknown fields, missing or extra IDs for the kind, a non-UUID value or an unknown kind starting with `terminal.` drop the payload with one log record (design note 14); a kind outside the prefix `terminal.` is ignored without a log, because M7-17 adds its own kinds to the same channel. The longest encoded signal stays below the payload limit of PostgreSQL `NOTIFY`; the limit is a protocol constant in code with its source, not a configuration key. The kinds are internal signals of the module, not event types of 05: no entry in `docs/spec/actions.yaml`, no message in `asyncapi.yaml`, nothing in the event log. Ruling: the receiver always reads state from the database, so signals that arrive late, twice or out of order change nothing wrong.

4. **Port `Signals` and the handler** (Ruling for docs/DECISIONS.md, `D-M2-47-4`). In `internal/terminal/app`:

    - `type Signals interface { Stage(ctx context.Context, s domain.Signal) error; Committed(ctx context.Context, s domain.Signal); Send(ctx context.Context, s domain.Signal) error }`. `Stage` runs inside the unit of work in phase `work`; `Committed` runs after `Do` returned nil; `Send` runs outside any unit.
    - `type SignalHandler interface { HandleSignal(ctx context.Context, s domain.Signal) }`, implemented by the `wsrelay` hub. It never blocks the caller: frames go to the writer of the connection, and every database read uses a context with `database.statement_timeout`.
    - `LocalSignals` (`single`): `Stage` does nothing, `Committed` calls the local handler (for `terminal.session_open` it registers the expectation and sends `session.open`, design note 3), `Send` does nothing.
    - `NotifySignals` (`multi`): `Stage` executes `NotifyEphemeral` on the unit's transaction, so PostgreSQL delivers the notification only after the commit and never after a rollback; `Committed` does nothing, because every node, the sender included, receives the notification through its listener; `Send` executes `NotifyEphemeral` through the pool in its own statement.
    - Every use case of the Scope ("Change") calls `Stage` in its unit and `Committed` after it; no use case calls the relay directly after a commit any more. One handler serves both modes, so the single-node behaviour is the multi-node behaviour with a local transport. Reason: a local shortcut on the sending node would act twice (locally and again through its own listener) or need a second code path.

5. **Listener** (Ruling for docs/DECISIONS.md, `D-M2-47-5`). `EphemeralListener` opens its own connection with `pg.DialDedicated(ctx, "bothy-terminal-ephemeral")`, executes `LISTEN ephemeral`, reads notifications in order on one goroutine, decodes them (design note 3) and hands each one to `SignalHandler`. On the loss of the connection it logs `terminal ephemeral listener lost` once, tries again at once and then every `database.listen_reconnect_backoff_cap` (the largest interval 02 22 allows for a `LISTEN` reconnect; no new key), runs the reconciliation of design note 9 after `LISTEN` succeeded again and logs `terminal ephemeral listener restored`. The listener is a soft dependency like the tail's `LISTEN` (02 14.4): no readiness check, `/readyz` unchanged. Stop step `terminal_ephemeral` in `lifecycle.PhaseEventTail` (02 15.3 api step 4, "Stop the log tail and `LISTEN`"); an unexpected end of its goroutine (a bug, not a lost connection) goes to `lifecycle.Runner.Fail`. One terminal listener per process; M7-17 may merge it with its own listener of the same channel, which the namespaced kinds allow; say so in the `terminal` README.

6. **Presence across nodes** (Ruling for docs/DECISIONS.md, `D-M2-47-6`). "Host connected" (24 6.1 point 2, 13) needs to know whether any node holds an eligible control connection; 03 has no column for it, so the view comes from signals.

    - The node of a control connection sends `terminal.host_present` after the connection's first `report` and again after each `heartbeat` it receives from the host service, and `terminal.host_gone` when the connection closes.
    - Each node keeps a `domain.PresenceView` of remote entries in memory. A remote entry counts while no more than `terminal.host_heartbeat_interval` times `terminal.host_heartbeat_miss_limit` has passed since its last `terminal.host_present` (the silence after which the holder closes the control connection itself, M2-43); `terminal.host_gone` removes only its own `conn_id`.
    - With `multi`, "host connected" for `openTerminalSession` and `attachTerminalSession` is an eligible local control connection or a counting remote entry; otherwise `409 host_unavailable`, as on one node.
    - A remote entry of a node that died without `terminal.host_gone` counts at most for the window above; an open it lets pass ends `open_failed` with `close_detail = open_timeout` after `terminal.open_timeout`. After a start or a listener reconnect the view is complete within one `terminal.host_heartbeat_interval`; until then an open may get `409 host_unavailable` for a host connected elsewhere, which the next attempt corrects.

7. **Second control connection across nodes** (24 3.4; Ruling for docs/DECISIONS.md, `D-M2-47-7`). Each node gives every accepted control connection a `conn_id` from an `ids.Generator` on its clock (UUIDv7, ordered by the accept time of its node, `kernel/ids`).
    a. A node ignores `terminal.host_present` of its own connections; a second connection of a host on the same node stays M2-43's local case.
    b. A node that holds a control connection `d` of the same host with `OlderConnection(d, c)` for an announced `c` starts one probe of `d` with M2-43's probe (WebSocket ping, `terminal.host_duplicate_probe_timeout`); at most one probe per connection at a time. No answer: close `d` with `4009` as M2-43 does and send `terminal.host_gone`. Answer: run M2-43's duplicate verdict in one unit (host `disabled` with `disabled_reason = duplicate_connection`, sessions end `host_disabled`, audit `host.connect` with code `duplicate_connection`, `host.updated` to all owners), which stages `terminal.host_close` (the sessions' ends reach the relays through the event-log tail, design note 3); every node then closes the control connections of the host with `4112`.
    c. A node that holds a newer connection `d` sends `terminal.host_present` for `d` at once, so that the node of the older `c` probes it after rule b. The periodic `terminal.host_present` of design note 6 repeats this after a lost notification.
    d. Probation: with `multi` a control connection receives no `session.open` before `ProbationEnd` (twice `terminal.host_duplicate_probe_timeout` after its first `terminal.host_present`: the other node's probe window plus the same again for notification and commit). A `terminal.session_open` for its host during probation waits and is checked again at the end against the database (session still `opening`, host still `active`, connection still open); the session's own `terminal.open_timeout` keeps running. Reason: otherwise a host service with copied keys on another node could get `session.open` and finish the handshake before the probe decides (T-TM-05).
    e. The order of two connections on two nodes rests on the clocks of the nodes; servers run with synchronized clocks, and only overlapping connections of one host are compared. Write this into 24 3.4 and the README.

8. **The lone side** (24 9 point 4, 6.1 point 6, 13; Ruling for docs/DECISIONS.md, `D-M2-47-8`). The same rules on one node and on several; this ticket makes them exact, and the counts go to M2-44's counter `bothy.terminal.relay.unpaired` (D-W-105).
    a. A device stream connection whose `identify` was accepted and that has no host data connection of its session on this node within `terminal.open_timeout`: close it with `4102`, count `bothy.terminal.relay.unpaired` with `bothy.terminal.side = client`.
    b. A host data connection whose `identify` was accepted, for a session in `opening`, with no device stream on this node within `terminal.open_timeout`: close it with `4102` (new on `hostData`, design note 15), count it with `host`.
    c. A session still in `opening` then ends `open_failed` with `close_detail = open_timeout` through M2-44's end function (audit `terminal.terminate`, `terminal_session.changed`, which the event-log tail brings to every node). When both sides time out on two nodes, the second end is a compare-and-swap that changes nothing: one audit entry, one event. A device that attaches to a `detached` session and finds no host data connection on its node gets `4102`, and the session stays `detached` (13: "attach later").
    d. A host data connection of a `detached` session waits for an attaching device until the session ends (`terminal.detach_grace`); it is not unpaired. A connection that was paired once never counts as unpaired.
    e. The timer starts when the side's `identify` is accepted and fires at `LoneDeadline`, the acceptance time plus `terminal.open_timeout`, inclusive. Frames of a lone side never leave the node: not into the database, the event log, a signal or another node. No readiness check is involved; `/readyz` stays `200`.

9. **Reconciliation after a listener reconnect.** After `LISTEN` succeeded again (never before, so nothing committed in between is missed), the node reads with `HostStatesByIDs` the hosts of all its control and data connections, then closes what ended while it was deaf: hosts no longer `active` with the codes of design note 3; it sends `terminal.host_present` for each of its eligible control connections at once. Sessions that ended meanwhile need nothing here: the event-log tail has its own `LISTEN` and poll and reads on from `local_head` (02 11.2), so M2-44's observer closes their connections whether this listener is up or not. Part of `D-M2-47-5`.

10. **Locks, order and idempotency.** Signals take no row lock; a staged `NotifyEphemeral` adds the commit-time `NOTIFY` lock of 02 11.7 only with `multi` (03 6.6 accepts that cost). Every end of a session goes through M2-44's compare-and-swap; the loser writes nothing. Closing an already closed connection, a second `session.close` for an ended session and a `terminal.host_present` for an unknown host are no-ops. Notifications of one sender arrive in commit order, those of several senders in any order; the handler's database reads make the order irrelevant.

## Acceptance criteria

- [ ] TM-T15 with hash routing: two api nodes with `cluster.mode = multi`; `session.open` reaches the node of the control connection over `NOTIFY ephemeral` only after the commit; both stream paths of a session meet on one node; every node registers the expectation of `terminal.session_open`, so the session runs whether the control node and the relay node are the same or not; attach works across nodes and replaces an older device side with `4103` on the hash node.
- [ ] TM-T15 without hash routing: each lone side closes with `4102` after `terminal.open_timeout`, `bothy.terminal.relay.unpaired` rises with `client` and `host`, `/readyz` stays ready on both nodes, the session ends `open_failed` exactly once, and no byte crosses nodes.

- [ ] Signals carry only a kind and IDs; rolled-back, forged and malformed signals open nothing.
- [ ] An end of a session or a host transition decided on any node, also in a worker, closes the connections on every node with the codes of one node.
- [ ] A second control connection on another node is probed: `4112` and `disabled` with `duplicate_connection` when the older answers, `4009` for a silent older one; a new connection gets no `session.open` during its probation.
