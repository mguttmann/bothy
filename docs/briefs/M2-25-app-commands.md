# M2-25: Commands and interactions for apps

Status: ready | Depends on: M2-15, M2-17, M2-26 | Milestone: M2

## Goal

After this ticket an installed app owns slash commands and message components exactly like an agent, and none of them ever triggers an agent. The commands of the app's manifest are created with the installation, follow manifest upgrades, are hidden while the app is suspended or lacks `commands:write`, and are removed at uninstall; the app posts cards with buttons, selects and forms, which are disabled when it is suspended or uninstalled. A person who runs an app command or operates an app component is checked for `required_level` (commands) or `trigger` (components), `required_capability` and `restricted_to`, and the app for an active installation, the scope of the feature and `write` on the channel; `agent.invoke` and I2 are never checked, because no agent runtime is involved (05 "Agent invocation `agent.invoke`", R-AZ-18). The personal durable events `command.invoked` and `interaction.created` reach the owning app on every way the specification names: through the app's gateway connection, the REST catch-up and webhook subscriptions when the app holds `events:subscribe`, and, for an app whose manifest declares `delivery.interactions_url`, as a POST signed like an outgoing webhook, sent after the commit by a job and answered within `app.interaction_timeout` with a message that the server writes in the app's name, with `202`, or with suggestions for autocomplete. This is 11 "Commands and interactions for apps" and the app half of 05 rule 1.6: integrations get interactive controls without becoming a way to run a model, to bypass a personal subscription (I2) or to reach a private address, and the reference apps M2-49 and M2-50 can build `/issue` with a form on it.

## Fixed requirements that apply

Owner's fixed build rules (apply verbatim):

1. No MVP. New from scratch and directly in the final state; stages are only the order.
2. Strictly modular: clear module and service boundaries, dependencies only through defined
   interfaces, no cross access.
3. Documentation in code: every public module, class, function and interface with a docstring/doc
   comment (purpose, parameters, return value, errors, example where useful); comments explain the
   why, not the what. API documentation is generated from code (OpenAPI from the routes, dartdoc,
   Python API docs in MkDocs).
4. Documentation in the repo: README per module/service, ADR for every architecture decision,
   CHANGELOG per release, keep the documentation site current. A change without matching
   documentation is not done.
5. Quality gates (SonarQube, linters, type checking, security scanners, test coverage) block the
   merge.

Rules for every brief:

6. Test first: write the failing test, run it and keep the red output for the report, then make it green, then clean up.
7. No en dash and no em dash in any file you write; the `text-rules` pre-commit hook rejects them. Use a hyphen or rephrase.
8. White label: examples and test data use `example.com` and the people Alex, Sam and Robin; no company, host or personal names, no paths under a home directory.
9. Limits, windows and thresholds only through named configuration keys listed in `docs/operations/configuration.md`; code comments and docs name the key, never the number.
10. Specification first: a change to behaviour, API, event, right or configuration updates `docs/spec/` or `docs/api/` in the same change. The core contract (`docs/spec/00-glossary.md`, `03-data-model.md`, `04-sync-protocol.md`, `05-actions.md`) is not edited by this ticket.

Product requirements implemented here:

11. Apps own commands and components like agents and never trigger an agent: no run, no invocation token, no `agent.invoke`, no I2 for app commands and app components (11 2 row "Triggers agents: never", 11 9, 05 5 last paragraph, 05 4.10 `command.invoke`, 09 10.4 last paragraph, R-AZ-18, E-EX-05, E-AG-17, D-K-D17).
12. An app command checks the person's `required_level` and the app's grants and scope; an app component checks `trigger`, the component state, `required_capability` and `restricted_to` and the app's grants and scope (05 5 last paragraph, 05 4.10, 11 9, 09 11.2). The read-only and archive rules hold for every principal (05 rule 1.8, 07 4.5).
13. App commands are listed for a channel only for apps with `write` there (09 10.3, 05 4.10 `command.read`); new commands that need a scope the installation does not grant stay inactive, removed scopes and commands take effect at once (11 4.2); a suspended app's commands are hidden, an uninstalled app's commands are removed, and its components are `disabled` in both cases, while its messages stay (11 4.3, R-EX-05).
14. The install transaction writes the commands of the manifest (11 4.1); a manifest names no target (11 4.1).
15. `command.invoked` and `interaction.created` are durable personal events of the module `runs` with the owning app as audience and the receive action `agent.events.consume`, for which an app is checked by `events:subscribe` (05 6, 03 `event_log.receive_action`, webhooks.md 7); they carry no invocation token (04 2.2) and no `resource.version` (04 9 point 3).
16. An app whose manifest declares `delivery.interactions_url` ("if commands or components without a gateway", 11 3.1) gets commands, interactions and autocomplete requests as a synchronous `POST` to that address, signed like outgoing webhooks, answered within `app.interaction_timeout`: suggestions, `200` with a message the server writes in the app's name, or `202`; without an answer the component stays `used` (11 9, 11 3.1, 04 15.7 point 2, webhooks.md 2 and 3).
17. Only `https` to hosts in `webhook.allowed_hosts`, through the egress client with the address check after DNS resolution, bound to the checked address, without redirects (11 1 point 4, 11 7 row "SSRF protection", SEC-NET-1 to SEC-NET-5, RK-04).
18. No network call inside a database transaction; consequences after the commit come from a job inserted with `InsertTx` in the same transaction; a job is repeatable without double effect and has a deadline (02 8.5, 12.1, 12.4); nothing is repeated automatically (09 1 point 5).
19. Messages of apps, including the reply the server writes for an app, have `origin = app` and never trigger an agent (05 5 point 1, SR4, 11 6 row "Never allowed", AZ-M30, AZ-M53); app cards show a header built from server fields and the badge of their origin (SEC-OUT-3, SEC-OUT-4, T-PL-01); apps never reach DM channels (11 6, 05 2.2).
20. `component.update` and `interaction.respond` need `components:write`, `command.register`, `command.remove` and `command.autocomplete.respond` need `commands:write`, `message.create` needs `messages:write` (05 2.6, 07 2.10: a missing scope with a grant gives `403 scope_missing`).
21. Every denial of a request is audited and aggregated per `audit.deny_aggregate_window`; filter checks write no denial (05 2.4, R-AZ-04, 07 4.2, AZ-P13). No read right gives `404`, identical to an unknown ID (R-AZ-01, AZ-P4).
22. No JSON `null` in answers, events and requests to apps (ADR 0053). No form value, option value, reply body, token, signature or URL path in logs, traces, metrics or audit details; the canary scenario covers the new way (SEC-LOG-2, SEC-LOG-4, SEC-AUD-5, SEC-T10).
23. Rate-limit classes `rl.trigger` (`command.invoke`, `command.autocomplete`), `rl.interaction` (`interaction.create`), `rl.write` (`component.update`), `rl.agent_runtime` (`interaction.respond`, `command.autocomplete.respond`), `rl.message` (`message.create`) (05 3, 4.7, 4.10).

    ```go

    type AppWay string
    const (
        AppWayGateway         AppWay = "gateway"          // no delivery.interactions_url in the manifest
        AppWayInteractionsURL AppWay = "interactions_url" // POST to delivery.interactions_url

    type AppPost struct {
        AppID, EventID ids.ID
        ReplyThreadID  ids.ID // thread for a 200 reply message; zero when there is none
    }
    // AppAsk is an autocomplete request for an app (ephemeral, never stored).
    type AppAsk struct {
        AppID    ids.ID
        Event    eventlog.EphemeralEvent
        Deadline time.Time
    }
    // AppOutcome is the result of one request to an app. Reason is one code of a closed list.
    type AppOutcome struct {
        Answered bool     // 200 in time and its reply was used
        Deferred bool     // 202 in time: the app answers later through the API
        Reason   string   // set when neither: inactive, no_url, denied, timeout, transport,

        Ask(ctx context.Context, a AppAsk) (AppOutcome, error)
    }
    ```

        1. `AppDispatcher.Way`. `gateway`: return; the event reaches the app through Design note 4, and an interaction stays `received` until `respondToInteraction`. `inactive`: an interaction becomes `failed` (compare-and-swap from `received`); return.

15. **Concurrency and idempotency** (03 6.3; 04 5; 06 7).
    - `invokeCommand`: `Idempotency-Key` through M1-20; `createInteraction`: the replay of M2-15 Design note 10 d, which inserts no second job.
    - Job reruns repeat the request with the same `webhook-id`; a reply message is idempotent by `(author, client_msg_id)`; interaction states change only by compare-and-swap, and whichever of the job and `respondToInteraction` leaves `received` or `dispatched` first wins; the job's final change starts only from `dispatched`.
