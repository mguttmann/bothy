# M2-17: Command autocomplete

Status: ready | Depends on: M2-16 | Milestone: M2

## Goal

A person who types the value of a slash-command option with `autocomplete = true` gets suggestions from the owner of the command, or an empty list, and never waits longer than `command.autocomplete_timeout`. `autocompleteCommand` checks the request like `agent.invoke` without a run: `trigger` on the channel, I2 (a personal subscription answers only its holder), SR2, SR4, read-only and archived channels. It then sends the ephemeral event `command.autocomplete_requested` to exactly one live gateway connection of the owning agent; in a forum channel without `thread_id` it asks nobody and answers an empty list at once after the check (R-AZ-26). The event carries a freshly issued invocation token with `trigger_kind = autocomplete` and no `run_id`. The owner answers with the gateway op `command.autocomplete_result` or with `answerAutocomplete`, with at most `command.autocomplete_max_choices` entries. The first valid answer goes back to the person. Without an answer in time, the person gets an empty list (AG-23). No run, no cost, no stored event and no model call ever comes from typing (09 "Autocomplete", R-AG-14). This puts the trigger path "autocomplete" of 05 rule 1.6 under the same check as every other trigger, which the red team of M2 tests for I2 ("another person triggering a personal subscription through every path ... autocomplete").

Product requirements implemented here:

11. `autocompleteCommand` uses the action `command.autocomplete`: resource `channel`, permission "trigger and `agent.invoke` without a run (for app commands `required_level`)", Audit `no`, Permissions `no`, class `rl.trigger`, effect `read`, no `Idempotency-Key` (`x-idempotency-exempt: read_only`) (05 4.10, 2.7; 06 7; openapi).
12. The request is checked like `agent.invoke` without a run, I2 included: the person is an active human (SR4), has `trigger` on the channel, the channel is not a DM, not read-only and not archived, the owning agent is active and reachable (operator, or guest under `allow_mentioned_agents`), `personal` agents answer only their credential holder (I2), tool class `host` only for owners (SR2), and a project-bound forum must be ready. Point 8 (active run) does not apply (04 15.7 point 1; 09 10.5 point 2; 05 5 and rule 1.6; 10 6).
13. No read right gives `404 not_found`, identical to an unknown ID; a denial by the trigger right or by `agent.invoke` gives `403 agent_invocation_denied` with `reason`; a read-only or archived channel gives `403 channel_read_only`; every denial of the request is audited and aggregated per `audit.deny_aggregate_window` (05 rule 2, 1.8, 2.4; 06 4 point 6; 07 4.1, 4.2, 4.5; R-AZ-01, R-AZ-04; 10 6).
14. The server sends the ephemeral event `command.autocomplete_requested {request_id, command_id, channel_id, thread_id, user_id, option, value, options, expires_at}` to one active gateway connection of the command's owner. For an agent owner it carries a freshly issued invocation token (`trigger_kind = autocomplete`, without `run_id`, triggering object `command_id`) as the delivery field `invocation_token`. Payload and token carry as `thread_id` the thread of the request or, in a text channel without one, the main thread; in a forum channel without `thread_id` nothing is sent to an agent owner and no token is issued, and after the check the person gets an empty list at once (04 15.7 point 2; 05 5 row `thread_id`; R-AZ-26). The event has no `seq`, is delivered at most once and is never stored (04 2.1, 2.2, 9 point 4, 15.1 point 5, 15.7 point 2; 05 5 claims, 6 table "Ephemeral events"; 09 4.5, 10.5; 03 `event_log`; R-SY-07, R-SY-17).
15. The owner answers with the op `command.autocomplete_result {request_id, choices}` or with `answerAutocomplete`. Both use the action `command.autocomplete.respond` (resource `command`, `agent-self` or `app-self` as owner of the command, class `rl.agent_runtime`, effect `read`, app scope `commands:write`, exempt `agent_runtime`), with at most `command.autocomplete_max_choices` entries (04 6.2, 15.7 point 3; 05 2.6, 4.10, 7; 06 7; asyncapi `receive.command.autocomplete_result`).
16. Without an answer within `command.autocomplete_timeout` the server answers `200` with an empty list (AG-23; 04 15.7 point 4; 09 10.5 point 4; R-AG-14).
17. Autocomplete never calls a model and never costs anything: no run, no `runs` row, no durable event, no cost entry. The token cannot start a run, because it has no `run_id` (09 10.5 point 5; R-AG-14; D-AG-13; 05 5).
18. No JSON `null` in bodies, frames or the event; every response, frame and payload matches its schema (ADR 0053; R-API-03; 06 15 G8 and G9).
19. Partial texts, option values, choices and tokens never appear in logs, audit entries, the event log or telemetry attributes (SEC-LOG-2, SEC-LOG-4, SEC-LOG-6; 03 `event_log`).

## Design notes

0. **Autocomplete without a thread** (core contract, amended by R-AZ-26 under D-W-104; no check any more): 04 15.7 point 2 and 05 section 5, claim table row `thread_id`, say that for an agent-owned command payload and token carry the thread of the request as `thread_id`, or the main thread in a text channel without `thread_id`. In a forum channel without `thread_id` the check of 04 15.7 point 1 runs as for a new thread of the channel; if it allows, the server does not ask the agent, issues no token and answers an empty list at once. 09 4.5 and 10.5 mirror this. Notes 2 g, 3 and 4 and the tests `TestAutocomplete_AppOwnerAndForumWithoutThread` and `TestAutocomplete_ForumWithoutThread` build exactly this.

1. **Placement and ports** (02 4.3, 4.4, 4.6, 4.7, 7.3; 02 4.1 point 4). `runs` owns both actions, the ephemeral event and the op (`modules.yaml`). The port `runs.CommandExec` of M2-16 gains (follow the merged name of the port):

    ```go
    // Autocomplete asks the owner of a command for suggestions for one option and waits at most
    // command.autocomplete_timeout (09 10.5). It never starts a run.
    Autocomplete(ctx context.Context, q AutocompleteQuery) (AutocompleteResult, error)
    // AnswerAutocomplete accepts the owner's suggestions for an open request (REST and gateway op).
    AnswerAutocomplete(ctx context.Context, a AutocompleteAnswer) error

    type AutocompleteQuery struct {
        ChannelID, CommandID ids.ID
        ThreadID             ids.ID // zero when the request names no thread
        Option, Value        string
        Options              []OptionValue // the other options entered so far
    }
    type OptionValue struct{ Name, Value string }
    type Choice struct{ Name, Value string }
    type AutocompleteResult struct{ Choices []Choice } // never nil: an empty list encodes as []
    type AutocompleteAnswer struct {
        RequestID ids.ID
        Choices   []Choice
    }
    ```

    `runs` declares the source port and `gateway` implements it (02 4.1 point 4; `gateway` may use `runs`, not the other way round):

    ```go
    // AutocompleteRelay hands one autocomplete request to exactly one live gateway connection of
    // the command's owner in this process (04 15.7 point 2). It never blocks on a connection.
    // sent is false when no such connection exists or its queue dropped the frame.
    type AutocompleteRelay interface {
        Ask(ctx context.Context, ownerID ids.ID, ev eventlog.EphemeralEvent, invocationToken string) (sent bool, err error)
    }
    ```

    `invocationToken` is the revealed string of M2-06's `InvocationToken`, as in M2-08's `DeliveryOutcome`; empty for app owners. Ruling for `docs/DECISIONS.md`: a source port of `runs`, not a new kernel port, because the one-connection rule, the report back and the delivery field belong to this use case only; precedent `agents.ConsumerFeed` (M2-07). The op handler lives in `gateway/app` and calls `CommandExec.AnswerAutocomplete`, as `ack` (M2-07) and `run.update` (M2-10) do; `authorize` runs inside `runs`.

2. **Use case `Autocomplete`**, in this order. It holds no transaction and no lock, writes nothing and appends no durable event:
   a. Load the command through the `agents` port (M2-16). Unknown, or `removed_at` set: `404 not_found`.
   b. Thread: if `ThreadID` is set, read `chat.Threads.Info`; unknown, or its channel is not `ChannelID`: `404 not_found`. This check runs before `authorize`, because M1-28 treats contradictory path hints as an internal error.
   c. Channel facts through the `chat` port (kind, space, `main_thread_id`); unknown: `404 not_found`.
   d. The command's scope (`scope_kind` with `scope_space_id` or `scope_channel_id`, 03 `commands`) must cover the channel; otherwise `404 not_found`. Ruling for `docs/DECISIONS.md`: outside its scope a command does not exist at this place (09 10.2 "Scope"). Whether the owner may be reached here is decided by `authorize` (`agent_not_reachable`), not by `runs`.
   e. Target thread (note 3) and `authorize` (note 3), with the rights version read once through `instance.Versions` and pinned with `authorize.WithPermissionVersion`, in request mode (not filter mode), so the authz layer audits every denial (R-AZ-04, AZ-P13). The answers of a, b, c and d and of an invisible channel have the same status, the same headers and the same problem body apart from `correlation_id` and `instance` (AZ-P4).
   f. Query validation (note 9): `400 validation_failed`.
   g. Answer `200` with an empty list at once, without contacting anybody and without issuing a token, when the owner is an app (until M2-25), or when the owner is an agent and there is no target thread (a forum channel without `thread_id`; R-AZ-26, note 0).
   h. Build the payload (note 4); if the encoded payload exceeds `sync.event_payload_max_bytes`: `400 validation_failed` with `errors[].code` `too_long`, an empty pointer (a rule of the whole request) and `detail` naming the key. Ruling for `docs/DECISIONS.md`: truncation (04 2.2 rule 2) makes no sense for a partial text, and `PublishEphemeral` would only report a programming fault.
   i. Issue the token (note 4), register the open request (note 6), then call `AutocompleteRelay.Ask`. `sent = false`: remove the request and answer `200` with an empty list at once. Ruling for `docs/DECISIONS.md`: without a live connection of the owner the server does not wait (R-AG-14 "never hangs"; adapters on REST poll or webhook never receive ephemeral events, 04 15.6 and 7.4).
   j. Wait (note 6): the first accepted answer gives `200` with its choices; the end of `command.autocomplete_timeout` gives `200` with an empty list; the end of the request context (client gone, `http.request_timeout`, shutdown) marks the request expired and writes nothing.

3. **Rights and target.**
    - Target thread (R-AZ-26): the given thread; else, in a text channel, the channel's main thread (`main_thread_id`, R-DM-11), which then also goes into payload and token as `thread_id`; else (forum) none, and note 2 g answers. So the adapter's check of 09 4.5 point 6 compares equal `thread_id` values in payload and token.
    - Descriptor: `Resource{Kind: channel, ID: ChannelID, ThreadID: <target thread or zero>, Command: &CommandFacts{OwnerID, OwnerKind, RequiredLevel}, Invoke: &InvokeFacts{AgentID: owner, TriggerOrigin: "human", MentionsAgent: true, ActiveRunAgentID: zero, NewThread: <true when there is no target thread>}}`. `OwnerKind` comes from the `agents` port: an agent record exists for agent owners (M1-51), every other owner is an app.
    - Requirement of `command.autocomplete` in `authz` (replaces `Deferred`, 07 4.2): owner kind `agent`: `Level(trigger)` and the `agent.invoke` guard of M1-28 steps 1 to 6 on the target thread (on the channel with the main-thread rule of M2-08's `NewThread` when there is none); step 7 never applies because `ActiveRunAgentID` is zero ("without a run", 05 4.10). Owner kind `app`: `Level(<RequiredLevel>)` only, without `agent.invoke` and I2 (R-AZ-18). A descriptor without `Command`, or an agent owner without `Invoke`, is an internal error. The read-only and archive rules of M1-28 run as for every `trigger` action (05 rule 1.8; 07 4.5).
    - `MentionsAgent = true`: a slash command addresses its owner explicitly, like a mention, so the mention rule of 05 5 point 3 holds and a guest owner still needs `allow_mentioned_agents`, `write` and `organization` (09 10.3; R-AZ-19). Ruling for `docs/DECISIONS.md`. If M2-16 decided otherwise for `command.invoke`, follow M2-16 and report it.
    - Problem mapping of `command.autocomplete` (06 4 point 6): `not_found` gives `404 not_found`; `forbidden` with `channel_read_only` or `channel_archived` gives `403 channel_read_only` with `reason`; `device_pending` and `scope_missing` keep their codes (M1-28 mapping); every other `forbidden` reason (`level_insufficient`, `origin_not_human`, `agent_not_reachable`, `billing_mode_personal_not_holder`, `tool_class_owner_only`, `project_not_ready`, `dev_environment_not_ready`) gives `403 agent_invocation_denied` with `reason`. Reuse the helper with which M2-16 maps `invokeCommand`; if it has none, add one in `runs` and use it for both.
    - `command.autocomplete.respond`: `Resource{Kind: command, ID: CommandID, ChannelID, ThreadID: <target thread>, OwnerID: owner}`; M1-28 decides `Any(AgentSelf, AppSelf)` with visibility on the path (the operator rule of 07 2.9 makes the channel or the fixed thread visible to its operator); apps need `commands:write` (05 2.6).

4. **Token and event.**
    - Grant for M2-06's `Issue`: `AgentID` owner, `TriggeredBy` the person, `TriggerKind` `autocomplete`, no `RunID`, `CommandID`, `ThreadID` the target thread, `ChannelID`, `SpaceID` the channel's space, `Level` `trigger` (an `allow` implies effective `trigger`, as in M2-08), `BillingMode` and `ToolClass` the current target of the agent through the `agents` port (never the reported class), `PermissionVersion` the pinned version of note 2 e. A fresh token per request (R-SY-07). The token lives only in memory and in the frame (SEC-LOG-2).
    - Event `eventlog.EphemeralEvent`: `Type` `command.autocomplete_requested`, `SchemaVersion` from the register, `Actor` `{id: person, kind: user}`, `Scope` `{space_id, channel_id, thread_id}`, `Resource` `{kind: command, id: command_id}` without `version`, `Audience` the owner. The envelope has a new UUIDv7 `id`, `occurred_at`, the request's `correlation_id`, `trace_context` when the request is recorded (04 2.2), the delivery field `invocation_token`, and no `seq` and no `permission_version`.
    - Payload `CommandAutocompleteRequestedPayload`: `request_id` (new UUIDv7), `command_id`, `channel_id`, `thread_id` (the target thread), `user_id` (the person), `option`, `value`, `options` (copied; absent when the query had none, never `null`), `expires_at` = now plus `command.autocomplete_timeout` (RFC 3339 UTC with milliseconds). No message content, no prompt (04 2.2 rule 1).

5. **Relay** (`gateway`). Candidates: connections of `ownerID` in this process that are in the live phase. For agents that means after the consumer window sent `catchup.complete` (M2-07 note 5), and ephemeral frames never go out before it (M1-66). Choose exactly one: the connection of consumer `default` if it is live, otherwise the most recently attached live connection. Ruling for `docs/DECISIONS.md`: `default` is the adapter's main stream (04 6.3); otherwise the newest connection wins, as with consumers (R-SY-09). Admit it through the hub's admission with the registered receive action `agent.events.consume` and audience self, in `authorize.Delivery(ctx)` mode (filter, no audit), as M1-65 and M1-66 admit personal events. Enqueue without blocking; if the frame would exceed `sync.outbound_queue_max` it is dropped (never `4014`, M1-66) and `Ask` returns `false`. Person connections and other principals never get the frame. `Ask` returns an error only for programming faults (unregistered type, oversized payload); `runs` turns that into `500 internal_error`.

6. **Open requests** (`runs/app`, in process memory; a mutex-guarded map keyed by `request_id`):
    - Entry: owner, command, channel, target thread, `expires_at`, state `open`, `answered` or `expired`, and the accepted choices.
    - Register before `Ask`, so an answer that arrives at once finds the entry.
    - The wait selects on the answer, a timer from `kernel/clock` set to `command.autocomplete_timeout`, and `ctx.Done()`. Every transition is a compare-and-swap under the mutex: `open -> answered` by the first valid answer, `open -> expired` by the timer or the end of the context. A timer that fires after an answer won returns the answer's choices; exactly one outcome per request.
    - Tombstones: answered and expired entries stay until `expires_at` plus `command.autocomplete_timeout`, then they are forgotten. Every `Autocomplete` and `AnswerAutocomplete` call sweeps them; there is no background goroutine. Ruling for `docs/DECISIONS.md`: `410 gone` needs a memory of the request (06 5 "autocomplete"), and the existing key bounds that memory without a new number; `rl.trigger` bounds the number of entries per person.
    - A server restart forgets every request: requests are ephemeral and at most once (04 9 point 4). With `cluster.mode = multi` before M7-17, only owner connections and REST answers on the same api node are reached; elsewhere the person gets an empty list and the answer gets `404`. Name this limit in the `runs` README (OQ-07; RK-37).

7. **Use case `AnswerAutocomplete`**, in this order:
   a. Find the entry. Unknown, never issued by this process, or forgotten: `404 not_found`, without `authorize` (an unknown resource ID, as M1-62 note 1 a; answers of `400` and above pass the proof of 02 9.3).
   b. `authorize(actor, command.autocomplete.respond, <descriptor of note 3>)` in request mode: `404 not_found`; `403 forbidden` with `reason` `not_self` (another agent that can read the place) or `subject_kind_not_allowed` (a person); `403 scope_missing` for an app.
   c. Answer validation (note 9): `400 validation_failed`; the request stays open, so a corrected answer within the window still counts.
   d. State `expired`: `410 gone`. State `answered`: `204` without effect (R-API-27). Ruling for `docs/DECISIONS.md`: the first answer counts (06 7 point 3, `agent_runtime`), and a retry after a lost response must not look like an error; a late answer learns that it came too late.
   e. Compare-and-swap `open -> answered` with the choices, wake the waiter, answer `204`. Two answers at the same moment, over REST and over the op, give exactly one accepted answer.
   No audit entry for an allowed answer (Audit `no`); denials are audited by `authz`.

8. **Gateway op `command.autocomplete_result`** (04 6.2; asyncapi `receive.command.autocomplete_result`). Register it in the dispatcher of M1-64 with action `command.autocomplete.respond` and move it to `gateway_ops.enabled`. Rate limit `rl.agent_runtime` keyed by the principal before anything else. A frame that breaks `GatewayAutocompleteResult` follows M1-64's decode rule (`4002`). Then call `CommandExec.AnswerAutocomplete`. Success sends no frame (asyncapi defines no reply); a failure sends `error {op: "command.autocomplete_result", code, detail, ref}` with the codes of note 7 and keeps the connection. `detail` names the pointer and the `errors[].code` of the first field error, never a value. If the merged dispatcher closes with `4000` after an op that answered `error` without an `authorize` check (note 7 a), restrict its proof to successful ops, as 02 9.3 does for HTTP and as 04 6.2 requires ("the connection stays"), with a test, and report it.

9. **Validation** (`runs/domain`; codes in `errors[]` of `FieldError`, 06 5 point 3; the chain of M1-18 already rejects schema violations and unknown members):
    - Query: `option` must name an option of the command (`/option`, `unknown_option`) whose `autocomplete` is `true` (`/option`, `autocomplete_not_enabled`). Each `options[i].name` must name another option of the command (`/options/<i>/name`, `unknown_option`), at most once (`duplicate`), never `option` itself (`duplicate`). Values are passed on without a type check, because the person is still typing. The command's `invokeCommand` (M2-16) checks the final values.
    - Answer: more than `command.autocomplete_max_choices` choices: `/choices`, `too_many_items`. Each `name` and `value` is non-empty (`/choices/<i>/name` or `/value`, `too_short`) and passes `kernel/textcheck.DisplayText` (code `invalid_utf8`, `control_character` or `bidi_control`). Ruling for `docs/DECISIONS.md`: suggestion names and values are display texts in the composer, so SEC-IN-4 applies; length is bounded by the body limit of the chain.
    - Ruling for `docs/DECISIONS.md`: the `errors[].code` values `unknown_option`, `autocomplete_not_enabled` and `duplicate`; write them into 09 10.5.

10. **Configuration** (09 21; extend M2-16's registration in `internal/wire/configkeys_commands.go`, `Chapter` `09-agents.md`; `command.autocomplete_max_choices` already exists there and only gains its `Max`):
    - `command.autocomplete_timeout`: duration, positive.
    - `command.autocomplete_max_choices`: int, `Min` one, `Max` equal to the `maxItems` of `GatewayAutocompleteResult.choices`. A test reads that value from `docs/api/openapi.yaml` and compares it with the key's `Max` and with the `maxItems` of `AutocompleteAnswer.choices` and `AutocompleteResult.choices`. Ruling for `docs/DECISIONS.md`: a configured value above the schema bound could never be used over the gateway; one bound on all three schemas keeps REST and gateway equal (04 6.2 "equivalent to REST").
    - Cross-check `autocomplete_below_request_timeout` (`AddCheck`): `command.autocomplete_timeout` must be lower than `http.request_timeout`, otherwise the request context would end before the empty answer (02 14.2). Ruling for `docs/DECISIONS.md`.
    - Keys used: also `sync.event_payload_max_bytes`, `sync.outbound_queue_max`, `agent.invocation_token_ttl` (through M2-06), `ratelimit.rl.trigger.*`, `ratelimit.rl.agent_runtime.*`.

11. **Never a model, never a run** (R-AG-14, 09 10.5 point 5). The server creates no run, no `run_steps` row, no `run.state_changed`, no durable event and no audit allow entry for autocomplete. The token carries no `run_id`, so M2-06's `Verify` with any `RunID` expectation answers `invalid`, and no `startRun` can accept it (09 4.5 "run wrong"). That the adapter's handler calls no model is the adapter's duty (M2-29, M2-30, M2-33, M2-34).

12. **Residual: confused deputy through suggestions** (07 SR9; T-AI-02). SR9 binds API calls to the triggering person only "within a run". An adapter that reads the API with its own rights while it computes suggestions could return names from channels the person cannot read; the server cannot filter free-form choices. This ticket does not build around it: it records the residual in the threat model (Scope), the `runs` README and the report. M2-14 decides whether an autocomplete token authenticates requests as `acting_for` (spec gap and plan gap reported).

13. **Maintenance mode and idempotency.** Both actions have effect `read` (05 2.7), so the maintenance layer (ADR 0065, M7-08) lets them through; nothing to build here. Both operations are idempotency-exempt (06 7 point 3); the generated route table carries `x-idempotency-exempt`, and no `Idempotency-Key` is required.

14. **Rulings for `docs/DECISIONS.md`** (section 10, one row `D-M2-17-<n>` each, with date, reason and place): source port `AutocompleteRelay` and op handler in `gateway` (note 1); command outside its scope is `404` (note 2 d); payload over `sync.event_payload_max_bytes` gives `400 validation_failed` with `errors[].code` `too_long` (note 2 h); empty list at once without a live connection and for app owners until M2-25 (notes 2 g and i; the forum case and the main thread as target are R-AZ-26, not rulings of this ticket); `MentionsAgent = true` (note 3); one connection, `default` first, then the newest (note 5); in-process registry with tombstones until `expires_at` plus `command.autocomplete_timeout`, and the multi-node limit (note 6); answer order with `404`, `410` and `204` (note 7); `error` frames and the proof only for successful ops (note 8); validation codes and SEC-IN-4 for choices (note 9); key bounds tied to the schema and the cross-check (note 10).
