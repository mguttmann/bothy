# M2-20: Heartbeat, presence and desired versus actual mode

Status: ready | Depends on: M2-07 | Milestone: M2

## Goal

After this ticket an agent adapter reports the state of its runtime with `sendHeartbeat` (`POST /api/v1/agents/me/heartbeat`) or with the member `agent` of the gateway op `heartbeat`, in the schema `agent_heartbeat.v1` of 09 "Heartbeat and reported state": state, runtime version, actual billing mode (`reported_billing_mode`) with its evidence (`billing_evidence`, never a key value), the modes it can prove, the tool class it actually loaded, capabilities, active runs and project readiness. The server keeps the presence of every agent in memory, derives `online`, `degraded` or `offline` (offline once `agent.presence_timeout` has passed without a heartbeat), stores the heartbeat fields at most once per `agent.heartbeat_persist_interval`, stores and audits a change of the actual billing mode or tool class at once (action `agent.heartbeat`), and sends the ephemeral event `agent.presence_changed {agent_id, state, reported_billing_mode}` to every principal with `agent.read` when state or actual mode change. The snapshot (`getSnapshot`, `ready`) and the agent card (`getAgent`, `listAgents`) show this presence instead of the placeholder `unknown` of D-G-280. When actual and desired mode differ, the agent card carries the warnings of 10 "Expected and reported", and a gauge lets the alarm `BothyBillingModeMismatch` fire in the local observability stack once the difference has lasted `billing.mismatch_alert_after`. This is the server part of BR-05: the heartbeat's actual mode is evidence for display, warning, audit and alarm and never a permission; the binding checks stay in the adapter (I3) and at `run.start` (BR-06, M2-09), so a lying heartbeat cannot weaken any check.

## Design notes

1. Placement (02 4.4, 4.6, 4.7). `sendHeartbeat`, the action `agent.heartbeat`, the table `agents` and the event `agent.presence_changed` belong to `agents`; the op `heartbeat` belongs to `gateway`, which may use `agents`. One use case in `agents/app` behind the port `Presence` serves both transports: the REST handler in `agents/adapters/httpapi` passes the request body (re-encode the generated request object or read the raw body, whichever the merged strict server allows) and the gateway passes the raw member `agent`; `domain.DecodeHeartbeat` is the only mapping from the wire form. The presence state lives in a process-wide tracker in `agents/app`, started only in the roles `api` and `all`, because only they receive heartbeats (02 3.2). `agents` publishes through `kernel/eventlog.EphemeralPublisher` (02 4.5; 02 11.6: "directly to the hub") and reaches project readiness only through the `chat` port. Ruling for docs/DECISIONS.md.
2. Use case `Heartbeat`, in this order (the rate limit `rl.agent_runtime` runs before, in the chain or the gateway, 05 2.5):
    a. `authorize(actor, agent.heartbeat, {kind: agent, id: actor, owner: actor})`. People and apps get `forbidden` with reason `subject_kind_not_allowed` from `AgentSelf` (M1-28); the denial is audited by `authz` (R-AZ-04). The body carries no agent id, so an agent can only report for itself.
    b. `DecodeHeartbeat` and validation (note 3); every violation returns one `errs` validation error with all field errors.
    c. Take the tracker entry's lock; read `GetPresenceRow` (desired `billing_mode` and `tool_class`, stored `reported_billing_mode`, `reported_tool_class`, `reported_runtime_state`, `last_heartbeat_at`) on every heartbeat, so a desired value changed in another process counts at once; create the entry if missing (handle from the identity `Directory`).
    d. Project readiness (note 11).
    e. Change of the actual mode or class (note 4).
    f. Update the entry: report, `last heartbeat = now`, state from the report, dirty unless step e wrote it; reassess (note 8); re-arm the deadline (note 5).
    g. After any commit of step e: publish `agent.presence_changed` if the pair changed (note 5).
    h. Answer `200 HeartbeatAck {presence: AgentRuntimeStatus of the entry, interval_ms: sync.heartbeat_interval}`.
3. Decoding and forms of `agent_heartbeat.v1` (`agents/domain`, 09 4.8; the openapi schema stays the contract of the top-level members):
    - Top-level members as `Heartbeat`: `state` (`online` or `degraded`), `runtime_version`, `reported_billing_mode`, `billing_modes_supported`, `billing_evidence`, `reported_tool_class`, `rate_limit`, `details`, `project_readiness`. An unknown member is a validation error (06 2 row Unknown values).
    - `details` is a closed object: `capabilities` (object; keys of 09 2.2: `followups` with `steer` or `queue`, `components`, `voice_input`, `title`, `files_out` as booleans), `active_runs` (run ids, UUIDs after R-DM-01 checked with `kernel/ids`), `degraded_reasons` (codes), `adapter` (`name` required, `version` optional), `runtime` (`name` required), `protocol_version` (integer, at least 1). Any other key, also inside `capabilities`, `adapter` and `runtime`, is an unknown member. `runtime_version` is the runtime's version and fills `reported_runtime_version`; `details.adapter.version` is the adapter's version (18 9 point 5 is aligned to this). Ruling for docs/DECISIONS.md.
    - Forms: names (`details.adapter.name`, `details.runtime.name`) `^[a-z0-9][a-z0-9._-]*$`; versions (`runtime_version`, `details.adapter.version`) `^[0-9A-Za-z][0-9A-Za-z.+_-]*$`; codes (`billing_evidence.provider`, `billing_evidence.method`, each entry of `degraded_reasons`) `^[a-z0-9][a-z0-9_.:-]*$`, the code form of SEC-AUD-5, so `method` enters the audit details unchanged. No duplicates in `billing_modes_supported`, `active_runs`, `degraded_reasons` and among the `channel_id` values of `project_readiness` (pointer `/project_readiness`, as M2-03 expects). Lengths are bounded by `http.max_json_body_bytes`. Reason: 09 4.8 forbids secrets, contents and paths, and these forms make path separators, whitespace, control and bidi characters and most key formats unrepresentable. Ruling for docs/DECISIONS.md.
    - `rate_limit` present: field error `not_enabled` at `/rate_limit` (06 5 point 3) until M6-14 builds the field.
    - Field error codes and pointers follow what M1-18 uses for the same kind of violation; REST answers `400 validation_failed` with `errors[]`. The domain checks every rule of this note itself, also those the chain or the gateway decoder already enforce from the openapi patterns (SEC-IN-1), so both transports reject the same bodies.
4. Full state and change of the actual mode or class (09 4.7 "last one wins"; 10 8; 03 `agents`):
    - Every heartbeat replaces the whole reported state; an absent optional member means "not reported": `reported_billing_mode` NULL (D-L8), `reported_tool_class` NULL, key absent in `reported_details`. Exception: `project_readiness` (note 11). Ruling for docs/DECISIONS.md.
    - A heartbeat whose `reported_billing_mode` or `reported_tool_class` differs from the stored value (also from or to "not reported", also the first report ever) is a change: one unit of work runs `LockPresenceRow`, compares again, and if still different runs `WriteReportedChange` (both columns, `reported_runtime_state`, `reported_runtime_version`, `reported_details`, `last_heartbeat_at = now()`) and records through `auditing.Recorder` in the same transaction: action `agent.heartbeat`, decision `allow`, actor the agent, resource `{kind: agent, id}`, details only `billing_mode_old`, `billing_mode_new`, `tool_class_old`, `tool_class_new` (for the changed column, each only when the value exists), `key_type` and `method` from `billing_evidence` when present. One entry per heartbeat, also when both columns change. Equal after the lock: nothing written, no audit (another process stored it). Ruling for docs/DECISIONS.md.
    - Only this path writes `reported_billing_mode` and `reported_tool_class`; the flush of note 6 never does, so neither column changes without its audit entry.
    - Nothing else happens: no `agents.version` change (it is the ETag of the record, and owners' `If-Match` writes must not fail on heartbeats), no `agent.updated`, no `permission_version`, no `access.changed`, no `event_log` row (05 4.10; 02 11.7). `authorize` reads agent policy facts fresh on every call (M1-28), so a new `reported_tool_class` counts for SR2 from the commit on and can only raise the effective class.
5. Presence state, deadline and event (04 12 item 2):
    - States: `unknown` (no heartbeat ever, the column default), `online` or `degraded` (the `state` of the latest heartbeat), `offline` once `now >= last heartbeat + agent.presence_timeout` without a newer heartbeat. Ruling for docs/DECISIONS.md: the boundary is inclusive.
    - Each entry has one timer of `kernel/clock` at its deadline; every heartbeat re-arms it. When it fires, under the entry lock and only if no newer heartbeat arrived: state `offline`, entry dirty, mismatch start times cleared (note 8), then publish.
    - `agent.presence_changed` is published exactly when `state` or `reported_billing_mode` differs from the last published pair of the entry (initially the stored values). Envelope through `EphemeralPublisher.PublishEphemeral`: type `agent.presence_changed`, `schema_version` from the event register, actor `{id: agent, kind: agent}` for a heartbeat and none for the timer, empty scope, resource `{kind: agent, id}` without `version`, no audience, payload `AgentPresencePayload {agent_id, state, reported_billing_mode}`; the last reported mode stays in the payload while `offline` (03: "last reported mode") and is omitted when not reported. The hub admits candidates with receive action `agent.read` in `authorize.Delivery(ctx)` (M1-65 candidates of an event with empty scope: all connections; M1-66 ephemeral rules: never before `catchup.complete`, dropped at a full queue, never `4014`). A publish error is logged with the agent id and never fails the heartbeat. Ruling for docs/DECISIONS.md: the trigger pair and the mode while offline.
6. Persistence (03 `agents`: at most once per `agent.heartbeat_persist_interval`):
    - A flush loop of the tracker runs every `agent.heartbeat_persist_interval` and writes each dirty entry, ascending agent id, in one unit of work per run, with `PersistHeartbeat`: `UPDATE agents SET reported_runtime_state = $state, reported_runtime_version = $version, reported_details = $details, last_heartbeat_at = $hb WHERE principal_id = $id AND (last_heartbeat_at IS NULL OR last_heartbeat_at <= $hb)`. No row updated means a fresher heartbeat is stored already; the entry becomes clean either way. The offline write is the same statement with the entry's last heartbeat time, so it never overwrites a newer heartbeat stored by another process. Ruling for docs/DECISIONS.md.
    - `reported_details` holds exactly `capabilities`, `billing_modes_supported`, `billing_evidence`, `active_runs` (array of run id strings), `degraded_reasons`, `adapter`, `runtime`, `protocol_version`, absent members omitted, never `null`; `rate_limit` stays out until M6-14; project readiness is stored only in `project_bindings.ready` (M2-03).
    - These statements take no counter, no `NOTIFY` and no audit (02 11.7).
    - Shutdown: a stop step `agent_presence` in `lifecycle.PhaseConnections`, registered after the gateway's step so no gateway heartbeat arrives later, stops the timers without publishing and flushes every dirty entry within the rest of `shutdown.total_timeout`; a server restart is not an agent going offline. Ruling for docs/DECISIONS.md; add the sentence to 02 15.3.
7. Start (`lifecycle.Component` of the tracker, roles `api` and `all`): `ListLivePresence` returns agents stored as `online` or `degraded`; keep those whose principal status is `active` (identity `Directory`, which also gives the handle). If `last_heartbeat_at` is missing or older than `agent.presence_timeout` plus `agent.heartbeat_persist_interval`, the agent is `offline` at once (the stored value lags the real last heartbeat by at most the persist interval, so no heartbeat came within `agent.presence_timeout`); otherwise it is tracked with the deadline start plus `agent.presence_timeout`, which gives adapters time to reconnect after `4013`. Agents not loaded get an entry with their first heartbeat (note 2c). Ruling for docs/DECISIONS.md.
8. Desired versus actual (10 7 and 8; 09 2.4 and 4.8), computed by `domain.Assess` from the desired values of note 2c or note 13, the last report and the state:
    - `billing_mode_matches` stays as M1-51 builds it from the reported mode.
    - Difference while the state is `online` or `degraded`: (a) `reported_billing_mode` present and unequal to `billing_mode`; (b) `reported_billing_mode` absent, `billing_modes_supported` reported and `billing_mode` not in it; (c) `billing_evidence.key_type = unknown` (10 7: an undeterminable mode counts as unequal to every desired mode). The tracker keeps the time a difference of any kind began and the time (a) began, and clears them when the condition ends or the state is `offline` or `unknown`.
    - `AgentRuntimeStatus.warnings`, only while `online` or `degraded`: `billing_mode_mismatch` when (a) has held longer than `billing.mismatch_alert_after` (10 8 row 1 names the duration); `billing_mode_unsupported` when (b) holds (row 2); `billing_evidence_unknown` when (c) holds (row 3); `tool_class_mismatch` when `reported_tool_class` is present and unequal to `tool_class` (09 2.4). A warning disappears with the heartbeat that ends its cause (10 9.2 point 5). Ruling for docs/DECISIONS.md: codes, the delay only for (a), no warnings while not present.
