# M2-50: Reference app for ticket systems (Jira)

Status: ready | Depends on: M2-49 | Milestone: M2

## Goal

After this ticket `plugins/jira-app` is the reference app for ticket systems of 11 10.2: a Python program on the SDK of M2-29 that receives Jira webhooks at its own address, reads the method from the header `X-Hub-Signature` (format `method=signature`), accepts exactly `sha256` and refuses every other method instead of assuming SHA-256, checks the HMAC over the raw body in constant time before it reads anything else, and posts the events `jira:issue_created`, `jira:issue_updated` and `comment_created` into a forum, one thread per Jira issue with the mapping kept in the app's own state, the same pattern M2-49 built for GitHub. A person with `trigger` on the forum runs `/issue` with a title; the app opens a forum post with a form, and when the form is submitted it creates the issue through the Jira REST API and answers in that thread. With the optional scopes for mirroring, replies of people in a linked thread go to Jira as comments, while the app's own messages are never mirrored back and its own Jira objects never come back into the chat (loop protection). The Python SDK of M2-29 left out the `webhooks` module of 11 11.2; this ticket adds it with the behaviour of M2-30's TypeScript verifier, proven against the test vectors of M2-26, so the app verifies the server's signed requests through the SDK exactly like the GitHub app does. The tests run against an in-process Fake-Jira API with fixtures after the Jira documentation, against an in-memory chat port, and inside `make check` against the real server through M2-29's `sdkserver` with the protocol parts M2-49 added; no test reaches a real Jira service, and the Python license gate stays green. Why: requirement 19 asks for working integrations (D-W-10), R-EX-11 asks for one real app per SDK as the proof that the Python SDK is enough for apps, and Jira announces that it may change the signature method, so an app that guessed the method would accept forged or reject valid deliveries (RK-83, T-PL-01, T-PL-02).

The app's README documents configuration, endpoints and operation.

Product requirements implemented here:

11. The app is its own process outside the server and uses only the public API, through the Python SDK of M2-29 and never through server-internal packages (11 1 points 1 to 3, 11 10, R-EX-11, ADR 0022, ADR 0026, `plugins/README.md`).
12. Jira webhooks go to the app's own address, never to an incoming webhook of the server; the app reads the method from `X-Hub-Signature` (`method=signature`), accepts exactly `sha256`, refuses every other method instead of assuming SHA-256, and checks the HMAC over the raw body in constant time before it parses or stores anything (11 10.2, RK-83).
13. One thread per Jira issue in the forum of the issue's project, with the mapping in the app's state; messages per event of `jira:issue_created`, `jira:issue_updated` and `comment_created` (11 10.2 "Like 10.1", 10.1 row "Output").
14. `/issue` with a form creates an issue through the Jira REST API and answers in the thread (11 10.1 row "Commands"; 09 10, 11; 11 9).
15. Scopes exactly as 11 10.1 after M2-49: required `messages:write`, `commands:write`, `components:write`; optional `messages:read` and `events:subscribe` with event `message.created`; grant `write` on the forum. An action without its scope is `403 scope_missing` (07 2.10, 05 2.6).
16. The app never mirrors its own messages (author = app) back (11 10.1 row "Loops"); apps never trigger agents and never hold `trigger` or `manage` (11 6 row "Never allowed", R-EX-03, SR4).
17. Commands and interactions reach the app as signed `POST` requests to `delivery.interactions_url`, answered within `app.interaction_timeout` with `202` and acted on through the API (11 9); requests of the server are verified with the SDK's `webhooks` module: raw body, `webhook-timestamp` within `webhook.receiver_tolerance`, `v1a` keys from `getWebhookKeys` only (webhooks.md 3, 11 11.2 row `webhooks`).
18. The Python SDK has the `webhooks` module of 11 11.2 with the behaviour of M2-30's TypeScript module, and every signature case of `docs/api/webhook-test-vectors.json` verifies with it (R-EX-11, ADR 0026, M2-30 Design note 2).
19. Duplicates are recognised by `webhook-id`, at least for `webhook.retry_max_age` (webhooks.md 3 point 4), and Jira deliveries by the digest of their body.
20. Foreign text never resolves a mention or becomes a link in the chat (03 content format rules 2 and 3, SEC-OUT-1); titles carry no control or bidi characters (SEC-IN-4); text sent to Jira is structured document text, never markup.
21. No test calls a real Jira service; the counterpart is a Fake-Jira API with webhook fixtures after the public Jira documentation (PLAN 8 "Test strategy", D-W-10, 11 10).
22. Secrets (the app's API token, the Jira credentials, the Jira webhook secret) never appear in logs, error messages or test output, and their files have mode `0400` or `0600` (SEC-SEC-1 and SEC-SEC-3 applied to the app, SEC-LOG-2, SEC-LOG-4, `plugins/README.md`).
23. Dependencies locked with hashes in `uv.lock`; the license gate for Python and OSV pass without a change to `quality/licenses/allowed.txt` (SEC-SC-1, licenses.md, PLAN row).
24. The app's own names do not carry the product name; it appears only as the SDK distribution `bothy-sdk` and the import package `bothy_sdk` (02 6, ADR 0044).
25. Own `VERSION` and `CHANGELOG.md` in the folder; the app is not a release component (11 10, D-W-38 for the English CHANGELOG).
26. No JSON `null` in requests to the server (ADR 0053); unknown members of server events are tolerated through the SDK (06 2).
27. The app passes its tests against the real server inside `make check` (PLAN 8 Exit criteria 9).

4. **HTTP surface** (Ruling for docs/DECISIONS.md). One aiohttp application with routes `POST /jira/webhook`, `POST /chat/interactions`, `POST /chat/events`; any other path gives `404`, another method `405`. Per request, in this order: `Content-Type` must be `application/json` (parameters allowed), else `415`; the body is read as bytes up to `jira_app.max_body_bytes` (`client_max_size`), a larger body answers `413`; signature check (Design notes 5 and 7), failure `401`; JSON parse, where invalid UTF-8, invalid JSON and duplicate member names answer `400`; duplicate check; classification and, in the same store transaction, the seen identifier and the new job; then `202` when a job was queued and `204` when there is nothing to do; `503` when the queue holds `jira_app.max_queued_jobs` jobs, the store fails, a secret file fails its check or the app is stopping. Bodies are empty except for the autocomplete answer of Design note 7. The app speaks plain HTTP on `jira_app.listen` behind the TLS-terminating proxy of the instance; `delivery.interactions_url` and `delivery.events_url` are `https` addresses of that proxy (11 3.2 rule 3), and the README shows the route. aiohttp keeps its default header limits; the proxy bounds slow clients.

5. **Jira signature** (11 10.2; RK-83). Ruling for docs/DECISIONS.md.

    - The request must carry exactly one `X-Hub-Signature` header: none is `missing`, more than one is `malformed`.
    - The value is split at its first `=` into method and signature; no `=` or an empty method is `malformed`.
    - The method is compared exactly with the allow list `SUPPORTED_METHODS = {"sha256"}`, a constant next to the HMAC function. Every other method (`sha1`, `sha384`, `sha512`, `md5`, `SHA256`, anything else) is `unsupported_method`, decided before any HMAC is computed; there is no fallback to SHA-256, also not when the value would verify as SHA-256. A new method is a code change with its test values (RK-83).
    - The signature must be 64 hexadecimal digits; it is decoded with `bytes.fromhex`, so upper-case digits decode to the same 32 bytes (the chapter names no case; accepting both adds no forgery path); anything else is `malformed`.
    - The app computes HMAC-SHA256 with the secret over the raw body bytes and compares the 32-byte digest with the decoded 32 bytes through `hmac.compare_digest`, called through the `hmac` module so tests can replace it. No string comparison of a signature anywhere.
    - Every failure answers `401` without body and logs only the reason (`missing`, `malformed`, `unsupported_method`, `mismatch`). Only after a valid signature is the body parsed as JSON.
    - Test values: the Jira documentation publishes none, so the tests reuse the HMAC-SHA256 test values of the GitHub documentation cited in 11 10.1 (same algorithm, hex encoding): secret `It's a Secret to Everybody`, payload `Hello, World!`, header value `sha256=757107ea0eb2509fc211221cce984b8a37570b6d7586c22c46f4379c8b043e17`. For the method rule the tests use the correct HMACs of the same input under other methods, recomputed while this brief was written: `sha1=01dc10d0c83e72ed246219cdd91669667fe2ca59` and `sha512=11ed355a617e98134e842012a7944ccf59c10256cb182357bd7e3a42013ff07c376f8c14cf5cc1923da20b51d64256b2fb8ebbf100aa67a61326f61fea8111bc`; both must be refused although they are correct. The test names the URL and the access date of 11 10.1 and of 11 10.2 in a comment.

6. **Jira events** (closed list; Ruling for docs/DECISIONS.md).

    - After a valid signature the body must be a JSON object with a string member `webhookEvent`. Supported: `jira:issue_created`, `jira:issue_updated`, `comment_created` (11 10.2, PLAN row). Every other value answers `204` with log reason `unsupported`. Reason: the list of the plan covers the life of an issue in the chat; more events are a later change with their fixtures.
    - The project is `issue.fields.project.key`, compared exactly with the keys of `jira_app.projects`; an unknown project answers `204` with reason `project_not_configured`.
    - The parser keeps only the fields used: `issue.id` (decimal digits), `issue.key` (`^[A-Z][A-Z0-9_]*-[1-9][0-9]*$`), `issue.fields.summary`, the project key, the actor's display name (`user.displayName` for issue events, `comment.author.displayName` for comments; absent: "someone"), the description (`issue.fields.description`, for `jira:issue_created`), `changelog.items[]` with `field`, `fromString` and `toString` (for `jira:issue_updated`), and `comment.id` and `comment.body` (for `comment_created`). A missing or malformed `issue.id`, `issue.key`, project key or, for comments, `comment.id` answers `400` with reason `invalid_payload`. Unknown members are ignored. The job stores the parsed event, never the raw payload.
    - Rich text (description, comment body) is read in two forms: a string is taken as it is; an object of `type` `doc` (Atlassian Document Format, ADF) contributes the `text` of its `text` nodes in document order, the `attrs.text` of `mention` nodes, and a line break after each `paragraph`, `heading`, `codeBlock`, `blockquote` and `listItem` node and for each `hardBreak`; every other form gives no text. Reason: the page cited in 11 10.2 does not fix the form of rich text in payloads, and the app must not drop events if it changes (RK-83).
    - `jira:issue_updated` without `changelog.items` or with an empty list answers `204` with reason `no_change`, because only field changes are news (a comment arrives as `comment_created`).

7. **Requests of the server** (11 9; webhooks.md 3 and the section of M2-25). Ruling for docs/DECISIONS.md.

    - Both `/chat/` endpoints verify with the SDK: `bothy_sdk.webhooks.verify_webhook` over the raw body with the keys of one `WebhookKeyCache` of the app's client and the default tolerance `webhook.receiver_tolerance`; never an own verifier and never keys from the request. `start_app` loads the keys (together with `getMe` and `getInstance`) before it opens the listener; a failure aborts the start. A `WebhookVerificationError` answers `401` and logs its `code`. No `v1` secret: an interactions address has no HMAC (M2-25), and the app's subscription is created without `enable_hmac`.
    - Duplicates: `webhook-id` (the event `id`) is remembered for `jira_app.dedupe_window`; a repeat answers as the first time (`202` on `/chat/interactions`, `202` or `204` on `/chat/events`) without a second job.
    - `/chat/interactions`: `command.invoked` with `command_name` `issue` queues the job `issue_command`; `interaction.created` queues `issue_form`; both answer `202`. `command.autocomplete_requested` answers `200` with `{"choices": []}` (`AutocompleteAnswer`; the app declares no option with autocomplete). Another type or command name answers `202` with Warn reason `unknown_request`. Reason: in a forum the server has no reply thread for a `200` (M2-25 `no_thread`), and Jira calls do not fit into `app.interaction_timeout`; the person sees the result through the API answers of Design note 12.
    - `/chat/events`: only `message.created` is handled (Design note 13); any other type answers `204`. `sync_epoch` is ignored, because the app keeps no `seq` state.

8. **The SDK module `bothy_sdk.webhooks`** (11 11.2 row `webhooks`; Ruling for docs/DECISIONS.md: M2-29 left the module out and M2-26 assigned the Python handling of the vectors to the SDK; this ticket is its first Python consumer). One behaviour with M2-30's TypeScript module (M2-30 Design note 2: function names are the snake_case forms, class names the same); where M2-30's merged behaviour and this note differ on a point the specification leaves open, follow M2-30 and record the difference. Public API, each with a google docstring and an example:

    - `parse_webhook_public_key(value: str) -> Ed25519PublicKey`: `whpk_` plus standard base64 of the DER SubjectPublicKeyInfo of an Ed25519 key (D-M2-26-11), parsed with `cryptography`; another prefix, bad base64 or another key type raises `WebhookConfigError`. `parse_webhook_secret(value: str) -> bytes`: `whsec_` plus standard base64; empty or malformed raises.
    - `verify_webhook(body: bytes, headers: Mapping[str, str], *, keys, secrets=(), tolerance=None, clock=None) -> VerifiedWebhook`: headers looked up case-insensitively; the three headers present, else `missing_header`; `webhook-timestamp` an integer of Unix seconds, else `invalid_timestamp`; its distance to the clock at most `tolerance` (default `webhook.receiver_tolerance` from `SdkSettings`) in both directions, else `timestamp_out_of_tolerance`; no key and no secret gives `no_trusted_key`; the header is split at spaces and each entry at its first comma, entries with an unknown scheme or bad base64 are ignored; a `v1a` entry is tried against every key over `{webhook-id}.{webhook-timestamp}.{body}`, a `v1` entry against every secret with HMAC-SHA256 and `hmac.compare_digest`; one valid entry returns `VerifiedWebhook(id, timestamp, scheme, envelope, sync_epoch)` with the envelope decoded through M2-23's `decode_event` into the SDK's `Envelope`; none gives `signature_mismatch`. Errors are `WebhookVerificationError` with `code` from exactly this list; messages never contain the body, a signature or a secret.
    - `WebhookKeyCache(client)`: `await keys()` fetches `getWebhookKeys` once, trusts every listed key (`next`, `active`, `retiring`), refreshes after the response's `Cache-Control` `max-age` (without the header: `agent.jwks_max_age`) and never because of an incoming request. It reads the header through the generated detailed call; if the merged `Client` offers no way to see response headers, add one with a docstring and a test.
    - `bothy_sdk.testing.sign_webhook(*, webhook_id, timestamp, body, seeds=(), secrets=()) -> str`: the `webhook-signature` value with `v1a` entries first in seed order, then `v1` entries in the given order (D-M2-26-10).
    - `SdkSettings` gains the fields `webhook_receiver_tolerance` (`webhook.receiver_tolerance`) and `webhook_keys_max_age` (`agent.jwks_max_age`), held by M2-29's `test_defaults_match_configuration_reference`.
    - No class of the module carries the name of an `openapi.yaml` schema (M2-29's `test_hand_layer_types.py`; `WebhookKey` and `WebhookKeys` are schema names). Not in the SDK: storing seen `webhook-id` values (the app's duty, Design note 7).

9. **State, queue and worker** (Ruling for docs/DECISIONS.md).

    - Port `Store` (`store/base.py`, a `typing.Protocol`) with `SqliteStore` in `jira_app.state_dir`: the file `state.sqlite3` with `PRAGMA journal_mode = WAL` and `PRAGMA synchronous = FULL`, one connection used through `asyncio.to_thread` under one `asyncio.Lock`; tables for the thread map in both directions (issue ID to thread and forum, thread to issue ID), the drafts, the Jira objects the app created (`issue` or `comment` with their ID and time), the seen identifiers with their time (`body_digest`, `webhook_id`) and the jobs (increasing ID, kind, parsed input, progress, creation time). Files `0600` through the umask of Design note 3. `MemoryStore` serves unit tests; one contract test runs against both.
    - The lock file `lock` in the state directory is held with `fcntl.flock(LOCK_EX | LOCK_NB)` for the life of the process; a second process fails its start with a message naming the directory. The kernel releases the lock when the process ends, so no stale-lock rule is needed.
    - A job is written before its request is answered; the worker processes jobs strictly in creation order, one at a time, so events of one issue keep their order and a `/issue` job records its issue before Jira's `jira:issue_created` event of that issue is handled (Design note 13).
    - A job records its progress per step. Every write to the server carries an identifier stored in the job before the first attempt: `client_msg_id` (SDK `uuid7`) for `createMessage` and for `createThread` with `first_message`, an `Idempotency-Key` (SDK `uuid7`) for `respondToInteraction`, passed as the operation's header parameter; if the merged SDK replaces a key the caller gives, change its retry transport so that a given key wins, with a test (06 7 makes the key the client's). A rerun after a crash repeats the same request and the server answers the original (04 5.1 and 5.2). The SDK client retries transient failures within `sdk.retry_max_attempts`; when they are exhausted, the job stays queued and the worker pauses `sdk.retry_backoff_cap`. Permanent answers end the job (Design note 14).
    - A write to Jira is never repeated: the job marks the step `attempted` in the store before it sends; a rerun that finds `attempted` without a stored result treats the outcome as unknown (Design notes 12 and 13). Reason: Jira's create calls are not idempotent, and a second issue is worse than a missing comment.
    - Finished jobs are deleted; seen identifiers, created objects and drafts older than `jira_app.dedupe_window` are pruned at each write; the thread map stays.
    - SIGTERM and SIGINT (`loop.add_signal_handler`): stop accepting (requests after the signal get `503`), let the running step finish, close the store, release the lock, exit 0.

10. **One thread per issue** (11 10.1 row "Output" through 10.2; Ruling for docs/DECISIONS.md).

    - The key is Jira's `issue.id`, not the issue key, because a key changes when an issue moves to another project while the ID stays. The map holds issue ID to `{thread_id, channel_id}` and thread to issue ID; the issue key of the latest event is kept for links.
    - Port `ChatPort` (`chat/port.py`) with `me()`, `limits()`, `create_forum_thread(...)`, `post_message(...)`, `get_message(...)`, `respond_interaction(...)`, typed with the generated models of `bothy_sdk.generated` (no own type repeats a schema, ADR 0026 "Confirmation"; drafts are `IssueDraft`, because `Draft` is a schema name); `chat/sdk_adapter.py` implements it on the SDK `Client` (`getMe`, `getInstance`, `createThread`, `createMessage`, `getMessage`, `respondToInteraction`).
    - Known issue: `createMessage` into its thread. Unknown issue: `createThread` in the forum of its project with `title` and `first_message` (the event's message) in one call, idempotent through `first_message.client_msg_id`; the map entry is stored with the answer.
    - Title `<KEY> <summary>` (for example `SUP-12 Login fails`), cleaned and cut as Design note 11 says; a thread is never retitled when the key or summary changes.
    - `404 not_found` when posting into a mapped thread (it moved out of reach or the grant there is gone): drop the entry, open a new forum post for the issue once, Warn reason `thread_unreachable`; a second `404 not_found` ends the job.
    - Messages (English templates; Jira text rendered as Design note 11; "SUP-12" stands for the key, linked as Design note 11 allows): `jira:issue_created` "**Issue SUP-12 created** by `Sam`" plus the description; `jira:issue_updated` "**SUP-12 updated** by `Sam`:" followed by one line per changelog item, "`<field>`: `<from>` to `<to>`" with `(none)` for an empty value, except for the field `description`, whose line is "`description` changed" (the full text stays in Jira); `comment_created` "`Sam` commented on SUP-12:" plus the comment.

11. **Foreign text in the chat** (03 content format, SEC-IN-4, SEC-OUT-1; Ruling for docs/DECISIONS.md).

    - Jira text never resolves a mention or becomes a link in the chat: display names, field names and field values inside messages go into a code span, descriptions and comments into a fenced code block; the delimiter of each is one backtick longer than the longest backtick run of its text (CommonMark 0.31.2, the version of 03), so the text cannot close it (03 content format rule 2: no mentions in code).
    - A link is written only to `<jira_app.jira_base_url>/browse/<KEY>`, built from the configuration and a key that matches the pattern of Design note 6; never to a URL of the payload (`self` members are REST addresses, and a payload URL is foreign text).
    - Messages are cut to `limits.message_max_content_bytes` of `getInstance` (UTF-8 bytes, at a code point boundary) by cutting the fenced text or the list of changes and adding the line "(cut, full text in Jira)", with the fence always closed; titles to `limits.thread_title_max_chars` code points.
    - Titles: Unicode control characters (category `Cc`) and the bidi controls U+200E, U+200F, U+061C, U+202A to U+202E and U+2066 to U+2069 are removed, line breaks become spaces, the result is trimmed; an empty summary leaves the key alone. If the server still answers `400 validation_failed` on the title, the job retries once with the key alone.
    - Limits come from `getInstance` at start and once more after a `400 validation_failed` with `errors[].code` `too_long`, followed by one retry.
    - Text the app writes itself (the confirmation of `/issue`, the form card) contains no mention.

12. **`/issue` with a form** (11 10.1 row "Commands"; Ruling for docs/DECISIONS.md).

    - The manifest command `issue`: description "Create a Jira issue" within `command.description_max_chars`, option `title` (`string`, required, description "Issue title"), `required_level` `trigger`. Reason: the form is submitted with `interaction.create`, which needs `trigger` (05 4.10); with `write` a person could run the command but never submit its form.
    - Job `issue_command`: the payload's `channel_id` must be a forum of `jira_app.projects`, else Warn reason `channel_not_mapped` and end (the README tells operators to grant `write` only on configured forums, so the command is listed only there, 09 10.3). Then `createThread` in that forum with the option `title` cleaned and cut as the title (empty: "New issue") and the first message "New Jira issue. Fill in the form below.", then `createMessage` in the new thread with `kind` `card` and one component built with the SDK's form builder: `custom_id` `issue:<draft id>` (a UUIDv7, within `component.custom_id_max_chars`), `single_use` true, `restricted_to` `any`, fields `description` (`textarea`, label "Description", not required) and, only when more than one project maps to the forum, `project` (`choice` of those keys, required), within `component.form_max_fields`. Store the draft `{draft id, thread id, card message id, title, projects}`. Reason: a thread belongs to exactly one issue and an app cannot retitle a thread (05 2.6), so `/issue` always opens its own forum post, also when it was run inside a thread.
    - Job `issue_form`: the draft is found by `interaction.custom_id`, else by `interaction.message_id`; unknown or pruned: `respondToInteraction` with state `rejected` and text "This form expired. Run /issue again.". The project is the only one or the chosen one, checked against the draft. Mark `attempted`, then create the issue with `summary` = the title, `issuetype.name` = the configured `issue_type` and `description` = the form text as an ADF document (Design note 15) whose last paragraph is "Created from chat.". Ruling: nothing about the person (name, handle, ID) goes to Jira from `/issue`, and the text is not neutralized, because the person wrote it for Jira.
    - Jira answers `201`: store `id` and `key`, record the issue as created by the app (Design note 13), map the issue ID to the draft's thread, `respondToInteraction` with state `acknowledged` and text "Created issue <KEY>", `createMessage` into the thread "Created Jira issue SUP-13." with the key linked as Design note 11 allows, delete the draft.
    - Jira answers `3xx` or `4xx` (not followed, so the issue was not created): `respondToInteraction` with state `failed` and text "Jira refused the issue (status <status>).", then a new form card in the same thread; the draft stays with the new card.
    - `5xx`, a time-out after `sdk.http_timeout`, a transport error, or `attempted` without result after a restart (outcome unknown): `respondToInteraction` with state `failed` and text "Jira did not confirm the issue. Check the project before you try again."; no new card, the draft is deleted.
    - A `409` answer to a repeated `respondToInteraction` (rerun after a crash) counts as done.

13. **Mirroring and loop protection** (11 10.1 rows "Scopes" and "Loops" through 10.2; Ruling for docs/DECISIONS.md).

    - Mirroring exists only when the owner granted `messages:read` and `events:subscribe`, added `message.created` to the installation's `event_subscriptions` and created a subscription to `delivery.events_url` for `message.created` (webhooks.md 1); otherwise `/chat/events` receives nothing.
    - Decision at receipt, in this order, each answering `204` without a job and logging its reason: the author is the app itself (`message.author.id` equals the principal ID from `getMe`; reason `own_message`, the loop protection of 10.1); `origin` is not `human` (`not_human`: agent, app, import and system messages are never mirrored, so two mirroring apps cannot feed each other and no agent output leaves the instance without a person); `kind` is not `text` (`not_text`); `deleted_at` is set (`deleted`); the thread is not mapped (`thread_not_mapped`). Otherwise the job `mirror`, answer `202`.
    - Job `mirror`: if `content_truncated` is set, load the message with `getMessage`; the comment body is an ADF document with one paragraph holding the display name as a text node with the `code` mark followed by the text " wrote in chat:", and one `codeBlock` with the content, because chat mentions name chat people and the content must stay literal; mark `attempted`, send the comment to the issue ID of the thread; `201`: record the comment ID as created by the app; any other outcome: log `status` or reason `jira_outcome_unknown` and end without retry.
    - Echo protection in the other direction: Jira's `jira:issue_created` event of an issue the app created through `/issue` and the `comment_created` event of a comment the app created are not posted (reason `own_jira_object`). The check runs at receipt (answer `204` when the object is already recorded) and again in the worker before posting, because Jira may deliver the event before the create call returned, and the FIFO worker finishes the creating job first. Later events of these objects (`jira:issue_updated`, comments of others) are posted. Reason: the chat already shows the original, and without the rule every mirrored reply would come back as an app message.

14. **Answers of the server** (06 5, 07 2.10), as M2-49 Design note 13:

    - `403 scope_missing`: end the job, one Warn line with `operation`, `status` and reason `scope_missing`, no retry; the Jira delivery was already answered `202`.
    - `404 not_found`: Design note 10 for threads; for `respondToInteraction` and `getMessage` end the job.
    - `403 forbidden` and `403 channel_read_only`: end the job and log the code and `reason`.
    - `400 validation_failed`: the retries of Design note 11, otherwise end the job and log the `errors[].code` values.
    - `401 unauthenticated` (token revoked, app suspended or uninstalled, M2-24): end the job with an Error line; the endpoints answer `503` until `getMe` succeeds again, tried once per `sdk.retry_backoff_cap`.
    - `422 idempotency_key_reuse`: Error line (the same identifier with another body is a programming fault), end the job.
    - `429 rate_limited` and `503 unavailable`: retried by the SDK, then Design note 9. Unknown codes are classified by status through the SDK's `ProblemError` classes.

15. **Jira REST client** (`jira/client.py`, `jira/adf.py`; Ruling for docs/DECISIONS.md). Two calls on one `httpx.AsyncClient` with `follow_redirects=False` (a `3xx` is a failure) and the time limit `sdk.http_timeout`: `POST <jira_base_url>/rest/api/3/issue` with `{"fields": {"project": {"key": ...}, "issuetype": {"name": ...}, "summary": ..., "description": <ADF>}}`, and `POST <jira_base_url>/rest/api/3/issue/<issue id>/comment` with `{"body": <ADF>}`. Headers `Accept: application/json`, `Content-Type: application/json`, `Authorization: Basic <standard base64 of the credentials line>` and `User-Agent: jira-app/<VERSION>`. The response body is read only on `201`, for `id` and `key` of an issue (the key checked against the pattern of Design note 6) or `id` of a comment; errors carry the status only, never a body. ADF: one function builds `{"type": "doc", "version": 1, "content": [...]}` from `paragraph` nodes (one per line of a text, an empty line as a paragraph without content), `text` nodes (never empty) with the `code` mark only where Design note 13 says, and `codeBlock` nodes; text is never parsed as markup, so chat text cannot create a Jira mention, link or macro. Only Jira Cloud as cited in 11 10.2. The README names the REST version 3 pages for creating issues and comments, ADF and basic authentication with an API token, and says that the account needs only the permissions to browse, create issues and add comments in the configured projects.

16. **Logs** (SEC-LOG-2, SEC-LOG-4 and SEC-SEC-3 as the rule for this app). ## Acceptance criteria

- [ ] `X-Hub-Signature` with method `sha256` verifies with the test values; every other method answers `401` without any HMAC being computed, also when its digest is correct for that method or for SHA-256; wrong, missing and malformed signatures answer `401` and create nothing; the comparison goes only through `hmac.compare_digest` on the digests.
- [ ] `jira:issue_created`, `jira:issue_updated` and `comment_created` from the fixtures give one forum post per issue and messages in it as in M2-49; a new issue creates exactly one post; the mapping survives a restart and a changed key; an update without field changes adds nothing.
- [ ] `/issue` with the form creates exactly one issue through the Fake-Jira API and answers in the thread; failures follow Design note 12, never with a second issue.
- [ ] The app's own messages are never mirrored back; mirrored human replies and the app's own issues and comments do not come back; Jira text never becomes a mention or link in the chat, and chat text reaches Jira only as ADF text.
- [ ] The manifest requests exactly the scopes of 11 10.1 (through 10.2); `installApp` refuses an installation without one of the required scopes; a missing scope at call time gives `403 scope_missing`, logged once and not retried.
- [ ] `bothy_sdk.webhooks` verifies every signature case of `docs/api/webhook-test-vectors.json`, and the app verifies the server's requests only through it.
- [ ] No test calls a real Jira service.
- [ ] The app passes its live test against the real server inside `make check` (`tests/live/test_live.py` in the default pytest run).
- [ ] The Python license gate and OSV pass without a change to the allowlist; ruff `D` fails on an undocumented public function of the app.
- [ ] 11 10.2, 11.2 and 16, `configuration.md`, `webhooks.md`, the threat model, `plugins/README.md`, the READMEs and CHANGELOGs of the app and the SDK, the root CHANGELOG and `docs/DECISIONS.md` describe what was built.
