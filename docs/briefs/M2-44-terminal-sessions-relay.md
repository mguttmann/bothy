# M2-44: Terminal sessions, session token and relay

Status: ready | Depends on: M2-43 | Milestone: M2

## Goal

After this ticket a person opens, attaches to, lists, reads and closes terminal sessions on a paired, connected host, and the server relays the end-to-end encrypted stream between the device and the host service without reading it. `openTerminalSession` and `attachTerminalSession` run `authorize` with SR10, SR11 (I6), SR12, the fresh step-up and the host and profile checks, consume the step-up in the same transaction, write the `terminal_sessions` row, the audit entry and `terminal_session.changed`, and return a one-time session token: a compact JWS after ADR 0067 with `typ = terminal-session+jwt`, signed with the server key of purpose `terminal`, carrying exactly the claims of 24 "Terminal session token", with `osu` taken from the person's own session user assignment (`terminal_sessions.host_session_user_id`) and `wdi` counted only in the person's own reported working directory list. The server then sends `session.open` over the control connection of M2-43, the host service opens its data connection `/api/v1/hosts/sessions/{session_id}/stream`, the device opens `/api/v1/terminal/sessions/{session_id}/stream`, and the relay of one node pairs both in memory and forwards every binary frame unchanged, recording only length, time and session ID. Full buffers close the slow end with `4014`, a missing counterpart after `terminal.open_timeout` ends the opening with `open_failed`, a newer device closes the older one with `4103`, text frames after `identify` close with `4002`, and every end of a session, whoever causes it, closes both connections. This is the server half of R-TM-02, R-TM-07 and R-TM-09 (24 "Decisions of this chapter") and of the scenarios TM-T07 and TM-T12 (each without the console part: PLAN row (D-W-105); the console part is M6-18's) and TM-T29 (g) (server part); the host side of the handshake is M2-45, revocation, limits and the remaining metrics M2-46, several nodes M2-47.

Product requirements implemented here:

11. `openTerminalSession` runs `authorize(person, terminal.open, host)` with the right `terminal`, SR10, SR11, SR12, the fresh and unconsumed step-up, host `active` and connected, the profile known and, for a profile of kind `claude`, a working directory of the own session user; on `allow` it consumes the step-up, inserts the `terminal_sessions` row in `opening` with the person's session user, writes the audit entry and `terminal_session.changed` in one transaction and answers `201` with `TerminalSessionGrant` (24 6.1 steps 1 to 3, 05 4.14, 08 6.3).
12. The session token is a compact JWS after ADR 0067 with the header `alg = EdDSA`, `kid`, `typ = terminal-session+jwt`, signed with the `active` server key of purpose `terminal`, valid `terminal.session_token_ttl`, with exactly the claims of 24 5.3: `iss`, `aud`, `sub`, `sid`, `jti`, `iat`, `exp`, `dev`, `prf`, `cek`, `own`, `osu`, `wdi` (only for a profile of kind `claude` and `att = open`), `att`. Every grant has a new `jti`, stored in `terminal_sessions.token_jti`; older tokens of the session are worthless (24 6.2, D-T33).
13. `osu` is `host_session_users.os_user` of `terminal_sessions.host_session_user_id`, the person's own valid assignment at opening, for every token of the session; it never comes from the request (24 2.2 point 3, R-DM-40, D-W-66).
14. A valid assignment whose name the host does not report gives `403 terminal_denied` with `reason: no_session_user` at opening, not a token that the host refuses with `4104` (SR12, D-W-63, R-TM-23, TM-T28 (e) server part).
15. `workdir_index` counts only in the `workdirs` list of the caller's own entry in `hosts.reported_session_users`; any other index gives `403 terminal_denied` with `reason: profile_unknown`, and a valid index stands as `wdi` in the token (24 11.1, D-W-62, D-W-69, TM-T29 (g) server part).
16. `attachTerminalSession` needs a fresh step-up, except from the same device in the same login session within `terminal.quick_reattach_window` after the disconnect, never in the console; it issues a new token, and the connection of an older device is closed with `4103` (24 6.2, 08 6.3 point 5, R-TM-07, TM-T12).
17. TM-T07 without the console part: `terminal.open` without step-up, with a step-up older than `terminal.step_up_max_age` and with an already consumed step-up gives `401 step_up_required`; of two concurrent openings with one step-up exactly one succeeds.
18. The server sends `session.open` (`HostSessionOpen`) only over a control connection that has delivered its `report` (24 2.2 point 5, M2-43 `ControlLinks.OpenSession`); the host service answers each `session.open` with one data connection (24 6.1 step 4).
19. The relay pairs the device stream and the host data connection of a session in the memory of one node and forwards every binary frame unchanged, one WebSocket binary message carrying exactly one Noise message of at most 65535 bytes; it records only length, time and session ID (SEC-TERM-1, 24 5.2, 5.4, 9 point 3).
20. A text frame after `identify` closes that connection with `4002`; a full relay buffer (`terminal.relay_buffer_max_bytes` per direction) closes the slow end with `4014` and the session becomes `detached`; a counterpart missing after `terminal.open_timeout` ends an opening session with `open_failed` (24 5.4, 6.1 step 6, 6.3).
21. The device stream sends `hello` with the server DPoP nonce and accepts only `identify` with an access token and a DPoP proof (`htm = GET`, `htu` the HTTPS form of the stream URL, `nonce` from `hello`, `ath`) of the device of the current session token (`terminal.stream`, Audit `denials`) (asyncapi `terminalStream`, 05 7).
22. `listTerminalSessions` and `getTerminalSession` show the person's own sessions, owners all, metadata only; `closeTerminalSession` closes an own session (`client_closed`) or, for an owner, any session (`closed_by_owner`) (05 `terminal.read_own`, `terminal.close`, 24 10.3).
23. Every end of a session, by the person, an owner, the host service, the server or another module's transaction, closes the device stream and the data connection (`4100` with the `close_reason`, or the code of 24 5.3 for a refused handshake) and tells the host service with `session.close` (24 8.3, 13).
24. `terminal_session.changed` goes only to the person of the session, at every state change, with the payload `TerminalSession`, never content (05 6, 24 10.2).
25. Audit after 24 10.1: `terminal.open` and `terminal.attach` with `host_id`, `session_id`, `profile`, `device_id`, `pin_changed`, `foreign_assignee`; `terminal.close` with `session_id` and who closed; `terminal.stream` denials with `session_id`, `device_id` and the reason code; `terminal.terminate` for every end by the server or the host with `session_id`, `close_reason`, `close_detail`, `bytes_in`, `bytes_out` and the duration. Never terminal content, commands, environment, paths or tokens (R-TM-10, SEC-LOG-2). No JSON `null` anywhere (ADR 0053).

7. **Relay model** (`domain/relay.go` decides, `wsrelay/relay.go` executes). Ruling for docs/DECISIONS.md: one data connection per grant. Every grant creates or replaces the slot of its session with an expectation `{session, host, device, deadline = grant time plus terminal.open_timeout, started, workdir index of an opening of a claude profile}` and one `session.open`; the host service opens exactly one data connection per `session.open`; the relay pairs the device side of the expected device with that host side. A new handshake therefore always runs on a fresh pair of connections, and the host service never has to tell a new handshake message 1 from transport data. 24 6.2 ("rebuilds the data connection after reconnecting") changes to "reopens the data connection as soon as the device attaches (`session.open`)".
    - Frames: each WebSocket binary message is read whole and forwarded as one binary message, never merged, split or altered; a message above 65535 bytes closes its side with `4002` (set the library read limit above it and enforce the limit in `frames.go`, so the code is `4002`, not `1009`). Until the other side is there, frames wait in the queue of their direction.
    - Queues: one per direction, bounded by `terminal.relay_buffer_max_bytes` in bytes of queued messages; a message that does not fit closes the side that does not read (the receiver) with `4014`.
    - Counting: per pairing the first message of each direction is the handshake (message 1 from the device, message 2 from the host); every later message adds its length to `bytes_in` (from the device) or `bytes_out` (to the device), and every later device message sets the in-memory time of the last device frame. When a pairing ends for any other reason than the end of its session, the relay writes its counts into the row (`bytes_in`, `bytes_out` added, `last_input_at`), one update without event or `version`. Ruling for docs/DECISIONS.md: handshake messages are not transport bytes (03 "bytes of the transport messages"), and counters are metadata written without an event.
    - Deadlines through the `Timers` port (`AfterFunc(d time.Duration, f func()) (stop func() bool)`, real in `wsrelay`, a fake driven by the fake clock in the tests; reuse M2-43's if it has one). The deadline of a slot is met by `session.started` (M2-43's use case, after which `wsrelay` tells the relay) for a session that never started and by the pairing for a started session. Ruling for docs/DECISIONS.md: the server cannot see the handshake, so "the handshake is complete" (24 17) means `session.started` before the PTY runs and the pairing afterwards. Ruling for docs/DECISIONS.md, stated identically in M2-45 Design note 15 d: on a host whose last `report` says `require_local_confirm = true` (`hosts.reported_require_local_confirm`), the server deadline of an opening (grant time plus `terminal.open_timeout`) is met by the pairing of both sides, not by `session.started`, because the consent window `host_service.local_confirm_timeout` (24 6.4) may be longer than `terminal.open_timeout`; the host service bounds the rest itself: `start` until `HostSessionOpen.expires_at`, the consent within `host_service.local_confirm_timeout`, and it ends a refused or unanswered opening with `session.ended` `open_failed` (`open_timeout` or `local_confirm_denied`). When such a pairing ends before `session.started`, the slot gets a new deadline of `terminal.open_timeout` from that moment.
    - Reactions (the pure table of `Decide`; state changes through `app`, using M2-43's transitions `opening -> active` and `active -> detached` and their reverse for a re-paired started session):

        | Event | Device side | Host side | Session |
        |---|---|---|---|

## Acceptance criteria

- [ ] `openTerminalSession`, `attachTerminalSession`, `listTerminalSessions`, `getTerminalSession` and `closeTerminalSession` are enabled; both upgrade routes and their channel ops are registered; AZ-P1 and AZ-P2 pass.
- [ ] The session token has the header `alg = EdDSA`, `kid`, `typ = terminal-session+jwt`, is signed with the `active` key of purpose `terminal` and carries exactly the claims of 24 "Terminal session token" (schema test green); every grant has a new `jti` stored as `token_jti`; the token appears in no log, event, audit entry or error.
- [ ] `osu` comes only from the person's assignment (`terminal_sessions.host_session_user_id`); an assignment with a name the host does not report gives `403 terminal_denied` with `reason: no_session_user` and never a `4104`.
- [ ] TM-T29 (g) server part: a `workdir_index` outside the caller's own reported list gives `403 terminal_denied` with `reason: profile_unknown`; a valid index stands as `wdi` in the token.
- [ ] TM-T07 without the console part: no step-up, a too old one and a consumed one give `401 step_up_required`; of two concurrent openings with one step-up exactly one succeeds.
- [ ] TM-T12 without the console part: another device without step-up `401`, the same device within `terminal.quick_reattach_window` allowed without consuming, after it `401`.
- [ ] `pin_changed` and `foreign_assignee` are in the audit entries of `terminal.open` and `terminal.attach`.
- [ ] The relay forwards binary frames unchanged and records only length, time and session ID; full buffers close the slow end with `4014`; a missing counterpart after `terminal.open_timeout` ends the opening with `open_failed` (on a host that reports `require_local_confirm`, the pairing meets that deadline); a second device closes the older one with `4103`; text frames after `identify` give `4002`.
- [ ] The host's refusal codes `4101` and `4104` reach the device exactly once, and an opening without a PTY ends with the host's `close_detail`.
- [ ] Every end of a session, also from M2-39's and M2-43's paths, closes the device stream and the data connection and sends `session.close`; a revocation between decision and commit ends the new session at once.
- [ ] `terminal_session.changed` reaches only the person of the session at every state change and validates against its schema; no JSON `null`.
- [ ] The changes to 24, 02, `openapi.yaml`, `asyncapi.yaml`, signals.md 5.3 and the collector allowlist of the Scope are made in the same change, and the rulings are recorded.
