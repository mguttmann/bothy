# M2-48: Conformance and chaos suite of the terminal

Status: ready | Depends on: M1-72, M1-73, M2-24, M2-46, M2-47 | Milestone: M2
## Goal

After this ticket the tests of 24 "Tests" run data driven against the real parts of the terminal, and they keep running in every `make check`. A catalogue `services/server/test/terminal/catalogue.yaml` names, for every ID TM-T01 to TM-T29 and for AZ-M54 to AZ-M61, ID-T28 and SEC-T05, where it runs and which ticket implemented it. The end-to-end suite under `services/server/test/terminal` starts the installation Compose file `infra/compose/compose.yaml` unchanged, with M1-73's smoke overlay and the new test overlay `infra/compose/test/compose.terminal.yaml` (for the two-node profile also M2-47's overlay and the test overlay `infra/compose/test/compose.terminal-twonode.yaml`): the server image built from the worktree with `services/server/Dockerfile` for the platform of the Docker host, PostgreSQL, the worker, the collector with its file export and a test-only TLS front for the instance origin; real host services `bothy-host` in Linux containers with systemd, installed with `bothy-host install`, paired with `bothy-host pair` and confirmed through `confirmHost`; and a Go test device that enrols with device keys and DPoP, confirms step-ups with its device key, opens and attaches sessions and speaks Noise through the host service's own `internal/noise` and `internal/frame`. TM-T15 runs on M2-47's two-node overlay behind its example edge; TM-T16 runs once per `make check` and again under load in `make perf` (`services/server/test/chaos`). The host-local platform suite of M2-42 and M2-45 (`services/host/test/platform`: the `doctor` matrix of exit criterion 8, the PTY and process tree tests, TM-T13 and the platform-only parts of TM-T22, TM-T24, TM-T28 and TM-T29) runs in a Linux container inside every `make check` and on disposable macOS, Windows 10 and Windows 11 machines that the launcher names; the report lists every platform run. A docs gate keeps chapter 24 "Tests", the catalogue, exit criterion 8 and threat model section 6.7 together, so every terminal threat names a test that exists. Why: M2-38 to M2-47 proved the terminal module by module with fakes; this suite proves the whole path at once (device, TLS edge, relay, host service, PTY, rights, revocation, limits, two nodes, restarts) and is the evidence that M2 exit criterion 8, the terminal points of the M2 red team and RK-23 ask for. It adds no product behaviour; a non-conformance it finds is fixed in the owning module (Design note 13).

## Fixed requirements that apply

Owner's fixed build rules (apply verbatim):

1. No MVP. New from scratch and directly in the final state; stages are only the order.
2. Strictly modular: clear module and service boundaries, dependencies only through defined
   interfaces, no cross access.
3. Documentation in code: every public module, class, function and interface with a docstring/doc
   comment (purpose, parameters, return value, errors, example where useful); comments explain the
   why, not the what. API documentation is generated from code (OpenAPI from the routes, dartdoc,
   Python API docs in MkDocs).
4. Documentation in the repo: README per module/service, ADR for every architecture decision,
   CHANGELOG per release, keep the documentation site current. A change without matching
   documentation is not done.
5. Quality gates (SonarQube, linters, type checking, security scanners, test coverage) block the
   merge.

Rules for every brief:

6. Test first: write the failing test, run it and keep the red output for the report, then make it green, then clean up.
7. No en dash and no em dash in any file you write; the `text-rules` pre-commit hook rejects them. Use a hyphen or rephrase.
8. White label: examples and test data use `example.com` and the people Alex, Sam and Robin; no company, host or personal names, no paths under a home directory. Host names and session user names in tests are neutral (`r1`, `r2`, `r3`, `r5`, `term-alex`, `term-sam`, `term-robin`, `term-owner`), the instance origin is `https://chat.example.com:8443`, and the product name appears only at the places of 02 "Code layout" ("Places that carry the product name"); suite names start with `termsuite`.
9. Limits, windows and thresholds only through named configuration keys listed in `docs/operations/configuration.md`; code comments and docs name the key, never the number. The short windows of the test stack live only in `services/server/test/terminal/profiles.yaml`, keyed by those names (Design note 4); bounds that only limit how long a test polls are test constants, not product limits. This ticket adds no configuration key.
10. Specification first: a change to behaviour, API, event, right or configuration updates `docs/spec/` or `docs/api/` in the same change. The core contract (`docs/spec/00-glossary.md`, `03-data-model.md`, `04-sync-protocol.md`, `05-actions.md`) is not edited by this ticket.
