# Computer use: where the time goes and how to make it faster

Status: research and design note of 2026-11-28, written for the owner. Nothing here is built and
no production code changed. It measures the computer-use path of [chapter 27](../spec/27-computer-use.md)
(`bothy-computer-mcp`, the host service, the helpers) and ranks the levers that make an agent
operate a desktop faster: quick to click and quick to think, like a person. The scope is every kind
of operation on a desktop (any website, a terminal, graphics programs, mail and chat apps such as a
mail client's rules dialog, games), not only the browser; the shopping-site run below is just the
measured example.

All figures are dated measurements of 2026-11-28, with their source named. None of them is a
contract that a test holds; re-measure before relying on one.

## 1. Goal and what was ruled out

Goal: shorten the wall time from an owner's order to the result of a computer-use step, on macOS
and Windows, for every app class, without lowering the protection of chapter 27.

Done-criterion of this note: the time of a real run split into its parts with sources, each lever
rated with evidence (gain, effort, risk, which app classes it helps), the free local measurements
done, and a decision sheet for everything that needs money or an API key.

Ruled out by the brief: no session on the owner's desktops for this note, no paid API call, no
change to production code, no restart.

## 2. Measured runs

Two runs of 2026-11-28 with the MCP build that was live that day (an older build of 2026-11-26).
Both used Claude Opus 5.5 at the runner's effort. Times come from the timestamps of the run
transcripts (one `api-request` entry when a model request starts, the assistant entry when its last
block arrived, the `tool_result` entry when a tool answered). The server log of the same minutes
shows only the REST calls of `list_desktops` (7 to 11 ms) and `open_session` (18 to 30 ms); the
action frames travel end-to-end encrypted, so the server logs no timing per action. The host logs

### 2.3 The host path in detail

- A plain `screenshot` on the Windows desktop took 0.27 s and 0.13 s end to end (MCP, server relay,
  host, helper capture and JPEG encode, back). A `batch` with only `wait 3000` took 3.16 s, so
  0.16 s beyond the wait.
- A `batch` of click plus `wait 2500` took 3.31 s (macOS) and 3.28 s (Windows): about 0.8 s beyond
  the wait. That matches the old build: every item waited `computer.settle` (500 ms, a fixed sleep,
  `services/host/internal/computer/actions.go`) and returned an image, so the click cost 0.5 s
  settle plus a capture, and the wait one more capture.
- The 7-item batch on macOS spent 3.5 s beyond its waits: five input items with 500 ms settle and a
  capture each.
- Typing is not slow: the macOS helper posts text in chunks of 16 UTF-16 units without a delay
  (`MacInjector.swift`), the Windows helper sends one `SendInput` call per action.

The build the runner loads from 2026-11-29 08:30 (main at 7e447724e) already removes most of the
host share: batch items before the last go with `quick` (50 ms pause, no image, chapter 27 6.4),
and `open_session` returns the first screenshot. Estimated from the parts above, the same macOS run
would take about 16 s (batch 1 about 5.2 s instead of 7.99 s, batch 2 about 2.7 s instead of 3.31 s)
and the Windows run about 15.6 s. This is an estimate; the first runs after the update measure it.

### 2.4 The model round

A fit over all 125 model rounds of the two transcripts (seconds against output tokens, r = 0.93)
gives a fixed part of 2.3 s per round and 6.3 ms per output token (about 160 tokens per second).
Computer-use rounds write 80 to 310 tokens, so 0.5 to 2 s of each round is output and about 2.3 s is
the fixed part (time to first token, the prompt read from the cache, the network). Grouped by
context size (63 Opus rounds under 400 output tokens from the runner transcripts since 2026-11-27),
the fixed part stayed between 1.6 and 1.9 s from 80k to more than 300k tokens of context; runs with
a small context were not in the data, so whether a small context helps is not measured.

### 2.5 Where the time goes

After the update, the two big parts are left: **the number of model rounds** (about 2.5 to 3.7 s
each, 3 to 4 per simple task) and **fixed waits that the model guesses** (2.5 to 3 s per page
change). The host path, encoding and transfer are a small part (section 4).

## 3. Free local measurements

All on the build machine, without a session on a desktop and without a paid call. The scripts are
in the appendix.

### 3.1 MCP, Noise and WebSocket path

The fake host of `computermcp` (`fake_test.go`) answers every action at once; a temporary test
drove 40 `batch` calls per image size through the real stdio MCP server, the Noise transport and
the WebSocket framing.

| Image | `open_session` | `batch`, 1 item | `batch`, 5 items |
| --- | --- | --- | --- |
| 15 kB | 42.8 ms | 0.25 ms | 0.58 ms |
| 100 kB | 43.1 ms | 0.93 ms | 1.29 ms |
| 220 kB | 43.9 ms | 2.06 ms | 2.48 ms |
| 400 kB | 45.5 ms | 3.52 ms | 4.14 ms |

`open_session` includes the 20 ms poll of the runner request file. The local path costs about 2 ms
per real-size screenshot; the 0.13 to 0.27 s of a real screenshot is the network relay plus the
capture on the desktop. Not a lever.

### 3.2 Image size and encoding

ImageIO (the encoder of the macOS helper) on four real screenshots of the day (decoded and
re-encoded, so already JPEG once) and two local renders: a native dialog in the style of a mail
rules wizard (52 accessible elements) and a terminal with 24 lines of real command output.
Visual tokens by the API rule `ceil(w/28) * ceil(h/28)` (vision docs).

| Screen | Size | JPEG q80 | q60 | q40 | PNG | Encode q80 | Tokens |
| --- | --- | --- | --- | --- | --- | --- | --- |
| browser, results (macOS) | 1280x831 | 214 kB | 152 kB | 106 kB | 637 kB | 5.6 ms | 1380 |
| browser, product (macOS) | 1280x831 | 244 kB | 172 kB | 119 kB | 736 kB | 7.4 ms | 1380 |
| browser, results (Windows) | 1280x720 | 186 kB | 143 kB | 104 kB | 490 kB | 4.1 ms | 1196 |
| game, full screen (Windows) | 1280x720 | 140 kB | 105 kB | 73 kB | 842 kB | 4.1 ms | 1196 |
| native dialog (render) | 1280x800 | 137 kB | 106 kB | 74 kB | 167 kB | 2.1 ms | 1334 |
| terminal (render) | 1280x800 | 188 kB | 144 kB | 102 kB | 183 kB | 2.2 ms | 1334 |
| browser, results (macOS) | 1024x665 | 153 kB | 108 kB | 70 kB | | 2.2 ms | 888 |
| browser, results (macOS) | 768x499 | 97 kB | 69 kB | 44 kB | | 1.4 ms | 504 |

Findings: encoding costs 2 to 10 ms, PNG 20 to 38 ms at three to six times the size, so JPEG for
screenshots is right. 1024 px instead of 1280 px saves 36 % of the visual tokens and about 30 % of
the bytes, but neither is a time lever here: 200 kB cross the local path in 2 ms, and the image is
1.2k to 1.4k uncached tokens in a round whose fixed part is 2.3 s. Size is a cost and legibility
choice. The vision docs advise 1080p as the balance and 720p or 1366x768 as the cheaper option for
computer use, and warn that heavy JPEG compression hurts small text.

### 3.3 Change detection for an adaptive wait

Two real 1280x831 frames reduced to 160x104 gray and compared cell by cell: 3.8 ms per pair on the
CPU. Polling every 100 to 150 ms costs a few percent of one core. Both platforms also report change
natively: Desktop Duplication on Windows (`AcquireNextFrame` returns only when the screen changed;
the helper uses it, but builds a new duplication per capture, `capturer.cpp`) and ScreenCaptureKit
streams on macOS (frame status idle when nothing changed; the helper takes one-shot screenshots and
asks `SCShareableContent` per capture, `MacCapturer.swift`).

### 3.4 Accessibility text next to the image (non-browser scenario)

The accessibility tree of the local dialog render (read through the NSAccessibility protocol, the
same data AX serves to another process) took 3.5 ms and 2647 bytes for 52 elements, one line each
with role, name, value or state and the center point, for example
`CheckBox "with specific words in the subject" =1 @310,775`. At an estimate of 3 to 4 characters
per token (not counted with the API) that is 700 to 900 tokens against 1334 visual tokens for the
same screen, and it carries what an image does not: exact click points and checkbox states. The
terminal screen is 1890 bytes of text against 1334 visual tokens. A real mail client or chat app
has many more nodes (a tree with hundreds or thousands of elements is common); a filter to visible,
interactive elements is needed. Not measured: a real AX or UIA dump of such an app, because the
build machine grants no accessibility right to a script and no desktop session was allowed.

## 4. Levers

Rated by expected gain per task of the measured kind (3 to 4 rounds, 2 page changes), effort, risk
and the app classes they help: B browser, N native apps (mail client, chat app on a web engine,
settings), T terminal, G graphics programs with a canvas and no accessibility, S games and full
screen video.

| # | Lever | Gain | Effort | Risk | Helps |
| --- | --- | --- | --- | --- | --- |
| 1 | Adaptive wait: `wait` and `settle` end when the screen is stable | 2 to 4 s per task (most of 5 to 7 s of guessed waits; real load time not yet measured) | medium | low with a cap | B, N, T, G; S falls back to the cap |
| 2 | Accessibility text (AX on macOS, UIA on Windows) next to the image | fewer rounds in forms and dialogs, 2.5 to 3.7 s per round saved; also fewer zoom and check rounds | high | medium | N, B (web engines expose a tree), T partly; not G, S |
| 3 | Larger batches up to the next decision, keyboard paths, a URL with the query | 1 round (2.5 to 3.7 s) where the model splits steps it could chain | low (tool texts and runner prompt) | low | all |
| 4 | Persistent capture on the desktop (stream inside the host, not to the model) | 0.1 to 0.2 s per image, and the base for lever 1 | medium | low | all |
| 5 | Smaller model or fast mode for simple steps | fast mode: at most 0.3 to 1.2 s per round (only output speed); smaller model: unknown, needs a paid measurement | low to high | quality, cost, owner rules | all |
| 6 | Smaller or cropped images | none for time; 36 % fewer image tokens at 1024 px | low | legibility of small text | B, N |
| 7 | Streaming the screen to the model | none: not possible (section 5) | | | |

### 4.1 Adaptive wait (lever 1)

What: a `wait` that ends as soon as the screen has not changed for a quiet time (for example 300 ms)
or the duration is reached, and the automatic `settle` after the last batch item done the same way
with a short floor. The model then asks for "up to 5 s" instead of guessing 2.5 s, and fast pages
return early. Chapter 27 6.4 and the tool texts change; the helper gets a change probe (a thumbnail
compare or the native change signal, section 3.3).

Evidence: 7.0 s of 19.5 s (macOS) and 5.0 s of 17.8 s (Windows) were guessed waits, which the update
of 2026-11-29 does not touch. How much of a guessed wait was really needed is unknown: the first
step is a shadow measurement in the host (log when the screen became stable, change nothing).

Risks: animated content (carousels, spinners, video, a blinking cursor) never settles, so a change
threshold that ignores small regions and the cap are needed; a game or a video always runs to the
cap, which is no worse than today. A page that is stable before its content arrives (blank while a
request runs) can end the wait early; the quiet time and a minimum against a blank frame cover
that, and the model still sees the image.

### 4.2 Accessibility text next to the image (lever 2)

What: with each image, a compact list of the visible interactive elements of the frontmost window
(role, name, state or value, center point in screenshot coordinates), and optionally an action
that targets an element by its line instead of a coordinate. The image stays the ground truth.

Why it saves time: in a form or dialog (a mail client's rules wizard, settings, a file dialog) the
model knows every target and state from the text, so it can put several clicks and fields in one
batch without a fresh image in between, and it needs no zoom to read a small label. Every round
saved is 2.5 to 3.7 s.

Permissions: the macOS helper already holds the accessibility right (chapter 27 section 9), which
covers reading AX; the Windows helper runs with `uiAccess` and can read UIA. No new right is needed.

Risks and costs: the text is screen content, so it is covered by the same rules as a screenshot
(end-to-end encrypted, never on the server, removed with the run; secure text fields masked by the
platform and checked). Large trees on web-engine apps need a filter and a size cap. Canvas apps
(graphics programs, games, remote desktops) expose little or nothing, so they keep the image path.
For the browser, the page structure through the browser's own accessibility tree (seen through
AX or UIA) is enough; a DevTools path would only be an extra for the browser and is not proposed.

Terminal: the host already has a PTY path for terminal sessions (chapter 24), but the runner has no
tool on it for a remote desktop; a text tool for a terminal would be faster and more exact than any
screenshot, as a separate topic with its own security review.

### 4.3 Larger batches and keyboard paths (lever 3)

The macOS run already chained seven items into one batch, and putting the search query in the URL
saved the search page. What is left is guidance in the tool descriptions and the runner prompt: put
every step until the next real decision into one batch, prefer keyboard shortcuts (address bar,
search, tab, menus) over click and look, and use the adaptive wait of lever 1 as the last item.
Cheap; the gain shows in the round count of the next runs.

### 4.4 Model choice and output speed (lever 5)

- A round is mostly its fixed part (2.3 s) plus 0.5 to 2 s output. Fast mode on Claude Opus 5.5
  raises output tokens per second up to 2.5 times; the docs say it speeds up output, not time to
  first token. At 80 to 310 output tokens per round that saves at most 0.3 to 1.2 s per round, at
  twice the token price on the API ($8 / $40 per million tokens instead of $4 / $20). Whether the
  runner's Claude Code can use it on its current access is not checked.
- A smaller model as an extra image reader adds a round (its own time to first token) instead of
  removing one, so it is slower unless it replaces the main model for whole stretches of simple
  steps. The comparative latency in the model overview is "Moderate" for Opus 5.5, "Fast" for
  Sonnet 5.5 and "Fastest" for Haiku 5.5, without numbers. Replacing the main model for computer-use
  stretches (a computer-use sub-agent on Sonnet 5.5 or Haiku 5.5) is an owner decision (section 6)
  and needs a paid measurement of speed and click accuracy on real screens.
- The docs note that Opus 5.5 reads screenshots and multistep computer use more reliably at its
  default effort than its predecessor at a higher effort; a lower effort for computer-use rounds
  would shorten the thinking part and is an owner decision as well.

## 5. Streaming the screen

Checked at the source: the vision docs list JPEG, PNG, GIF and WebP as image inputs, say animations
are unsupported and only the first frame is used, and the model overview says every current model
takes text and image input. There is no video input, and an MCP tool result reaches the model as
an image block. So the model cannot watch a stream; every look stays one image per round.

Streaming makes sense inside the host: a persistent capture (ScreenCaptureKit stream, a kept
Desktop Duplication) keeps a fresh frame ready (saves the per-capture setup, 0.1 to 0.2 s at most
by section 2.3) and gives the change signal for the adaptive wait. That is lever 4, the base of
lever 1, not a lever of its own size.

## 6. Recommendation

1. **Measure first, free.** Re-run the measured task after the update of 2026-11-29 and split it
   with the method of section 2. Add a shadow log to the host: for each `wait` and `settle`, when
   the screen became stable. That gives the real gain of lever 1 before it is built.
2. **Build the adaptive wait (lever 1)** with the change probe of the helpers (lever 4 where it is
   cheap): the largest gain without touching the model, for every app class.
3. **Tune tool texts and the runner prompt (lever 3)** in the same change: whole batches up to the
   next decision, keyboard paths, the adaptive wait as the last item.
4. **Design the accessibility text (lever 2)** as its own ticket with a security review: the main
   gain for native apps, forms and dialogs, where pure screenshots need the most rounds.
5. Do not change image size, encoding or the relay for speed; do not stream to the model.
6. Model choice and fast mode only after the decision sheet below.

## 7. Decision sheet (needs the owner)

| Question | Cost | What it proves | What can go wrong | Recommendation |
| --- | --- | --- | --- | --- |
| A paid replay: about 20 recorded computer-use steps (image plus the prompt of the step) through Opus 5.5, Sonnet 5.5 and Haiku 5.5, three times each, with an API key | 60 calls per model (180 in all) of about 7k input and 300 output tokens: roughly $2 for Opus, $1 for Sonnet, under $0.10 for Haiku at list prices; under $5 in total even if thinking doubles the output | time to first token and total time per model on our real images, and whether the smaller models click the same targets | screenshots of the owner's screens go to the API under the key's retention rules; use synthetic or owner-approved screens only | yes, with synthetic screens (renders like section 3.2), once lever 1 is in, so the model share is measured on the new baseline |

| Fast mode for the runner | twice the token price on the API | at most 0.3 to 1.2 s per round | cost, separate rate limit, cache misses when switching speed | no for now: small gain against the guessed waits |
| A lower effort for computer-use rounds | none | shorter thinking per round | conflicts with the standing effort rule; more wrong steps | test only together with the replay |

## Appendix: reproduction

Transcript split (Python, any run transcript of the runner): read every line as JSON; an entry of
type `api-request` starts a model round, the last `assistant` entry before the next `user` entry
ends it (its `usage.output_tokens` is the round's output), and the `tool_result` timestamps end the
tool calls. The fit of section 2.4 is an ordinary least squares fit of round seconds against output
tokens over all rounds under 120 s.

MCP path (section 3.1): a temporary test in `services/host/internal/computermcp`, not committed:

```go
func TestZZSpeedBench(t *testing.T) {
	for _, size := range []int{15000, 100000, 220000, 400000} {
		r := newRig(t)
		r.host.mu.Lock()
		r.host.script = func(a frame.Action) []frame.Frame {
			if a.Quick {
				return codeOnly(a, "ok")
			}
			return okImage(a, size, "jpeg")
		}
		r.host.mu.Unlock()
		r.initialize()
		r.open()
		// 40 times: time r.call("batch", ...) with 1 item and with 5 items, log the medians.
		r.stop()
	}
}
```

Image and accessibility measurements (sections 3.2 to 3.4): a Swift script with AppKit and ImageIO
that renders the dialog and the terminal offscreen (`cacheDisplay`), walks the dialog's
NSAccessibility children, resizes each image with a CGContext (high interpolation) to 1280, 1024
and 768 px on the long edge, encodes it with `CGImageDestination` at JPEG quality 80, 60 and 40
and as PNG (median of 7 runs), and compares two frames reduced to 160x104 gray (median of 50).
The screenshots used are private screen content and stay out of the repository.

Sources for the API facts: the vision, models overview and fast mode pages of the Claude developer
docs, read on 2026-11-28.
